Platform Agent Harness

Claude Code and Codex, wired so they keep what they learn.

Vaibhav Thakur · platform engineering

Why this exists

A chat starts from zero every time

Open a window, explain the situation, get an answer, close it. It works. But everything you taught it is gone: your cluster layout, the deploy quirk that cost you an afternoon, the reason a previous approach was abandoned.

So you explain it again next week. And the agent, starting clean, confidently re-derives a conclusion you already disproved.

  • Knowledge outlives the session and stays findable, or it may as well not exist.
  • Work splits across specialists without any one of them drowning in context.
  • Every change is checked by a second model that never saw the first one's conclusions.

This is a setup layer over tools that already exist, not a replacement for them. The accumulated knowledge happens to be Kubernetes platform work, because that is the work; the machinery underneath has nothing specific to it.

What's in the box

Eight specialists and a dispatcher

A main session holds the plan and hands work to specialists. Each is a role definition: a prompt, a set of references, and explicit criteria for what "done" means.

AgentOwns
task-plannerBreaks a project into tracked units, sets dependencies, maps each to a specialist. Plans; writes no code.
tool-researcherProduction readiness of a new tool: version, sizing, hardening, monitoring, fit with the stack.
helm-chart-engineerCharts and values. Renders across every cluster before claiming a change works.
argocd-manifest-engineerApplication and ApplicationSet manifests for GitOps delivery.
platform-engineerCI workflows, alert rules, dashboards, observability wiring.
alert-investigatorRead-only triage of a firing alert: cause, scope, impact. Mutates nothing.
pr-reviewerThe two-model review below. Runs on a different model from whoever wrote the code.
general-engineerAnything without a specialist: exploration, scoped research, independent validation.

The role is not tied to one vendor. The same definition runs as a Claude subagent or a Codex worker, and both write findings back to the same store. That is what makes a second opinion genuinely independent rather than the same model agreeing with itself.

Where knowledge lives

One store, two jobs

The memory layer is beads, a local issue store, doing two things that look unrelated and are deliberately the same system. It tracks work, as units with real dependencies between them, and it holds what was learned, keyed by domain, category and topic.

Keeping them together is what lets a finding from Tuesday's task surface while planning Thursday's.

env.sh
The single switch. One file names where work lives, which store to use, and which organisation is current. Everything else reads those values instead of hardcoding paths, so moving machine or employer is one edit.
references/
Portable knowledge. Numbered, curated files: method, and third-party behaviour cited at a pinned version. True anywhere, and it travels with you.
orgs/<org>/
Local knowledge. Cluster registry, account IDs, per-environment tables, house conventions. True only of one estate.
the store
Working memory. Fast to write mid-task, and the task graph itself. Periodically distilled into the two tiers above.
Making it findable

Built as an LLM wiki

Adapted from Karpathy's LLM Wiki: documentation written to be read by a model rather than a person, where retrieval is the design constraint instead of an afterthought. The practical test is whether an agent reads it before it starts grepping the repo. A pile of markdown notes never passes that test.

  • Entries are numbered and citable. An agent writes [learnings-argocd.md#42] and a later reader goes straight to it. Knowledge compounds instead of being silently rewritten.
  • The index is a catalogue of every file, with keyword and cross-reference columns, so an agent finds the right file without reading all of them.
  • The log is an append-only chronology, one entry per non-trivial task, currently around 160.

The index answers "where is this written down". The log answers "what happened, and when".

Search runs across all three at once, plus the working store, so one query covers both the durable and the recent. The failure this prevents is specific and was observed repeatedly before the search step existed: an agent re-derives a conclusion from scratch that was already recorded, sometimes from the same incident a day earlier.

How an agent knows any of this

One file is loaded at birth

A fresh agent starts with nothing. Nothing is injected automatically, and it cannot be told things mid-flight by a human who is not watching. So the bootstrap has to be one file, loaded at task start, whose first section tells it where everything else is.

That file is the shared protocol. Its opening is a checklist that every agent runs, including the main session.

  1. Read the shared protocol for workflow, constraints and completion rules, and the engineering standards file before writing any code.
  2. Read the index to discover what exists. Load every topic file whose domain overlaps the task. When uncertain, load it: a false positive costs less context than a missed lesson.
  3. Run the search across memories, curated files and docs with two or three keywords from the task. This catches matches that an exact keyword lookup would miss.
  4. Read the cluster registry for the active organisation, on effectively every task, because nearly all the work is cluster scoped.
  5. Drift check, main session only: stale graphs, store over threshold, distillation overdue. Surface warnings before starting work.

This is also why the protocol file, rather than the interactive helper library, is the home for anything load bearing. A specialist cannot invoke those helpers. If a rule has to reach one, it has to be in the files it reads at startup, and a rule that lives anywhere else does not exist as far as that agent is concerned.

How a project becomes work

Split by dependency, not by size

A project is decomposed into tracked units. What matters is which of them actually block each other, because that decides what can run at the same time.

Not everything becomes a tracked unit. A one-line fix, a quick question, a five-minute investigation: those are just done. Tracking them would be ceremony.

But if one of them teaches something, a flag that behaves differently than documented, a failure mode with a non-obvious cause, that lands in the store anyway. The work goes untracked; the lesson does not. Most of what accumulates arrives this way rather than from planned projects.

Wide, repetitive work takes the other shape. The same playbook against twenty clusters is twenty independent units fanned out at once, capped at around ten concurrent workers. Running a dependent chain in parallel is the most common way this goes wrong.

Keeping knowledge true

A corpus nobody prunes becomes a corpus nobody trusts

Capture is cheap, so the store fills fast. A busy week adds a few hundred entries. Left alone it turns into a landfill: the same finding written three times by three sessions, notes about work that finished a month ago, and claims that a later measurement quietly disproved.

So it gets distilled. Each entry is sorted into one of three outcomes, and anything worth keeping is moved into one of the two durable tiers before it leaves the store.

RuleWhy
Write it, confirm it landed, then removeRemoval is irreversible and there is no history to recover from. Never delete on the strength of intending to write.
Full text archived before any removalOtherwise the discarded pile is unauditable. You cannot inspect what you threw away to judge whether it deserved it.
"Already covered" needs a citationOne pass judged 35 entries already captured elsewhere. An audit found 6 were, and 21 existed nowhere else.
Read frequency ranks, never prunesA rarely read file may hold the once-a-year gotcha that prevents an incident.

Cadence decides the cost. At around a hundred entries this is one agent and an hour. A backlog of seven hundred once took thirteen agents and most of a day. Growth is the system working, so the fix is running the pass more often rather than capturing less.

Why it scales

Context is the budget that runs out

Every agent has a finite window, and reading burns it faster than writing. Two decisions follow.

Specialists spend their own budget, not the main session's. A specialist reads the protocol files, searches prior art, greps the repo, queries live clusters, and returns a report. The tens of thousands of tokens of raw output die with it. Ten workers can read ten times what one session could afford.

Memory is searched, never loaded. Injecting the whole corpus into every agent sounds helpful and is the opposite. The preamble instead says: you have no memories loaded, here is how to fetch the ones your task needs.

Preamble per dispatchBytesRoughly
Corpus injected into every agent163,949~40k tokens, before reading anything
Replaced with "fetch what you need"2,175~0.5k tokens

Measured, and not the first time. An earlier estate reached 774 KB, about 193k tokens, injected into every worker. The detail that settles it: two entries already held a lesson that a later change then re-learned across three correction commits. The knowledge was there and went unused, because dumping all of it crowded out the context needed to read the file being edited. Auto-loading everything is why nothing gets used.

Two smaller savings compound quietly. Verbose read-only commands are rewritten before they run by rtk, compressing output by 60 to 90 percent; nobody has to remember, because it is a hook rather than a habit, and mutating or piped commands are never touched. Architecture questions go to a Graphify repo graph instead of linear file reads, which is worth roughly two orders of magnitude on "what calls this".

Scope

What this is not

  • Not a new agent. Claude Code and Codex are used as they ship. This is configuration, protocol and glue, which is why it survives their updates instead of breaking on them.
  • Not a documentation library. Every file is loaded by an agent in a real session, or it gets deleted. Prose nothing reads is the failure being avoided, not the product.
  • Not a benchmark claim. What is measured here is narrow: tokens spent per dispatch, entries promoted per pass, files read per week. No speedup multiplier, because that depends entirely on the work.
  • Not finished. About a fifth is enforced by code. The rest is prose an agent follows by choice, and the last section shows how unevenly that lands.
How work gets checked

Two models that never compare notes

Every non-trivial change gets two passes. The independence is the mechanism: the second model never sees the first one's findings, because a second opinion from the same model is not one.

Reviews lead with blocking findings only, one line each, naming the consequence, capped at five. Everything else folds away. Nothing is deleted; the reading path is just short enough that a human finishes it.

Roughly 2,100 lines of code against 9,000 lines of prose. The split is deliberate: a rule belongs in prose only if it is short enough to survive attention decay, and anything longer should become a count a script can check. The written-down half does not reliably fire. Measured reading in the first week of a new estate was two file reads and zero citations. When a documented rule keeps being broken, the fix is the enforcement point rather than the wording.
