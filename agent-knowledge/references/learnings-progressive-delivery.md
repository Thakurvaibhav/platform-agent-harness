# Progressive Delivery Learnings

Argo Rollouts + Gateway API plugin patterns, pitfalls, and ArgoCD integration. Numbered, append-only. **Update the existing entry — never duplicate.**

See also: `learnings-argocd.md`, `learnings-helm-ci.md`, `learnings-code-review.md`, `learnings-envoy-gateway.md`

## Gateway API plugin (`argoproj-labs/gatewayAPI`)

1. **`httpRouteSelector` does NOT support header-based routing.** The plugin hardcodes `UseHeaderRoutes: false` for routes discovered via `httpRouteSelector`. `setHeaderRoute` silently no-ops (returns success without patching the HTTPRoute). Selector-based discovery only supports weight management. For header-based canary, use explicit `httpRoutes` with `useHeaderRoutes: true`. Applies to all plugin versions since v0.7.0.

2. **`managedRoutes` is required for `setHeaderRoute`.** The Rollout spec must declare `trafficRouting.managedRoutes` listing every header route name used in `setHeaderRoute` steps. Without it: `InvalidSpec: missing field spec.strategy.canany.trafficRouting.managedRoutes`. The field path is `spec.strategy.canary.trafficRouting.managedRoutes`; `canany` in the historical error quotation above is a transcription typo.

3. **`setCanaryScale` requires `trafficRouting`.** Using `setCanaryScale` without `trafficRouting` causes `InvalidSpec: SetCanaryScale requires TrafficRouting to be set`. When traffic routing is disabled, use plain `setWeight` steps instead.

4. **Plugin v0.13.0 requires Gateway API v1.2+.** The refactored header routing uses the `name` field on HTTPRoute rules (introduced in Gateway API 1.2) instead of ConfigMap tracking. The ConfigMap is no longer needed and can be deleted.

5. **Plugin v0.13.0 `in-progress` label.** The plugin adds `rollouts.argoproj.io/gatewayapi-canary: in-progress` to HTTPRoutes during active canary and removes it when stable returns to 100%. Introduced in v0.9.0 for ArgoCD drift avoidance.

6. **Upstream chart renders empty `annotations:` on Services.** The argo-rollouts chart (2.40.9) unconditionally renders a bare `annotations:` key on Service templates. The API server normalizes this away, causing a perpetual ArgoCD OutOfSync diff. Fix: set `serviceAnnotations` with a real value (e.g. `app.kubernetes.io/managed-by: argo-rollouts-chart`).

## ArgoCD integration

7. **Per-Application `ignoreDifferences` with `select()` on plugin labels doesn't work.** The plugin adds the `in-progress` label AND modifies `.spec.rules`. If only `.spec.rules` is ignored (with `select()` on the label), ArgoCD sees the label itself as a diff and reverts the entire resource, removing both label and rules. Fix for per-app: ignore both the label (`jsonPointers: /metadata/labels/rollouts.argoproj.io~1gatewayapi-canary`) and rules (`jqPathExpressions: .spec.rules`). For production: use ArgoCD CM-level `resource.customizations.ignoreDifferences` which evaluates during normalization and handles this correctly. **Superseded by #61:** whole-list ignores can delete live rules under client-side apply; #25 and #59 cover static-label symmetry and phase-specific failures.

8. **Required `ignoreDifferences` for Rollout-managed resources.** Three resource types need ignore entries:
   - **Deployment** `/spec/replicas` (when using `workloadRef` with `scaleDown: onsuccess`)
   - **Service** `/spec/selector/rollouts-pod-template-hash` (Rollout controller adds hash to selector)
   - **HTTPRoute** `.spec.rules` + `/metadata/labels/rollouts.argoproj.io~1gatewayapi-canary` (plugin modifies rules and adds label during canary) **HTTPRoute guidance superseded by #61:** ignore specific managed rules/fields, not the entire list. If the chart renders Deployment `replicas: 0` while rollout is enabled (#20), a replicas ignore is unnecessary. Keep per-cluster overrides in values, not hardcoded application templates. A chart can expose `extraIgnoreDifferences` and `extraSyncOptions`, adding `RespectIgnoreDifferences=true` for non-empty ignores and allowing an explicit false override. Name-scope stable/canary Service selector ignores; for multi-service Applications, a shared static-label-scoped HTTPRoute ignore can cover future services without naming each route. The historical whole-list form is superseded by #61.

## Rollout patterns

9. **`workloadRef` is the correct approach for existing Deployments.** `workloadRef` with `scaleDown: onsuccess` is required when you want Deployment and Rollout to coexist during migration. The controller reads the Deployment's pod template, creates its own ReplicaSet, and scales the Deployment to 0 once stable. With inline template, the Rollout has NO relationship to the Deployment — it won't scale it down, resulting in 2x pods. Inline template only makes sense if you suppress the Deployment from rendering (hard cutover).

10. **Triggering a canary with `workloadRef`.** `kubectl argo rollouts restart` does NOT trigger a canary — it just cycles pods within the current revision. To trigger a canary, change the referenced Deployment's pod template (e.g. patch an annotation). The Rollout detects the template change and creates a new revision.

11. **Abort state is sticky.** After `kubectl argo rollouts abort`, the Rollout stays Degraded until a new spec change triggers a new revision. `retry`, `undo`, and `promote --full` do not reliably clear the abort state. Clean approach: remove overrides, let ArgoCD prune the Rollout, then re-enable for a fresh revision 1.

12. **Rollout template must guard on `deployment.enabled`.** Since `workloadRef` references the Deployment, the Rollout template must also check that the Deployment renders. Without this, enabling `rollout.enabled` with no Deployment produces a Rollout pointing at nothing. Exact component guard: `{{- if and $component.enabled (($component.rollout).enabled) $component.deployment (ne $component.deployment.enabled false) }}`; this also rejects `rollout.enabled: true` with `deployment.enabled: false`.

13. **Promotion modes + steps override pattern.** Three modes with escape hatch. If `rollout.steps` is non-empty, render those directly. Otherwise: **auto** = OMIT `steps` entirely, use `maxSurge`/`maxUnavailable` (true rolling update). **soak/manual with trafficRouting** = (1) `setCanaryScale: {replicas: max(3, ceil(replicas/4))}`, (2) `setHeaderRoute`, (3) pause (timed/indefinite), (4) `setCanaryScale: {matchTrafficWeight: true}`, (5) progressive weight ramp. Key insight: `steps: [{setWeight: 100}]` is instant cutover, NOT rolling update — omit steps entirely for true rolling. **Step-order correction from #28:** the first positive `setWeight` MUST precede `matchTrafficWeight: true`. `setCanaryScale: {replicas: N}` persists until that reset; forgetting it can leave one pod carrying the whole ramp. In this pattern, auto takes `maxSurge`/`maxUnavailable` from `$component.deployment.updateStrategy.rollingUpdate`; soak/manual without traffic routing uses only a 25/50/75/100 weight ramp. The example uses a warm-pod floor of 3 and `soakDuration: 3m` (12m over four stages).

14. **Values key naming: use `trafficRouting` not `httpRoute`.** The values key controlling Rollout's Gateway API traffic routing should be `rollout.trafficRouting.enabled`, NOT `rollout.httpRoute.enabled`. The latter sounds like it toggles HTTPRoute rendering; the former correctly describes what it does. Related keys: `trafficRouting.httpRoutes` lists route names; `rollout.managedRoutes` lists names used by `setHeaderRoute`.

15. **Deployment replicas stuck at 0 after rollout disable with `ignoreDifferences`.** When a Rollout uses `workloadRef` and `scaleDown: onsuccess`, disabling leaves the Deployment at `replicas: 0`. ArgoCD `ignoreDifferences` on `spec.replicas` prevents reconciliation. Fix: `kubectl scale` or temporarily remove ignoreDifferences; HPA will restore once Rollout is removed.

16. **Gateway API plugin `httpRoutes` entries must NOT include a `namespace` field.** The plugin discovers HTTPRoute resources by label selector, not namespace lookup. Including a `namespace` field causes route discovery failures. Use only `name` and `useHeaderRoutes: true`.

17. **Envoy Gateway returns hard 503 when no endpoints exist.** EG produces 503 with response flags NH/NC when a backend has zero ready endpoints. During canary rollouts, the Service backing the canary MUST always have ready endpoints for the duration of the traffic split. There is no fallback for an empty canary backend: its configured weight share receives 503s, including during experiments.

18. **Argo Rollouts Experiment CRD is single-shot with hours-format duration.** `spec.duration` accepts hours format (e.g., `120h` = 5 days). Experiments are SINGLE-SHOT — re-run requires a name change (use date suffix). Controller GCs the experiment's ReplicaSets on duration expiry. A reusable name shape is `exp-<ticket>-<yyyymmdd>`. The recorded experiment coexisted with ArgoCD because the controller mutated `status`, not the declared spec; multi-day behavior still needs verification for the deployed version.

19. **With workloadRef, rollout.yaml needs NO pod template.** The Rollout references the Deployment's pod template — it does NOT duplicate it. The rollout.yaml should be slim: metadata + selector + workloadRef + strategy.canary. The slim strategy contains traffic routing and steps; no podSpec helper is needed. For an inline-template cutover, extract a shared pod-template helper instead (#9).

20. **Deployment MUST gate `spec.replicas: 0` when rollout.enabled.** With `RespectIgnoreDifferences=false`, ArgoCD keeps re-applying `replicas: N` from the chart, overriding the `scaleDown:onsuccess` state. Fix: gate in deployment.yaml `{{- if ($component.rollout).enabled }} replicas: 0 {{- else }} ...`. Setting `replicas: 0` in the chart is GitOps-correct because the Rollout controller owns replicas when `workloadRef` is active. `ignoreDifferences` with `RespectIgnoreDifferences=false` hides the UI diff without protecting replicas at apply time; a Deployment of 3 plus a Rollout of 3 gives 6 pods. For an HPA-capable chart: `{{- if ($component.rollout).enabled }} replicas: 0 {{- else if not $component.hpa.enabled }} replicas: {{ .deployment.replicas }} {{- end }}`; without HPA, use plain `else`. The parenthesized rollout lookup handles an absent rollout key; scaffold-safe HPA lookups are in #56.

21. **HPA must target the Rollout (not Deployment) when `workloadRef`+`scaleDown:onsuccess`.** After first successful promotion, the Deployment's `spec.replicas` goes to 0. An HPA still targeting the Deployment sees 0, falls below `minReplicas`, and fights the Rollout controller. Fix: conditionally set `scaleTargetRef` to `Rollout` when `rollout.enabled`. Set `scaleTargetRef` to `argoproj.io/v1alpha1 / Rollout` when enabled and `apps/v1 / Deployment` otherwise. KEDA has a corresponding target-kind trap (#53).

22. **`canaryService`/`stableService` must be conditional on the Service rendering.** For workloads where container ports may not be defined, the Service guards on `$serviceEnabled && $containerPorts`. The Rollout template must apply the same guard, otherwise it references non-existent Services. Pure replica-based canaries can omit both `canaryService` and `stableService`.

## HTTPRoute and canary routing

23. **Gateway API `HTTPRoute.spec.rules` is hard-capped at `maxItems: 16`.** Overflow rejects the WHOLE route. Fix: split into a second HTTPRoute that OMITS `parentRefs`/`hostnames` — it inherits the same listener. EG flattens all HTTPRoutes on a listener into one rule list and sorts by specificity regardless of source route. Offline proof: render before/after and assert order-normalized UNION is byte-identical. **Scope correction from #24:** listener/hostname inheritance is chart-specific; compare rendered metadata and spec excluding rules to prove both children attach identically. Overflow is rejected as `Too many: N: must have at most 16 items`. A hash-equal order-normalized rule union alone does not prove precedence: also check tied-overlapping rules and run a negative control that changes one rule.

24. **Route-split is behavior-preserving — conditions and proof.** EG sorts rules by: path-type (Exact>Regex>Prefix), path char count, #header, #exact-header, #cookie, #query. Source-HTTPRoute identity does NOT affect ordering. The ONLY delta: rules that tie on ALL sort keys break by creationTimestamp/namespace/name (cross-route) post-split vs rule-list-index (intra-route) pre-split. GitOps bulk-apply gives same creationTimestamp, so split route NAMES must preserve original rule order for tied-overlapping pairs. Pinned source context: Envoy Gateway v1.7.1, `preserveRouteOrder=false`; flattening is in `internal/gatewayapi/route.go`, specificity in `internal/gatewayapi/sort.go` (`XdsIRRoutes.Less`), cross-route provider sorting in `resource.go`. `Less()` has no Method criterion. Tied rules matter only if both can match one request; distinct PathPrefix rules and path-versus-path+header pairs avoid that tie. Creation timestamps have 1s granularity; inspect actual timestamps instead of assuming a batch ties. Timeouts and URLRewrite filters travel with each rule. **Executable xDS equivalence proof.** Render both dumps from the same Gateway API input: `egctl x translate --from gateway-api --to xds --type route --add-missing-resources -o yaml -f "$input"` and the same with `--type endpoint`. **Route path**: `xds[<only-gateway-key>].dynamicRouteConfigs[0].routeConfig.virtualHosts[0].routes[]`. **Endpoint path** (needed to resolve weights): `xds[<only-gateway-key>].dynamicEndpointConfigs[].endpointConfig.endpoints[].metadata.filterMetadata["envoy-gateway"].resources[]` — resolve each `kind: Service` to `{namespace/name, sectionName}` and pair it with `endpoint.loadBalancingWeight`. Route actions carry either `route.cluster` or `route.weightedClusters.clusters[].{name,weight}`. **Normalize away the synthetic `route.name` AND cluster names, then compare the ORDERED route arrays retaining**: path type/value, sorted header matches, sorted query matches, case sensitivity, prefix/regex/path-template rewrites, `timeout`, `idleTimeout`, `upgradeConfigs`, `retryPolicy`, redirect/direct-response action, resolved Service/port identity, route weight, endpoint load-balancing weight. **Equivalence and anti-vacuity assertions**: every virtual host has the same route count; `numRoutes` on each side equals the source rule count; the ordered normalized arrays are byte-identical; **a header-qualified route's index is LOWER than the same plain-path route** (proves precedence, not just presence); **a negative control mutating one `timeout` `900s → 123s` MUST produce a non-empty diff**; and **the listener must be hostname-less** — a wildcard like `*.example.com` does not match `app.sub.example.com`, so a hostname mismatch yields an empty-vs-empty comparison that passes while proving nothing.

25. **ArgoCD ignoreDifferences jq guard must use a STATIC chart label, not a controller-toggled label.** The guard must evaluate identically on git-desired and live (symmetric). A guard on a static `canary-traffic-managed` label is symmetric; a guard on the controller's `in-progress` label is asymmetric (causes the incident). For multi-rule routes (plugin v0.15.0+), use `startswith("canary-header")` not exact match — covers indexed names (`canary-header-1`, etc.). Use `(.name // "") | startswith("canary-header")`: unnamed original rules otherwise cause a null-input error. Negative cases must include an unlabeled route, a labeled steady-state route without managed rules, and a missing labels object; none should match or error. Positive cases include both `canary-header` and `canary-header-1`.

26. **jq `del()` is INVALID for nested-array paths — ArgoCD gotcha.** ArgoCD wraps `jqPathExpressions` in `del()`, and `del(.spec.rules[].backendRefs[].weight)` is invalid jq for nested arrays (upstream issue argoproj/argo-cd#26870, OPEN). Use `walk(if type=="object" and has("weight") then del(.weight) else . end)` or explicit `jsonPointers`. For example, an explicit pointer is `/spec/rules/0/backendRefs/0/weight`. A weight-only ignore is symmetric when both backendRefs are declared and list length stays stable. Pair it with `RespectIgnoreDifferences=true`; diff suppression alone does not stop apply from reverting weights. The issue status above is historical, not a current upstream-status check.

27. **jq CAN ignore a SINGLE element of an atomic list.** `HTTPRoute.spec.rules` is `listType: atomic`, but `jqPathExpressions: '.spec.rules[] | select(.name == "canary-header")'` correctly removes ONLY the named rule from the diff. Atomic-list semantics block partial SSA MERGE, not jq-based diff suppression. Recorded validation used ArgoCD v3.3.6: unnamed Git-authored rules still diffed and applied.

28. **`setHeaderRoute` managed route is REMOVED when canary RS has 0 available replicas** (argo-rollouts v1.9.0 source, `rollout/trafficrouting.go` L199-269). The route is never re-added because `SetHeaderRoute` only re-fires on a `setHeaderRoute` step. Failure trap: `setCanaryScale: {matchTrafficWeight: true}` at weight=0 un-pins the canary, scales to 0, triggers removal. **FIX: order `setWeight: N>0` BEFORE any `matchTrafficWeight` step.** At v1.9.0, `rollout/trafficrouting.go:222` calls `RemoveManagedRoutes()` when `c.newRS == nil || c.newRS.Status.AvailableReplicas == 0`; subsequent `setWeight` steps do not call `SetHeaderRoute`. A fixed floor can therefore produce a 3→0→1 pod transition at un-pin. In plugin v0.13.0 (`pkg/plugin/httproute.go`, also recorded at v0.15.0), `setHTTPRouteWeight` rewrites existing backendRef weights only; its canary/stable-found guard is route-level. A single-backend cohort rule inside that managed route can receive weight 0 and return 503. Keep permanent cohort rules in a dedicated HTTPRoute outside `trafficRouting.httpRoutes`. **A `setHeaderRoute` cohort rule is DESIGNED to persist through every later weight step, and is torn down only on completion or abort — do not "clean it up" before the ramp.** The injected `canary-header*` rules stay for the entire rollout by design: the header rule pins a **deterministic cohort** to canary, and **removing it mid-weight silently converts that cohort to probabilistic routing** — the cohort you were deliberately steering starts landing on stable at `1 - weight`, and nothing reports it because the rollout still progresses normally. So do **not** add a `setHeaderRoute`-removal step to the step list. Distinct from #28's failure, where the same rule is removed *by the controller* when the canary ReplicaSet has zero available replicas; that one is involuntary and permanent, this one is a self-inflicted step-list mistake.

29. **HTTPRoute `spec.rules` field-manager is `gatewayAPI`, not `rollouts-controller`.** The plugin does a full PUT with no explicit FieldManager, but apiserver populates `managedFields` as `manager='gatewayAPI'`. A `managedFieldsManagers` ignore is fragile (name is User-Agent-derived, `spec.rules` is atomic, and it breaks GitOps route-edit visibility). Use the static-label jq guard instead. Recorded at plugin v0.13.0, `pkg/plugin/plugin.go`: `.Update()` is a full PUT; inspect ownership with `kubectl get httproute --show-managed-fields=true` (hidden by default). The observed `gatewayAPI` entry had `op=Update` and owned rules; `argocd-controller` had `op=Apply` and owned labels only. A separate historical concern is `argoproj/argo-cd#20178` (managedFieldsManagers with ServerSideDiff on 2.12+); verify on the actual version.

30. **Argo Rollouts keeps canary Service pointed at STABLE pods when idle.** `rollouts-pod-template-hash` on the canary Service == stable RS hash at rest, same endpoints as stable. So the canary Service is NEVER empty (no 503), and a permanent cohort header rule pointing at the canary Service needs NO warm canary replica. For a permanent cohort, declare one single-backend canary rule per path in a dedicated HTTPRoute outside `trafficRouting.httpRoutes`, so plugin weight changes cannot dilute it.

31. **`setHeaderRoute` with a COOKIE match FAILS on routes that already match cookie.** The plugin copies the base match and APPENDS the setHeaderRoute match; if the base already matches `cookie`, the result has two `cookie` headers in one match — Gateway API rejects `Duplicate value: {name: cookie}`. Use a non-cookie signal for canary routing on cookie-matching routes. An app-injected `x-example-canary` is a neutral non-cookie signal. The duplicate invalidates the whole HTTPRoute; routes without a base cookie match do not have this collision.

## GitOps-friendly alternatives

32. **GitOps-friendly alternatives to controller-mutated HTTPRoute canary.** (1) STATIC PINNING: separate static HTTPRoutes for stable+canary, Rollout manages only weight. (2) Unconditional weight ignore + `ApplyOutOfSyncOnly=true`. (3) **Flagger**: AVOIDS drift BY DESIGN (generates HTTPRoute at runtime with ownerReferences, never in git). (4) Structural root cause: one object both declared in git AND mutated by a controller; fix by making them different objects. Flagger's Gateway API provider uses `mergeMatchConditions` to overlay headers on every `Canary.spec.service.match` path, but owns/regenerates the route and requires re-declaring those paths and replacing Rollouts. The recorded alternatives survey found no native Envoy Gateway progressive-delivery primitive beyond weighted backendRefs, and treated native Istio VirtualService on ambient as unsuitable because of alpha support and undefined Gateway API mixing (`istio/istio#56773`); recheck those version-sensitive limits before choosing.

33. **Two-layer ArgoCD deploy for canary + app-of-apps cascade.** The `ignoreDifferences` lives on the APPLICATION object (rendered by app-of-apps), while route labels + rollout config come from the app SOURCE chart. To test a branch, repoint the app-of-apps at the branch (cascades both layers). ORDER matters: the safe ignore must be live BEFORE the canary runs. The child's `targetRevision` must itself come from the app-of-apps for the cascade to work. During a branch test, syncing an app-of-apps still pointed at the default branch can revert the child ignore. Both layers become desired state only when the changes land.

## Helm and chart patterns

34. **Helm `default` filter treats 0 as falsy.** `{{ .maxUnavailable | default "25%" }}` replaces explicit `0` with `"25%"`. Use `kindIs "invalid"` check instead: `{{- if not (kindIs "invalid" .maxUnavailable) }}{{ .maxUnavailable }}{{- else }}"25%"{{- end }}`. The original rendering example quotes the explicit value: `{{- if not (kindIs "invalid" .maxUnavailable) }}{{ .maxUnavailable | quote }}{{- else }}"25%"{{- end }}`; test an explicit zero as the negative case for the `default` form.

35. **Helm route-split surgical-edit techniques (behavior-preserving).** (a) Don't `yaml.safe_load`+`safe_dump` already-scrutinized values files — it reformats flow style, re-quotes regex matches, drops comments. Use LINE-SPAN SURGERY: parse by indentation, extract rule source lines verbatim, re-emit as N single-rule routes. (b) `ruamel` gotchas: reusing same object reference across split children emits YAML anchors — `copy.deepcopy` every moved subtree. (c) Behavior-preservation proof = MATCH-TUPLE UNIQUENESS across all rendered rules (path.type/value + sorted header tuples + method). (d) Orphan-ref check: after split/rename, grep for old route name in `charts/argo-apps` and Rollout `trafficRouting.httpRoutes` list. After line-preserving edits, run `yamlfmt`. `ruamel` can turn `nodeSelector: null` into `nodeSelector:`; restore only where the next line is not more indented. Full-rule-spec multiset equality does not replace match-tuple uniqueness, because duplicate matches can change precedence. Search rendered references outside the old route's own `metadata.name`; label-scoped ignores cover split children, while name-scoped ignores may dangle. Indentless YAML list items sit at the parent key's indentation, so block detection must also include same-indent `-` lines. Use explicit absolute checkout paths if shell calls reset cwd.

36. **Envoy Gateway inline-Lua edge header injection.** Use `EnvoyExtensionPolicy` kind, `lua.type: Inline`; reads/mutates request headers. Attach at GATEWAY scope for anything that must run BEFORE routing. EG's default filter order places EEP-Lua AFTER ext_authz BEFORE router. Envoy Lua `clear_route_cache` defaults true, so header mutation auto-clears route cache for re-evaluation. Recorded against Envoy Gateway v1.7.1. Use `targetRefs.kind: Gateway` and `request_handle:headers():get/replace/add`; HTTPRoute-scoped Lua runs after route selection. An `EnvoyPatchPolicy` reorder is needed only if the Lua must move before ext-authz, such as a login redirect.

37. **HTTPRoute else-hardcoded-defaults footgun in templates.** Templates that emit hardcoded labels ONLY in the `{{else}}` branch (no explicit `labels` block) silently DROP those defaults when any `labels` block is added. ALWAYS render before/after and diff the label set per route. Do not copy another chart's canary-ignore selector without checking its rendered labels: `a.example.com/canary=="enabled"` will not match `b.example.com/canary-managed=="true"`. Such an ignore silently matches nothing.

38. **Argo Rollouts default `progressDeadlineAbort: false` → a stuck canary hangs in Degraded/Timeout INDEFINITELY.** A chart that omits `spec.progressDeadlineAbort` gets the `false` default → a canary that exceeds `progressDeadlineSeconds` (600s default) does NOT auto-revert to stable; it hangs, needs a manual `kubectl argo rollouts abort <ro> -n <ns>`, AND re-sticks on every image-updater push. Common trigger: canary pods unschedulable (node group at max size + affinity). Durable fix: `spec.progressDeadlineAbort: true` (validate the retry cadence in dev first) so stuck canaries auto-abort to stable. Stuck-rollout metric phase = `Timeout`.

39. **An alert whose "bad" phase set includes `Abort` can NEVER be cleared by the abort remediation — and abort IS the safe state.** If a degraded-rollout alert matches `rollout_phase{phase=~"Error|Timeout|Abort"}`, the standard remediation `kubectl argo rollouts abort` transitions the phase `Timeout→Abort`, which the alert ALSO matches → it re-fires on `Abort` instead of resolving. But an aborted rollout has reverted to the stable ReplicaSet = safe/serving. Fix: alert on `Error|Timeout|InvalidSpec` only (drop `Abort`) so an abort clears the page; pair with `progressDeadlineAbort: true` (#38) for auto-revert (a brief `Timeout` page, then self-clears). `Abort` can also come from a failed `AnalysisRun`. **Metric-enum caveat (#40):** `rollout_phase` v1.9.0 has no `InvalidSpec` series, so including it in this regex cannot detect invalid specs. Whether `Abort` should page is an operator policy decision; the mechanism above alone does not decide that policy.

## Argo Rollouts metrics, dashboards & alerting

40. **Argo Rollouts exposes two different phase enums that look interchangeable but aren't — a Prometheus metric named `rollout_phase` and the Rollout object's own `.status.phase` use different value sets, and querying one with the other's values silently matches nothing.** At v1.9.0, the `rollout_phase` gauge emits exactly six fixed series per rollout: `Completed|Progressing|Paused|Timeout|Error|Abort` (note `Abort`, not `Aborted`; there is no `Degraded` and no `InvalidSpec` in this enum). The Rollout CR's own `.status.phase` is a smaller, different enum: `Healthy|Degraded|Progressing|Paused`, computed separately by the controller. Concretely: a rollout that exceeded its progress deadline shows object phase `Degraded` via `kubectl`, but the metric emits `rollout_phase{phase="Timeout"}==1` — so an alert meant to catch a stuck rollout must match `Timeout`, and matching `Degraded` against the metric matches nothing at all. The newer replacement metric, `rollout_info`, carries one series per rollout whose value tracks the current phase and adds `InvalidSpec` to its enum — but it has no per-phase label at all, so querying it with a `phase="X"` label selector (as if it behaved like the older metric) also returns nothing. Before writing any Rollout alert, confirm the actual label values live against your own metrics store rather than assuming the CR enum and the metric enum match. Source anchors for the recorded v1.9.0 behavior: `controller/metrics/rollouts.go:137-142`; the CR enum is `RolloutPhase` in `types.go`, computed by `calculatePhase`. Steady state corresponds to `Completed`. Verify the local `label_values(rollout_phase,phase)` result before choosing an alert's phase set.

41. **Argo Rollouts' Prometheus metrics carry the CONTROLLER's namespace on the standard `namespace` label, not the workload's — the workload's namespace is a separate `exported_namespace` label, and copying a workload-scoped alert filter onto a rollout metric matches zero series.** Also worth checking before trusting a replica-mismatch alert during a canary: `rollout_info_replicas_desired` reports the full `spec.replicas` (not the canary-scaled count), and the corresponding available-replicas metric reports total available replicas across stable+canary combined — so an `available < desired` alert only produces a false positive during a canary pause if the rollout scales the stable ReplicaSet down below spec (a `dynamicStableScale`-style setting); with the stable ReplicaSet held at full size throughout the canary, total available stays at or above desired the whole time. Verify which scaling mode is in effect before trusting either alert's behavior during a multi-hour manual soak. Treat controller/workload namespace labels and external labels as scrape-configuration observations to verify locally. Where available, `name=~"<service>.*"` includes tenant variants; group workload alerts by `exported_namespace`. If `cluster` and `environment` are present, `max by(cluster,environment,name,exported_namespace)` protects against duplicate controller emission. Replica source anchors: `controller/metrics/rollouts.go:131-133`; desired is `Spec.Replicas`, available is `Status.AvailableReplicas`.

## ArgoCD integration (continued)

## Header inspection & canary routing headers

45. **Whether a header is available for HTTPRoute matching is decided entirely by Envoy's filter CHAIN ORDER, not by which filter added the header — confirm order from the live config dump, not from documentation or intent.** A representative chain: an early header-strip filter (removing client-spoofable auth-adjacent headers) runs BEFORE an ext-authz filter, which re-injects trusted values for those same header names, which in turn runs BEFORE the router — so headers injected by ext-authz ARE available for HTTPRoute header-matching, even though a naive reading of "headers were stripped earlier in the chain" would suggest otherwise. The strip-then-reinject pattern exists specifically to prevent client-spoofed values from reaching the authorization filter, not to keep those headers out of routing. Two verification notes: (1) a route's own `requestHeaderModifier` filters run AFTER routing decisions, so headers they add are visible at the backend but were never available for the match that sent the request there — always check a route's own filters, not just the global chain, before asserting what was or wasn't available at match time; (2) when on-the-wire behavior actually matters, a packet capture at the backend is the authoritative source — an L4-only proxy in the path (one that never modifies HTTP headers) means the backend's inbound bytes equal the upstream's outbound bytes, but that equivalence needs to be confirmed for your specific proxy stack, not assumed. One observed chain shape was `csrf → cors → header_mutation (CTP earlyRequestHeaders strip) → login-redirect Lua → ext_authz → Lua extensions → router`. Treat it as a verification example, not a universal order; a pure L4 ztunnel hop does not mutate HTTP headers.

46. **If your application's session already carries a stable identifier in a cookie on every authenticated request, per-tenant or per-user canary routing needs no application change at all — HTTPRoute can match the raw `cookie` header with a regex.** An anchored pattern like `(?:^|;\s*)<key>=<id>(?:;|$)` selects a specific cookie value without a client-side header-injection step; the anchors matter because an unanchored substring match on an id would also wrongly match a longer id that contains it as a prefix. This is complementary to, not a replacement for, an explicit opt-in canary header — cookie matching gives automatic targeting for anyone already carrying that cookie, an opt-in header gives manual per-request control, and a Rollout can use both. One caveat that only bites when combining them: a plugin-managed header-based canary route cannot be layered onto a route that already matches on the `cookie` header — the plugin builds its canary rule by copying the base match and appending its own header match, and Gateway API rejects two `cookie` matches in one rule.

## Traffic validation

50. **Positive-only application logs cannot prove canary traffic isolation.** If a log field exists only when `x-example-canary` is present, logs prove marked requests reached canary but cannot reveal unmarked leakage at weight 0. Capture both ReplicaSets, selecting pods by `rollouts-pod-template-hash` equal to `status.currentPodHash` versus `status.stableRS`. On a verified plaintext backend hop, capture `tcpdump -i any 'tcp dst port <app-port>' -w pcap`, then use `tshark -d tcp.port==<app-port>,http -Y http.request` to inspect `http.host`, URI, cookie and request headers. Exclude health probes and `/metrics` by both path and `host==pod-IP`; they can hit the same application port and look like leaks. Weight 0 is the strict test: any unmarked application request on canary is a leak. At positive weight, unmarked canary traffic is expected. A complete recorded weight-0 proof had canary 100% marked, stable 100% unmarked, and no leakage either way.

51. **Pick capture/test cohorts by traffic CONSISTENCY, not volume — and rank them with a stepped presence query.** When the signal you need to capture is emitted client-side behind a feature flag, a high-VOLUME cohort can still be useless: it emits in bursts, so a capture window lands in a quiet stretch and the on-wire positive proof keeps eluding you. A cohort can even be measurably busy in a window while emitting ZERO of the flagged header. **Rank by PER-BUCKET PRESENCE instead**: a Loki/PromQL range query stepped at ~10 min over an hour, keeping cohorts present in EVERY bucket with low variance, then add those to the flag. **Corollary for triage: a cohort active-but-not-emitting for ONE window is NOT a regression — confirm sustained inactivity before escalating to the app team.**

## Canary enablement and scaling

52. **Arming a header canary requires both promotion mode and traffic routing, but starts no new revision.** Set `rollout.promotion.mode: manual` and `rollout.trafficRouting.enabled: true` in cluster values or ArgoCD Helm parameter overrides such as `<service>.<component>.components.<component>.rollout.promotion.mode`. In this chart pattern, auto renders neither steps nor traffic routing. Verify the sync installed both before changing the pod template/image: otherwise the new revision races ahead without the header step. A recorded arm restored 75/25 weights to 100/0 before the trigger. Removing overrides returns to the underlying basic-canary configuration. Queue-worker charts without HTTPRoutes use only manual mode; a traffic-routing value they never read is inert. When reordering steps, retain `{{- if (.rollout.trafficRouting).enabled }}` around traffic-routing-only steps and keep the weight ramp outside; a negative-control render with traffic routing disabled must stay byte-identical.

53. **Queue-consumer canaries are replica canaries; prove pod lifecycle and autoscaler ownership.** Stable and canary consume the same queue in parallel, so `setWeight` controls replica proportion rather than HTTP routing. At `setWeight: 25`, inspect pods by hash and readiness, source Deployment at 0, and clean reconciliation on promote. The stable ReplicaSet can remain full depending on the strategy. An old KEDA ScaledObject targeting the Deployment fights a chart's zero-replicas gate: KEDA defaults `scaleTargetRef.kind` to Deployment and can scale 0→3 while ArgoCD forces 0 again. Remove the obsolete target or point it at `{apiVersion: argoproj.io/v1alpha1, kind: Rollout}`; validate any remaining autoscaler against #43. In the recorded manual worker profile, the first step was `pause: {}` at weight 0, so promote once to reach `setWeight: 25` before expecting canary pods.

54. **Per-pod capture-harness tooling gotchas**: (a) a script that reads capture TSVs must clear its own prior-run files before combining them — stale files from a prior run (e.g. a 25%-weight canary's legit traffic) contaminate a later weight-0 verdict → a FALSE "non-header leaked to canary"; tell = stable count byte-identical across a canary-only re-run. (b) a bare `except:` around the weight-detection helper CATCHES `SystemExit` from `sys.exit()` → after `print(weight);sys.exit()` it falls through to the fallback `print('?')` → `weight="0\n?"` → verdict mislabels PASS as INFO and the wt≠0 warning misfires. Use `except Exception:`.

55. **Canary pod-count churn during a header canary is the two-phase `setCanaryScale` by design — but `matchTrafficWeight` sizes by weight%, not cohort size**: Step 1 `setCanaryScale: {replicas: max(3, ceil(replicas/4))}` pins a fixed warm canary for the weight-0 header gate; the later `setCanaryScale: {matchTrafficWeight: true}` rescales the canary to TRAFFIC% (~1 pod at 25%), terminating the extra header-phase pods — "new pods being taken down" mid-rollout is expected, not an ArgoCD fight. CAVEAT: after matchTrafficWeight the canary is provisioned by weight%, NOT by header-cohort size — a large dogfood cohort at low weight risks under-provisioning. With `workloadRef` + `scaleDown: onsuccess`, Deployment and Rollout ReplicaSets coexist transiently (~2x pods) during the canary.

## Preconditions, proof recipes, and lifecycle contracts

59. **Gateway API plugin defects need a versioned reproducer and precise documentation framing.** Historical reports for `argoproj-labs/rollouts-plugin-trafficrouter-gatewayapi`: #207 covered one-rule-per-route `setHeaderRoute` behavior on multi-path routes; #208 covered the in-progress-label ignore on ArgoCD 3.x. Name-select ignores cover injected rules but not weight rewrites. **Evidence boundary:** the earlier issue summary described ServerSideApply plus RespectIgnoreDifferences enabled; the exact reproduction below used client-side apply and RespectIgnoreDifferences unset. These are distinct recorded configurations and must not be collapsed into one verified setup.

**Recorded #208 reproduction.** **Versions**: ArgoCD `v3.3.6`, Argo Rollouts `v1.9.0`, plugin `v0.13.0`, Envoy Gateway `v1.7.1`; a trivial echo-server behind a **single-rule** HTTPRoute. **Sync config**: `ApplyOutOfSyncOnly=true`, `selfHeal: true`, **`RespectIgnoreDifferences` unset (default false)**, client-side apply. **The plugin's own DOCUMENTED ignore**: `jqPathExpressions: [select(.metadata.labels["rollouts.argoproj.io/gatewayapi-canary"] == "in-progress") | .spec.rules]` on `gateway.networking.k8s.io/HTTPRoute`. **Two phase-specific behaviours, which is why the bug reads as intermittent:** in the **header phase** the `in-progress` label is not yet applied (it is weight-gated), so the ignore does not match and **`selfHeal` reverts the injected header rule**; in the **weight phase** the label IS on live but not on git-desired, so `select(in-progress) | .spec.rules` **matches live and not desired → asymmetric diff → unreconcilable `OutOfSync`**. **Functional signature — the one that makes it a correctness bug rather than a status annoyance: `setWeight 50` reverts to `stable:100, canary:0` on the live object while the Rollout still reports `canaryWeight=50`, so the canary receives 0% of traffic during a "50%" step.** **Working fix**: gate on a **static, git-authored** label present on **both** live and desired (#25), and ignore only `.spec.rules[] | select(.name == "<managed-route-name>")` and `.spec.rules[].backendRefs[].weight` — never the whole list (#61). **Weight-path conflict:** #26 records a nested-array `del()` failure for the weight expression used in this reproduction. Validate the exact ArgoCD/jq version or use explicit weight pointers before adopting it.

60. **Progressive delivery does not make a release safe — it assumes three capabilities already hold, and without them the canary just shows you the same failure earlier and blames the canary.** The prerequisites: (1) **expand/contract migrations** — additive-first schema changes, because `v_old` and `v_new` run **concurrently against the same schema** during the canary window; (2) **honest probes** — readiness must actually gate traffic, or the router weights traffic to pods that are not serving; (3) **connection draining** — `preStop` + real `SIGTERM` handling, or every step of the ramp sheds in-flight requests and the metric analysis reads it as a bad revision. **The migration rule that follows is a hard ordering, not a preference: expand-only changes land BEFORE the canary; contract changes (column drops, type narrowings, enum removals) land in a LATER release, after `v_new` is fully promoted.** A contract migration executed during the canary window breaks the *stable* version, which is the one failure mode a canary cannot roll back. **The queue equivalent is the one people miss on replica canaries** (#53): stable and canary consumers read the **same queue in parallel**, so compatibility must hold in **both directions** — `v_old` consumers must accept `v_new` producers' messages *and* `v_new` consumers must accept `v_old` producers'. One-directional compatibility is the usual assumption and it crashes the canary pods on the first message from the other side.

61. **A jq `ignoreDifferences` that strips an ENTIRE controller-managed list can make ArgoCD DELETE that list under client-side apply — and then report `Synced` while the object is empty.** Extends #25, which gives the symmetry property; this is the mechanism and the damage. Chain, all four steps required: (1) `RespectIgnoreDifferences=true` evaluates the jq against the **desired** manifest, matches, and **strips `.spec.rules` from what gets applied**; (2) **client-side three-way merge** sees `spec.rules` present in `last-applied-config` but absent from the new apply, and concludes you deleted it — **so it deletes the live list**; (3) once the state is symmetric on both sides the conditional ignores it consistently, so **ArgoCD reports `Synced` while the object is empty and `selfHeal` never restores it**; (4) the traffic controller need not be involved at all — this fired with traffic routing entirely disabled, so "the rollout controller did it" is the wrong first hypothesis. **Detection signature — all four together, because each alone is innocuous: an unexpectedly EMPTY live list + `Synced` + no controller activity in that window + managed-field ownership pointing at the GitOps controller rather than the workload controller.** **Fix shape: (a) NEVER ignore a whole list — narrow to specific elements and fields (`.spec.rules[] | select(.name == "<managed-route>")`, `.spec.rules[].backendRefs[].weight`); (b) use per-resource ServerSideApply, where field ownership makes this deletion STRUCTURALLY impossible rather than merely avoided.** Generalizes to any GitOps-managed object a controller also writes to.
    - **RECOVERY — and the trap that makes the obvious first move do nothing: REVERTING THE PR DOES NOT RESTORE THE LIST.** (Promoted 2026-08-28 from a project-scoped memory; this half was missing from the entry above, which had only the mechanism and the prevention.) The revert restores the *previous* broad whole-list ignore, and that ignore **blocks ArgoCD from re-pushing the rules just as effectively as the one you reverted** — so the app returns to `Synced` over a still-empty object and the incident looks fixed while nothing was restored. **Per cluster you must do one of two things: (a) TEMPORARILY REMOVE the `ignoreDifferences` entry for that resource entirely, so ArgoCD re-pushes the full list from git, then let the app-of-apps re-sync the broad ignore back once the rules have settled — that re-sync is harmless once live and git agree; or (b) `kubectl apply` correctly-rendered objects directly.** Verify restoration against the LIVE object, never against sync status — `Synced` was the misleading signal in the first place. **Two things to check while you are in there:** an emptied object's `managedFields` is the diagnostic tell (it reads empty, pointing at the GitOps controller rather than the workload controller), and a recovery re-apply is the natural moment to complete any dual-backendRef bootstrap the incident interrupted. **Render with the DEPLOYING APPLICATION'S REAL VALUE STACK before reasoning about desired state at all** — a partial two-file render is what hid the true diff from both the implementer and the reviewer here; enumerate the stack from `kubectl get application <app> -n argocd -o jsonpath='{.spec.source.helm.valueFiles}'`. **Weight-path conflict:** #26 records `.spec.rules[].backendRefs[].weight` as invalid under ArgoCD's `del()` wrapping; verify the installed implementation or use explicit pointers rather than copying that expression blindly.

62. **Validating a CLIENT-emitted canary marker takes two phases, and skipping phase 1 is how an exact-match canary silently no-ops forever.** **Phase 1 — prove EMISSION, before any routing exists.** Gateway API `Exact` matching is **case-sensitive**, so `On` / `true` / `1` / `enabled`, or a renamed header, no-ops the entire mechanism with no error anywhere. Prove the exact byte value **on application-originated traffic** — **a forced `curl` proves only that the proxy chain preserves the header, not that the app emits it**, and that substitution is the standard way this check gets faked. **Phase 2 — prove ROUTING**: marked requests land on canary pods and unmarked ones on stable (attribute by `rollouts-pod-template-hash` = `status.currentPodHash` vs `status.stableRS`), the GitOps app stays `Synced` throughout, and the rule is removed on completion/abort. **The capture method, dependency-light and reusable for any plaintext hop**: attach `kubectl debug pod/<pod> --image=nicolaka/netshoot --target=<container> -- sleep 600`, then capture **data packets only** — `tcpdump -A -s 2048 -c 30 -i any 'tcp dst port <p> and (((ip[2:2] - ((ip[0]&0xf)<<2)) - ((tcp[12]&0xf0)>>2)) != 0)'` (the arithmetic drops pure-ACK/handshake frames, which otherwise dominate the capture) — and census header names with `grep -oE '^[A-Za-z][A-Za-z0-9_-]+: .*' | sed 's/: .*//' | sort | uniq -c | sort -rn`. **Cleanup gotcha: `kill 1` does NOT work — `sleep` ignores SIGTERM as PID 1. Use `killall sleep`.** **Trigger the capture on state, not a stopwatch**: poll `.status.currentPodHash`, `.status.stableRS`, `.status.currentStepIndex`, `.status.pauseConditions` and the canary pods' ready count, and fire only when `currentPodHash != stableRS` AND `pauseConditions` is non-empty AND at least one canary pod is ready — otherwise the window lands before the canary is serving and the run is wasted.

63. **Promotion-profile acceptance matrix — five distinct contracts, plus the one change you must never make mid-flight.** Verify the **rendered** step shapes before triggering any live test (#13), then prove each behaviour separately, because they fail independently: (1) **auto** — completes with zero pauses; (2) **manual** — pauses indefinitely and advances only on explicit `kubectl argo rollouts promote`; (3) **soak** — auto-advances only after each timed window elapses; (4) **abort** — an operator can `kubectl argo rollouts abort` *during* the soak window, before auto-promotion fires (the soak window being abortable is the whole point of choosing soak over auto, and it is the contract most likely to be assumed rather than tested); (5) **disable** — turning the feature off returns to the non-Rollout baseline (and see #15: the Deployment is left at `spec.replicas: 0` when its replicas are in `ignoreDifferences`). **Do NOT change `promotion.mode` while a canary is in flight** — the generated step list changes underneath the controller, which **recomputes the current step index**, so a rollout can jump or repeat steps. Select the mode **before**, or in the **same** change that bumps the image; mode switches are a between-revisions operation only.
