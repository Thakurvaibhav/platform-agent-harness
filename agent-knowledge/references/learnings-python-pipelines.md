# Python Batch & Data-Pipeline Learnings: Parallelism, Object Stores, Huge Payloads

See also: `learnings-uv.md` (packaging and environment semantics for the code these pipelines run), `learnings-validation-framework.md` (making a throughput or completeness claim non-vacuous: every measurement below needs its control), `learnings-observability.md` (the logging/ContextVar and query-side behaviour of the same services), `learnings-container-images.md` (the images these jobs run in, and the layer-streaming analyses several of them feed), `learnings-agent-workflow.md` (the worker/fan-out discipline these job shapes mirror).

Shape of this file: Python jobs that read a large, skewed corpus out of an object store or a
database and reduce it. Every entry here is a case where the OBVIOUS implementation is correct
and far too slow, or silently drops the exact records that mattered. Measured numbers are from
one fleet and are included to give the ORDER of magnitude, not as targets.

1. **Downloading in the PARENT of a process pool caps throughput by the parent's GIL, not by CPU or network.** An object-store `download_as_bytes` costs roughly **20 ms of parent CPU per MB**, TLS read plus checksum, so sub-megabyte objects pegged a 96-thread parent at about **55 objects/s** while the pod used 2.5 of its 10 cores and 20-31 MB/s of its available bandwidth. The pool looks idle and the fix looks like "more threads", which does nothing. ✅ **Partition whole UNITS of work across worker processes**, give each worker its own pooled client and its own threads, and return only aggregated results to the parent. A CPU-bound control scaled 994 → 1,717 → 2,399 units/s at 4/8/12 workers with the parent at 1 % CPU: that near-linear scaling is the evidence the parent was the bottleneck.

2. **An object-store client's HTTP pool defaults to 10 connections, and the AUTH session is a second pool nobody resizes.** `google-cloud-storage 3.10.1` / `google-auth 2.49.2`: `Client()` uses `requests`' default pool of 10, so more than ten download threads log *"Connection pool is full, discarding connection"*, and for **two** hosts, because `AuthorizedSession` keeps a separate session for token refresh (`google/auth/transport/requests.py:402-413`). ⚠️ The library's own bulk-transfer helper does **not** resize the pool. ⚠️ **There is NO PUBLIC knob for this pool.** The constructor parameter that accepts a pre-built session (`storage.Client(_http=…)`, `google-cloud-core 2.5.1` `client/__init__.py:140-147`) is documented as *"should be considered private"*, so building `AuthorizedSession(creds, auth_request=Request(session_with_adapter))`, mounting an `HTTPAdapter(pool_maxsize=N, max_retries=3)` on it and passing it in **works and is measurably better**, 48 threads over 240 downloads gave **76 pool-full warnings** unpooled and **0** pooled, but it is an unsupported interface that can break on a minor upgrade. ✅ **So the DEFENSIBLE default is the public client with download threads capped at 10 per process, failing fast above that**, and the scaling you actually want comes from more PROCESSES (#1), not more threads in one. Reach for the private parameter only with the pin and the risk written down.

3. **A blob stored with `Content-Encoding: gzip` arrives DECOMPRESSED, so the "compressed" size you budgeted for is not what you receive.** The client transparently decodes on download; `raw_download=True` is what keeps the bytes compressed. ⚠️ This interacts badly with a size-based routing rule: a job that decides "this object is small enough for the shared pool" from the stored size then materialises several times that in memory. (Same transparent-gunzip behaviour as the cloud CLI's copy command: `learnings-gke.md`#23`.) ✅ Decide routing on the DECOMPRESSED estimate, and fetch raw when you intend to stream.

4. **`json.loads` on a multi-gigabyte document peaks at 3-5× its uncompressed size, and the usual "faster JSON library" does not help.** Measured on a 2.07 GB document: gunzip + standard-library parse + an AST walk peaked at **10.7 GB**; a faster third-party parser and a decode-then-free variant were **worse** (7-11 GB) because they still materialise the whole tree. ✅ **A streaming REDUCER beats both** when you only need a few paths out of a huge payload: scan for quotes with `str.find` plus backslash-parity, skip structure by regex, and feed a `zlib.decompressobj` in ~1 MB input slices, **not** by re-reading `unconsumed_tail` over the whole buffer, which recopies it at every step. That brought peak memory to **0.25-0.6 GB** at the same CPU cost per ordinary document (4.8 ms vs 4.4 ms), because the corpus is dominated by a few giants.

5. **`ast.parse` raises `MemoryError` on some long single-line expressions regardless of available RAM: catch it as a parse failure.** CPython 3.12/3.13 report *"Parser stack overflowed - Python source too complex to parse"* as a `MemoryError`, instantly, for input like `'x = ' + '-'*100000 + '1'`; a real 523k-character input hit it with a 32 GiB limit in force. ✅ Wrap `ast.parse` in `except (SyntaxError, MemoryError)` and count the failure: treating it as an out-of-memory condition sends you tuning the pod instead of handling the input.

6. **In a DROP-SET analysis, never skip a record silently: route the outliers to a solo pass and COUNT the failures.** A full run died two-thirds of the way through with a `MemoryError` surfaced from a pool future, because a handful of enormous records blew up the parser (#4, #5). The tempting fix, skip what does not parse, is fatal to the analysis, since the question being answered is *what is never used*, and an unparsed record reads as unused. ✅ **Size-route instead:** run the shared pool over the bulk, then re-run anything above a threshold **alone in a fresh spawned process** with a higher memory limit, and retry pool failures there. Measured distribution that motivates it: p50 0.1 MB, p99 8.5 MB, p99.9 37.9 MB, **max 2.74 GB**; only 64 records exceeded 64 MiB and only 21 exceeded 1 GiB across 90 days. A fresh process per outlier cost ~2.3 s, which is nothing against the tail. ✅ Throughput achieved: ~39 records/s with 48 download threads and 4 parse processes.

7. **Know which phase you are actually bound by before optimising: in an object-store pipeline it is almost always the download.** Profiled per ~0.36 MB compressed record: **download ~14.8 ms/MB** (disabling the checksum saves 0.6 ms/MB, not worth the integrity loss), streaming scan ~2 ms, extraction ~5 ms dominated by the AST walk. ✅ The one extraction win that paid was a **per-unit cache keyed on (content digest, context)**, which cut parse from 6.9 to 2.5 ms per record where the same content recurs. ✅ Streaming peak for 266-834 MiB records stayed at 0.12-0.41 GiB, which is what makes the solo-pass threshold in #6 so high.

8. **A read REPLICA cancels long queries by default, so a batch job against one must keep every statement short.** A streaming replica with the default 30 s `max_standby_streaming_delay` and no `hot_standby_feedback` kills queries with SQLSTATE **40001** *"conflict with recovery"*, which surfaces as an intermittent, data-dependent failure rather than a timeout. ✅ **Autocommit, a statement timeout BELOW the replica's delay (25 s), and batching** are the whole remedy. ⚠️ **Query shape matters more than row count here.** Measured on 1.8M rows: a `LIKE 'prefix-%'` under a non-C collation is a parallel sequential scan (btree indexes are unusable for prefix matching) at 0.7-3 s; fetching the newest child per parent via `unnest(ids) CROSS JOIN LATERAL (… ORDER BY … DESC LIMIT 1)` walks the index backwards at ~0.24 s per 500 parents, while the obvious `DISTINCT ON` over `ANY(ids)` sorts every child row at 1.15 s per 200. ⚠️ And a `json` (not `jsonb`) column holding tool output moves enormous volume: 50 rows pulled ~60 MB in 15 s until the large field was returned only for rows matching a filter.

9. **When de-duplicating parsed records by content digest, dedupe the COUNTERS but UNION the NAMES: a record's resolvable names can depend on context established by EARLIER records, so skipping a repeated digest loses names that only the older context could resolve.** Concretely, in a notebook-style stream, a cell's referenced tool names depend on aliases bound by earlier cells (`from subprocess import run as f`), so the same cell source yields different name sets in different positions. Counters (records, parse failures, inline counts) are alias-independent and safe to dedupe. ✅ Split the aggregation into "alias-independent → dedupe" and "alias-dependent → union" explicitly, and say which is which at the call site.

10. **A batch job that counts only per-ITEM failures and fails the whole run on anything else will be defeated by ONE permanently-bad item in its window.** A census tolerated a fixed list of per-frame failure classes, raised on a long run of unreadable items, and exited nonzero if ANY item failed to fetch, decode or parse, so a single corrupt or deleted object makes every full run exit 1 forever. ✅ That design is correct as a default (silent partial results are worse), but it **forces an owner decision about known-bad items** (a durable allowlist, a watermark, or an accepted failure budget) and the job should say so in its output rather than just failing. ⚠️ Also record what the job structurally CANNOT see: where state is persisted only on transitions, work done inside a never-completed first step leaves no record at all, so "no rows" means "no transition", not "nothing happened".

11. **Unwrap wrapper commands before attributing a invocation to a tool**: `timeout`, `env`, `xargs`, `nice`, `nohup`, `stdbuf`, `sudo`, `taskset`, and package-manager `run` shims all take the real command as their argument, so a naive "first token" attribution counts the wrapper. ✅ Strip them iteratively (each can wrap another), and keep the unwrapped prefix in the record so the attribution is auditable rather than lossy.

12. **PostgreSQL 16+ `pg_has_role(..., 'MEMBER WITH ADMIN OPTION')` and `GRANT` use DIFFERENT recursion rules, so the obvious admin test reports true while the GRANT fails with 'no possible grantors'.** Verified locally on PG18. `pg_has_role` with that privilege is `is_admin_of_role`, which recurses `ROLERECURSE_MEMBERS` and IGNORES `INHERIT`; `GRANT` picks its grantor through `select_best_admin` with `ROLERECURSE_PRIVS`, which follows INHERIT only. ⚠️ **A `CREATEROLE` creator gets an implicit `INHERIT FALSE SET FALSE ADMIN` membership in every role it creates**, so a managed-database master that created an admin role is a NON-INHERITING member of it, and `pg_has_role` then reports ADMIN on any role that admin role created while `GRANT` fails. ✅ **Correct admin test: superuser OR an `EXISTS` over `pg_auth_members` for that role with `admin_option` whose member satisfies `pg_has_role(current_user, member, 'USAGE')`.** ✅ **Reproduce the real topology in tests by creating the intermediate admin role AS THE MASTER, not as the superuser**, or the bug cannot occur. **Where this bites in practice:** a migrator that ensures the database user as master and then runs migrations as the admin role creates every migration-created role as THAT role, so a pre-migration `GRANT` by the master aborts every migration. The fix pattern is to test for real admin as above and, if absent, connect as the admin role and `GRANT <role> TO <master> WITH ADMIN OPTION`.

13. **Two asyncpg behaviours that change how a per-item error handler and a TLS test must be written.** (1) **`server_settings` `lock_timeout`/`statement_timeout` are startup GUCs, so Postgres raises `LockNotAvailableError`/`QueryCanceledError`, which SQLAlchemy wraps as `sqlalchemy.exc.DBAPIError`** (with the asyncpg exception as `orig`). **An `except SQLAlchemyError` per-item handler therefore swallows a LOCK WAIT as an ordinary item failure**, which is usually not what the author intended. ✅ Test it by holding `FOR UPDATE` from a SECOND session inside the fake IO step (`run_coroutine_threadsafe(holder.execute(...), loop)` from the `to_thread` callback), monkeypatch the timeout constant down to 1 second, and wrap in `asyncio.timeout` **so that dropping the setting fails as a TimeoutError rather than hanging**, which is what makes the test non-vacuous. (2) **asyncpg 0.31.0 given an `ssl.SSLContext` (rather than an sslmode string) treats TLS as MANDATORY:** `connect_utils` sets `sslmode=disable` but still wraps the socket with `ssl_is_advisory=False`, so a server answering 'N' raises `ConnectionError 'rejected SSL upgrade'` and never falls back to plaintext. ✅ That makes a TLS-less local Postgres a clean NEGATIVE CONTROL for 'TLS is required'. ✅ And a SQLAlchemy `do_connect` listener registered after the application's own still observes the injected `cparams['password']` even though the connect then fails, which proves a per-connection token path without needing a TLS server at all.

14. **Cancelling an in-flight command on a MULTIPLEXED Redis client fails every OTHER pending request on that connection, so an `asyncio.timeout` around a cheap command is not a local safety net.** coredis 5.7 quick-releases non-BLOCKING commands (SET, GET) back to the pool BEFORE their reply is awaited (`client/basic.py:584-585,1056-1058`). Cancelling one makes `Request.cleanup` call `connection.disconnect()` (`connection.py:68-70`), which fails every other pending request on that connection with `ConnectionError` (`connection.py:697-709`). There is no reply DESYNC, but concurrent callers fail whenever Redis is slower than the timeout, which is exactly when the timeout was meant to help. ⚠️ Error-mapping asymmetry in the same client, which matters for any retry classifier: `READONLY` maps to `ReadOnlyError` (a `ResponseError` subclass, `parser.py:160`), **`OOM` falls back to a BARE `ResponseError`** (`parser.py:344`), and `LOADING` is `BusyLoadingError`, a `ConnectionError`. So an `except ConnectionError` retry catches loading and disconnects but not out-of-memory.

15. **Running a Postgres-backed Python test suite and MUTATING its source on a machine with no container runtime: the full recipe and the four traps.** (1) **Throwaway cluster:** `initdb` a scratch cluster from a MODERN server build (an older major fails on newer syntax such as `NULLS NOT DISTINCT`), start it with the unix socket directory EMPTIED (`-o "-k ''"`, because a scratchpad path exceeds the 103-byte socket path limit), create the test database, and run pytest with the host and port environment variables set, since a well-written local-stack config reads the environment FIRST. (2) **Use real password auth:** `initdb --pwfile` with `-A scram-sha-256` mirrors CI, so a test that builds its OWN engine without a password FAILS locally the way it would in CI; a trust-auth throwaway cluster HIDES that class entirely. The passwordless-engine case is then fixed by a `do_connect` listener that injects `engine.url.password`. (3) **Mutating source without touching a shared editable worktree:** `rsync` the package and its local-stack helper plus the root project file to scratch, mutate THERE, and run pytest from the scratch root with `PYTHONPATH` pointing at the scratch copies, because **PYTHONPATH shadows an editable `.pth` install**. Give each concurrent runner its OWN database, since the cleanup fixture truncates every table. A separate worktree needs its own virtual environment or the parent checkout's editable install is imported instead. (4) **Lock-race tests:** poll `pg_locks WHERE NOT granted AND:pid = ANY(pg_blocking_pids(pid))` under an `asyncio.timeout`, never a sleep.

16. **A least-privilege batch job cannot simply import the application's own modules, and an ORM `onupdate` column defeats a column-scoped GRANT.** Two findings that together determine the shape of such a job. (1) **Import graph:** modules that build a global settings object AT IMPORT TIME (cloud, secrets, provider and database-environment modules here) fail in the job's minimal environment, because the settings object requires variables the job has no reason to carry. Only the plain model and utility modules import cleanly. ✅ Map which modules are import-safe BEFORE designing the job, and build what you need locally rather than reusing a helper that drags the settings object in. (2) **`onupdate=func.now()` on a timestamp column means ANY ORM or Core update adds that column to the SET clause**, so a role granted `UPDATE(one_column)` is denied. ✅ Use a SQLAlchemy `table()` TableClause declaring ONLY the columns the job touches. ✅ Prove both with a `SET ROLE` test using the EXACT grants, which is what turns a permissions assumption into a test.

17. **Two review findings from one garbage-collection PR, both of which look like test detail and are actually correctness.** (1) **A VACUOUS fixture:** an ORM `update(...).values(...)` in a test applies the `onupdate` timestamp, so a row meant to be excluded by its JSON MARKER was really excluded by the GRACE-PERIOD filter, and the marker logic was never exercised. ✅ Set the timestamp EXPLICITLY in the same `values()` call so the fixture tests what it names. (2) **The row-lock MODE is load-bearing and needs a test that holds the conflicting session open:** `FOR NO KEY UPDATE SKIP LOCKED` is required, because `FOR KEY SHARE` does NOT conflict with a `NO KEY UPDATE` reactivation guard, so the collector would write its tombstone and delete data under an in-flight reactivation. ✅ Pin it with a test that holds the reactivating session open while the collector runs, under `asyncio.timeout`. A weaker lock mode passes every test that does not hold a real conflicting transaction.
