# Learnings: Envoy Gateway (HTTPRoute migration + ext-authz)

Durable, vendor-neutral patterns for migrating services from a legacy Envoy/ingress config to Envoy Gateway `HTTPRoute` resources, and for validating auth on the migrated routes. Applies to any Gateway API + Envoy Gateway setup with an external-authorization (`ext-authz`) `SecurityPolicy` layer.

See also: `learnings-helm-ci.md` (Helm deep-merge), `learnings-observability.md`, `learnings-progressive-delivery.md` (Gateway API canary routing), `learnings-code-review.md`, `learnings-agentgateway.md`, `learnings-istio.md`.

## HTTPRoute status & XDS

1. **Empty `status.parents: []` on an HTTPRoute does not mean the route is broken — it's an Envoy Gateway status-writeback lag. The Envoy XDS config dump is the source of truth, not the CR status.** A route can be fully programmed and serving traffic while its status is empty. Verify by port-forwarding the Envoy proxy admin port (`:19000`) and dumping `/config_dump` — look for your hostname's `virtual_host` and its routes. Don't gate a migration verdict on `Accepted: True` / `ResolvedRefs: True` alone; if status is empty, go straight to the XDS dump. (Same status-layer-vs-dataplane split shows up in EG Gateway-programmed alerts.)

2. **Envoy is first-match-wins for equal path prefixes; a migrated service's specific routes must sort ABOVE any catch-all fallback route in the XDS dump.** A fallback/catch-all on `/` (forwarding to the legacy backend) will silently swallow traffic if the service's direct routes don't appear before it. More-specific prefixes beat less-specific (`/api/foo/v2` beats `/api/foo` beats `/`). Envoy Gateway translates the Gateway API `PathPrefix` match to Envoy `path_separated_prefix`.

3. **A catch-all/fallback cluster showing very high request counts is normal ambient traffic, not a routing failure.** It absorbs every hostname/path that only has a fallback route. To prove YOUR service went direct: check per-cluster `upstream_rq_total` on the `httproute/<ns>/<route-name>` Envoy clusters (admin `:19000/stats?format=json`), or use a before/after delta for short bursts. Don't read high fallback volume as misrouted service traffic.

## PR-preview / templated route conflicts (Helm deep-merge)

4. **To disable HTTPRoutes in an overlay/preview values file you must set the routes map to `null`, never `{}`.** Helm deep-merges maps, so `{}` is a truthy empty map that gets refilled with the base/host values during merge → routes render anyway → preview pods collide with production on the shared Gateway (same hostname + prefix = first-match-wins traffic theft). `null` deletes the key entirely → the template's truthiness gate skips rendering. There is typically no `.enabled` flag on such a map — the gate is the truthiness of the whole map. This is a general Helm deep-merge trap, not Envoy-specific.

## ext-authz auth classification

5. **Detect auth-protected routes by the PRESENCE of the ext-authz label with any value, not by a specific value like `default`.** An Envoy Gateway `SecurityPolicy` targets HTTPRoutes by label; a setup often has several policies (e.g. a standard session policy, an embed policy, an agent/header policy) keyed by different label values. Checking only for one value misclassifies the others as bypass. A route with an empty label set (`labels: {}`) is the correct bypass pattern (skips all ext-authz policies).

6. **A bypass route (no ext-authz label) is not necessarily unauthenticated — the backend may validate its own token.** The HTTPRoute config can't tell you this; ext-authz is simply not involved. Testing implication: don't send an invalid bearer expecting an ext-authz 401 — any 401 comes from the backend, not the Envoy filter. Confirm with the service owner which bypass routes self-authenticate before classifying them as no-auth.

7. **Route names generated by a Helm template (`<serviceName>-<routeKey>` style) may not contain the literal service name — always drive off the exact `kubectl get httproutes` names, never a service-substring filter.** Same applies to Grafana/PromQL: match on the real `httproute/<ns>/<route-name>` Envoy cluster names, don't assume a `-api` suffix or a service-name wildcard.

8. **For session-cookie-auth routes, an invalid-bearer negative test is misleading — ext-authz validates the cookie, not the `Authorization` header.** Sending `Authorization: Bearer invalid` to a cookie-auth route still 401s (because the cookie is missing), which looks like a pass but proves nothing. Negative-test cookie routes with no-creds and an invalid cookie instead.

## Test-credential + traffic gotchas

9. **A CDN / WAF bot-defense layer can reject a request BEFORE your ext-authz filter ever sees it, producing false-negative auth tests.** When the service sits behind a CDN/WAF, a scripted request without a real browser `User-Agent` may get a CDN-level 403 (its own error code, not your 401). Always send a browser UA for tests through the CDN; it's not needed when hitting an internal/tailnet URL directly.

10. **Acquire test credentials the same way your test suite does — don't trust orphaned credential-store entries.** Reuse the programmatic path your automated tests use (e.g. the RPC/registration the test framework calls) rather than a stale shared-vault login that may not work against the target environment. Note whether the recipe is environment-scoped (a token minted against one cluster's auth service usually won't validate on another).

11. **Auth-protected routes show zero upstream stats for unauthenticated traffic — ext-authz returns 401 before the request reaches the backend cluster.** So upstream request-rate panels stay flat for auth routes unless you generate AUTHENTICATED traffic. If credentials aren't available, XDS config verification + a no-creds→401 negative test are the authoritative proof; the upstream counters legitimately remain 0. A response-code-class metric grouped by class (not route) is a coarse sanity check only, never route-specific proof.

## Deployment-aware validation

12. **A missing HTTPRoute is only a failure if the service is actually DEPLOYED on that cluster — check deployments/pods first.** Not every service runs on every cluster. If undeployed, its paths correctly fall through to the legacy fallback (which may return 200 without auth) — expected, not an auth gap, because no backend exists there. Classify: route-missing + deployed = FAILURE (auth gap); route-missing + not-deployed = NOT APPLICABLE. Only run auth tests on paths that have a direct HTTPRoute on that specific cluster.

## Incident-signature traps

13. **During an ext-authz fail-closed incident, downstream p99 latency can DROP rather than spike — a low-latency signal that looks like evidence the auth layer isn't involved is actually the fingerprint of it failing closed.** When the ext-authz backend starts erroring and its "ok" counter pins to zero, the proxy's fail-closed local 4xx responses are fast (no round-trip to the real backend), so the overall downstream request-time percentile falls at the same time the 4xx rate rises in lockstep with the ext-authz error rate. The diagnostic signature for "ext-authz is failing closed and rejecting everything" is precisely: error counter up, ok counter at zero, latency DOWN, 4xx rate up — the intuitive read ("latency is fine, must not be this layer") is backwards for this specific failure mode.
    - **Companion trap:** a range query whose end time is set past the environment's actual current time makes monotonic counters (like an uptime gauge) flatline identically across every series at the query's cutoff instant — that is query staleness, not evidence every instance restarted at the same moment.
