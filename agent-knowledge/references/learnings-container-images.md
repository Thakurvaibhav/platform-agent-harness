# Container Image Learnings — Build Cache, Layer Size, Diffing

Portable lessons on BuildKit cache, Docker/OCI layers, image diffing, and build verification.

## Build cache — what inline cache does and does not give you

1. **SUPERSEDED by #13 — CACHED-to-DONE progress updates do not prove execution; use exec output or cache records to establish misses.** **`BUILDKIT_INLINE_CACHE=1` + `--cache-from <prev image>` is `mode=min`: it records cache metadata for the FINAL stage only, so a multi-stage build's BUILDER stage is cached only when the whole build is a no-op.** Measured across real builds: two builds with changed source re-ran **all 25 builder vertices** including steps whose inputs had not changed (an `ssh-keyscan` at builder step 1/25), while a build of **unchanged** source marked all 25 CACHED. **So "every step CACHED" on an unchanged rebuild is NOT evidence the builder is cached** — the final result short-circuits and the builder vertices inherit that. **Proof method that actually discriminates: pick a step whose inputs demonstrably did not change and check whether it re-ran.**

2. **SUPERSEDED by #3 — The archived logs put the first miss before source COPY, so COPY ordering alone does not explain those misses.** **The usual cause of builder-stage misses is `COPY <source>` placed BEFORE the pinned dependency install — reordering is the real lever, and `mode=max` is not.** When source is copied at builder step 2, every later vertex (including multi-minute dependency installs) is invalidated by any source edit. Registry `mode=max` retains intermediate filesystem snapshots and is worth a few seconds at most against that; it also **requires the `docker-container` buildx driver**, not a plain `docker build`, so adopting it is a CI change and not a flag. Keep two things apart when quoting a saving: **no-change cache hits** (free, prove nothing) and **changed-source reuse** (the thing you are actually buying).

3. **Do not attribute a cache miss to a `COPY` that runs AFTER the first observed miss.** A grounding pass found the archived build logs showed the SSH-setup vertex already re-running *before* the source `COPY`, which refutes "the source copy causes these misses" on its own evidence. Likewise, a quoted "15.3 s / 11.2 s" for a requirements install turned out to be the **combined** requirements + wheels + application `RUN`. Read the vertex timings, not the stage summary.

## Layer size — attribution, and the arithmetic that is wrong

4. **Never estimate a saving by summing inherited layers — diff them by content hash first, then estimate the DELTA as a recompressed tar.** A final-stage `COPY` of a whole site-packages tree measured **319 MB** compressed, but SHA256 comparison showed **769 MB uncompressed of it was byte-identical to earlier tiers**; a synthetic gzip-6 tar of the genuine delta was **84.9 MB**. The defensible claim was therefore ~**293 MB** saved by a delta install, not the full `COPY` size. Corollary: a candidate saving quoted by one reviewer may silently include another candidate's saving (a 4.7-4.85 GB figure that included a 59 MB `chown` already counted elsewhere) — **de-overlap the candidates before adding them up.**

5. **A final-stage `COPY` of a directory that earlier stages already populated is the classic size antipattern, and it also produces a NEW layer digest on every single build.** Because `COPY` *merges* into an existing directory rather than replacing it, a builder-stage pip/uv downgrade leaves **both** dist-info directories behind (observed: `packaging-25.0` and `packaging-26.0` shipped together). And since the layer is rebuilt each time, every deploy pushes and every node pulls it — on a large agent image that was ~5 GB of new blobs per deploy. Install the delta in the runtime stage instead of copying the whole tree. Observed: a `<runtime-image>` image shipping `pandas 2.3.3` files beside a stale `pandas-3.0.1.dist-info` and 3.0.1-only modules, plus `importlib_metadata` 9.0.0 next to 8.9.0 and `packaging` 26.0 next to 25.0. Replacing the `COPY` with a delta install into the base env removed 82 stale paths on one image and 13 on another.

6. **A package-manager cache cleaned in a LATER `RUN` still ships in the earlier layer — fold `clean` (and any `chown -R`) into the RUN that creates the content.** Measured on micromamba/conda: a 391 MB layer was ~93 MB of environment plus ~298 MB of `/opt/conda/pkgs` cache; a 2,564 MB env-creation layer carried ~945 MB of incompressible `.conda` archives plus 1,281 MB of extracted cache because `mamba clean` ran in its own `RUN`. The same applies to a separate `chown -R` over a large tree, which duplicates every file it touches into a new layer (observed: 709 MB of pure duplicate).

7. **Attribute apt bloat with the dpkg `Depends` CLOSURE, not with intuition — and expect the closure to reach further than you think.** Compute the exclusive closure of the packages you want to drop (everything reachable from them and from nothing you keep), then size each package's own file payload. Two results that repeatedly surprise reviewers: **(a) removing a "small" package may remove nothing**, because a large package depends on it too (`software-properties-common` alone was 8 MB because `texlive-latex-extra` also pulls Python); **(b) a media package drags in the graphics/LLVM stack** — `ffmpeg → libavdevice59 → libgl1 → libglx0 → libglx-mesa0 → libgl1-mesa-dri → libllvm15`, ~132 MB gz exclusive, replaceable by a ~29 MB gz static `ffmpeg` build. Also check for content a package GENERATES that is not in any dpkg file list (a TeX install wrote ~60 MB gz of `/var/lib/texmf`), and for a runtime that shells out to a toolchain you were about to delete.

8. **Recompressing layers gzip → zstd buys far less than the marketing number, and it imposes a runtime floor — measure both before proposing it.** Measured on five SHA256-verified real layers: **1,582.9 MB gzip → 1,482.6 MB zstd-3, a 6.34 % saving**, not the 10-20 % commonly quoted; zstd-9 reached ~11-17 % on the same corpus. Separately, zstd layers need a containerd/runtime floor across the **whole** node fleet — census the fleet's containerd version first (one straggler node is enough to break pulls), and note that a version census proves only the decoder floor: no image has actually been deployed.

## Measuring and diffing images without Docker

9. **`crane` reads and exports images with no Docker daemon, which is what makes layer forensics possible from a laptop or a sandboxed agent.** `crane manifest --platform linux/amd64 <ref>` for per-layer digests and sizes; `crane export <ref> - | tar -tv` for the flattened filesystem; `crane blob` for a single layer. On a machine with no Docker Desktop, isolate the config — `export DOCKER_CONFIG=<empty dir>` plus a registry token login (`learnings-gke.md`). Cost at the scale measured: a ~2 GB image exported in 72 s / 166 MB RSS, a ~16 GB image in 495 s / 317 MB RSS; write a TSV, not the files.

10. **Four `crane`/tar quirks that silently corrupt an image diff.** Verified against **crane 0.22.1** (go-containerregistry): **(a)** `export` handles `.wh.` and `.wh..wh..opq` whiteouts correctly (`mutate.go:346,351`) but **silently drops relative symlinks that escape the rootfs** (`:331`) — those files simply vanish from your inventory. **(b)** The tar `mode` field carries file-type bits on some layers (`100755` where another layer says `0755`), so mask with `& 07777` before comparing permissions. **(c)** A raw `.pyc` hash differs on **every** build because the 16-byte header holds the source mtime — hash `bytes[16:]` instead. **(d)** Even then, `marshal` is not fully deterministic: one `.pyc` differed with a byte-identical `.py`. Treat a handful of residual `.pyc` differences as noise, not as a finding.

11. **Two builds of the SAME commit are not byte-identical when any dependency floats, so an equivalence proof must build old and new BACK TO BACK through the same pipeline — or enumerate the drift.** Observed on two prod builds of one commit: a transitive `google-auth 2.59.0` vs `2.59.1`, plus `RECORD` / `uv_cache.json` / `direct_url.json` churn for locally-built packages. Across two adjacent commits, **1,050 of 1,176 changed files were third-party dependency bumps, not application code** — so a naive file-count diff between two tags measures the index, not the change. Related identity trap: a file inside the image may not match the commit the image is tagged with, if a *different* service's build injects it; check the injecting pipeline before using image contents as ground truth for a commit.

## BuildKit cache keys, progress output and the exporters

12. **A failing `--cache-to` cancels the image push unless you set `ignore-error=true`.** BuildKit v0.33.1 runs image finalize (manifest push) and remote cache export **in parallel in one errgroup** (`solver/llbsolver/solver.go` ~414-438), so a best-effort cache export that errors takes the whole build down with it; `ignore-error` is honoured at `solver/llbsolver/export.go:139-141`. Note also that buildx still turns `--build-arg BUILDKIT_INLINE_CACHE=1` into an inline cache exporter (`buildx build/opt.go:262-269`, v0.37.2), and inline + registry exporters coexist (`splitCacheExporters`) — so "I only configured registry cache" can be false.

13. **`--progress=plain` reprints a CACHED vertex as `DONE` when the next step unlazies it, so a last-status-wins log parser reports the last cached step before the first miss as a RE-RUN.** The lazy cached ref is unlazied through a `progress.Controller` carrying the vertex digest but **no `Cached` flag** (buildkit v0.33.1 `solver/jobs.go:1192-1197`, `util/progress/controller/controller.go:42-48,61-69`, `cache/remote.go:353-356`, `cache/refs.go:1406-1409`), and progressui replaces the vertex so `Cached` becomes false (`progressui/display.go:683-684`, `printer.go:189-205`). Discriminate by **exec output lines** (`#N <secs> <text>` — only a step that ran has them) or by cache records (same record digest + same result layer blob across rounds = reused). On an ephemeral builder the reported `DONE` time is mostly the base-image pull the cold build paid under `FROM`.

14. **`FROM <tag>` is keyed on the INDEX digest, and a buildx provenance attestation changes that digest on every push — so a tag-chained multi-tier build can NEVER hit registry cache.** BuildKit v0.33.1: `FROM` cache key = `mainManifestKey(resolved desc)` (`source/containerimage/pull.go:176-186`, whose comment explicitly rejects a diffID alternate key) and the tag resolves to the index digest (`util/pull/pull.go:178`). Default `--provenance=mode=min` writes `invocationId` + `startedOn`/`finishedOn` into the attestation, so identical content yields a new index digest every time. **Fix: chain tiers by the platform manifest digest** (`buildx imagetools inspect --raw`, select `linux/amd64`), or disable provenance. Expect **one cold build per environment** when you switch, then normal no-change rebuilds. A second, smaller effect: two no-op `RUN`s share the empty-layer blob, and cache import gives both one `createdat`, so the amd64 manifest can also change with identical layers and diff_ids.

15. **`COPY --chmod` sets the mode of the destination directory it CREATES on new BuildKit, and did not on old — so moving a build from `docker build` to buildx can make a directory untraversable.** fsutil commit `183e7fb` (2025-02-25) changed `prepareTargetDir`'s `MkdirAll` from a hardcoded `0755` to `c.mode` (`copy/copy.go:169-173` as vendored in buildkit v0.33.1); Docker 20.10.24 (`gcr.io/cloud-builders/docker`) embeds buildkit `eeb7b65`/fsutil `0834f99`, which hardcodes `0755` (`copy.go:142`). Proved from layer tar headers: `drwxr-xr-x` vs `d---------`. Children got `--chmod` in both versions. **Any Dockerfile with `COPY --chmod=<no-x mode>` into a NEW directory is affected.**

16. **`COPY --chmod=755` of a whole tree sets EVERY file to 0755, not just directories.** Measured: a runtime-stage `COPY --chmod=755 --chown=<user>` of site-packages left 36k files at 0755 (e.g. `numpy/__init__.py`) where the source tiers had natural pip modes (0644). So any delta-install replacement of that `COPY` **cannot be mode-identical** to the old image — ~all files go 0755 → 0644. Declare that as a deliberate change, not rebuild noise.


17. **`buildx --secret id=X,src=PATH` is read by the buildx CLIENT from its own filesystem, never from the transferred context — so `.dockerignore` can exclude the key files from every `COPY` while `--secret` still resolves them.** buildx v0.23.0 `controller/pb/secrets.go:8-17` → buildkit v0.21.0 `session/secrets/secretsprovider/store.go:18-34` (`os.Stat` at build start), `:51-59` (`os.ReadFile`), relative to the client cwd. Two traps when you GENERATE a `.dockerignore` into a build tar that also carries caller uploads: BuildKit prefers `<Dockerfile>.dockerignore`, so merge into **both** the caller's `.dockerignore` and `Dockerfile.dockerignore`; and archive each member name **once** — a duplicate tar member silently drops one rule set.

18. **Cloud Build docker steps get a STATIC `oauth2accesstoken` in `/builder/home/.docker/config.json`, minted at step start with ~3600 s of life and never refreshed — so any push more than ~60 minutes into a step 401s.** Measured: same token sha, `expires_in` 3597 → 3447 after 150 s. The builder image (Docker 20.10.24, buildx v0.23.0 / BuildKit v0.21.0) has no `gcloud` and no `docker-credential-*` helper. BuildKit's authprovider re-asks the client every 4m50s (`session/auth/authprovider/authprovider.go:48-68,268-292`) but the client just returns the same in-memory static auth. **Fix: write a shell `docker-credential-<name>` that curls the metadata token and add `credHelpers[<region>-docker.pkg.dev]`; credHelpers takes precedence over the `auths` entry** (verified: pull OK and `buildx build --push` via the docker-container driver OK, and the minted token is never persisted into `config.json`). Proven on a cold 6-tier build that pushed its last tier at 65 min.

19. **buildx credential resolution is LAZY and TTL-refreshed, not once per invocation — so a short probe build invites exactly the wrong generalisation.** Measured (buildx v0.23.0): one helper INVOKE at t = END-1s, i.e. at the push, not at build start; and buildkit's authprovider expires a cached auth config after **4m50s** (`DockerAuthProviderConfig.ExpireCachedAuth`, whose comment names the 5-minute Artifact Registry WI token). Consequence: a metadata credHelper fully fixes #18 with **no per-build ceiling**. A probe shorter than 4m50s shows COUNT=1 and suggests a false "once per invocation, so an N-minute ceiling" rule — **size the probe past the TTL before concluding.**

20. **A shell credential helper that pipes `curl` into a parser fails CLOSED on DNS/HTTP errors but HANGS FOREVER on a server that accepts TCP and never answers — `curl` has no default timeout and `set -e` is not a deadline.** Reproduced twice independently (and once by an adversarial review lens): the unbounded form was still hanging at 60 s against a stalled socket, while `--connect-timeout 5 --max-time 30` exits 1 at exactly 30.0 s and still mints a real token when the metadata server is healthy. **Always run the unbounded form as the control-of-the-control** — without it, "BOUNDED" is a vacuous result. Test stalled-response paths, not only immediate errors.

21. **Cloud Build shares one docker volume `homevol` at `/builder/home` with `HOME=/builder/home` in EVERY step, and steps share the host docker daemon — so a buildx builder created in one step is found by a later step.** Source: `GoogleCloudPlatform/cloud-build-local` `build/build.go:54-57, 464-466, 1325`; builder metadata lands in `/builder/home/.docker/buildx` and the docker-container node starts lazily on first build. A review bot flagging "builder lost across steps" is a **false positive** by this source (hosted behaviour inferred from the local reference implementation).

22. **`gcr.io/cloud-builders/docker` measured contents (2026-10-05):** python3 3.8.10, curl 7.68.0, Docker 20.10.24, buildx v0.23.0, `HOME=/builder/home`, and a ~93 KB `/builder/home/.docker/config.json` with keys `['HttpHeaders','auths']` holding a static `oauth2accesstoken` for **every** `*-docker.pkg.dev` host. Useful when deciding whether a build step can mint its own credentials.

23. **`--mount` target directories that did not already exist are left behind as EMPTY DIRS in the layer on BuildKit < v0.11.** `executor/stubs.go` removes a stub only when `st.Size()==0`, and an ext4/overlay directory has size 4096; v0.11.0 added the `IsDir`+`ReadDir` empty check. Docker 20.10.x vendors BuildKit v0.8, so a bind mount at a new path ships an empty root-owned directory unless a later `RUN` removes it (`rm -df`). **File** stubs (size 0) are removed even on v0.8.

24. **Compressing layers at `compression-level=1` is a bad trade for a base image every node pulls.** Measured on one tier: layer export 103.8 s → 36.4 s, but new layers 1,417.6 → 1,576.7 MB (**+11.2 %**). That is +~11 % pull bytes per node on every deploy against a once-per-base-build saving of ~1 minute per tier. Evaluate the export-time saving against repeated fleet pull costs.

## Proving a Dockerfile change without running the build

25. **An image's layers map 1:1 to its instructions, so `crane manifest` settles ordering and "does this RUN write anything" questions offline — and BuildKit's EMPTY layer has a fixed tell: 32 bytes at `sha256:4f4fb700ef54…acc1`.** Two instructions in one real image (an R import test, and a standalone recursive `chmod a+rX`) were both that empty layer, proving each writes nothing to the filesystem and can be reordered or folded. **Ask of any offline layer *replay*: which layers did it NOT include, and is the changed step one of them** — one author's replay silently skipped three of the layers the question turned on. The rendered-proof equivalent for a Dockerfile PR is (a) a shell **exit-status truth table** over every single-command failure in the merged `RUN` chain plus (b) the published layer manifest.

26. **In `A && B && { C && D || true; } && E`, a failing `C` exits 0 for the whole RUN — `|| true` covers the whole brace group.** Proven by truth table over all 8 combinations. When a merge makes `C` (e.g. `mamba clean`) the load-bearing step for a size saving, **scope `|| true` to only the command that needs it** (typically a `find -exec rm -rf` that returns non-zero after removing a directory it then descends into), or a failed clean ships the cache with a green build.

27. **A `#` comment INSIDE a Dockerfile line continuation is stripped by the parser and is safe — unlike raw `sh`, where it would become argv.** Proven twice: (a) a real Cloud Build log shows the merged `RUN` with the indented comment line absent and the adjacent version pin intact and resolved; (b) the dockerfile frontend 1.21 parser preserved the pin, with a raw-shell negative control that failed. So an indented `# why` line between continued args is a legitimate way to comment a long `RUN`.

28. **Replace an unconditional `chmod -R`/`chown -R` with a `find` predicate that only touches entries whose mode would change — an unconditional recursive chmod copies up every file in overlayfs even when BuildKit's diff later drops the unchanged ones.** The exact `a+rX` equivalent (coreutils skips symlinks), exhaustively checked over 2×4096 modes: `find DIR ! -type l \( ! -perm -444 -o -perm /111 ! -perm -111 -o -type d ! -perm -111 \) -exec chmod a+rX {} +`. This is what turns a 700 MB `chown` layer into the 32-byte empty layer of #25.

29. **A `find`-based build assertion of the form `test -z "$(find PATH … -print -quit)"` FAILS OPEN three ways.** Reproduced: a missing PATH, an unresolvable `-user NAME`, and any other `find` error all print nothing to stdout and exit non-zero, and `test -z` discards that status, so the check PASSES. Hardened form: `id USER >/dev/null && test -d PATH && o=$(find … -print -quit) && test -z "$o"` — an assignment's exit status IS the command substitution's, so the failure propagates. Applies to every `verify_container`-style image assertion.

30. **A conda/mamba `create` REUSES the package cache of a preceding `install` in the same layer chain, so cleaning between them re-downloads and changes the shipped `urls.txt`.** Measured: 12 packages present in the install step's `urls.txt` were not re-appended by the create step. The fix that keeps the final filesystem identical is **install + create + chmod + clean + find-fixups in ONE `RUN`**. Note `/opt/conda/pkgs/urls.txt` survives `mamba clean --all` and ships in the final image, so it is a diff-visible artifact.

31. **Folding two conda `RUN`s into one makes the packages both environments share HARDLINKED between them, where separate RUNs gave independent copies — overlay copy-up breaks cross-layer hardlinks.** Observed: 12 shared packages / 588 paths became same-inode from the shared `/opt/conda/pkgs` extract. Content, owner and mode are identical, but an image-diff tool reports them as changed-content `file → hardlink`. If strict identity is required, `mamba create --copy` is the candidate (verify libmamba symlink handling first).

32. **`micromamba clean -all` is NOT `--all`: CLI11 parses the single-dash form as `-a -l -l`, i.e. `--all --locks`.** Verified on micromamba 1.5.10 (`clean --help`: `-a,--all` = index cache + lock files + unused pkgs + tarballs; `-l,--locks` = lock files). So the long-standing idiom happened to be a superset and dropping a later redundant `clean` is a no-op — proven by a tier-only rebuild whose image diff was 12 changed-content entries, all rebuild noise (fontconfig caches, `conda-meta/history`, a `urls.txt` whose sorted URL set is identical), 0 added/removed, config identical.

33. **A platform selector that matches only `architecture` can pick the wrong image — always match the `(os, architecture)` PAIR.** Reproduced: an OCI index listing `[attestation(unknown/unknown), windows/amd64, linux/amd64]` resolved to the **Windows** digest because `next()` took the first entry satisfying `architecture == "amd64"`. The defect can stay latent when `--platform linux/amd64` is hardcoded and the pushed index holds one real entry. Use `m.get("platform", {}).get("architecture")`, never `next()` over a generator that can raise `KeyError` mid-iteration — that aborts even when a valid entry exists later in the list. Found by an adversarial (second-model) review lens and missed by the correctness lens.

34. **To prove two `.pyc` files differ only as marshal noise, unmarshal both (`bytes[16:]`) with the matching CPython minor version and compare the code objects.** Compare `==` plus recursive `co_code` / `co_consts` / `co_names` / `co_linetable` / `co_exceptiontable`. Equal objects with different bytes = `FLAG_REF`/ref-table non-determinism, not different source. Observed in the wild: the *same two* byte-variants of one module flipping between control and candidate across unrelated images, which is the signature of noise rather than a real change. (Sharpens #10(c)/(d).)

35. **To prove a `chown` relocation changes nothing, enumerate every reference to the chowned path AFTER each chown position on BOTH refs** — `git show <ref>:<file>`, then index the lines past the chown. On a real tier-0 Dockerfile this reduced to a single writer (a `wget` shim) that was root-owned on both sides, i.e. not a regression. Two independent review lenses reached the same answer by this method, which is itself the evidence that the method — not the reviewer — did the work.

36. **A cheap single-tier A/B: build only the changed tier with `--cache-from <parent build>-cache` and NO `--cache-to`.** Layers before the changed `RUN` are reused, so the image diff isolates the change instead of drowning in environment drift. Two CLI traps found doing it: a local `gcloud` without the `beta` component must use `gcloud builds submit` (GA), and `crane digest` returns the **amd64 platform digest**, which differs from the index digest `gcloud artifacts tags list` shows (see #14).

37. **Two Cloud Build config traps.** (a) A substitution **declared** in the YAML but no longer **referenced** after trimming a step makes `gcloud builds submit` fail with `INVALID_ARGUMENT: key _X in the substitution data is not matched in the template` — keep a harmless `echo` of it. (b) A multi-line `python3 -c` inside a `- |` block scalar works without `textwrap`: write the Python at the block's base indent, YAML strips it so Python sees column 0, while the surrounding bash stays indented. Verify by YAML-loading `args[1]`, replacing `$$` with `$`, and sourcing the extracted function with a stubbed `docker`.

38. **Selecting a CPU-only wheel variant without forking the lockfile: in the SAME `RUN`, first `pip install --no-deps --index-url <alt> -c <lock> <pkg>`, then `pip install -r <lock>`.** Verified against real pip 26.2.1 with local wheels: the CPU path keeps the `+cpu` build and installs **no GPU-only deps**; the public index path resolves exactly as before (installed-candidate deps *are* resolved in step 2); a lock/index version mismatch fails `ResolutionImpossible`; an empty `--index-url` fails `No matching distribution`. The mechanism is that **pip retains an installed local-version build (`2.10.0+cpu`) against an unqualified public pin (`==2.10.0`)** — `commands/install.py` uses to-satisfy-only without `--upgrade`, `resolution/resolvelib/provider.py` prefers installed, and packaging specifiers accept local versions for `==<public version>`. Reproduced with the real cp313 manylinux CPU wheel against 184 lock pins: proposed installs `[]`, `pip check` clean; the public-index negative control required 15 NVIDIA packages plus triton/cuda-bindings/cuda-pathfinder. This proves **resolution and metadata**, not runtime numerical parity. Why not a `+cpu` lock: a macOS host resolves plain `2.10.0` (mac wheels have no `+cpu`), and with `--python-platform` forced the exported index URL is PyPI only, so pip cannot install it — one variant-neutral lock serving both builds is the simpler shape.

39. **Image size on containerd is the COMPRESSED size.** containerd v2.2.7 `internal/cri/store/image/image.go:50-51,157` (`Size` = compressed, `usage.CalculateImageUsage`) feeds CRI `ImageStatus` (`image_status.go:69`), so `Node.status.images[].sizeBytes` and the kubelet `image_size_in_bytes` buckets match the registry's reported `imageSizeBytes` (measured delta ~17 KB = manifest + config on a 15.8 GB image). `kube_pod_container_info`'s `image_id` equals the registry `uri` verbatim, so a digest join works.

40. **Cloud Build ECHOES the request's `images` list into `build.artifacts.images`, and that is where an image→build association (and therefore the next build's `--cache-from`) comes from — so switching to `buildx --push` with `images=[]` silently empties it.** Cloud Build **cannot** keep `images=[tags]` alongside `buildx --push`, because it pushes from its local daemon where a `docker-container` build never lands. Associate the computed tags explicitly instead.

41. **A caller-uploaded `/Dockerfile` can silently replace yours inside a build tar.** Caller files appended after your own are distinct tar members in Python `tarfile`, but **GNU tar strips the leading `/` on extraction and the last entry wins**. Any check on "the Dockerfile" must normalise member names and look at the caller payload too.

42. **Registry cache `mode=max` EXPORTS every stage's layers, so a builder stage that writes a secret into a layer publishes it to anyone with registry read.** Observed pattern: a builder `RUN` that `cp`s each mounted deploy-key secret to `/root/.ssh/*` and never deletes it — harmless while only the final stage ships and cache is `mode=min`. **Before enabling `mode=max` on any multi-stage build, check that no non-final stage writes a secret into a layer**; mount secrets at their final path (`mode=0400`) instead of copying them. Also check for Dockerfiles that live OUTSIDE the repo — a downstream project may ship its own copy of an old template with the same `cp`-the-secret pattern, in which case `mode=max` must be gated off for custom Dockerfiles carrying `type=secret`.

43. **`rsync`ing a developer's working tree into a build context ships their local `src/*.egg-info`, and setuptools then copies the stale metadata into `dist-info` and reuses its `SOURCES.txt` for package data when no git is present.** Consequence: a FIRST build from a fresh worktree ships **fewer** `dist-info` files than later builds from the same tree, which reads as a real diff in an A/B. Run a sync in both worktrees before the first build, or rebuild the first image.

44. **`MAKEFLAGS` set in a `RUN` reaches `R CMD INSTALL` because callr's `rcmd_process`/processx inherit the environment** (`callr rcmd-process.R:52-57`, `processx process.R:171`), and **GNU make 4.3/4.4.1 `-l` reads the runnable count from `/proc/loadavg`**, which is a VM-wide bound rather than a per-invocation one. Measured on a 32-vCPU builder: a baseline source-build `RUN` of 2,068.7 s dropped to 939.3 s at `-j4 -l$(nproc)` and only to 903.6 s at `-j16`, while minimum available memory fell 19.1 → 8.2 GB — so **`-j4` captures nearly all of the win at the lowest memory risk**. Individual packages floor out regardless of `-j` (one stayed at ~320 s), which is the tell that the remaining time is a single-package serial compile, not parallelism you can buy.
