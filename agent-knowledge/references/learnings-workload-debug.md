# Workload Debugging Learnings

See also: `learnings-observability.md`, `learnings-helm-ci.md`, `learnings-k8s-sa.md`, `learnings-gke.md` (the cluster PLATFORM underneath these workloads -- node-pool capacity, drains, upgrades)

Kubernetes workload debugging patterns where the obvious check reports the opposite of the real state -- probe and restart semantics, native-sidecar visibility, image-level container-start failures, resource-constrained scheduling, and recognising when a client-reported error is actually correct.

Numbered, append-only. **Update the existing entry — never duplicate.**

## Probes and pod status

1. **A failing STARTUP PROBE can masquerade as a healthy pod: if the container exits 0 on `SIGTERM`, the kubelet's probe-triggered kill shows up as `Running` with a CLIMBING RESTART COUNT -- not `CrashLoopBackOff`.** The diagnostic that names it immediately: the restart interval equals `failureThreshold x periodSeconds` exactly (a `failureThreshold: 20`, `periodSeconds: 15` probe restarts the container every 300 seconds, on the dot). Confirm the actual failing path from INSIDE the pod before touching the chart -- `kubectl exec ... -- wget -qO- -S localhost:<port>/<path>` against the exact probe endpoint. A common root cause: the chart's probe path does not match the path the application actually serves (probing `/health` when the app serves `/api/<service>/health`).

2. **`kubectl ... -o jsonpath='{.spec.containers[*].name}'` returns a FALSE NEGATIVE for native (Kubernetes 1.29+) sidecars.** Native sidecars live in `.spec.initContainers` with `restartPolicy: Always`, so `.spec.containers` lists only the main application container while the pod still reports e.g. `3/3 Ready`. An investigation that inspects only `.spec.containers` can wrongly conclude a workload has no connection to a companion process -- a proxy, a log shipper, a database sidecar -- that is in fact running right next to it. **Correct check: query `.spec.initContainers[*]` too -- or simply trust the mismatch itself**, since fewer containers listed than the pod's own Ready count reports means native sidecars are present.

## Container never starts — causes that live in the image

3. **Two "the pod is scheduled but the container never runs" causes that live in the IMAGE, not the chart or manifest:**
    - **A required environment variable with no usable default.** A vendored SDK can validate-and-require an env var whose documented development default is inert because the image sets `NODE_ENV=production` (or an equivalent production-mode flag) which disables dev defaults. The pod clears scheduling and container creation, then `CrashLoopBackOff`s with a "missing required environment variable" message and a non-zero exit code. **Fix: set the variable explicitly wherever the workload is enabled, and make the chart's own default a LOUD sentinel value (e.g. `CHANGE_ME_<VAR>`) so a missing override fails at render time, not at runtime** -- a chart with no key for the variable at all only surfaces the defect live, in production.
    - **`CreateContainerConfigError: container has runAsNonRoot and image will run as root`** happens when the pod spec sets `runAsNonRoot: true` with no `runAsUser`, AND the image itself declares no `USER` -- so the kubelet resolves uid 0 from the image's own config and refuses to start it. **The fix belongs on the image side**: adding a non-root `USER` directive after any layers that need root (package installs, build steps) is normally sufficient, and several common base images already ship a pre-created non-root user for exactly this reason. **You can prove the fix works without a full rebuild**: build a minimal image on the same base with and without the `USER` directive and compare `docker inspect --format '{{.Config.User}}'` between the two.

## Scheduling and capacity

4. **Constrained-resource headroom (GPU, or any schedulable resource limited to a subset of nodes) must be filtered through the workload's own `nodeSelector`/`tolerations`/affinity rules before you call it available -- never computed fleet-wide.** A cluster-wide "N allocatable minus M allocated" can show free capacity that the workload in question structurally cannot reach, because the free unit sits on a nodepool the workload's own selector excludes. **Second, equally load-bearing half: if the compatible nodepool is healthy and simply below its configured maximum, a pending pod is "Pending until cluster-autoscaler scales up," not structurally deadlocked** -- check autoscaler headroom (max nodes vs current nodes on the compatible pool) before reporting a scheduling failure as a hard deadlock. Report those as the two different states they are.

## When the error is correct

5. **A "read-after-write race" hypothesis for an intermittent 404-after-create is refutable two cheap ways, before reaching for retries or backend changes: infra topology and client source.**
    - **Infra:** if the service's database access path points only at a primary/writer instance -- no read-replica pool, no replica connection string in play -- there is no replica for a read to lag behind, so a replication-lag explanation is off the table by construction.
    - **Source:** read the client at the exact version deployed. If the client generates the entity's id on its own side, seeds an optimistic local cache with it, and only THEN makes the backend call that would actually create the row, then a request racing ahead of that backend call is hitting a row that genuinely does not exist yet -- the 404 is architecturally correct, not a race.
    - **When the 404 is correct, the real defect is almost always in the banner or error-handling path, not the backend.** Suppression logic keyed to a client-local flag (a `sessionStorage` entry, an in-memory variable) silently stops working the moment the same action happens in another tab, for another user, after a reload, or via a shared link -- and a short retry policy then surfaces a dead-end error banner for what is functionally just a timing issue on first load. **General rule: once a not-found response is shown to be architecturally correct, stop tuning the backend and go read the client's retry and suppression policy instead.**

6. **StorageClass is NOT portable across clouds, and a PVC-backed debug capture has two ways to destroy its own data.** For a long-running capture (memray, heap dumps, profiles) written to a container path: back that path with a PVC and set **`strategy: Recreate`** -- an RWO volume deadlocks a rolling update, because the new pod cannot attach while the old one still holds it. The class name differs per cloud: `premium-rwo` (pd-ssd) is GKE-only; on EKS use the gp3 default (`auto-ebs-sc`, encrypted) -- **`gp2` is the legacy in-tree driver with no volume expansion.** Both defaults are `reclaimPolicy: Delete`, so **`kubectl delete -f` on a manifest holding BOTH the PVC and the Deployment destroys the capture you just collected** -- split them across separate files. Check whether the image runs as root before adding `fsGroup`; if the image config declares no `USER`, the mount needs none.

7. **An error logged INSIDE a streaming loop amplifies ONE failure into N log lines -- never read raw log counts as distinct failures.** A helper-generation failure returned "not persisted" without marking the task terminal, so the enclosing `async for chunk in ...` loop re-checked the same already-failed task and re-logged an ERROR on EVERY subsequent chunk. Downstream, a single failed generation looked like a ten-fold incident. Two rules: (1) before treating a log-volume rise as an incident, establish whether the emitting site sits inside a per-chunk/per-item loop, and count DISTINCT ORIGINATING TASKS rather than lines; (2) "retried 3 times" in such a message may mean three fresh upstream calls rather than three retries of one -- read the retry helper before quoting the number. The blast radius is often NOT cosmetic even when the primary path is unaffected: here the failed sidecar record broke grouping downstream, so the UI silently dropped content while the main response was fine.

8. **A burst of identical credential-init failures during a large simultaneous rollout is metadata-server CONTENTION, and node age refutes the obvious alternative.** 8 of 12 pods failed their cloud-SQL-proxy sidecar with `could not find default credentials` exactly ~10 s after container start -- the sidecar's ADC timeout -- then succeeded on automatic restart, during a roll of ~56 pods across 7 deployments. **The node-age hypothesis was REFUTED by direct check, not by correlation:** restarted pods and clean pods sat on nodes of the same three ages. Establish a baseline first (here: zero such restarts over the preceding 3 days, so it is load-dependent and new, not chronic). It self-heals, but each occurrence costs a pod ~10 s of readiness on every rollout -- which makes it a latent bug worth its own ticket rather than noise to filter.

## Node pools, drains and config precedence (GKE)

9. **GKE node-pool DELETION does NOT respect PodDisruptionBudgets by default, and the common belief that it honours them and then force-deletes after a timeout is WRONG -- there is no timeout margin.** `--respect-pdb-during-node-pool-deletion` is an explicit per-pool opt-in (Google Cloud SDK 583+); a pool with no `nodeDrainConfig` bypasses PDBs immediately on delete, and a Terraform `destroy` of the node-pool resource inherits that behaviour. **Always require a manual cordon plus drain before deleting a pool that hosts quorum workloads -- the manual drain IS the protection, not the platform.** Verify with `gcloud container node-pools describe <pool> --format=json | jq 'has("nodeDrainConfig")'`.

10. **Node-pool drain protocol -- six rules, four of which cost a real incident when skipped.** (1) See #9: drain manually, the platform will not. (2) **CORDON EVERY NODE IN THE POOL BEFORE DRAINING ANY**, or evicted pods reschedule straight back onto the pool -- this actually happened, with two nodes *gaining* pods mid-drain (15 to 16, 17 to 21). (3) **A CNI component that tolerates `node.kubernetes.io/unschedulable` re-lands on cordoned nodes and is always the last pod left** -- do not read it as a failed drain. (4) **`kubectl drain` keeps working in the background** -- check counts twice before concluding pods are stuck. (5) **A StatefulSet with `podManagementPolicy=OrderedReady` will never recreate replica N+1 while replica N is unready**, so evicting from a pool that holds one crashlooping replica takes the whole set down. (6) Order nodes lightest-first, and for a PDB-constrained StatefulSet wait for full rollout status between nodes.

11. **A node pool's configured `max_node_count` can be UNREACHABLE by pod-CIDR arithmetic, so "reduce the max" may be a no-op and "this pool can absorb that workload" may be false.** A pool with no explicit `network_config` draws pod IPs from the CLUSTER-DEFAULT secondary range. **Real ceiling = (pod range size) / 2^(32 - podIpv4CidrSize).** Observed: a pool configured `max_node_count=300` whose pod range was a `/18` (16,384 IPs) at the 110-pod default (`/24`, 256 IPs per node) had a HARD CAP OF 64 NODES. **Ground it from the API, never infer:** `gcloud container node-pools describe <pool> --format="yaml(networkConfig,podIpv4CidrSize,maxPodsConstraint)"`, and cross-check the denominator against `clusters describe` -> `ipAllocationPolicy.defaultPodIpv4RangeUtilization` (0.0938 == 6/64 confirmed the arithmetic). **Always check this before claiming a pool autoscales enough to absorb a deleted pool's workload.**

12. **A node pool with "no custom labels and no taints" is NOT untargetable -- every node still carries `cloud.google.com/gke-nodepool=<pool-name>`, a perfectly good `nodeSelector`/affinity target.** So when arguing a pool is safe to delete, **the claim to prove is "nothing DOES target it" (sweep live pods for a positive `nodeSelector`/affinity, plus a repo grep), never "nothing CAN target it".** Filter DaemonSet pods out of that sweep: their controller injects `matchFields: metadata.name In [<own node>]`, which looks like a pool affinity and is not.

13. **A clean `kubectl diff --server-side` is NOT proof a config change takes effect -- it only proves the OBJECT will look how you expect.** For any component that layers config sources (a CNI's felix/cilium agent, kubelet, Envoy), check the PRECEDENCE TABLE and whether a higher-ranked source already pins the field. **Worked case:** GKE's addon-managed Calico sets `FELIX_LOGSEVERITYSCREEN=info` as a CONTAINER ENV VAR on the DaemonSet, and felix ranks its sources `Default(0) < DatastoreGlobal(1) < DatastorePerHost(2) < ConfigFile(3) < EnvironmentVariable(4) < InternalOverride(5)` (`felix/config/config_params.go:64-71` at v3.30.4) -- so `logSeverityScreen` on `FelixConfiguration/default` applies cleanly, shows a clean diff, AND DOES NOTHING. Editing the env var is reverted, because the DaemonSet carries `addonmanager.kubernetes.io/mode=Reconcile`. (Side note: the default `FelixConfiguration` instance has no addonmanager label -- the CRD does -- so it is not itself reconciled; moot given precedence.) **An offline proof for a config change must show that the VALUE THE PROCESS USES changes, not that the CR changed.** The remaining levers in that situation are external (a log-ingestion exclusion) or structural (migrate off the addon).

14. **An "allocatable divided by request" packing table is NOT achievable density -- subtract DaemonSet/system overhead AND native sidecars before quoting a number.** Two deductions, both easy to forget: (a) **DaemonSet plus system overhead** (measured: 11-13 pods, ~1.21 CPU / 1.61 Gi on an 8-vCPU node); (b) **native sidecars counted in the pod request** -- `restartPolicy: Always` init containers add their requests to the pod (measured: +60 m CPU / +96 Mi per pod from two such sidecars). On one node type the honest budget was **6.698 CPU / 26.12 Gi / 20 pod slots, not 7.91 / 27.7 / 32**. Also: **a gVisor `RuntimeClass` declares no `overhead`, so the sandbox runtime costs the scheduler nothing -- and is correspondingly unbounded.**

15. **Repointing an affinity at a surviving node pool is insufficient if the workload's DEFAULT RESOURCE REQUEST exceeds the new pool's allocatable -- check both dimensions before calling a pool a safe migration target.** A workload defaulting to 8 CPU / 32 Gi cannot land on a pool whose allocatable is 7910 m / 27.7 Gi: BOTH axes fail, so the pods fit nowhere and must be DELETED before the old pool is removed, not migrated. **Compare against `kubectl get node -o json` `.status.allocatable` on the proposed target, not against the machine type's nominal size.** Redirect targets are often NOT symmetrical -- if the only surviving pool with a given accelerator is also taint-gated for a sandbox runtime, a workload that needs the accelerator *without* that runtime has NO VALID HOME AT ALL, and the migration is actually a deletion decision.

## Startup budgets, image streaming and single-replica volumes (GKE)

16. **Never size a pod-readiness budget against IMAGE SIZE -- measure `PodScheduled -> Ready` percentiles on the live pool first, because app boot usually dominates and a cached pull is nearly free.** Measured on a production cluster from live pod conditions (n=225 warm-pool sandbox pods): **p50 38 s, p90 43 s, p95 159 s, min 24 s** against a 29 s effective budget -- **82.7 % exceeded it**. Stage split: `Scheduled -> Initialized` p50 15 s, `Initialized -> ContainersReady` p50 23 s, `ContainersReady -> Ready` 0 s. So **app boot plus readiness probe is 61 % of startup**, and image pull sits INSIDE the 15 s init term, whose median pull is 0.36 s because layers are cache hits. **Even a zero-second pull leaves ~23 s against a 29 s budget** -- no amount of image-cache work fixes a budget that is structurally below p50. The corollary for the *fix*: a proposal that shrinks pull time can only move the pull term, so quote its share of startup before grading it. Pairs with `learnings-agent-sandbox.md`, where the budget is split across two sequential waits, so the configured number and the logged number differ.

17. **GKE Image Streaming (`gcfs_config`) works UNDER gVisor, and one IAM role the docs call required is not -- verify both on your own fleet before designing around the docs.** (a) GKE docs are silent on gVisor compatibility, but a pool running `sandbox_config{gvisor}` plus `gcfs_config{enabled}` together pulled a **15.08 GB image COLD in 4.669 s on a node created 94 s earlier** (~3.2 GB/s -- not a download). That measurement also refutes the common review claim that streaming pods "fail at start with I/O errors instead of falling back." (b) `roles/serviceusage.serviceUsageConsumer` is documented as required for custom node service accounts in the image-hosting project, but streaming worked with the node SA holding it in NEITHER the workload project nor the registry project. Watch for the matching undeclared drift: `containerfilesystem.googleapis.com` was enabled live in two environments and declared NOWHERE in Terraform. **Free A/B technique:** GKE node names carry a pool-identifying infix, so **every kubelet `Pulled` event is attributable to a pool** -- a pool that already has streaming on is a ready-made control against the pools that do not. The blast-radius half of the same change is in `learnings-terraform.md`.

18. **A single-replica workload on an RWO PVC guarantees an outage on EVERY node drain, and a PodDisruptionBudget cannot help -- the pod has to move.** The drain evicts the only replica; the replacement cannot attach until the old attachment releases, and the gap is extended by `FailedAttachVolume: Multi-Attach`. A PDB only delays the eviction, it never prevents the single pod from moving, so `minAvailable: 1` on a 1-replica RWO workload just blocks the drain instead of protecting availability. **Consequence to state explicitly in any node-pool upgrade plan: every node-pool upgrade is a guaranteed gap for that workload** (for a metrics agent, a guaranteed metrics-ingestion gap). Same RWO mechanism as #6, different trigger -- #6 is the rolling-update deadlock, this is the drain. Real fixes are structural: more replicas on RWX/shared storage, or accept and schedule the gap.

19. **Pod phase `Running` means "at least one container running, starting, or RESTARTING", so a phase-only "is it running" filter silently counts `CrashLoopBackOff` pods.** Measured on one sandbox namespace: 5 of 828 `Running`-phase pods had a not-ready primary container (0 crashlooping and 0 with `restartCount>0` at that moment, so the overcount was real but empty) -- which is exactly why the bug survives: the census looks right until the day it does not. **If a count must mean "usable", read `containerStatuses[name==X].state` / `.ready`, never `status.phase` alone.**

20. **A HEADLESS Service with ZERO READY endpoints publishes NO A record, so DNS returns NXDOMAIN while `get svc` still shows the Service -- "the Service exists" and "the name resolves" are INDEPENDENT facts.** This reconciles the two observations that otherwise look contradictory during a per-pod-Service incident: the Service object is right there, and the client gets *"Name or service not known"*. **Check ENDPOINT READINESS, not Service existence** -- measured on one namespace, 530 Services and 530 Endpoints objects, with 500 carrying at least one ready address and 30 carrying ZERO, and the 30 were exactly the broken sessions. **The downstream status code is a usable discriminator, but only if you read the proxy's exception handling:** a router that maps `httpx.ConnectError` to 502 and everything else to its generic 500 means a literal 502 specifically means connect/DNS failure. And in current `httpx`, **`ConnectTimeout` does NOT inherit from `ConnectError`** (MRO: `ConnectTimeout -> TimeoutException -> TransportError`), so a stale-IP connect timeout falls to the generic handler and yields 500, not 502 -- two different failure surfaces with two different status codes, and treating them as one hides half the population.

21. **A CACHED POD IP can bypass the service-discovery layer entirely, so the failure you find in the proxy may not be the failure the user hit.** A client SDK that resolves a pod IP once and caches it for the connector's lifetime (a `_resolve_base_url` built from a `get_pod_ip` callable) NEVER TOUCHES THE ROUTER, and the trace shows a bare IP as the target rather than the service name. If the calling process constructs a NEW client per request, the cache is per-request -- so every attempt re-reads the SAME stale IP from the object's status, which is never cleared when the pod dies. A stale status can even report `Ready=True` alongside dead pod IPs. **Two consequences: (1) read the TRACE'S TARGET (`http://10.x.x.x:8080/...` versus `http://<service>...`) to tell which surface you are on before designing a fix; (2) a PROACTIVE readiness check on reuse is NECESSARY BUT NOT SUFFICIENT -- a transient stale `Ready=True` with dead IPs was observed -- so pair it with REACTIVE invalidation on an unreachable dispatch.**

22. **A retry policy that recognises "unreachable" and responds by NOT RETRYING leaves the caller bound to a corpse -- and the log line it prints is actively misleading.** Observed shape: an `_is_dispatch_retryable` helper retried only on a conflict status and a client-side timeout, with its own comment saying *"other network errors usually indicate the sandbox is unreachable"* -- **the code NAMES the unreachable condition and then declines to act on the BINDING**, and the handler swallows it with *"will recover on next message"*, when the next message re-resolves the same dead binding. **Cost accounting worth doing before you call a retry policy harmless: the SDK beneath it burned `MAX_RETRIES=5` with `0.5*2**n` backoff (~15 s and ~6 HTTP attempts) per user turn, all of it guaranteed to fail.** **RULE: "do not retry an unreachable endpoint" is only correct if something INVALIDATES the binding; otherwise it is an infinite outage with polite logging.**
