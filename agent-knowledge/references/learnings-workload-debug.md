# Workload Debugging Learnings

See also: `learnings-observability.md`, `learnings-helm-ci.md`, `learnings-k8s-sa.md`, `learnings-gke.md` (the cluster PLATFORM underneath these workloads -- node-pool capacity, drains, upgrades), `learnings-eks.md` (what an evicted or rebalanced managed-node-group node does to a workload), `learnings-gvisor.md` (node pressure and probe budgets on sandboxed nodes)

Kubernetes workload debugging patterns where the obvious check reports the opposite of the real state -- probe and restart semantics, native-sidecar visibility, image-level container-start failures, resource-constrained scheduling, and recognising when a client-reported error is actually correct.

Numbered, append-only. **Update the existing entry — never duplicate.**

## Probes and pod status

1. **A failing STARTUP PROBE can masquerade as a healthy pod: if the container exits 0 on `SIGTERM`, the kubelet's probe-triggered kill shows up as `Running` with a CLIMBING RESTART COUNT -- not `CrashLoopBackOff`.** The diagnostic that names it immediately: the restart interval equals `failureThreshold x periodSeconds` exactly (a `failureThreshold: 20`, `periodSeconds: 15` probe restarts the container every 300 seconds, on the dot). Confirm the actual failing path from INSIDE the pod before touching the chart -- `kubectl exec ... -- wget -qO- -S localhost:<port>/<path>` against the exact probe endpoint. A common root cause: the chart's probe path does not match the path the application actually serves (probing `/health` when the app serves `/api/<service>/health`).

2. **`kubectl ... -o jsonpath='{.spec.containers[*].name}'` returns a FALSE NEGATIVE for native (Kubernetes 1.29+) sidecars.** Native sidecars live in `.spec.initContainers` with `restartPolicy: Always`, so `.spec.containers` lists only the main application container while the pod still reports e.g. `3/3 Ready`. An investigation that inspects only `.spec.containers` can wrongly conclude a workload has no connection to a companion process -- a proxy, a log shipper, a database sidecar -- that is in fact running right next to it. **Correct check: query `.spec.initContainers[*]` too -- or simply trust the mismatch itself**, since fewer containers listed than the pod's own Ready count reports means native sidecars are present.

## Container never starts — causes that live in the image

3. **Two "the pod is scheduled but the container never runs" causes that live in the IMAGE, not the chart or manifest:**
    - **A required environment variable with no usable default.** A vendored SDK can validate-and-require an env var whose documented development default is inert because the image sets `NODE_ENV=production` (or an equivalent production-mode flag) which disables dev defaults. The pod clears scheduling and container creation, then `CrashLoopBackOff`s with a "missing required environment variable" message and a non-zero exit code. **Fix: set the variable explicitly wherever the workload is enabled, and make the chart's own default a LOUD sentinel value (e.g. `CHANGE_ME_<VAR>`) so a missing override fails at render time, not at runtime** -- a chart with no key for the variable at all only surfaces the defect live, in production.
    - **`CreateContainerConfigError: container has runAsNonRoot and image will run as root`** happens when the pod spec sets `runAsNonRoot: true` with no `runAsUser`, AND the image itself declares no `USER` -- so the kubelet resolves uid 0 from the image's own config and refuses to start it. **The fix belongs on the image side**: adding a non-root `USER` directive after any layers that need root (package installs, build steps) is normally sufficient, and several common base images already ship a pre-created non-root user for exactly this reason. **You can prove the fix works without a full rebuild**: build a minimal image on the same base with and without the `USER` directive and compare `docker inspect --format '{{.Config.User}}'` between the two.

## Scheduling and capacity

4. **Constrained-resource headroom (GPU, or any schedulable resource limited to a subset of nodes) must be filtered through the workload's own `nodeSelector`/`tolerations`/affinity rules before you call it available -- never computed fleet-wide.** A cluster-wide "N allocatable minus M allocated" can show free capacity that the workload in question structurally cannot reach, because the free unit sits on a nodepool the workload's own selector excludes. **Second, equally load-bearing half: if the compatible nodepool is healthy and simply below its configured maximum, a pending pod is "Pending until cluster-autoscaler scales up," not structurally deadlocked** -- check autoscaler headroom (max nodes vs current nodes on the compatible pool) before reporting a scheduling failure as a hard deadlock. Report those as the two different states they are.

## When the error is correct

5. **A "read-after-write race" hypothesis for an intermittent 404-after-create is refutable two cheap ways, before reaching for retries or backend changes: infra topology and client source.**
    - **Infra:** if the service's database access path points only at a primary/writer instance -- no read-replica pool, no replica connection string in play -- there is no replica for a read to lag behind, so a replication-lag explanation is off the table by construction.
    - **Source:** read the client at the exact version deployed. If the client generates the entity's id on its own side, seeds an optimistic local cache with it, and only THEN makes the backend call that would actually create the row, then a request racing ahead of that backend call is hitting a row that genuinely does not exist yet -- the 404 is architecturally correct, not a race.
    - **When the 404 is correct, the real defect is almost always in the banner or error-handling path, not the backend.** Suppression logic keyed to a client-local flag (a `sessionStorage` entry, an in-memory variable) silently stops working the moment the same action happens in another tab, for another user, after a reload, or via a shared link -- and a short retry policy then surfaces a dead-end error banner for what is functionally just a timing issue on first load. **General rule: once a not-found response is shown to be architecturally correct, stop tuning the backend and go read the client's retry and suppression policy instead.**

6. **StorageClass is NOT portable across clouds, and a PVC-backed debug capture has two ways to destroy its own data.** For a long-running capture (memray, heap dumps, profiles) written to a container path: back that path with a PVC and set **`strategy: Recreate`** -- an RWO volume deadlocks a rolling update, because the new pod cannot attach while the old one still holds it. The class name differs per cloud: `premium-rwo` (pd-ssd) is GKE-only; on EKS use the gp3 default (`auto-ebs-sc`, encrypted) -- **`gp2` is the legacy in-tree driver with no volume expansion.** Both defaults are `reclaimPolicy: Delete`, so **`kubectl delete -f` on a manifest holding BOTH the PVC and the Deployment destroys the capture you just collected** -- split them across separate files. Check whether the image runs as root before adding `fsGroup`; if the image config declares no `USER`, the mount needs none.

7. **An error logged INSIDE a streaming loop amplifies ONE failure into N log lines -- never read raw log counts as distinct failures.** A helper-generation failure returned "not persisted" without marking the task terminal, so the enclosing `async for chunk in ...` loop re-checked the same already-failed task and re-logged an ERROR on EVERY subsequent chunk. Downstream, a single failed generation looked like a ten-fold incident. Two rules: (1) before treating a log-volume rise as an incident, establish whether the emitting site sits inside a per-chunk/per-item loop, and count DISTINCT ORIGINATING TASKS rather than lines; (2) "retried 3 times" in such a message may mean three fresh upstream calls rather than three retries of one -- read the retry helper before quoting the number. The blast radius is often NOT cosmetic even when the primary path is unaffected: here the failed sidecar record broke grouping downstream, so the UI silently dropped content while the main response was fine.

8. **A burst of identical credential-init failures during a large simultaneous rollout is metadata-server CONTENTION, and node age refutes the obvious alternative.** 8 of 12 pods failed their cloud-SQL-proxy sidecar with `could not find default credentials` exactly ~10 s after container start -- the sidecar's ADC timeout -- then succeeded on automatic restart, during a roll of ~56 pods across 7 deployments. **The node-age hypothesis was REFUTED by direct check, not by correlation:** restarted pods and clean pods sat on nodes of the same three ages. Establish a baseline first (here: zero such restarts over the preceding 3 days, so it is load-dependent and new, not chronic). It self-heals, but each occurrence costs a pod ~10 s of readiness on every rollout -- which makes it a latent bug worth its own ticket rather than noise to filter.

## Node pools, drains and config precedence (GKE)

9. **GKE node-pool DELETION does NOT respect PodDisruptionBudgets by default, and the common belief that it honours them and then force-deletes after a timeout is WRONG -- there is no timeout margin.** `--respect-pdb-during-node-pool-deletion` is an explicit per-pool opt-in (Google Cloud SDK 583+); a pool with no `nodeDrainConfig` bypasses PDBs immediately on delete, and a Terraform `destroy` of the node-pool resource inherits that behaviour. **Always require a manual cordon plus drain before deleting a pool that hosts quorum workloads -- the manual drain IS the protection, not the platform.** Verify with `gcloud container node-pools describe <pool> --format=json | jq 'has("nodeDrainConfig")'`.

10. **Node-pool drain protocol -- six rules, four of which cost a real incident when skipped.** (1) See #9: drain manually, the platform will not. (2) **CORDON EVERY NODE IN THE POOL BEFORE DRAINING ANY**, or evicted pods reschedule straight back onto the pool -- this actually happened, with two nodes *gaining* pods mid-drain (15 to 16, 17 to 21). (3) **A CNI component that tolerates `node.kubernetes.io/unschedulable` re-lands on cordoned nodes and is always the last pod left** -- do not read it as a failed drain. (4) **`kubectl drain` keeps working in the background** -- check counts twice before concluding pods are stuck. (5) **A StatefulSet with `podManagementPolicy=OrderedReady` will never recreate replica N+1 while replica N is unready**, so evicting from a pool that holds one crashlooping replica takes the whole set down. (6) Order nodes lightest-first, and for a PDB-constrained StatefulSet wait for full rollout status between nodes.

11. **A node pool's configured `max_node_count` can be UNREACHABLE by pod-CIDR arithmetic, so "reduce the max" may be a no-op and "this pool can absorb that workload" may be false.** A pool with no explicit `network_config` draws pod IPs from the CLUSTER-DEFAULT secondary range. **Real ceiling = (pod range size) / 2^(32 - podIpv4CidrSize).** Observed: a pool configured `max_node_count=300` whose pod range was a `/18` (16,384 IPs) at the 110-pod default (`/24`, 256 IPs per node) had a HARD CAP OF 64 NODES. **Ground it from the API, never infer:** `gcloud container node-pools describe <pool> --format="yaml(networkConfig,podIpv4CidrSize,maxPodsConstraint)"`, and cross-check the denominator against `clusters describe` -> `ipAllocationPolicy.defaultPodIpv4RangeUtilization` (0.0938 == 6/64 confirmed the arithmetic). **Always check this before claiming a pool autoscales enough to absorb a deleted pool's workload.**

12. **A node pool with "no custom labels and no taints" is NOT untargetable -- every node still carries `cloud.google.com/gke-nodepool=<pool-name>`, a perfectly good `nodeSelector`/affinity target.** So when arguing a pool is safe to delete, **the claim to prove is "nothing DOES target it" (sweep live pods for a positive `nodeSelector`/affinity, plus a repo grep), never "nothing CAN target it".** Filter DaemonSet pods out of that sweep: their controller injects `matchFields: metadata.name In [<own node>]`, which looks like a pool affinity and is not.

13. **A clean `kubectl diff --server-side` is NOT proof a config change takes effect -- it only proves the OBJECT will look how you expect.** For any component that layers config sources (a CNI's felix/cilium agent, kubelet, Envoy), check the PRECEDENCE TABLE and whether a higher-ranked source already pins the field. **Worked case:** GKE's addon-managed Calico sets `FELIX_LOGSEVERITYSCREEN=info` as a CONTAINER ENV VAR on the DaemonSet, and felix ranks its sources `Default(0) < DatastoreGlobal(1) < DatastorePerHost(2) < ConfigFile(3) < EnvironmentVariable(4) < InternalOverride(5)` (`felix/config/config_params.go:64-71` at v3.30.4) -- so `logSeverityScreen` on `FelixConfiguration/default` applies cleanly, shows a clean diff, AND DOES NOTHING. Editing the env var is reverted, because the DaemonSet carries `addonmanager.kubernetes.io/mode=Reconcile`. (Side note: the default `FelixConfiguration` instance has no addonmanager label -- the CRD does -- so it is not itself reconciled; moot given precedence.) **An offline proof for a config change must show that the VALUE THE PROCESS USES changes, not that the CR changed.** The remaining levers in that situation are external (a log-ingestion exclusion) or structural (migrate off the addon).

14. **An "allocatable divided by request" packing table is NOT achievable density -- subtract DaemonSet/system overhead AND native sidecars before quoting a number.** Two deductions, both easy to forget: (a) **DaemonSet plus system overhead** (measured: 11-13 pods, ~1.21 CPU / 1.61 Gi on an 8-vCPU node); (b) **native sidecars counted in the pod request** -- `restartPolicy: Always` init containers add their requests to the pod (measured: +60 m CPU / +96 Mi per pod from two such sidecars). On one node type the honest budget was **6.698 CPU / 26.12 Gi / 20 pod slots, not 7.91 / 27.7 / 32**. Also: **a gVisor `RuntimeClass` declares no `overhead`, so the sandbox runtime costs the scheduler nothing -- and is correspondingly unbounded.**

15. **Repointing an affinity at a surviving node pool is insufficient if the workload's DEFAULT RESOURCE REQUEST exceeds the new pool's allocatable -- check both dimensions before calling a pool a safe migration target.** A workload defaulting to 8 CPU / 32 Gi cannot land on a pool whose allocatable is 7910 m / 27.7 Gi: BOTH axes fail, so the pods fit nowhere and must be DELETED before the old pool is removed, not migrated. **Compare against `kubectl get node -o json` `.status.allocatable` on the proposed target, not against the machine type's nominal size.** Redirect targets are often NOT symmetrical -- if the only surviving pool with a given accelerator is also taint-gated for a sandbox runtime, a workload that needs the accelerator *without* that runtime has NO VALID HOME AT ALL, and the migration is actually a deletion decision.

## Startup budgets, image streaming and single-replica volumes (GKE)

16. **Never size a pod-readiness budget against IMAGE SIZE -- measure `PodScheduled -> Ready` percentiles on the live pool first, because app boot usually dominates and a cached pull is nearly free.** Measured on a production cluster from live pod conditions (n=225 warm-pool sandbox pods): **p50 38 s, p90 43 s, p95 159 s, min 24 s** against a 29 s effective budget -- **82.7 % exceeded it**. Stage split: `Scheduled -> Initialized` p50 15 s, `Initialized -> ContainersReady` p50 23 s, `ContainersReady -> Ready` 0 s. So **app boot plus readiness probe is 61 % of startup**, and image pull sits INSIDE the 15 s init term, whose median pull is 0.36 s because layers are cache hits. **Even a zero-second pull leaves ~23 s against a 29 s budget** -- no amount of image-cache work fixes a budget that is structurally below p50. The corollary for the *fix*: a proposal that shrinks pull time can only move the pull term, so quote its share of startup before grading it. Pairs with `learnings-agent-sandbox.md`, where the budget is split across two sequential waits, so the configured number and the logged number differ.

17. **GKE Image Streaming (`gcfs_config`) works UNDER gVisor, and one IAM role the docs call required is not -- verify both on your own fleet before designing around the docs.** (a) GKE docs are silent on gVisor compatibility, but a pool running `sandbox_config{gvisor}` plus `gcfs_config{enabled}` together pulled a **15.08 GB image COLD in 4.669 s on a node created 94 s earlier** (~3.2 GB/s -- not a download). That measurement also refutes the common review claim that streaming pods "fail at start with I/O errors instead of falling back." (b) `roles/serviceusage.serviceUsageConsumer` is documented as required for custom node service accounts in the image-hosting project, but streaming worked with the node SA holding it in NEITHER the workload project nor the registry project. Watch for the matching undeclared drift: `containerfilesystem.googleapis.com` was enabled live in two environments and declared NOWHERE in Terraform. **Free A/B technique:** GKE node names carry a pool-identifying infix, so **every kubelet `Pulled` event is attributable to a pool** -- a pool that already has streaming on is a ready-made control against the pools that do not. The blast-radius half of the same change is in `learnings-terraform.md`.

18. **A single-replica workload on an RWO PVC guarantees an outage on EVERY node drain, and a PodDisruptionBudget cannot help -- the pod has to move.** The drain evicts the only replica; the replacement cannot attach until the old attachment releases, and the gap is extended by `FailedAttachVolume: Multi-Attach`. A PDB only delays the eviction, it never prevents the single pod from moving, so `minAvailable: 1` on a 1-replica RWO workload just blocks the drain instead of protecting availability. **Consequence to state explicitly in any node-pool upgrade plan: every node-pool upgrade is a guaranteed gap for that workload** (for a metrics agent, a guaranteed metrics-ingestion gap). Same RWO mechanism as #6, different trigger -- #6 is the rolling-update deadlock, this is the drain. Real fixes are structural: more replicas on RWX/shared storage, or accept and schedule the gap.

19. **Pod phase `Running` means "at least one container running, starting, or RESTARTING", so a phase-only "is it running" filter silently counts `CrashLoopBackOff` pods.** Measured on one sandbox namespace: 5 of 828 `Running`-phase pods had a not-ready primary container (0 crashlooping and 0 with `restartCount>0` at that moment, so the overcount was real but empty) -- which is exactly why the bug survives: the census looks right until the day it does not. **If a count must mean "usable", read `containerStatuses[name==X].state` / `.ready`, never `status.phase` alone.**

20. **A HEADLESS Service without `publishNotReadyAddresses` and with ZERO READY endpoints publishes NO A record, so DNS returns NXDOMAIN while `get svc` still shows the Service -- "the Service exists" and "the name resolves" are INDEPENDENT facts.** This reconciles the two observations that otherwise look contradictory during a per-pod-Service incident: the Service object is right there, and the client gets *"Name or service not known"*. **Check ENDPOINT READINESS, not Service existence** -- measured on one namespace, 530 Services and 530 Endpoints objects, with 500 carrying at least one ready address and 30 carrying ZERO, and the 30 were exactly the broken sessions. **The downstream status code is a usable discriminator, but only if you read the proxy's exception handling:** a router that maps `httpx.ConnectError` to 502 and everything else to its generic 500 means a literal 502 specifically means connect/DNS failure. And in current `httpx`, **`ConnectTimeout` does NOT inherit from `ConnectError`** (MRO: `ConnectTimeout -> TimeoutException -> TransportError`), so a stale-IP connect timeout falls to the generic handler and yields 500, not 502 -- two different failure surfaces with two different status codes, and treating them as one hides half the population. For a per-pod Service, its only A record disappears as soon as the pod goes NotReady. Full chain, reproduced on a real incident: CPU-bound work on the app's event loop stalls `/health` -> the readiness probe fails -> the pod goes NotReady -> the headless Service has no endpoints -> the proxy's DNS lookup fails with `[Errno -2] Name or service not known` -> 502. **The timing is the tell: each failed request takes 4-5 s (DNS + a few client retries), not the 60 s a hung upstream would cost.** Three independent fixes, in increasing order of correctness: raise the readiness probe's budget, set `publishNotReadyAddresses` on the Service, or move the blocking work off the event loop. Check `publishNotReadyAddresses` across the whole set -- in one inspected set **every** Service had it unset.

21. **A CACHED POD IP can bypass the service-discovery layer entirely, so the failure you find in the proxy may not be the failure the user hit.** A client SDK that resolves a pod IP once and caches it for the connector's lifetime (a `_resolve_base_url` built from a `get_pod_ip` callable) NEVER TOUCHES THE ROUTER, and the trace shows a bare IP as the target rather than the service name. If the calling process constructs a NEW client per request, the cache is per-request -- so every attempt re-reads the SAME stale IP from the object's status, which is never cleared when the pod dies. A stale status can even report `Ready=True` alongside dead pod IPs. **Two consequences: (1) read the TRACE'S TARGET (`http://10.x.x.x:8080/...` versus `http://<service>...`) to tell which surface you are on before designing a fix; (2) a PROACTIVE readiness check on reuse is NECESSARY BUT NOT SUFFICIENT -- a transient stale `Ready=True` with dead IPs was observed -- so pair it with REACTIVE invalidation on an unreachable dispatch.**

22. **A retry policy that recognises "unreachable" and responds by NOT RETRYING leaves the caller bound to a corpse -- and the log line it prints is actively misleading.** Observed shape: an `_is_dispatch_retryable` helper retried only on a conflict status and a client-side timeout, with its own comment saying *"other network errors usually indicate the sandbox is unreachable"* -- **the code NAMES the unreachable condition and then declines to act on the BINDING**, and the handler swallows it with *"will recover on next message"*, when the next message re-resolves the same dead binding. **Cost accounting worth doing before you call a retry policy harmless: the SDK beneath it burned `MAX_RETRIES=5` with `0.5*2**n` backoff (~15 s and ~6 HTTP attempts) per user turn, all of it guaranteed to fail.** **RULE: "do not retry an unreachable endpoint" is only correct if something INVALIDATES the binding; otherwise it is an infinite outage with polite logging.**

## Shutdown notifications and rollout disruption

23. **A pod's SIGTERM handler cannot make an OUTBOUND call once its NATIVE SIDECAR proxy is torn down in the same second -- so "finalize status, then notify the caller" loses the notification while the status write succeeds.** Verified on an eviction: the workload's shutdown path cancelled the run, PATCHed its own status to FAIL, and sent its local websocket message -- then the separate caller notification failed with *"All connection attempts failed"*, because the proxy sidecar had already exited. **The failure is asymmetric and that is what makes it confusing: in-cluster/apiserver writes survive, egress through the mesh does not.** **A janitor/reaper CronJob is NOT a substitute** -- one that marks orphans FAIL but never notifies the caller leaves the caller blocked until its own polling notices, which in the observed incident was **3 h 27 m** later. Two structural causes to look for: the terminal status update has **no listener/outbox** and the caller's identity is carried only in **runtime config**, never persisted on the row, so the reaper *cannot* reconstruct who to notify even if it wanted to. **Fixes are an outbox/persisted caller reference, or an independent heartbeat -- not more retries**, and retry config is worth reading before blaming it: a policy that retries only on 429/5xx/ConnectError/Timeout makes **exactly one attempt** on a `ReadError`, while still logging a generic *"after retries"* line that reads like five.

24. **StatefulSet rolling updates bypass PodDisruptionBudgets.** A PDB constrains Eviction API requests, not the direct Pod DELETE used by the StatefulSet controller during rolling updates. Do not claim that `minAvailable` guarantees RabbitMQ quorum during `rollout restart`; update pacing and meaningful readiness/quorum checks are the relevant controls. Source: Kubernetes v1.35.0 `pkg/controller/statefulset/stateful_pod_control.go:96-97,196-199`; the controller calls `Pods.Delete`, not eviction. Confirmed by https://kubernetes.io/docs/concepts/workloads/pods/disruptions/ .

## Event-loop starvation, sizing from metrics and shared-broker exhaustion

25. **A SYNCHRONOUS filesystem walk inside an async request handler starves the HEALTH PROBE in the same process, and the pod dies as `exit 137 / reason=Error` with no OOM and no eviction -- so every memory-shaped hypothesis is wrong.** Worked instance, fully attributed: a release added a recursive permission pass (`os.walk` + `chown`/`chmod` over a whole project tree, including scratch) plus a synchronous read/regex/write, inside a function **with no `await` between two known log lines**. The service ran **one** Uvicorn worker (no `--workers`, so the default 1) serving an async `/health`, while the work itself was scheduled with `create_task` on that same loop and `await`ed a synchronous call chain. Result: the gap between those two log lines went from a **max of 1.7 s over 650 runs** to a **max of 203 s with 27/926 over 30 s**, and the kubelet's liveness probe (every 30 s, 5 failures, then `SIGKILL` after the grace period) killed **105 pods in 19 h** against 12 in the prior 48 h. **Attribution method, in the order that worked and is reusable:** (1) **timestamps first** -- the first kill was +61 min after the suspect image rolled and **3.6 h BEFORE** the control-plane upgrade that everyone blamed; (2) **pair two log lines per pod and compare the distribution** pre vs post over the same clock window (p50 barely moved, 1.318 -> 1.440 s -- **the tail is the signal, not the median**); (3) **a sibling control** -- other pools on the *same* new image showed zero events, which localised the cause to the one workload with heavy traffic on that path (1,552 invocations vs 5/34/0 elsewhere); (4) **exact-diff the two image commits** and confirm the probe/process wiring is byte-identical, so only the new code can explain it. Specific syscall attribution stayed unproven without `strace`/`py-spy` -- say so rather than over-claiming. **Fix shape: offload the whole initialization block with `asyncio.to_thread` (not just the obvious call), and stop recursively walking scratch directories at all.** Generalisable trap: an *existing* offload elsewhere in the codebase (here, for the job path) is easy to mistake for coverage of the path that actually broke.

26. **Do NOT size memory from a snapshot of YOUNG pods -- long-lived sessions accumulate, and a cohort p99 hides the heavy members.** Worked instance: a `kubectl top` snapshot of hours-old pods showed **p99 1.6 GiB (max 5.9)** and produced an 8 Gi recommendation; the 30-day per-agent view showed long-lived chat/curator workloads on the **same profile default** peaking at **20-27 GiB**. Use a **30-day max per logical agent (worst pod)**, not a percentile across pods -- the percentile is dominated by the many short-lived ones. Second half: when memory is what pins a pod to one-per-node, **cutting CPU requests buys no packing at all** for those pods; identify which dimension is binding before proposing either.

27. **A single shared broker cap that is consumed PER QUEUE PER CONNECTION fails every new instance at once, and it presents as a STARTUP PROBE timeout rather than as a broker error.** Worked instance: a dispatcher opened **one channel per queue** on a single connection (up to 4 per tenant), and once the fleet had accumulated enough tenants a deploy hit the negotiated channel cap (2047) -- the new revision never became healthy and the previous revision kept serving, so there was no outage, just a stuck deploy. **Every** new instance fails the same way thereafter (deploy, scale-out, restart) until the population shrinks, the channels are spread across connections, or the cap is raised. Diagnose by reading the **failed revision's own logs** at `severity >= WARNING`, not the service's aggregate logs -- the healthy old revision's noise buries it.

28. **During a revision/rollout switch, the OLD instances keep consuming queued work for minutes after traffic shifts -- so work created with the old code arrives AFTER the cutover.** Measured ~3 minutes, bounded by when the deploy job ends. This is the mechanism behind a whole class of "impossible" post-deploy errors: an object written by the old code path (an old API version, an old schema, an old header) shows up well after you believe that code is gone. It only matters if the receiving side has **stopped accepting** the old form -- so when a deploy also narrows what is accepted, sequence the two so the narrowing lands **after** the queue has drained, not in the same release.

29. **A readiness probe with no `timeoutSeconds` gets the 1-second default, which is routinely shorter than the sibling liveness probe and shorter than a loaded app's health handler.** This is the most common cause of #20: a probe written as `periodSeconds: 10, failureThreshold: 3` looks generous and is actually a 1-second deadline three times in a row. Set `timeoutSeconds` explicitly to at least the liveness probe's value. If the probe lives in a **rendered template object** rather than a live workload, know when it is re-rendered: one such template is rebuilt only on deploy/register/upgrade, so existing workloads keep the old probe until redeployed -- and rolling back to an earlier revision re-applies that revision's **stored** manifest, i.e. the old probe comes back.

30. **An identical-code redeploy can LOSE a startup-probe race that the previous revision won, so "the same code was healthy yesterday" is not evidence.** Observed where app startup (~100 s of lifespan work + ~35 s process start) sat right at the probe budget (15 × 10 s): the healthy revision already logged `STARTUP HTTP probe failed 15 times consecutively` on some instances and passed at attempt 15 on others; the next revision -- identical code, redeployed only because an unrelated config file changed -- failed and traffic stayed on the old one. Immediate fix is to rerun the deploy; the real fix is a faster startup path or a larger startup budget. **Budget headroom, not a passing margin**: a probe that passes on the last attempt is already failing half the time.

31. **A NAT egress IP identifies a NODE, not a caller, so IP alone cannot attribute an outbound request burst -- join on the workload's own creation time instead.** On one repeated incident the source IPs were three different NAT addresses all belonging to the same node pool. **Fast attribution with no database query:** list the claims/pods of the suspected workload and match `creationTimestamp` to the burst onset (for example, the first error followed workload creation by about a minute), then read that pod's logs for the session identifier. Where the request-handling log line carries no caller, read the **load-balancer / platform request log** instead, which has user-agent and remote IP -- and remember an app-level 404/4xx rate alert can have a **100 % baseline route** in it that must be excluded before the rate means anything.

## Event-loop starvation, sizing from metrics, and shared-broker exhaustion (2026-10)

32. **To prove POD CHURN after the pods are gone, read the API server's AUDIT log: a live listing cannot see them.** `kubectl` only shows pods that still exist, so "did something recreate these pods?" is unanswerable from the cluster an hour later. ✅ Query the admin audit log for `pods.create` / `pods.delete` on the namespace and **count creations of a NAME that was deleted earlier**: this works precisely because a controller that recreates a pod under the same name (see `learnings-agent-sandbox.md`#86`) makes name reuse the signal rather than the obstacle. Measured: 166 same-name recreations on one release day versus 1 on a quiet day. ⚠️ **And do not assume the controller is the cause.** On the day with 167 recreations, the controller restart recreated **zero** pods; the churn came from NODE-POOL UPGRADE drains: the kubelet's node principal deletes the pod and the controller recreates the same name about 0.06 s later. ✅ Check the cluster's operations list for upgrades before blaming a deployment.

33. **Two log-shape traps that make a retry/give-up analysis report the wrong failure.** **(a) A client wrapper that stringifies every HTTP status identically.** A per-attempt warning rendering the SDK's exception showed the same *"Failed to communicate with …"* text for a busy-409 and for a gateway 502, with the status code present only in the final give-up traceback, so a naive count of "dispatch attempt failed" lines is dominated by an ordinary busy-retry path, roughly 1:1 with the "already busy" lines on a healthy day. ✅ **Discriminate on attempt number and on the correlated busy line within ~1.2 s; count outage episodes as those reaching attempt ≥ 2.** **(b) The give-up line differs by CALLER.** A service that logs *"will recover on next message"* only when it swallows the error, and a different phrase when it re-raises, makes a grep for the first phrase silently EXCLUDE every raising caller. ✅ Enumerate both phrases before quoting a give-up rate. ⚠️ A give-up carrying a timeout and **no attempt line at all** means ONE attempt consumed the whole budget: short-budget callers therefore get no retry when the backend hangs, which is invisible in a count of failed attempts.

34. **Joining application logs to the request that produced them can require normalising a TRACE identifier whose format differs between the two log streams.** On one managed runtime the application lines carry a bare hex trace while the platform's own request lines carry the fully-qualified `projects/<project>/traces/<hex>` form, so the obvious equality join returns nothing and reads as "these logs are not correlated". ✅ Filter on the qualified form when selecting request lines and strip to the bare hex when selecting application lines. Having done that, the give-up episodes in one investigation resolved cleanly by ROUTE (a long-budget recovery callback, a 5-second queue route, and a 30-second periodic tick) which is what turned a flat failure count into a per-caller budget problem.

35. **A torn-down preview environment leaves third-party workloads pointed at its dead hostname, and the resulting failure imitates an unrelated bug.** Teardown removed the preview service but not the agents deployed against it, whose sidecar configuration still held the preview's URL; every request then failed with a 503 originating in a name-resolution error deep in a config-refresh call, on a periodic tick, long after anyone remembered the branch. It presented exactly like a dispatch give-up in the main service. ✅ **Check the pod's own sidecar/init logs and its configured upstream URL before attributing a 503 to the caller**, and ✅ treat *what still points at this environment* as part of any teardown's definition of done.

36. **Probe period × failureThreshold is not an invariant startup grace window.** Kubelet v1.35.0 `pkg/kubelet/prober/worker.go:186-197` probes before waiting for the ticker; `:316-331` applies initial delay against container StartedAt and gates liveness/readiness until Started; `:359-375` publishes the Nth failure and holds until restart. Removing delay while halving period and doubling failureThreshold can therefore kill a start that previously succeeded. A deterministic prompt-failure example: delay=2/period=2/threshold=15 probes at 2..30s; delay=0/period=1/threshold=30 fails at29s, so a service available at29.5s succeeds only with the old spec. Native sidecars are killed/restarted on this result (`kuberuntime_container.go:1126-1144`), blocking later containers. Size from actual elapsed deadlines, sweep probe phases, and test sidecar budgets as well as the main container; a period-only assertion misses this. Source: https://github.com/kubernetes/kubernetes/blob/v1.35.0/pkg/kubelet/prober/worker.go. Reproduced during a PR review with a standalone probe-timing simulation (no cluster execution).

37. **Measure a PROBE change against the application's own readiness log line, not against pod create→Ready: scheduling, image pull and workload mix swamp the signal you are trying to see.** Use the server's "listening"/"started" log timestamp (`kubectl logs --timestamps -c <c> | grep -m1 …`) to pod Ready. Evidence that create→Ready is unusable: untreated CONTROL workloads moved 10-14s day over day on their own. 🔎 **A distribution signature confirms the mechanism:** with a slow readiness period, `(Ready − container startedAt) mod <period>` CLUSTERS at a fixed offset; after a fast startup probe gates readiness, it goes uniform. ⚠️ **Expect a side effect to be mis-read as a regression:** a 1s startup probe logs ~15-20 `Startup probe failed: connection refused` Unhealthy events per pod (p50 15, p90 20, max 34 of 300), so cluster-wide Unhealthy event volume can triple at identical pod counts, **any alert on Unhealthy counts must exclude startup-probe failures.** Liveness-failed events fall sharply in exchange, because the startup probe now gates liveness.

38. **Readiness runs IMMEDIATELY after a startup probe passes, not at the next readiness period tick** (kubelet v1.35: `kubelet.go:2655 SetContainerStartup` → `handleProbeSync` → the prober manager sends a manual trigger to the readiness worker, `prober_manager.go:352`). So a 1s-period startup probe plus a 10s readiness period yields Ready ≈1s after the app binds: the slow readiness period costs nothing once a startup probe exists. ⚠️ **Readiness and liveness are SKIPPED entirely until startup passes** (`worker.go:329`), so `startup.failureThreshold × period` must EXCEED the old liveness kill bound (`initialDelay + period × (failureThreshold − 1)`) or you have shortened the application's grace period while believing you extended it.

39. **Removing `initialDelaySeconds` while doubling `failureThreshold` at half the period SHRINKS the startup deadline by 1-2s: it is not an equal-wall-clock swap.** The old first counted probe is the first tick at or after the **integer-truncated** initial delay; the new one is the first tick after container start (kubelet `worker.go:317`, which probes before its first ticker wait and gates the delay on container `StartedAt`). ✅ Add **+2 to the threshold** to make "same budget" exact, and work the arithmetic per sidecar rather than assuming it scales. 🔎 Worked counter-example at these settings: a dependency ready at 29.5s still SUCCEEDS at 30s on the old config but reaches Failure at 29s on the new one. ⚠️ A test that pins this must escape the obvious wrong paths (wrong main port, threshold of 1, a delay that dominates) or it passes on a broken config.

40. **Split "slow page load" into server time and transfer time before attributing it: the platform's REQUEST log is server time only, while the external load balancer's log runs until the LAST BYTE reaches the client, so size ÷ latency there approximates the user's download speed.** A case graded as a service regression (server 1-2s) was a 100s+ load on one network at ~90 KB/s while other users on the same response size got ~2.5 MB/s. ✅ Compare against OTHER users' same-size responses; that comparison is what converts "slow for them" into "slow network" or "slow us".

41. **Pull ≥30 DAYS of a specific user's history before claiming a problem "started yesterday": a 4-day window manufactures a regression out of a long-standing variable condition.** The same user's slow days were present on five earlier dates across the month; what actually drove it was that their response pages were 6-15 MB, so load time *is* download time and swings with their connection. ✅ When per-user latency tracks per-user payload size, the fix is to cap the payload, not to chase the latency. 🔎 Generalises: any "new since X" claim needs a baseline window several times longer than X.

42. **A workload reporting "cancelled (shutdown)" with a failed status mid-run is usually a kubelet NODE-MEMORY EVICTION, not a user cancel, and the two are indistinguishable from the application's own logs.** ✅ Confirm from the cluster's event stream by eviction reason rather than from the app. 🔑 Root cause to check first: a per-pod memory LIMIT that exceeds what the node can actually give once sidecars and DaemonSets are counted. ⚠️ And where those limits are rendered from a stored template, **capping them in code does not change the live templates until each workload is redeployed**, so a merged fix can be live and ineffective at the same time.

43. **A V8 heap OOM sits at ~2.0-2.08 GB regardless of the container's memory limit, so raising the container memory does NOT lift the ceiling: the knob is `--max-old-space-size`.** Seen as recurring `Reached heap limit`/Mark-Compact failures at ~2050 MB inside a 4 GiB / 2 CPU container, 7-17 times a day on bad days. 🔎 Two things to check alongside: whether the upstream caller is posting very large bodies (and whether the rejections you see are the app's own body-size limit rather than the proxy's), and whether a fan-out path **re-serializes the payload per recipient**, which multiplies peak heap by the recipient count.

44. **A Redis pub/sub `client-output-buffer-limit` (OSS default 32 MB for the pubsub class) is a hidden ceiling on broadcast size, and crossing it DROPS THE SUBSCRIBER while the publish still returns success.** Reproduced on Redis 7.2.7: a 32,505,856-byte body was delivered and a 33,554,368-byte body silently killed the subscriber, with the publishing request returning 200 either way. ⚠️ Remember the payload GROWS between your size check and the publish (added ids/timestamps), so keep the request-body limit **comfortably below** the buffer limit, not equal to it. 🔎 Negative result worth recording: an existing high-volume "subscriber socket closed" log was NOT explained by message size, hours with hundreds of near-limit posts showed none of it, so size and that churn are separate problems.

45. **`curl --retry` also retries exit 28 (the `--max-time` timeout), so on a SYNCHRONOUS endpoint `--max-time` must exceed the handler's normal runtime or every run re-sends while the first handler is still working.** Measured with curl 8.x in a Kubernetes CronJob: `--retry 2 --max-time 45` against a server that accepts and never answers costs `3x45s + 2x2s = 139s` before exit 28, which fits inside a 300s `activeDeadlineSeconds` but burns half of it. A real handler taking 44 to 95 seconds against `--max-time 45` means the Job logs the RETRY's response and the first handler's outcome is lost, even when the operation itself is idempotent. **`--retry` also re-POSTs on HTTP 500/502/503/504** (a 500 stub saw 3 POSTs per run), so use it only on idempotent internal endpoints. **Shape that works for a synchronous sweep:** one POST, `--max-time` comfortably above the observed p99, `activeDeadlineSeconds` above that, and retry left to the pod `restartPolicy`. **Testing note that saves a wrong conclusion:** an unroutable address fails FAST with exit 7 (no route), not a timeout, so test timeout behaviour against a socket that accepts and never replies.

46. **A `kubectl run` egress-IP probe: the three mechanics that make it give a wrong or doubled answer.** The single-pod form works (`kubectl run x --rm -i --restart=Never --image=<curl image> --command -- curl -s <an echo-your-IP endpoint>`) but also prints `pod deleted` into the same stream. ⚠️ **Per-node pinning via `--overrides` needs `"apiVersion":"v1"` INSIDE the JSON** or kubectl fails with `Invalid JSON Patch`; add `tolerations: [{operator: Exists}]` for tainted pools. ⚠️ **When attach fails, kubectl falls back to log streaming and prints the output TWICE**, so extract addresses with `grep -oE` and `sort -u` rather than counting lines. ⚠️ **Never run `kubectl config use-context` inside a test**: it mutates the user's current context, which outlives the probe.
