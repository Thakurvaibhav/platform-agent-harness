## PromQL & rate intervals

1. **Always verify metric names exist before writing alerts.** A typo silently produces a no-op alert that never fires. Verify with:
   ```bash
   curl -s <pod-ip>:<port>/metrics | grep <metric>
   ```
   or:
   ```bash
   rtk gcx --agent metrics query -d <prom-uid> '<metric_name>' --since 5m -o json
   ```

   Availability is an exporter/allowlist property: verify `count by (cluster) (<metric>)` across the applicable targets and a real window. Name-index membership is insufficient (#21); if pod readiness is not exported, read `.status.conditions[type=Ready]` from the Kubernetes API.

2. **`$__rate_interval` fails with 60s scrape intervals.** With a 60s scrape interval, Grafana's `$__rate_interval` resolves to ~60s, which yields only 1 data point — `rate()` needs at least 2 samples. Use a hardcoded `5m` rate window for any datasource with a 60s scrape interval.

3. **Prefer a custom `$rate_interval` Grafana variable over hardcoded windows.** Add a Grafana custom variable (options: `1m,5m,10m,15m`; default `5m`) rather than hardcoding `[5m]` in every query. Avoids the auto-scaling problem in learning #2 while giving operators flexibility.

## PromQL aggregation & joins

4. **Bare aggregations drop labels.** `min(metric)` without a `by` clause drops every label, leaving `{{ $labels.cluster }}` empty in the rendered annotation. Always use `min by (cluster, environment) (metric)` (or similar).

5. **`sum by(...)` clauses are mandatory when labels are referenced in annotations.** Stripping a label that the annotation template uses leaves a literal `{{ $labels.foo }}` in the rendered alert.

   This is distinct from #66 (which is about `environment` being an `external_label` absent from some metrics). Here the metric DOES carry `environment`, but an alert that filters `environment=~"dev|test"` in the selector while aggregating with `sum/min/histogram_quantile by(cluster, ...)` strips `environment` from the OUTPUT/firing TSDB series → Alertmanager cannot route by env. Fix: add `environment` to every `by()` / `min by()` / `by (le, cluster)` grouping. For **ratio alerts** (`failed/(opened+failed)` with a trailing `and ... > N`, e.g. `IstioMeshConnectionFailures`, `ZtunnelHighConnectionFailureRate`), add `environment` to ALL `sum by()` clauses — numerator, both denominator legs, AND the trailing `and` — or the binary-op label sets stop matching and the result is empty. `group_left` / bare-metric / `up{...} * group_left` exprs already retain `environment` (left labels) and need no change. For a restricted-join alert (`StrictMtlsUnexpectedPlaintext`, `and on(cluster, source_workload_namespace)`), adding `environment` to the left `sum by()` is safe — the `on()` clause restricts matching keys and left-side extra labels carry forward. `environment` is NOT a static rule label (NonProd spans `dev|test`). istio-ambient alerts live in `charts/global-alerts/services/istio-ambient.yaml` and `charts/istio-base/service-observability/istio-ambient.yaml` (latter double-templates via `{{ .selector }}`).

6. **PromQL `on()` joins must include `cluster` in multi-cluster setups.** `/ on(namespace, pod, container)` drops the `cluster` label. Always use `/ on(cluster, namespace, pod, container) group_left`.

   See #19 for the composed-expression arming control; proving each operand separately is insufficient.

7. **Scope queries with `cluster="<name>"` label.** Multi-cluster Thanos / Mimir / VictoriaMetrics deployments will otherwise merge series across clusters and produce misleading aggregates.

## Alert design

8. **Prefer ratios over absolute thresholds.** `errors/total > 0.02` survives traffic changes; `errors > 100` does not. Resource alerts should compare against request/limit ratios rather than raw byte thresholds.

   Two independent blockers appear together and each alone is fatal: (1) a cluster where the workload already sits ABOVE the proposed multiple, so the alert fires the moment it merges; and (2) a cluster whose `req:limit` ratio is SMALLER than the multiple, which makes the rule **STRUCTURALLY UNREACHABLE — the pod OOMKills before the alert can fire, a permanently dead rule.** When the fleet's `req:limit` ranges widely, **no single request multiple is both reachable on the tightest cluster and quiet on the deliberately under-requested dev tier.** **Use percentage-of-LIMIT instead** (e.g. 0.70 warn / 0.85 critical), which is comparable across clusters by construction. **GENERAL RULE: before mirroring a ratio threshold onto a second workload, enumerate that workload's `request:limit` ratio across EVERY cluster.** #8 says use ratios; this says check WHICH DENOMINATOR survives the fleet.

9. **CPU throttling: use CFS period ratios, not CPU vs limit.** `rate(container_cpu_cfs_throttled_periods_total[5m]) / rate(container_cpu_cfs_periods_total[5m])` directly measures the scheduler denying CPU time. Comparing CPU usage to limit is a proxy that misses bursts.

10. **`absent()` alerts catch silent failures.** When a metric exists, downstream alerts work. When it doesn't (target removed, scrape config broken, exporter crashed), nothing alerts unless `absent({...}) == 1` is also configured.

   `absent()` is true when the series is missing, and an exporter outage makes **every** series missing, so a per-target `absent()` disjunction — the correct shape for detecting a silently-reverted configuration (`learnings-istio.md`) — fires on **every disjunct at once** the instant the exporter, its scrape job, or its ServiceAccount breaks. The page says "the security control is gone on all N clusters", which is indistinguishable from the real thing it exists to catch and is the worst possible time to be wrong. **Fix: AND-guard the chain with a liveness term proving the measurement path is alive** — `and on(cluster) (count by (cluster) (up{job="<exporter>"} == 1) > 0)`, or an equivalent assertion that some *sibling* series from the same exporter is still present. Choose the guard so it is **armed by the exporter's existence, not by the thing being watched** — guarding with another series from the same absent family buys nothing. **Also set `for:` long enough to ride out a scrape restart**, because an exporter rollout produces exactly this signature for a minute or two on every target simultaneously. **The general rule: any alert whose predicate is ABSENCE needs a second predicate asserting that presence was possible.** This is the alerting-layer instance of the arming-proof rule (#82, `learnings-validation-framework.md` §arming proof) — absence is only evidence when you have proved the measurement could have produced data. For an `absent()` chain, only equality (`=`) matchers propagate labels to the synthesized result; a regex (`=~`) environment matcher does not. Use explicit per-environment equality where routing needs that label.

11. **SLO error and total queries MUST contain the literal `{{.window}}` placeholder.** Helm does not process strings inside values files; the SLO chart performs the substitution at template time. Hard-coding a window (e.g. `[5m]`) breaks multi-window SLO calculations.

## ServiceMonitor & ingestion

12. **ServiceMonitor selector mismatch is the #1 cause of "metrics not in Prometheus".** The ServiceMonitor's `selector` must match the Service labels exactly. Verify with:
    ```bash
    kubectl get svc -n <ns> --show-labels
    kubectl get servicemonitor -n <ns> -o yaml | yq '.items[].spec.selector'
    ```

13. **Recording rule outputs take 1–2 minutes to appear** after creation. SLO statuses showing NODATA immediately after creation are usually slow propagation, not configuration errors.

## Grafana dashboards

14. **`label_values()` and Prometheus `external_labels`.** `label_values(some_metric, cluster)` fails when `cluster` is added by Prometheus `external_labels` rather than carried on the metric. Use `label_values(up{job="..."}, cluster)` since `up` always carries external labels.

15. **Grafana import may fail with 403.** The API token may lack folder-level permissions. Fall back to providing JSON for manual UI import.

16. **Dashboard conventions.** Store dashboards in `artifacts/grafana-dashboards/`. Include the standard template variables: `datasource`, `cluster`, `namespace`, `pod`. Use `graphTooltip: 1` (shared crosshair). Verify the namespace in each query matches the actual deployment namespace.

## Metric label differences

17. **HTTP metrics from different collectors use different label names but identical values.** Auto-instrumentation tools (Beyla and similar) emit `k8s_namespace_name` / `service_name`. Service meshes (Istio and similar) emit `source_workload_namespace` / `source_workload`. The values are identical strings (both derived from the same K8s objects), so Grafana dashboard variables can be shared across metric sources — just use the appropriate label name per query.

## PromQL & rate intervals (continued)

18. **`increase()` extrapolates to the full window edges — never grade an integer-valued counter delta against an integer threshold using it.** Prometheus scales the observed rise proportionally to cover the whole requested window, so a counter that moved by exactly an integer amount reports a non-integer value close to but not equal to it (a true delta of 3 can report as 3.21). A check with an integer threshold ("more than 2", "3 or more") then produces a value sitting between the two branches, and two structurally-equivalent checks measuring the same real event can disagree on the verdict purely from extrapolation noise. For an exact integer delta, use `max_over_time(X[w]) - min_over_time(X[w])` instead — it reads the same series without boundary extrapolation. Caveat: the exact form reads a single series identity, so it under-counts (never over-counts) if the underlying series is replaced mid-window (e.g. a workload restart that changes an instance label starts a new series from zero) — pair it with an independent cross-check when that distinction matters.

   `TempoComponentRestarts` fired on `<cluster-b>` (2026-08-05 16:25Z) at value **2.032058757062147** against a `> 2` threshold while the EXACT restart delta was **2**: it fired ONLY because `increase()` extrapolates. Shape: `sum(max by (pod,container)(increase(kube_pod_container_status_restarts_total[1h]))) > 2` (`charts/tempo/service-observability/tempo.yaml:53`). Two consequences: (1) the **effective threshold is `>= 2`, not `> 2`**; (2) because it SUMS across pods, **N replicas each restarting ONCE trips it** — so an alert named "component restarting repeatedly" fires on a single simultaneous restart of both replicas and never on a crash loop. Identical shape + threshold siblings from the same PR : `charts/loki/service-observability/loki.yaml:85` `LokiComponentRestarts` and `charts/mimir/service-observability/mimir.yaml:36` `MimirComponentRestarts`. Fix: exact integer delta, and grade **per-pod** (`max by (pod)`) rather than summing across pods.


## PromQL aggregation & joins (continued)

19. **Every label named in a PromQL join's `on(...)` clause must also appear in the `by(...)` of EACH aggregation feeding that join, or the join can never match — and this fails silently as a permanently-empty result, not as an error.** A `sum by (a, b, c)` feeding a join written as `and on (cluster, a)` will never match anything if the `by` clause drops `cluster`, because the aggregation itself already discarded the label the join needs — the query returns empty for every input, forever, while a naive "did this arm at least once" check on either individual operand can still report armed (each operand individually is non-empty; only the *joined* expression is empty). Discriminate this class by running the identical query with and without the missing label in `by()`, holding everything else constant — a jump from zero rows to non-zero rows on that one token change is the proof. General fix pattern: your arming/liveness proof should run the FULL composed expression with only the graded condition removed, not just check that each operand independently returns data — per-operand arming checks structurally cannot catch a broken join key.

   Live discrimination: the fixed form returned 31/124, 1/65, 1/66 rows where the shipped form returned empty everywhere; the negative control (drop `cluster` from `by()`) goes empty at EVERY window on the same cluster at the same instant — **one token separates "quiet" from "blind"**, which is also how to tell them apart. **Arming scope is the CHECK, not the window**: requiring the composed control to be non-empty *at the window being graded* produced INCOMPLETE verdicts on quiet clusters for 59–68% of five-minute instants; require it non-empty at AT LEAST ONE of the graded windows. That is sound because the control at window W is the gate minus one matcher (a strict superset, so control-empty entails gate-empty and the leg cannot hide a violation), and the failure mode it guards — an unresolvable join key — is WINDOW-INDEPENDENT. Audit the class programmatically: enumerate every `on()` / bare `unless` / `group_left` / `or`-guard site and prove each one's label signature live. Run the composed control at both short and long windows, requiring at least one graded window to return data. Additional one-token proof: without `cluster` in `by()` → 0 rows; with it → 7 rows, with the same negative-control behaviour.
    - **PROVING BOTH OPERANDS EXIST IS NOT PROVING THE EXPRESSION CAN PRODUCE A ROW.** A check joined connection telemetry against namespace labels and carried TWO arming proofs, one per side, both green — but on the live cluster every row of the graded class carried `source_workload_namespace="unknown"`, which matches NO ambient namespace, so the composed join was STRUCTURALLY INCAPABLE of returning a row. The empty result was correct; the `armed: true` claim was not. A negative control (same join, different security-policy class) was also empty, confirming the join key never resolves rather than that violations were absent. **For any `join` / `unless` / `and` expression, add a JOIN-KEY-RESOLVES control proving at least one row matches on BOTH sides** — otherwise an empty result means "this can never match" while reading as "no violations".
    - **A co-sampling window must be measured BETWEEN the two reads, never from a run-wide frozen `as_of`** — the anchor is set at generation time and a long sweep drifts past its own tolerance (observed 157 s against a 120 s window).
    - **Operational corollary**: any edit to a validation catalog invalidates a metric attestation bound to its fingerprint, so the runner refuses to generate until `verify-metrics` is re-run — budget that regeneration into every catalog change. A healthy-form composite should produce rows: example validation returned 367 DaemonSet rows and 21 control-plane memory rows, proving the join could match before grading failures.

20. **PromQL vector arithmetic propagates emptiness — one empty operand deletes the ENTIRE expression it's part of, including any arming/liveness proof riding on the same expression.** If a ratio's denominator is itself a sum of two series (e.g. `opened_total + failed_total`) and one of those two has simply never emitted a sample for the slice you're querying, the vector addition returns completely empty — not zero, empty — and that silently deletes the whole downstream expression, including any check meant to prove the query is "armed" (returning data at all). Guarding only the operand you suspect can be sparse is not enough: every operand in the expression that CAN independently be lazy needs an `or (<operand> * 0)`-style guard (or your engine's equivalent "coalesce with zero" idiom), not just the one you think is the risky one. Verify by comparing an unguarded version (empty), a guarded version (reads zero correctly), and an already-known-good control (matches to several significant figures).

   **COROLLARY, equally important: do NOT reflexively add `or (denom*0)` everywhere.** On a check whose real risk is a MISTYPED LABEL, that guard converts an empty result — which would correctly ERROR — back into a silent 0 that reads as PASS. There the **positive existence matcher IS the protection** and the zero-fill would undo it. **Choose per failure mode: zero-fill protects against genuine laziness; existence matchers protect against wrong names. Applying the wrong one re-creates the bug you just fixed.**


## Verification traps (metrics, logs, shell)

21. **A metric appearing in the store's metric-NAME index is not proof that it has any live series — and this failure class is strictly more dangerous than a metric that doesn't exist at all, because it looks reassuring instead of obviously broken.** A metric name can be indexed while carrying zero actual time series — commonly because an exporter's own allowlist drops the series even though the metric name is still known to the store from another target or a historical scrape. A check written as `count(metric{...} == 0)` then returns empty and reports "nothing bad found" forever, and a reviewer who checks "does this metric name exist" and stops there will be satisfied by exactly the broken case. Always verify a non-zero SERIES count over the time window and label scope you actually care about — never metric-name-index membership — and check more than one target/instance, since a single healthy instance can mask the rest being silently absent.

   **Second-order lesson, worth more than the fact: the corpus ALREADY documented this metric as dead in a DIFFERENT check, and that knowledge did not propagate to the check that used it. Knowledge recorded in one place does not defend a second place — only a MECHANICAL SWEEP across the whole corpus does.** This was the 7th instance of absence-reads-as-PASS in one project, and it survived a static linter, human review, AND a metric verifier that consulted the name index.


## PromQL & rate intervals

22. **Both `increase()` and the "current minus (current offset window)" pattern are wrong ways to difference two counter readings when the underlying series set churns — use `sum(max_over_time(X[w]) - min_over_time(X[w]))` instead.** Measured side by side on a real counter-differencing task where the true delta was a small negative residual: the three methods disagreed by an order of magnitude (`increase()` and the offset-subtraction form were both off by roughly 10x from the correct value). `increase()` boundary-extrapolates (a separate, always-present error); the offset-subtraction form additionally breaks whenever the series set changes across the window boundary — e.g. pods being replaced mid-window mean the two endpoints are literally not measuring the same set of series. That churn is exactly the condition you're most likely to be measuring under (a rolling deploy, a scale event), which is precisely when this bug bites hardest. The `max_over_time - min_over_time` form is computed per-series and survives that churn.

   **For detecting a transient DIP in a gauge, `min_over_time` is BACKWARDS and amplifies the dip — use `max_over_time(X[5m]) == 0` as the "sustained" test.** Measured on `istio_cni` `install_ready`: the instantaneous `== 0` fired at 14/289 samples over 24 h (~4.8%, all benign ~145 ms dips) while `max_over_time([5m]) == 0` fired 0/96. **`max_over_time` is the PromQL equivalent of an alerting `for:` clause.**

23. **Subtracting two `increase()` values COMPOUNDS their extrapolation error instead of cancelling it — do not assume the errors on both sides of a subtraction wash out.** Comparing `increase(counter_a) - increase(counter_b)` when the two true counts are actually equal can still produce a nonzero result, because each `increase()` is independently boundary-extrapolated in its own direction — two true counts of 412 each can render as, say, 413.2 and 411.8, giving a difference of 1.4 where the true difference is exactly 0. A delta rule with no tolerance then manufactures a false alarm on a perfectly healthy system. Use exact deltas (`max_over_time - min_over_time`, or a same-series offset-subtraction where series identity is stable) on BOTH sides of any counter subtraction, not just one. Exception worth keeping: `increase()` IS safe under a bare `> 0` predicate, because `increase()` is exactly zero if and only if the true delta is zero — extrapolation cannot flip that boolean. So an "did anything happen at all" check can keep using `increase()`; a magnitude comparison or a difference between two counters may not.


## Verification traps (metrics, logs, shell)

24. **`kubectl <list-command> --no-headers 2>&1 | wc -l` returns 1 on an EMPTY result, not 0.** `kubectl` writes its "No resources found" message to STDERR (not stdout) and exits 0, so folding stderr into stdout with `2>&1` turns a genuine zero-objects result into a line count of one — a phantom finding on a perfectly clean cluster. The fix is not simply `2>/dev/null` (which silently discards a real error too); prefer `-o json` piped into a real JSON parser and count the `items` array — the count then comes from parsed structure, so stderr cannot contaminate it, and the same pass gives you the structured data you usually need anyway. Audit for this specific pattern whenever a shell-based validation script reports a suspicious exact count of 1.

   A failed authenticated read is a separate trap: check the command's exit status so expired credentials cannot become a false zero (#97).

25. **Querying a metrics or log time-series store with an `endTime` that is still in the future silently UNDER-FILLS the result — no error, no warning, just a plausible-looking wrong number.** A range query with `endTime` set even a few minutes ahead of the actual wall clock returns a result stamped at that future timestamp but computed over only the portion of the window that has real data — which can under-report a rate by a large margin (a measured case: a 30-minute-window rate query returned roughly 60% of the correct value when `endTime` was 12 minutes ahead of the clock). A related, easy-to-misread symptom: an instant query at a future `endTime` can return data while a range query over an overlapping strictly-past interval returns nothing, making a perfectly healthy metric look intermittent. Rule: before any measurement pass, read the actual wall clock and set BOTH window edges strictly in the past (`endTime <= now - one scrape interval`) — never trust a mental estimate of elapsed time, especially in a long working session. Detection if you suspect this already happened: cross-check the same quantity at two different window lengths; if they disagree by more than normal diurnal variation, one of them was short-filled.

26. **A pod on an unreachable node keeps reporting `Running` / `1/1` / `0 restarts` indefinitely — that is FROZEN LAST-KNOWN STATUS, not live health, and `kubectl get pods` will not tell you the difference.** When a kubelet stops reporting, the API server retains the last status it received; nothing marks the pod's containers as unknown until the node controller's eviction timeout elapses, and on a node that is `NotReady` but not deleted that can be a long time or never. **So the most reassuring line in a health sweep — a full column of `Running 1/1 0` — is exactly what a dead node produces.** Any census that reads pod status must **co-read node conditions and treat pods on a `NotReady` node as UNKNOWN, never as healthy**; a check that grades "all pods Running" without that join is structurally incapable of detecting a lost node and will report improving health as nodes drop out. **Discriminators, cheapest first:** the node's `Ready` condition and its `lastHeartbeatTime`; whether the pod's metrics are still arriving (a live workload keeps producing series — this is the same "presence is not activity" question in reverse); and `kubectl top pod`, which fails rather than lying because it reads a live metrics path. **Related but distinct traps in the same family:** `Running` + `Ready` + `restarts == 0` is also satisfied by a pod thirty seconds old (`learnings-validation-framework.md` — age the container, not the pod), and a departed pod's *metrics* linger for one staleness window after the pod is gone. All three are "the reading is real but describes a different moment than you think."

## Autoscaler bounds, exporter reuse and TSDB disk sizing

27. **`promtool check rules` is SHAPE-ONLY and passes mutations that change behaviour — use `promtool test rules` with synthetic `input_series`, then MUTATION-CHECK the tests so they are not vacuous.** Two mutations proved a suite on one alert change: moving the threshold 638→700 failed the boundary test, and dropping `by (<zone label>)` failed the zonal test with output that showed the exact regression — the alert collapsed to a single whole-pool count, lost the zone label, and rendered its summary with an **empty** zone. **Cheap high-value cases for any threshold alert: at-threshold, one-unit-below (boundary), and inside-the-`for`-window (proves `for:` is honoured).** **Alertmanager ROUTE changes have an equivalent offline proof:** render the config both ways and run `amtool config routes test --config.file <f> severity=warning` **at the same version as the live image** (read it from the running pod spec), which prints the receiver name — turning a routing change into a two-row before/after table instead of a claim. ⚠️ Build that table with literal arguments, not a shell variable (`learnings-agent-workflow.md`).

28. **TRAP — the `kube-system/cluster-autoscaler-status` ConfigMap's per-zone `nodeGroups[].health.maxSize` is NOT the pool's configured bound. It is REMAINING HEADROOM, recomputed every CA loop, and every off-the-shelf exporter faithfully exports the misleading number.** Exact formula, measured **18/18 exact with zero mismatches** on a live GKE cluster and independently re-derived by a second agent: `maxSize[zone] = totalMaxNodeCount − SUM(cloudProviderTarget of the pool's OTHER zones)`. Worked example: a pool with `totalMax=1000` and per-zone targets `0/20/654` reports `maxSize` `326 / 346 / 980` — all three exact. For pools that use the PER-ZONE `maxNodeCount` instead, `maxSize` passes through unchanged. `minSize` is derived the same way (shows 0 where `totalMinNodeCount=1`). **Three consequences: (1) the DENOMINATOR MOVES INVERSELY WITH LOAD, so any `target/maxSize > threshold` alert shrinks its own denominator as you scale up; (2) SUMMING `maxSize` across a pool's zones gives 1.5×–2.8× the real bound** (1532 vs 550, 840 vs 300, 1652 vs 1000), so a pool-level saturation alert built that way reads ~41 % when the truth is ~68 % — **it under-reports worst exactly as saturation approaches, and would never fire on the incident it exists to catch**; (3) recovering the real bound from it needs `maxSize_z + Σtargets − target_z`, a cross-zone aggregation over an **undocumented derived field the platform can change silently**. **The cloud's own `clusters.get` API is the only trustworthy source of the bound.** (Exporters checked and all affected: prosimcorp, archived 2025-03-20; bringg/cluster_autoscaler_status_exporter v0.1.0; codefresh-io 2020, which still regexes the pre-1.30 free-text format.)

29. **On GKE Standard the node cluster-autoscaler runs on the Google-managed CONTROL PLANE — there is no pod, deployment, namespace, `/metrics`, log stream or flag for it in-cluster.** `kubectl get pods,deploy -A | grep -i autoscal` returns only the addon autoscalers (CNI vertical/horizontal, konnectivity, kube-dns) — **none is the node autoscaler.** Its ONLY observable surfaces are (1) the `kube-system/cluster-autoscaler-status` ConfigMap — **no `ownerReferences`, EMPTY `managedFields`** (written by an off-cluster client, not server-side apply), annotation `cluster-autoscaler.kubernetes.io/last-updated`, **recreated on CA restart so handle `NotFound`** — and (2) the `container.googleapis.com/cluster-autoscaler-visibility` Cloud Logging stream. **Corollary: the OSS `cluster_autoscaler_*` gauges DO NOT EXIST** (zero descriptors in Cloud Monitoring, empty in the in-cluster TSDB), and CA is absent from GKE's exportable control-plane components (`SYSTEM`/`API_SERVER`/`SCHEDULER`/`CONTROLLER_MANAGER`).

30. **NO metric anywhere carries a GKE node pool's autoscaling MAX — verified live, not from docs — so node-pool saturation alerting requires a small bespoke exporter.** Cloud Monitoring: substring `nodepool` = **0 descriptors**; all 11 `kubernetes.io/node_pool/*` descriptors are TPU-gated (their descriptions say *"Multi-host TPU node pool only"* verbatim) and return 0 series in 24 h; Bigtable and Spanner publish `autoscaling/max_node_count` but GKE publishes no equivalent. The near-miss `autoscaler.googleapis.com/configured_max_size` **exists but is a dead end for GKE**: its only series was a Serverless VPC connector MIG, because GKE's CA drives MIG `targetSize` directly and never creates a GCE Autoscaler object. **The bounds ARE clean from `container.googleapis.com` `clusters.get`, and Node objects carry `cloud.google.com/gke-nodepool` UNTRUNCATED plus `topology.kubernetes.io/zone`** — while the GKE-truncated node NAME is far too fragile to key an alert on. ⚠️ **Absence claims about a given TSDB are INSTANCE-scoped** (a kube-state-metrics allowlist, not a platform fact) — re-derive those per estate.

31. **GKE `clusters.get` `nodePools[].autoscaling` has a HETEROGENEOUS SCHEMA ACROSS POOLS IN THE SAME CLUSTER, which is what disqualifies every pure-JSONPath exporter.** Verified live across 9 pools, three distinct key shapes: (1) `{enabled, minNodeCount, maxNodeCount}` where the counts are **PER-ZONE**, so the cluster-wide max is `maxNodeCount × len(nodePools[].locations)`; (2) `{enabled, totalMinNodeCount, totalMaxNodeCount}`, already cluster-wide; (3) **`{enabled, totalMaxNodeCount}` ONLY — the min key is ABSENT, not zero.** **The GKE API OMITS the unused field entirely, which makes `total_max_node_count > 0 ? cluster-wide : per-zone` a SOUND discriminator rather than a guess** (Terraform's `google_container_cluster` data source surfaces each omitted field as `0`; verified 9/9 pools against both the raw API response and the data source at provider 6.32.0). ⚠️ **`locations` count DIFFERS PER POOL** (2 zones for some, 3 for others), so the multiplier is not a constant. A config-language exporter cannot branch on which key exists, cannot multiply by a sibling array's length, and cannot distinguish absent-key from zero.

32. **Exporter reuse research for "emit a cloud API's configured bound as a gauge": ALL off-the-shelf candidates fail, and the decisive test is running the real binary against the real API response.** Findings, each tested rather than read: **`json_exporter` v0.8.0 is the closest miss** — it correctly emits the per-pool bound gauges (24 correct series across 9 pools, matching the API exactly) using `type: object`, path `{.nodePools[*]}`, labels from `{.name}` — **but `{.locations}` (the zone list) dies with `strconv.ParseFloat: invalid syntax` at `collector.go:112` and emits NO series, because it only ParseFloats a SCALAR and cannot count an array.** Its JSONPath library is `k8s.io/client-go/util/jsonpath` (`exporter/collector.go:24`), so k8s brace syntax **with no `length()` function**; you would have to hardcode the zone count in PromQL, which drifts. Three more measured gotchas: with the default `allow_missing_key=false` a SINGLE scrape logged **51 ERROR lines / 75,200 bytes** because each error echoes the whole JSON blob, and `allow_missing_key=true` only halves it — it does not silence it; there is **no `probe_success` metric**, so failure shows only as a synthesised `up=0`; and it delivers only the DENOMINATOR (the GKE API has no live per-pool node count — `NodePool` has no `currentNodeCount` and `Cluster.currentNodeCount` is documented Deprecated). **Others: `stackdriver_exporter` v0.19.0 — ListTimeSeries only, cannot invent a series with no descriptor. `cluster-autoscaler-status` exporters — export headroom, not the bound (#28). `opentelemetry-collector-contrib` v0.160.0 — ZERO receivers touch the API. A resource-controller (Crossplane / Config Connector) — grants WRITE access to node pools just to read four integers.** **Verdict: a ~140-line stdlib-only exporter beat all of them (see #33).**

33. **A bespoke stdlib-only exporter can be cheaper than adopting one — and the thing that justifies it is usually ~12 lines of branching a config language structurally cannot express.** Prototype measured against a live cluster: **138 lines / 114 code lines of Python, stdlib only** (`json, os, ssl, time, urllib, http.server, threading`) — **no third-party deps, so it runs from a stock `python:3.13-alpine` image with the script in a ConfigMap: no image build, no registry artifact, no new CI pipeline.** It reads bounds from the cloud API (token from the node metadata server) and current counts from the in-cluster k8s API (SA token + `ca.crt`), grouping Nodes by the pool label, and emits **exactly 37 series for the whole cluster**. The irreducible branching is #31's: use `totalMaxNodeCount` as-is if present, else multiply `maxNodeCount` by `len(locations)`. **THREE NEGATIVE CONTROLS, all passed, and all worth copying as a pattern:** (1) **dropping the zone multiplication understates the per-zone pools' ceilings by exactly 3×**, so a pool at 250 live nodes would read 83 % instead of the true 28 % — a false page; (2) **mutating one pool's max 750→620 moves its ratio 80.9 %→97.9 %, crossing a 90 % threshold** — proving the output is sensitive to its input; (3) **a forced API failure flips `<prefix>_scrape_success` to 0** rather than serving a stale-but-healthy-looking payload. **Least-privilege note: `roles/container.clusterViewer` contains exactly 5 permissions** (`container.clusters.connect/get/list`, `resourcemanager.projects.get/list`) — verified via `gcloud iam roles describe` — the correct grant for a bounds reader.

34. **An aggregate-server-side exporter costs FLAT series; recovering the same attribution per-node costs series proportional to NODE CHURN, which on an autoscaling fleet is ~7× the live node count per day.** Measured on an autoscaling cluster: `count(kube_node_info)` = **1354 live** but `count(count_over_time(kube_node_info[24h]))` = **9,180 distinct series in 24 h** — ~7,800 node names created and destroyed per day (55 % of the fleet under a day old; per-node metric FAMILIES churn ~6.8×). **So exposing a node label through kube-state-metrics to recover pool attribution adds one series per node *and* scales with exactly the churn the alert exists to watch (+1,354 active, +9,180/day into the index), while an exporter that aggregates server-side emits ~9 series, flat forever, zero churn.** **PRACTICAL RULE for any monitoring proposal on an autoscaling fleet: never put the NODE NAME in a label set.** That 9-flat vs 9,180-churned asymmetry is the strongest cardinality argument available for a bespoke exporter over any per-node route.

35. **kube-state-metrics v2.13: `createNodeLabelsGenerator` returns NO `kube_node_labels` metrics ONLY while the per-node allowlist is EMPTY — allowlist any single node label and it emits one metric PER NODE.** The node wrapper adds the `node` label even when none of the allowed Kubernetes labels exist on that node, so **an empty allowlist means the metric is missing entirely, not present-with-zero-labels** — which is why `count(kube_node_labels)` returns empty rather than 0 (`learnings-validation-framework.md`, the INDEXED_BUT_EMPTY class). ⚠️ **A shared cloud-specific node allowlist therefore adds active series on EVERY cloud consuming that chart**, not just the one that needed it — price the change fleet-wide.

36. **VictoriaMetrics: `sum(vm_data_size_bytes)` counts ONLY COMMITTED PARTS, so an in-flight merge can make filesystem "used" exceed VM's own accounting by tens of GB with zero change in active series, ingestion rate, or part count.** Measured live (vmsingle v1.148.0): kubelet `used` 357.33 GB vs `sum(vm_data_size_bytes)` 283.4 GB — a **74 GB gap** — while `vm_data_size_bytes{type="storage/big"}` sat **byte-identical across scrapes** and `vm_parts{type="storage/big"}` was frozen. **That frozen pair is the tell: a merge is in flight and nothing has committed.** TRIAGE RECIPE for "disk grew but nothing explains it": (1) diff `sum(vm_data_size_bytes)` against `kubelet_volume_stats_used_bytes`; (2) check `vm_active_merges{type="storage/big"}` and whether `vm_rows_merged_total` climbs while `vm_data_size_bytes` stays flat; (3) **independently ground the REAL dataset size from the object-store backup** (`du -s` on the backup destination) — it matched `vm_data_size_bytes` to within 0.1 %, proving the gap was not real data. **⚠️ SECOND-ORDER TRAP, the one that actually bites: VM REFUSES merges it cannot fit**, logging *"cannot initiate force merge for the partition \<YYYY_MM\>; additional space needed: N bytes"* (`partition.go:1094`) on the `storage.finalDedupScheduleCheckInterval` poll (default 1 h). **A disk-pressure incident therefore SUPPRESSES merges and the debt accumulates silently — and the moment you RESIZE the PVC every blocked merge starts at once, so usage accelerates 50–100× for hours and the disk alert predictably RE-FIRES ~30 min later, looking exactly like runaway growth.** Do not chase it as a new fault and **do not resize again**: grep the log for *"additional space needed"* first — if the refusals stop right before the growth starts, that IS the explanation. (Full worked case: a 300→400 Gi resize released ~67.5 GB of merge scratch; `vm_rows_merged_total` jumped +9.3e9 rows in one 5-minute bucket after several buckets at exactly 0, then decelerated 66 GB/h → 4 GB/h and self-resolved. Snapshots were ruled out four ways — `vm_snapshots=0`, empty `/snapshot/list`, equal create/delete counts with 0 errors, and `snapshotsMaxAge` set — which is the elimination worth copying.) **Setting `-dedup.minScrapeInterval` is what schedules these final-dedup force merges at all.**

37. **Cardinality regressions are diagnosed by DAY-OVER-DAY `topN` DIFF plus a PEER-ENVIRONMENT CONTROL — and the churn metrics everyone blames are often shrinking while the real driver hides on one label.** Method: `/api/v1/status/tsdb?topN=30&date=<d>` on two consecutive days, then diff. On one cluster this identified **seven per-channel exporter metrics each growing ~+1.35 M series in ONE day (~+9.5 M combined)**, with one label going 14.6 M → 24.2 M series and **2.1 M → 3.6 M DISTINCT VALUES (+1.44 M new values/day)**. **COUNTER-FINDING that makes the method worth the effort: the node/pod/instance churn series everyone assumes are the problem all SHRANK day-over-day** (pod distinct values 128 k → 90 k, node 8,192 → 6,328, instance 25 k → 18 k). **Metric NAMES and label NAMES were unchanged, which proves this is pure value-cardinality blowup on an existing label, not new instrumentation** — no new scrape object had been added. **PEER PROOF that it is not simply "this environment is busier": the same metric read 83,430 in one environment vs 3,687 and 339 in its two siblings (23× and 246×) with near-identical instrumentation (1,234 vs 1,236 metric names) and the smallest sibling running a SMALLER disk.** **FIX DIRECTION for this shape is always to drop or aggregate the offending label at the exporter/relabel level, never to resize the volume again** — and watch for active series brushing `search.maxUniqueTimeseries`, past which `count({__name__=~".+"})` itself starts timing out and you lose the diagnostic.

38. **Count an alert-routing change's BLAST RADIUS from the RULE SOURCE, never from the plan's list of affected objects.** A plan for one routing change named **3** affected alerts and included one that was not affected at all; grepping the rule source for the label being matched returned **9**, and the plan's extra entry was a different severity. **Reflex for any routing/matcher change: `grep -c` the matched label in the rule source and ENUMERATE the hits before writing the PR body.** Related shape worth checking first: a route whose `receiver` is a bare ternary on a feature flag is **BINARY AND ENVIRONMENT-WIDE** — when the flag is on, *every* severity pages, including warnings — so adding a single child route with a `severity="warning"` matcher silently demotes **all** warning-tier alerts at once.

## Alert-window sizing and the vmalert query grid

39. **`rate(counter[W]) > 0` with `for: F` has TWO bounds on W, and fixing only one creates the opposite bug.** **UPPER bound:** `rate(c[W])` stays `> 0` for a full `W` after the *last* increment, so `W == F` means the decay tail alone satisfies `for: F` — the `for:` clause contributes **zero filtering**, a single event pages one rate window late, and any annotation of the form "has continued for F" is false. Fingerprint: **the alert fires ~W AFTER the condition already cleared** (measured on a remote-write error-rate rule at `rate[5m]` + `for: 5m`: it went true on the first scrape showing a 33 s burst at 03:55:30Z and paged at 04:00:40Z, ~5 min after remote-write was healthy). **LOWER bound:** `W` must EXCEED the worst-case gap between increments of the underlying counter, or the expression dips to 0 at one evaluation mid-incident, which deletes the pending alert and resets `F` — and with a long `F` the alert then never fires at all. **The attractive wrong fix is to correct only the upper bound:** the first revision went `[5m]`/`for:5m` → `[2m]`/`for:15m` and broke the lower bound, because vmagent's worst-case retry gap is 120–186 s (> `[2m]`), giving a simulated 49 % missed 25-minute outages on a 2-queue vmagent (#42, #43). Final shape `[5m]` + `for: 15m` satisfies both: the tail is `F/3` so `F` still demands ~10 min of genuine signal, and `W` clears the counter's gap ~2.7×. **PROCEDURE for any `> 0` predicate on a rate/increase of an event counter: derive the counter's SLOWEST LEGITIMATE EMISSION INTERVAL first — that is the floor on `W` — then require `F >= 3W`, then verify with an offline replay that reports the LONGEST PENDING RUN against `F` (≥2× headroom, #41), not just fires/doesn't-fire.** The same idiom sits in any `increase(...[5m])>0` + `for: 5m` queue-drop rule and in every ratio rule in the same module — audit them together. This adds the window-sizing rule that a detection-latency analysis alone stops short of.

40. **vmalert does NOT query at wall-clock evaluation time — model the grid as `truncate(wall − evalDelay, interval)` or every offline `for:` replay disagrees with what vmalert actually did.** `app/vmalert/rule/group.go:38` sets `-rule.evalDelay` default **30 s**; `adjustReqTimestamp` (`group.go:709-725`) subtracts it and then calls `timestamp.Truncate(g.Interval)` whenever `evalAlignment` is nil or true — **which is the default** (alignment exists so vmalert results match Grafana plotting; VM issues 5049/1232). Three consequences: (1) with a 1 m group interval every query lands on an **exact minute boundary ~30 s+ behind wall clock**, so the wall-clock evaluation phase is NOT a free parameter — sweeping it measures nothing, and the real free parameter is the **scrape** phase; (2) `ActiveAt` is set from the adjusted timestamp, so the `for:` clock runs on the aligned grid; (3) a replay reasoning in wall-clock or scrape time gives the wrong fire time — the corrected grid put the old rule's earliest fire at 04:02:00Z against an observed 04:00:40Z page, **so the observed page did NOT validate the stated mechanism**. Groups with `eval_offset` set skip the adjustment entirely. Found by a cross-model adversarial lens *after* the correctness lens had swept the wrong parameter and published a verdict off it.

41. **A standalone offline `for:` replay needs three things hand-rolled simulators get wrong, and three controls, or it proves nothing.** (Complements the technique of simulating `for:` *inside* Prometheus with synthetic input series; this is the executable replay to write when parameters must be swept.) (1) **BASELINE** — extend the sample series well before `t=0`. If the first evaluation has no sample at or before its window start, MetricsQL `rollupDelta` (`app/vmselect/promql/rollup.go`) has no `prevValue` and the sim reports "never fires" — a truncation artefact that made a real-world rule look dead. (2) **SWEEP THE EVALUATION PHASE** — vmalert offsets each group's evaluation by a hash of the group name, so the phase is unknown; sweep 0–55 s in 5 s steps at a 1 m interval instead of assuming 0. A 33 s burst under `[5m]`+`for:5m` fires at only *some* phases, and the phase is exactly what decides the observed page time (sweeping reproduced an observed 04:00:40Z page as "earliest 04:00:30Z across phases"). (3) **EFFECTIVE WINDOW > NOMINAL WINDOW** — VM's `rollupDelta` computes `last_sample_in_window − last_sample_at_or_before_window_start`, so coverage is `window + one scrape interval`; ignoring it overstates false-negative risk by a full scrape interval. **Measure FIRE LATENCY and miss-rate against a FINITE outage, not fires/never over a long horizon** — "it fires eventually" hides a 32 min page on a 25 min outage, which is a miss. **Controls that must pass or the sim proves nothing: a sustained outage MUST fire; zero increments MUST never fire; the OLD rule MUST reproduce the historical page.**

42. **Size a `rate()` window against `request duration + backoff`, never backoff alone — and find out how many concurrent senders share the counter.** vmagent `sendBlockHTTP` (`app/vmagent/remotewrite/client.go`, v1.148.0) loops `doRequest → bt.Wait(backoff) → retriesCount.Inc() → goto again`, so one cycle = **request duration + backoff**. Backoff starts at `-remoteWrite.retryMinInterval` 1 s, doubles, and caps at `-remoteWrite.retryMaxInterval` default 1 m (`client.go:41-44`), carrying 0–10 % jitter capped at 10 s (`lib/timeutil/timeutil.go:12-16` `AddJitterToDuration`) — so it is **60–66 s, never exactly 60 s**. Request duration is ~0 for connection-refused (endpoints empty → iptables REJECT) but equals `-remoteWrite.sendTimeout` (`hc.Timeout`, default 60 s, `client.go:154-156`) for a **timeout-class** outage (NetworkPolicy DROP, node partition, destination accepts and hangs). Per-worker cadence is therefore **60–66 s refused vs 120–126 s timeout** — the latter EXCEEDS a `[2m]` window. What rescues it is undocumented and load-bearing: `-remoteWrite.queues` (default `cgroup.AvailableCPUs()*2`, `client.go:207`) runs N concurrent `sendBlockHTTP` loops that all `Inc()` the **same per-URL counter**, so the aggregate cadence is ~N× faster. Measured by offline simulation, `[2m]`+`for:15m` on a timeout-class 25-minute outage: **1 active sender → max page latency 32 m 30 s and a miss in 21 % of phase/seed combinations; 4 senders → never misses, max 18 m.** `[5m]`+`for:15m` never misses in any configuration. **Never rely on queue concurrency you have not written down.**

43. **An alert window's correctness can be silently coupled to a CPU LIMIT in an unrelated file — and the coupling differs per caller of a shared module.** Chain: vmagent's `-remoteWrite.queues` defaults to `cgroup.AvailableCPUs()*2` (`client.go:207`); `AvailableCPUs()` is GOMAXPROCS (`lib/cgroup/cpu.go:19-21`) derived from the cgroup CPU quota by `int(quota)` clamped to ≥1 (`cpu.go:44-47`). All N queue workers `Inc()` the same per-URL retries counter (#42), so **whether a short `rate()` window is ever empty during an outage scales with the vmagent CPU LIMIT.** Simulated miss rate for `rate(retries[2m]) > 0` + `for: 15m` on a timeout-class 25-minute outage: **0/360 at 4 queues, 15/360 at 2 queues, 58/360 at 1 queue.** **Two generalisations:** (a) before sizing an alert window against a client's retry cadence, find out how many concurrent senders share the counter; (b) **when one Terraform module is shared by two callers and only ONE passes a resource override, the MODULE DEFAULT is the config the un-passing caller actually runs** — read it, do not assume the root default applies everywhere (`learnings-terraform.md`). The common instance of this is a per-cloud split where one cloud's caller passes a CPU limit and the other does not.

44. **Picking the right vmagent remote-write metric: three traps, each of which reads as reassuring when it is wrong.** (a) **Do NOT build a `retries/requests` RATIO.** Connection-level failures take the `err` branch at `client.go:427-437` and return before `vmagent_remotewrite_requests_total{status_code}` is ever touched (`client.go:448`), so the denominator goes to 0/NaN **exactly during a full outage** — the alert goes silent when it matters most. (b) **`vm_persistentqueue_bytes_written_total` is cumulative THROUGHPUT, not peak backlog.** vmagent routes *all* remote-write traffic through the persistent queue, so it tracks normal volume; it must never be used to compute buffer headroom against `maxDiskUsagePerURL`. For backlog use **`vmagent_remotewrite_pending_data_bytes`** — and sample it at **≤30 s step**, because a sub-minute stall aliases away entirely at a 5 m step and reads as a flat, reassuring 0. (c) For **DATA LOSS** ignore both and use the hard counters: `packets_dropped_total`, `samples_dropped_total`, `vm_persistentqueue_bytes_dropped_total` (confirm exact prefixes against the pod's own `/metrics` before writing a rule). **Sizing note:** any rate window on vmagent SELF-metrics must span ≥ 2 m to get 4 samples, because the VM operator applies a **30 s** global `scrape_interval` when the VMAgent CR sets none (operator v0.74.0, `internal/controller/operator/factory/vmscrapes/objects.go:393-398`, constant at `vmscrapes.go:66`) and the operator's self-scrape VMServiceScrape sets no interval of its own (`factory/build/vmscrape.go:69-76`).

45. **An alert's description is a CLAIM, and the `(W, F)` pair bounds exactly what it may claim — derive the wording, never hand-write it.** For `rate(counter[W]) > 0` with `for: F`, all the rule establishes is *an increment landed in every trailing W-window across F*. So the LAST increment may be up to **W stale**, and the true activity span may be as short as **F − W**. "continuously for F" therefore overstates on BOTH ends — the same defect class as `W == F` (#39): a rule that mis-describes its own condition. Concrete: a rule shipped at `[5m]`+`for:15m` guarantees a span of ~10 min with a possibly 5-minute-old last retry, so "continuously for 15 minutes" had to become **"repeatedly over the last 15 minutes"** — recurrence across the span, with no claim of a W-length quiet gap. The trap is silent rot: the annotation is falsified whenever `W` or `F` is retuned, and the original bug behind that rewrite was discovered precisely because the old text said retries "have continued for 5 minutes" when they had continued for seconds. **Rules: (1) re-derive the annotation in the SAME commit as any `W`/`F` change, and grep the repo for prose restating the rule — a module README alert table carried the identical overstatement and had to be fixed too; (2) prefer wording that does not depend on `W` at all ("repeatedly over the last F"), so a future retune cannot falsify it; (3) remember `F` is `F` consecutive ALIGNED evaluations, not `F` seconds of wall-clock continuity (#40).**

46. **Pod churn on a PER-INSTANCE series makes a long `for:` unreachable for the churned pod — and the driver is usually the cluster autoscaler, not node upgrades.** Measured on one production cluster: all four vmagent pods (shardCount 2 × replicaCount 2) had ages 38/53/61/73 min while their ReplicaSets were **28 d** old — four pod REPLACEMENTS inside 73 minutes, one logged as `ScaleDown: deleting pod for node scale down` because vmagent sat on the default pool. The operator-generated VMServiceScrape (`kubectl get vmservicescrape <name> -o yaml`) carries **no relabeling that stabilises `instance`** — only an app label and a job rewrite for the reloader port — so `instance` stays `<podIP>:<port>` and changes on every replacement. **A new `instance` is a new alert series identity, which resets vmalert's pending timer, so a `for: 15m` alert on that series is unreachable for any pod replaced inside the window.** With 4 independent pods at least one usually survives 15 min, so the alert stays reachable *in aggregate* — that bound is what to state, not "it works". This is the concrete form of the per-instance series-identity trap, and the thing to measure is **pod-replacement rate**, not just `up[24h]`. **Cheap read-only proxy when the dashboards are unreachable: compare pod AGE against ReplicaSet AGE.**

47. **vmagent redacts remote-write URLs as `<N>:secret-url` where N is ONE-BASED — reading it as a zero-based index invents a second target that does not exist.** Verified on a single-target vmagent v1.148.0: the pod has exactly ONE `-remoteWrite.url` flag, its metrics emit `vmagent_remotewrite_requests_total{url="1:secret-url"}`, the on-disk queue path is `persistent-queue/1_<hash>`, and startup logs `initialized client for -remoteWrite.url="1:secret-url"`. **TRAP:** reading `1:secret-url` as "remote-write index 1 = the SECOND target" makes you conclude there are ≥2 targets and that only one of N is failing — a false discriminator that sends you hunting for an external endpoint, a credential rotation or an egress/NAT change that does not exist. On a single-target vmagent, `1:secret-url` IS the only target. **Always confirm target count from the live pod args (`kubectl get pod -o jsonpath='{.spec.containers[*].args}'`) before theorising about which target failed.** `-remoteWrite.showURL=true` unredacts, and is safe only when the URL carries no credentials.

## Cloud Logging query traps

48. **SUPERSEDED by #49 — prove truncation with result < limit and bound ascending queries explicitly.** **`gcloud logging read` has three defaults that silently produce WRONG incident numbers — two of them reversed a conclusion inside a single investigation.** (1) **`--freshness` defaults to `1d`.** An explicit `timestamp>=X AND timestamp<Y` filter for an older window is ANDed with that default and returns ZERO — indistinguishable from a real absence. This made a chronic error look like it had a clean onset date. **Always pass `--freshness` explicitly whenever the filter contains a timestamp predicate.** (2) **`--limit` truncates NEWEST-FIRST**, so a per-day histogram built from a limited result set shows a **fake cliff at the oldest returned day**, and that oldest bucket is a partial count. Raising 1000 → 5000 moved the apparent "first day" backwards and changed per-day counts; a 5000-row cap was hit at only 10 days back during a volume spike. **Test for saturation by running the same query at two limits — identical output means untruncated, and only then is the series usable.** For "when did this start", use `--order=asc --limit=2`, which is not limit-sensitive the same way; for a full history, page backward with `timestamp<"<earliest-seen-cursor>" AND timestamp>="<window-start>"` until a query returns under its limit. (3) **Confirm the resource type from a RAW log line, never assume it** — a Cloud Run service's logs are `resource.type=cloud_run_revision` (with `resource.labels.service_name`), NOT `k8s_container`, even when the workloads it drives run in GKE; filtering on the cluster resource type returns a vacuous empty. **A negative control for an empty log query must be a window WIDE enough to contain traffic** — a 1-minute probe returned 0 lines on a service doing 500+/hour and nearly confirmed a false "logs are not retained" story.

49. **Three MORE `gcloud logging read` traps beyond #48's freshness/limit pair — and the limit check is "result < limit", NOT "two limits agree".** **(1) `--order=asc` SILENTLY IGNORES `--freshness` as a lower bound.** Observed: `--freshness=7d --order=asc --limit=5` returned entries from ~30 days **outside** the stated window, while the same filter in default (desc) order correctly returned only 7 days. This matters because `--order=asc` is the natural way to answer *"when did this start"* — so earlier advice that *"`--order=asc --limit=2` is not limit-sensitive, use it for earliest occurrence"* is **only safe if you ALSO put explicit `timestamp>=` / `timestamp<` bounds INSIDE the filter string**, using `--freshness` merely as a generous outer guard larger than the explicit range. **(2) THE TRUNCATION CHECK CAN NEED ESCALATING FAR PAST 2000/5000.** For one high-volume signature the counts were 2000@limit2000, 5000@limit5000, 20000@limit20000 — **every one exactly equal to its limit** — and only `limit=100000` returned a real figure (41,750). Two limits that happen to saturate at the *same* ceiling would read as *"identical ⇒ untruncated"*. **The rule is `result < limit`, escalating 10–20× until it holds.** **(3) PROVING AN ONSET IS REAL AND NOT A RETENTION EDGE:** show that ordinary service logs **DO** exist earlier in the same window while the signature has **zero** matches there — logs reaching back two months with zero hits for five weeks before the first match makes the onset genuine.

50. **A LOG-RETENTION BOUNDARY is proved by running the IDENTICAL query at 30 d / 60 d / 90 d freshness: if the count AND the oldest timestamp are identical across all three, that is the true data boundary, not a truncation artifact.** If either keeps moving as freshness grows, you have not hit the boundary. Used to establish a ~29.5-day true window (969 results, oldest fixed) on a store whose nominal retention suggested much more. **Pair it with the `result < limit` check of #49 — the two controls answer different questions** (am I seeing everything in the window, vs is the window the real one).

51. **A broad, untargeted substring filter over a wide freshness window can HANG FOR MINUTES even at a small `--limit`, because freshness and limit bound the RETURN SIZE, not the SCAN COST.** A bare `textPayload:"<substring>"` over 30 d with `--limit=500` on a busy service ran 6+ minutes. **Always pair a `textPayload:` / `jsonPayload.message:` substring search with explicit `timestamp>=` AND `timestamp<=` bounds** — e.g. ±30 min around a known event — rather than relying on freshness plus limit.

52. **Pick the RESOURCE TYPE by probing, not by intuition — the wrong one returns a VACUOUS EMPTY that is indistinguishable from a real absence.** Two measured cases on one platform: kubelet **`Evicted` pod records live ONLY under `resource.type="k8s_pod"`** with `jsonPayload.reason="Evicted"` — `k8s_event` and `k8s_node` both return **zero** for the same filter, which is a negative control, not a query bug. And a service running on a **serverless** runtime logs as that runtime's type, **not** `k8s_container`, even when its workloads run in Kubernetes. **Pull ONE raw log line and inspect `resource.type` before assuming any filter works.** For cluster-autoscaler node-removal evidence specifically, `logName:"cluster-autoscaler-visibility"` with `resource.type=k8s_cluster` plus a node-name substring returns `scaleDown.nodesToBeRemoved` decision records fast and reliably — where the "obvious" `protoPayload.methodName:"NodeDeletion"` alternative did not return within 90 s.

53. **Default DESC order and ASC order answer DIFFERENT questions, and a truncated desc result is still trustworthy at one end.** When a per-id query truncates at `--limit`, the returned **`max(timestamp)` is still reliable** as the true latest activity for that id (desc always starts from the newest), but **`min(timestamp)` is an artificial cutoff hiding older history.** **Useful pattern: use default desc to reliably answer "is this still happening / has it gone silent", then a separate `--order=asc` query BOUNDED TO THE MISSING GAP (first-known-event → the desc fetch's `min`) to backfill the immediate aftermath of an old incident.**

54. **A SHORT event-window sample gives you a reliable MIX and an unreliable RATE — do not extrapolate an incident rate from `kubectl get events`.** A measured 29 evictions in a **49-minute** window extrapolated to ~770 ephemeral-storage + ~30 memory evictions/day. The authoritative 29.5-day census from the long-retention log store returned **976 total: 788 ephemeral-storage (26.7/day), 105 other/disk (3.6/day), 83 memory (2.8/day)** — a **25× overstatement**, because the short window landed inside a 3-day burst (139/202/236 all-cause per day against a ~33/day mean). ⚠️ **And k8s event TTL is NOT stable or documented per-cluster — one pass measured ~4.5 days on a cluster where a later pass found only ~59 MINUTES live in the API.** **Always re-measure the live window (oldest/newest `firstTimestamp`) rather than trusting a previously-recorded retention figure, and use the log store for anything older than the last hour.** **Two cheap controls that would have caught the extrapolation: (a) run the long-retention query at two limits and confirm identical counts; (b) push freshness to 60 d and 90 d and confirm the OLDEST timestamp stops moving (#50).**

55. **⚠️ SIZING A MEMORY LIMIT FROM EVICTION EVENTS OR FROM A LIVE-POD SNAPSHOT IS INVALID IN BOTH DIRECTIONS — this shipped wrong in a delivered production recommendation and had to be retracted.** **(1) A live-pod snapshot (`kubectl top pods`) is SURVIVORSHIP-BIASED** — it can only sample pods that have not yet died, so its max **understates** the tail. **(2) Eviction-event usage is CENSORED at the node ceiling** — the kubelet cuts the workload off, so every observation is a **truncated lower bound**, never the session's true demand. ✅ **THE TELL IS A SUSPICIOUSLY TIGHT CLUSTER JUST UNDER A HARD BOUNDARY.** Measured over 29.5 d (n=79 memory evictions, usage parsed from the event's `offending_containers_usage`): one profile on a 12.96 GiB-allocatable node died at **12.0 / 12.2 / 12.4 GiB** min/p50/max — a **0.4 GiB spread across 9 events**; every other profile likewise died in a narrow band **at its own node's allocatable**. **That is the signature of a workload with no enforceable ceiling growing until the node stops it — NOT of a workload that needed exactly that much.** Consequence: the limit derived from the snapshot would have OOM-killed **78 of 79 (99 %)** of the population that actually died. **RULE: when observations cluster tightly just under a hard boundary, treat them as CENSORED, say the number is NOT DERIVABLE, and either measure true demand on a deliberately OVERSIZED node or make the cap an explicit product decision. Do not report max-observed as max-needed.**

56. **A useful IDLE-vs-ACTIVE discriminator lives INSIDE the eviction event itself — no cross-service log correlation needed.** Log-correlating an eviction against application logs was noisy, window-dependent and had a ~28 % miss rate on a 30-minute lookback. The event's own `jsonPayload.metadata.annotations.offending_containers_usage` for the workload container separates them cleanly: an **idle** pooled pod shows ~50–150 Ki (near a request of 0), while an **actively-claimed** pod under real pressure shows **multiple GiB** (observed median ~27 GiB across 83 memory evictions, min 4.3 GiB). **Zero-vs-GiB is a clean, self-contained signal straight from the event.**

57. **`container`-label gaps in cAdvisor for a namespace are usually the RUNTIME, not a relabel bug — and the decisive test is the RAW kubelet scrape, not the ingested series.** For pods under a **gVisor / sandboxed RuntimeClass**, the **raw** cAdvisor exposition already emits `container=""` (and empty `image`/`name`), because the userspace kernel hosts the containers and the host-side cgroup stops at the **pod slice**; `runc` DaemonSets on the **same node in the same scrape** carry proper `container=` labels. **No `metricRelabelConfigs` change can restore it — it is an upstream sandboxed-runtime limitation, and an upstream-triage candidate rather than a config fix.** **DECISIVE TEST: `kubectl get --raw /api/v1/nodes/<node>/proxy/metrics/cadvisor` and diff the sandboxed-pod lines against the `runc`-pod lines ON THE SAME NODE** — looking only at already-ingested series cannot distinguish *"the pipeline dropped it"* from *"the source never had it"*. ✅ **THE WORKAROUND IS NOT A DOWNGRADE: the POD-LEVEL cgroup slice IS the real number, and it is selectable as `name=""`** (the leaf `cri-containerd-*` scope carries `name=<hash>`). For a single-workload-container pod, grouping by pod is per-container-equivalent. Working shape: `max_over_time(sum by (pod)(container_memory_working_set_bytes{namespace="…",name=""})[30d:30m])`. ⚠️ **Two cautions when you read those numbers: every profile's MAX will sit just under its own pool's allocatable, i.e. the data is still CENSORED per #55 — p99 is trustworthy, max is not a statement about demand.** **SEPARATELY and genuinely fixable: `container_spec_memory_limit_bytes` / `container_memory_failcnt` / `container_oom_events_total` returning ZERO series is usually an explicit `action: keep` ALLOWLIST regex in the cAdvisor scrape config** — fix that by widening the alternation, and meanwhile **fall back to kube-state-metrics**, whose `kube_pod_container_resource_limits{container=…}` and `kube_pod_container_status_last_terminated_reason{container=…}` DO carry a real container label.

58. **Verify a `metricRelabelConfigs` DROP regex against the TARGET'S LIVE PAYLOAD, not against the ticket's top-N list — the top-N list is what will be wrong.** A ticket named **7** offending metric families and prescribed a regex for them; fetching the real payload (356,544 lines, 268 distinct names, via `kubectl get --raw /api/v1/namespaces/<ns>/pods/<pod>:<port>/proxy/<path>`) showed the regex actually matched **18** families — 11 sparse per-object counters that only appear once the object has traffic, so **they never reach a top-N list while carrying the SAME unbounded label**. Two more findings only the live payload gave: **a dashboard-queried family was saved ONLY by an underscore in the pattern** (`channel_.*` vs `channel.*` — the latter silently kills it), and **a residual copy of the offending label survived on 8 OTHER families**, so "drop the N families" did **not** fully remove the label. ✅ **GENERALIZABLE TEST SHAPE: parse the regex back OUT of the rendered manifest, anchor it as `^(?:re)$` (Prometheus semantics), then assert the INVARIANT — every matched family carries the offending label, and nothing WITHOUT it is matched — rather than a hand-listed expected set. The hand-listed set is what was wrong.**

59. **Cardinality cleanup has a MANDATORY ORDER: deploy the drop rule FIRST, then delete the series.** Deleting first is a **no-op** — the agent re-ingests on the next scrape (30 s). **Use the SAME regex in both so they cannot disagree.** After the delete the **index shrinks immediately but disk is reclaimed only during subsequent background merges**, so `df` lags by hours — **verify via `/api/v1/status/tsdb?topN`, not `df`.** A manual delete replaces waiting a full retention period for series to age out, which is what lets you size a volume bump for weeks instead of months.

60. **INDEX ROWS COST ~42× WHAT SAMPLES DO, which is why CARDINALITY is the only real lever on a single-node TSDB and why `indexdb`-as-percent-of-total is the best one-number health check.** Measured on one VictoriaMetrics v1.148.0 instance: `vm_rows{type='indexdb/file'}` = 5.0 e9 rows in **144.55 GB** (~**29 bytes/index row**) against `vm_rows{type='storage/big'}` = 276.5 e9 in **191.78 GB** (~**0.69 bytes/sample**). Live confirmation of the asymmetry: one exporter was **~13 %** of ingested samples but **54.8 %** of stored series. **`indexdb` was 42.8 % of total on the sick instance vs 32.6 % and 7.9 % on its healthy peers — so the metric NEEDS A PEER to read against.** **COROLLARY: adding retention or disk scales the CHEAP axis; only relabeling touches the expensive one.**

61. **A fixed-retention TSDB with GROWING cardinality can NEVER reach steady state, which makes volume resizes a treadmill — and a naive regression over the whole window says the OPPOSITE.** Mechanism: a retention purge reclaims the partition from N days ago, which was written when cardinality was **half** of today's — so every purge cycle pays **yesterday's smaller bill while today's ingest bills double**. Free space is therefore a **SAWTOOTH whose post-purge peak declines monotonically**. Measured: active series doubled in 30 days (+110 %), and a linear regression over 7 d **straddling a purge jump** reported free space **GROWING at +1.92 GB/day** while it was actually **falling 8.5–10.6 GB/day**. Treadmill evidence from the same instance: the volume went 200 → 240 → 300 → 400 Gi in ~7 weeks and the last +100 GB bought **exactly 6 days**. ✅ **MEASUREMENT RULE: on any TSDB disk-headroom question, regress ONLY the segment since the last partition-drop jump — a whole-window slope is an artifact — and separately say whether that segment is flat/decelerating (approaching a real steady state) or accelerating.** ⚠️ **A second artifact compounds it: `vm_free_disk_space_bytes` and `vm_data_size_bytes` carry pod/instance labels, so a `query_range` spanning pod restarts returns N DISJOINT series rather than one line** (12 restarts over 30 d in this case) — merge across pod labels sorted by timestamp, or aggregate with `sum() without(pod, instance)`, which VictoriaMetrics merges at query time. A regression on the raw multi-series JSON is meaningless.

62. **A STATIC percent-full threshold on a SAWTOOTHING volume is a flapper that actively TRAINS THE TEAM TO RESIZE AND MOVE ON.** One disk alert crossed 80 % **six times in 30 days**; **five self-healed within hours** when a retention partition-drop reclaimed tens of GB, and only the sixth stuck. **So the rule carries NO information about whether you have six hours or six weeks — and its own annotation prescribed the stop-gap ("grow the volume or lower retention"), which is how a team ends up doing four resizes and zero cardinality work.** ✅ **BETTER SHAPE: keep the static rule at a HIGHER floor as a backstop, and add `predict_linear(kubelet_volume_stats_available_bytes[6h], 7*24*3600) < 0`** — it ignores transient crossings a purge will fix and fires on the trajectory a purge will **not** fix. **This is the alert-design consequence of #61: if the underlying signal is a sawtooth, a level predicate is the wrong predicate.**

63. **A scrape config can BUDGET FOR PAYLOAD SIZE AND STILL HAVE UNBOUNDED TSDB CARDINALITY — those are different budgets, and conflating them is the generalizable trap.** One exporter's "per-object" endpoint labels every metric with a **process-level identifier regenerated on every connection open**, so cardinality is unbounded **by construction**. The template's own comment explicitly anticipated payload growth and budgeted for it with a raised `scrapeTimeout` and a 64 MiB `max_scrape_size` — it budgeted **scrape size** and never **cardinality**. Measured consequence: 7 families = **53 %** of a 39.27 M-series/day total, with that one label holding **3,000,258 distinct values**, while a peer cluster on the same instrumentation had 78× fewer. ⚠️ **When a scrape path is named `per-object`, `per-connection`, `detailed` or similar, assume an unbounded identifier label until you have counted its distinct values — and note that "the fill is REAL DATA" is provable by `vm_active_merges = 0` alongside `sum(vm_data_size_bytes)` ≈ used**, which distinguishes it from transient merge scratch.

## Alert validation, query semantics and telemetry operations

64. **Split noisy panels into actionable + informational tiers**: If a monitoring panel is consistently non-zero across all environments, it's masking real signals. Split into separate panels: actionable (red threshold, must be zero) and informational (blue/neutral, track trend). Applied to Istio Cat 1 -> Cat 1a (mesh errors) + Cat 1b (HBONE ping). Use Grafana MCP patch operations to split panels without rebuilding the dashboard.

65. **Grafana MCP patch for panel splits**: To split a panel: (1) patch existing panel's title/description/query to the "actionable" variant, (2) add new panel via `$.panels/-` append with the "informational" variant, (3) adjust `gridPos` of displaced panels to prevent overlap. Single `update_dashboard` call with multiple patch operations. Avoids full dashboard JSON replacement.

66. **Alert `group by` must use labels present on the metric**: Use `group by (cluster, namespace)` not `group by (cluster, environment)` for per-resource alerts. `environment` is often an `external_label` added by Prometheus, not present on all metrics directly (e.g., `rollout_info`). `namespace` provides the correct cardinality for per-workload alerts. Discovered on Argo Rollouts `ArgoRolloutsRolloutDegraded` alert.

67. **PromQL `unless` fails as a node-drain filter when nodes vanish without cordoning**: GKE preemptible eviction and auto-repair remove nodes WITHOUT `kubectl cordon`, so `unless on (node, cluster) (kube_node_spec_unschedulable == 1)` passes everything through when the right side is empty (vanished node produces no metrics). Fix: flip to a positive assertion: `and on (node, cluster) (kube_node_spec_unschedulable == 0 and kube_node_status_condition{condition="Ready", status="true"} == 1)` — only alerts when the node is actively schedulable+Ready; vanished nodes produce no metrics, so `and` yields nothing. Applied to `ZtunnelDown` + `IstioCNIDown` alert rules.

68. **Replace hardcoded namespace exclusion lists with dynamic `kube_namespace_labels` joins**: Instead of maintaining `source_workload_namespace!~"unknown|gmp-system|kube-system|tailscale|kong|langgraph"` (brittle, requires PR for every new namespace), use `and on (cluster, source_workload_namespace) label_replace(kube_namespace_labels{label_istio_io_dataplane_mode="ambient", namespace!~"tailscale|kong|langgraph", environment=~"dev|test"}, "source_workload_namespace", "$1", "namespace", "(.*)")`. Self-maintaining: new non-mesh namespaces are auto-excluded, new enrolled namespaces are auto-included. Requires `istio.io/dataplane-mode` in the kube-state-metrics `kube_namespace_labels` allowlist . Keep explicit exclusions only for namespaces that are enrolled but architecturally bypass ztunnel (e.g., tailscale kernel WireGuard).

69. **Exclude `destination_workload="unknown"` from mesh connection failure alerts, but keep `source_workload="unknown"`**: `destination_workload="unknown"` = outbound to external endpoints the mesh can't control (false positives). `source_workload="unknown"` = inbound from external sources -- this IS actionable, especially under STRICT mTLS where external plaintext gets rejected. Applied to `IstioMeshConnectionFailures` and `ZtunnelHighConnectionFailureRate` alerts .

70. **Transient rollout plaintext requires longer alert `for` durations**: During deployment rollouts, new pods briefly send plaintext before ztunnel CNI redirect rules take effect (seconds, not sustained). One measured tuning used `for` durations on `StrictMtlsUnexpectedPlaintext` alerts of 15m (NonProd) and 10m (Prod) to exceed the rollout plaintext window and avoid false fires. `StrictMtlsPlaintextRejections` can stay at 5m because actual STRICT rejections are sustained, not transient .

71. **gmp-system namespace generates noisy istio_tcp_connections_failed_total**: GCP Managed Prometheus (gmp-system) scraping pods not ready triggers ambient mesh connection failure alerts. Fix: add `source_workload_namespace!="gmp-system"` to metric selectors. Also raise connection failure traffic floor from `>0.1` to `>0.5` to filter low-traffic noise. Calibrate any volume floor against the path's traffic baseline and pair it with absolute-error-count and availability companions (#113).

## Alert triage and query semantics

72. **Mimir intermittent HTTP 500 "too many unhealthy instances in the ring" is a transient ring degradation, NOT an absent-metric or query-syntax problem**: The prod Mimir datasource can return 500 on ALERTS / metric-names queries while ordinary metric queries (e.g. `istio_tcp_*`) answer fine — it's a transient store-gateway/ingester ring blip. Fix: just retry (recovered in ~30s during a prod soak). Do NOT mis-diagnose as "ALERTS not in this datasource" and do NOT chase a regex. Separately, Grafana `query_prometheus` INSTANT queries require the `endTime` param (`startTime` is ignored for instant; required only for range).

73. **`histogram_quantile` over SPARSE/BURSTY event counters produces flaky latency alerts — an artifact, not a regression**: A p9x latency alert on a low-rate bucketed counter (e.g. `IstiodHighXDSPushLatency` on <cluster-a>) can flap when pushes are sparse and bursty: with few samples per window, `rate()` on `_bucket` series is dominated by single bursts and the interpolated quantile jumps to the top bucket boundary. Before treating a high-quantile spike as real, check the event RATE (`rate(..._count[window])`) — if events are sparse, the quantile is a histogram-quantile artifact and the component may be perfectly healthy. Consider gating such alerts on a minimum event rate.

74. **For a ratio-AND-guard alert, query the ratio and the guard variable SEPARATELY over a long baseline to find which condition is the real trigger**: Compound alerts of the form `failure_ratio > R AND traffic_rate > G` (e.g. `ZtunnelHighConnectionFailureRate*`: `failed/(opened+failed) > 5% and opened_rate > 0.5/s`) can fire because EITHER condition newly crossed. Don't assume the firing = a new failure spike. Plot both variables over 24h: here the failure ratio was **chronically ~25–40% all day** (pre-existing, latent) while the `opened_rate` traffic guard sat below 0.5/s and only briefly crossed (0.97/s) during a rollout + migration-Job traffic uptick — so the **traffic guard was the trigger, not a failure regression**. Implication for triage: the acute alert is benign/self-limiting (traffic drops → resolves), but it EXPOSED a real chronic condition worth a separate follow-up. Also implies the guard/`for` may be mistuned for that pair. On the prod sibling (same 5%+0.5/s, `for: 5m`) the same chronic ratio on a real-traffic path would fire meaningfully.

75. **A "Gateway not programmed" alert firing with `reason=AddressNotAssigned` while the LB is actually healthy is a control-plane STATUS-WRITEBACK stall, not a traffic problem** (Envoy Gateway v1.7.1). When the backing LB Service already has a valid `.status.loadBalancer.ingress[].ip` AND all listener conditions are `Programmed/Accepted/ResolvedRefs=True`, the data plane is fine (pods ready, VIPs live, routes attached) — real traffic impact ≈ none, and the alert's "listeners not accepting traffic" text is MISLEADING. **Triage order: check listener conditions + the Service's `status.loadBalancer.ingress` BEFORE chasing the runbook's usual causes** (missing TLS secret / listener conflict / dataplane rollout). **It FLAPS SYNCHRONIZED across clusters** — `Programmed` flipping True→False at the exact chart-sync/certgen hook time on several clusters at once, from a common controller reconcile/leadership blip. **Remediation is PER-CLUSTER**: restarting the EG control-plane deployment cycles the controller only (data-plane proxy pods untouched) and clears it within ~1 min; every affected peer needs its own restart. If it recurs per chart-sync, upstream-triage it as an EG v1.7.1 status-writeback bug.

76. **Update runbook PromQL in the SAME PR that changes a live alert's selectors** — runbook-to-live-alert drift is a silent trap. When you tighten a selector on a live alert rule (e.g. adding `source_workload!="waypoint"` to `ZtunnelHighConnectionFailureRate`), the runbook's example PromQL still shows the OLD selectors and misleads the next responder. Add "runbook selector sync" to the alert-PR checklist.

77. **Distinguish a REAL STRICT-mTLS rejection from accepted-plaintext churn with an `opened_total{unknown}` absence discriminator, NOT a failure ratio.** A genuine STRICT reject has `istio_tcp_connections_opened_total{connection_security_policy="unknown"}` ABSENT by construction (the connection never completes the handshake), while high-volume accepted-plaintext traffic (external LB/probe, canary reconnect churn) has `opened_total{unknown}` HIGH. So a `failed/(opened+failed)` ratio silently DROPS the real-reject case (empty denominator) — the very thing you want to catch. Correct form: `sum by(KEY)(rate(failed_total{unknown}[5m])) > 0.1 unless sum by(KEY)(rate(opened_total{unknown}[5m])) > 0.1` (`unless`, same `by()` key incl `environment` on both legs). Keep `source=unknown` (a rejected enrolled source loses identity → `unknown`) but exclude benign infra by name (`gmp-system|kube-system|tailscale` ns, `otel.*|konnectivity-agent` workloads — konnectivity apiserver service-proxy rejects survive as failed-without-opened but are benign human `kubectl proxy`). Note `source=unknown` alone does NOT distinguish reject from churn. A prod rejections rule of the raw form `failed_total{unknown}>0.1` CANNOT be re-enabled as-is — it false-fires on external/LB/ingress-edge/canary series that are all accepted, not rejected.

## Measurement and validation design

78. **LAZY vs NON-LAZY counters — a "lazy" series does not exist until the fault first occurs, so `== 0` on it passes FOREVER and absent-and-healthy is indistinguishable from absent-because-dead.** Any zero-assertion therefore needs a non-lazy **ARMING PROOF**, verified across the WHOLE applicable profile set, not one cluster. Three rules: (1) **prefer a gauge, or an always-emitted total, over an error-only counter**; (2) **a sibling that is itself lazy is not an arming proof — it just moves the problem**; (3) **COUNTER-INTUITIVE and worth measuring rather than assuming: an ERROR-DIMENSION child series is not automatically lazy.** Some exporters emit every enum member of a dimension from startup (all response-code classes per listener, all pod-phase enums per pod), which makes a genuine zero AFFIRMATIVE — and an enum-complete gauge is the best arming proof available. **Measure it; do not infer laziness from the fact that a label value names an error.**

79. **Count pre-existing-vs-new by OWNER-PREFIX, never by pod name.** Any check that carves out pre-existing bad state (crash loops, `ImagePullBackOff`, unhealthy pods) must key its baseline set on `namespace/<owner-prefix>/<container>`, stripping the ReplicaSet hash and pod suffix (`<application-service>-58694b87bf-2v6rp` → `<application-service>`). A crash-looping or image-stuck pod is recreated under a new name constantly, so a pod-keyed set classifies the SAME pre-existing condition as "new" on every single run — the exact false-positive the carve-out exists to prevent. Grade as: absent-from-baseline = NEW = FAIL; in both and within tolerance = pre-existing = note only; in both and materially worse = WORSENING = FAIL. (An unrelated app crash loop — `<cluster-g> <workload-namespace>/<application-service>`, 335 cumulative restarts — must never gate a mesh upgrade.)

80. **`VAR=value cmd | python3 …` does NOT export VAR to the python stage.** A command-prefix assignment applies only to the FIRST stage of a pipeline, so the downstream interpreter dies with `KeyError` — and in a validation harness that surfaces as `ERROR` on a perfectly healthy target, which reads as a real finding. Use an explicit `export VAR` before the pipeline. (Hit while wiring a supplied `$EXPECTED_REV` into an ArgoCD `targetRevision` check.)

81. **Comparing a kubectl-derived count against a PromQL-derived count is SAMPLING-SKEW sensitive and produces off-by-N on perfectly healthy clusters.** A three-way equality read `active_proxy_count=183` vs `redirection_annotated=182` purely because the pod dump and the metric scrape were ~10 minutes apart; co-sampled 5 minutes later it was 182==182==182 (the underlying gauge oscillates continuously with no fault). Any check equating a live API snapshot to a scraped metric must either co-sample at one instant or declare a bounded skew tolerance (~120s ceiling, ±1 beyond one scrape interval), MUST store BOTH wall-clock sampling timestamps so a later diff is interpretable, and should re-sample before grading rather than FAIL. Excess skew is a WARN, not a FAIL. Two refinements: (a) a join that crosses TWO scraped exporters (e.g. ztunnel + KSM) is a different problem — it is not kubectl-vs-scrape, so the remedy is re-evaluating a single-evaluation tuple one interval later and storing `evaluated_at`, not co-sampling; (b) a run-wide frozen observation anchor and a per-check co-sampling window are ORTHOGONAL and both bind — the anchor makes N targets comparable to EACH OTHER, the between-the-two-reads window makes one target's two sides comparable to THEMSELVES. A frozen anchor drifts past its own co-sampling window as a long sweep runs (observed 157s apart), so measure the window BETWEEN THE TWO READS, not from the anchor. When N workers hit one Prometheus with RELATIVE windows evaluated at different instants, two targets' "last 15m" can be 40 minutes apart — derive absolute windows from the anchor (PromQL `@` modifier) and report the anchor SPREAD (earliest/latest/delta) so cross-target claims can be qualified. **EXTENDED by #95: exact-count equality across independently-sampled populations needs a two-dimensional set difference plus a sustained form, not a wider tolerance.** **Owner entry for the skew rule** — `learnings-validation-framework.md` is a shorter earlier copy that now points here, and separately owns the **quantile-window asymmetry** finding (a p99 read 24.8 ms at `[5m]` vs 7865 ms at `[1h]` at the same instant: the SHORT window misses the tail rather than smoothing it; store the window as a mandatory payload field and refuse cross-window diffs).

82. **Two ratio shapes that report a confident wrong number instead of erroring: the NEGATED MATCHER on a mistyped label, and the LAZY NUMERATOR.** (a) **A negated matcher (`!~` / `!=`) on an ABSENT label matches EVERY series** — an absent label compares equal to `""`, and `"" !~ "2.."` is true — so a mistyped label name makes the numerator silently select the WHOLE denominator and the ratio is EXACTLY 1.0. It does NOT return empty. Measured: the mistyped `http_status_code!~"2.."` selected all 99 jobs value-for-value == denominator, while the correct `http_response_status_code!~"2.."` selected 35 of 99 with discriminating per-job values (0.0587 / 0.517 / 0.0). It read as PASS for weeks because the check graded the ratio as "unchanged vs baseline" and the baseline was also 1.0 — a signal structurally incapable of moving. **Fingerprint: a clean 1.0 across ALL series is a mistyped label, not an outage.** STANDING RULE: never arm a check with a negated matcher; arm with a POSITIVE existence matcher (`{label!="", label!~"2.."}`) which returns empty ⇒ ERROR when the label is absent. Do NOT "simplify" that pair to a positive class match like `=~"[^2].."` — a 3-char class silently drops the `"0"` status code Beyla emits for aborted requests. Do NOT add an `or (denominator*0)` zero-fill to that ratio either: it would turn the mistyped label back into a silent `0` PASS. The arming leg is the protection, the zero-fill guard is not. (b) **A lazy slice in a ratio numerator (`response_code=~"5.."`, an error-only counter) makes `sum()/sum()` return EMPTY, not 0**, on a target that has simply never had the fault — turning a healthy target into an ERROR. Guard with `or (<non-lazy denominator> * 0)`. GOTCHA that bit us: PromQL vector `+` with one empty side is ITSELF EMPTY, so where the denominator is `opened + failed`, a never-armed `failed` takes the denominator AND the arming proof down with it — the guard must wrap BOTH occurrences of the lazy term. Distinguish this from the lazy-counter-zero-assertion trap (#78): same root cause, different site, and the fixes are different. The absent-label case was independently reproduced with the OTel semconv ≥1.21 label **`http_response_status_code`** misnamed as `http_status_code`: every service on every cluster reported 100% errors, including the positive control. **Before filtering, run `count by (<label>) (<metric>)`; a single `{}` group means the label is absent, not empty-valued.** A control that merely returns something is insufficient. Same family as the doubled-cluster-label trap . Before rewriting a matcher, enumerate its actual values with `count by (label)`: Beyla's aborted-request status `http_response_status_code="0"` occurred on 6 series on one cluster, 20 fleet-wide, and a three-character positive class discarded it. The existence-plus-negation form had a per-job delta of zero across all 35 matching jobs.

83. **A first-match-wins grading table needs BRANCH REACHABILITY, not just "every branch names a status" — and an unreachable graded row is invisible to every linter.** The validation suite catalog specification in this example requires every delta-table row to end in PASS/WARN/FAIL/INFO/ERROR. That is necessary and not sufficient: rows are evaluated in order, first match wins, so a row can name a status, read perfectly to a human, and never fire. Audit method: transcribe the table to code in shipped order, then construct ONE concrete input per row and assert it lands on that row; a row with no such input is dead. Four sub-classes found in one audit of two checks (`<check-id>` / `<check-id>`, 2026-07-28): **See #96 for the DUAL class — a reachable row whose collection-valued predicate is ambiguous between existential and universal readings, which produces a FALSE PASS.**
    - **Shadowed row** — a later row's inputs are fully covered by an earlier one. `| Tuple set equals baseline | PASS |` sat above `| Tuple sustained at [1d] and present at baseline | WARN |`; those are the SAME input when the sustained tuple is already in the baseline, so the check's own explicit "the only condition under which this check may WARN" mandate was unreachable and a live-but-pre-existing plaintext path graded PASS silently. **Reordering alone was NOT the fix** — the equals-baseline predicate was 100% subsumed by (all-empty PASS) ∪ ([7d]-only INFO) ∪ (WARN), so promoting WARN would merely have moved the shadow onto the PASS row. The row had to be **re-predicated** as a terminal benign catch-all ("no tuple live at the short windows"). General shape: order graded rows **specific before general**, put the benign catch-all **last**.
    - **Nesting-shadowed row** — `rate(x[7d])` is a superset of `rate(x[5m])` at the same instant, so `arm3_rows_7d == 0` *entails* `arm3_rows_5m == 0`. A specific "the join stopped resolving between phases" ERROR row was therefore unreachable behind a generic "armed == false" ERROR row. Fix: move the specific row first and predicate it on the other arming legs being live. Verdict-neutral (both ERROR) — it only changes which *diagnosis* is emitted, which is the whole value of the row.
    - **Uncovered input (the dual of an unreachable row)** — "all tuple sets empty NOW while the baseline was non-empty" (the condition cleared) matched no row at all and fell off the bottom with no status. Enumerate the input space, not just the rows.
    - **Rows incorporated by reference** — a delta rule whose graded outcomes live in prose ("Identical to `<check-id>`, but a new tuple yields WARN") cannot be linted for reachability at all, and silently imports rows keyed on a window the borrowing check does not measure. Treat cross-check row inheritance as a defect, not a DRY win.
    Worth a linter rule; until then, any table edit should ship with the per-row reachability transcript.

84. **Deliberately WEAKENING a check is a distinct change class from fixing one, and it needs three artifacts a fix does not: a recorded justification, a negative-control set proving the weakening is BOUNDED, and a written coverage-hole statement.** When an operator decides a signal is unreliable and must stop gating (worked example: the validation suite `<check-id>`/`<check-id>` p99 demoted to `WARN`, 2026-07-28, catalog `<catalog-hash> → <catalog-hash>`), the risk is not that the change is wrong — it is that (a) a later reader "restores" it thinking it was a bug, and (b) it silently over-applies to sibling legs.
    - **Write the decision INTO the check, adjacent to the demoted branch, labelled as a decision** ("p99 is non-gating by operator decision — a deliberate coverage trade, not a defect fix. Do not restore it"), with the evidence that motivated it. If the check has a formal explicit-WARN mandate (a specification requirement), keep the *new* condition **textually separate** from the pre-existing statistical-insufficiency one — otherwise the next reader mistakes the trade for a low-sample artefact and "fixes" it by widening a window.
    - **The negative controls are the deliverable.** Replay recorded payloads through OLD and NEW rules and show (i) OLD reproduces every recorded status — a replay that cannot reproduce the past proves nothing about the present; (ii) each *retained* FAIL path still fires (here: common-mode p50 ×2.0 and ×1.6 → FAIL, aggregate p50 ×100 vs its mixture band → FAIL, the absolute memory ceiling at 90% → FAIL even at the worst parity on the fleet, and every ERROR branch); (iii) an inside-band input still PASSes, so the controls are not vacuous; (iv) the *demoted* path lands on WARN and its numbers survive in `payload`/`evidence`. Item (ii) is what catches over-demotion, and it is the one people skip.
    - **State the coverage hole in the artifact an operator reads**, in the form "class X of real regression now escapes as WARN", not "p99 no longer fails". Here: a tail-only regression — a slow path taken by a minority of requests (burst-contended lock/queue, added retry on a subset of routes, cold-path allocation) — with the median flat. The one-line takeaway a reviewer needs: *a green row is now evidence about medians, not about tails.*
    - **Audit the whole catalog for the same predicate shape before stopping**, and separate *comparison*-derived FAILs from *absolute*-threshold FAILs — they are different decisions. The audit found one other p99 FAIL (`<check-id>`), left it alone because its `5 s` ceiling is absolute and deliberately equal to a shipped paging alert, and flagged it for the operator instead of quietly extending the decision. Demoting a check that is pinned to a page silently decouples the gate from the page.

85. **A check whose graded comparison becomes non-gating must LOSE its `PASS` branch and have its TITLE rewritten — otherwise the row keeps its old authority after losing its teeth.** Extends #84 (weakening is a distinct change class needing justification + bounded negative controls + a written coverage hole). Three additions learned when the the validation suite waypoint-latency family was made non-gating (2026-07-29, catalog `<catalog-hash> → <catalog-hash>`, `<check-id>`/`<check-id>` fully, `<check-id>` p99): **Worked instance and the evidence behind it: `learnings-istio.md`.**
    - **No `PASS` branch.** If no comparison can grade, `PASS` asserts a verification that did not happen, and `PASS` is the status readers trust most. Emit `FAIL`/`ERROR` from the retained absolute legs and `INFO` otherwise. `INFO` outranks `PASS`, gets its own aggregator column, never affects a verdict. Accept knowingly that the row then reads `INFO` forever — which is why the retained `FAIL`/`ERROR` paths must stay at *check* level rather than being split into a separate check, so the row can still go red on its own.
    - **Rewrite the `title`.** A title still advertising the demoted subject ("Waypoint p50/p99 latency within budget") is how a green-ish row keeps its authority. Change the title, never the `id` — the id is the baseline-join key and the catalog-count identity.
    - **Give the status a distinguishable SPEC case.** `INFO` now means two different things: *the comparison could not be made* (statistical insufficiency) and *the comparison was made and does not grade* (operator decision). The status column cannot tell them apart, so the spec needs a separate numbered case (a separate case in the specification) and the result's `notes` must name which one produced the row. Without that, the next reader "fixes" a coverage decision by widening a window, or "restores" an insufficiency `INFO` to `FAIL`.
    - **Watch the verdict arithmetic.** Removing the last `WARN` moved both clusters `PASS_WITH_WARNINGS → PASS` with **zero** measurements changed. A demotion that makes the fleet greener must say so at the top of the report, in the gate line, and in the verdict section — otherwise the artifact reads as an improvement.

86. **Build a same-version noise control at a load ratio the check's OWN parity guard would accept, or it proves nothing.** When arguing that a metric is too noisy to gate, the instinct is to pick the two instants that show the biggest same-version swing. If that pair fails the check's load-parity band, the check would have refused to grade it anyway and the control is vacuous. Worked example: the `71.6×` same-version p99 swing offered for the validation suite `<check-id>` sat at a `2.93×` load ratio, outside leg B's `[0.5, 2]`. Re-built at a load-comparable pair (`1.032×`) the argument survives and is much stronger — p99 `2.666×` against its `1.5×` band while p50 stays at `1.180×` inside its `1.25×` band, i.e. the noise breaches on a version change that did not happen. Corollary: apparent counterexamples on the *retained* leg often turn out to be load excursions the parity guard already rejects (here a `~109×` p50 move at a `14.07×` load ratio → `INFO`, never graded), so check the sample counts before concluding the retained leg is also unreliable. **EXTENDED by #91 (SVLM) for the case where no same-version instant inside the baseline window has comparable load.**

87. **A ratio between two series needs BOTH denominators as mandatory payload fields, or it cannot be audited and a population mismatch is invisible.** the validation suite `<check-id>` graded a Beyla-vs-waypoint "agreement ratio" of `19.51` and `25.53` as a confident `WARN` twice. Both were *max per-service Beyla p99 ÷ cluster-**aggregate** waypoint p99* — a population mismatch — and the numerator's service had **zero** waypoint observations at both anchors. Neither defect is visible in the ratio; both are obvious the moment the two sample counts sit beside it. Two rules follow: record the join key explicitly (a stored `svc` field, not a string operation a reader must trust), and add a **single-digit arming guard** — a quantile over `< 10` samples is written `null`, not as a number, and contributes to nothing. The guard is separate from any grading floor: the floor decides whether a value *grades*, the guard decides whether it is *recorded as a number at all*, and it belongs in the check **whether or not the value can gate** — non-gating output must still not be confidently wrong.

88. **An exemption declared at one STRENGTH does not carry to a stronger state of the same finding — and the tool must say which upgrade is missing, not label the declaration "stale".** the validation suite's allowlist has two lazy tiers: `kind: lazy` justifies a PARTIAL presence set, `kind: lazy` + `absent_everywhere: true` justifies `0/N`. `galley_validation_passed` carried the weaker one, written when it read `3/13`; the istio `1.29.1→1.29.6` fleet roll restarted every istiod, its `NewSum` counters reset, and it fell to `0/13` — where the entry silently stopped applying (`verify-metrics.py` `justify()` early-returns for any non-`PARTIAL` row unless `absent_everywhere` is set), blocking `--final` on `indexed_but_empty_metrics=1` with `justification: null`.
    - **The misdirection was the real defect.** The unmatched entry surfaced only in `stale_allowlist_entries` — which reads "this declaration is no longer needed, delete it" — when the required action was the exact opposite: *strengthen* it. A diagnostic that points at the opposite remedy is worse than none, because it is actionable. Fix shape: keep `classification` untouched (so gating is provably unchanged), but mark the entry matched and emit a named justification (`lazy-absent-under-declared` / `structural-cannot-justify-empty`) whose text names the missing upgrade and the evidence it requires.
    - **The forbidden fix is the obvious one.** The metric returns `3/13` at 24h and `6/13` at 30d against `0/13` at the 6h contract window. Widening the window makes the blocker vanish while destroying the thing the gate measures. Same class as the earlier `pilot_xds_expired_nonce` window blocker: *window-sensitivity is a declaration problem, never a window problem.*
    - **Wider-window presence is EVIDENCE FOR the declaration, not a substitute for it.** The header rule on `absent_everywhere` is "check the name against the vendor source, because absent-because-nothing-fired and absent-because-the-name-is-wrong are indistinguishable from telemetry". Here 24h/30d series plus `__name__` index membership positively corroborate the name, making this the *best*-evidenced entry of its class — say so in the `reason`, and cite the vendor symbol (`monitoring.NewSum("galley_validation_passed", …)`, `reportValidationPass()`) anyway.
    - **A tiered exemption must degrade gracefully in BOTH directions or it rots.** `absent_everywhere: true` is self-limiting here: the moment one cluster takes a config write the row goes `PARTIAL`, `empty_declared` is false, and it falls back to the ordinary `LAZY_DECLARED` path. Check that fallback exists before adding a stronger tier, otherwise the strong claim outlives the condition that justified it.
    - **Negative-control set that makes the "did not weaken it" claim non-vacuous** (all run at the default window, in a sandbox copy so the catalog fingerprint is untouched): fabricated name → `ABSENT`, blocks; a *real* `INDEXED_BUT_EMPTY` name (`kube_pod_status_ready`) referenced from a check → blocks (this also proves the built-in control rows are exempt only because `kind != "metric"`, and lose that exemption the instant a check queries them); `absent_everywhere` removed → re-blocks with the new diagnostic; `armed_by` swapped to a lazy sibling → `lazy-arming-unverified`, blocks — the independent arming requirement still applies *with* `absent_everywhere` set, which is the property that stops the strong tier being a mute button.

## Logs, quantiles and controls

89. **`service_name` in `k8s-monitoring` v4 `podLogsViaLoki` is a 3-STEP FALLBACK, and step 3 silently mislabels operator-generated pods.** `feature-pod-logs-via-loki/templates/_discovery.alloy.tpl` sets `service_name` from the first non-empty of: (1) pod annotation `resource.opentelemetry.io/service.name`, (2) pod label `app.kubernetes.io/name`, (3) `__meta_kubernetes_pod_container_name`. Pods generated by an operator (rather than by a chart) often carry neither (1) nor (2), so **every one of their log lines is filed under the CONTAINER name** — while a sibling component whose upstream chart DOES set `app.kubernetes.io/name` shows up correctly. Scanning `service_name` values then yields the sibling and not the operator-generated component, **which reads as "those logs are not being collected" when they are.** **Before concluding a stream is missing from Loki, probe by pod name / namespace, not by `service_name`.** **Fix for a mislabelled operator-generated pod: supply source (1) on the POD TEMPLATE rather than touching the collector config** — for an operator-managed workload that means its deployment-overlay mechanism (a strategic-merge patch supporting `spec.template.metadata.annotations`). **Note it re-rolls the pods** (pod-template hash changes).

90. **An aggregate quantile is a MIXTURE, so a mix shift alone can manufacture an arbitrary ratio — bound the alibi with the total-variation mix band instead of tuning a threshold**: Let `d` = total-variation distance between the reference and current request-share distributions over the grouping label. TV bounds the CDFs pointwise, so `Q_now(q) ∈ [Q_ref(q−d), Q_ref(q+d)]` exactly, and `mix_band(q) = Q_ref(min(1, q+d)) / Q_ref(q)` is **the largest ratio a pure mix shift can produce** — one extra query, measured from the reference histogram at a SHIFTED quantile level (needs the PromQL `@` modifier, since the level is not 0.5/0.99). Three branches, each with a named status: `ratio > max(tolerance, mix_band)` and the absolute floor met ⇒ FAIL (not mix-explicable — the alibi is BOUNDED by the size of the mix shift); `mix_band < tolerance` and `ratio ≤ tolerance` ⇒ PASS; **`mix_band ≥ tolerance` ⇒ INFO, because a PASS there would be a never-fails PASS.** **The consequence that surprised us: once `d ≥ 1−q` the shifted level clamps to 1.0 and `mix_band` becomes `max/quantile`, so an AGGREGATE p99 comparison is VACUOUS on any real cluster** — at `d = 0.0357` the p99 mix band is 695.9× while the p50 band is 1.032×. So p50 survives aggregation and **p99 teeth must move to load-matched STRATA**: grade the MEDIAN ratio across strata (a shared proxy moves every stratum; a single app regression cannot move the median) and record single-stratum breaches as ungraded outliers. Sensitivity is unchanged — only the denominator is fixed. Absolute legs (memory ceilings) stay parity-independent and FAIL at any `d`. Worked concretely in `learnings-istio.md`.

91. **When the baseline anchor's load is outside the parity band, do NOT re-baseline and do NOT give up — select a SAME-VERSION LOAD-MATCHED reference (SVLM) from inside the pre-change period**: Scan a fixed grid of instants, keep those whose whole comparison window lies BEFORE the first component flipped to the new version, require `load_ratio ∈ [0.5, 2]`, and take `argmin |ln(rps(t)/rps_now)|`. That is a second measurement of the OLD version, so it holds version AND load constant at once — which the original anchor structurally cannot. **It is not a new baseline**: the recorded artifact is untouched, the join still keys on it, and the SVLM is measured live at grading time via the `@` modifier. Anti-cherry-pick discipline: the rule must be deterministic and the grid, bounds, eligible count and winner all go into the recorded output. **The version fence is PER COMPONENT and the components move HOURS apart — use the EARLIEST** (on one cluster the waypoint proxy flipped at 16:30–16:45Z via an istiod Gateway re-reconcile while ztunnel flipped 17:10–17:40Z). Known residual: an SVLM winner can sit ~24h away, so if the check's diurnal-skew branch is wired only into one leg, the other leg carries unbounded diurnal skew with no branch naming it — wire the skew guard into every leg that consumes the reference. Extends #86.

92. **A MULTIPLICATIVE delta band against a baseline MEASURED as exactly 0.0 fires on any nonzero value forever — condition the multiplicative row on `baseline > 0` and let an ABSOLUTE band govern the zero case**: Shipped live: all 6 waypoint clusters recorded `ratio_5xx = 0.0`, so `2 × 0 = 0` made every first 5xx a permanent WARN; and a `ratio ≤ baseline*1.5 AND ≤ baseline+0.005` rule became a zero-tolerance band whose additive floor was the only leg with any power (1 5xx in 71,076 requests vs a baseline of 0.0 over 1,219 requests, which cannot resolve 1.4e-5 — expected count 0.017). **Grade the additive floor only when the baseline ratio is exactly 0.0.** Note the disjunctive form (`ratio ≤ baseline*1.5` **OR** `ratio ≤ baseline+0.005`, FAIL only if BOTH are exceeded) is what makes this survivable, and it is orthogonal to the sample-sufficiency leg — a listener that went from 5,000 req/h to 4 is itself a finding even though its ratio is uncomputable. Check this shape anywhere a ratio or rate baseline can legitimately be zero.

93. **Statistical insufficiency is INFO, not WARN — the WARN/INFO line is EVALUABILITY, not severity**: WARN asserts a signal WAS observed and is outside nominal; INFO asserts there was NO signal to observe. A quantile over too few samples, a missing anchor, a soak window shorter than the trend needs — none of these are soft failures, and grading them WARN drags every quiet run to a warned verdict and trains readers to ignore the column. Three constraints keep it honest: the sufficiency floor must be stated as a NUMBER + WINDOW in the check itself (so nobody can talk their way into INFO), **window-widening must be attempted FIRST**, and sibling legs that ARE evaluable still grade normally. **The criterion that separates the classes:** it is a non-measurement iff no value was computed and compared to a stated bound — a measured-but-benign or measured-but-**pre-existing** result stays WARN. Two second-order effects worth expecting: re-predicating sub-legs to INFO can flip a check to PASS rather than INFO if the shipped aggregation is "INFO legs do not participate" and the remaining legs graded cleanly; and a rule like "a check all of whose LEGS are INFO emits WARN" is UNREACHABLE if any leg is parity-independent and always grades — re-key it on the comparison legs only (same reachability class as #83).

94. **A cumulative counter is safe as EVIDENCE and unsafe as a GATE — and the audit for the class is cheap if you scope it to GRADED sections only**: `restartCount == 0` / `lastState.terminated.reason` with no observation window gets redder with cluster age and fires on history: a 20-DAY-OLD OOMKill and a 46-day-old exit-255 each produced a blocking FAIL on healthy clusters. Replace with an in-window leg (`.state.terminated.finishedAt` inside the window, plus an exact PromQL delta `max_over_time(X[W]) − min_over_time(X[W])`) and demote the cumulative value to context. **Prove the replacement is a real negative control, not a weakened check**: the SAME expression on the SAME pod read 0 at `[1h]` and 1 at `[30d]` — one expression, only the window moved. **Audit method (94 checks → 3 hits, 1 real):** parse each check's front-matter, extract ONLY the graded sections (`Expected` / `Delta rule` / per-phase status), then regex for cumulative predicates and for long windows lacking a shorter corroborating leg. A cumulative value named in a *Command* or *Gotchas* section is fine — it is only a defect inside a GRADED section. See also #79 (count pre-existing vs new by owner-prefix) and #18.

95. **Exact-count equality between two INDEPENDENTLY-SAMPLED populations is unfixable by widening the tolerance — it needs a two-dimensional set difference, and cross-boundary residuals need a SUSTAINED form**: The residual is BIDIRECTIONAL, so no one-sided band rescues it: on a busy cluster `count(up{job=…}) − numberReady` ranged **+52 to −6** over 6h while the mesh never degraded. Three shapes that DO work: (a) **`uncovered = eligible − covered − settling`**, where a node-age settle window ALONE is insufficient — it fixes scale-UP, but a rolling restart happens on nodes that are DAYS old (node settled, only the POD is mid-restart), so a SECOND settling-**pod** dimension is required (pod exists, not Ready, container (re)started within the settle window). Anchor pod age on `.status.containerStatuses[].state.running.startedAt` (which MOVES on restart), never `pod.creationTimestamp`. (b) **Sustained rather than instantaneous**: `max_over_time(observed[10m]) ≥ min_over_time(expected[10m]) − TOL` turned 46 false FAILs into 0 over 4,323 samples **even at TOL=0**, with a tighter detection floor than the band it replaced; an ENVELOPE form (min/max of expected ±2) still produced 16 false FAILs. (c) **Compare SETS, never counts, across an API/scrape boundary** — e.g. `{pods Ready longer than SCRAPE_SETTLE} − {pods carrying a series}`. **Calibrate, don't guess**: measured DaemonSet-pod-Ready-after-node-join was p50 37s / p95 77s / p99 199s / max 204s over 286 samples ⇒ a 300s settle is ~1.5× max (exclude pods with `restartCount>0` or a late readiness flap when measuring, or two multi-day outliers destroy the percentiles). **Negative-control trap that produced a false-green control: the victim removed from the covered set MUST be drawn from the ELIGIBLE set** — pick an arbitrary covered node and you may select one the tolerance legitimately excludes, so removing it changes nothing and the control passes while proving the predicate has stopped grading. **Method that found the missing dimension: an offline churn SIMULATOR over real cluster snapshots** (inject scale-up, mid-roll restarts, drain, stale targets, plus genuine holes including one hidden inside the churn storm and a boundary probe), evaluating OLD vs NEW predicates on identical inputs. Inspection did not find it, and the clusters were quiet exactly when the evidence was needed — a quiet cluster proves nothing about a roll. Extends #81. Additional calibration detail: the 286 first-pod samples covered 3 clusters; two readiness flaps WEEKS after node join would have inflated the settle window to 1.8 M s. Scrape settle = scrape interval + staleness (120 s for a 60 s interval). For `pilot_xds`, churn swung +46/−27: an envelope gave 16 false FAILs, while the sustained form gave 0 across 4323 samples with a TIGHTER detection floor.

96. **A grading row whose subject is a COLLECTION is ambiguous between an existential and a universal reading, and the per-tuple reading is systematically LESS severe — this is a FALSE-PASS class, strictly worse than the false-FAIL class that dominates most audits** (the dual of #83): A first-match-wins row reading *"Tuple present at [7d] but absent at [1d] and [5m] ⇒ INFO"* matches, on a MIXED input (one live sustained tuple + one stale artifact), under the per-tuple reading — grading the WHOLE ROW INFO and masking a live plaintext path into a STRICT namespace. Exhaustive enumeration of 2,304 co-sampled inputs: the two readings diverge on **540**, and on **all 540** the per-tuple reading is strictly less severe. **Fix without a payload-contract change:** define the partitions in a binding preamble derived from arrays the payload already carries (`live = A ∪ B`, `artifact = C − A − B`), state that classification is PER-TUPLE for diagnosis while the ROW STATUS is the MOST SEVERE tuple class, re-predicate the benign row with an explicit `AND live is empty` conjunct so a mixed set cannot match it, and still record every member with its per-tuple class. **General rule, worth a linter alongside the reachability one: for any row whose subject is a collection, the text must state whether the predicate is existential or universal, and the table must state a status-aggregation rule — reachability analysis does NOT catch this class** (every row was reachable both before and after). **Proof method that generalises:** transcribe the table THREE times (per-tuple, set-level, amended) plus a FOURTH independent implementation of the prose aggregation rule, exhaustively enumerate the input space, and assert amended == prose while counting divergence on the original text.

97. **A fleet census loop of the form `kubectl … | wc -l` reports `0` for every cluster whose credentials expired — test the EXIT STATUS, never the emptiness of the output** (same family as #24): The error goes to stderr, stdout is empty, and `0` is indistinguishable from "genuinely none". Hit live while building a check: an expired AWS SSO session made all six EKS clusters report zero at-risk workloads — **including the exact cluster whose incident motivated the check, which would have been recorded as IMMUNE.** Fix: `|| exit 9` on every per-cluster read; a failed read is ERROR, never SKIP and never PASS. Corollary: such a census moves week to week (one cluster went 79 → 85 in a day), so never hardcode the result.

## Alert replay and exporter dimensions

98. **An L4 connection-failure alert firing on a `waypoint → <backend>` pair is a KNOWN-BENIGN accounting artifact — exclude `source_workload != "waypoint"` from its L4 selectors.** The istio-native waypoint Envoy recycles reset-terminated HTTP/1.1 upstream connections under long-poll / durable-execution traffic; the destination-side ztunnel buckets those RSTs into `istio_tcp_connections_failed_total`, producing a **CHRONIC 20–74% L4 failure ratio persisting for days at `connection_security_policy="mutual_tls"` with NO `response_flags`.** **L7 through the same waypoint is 100% `response_code=200` with zero 5xx and the backend pods are Running with zero restarts — there is no user impact.** The alert flaps only because it fires when the traffic floor is briefly crossed on top of the chronic ratio. **Rely on the L7 error-rate rule for real waypoint user impact.** **General rule, and the one that matters: every selector on a connection-failure counter needs its structural-noise exclusions ENUMERATED, not just the one that was noisy first** — same family as #69/#71, and see #118 for the rolling-deploy class that a waypoint exclusion does NOT cover.

99. **A "constant-load" control pinned to ONE destination is not a control — the destination is itself a MIXTURE over its callers; key control strata on `(source, destination, response_code)`**: A destination that looked stable (0.2000 → 0.23475 rps, +17%; p50 7.5178 → 7.5743 ms) had simultaneously gained two new callers and seen its share of cluster traffic fall from 56.6% to 0.8% — so the "unchanged" reading was a coincidence of offsetting mix, not evidence about the proxy. The **source-matched** form does hold: the same pair with the source pinned read EXACTLY 0.2000 rps at both anchors with p50 7.5178 → 7.5394 ms. Verify the label survives your metric-relabeling pipeline before designing around it (one waypoint PodMonitor's relabelings dropped `response_flags`, `source_version`, `destination_version` and `locality`, but keep source/destination/`response_code`). **Two adjacent arguments that were refuted in the same pass — do not reuse them:** (a) idle proxy CPU/memory does NOT exclude added latency, since a proxy can add milliseconds of queueing at 4% CPU; (b) an "independent lens corroborates it" claim collapses if the two lenses are read over different windows or populations — a `[30m]` per-service max against a `[1h]` cluster aggregate reversed direction entirely once aligned. Sound substitutes for a latency control: upstream-connect latency plus retry/pending/overflow counters, and the offered-load curve plotted against the change instant. Extends #86 and #90.

100. **Tune an alert's `for` OFFLINE against historical data by simulating for-semantics in PromQL — but zero-fill absence or the simulation lies at every gap edge**: `min_over_time((<alert expr> > bool 0)[<for>:1m])` returns 1 exactly where the alert would be FIRING, so you can replay a candidate `for` over a past incident and see whether it would have cried wolf — no cluster change, no waiting. **The trap:** `min_over_time` SKIPS missing points, whereas Prometheus `for` treats series absence as resolved and RESETS the pending timer. On any lazy metric the naive form therefore fires early at the leading edge of a gap and can even report a `for` value as firing when it never would. Measured on `circuit_breaker_opens_total`: the naive sim showed `for: 1h` firing from 15:17Z and `for: 4h` firing at all; after zero-filling, the true answers were 16:18Z and never. **Fix — `or` in a non-lazy companion series scaled to zero**, matching the label set of the aggregation: `((<expr> > bool 0) or (sum by (cluster) (up{job="X"}) * 0))`. Same guard shape as #82(b) but applied to a subquery window rather than a ratio denominator, and it doubles as the absence-safety negative control (a cluster scraping the job but never emitting the metric shows up as a solid 0 instead of vanishing). Method: run the sim at several candidate `for` values, measure the longest *legitimate* burst, and pick a `for` with >=2x headroom — remembering that a counter reset across a pod restart makes any observed burst duration only a LOWER bound. Prefer lengthening `for` over raising the threshold whenever the benign event is *hotter* than the pathology it must be distinguished from. See also #20 for the zero-fill shape, and #41 for a standalone executable replay with baseline extension, evaluation-phase sweep and effective window greater than nominal when sweeping parameters against a FINITE outage rather than querying history in place.

101. **A CloudWatch/exporter alert's `by()` clause must enumerate EVERY label that varies — both the resource dimensions AND the exporter's own pod/instance labels — or the aggregation silently swallows the failure it exists to catch.** Two live defects in `charts/platform-alerts/service-observability/aws.yaml`, same root cause: (a) `AlbNoHealthyHosts` groups `sum by(dimension_LoadBalancer, account_id, environment, cluster)` and **omits `dimension_TargetGroup`**, so it sums across every target group on the ALB — one fully-dead target group beside a healthy sibling never fires. This is a false negative at **any** threshold, including `< 1`; it can remain latent while every ALB has only one target group, so the fix needs `dimension_TargetGroup` added to `by()` **and** `dimension_AvailabilityZone=""` pinned. (b) `NlbNoHealthyHosts` uses `min by(account_id, environment, cluster, dimension_LoadBalancer, dimension_TargetGroup)`, which also collapses across the yace exporter's `pod`/`instance` labels — during an exporter rollout two concurrent yace pods feed one `min()` and a scrape gap on either injects a `0`. Measured: exactly one isolated 5m zero sample in 14d on <cluster-b>, which `for: 15m` absorbs. **General rule: `min`/`sum` over an unintended dimension is the same defect whether the dimension is a cloud resource dimension or a scrape-topology label — enumerate the label set of the raw series, not the labels you think the alert is about.** Same family as #66 and #19.

102. **Attributing an alert to a deploy: use the GitOps controller's `Application.status.history[]`, never `git log` on the default branch.** A busy GitOps repo takes hundreds of commits a day, most of them bots, so a git-log window is unusable. `.status.history[]` carries `deployedAt` + `revision` and is the authoritative deploy signal. **Procedure**: pick the history entry with `deployedAt <= alert start` = `CUR`, the entry before it = `PRV`, then compare `PRV...CUR` — that collapses hundreds of commits to one to three. **Tier caveat**: a cluster that pins `targetRevision` to a release tag is UNAFFECTED by commits on the default branch until the tag bumps; only branch-tracking clusters see them. **Two supporting probes.** (a) **Commit-author classes: `.author.type != Bot` alone is INSUFFICIENT** — a programmatic release/deploy account can be registered as `type=User`, so a human-commit filter must be a case-insensitive NAME regex; and some automated authors touch only preview values and are pure noise for real clusters. (b) **Service → source commit**: a container registry sometimes surfaces the 40-hex git SHA as an extra tag (some images do, some do not), `createTime` is rendered in **LOCAL** tz not UTC, and the `dev` and `release` tags of one version share a digest.

103. **An alert DESCRIPTION must state only what its expression can know — a hardcoded impact claim that is true on some clusters trains responders to discount the page.** `NlbNoHealthyHosts` asserted "On <cluster-k> and <cluster-d> the NLBs front the Envoy Gateway ingress … so this is a customer-facing outage" on **every** firing. It then fired on <cluster-b> (internal ops, OTLP aggregator) and responders distrusted the alert because the description was visibly wrong about their cluster. A description that over-claims costs more than the alert saves. **Rule: interpolate the firing instance's own labels (`{{ $labels.cluster }}`) and push conditional per-cluster impact assessment into the runbook, where it can branch.**

104. **Positive AND negative controls against the live metric store are the default shipping bar for ANY alert rule — not a progressive-delivery specialty.** Alerts and dashboards fail **silently**: a wrong label *value* yields a permanently-empty expression that is indistinguishable from "healthy", and a green `helm lint`/`helm template` proves nothing about whether the rule can ever fire. Before shipping: **POSITIVE** — the expression matches a genuinely bad instance right now; **NEGATIVE** — it stays empty across the healthy population. This is exactly what exposed `ArgoRolloutsRolloutDegraded` querying `rollout_info{phase="Degraded"}`, a phase value the metric never emits, dead in prod for an unknown period — plus the same phantom-phase bug in the Grafana dashboard, which reported 0 healthy of 35.

105. **`grafana-mcp` (mcp-grafana) enforces DNS-rebinding Host/Origin validation on EVERY route including `/healthz` and `/metrics` — the default breaks Kubernetes probes and ALB traffic simultaneously.** `http_security.go` validates on all routes and `--allowed-hosts` defaults to loopback only, so the kubelet's `httpGet` probe (`Host: <podIP>:8000`) **and** the ALB-forwarded `Host` both get 403 → CrashLoopBackOff plus unhealthy target group. **Fix: `--allowed-hosts=*`** (safe behind a trusted ALB proxy) and **leave `--allowed-origins` UNSET** — an empty value rejects any `Origin` header, which preserves browser DNS-rebind protection while letting non-browser MCP clients and the probe through. Three deployment traps in the same chart (`grafana-community/mcp-grafana` v0.18.1): (a) `extraArgs` **overrides** the image CMD (the entrypoint is the bare binary), so it must be a COMPLETE argument list; (b) `disableWrite: true` appends `--disable-write` separately — do not duplicate it in `extraArgs`; (c) the deployment's whole `args` block is gated on `if or (.debug) (.metrics.enabled) (.disabledCategories) (.extraArgs)` and **`disableWrite` is NOT in that gate**, so if `extraArgs` is ever cleared by a later override, `--disable-write` silently disappears with no template error. Also: the server serves streamable-http at **`/mcp`**, not `/` (`--endpoint-path /mcp`, `cmd/mcp-grafana/main.go`) — an Ingress path of `/` (Prefix) is right for ALB routing, but the README must document `/mcp` as the client endpoint.

106. **Three fleet-sweep query mechanics worth not re-deriving.** (a) `rollout_phase` is a **phase-enum gauge** — several phases can read `1` for one rollout — so counting means `count by (phase) (rollout_phase == 1)`, never a bare `count`. (b) **rtk-wrapped `kubectl -o json` mangles control characters inside `managedFields` and breaks client-side `jq`** — use server-side `-o jsonpath` for sweeps instead. (c) **Firing alerts are readable as `ALERTS{alertname=~"…"}` in mimir**, NOT via the Grafana alerting rule API (`alerting_manage_rules` returns null for these — they are Prometheus-recorded rules, not Grafana-managed ones).

107. **Two "looked in the wrong place" traps that both produce FALSE NEGATIVES.** (a) **A chart-glob'd alert file does NOT necessarily become a `PrometheusRule` on the cluster it DESCRIBES.** If an ApplicationSet renders those files on a CENTRAL cluster and ships the rules to a central ruler, then `kubectl get prometheusrule -A` on the described cluster returns nothing — which reads as "the alert never shipped". **Find the rendering CONSUMER first**, then verify on the cluster that actually holds the object and read `.spec.groups[].rules[].alert`. (b) **A config value nested INSIDE a single YAML blob is invisible to a grep of key NAMES** — and it looks especially real when sibling keys at the same level ARE discrete. **Parse the blob; do not grep key names.** And if the config is authored in a different repo (e.g. the Terraform module that installs the controller), grepping your own repo can never answer the question at all (`learnings-k8s-sa.md`).

108. **A runbook's `jq` filter must reproduce the ALERT selector's semantics exactly — PromQL `=~` is fully anchored, `jq test()` is not.** An alert matching `namespace=~"default|<workload-namespace>|service.*"` means *exact* `default`/`<workload-namespace>` plus *prefix* `service`. The faithful jq is `test("^(default|<workload-namespace>)$|^service")`. Writing `test("^(default|<workload-namespace>|service)")` instead prefix-matches `<workload-namespace>-foo` and `default-bar` — the same widening the alert itself avoids. (found in a change's class-B check section)

109. **Two Stackdriver/CloudWatch exporter shapes that make an alert unfireable or flappy, both invisible to `helm lint`.** (a) **Stackdriver gauges scraped every 5m collide with the default 5m PromQL lookback**: one delayed or missed Cloud Monitoring sample empties the rule result and RESETS a pending `for` duration. Reproduction: exporter `up=1` while the gauge is absent; `max_over_time[5m]` is also empty while `last_over_time[10m]` retains the series. **Use a window longer than the scrape cadence — prefer `last_over_time` for gauges — or a rule query offset, and alert on exporter/metric ABSENCE separately.** (b) **A CloudWatch target group with zero registered targets goes ABSENT, it does not report 0** — CloudWatch simply stops publishing, so no threshold rule can ever fire on an emptied or brand-new target group. Related NLB design tension: pinning a healthy-host alert to the target-group aggregate trades a false positive for real loss of **zone-level** signal. AWS withdraws a zone's DNS record once it drops below `dns_failover.minimum_healthy_targets.count` (default 1), but the NLB DNS TTL is 60s so clients caching the withdrawn IP keep failing; and cross-zone LB is OFF by default on NLBs and overridable per target group — check the target group's override before relying on the default. Extends #101.

110. **A ratio-based saturation alert on a workload DESIGNED to run at its ceiling fires chronically from the moment it merges — and lowering `severity` does not necessarily stop it paging.** An LRU-evicting cache sits at `usage_ratio` 1.0 as STEADY STATE, so a `> 0.9` rule is on essentially every sample. **Check your ROUTING TREE before assuming severity is a mute**: if routing keys on an environment label and severity only sets urgency, a `warning` still reaches the on-call system. **The tension is genuine and a reviewer should SURFACE it, not resolve it**: `allkeys-lru` does NOT protect `EVAL` write-scripts (Redis pre-gates via `pre_command_oom_state`), so an at-1.0 instance really IS vulnerable and the firing may be correct early warning rather than noise — fire-on-all vs allowlist is an owner decision. **Two implementation notes**: an eviction-rate gate is UNDEPENDABLE where the exporter's `evicted_keys` series is gappy or absent; and if an allowlist is chosen, prefer an **owner-curated LABEL** over a hardcoded instance-id regex. Clean example of an adversarial lens catching what a correctness lens missed.

111. **yace publishes CloudWatch ELB metric families at TWO granularities SIMULTANEOUSLY, and the aggregate series carries `dimension_AvailabilityZone=""` — empty means ALL zones, not "no zone".** Mechanism, verified in source at v0.62.1: `pkg/promutil/migrate.go` `BuildLabels` unions the metric family's labels and `EnsureLabelConsistencyAndRemoveDuplicates` fills any label a given descriptor lacks with `""`. So an `AWS/NetworkELB` aggregate descriptor carrying only `LoadBalancer` + `TargetGroup` acquires `dimension_AvailabilityZone=""` because the per-AZ descriptors expose `AvailabilityZone`; the label name is always `dimension_` + the AWS dimension name. **Any `min()`/`sum()`/`avg()` whose `by()` omits `dimension_AvailabilityZone` silently mixes both shapes — `min()` returns the WORST AZ (false page on a single drained zone) and `sum()` DOUBLE-COUNTS.** Fix: pin `dimension_AvailabilityZone=""` in the selector to read the target-group total. **Example configuration cause**: the `AWS/NetworkELB` + `AWS/ApplicationELB` discovery jobs in `charts/otel/templates/_helpers.tpl` set no `dimensionNameRequirements`, so every dimension combination is kept. **General rule for any CloudWatch-exporter metric: before writing an aggregation, enumerate the dimension labels the exporter actually emits and confirm none of them carries a ROLLUP series your `by()` will fold in.** **And a zero-threshold backtest CANNOT detect this class of defect** — it passes vacuously whenever the skew condition simply did not occur in the baseline window, so a green backtest is not evidence the expression is correct. Pairs with #101 (the `by()`-completeness half) and #104 (positive/negative controls). Observed on `<cluster-b>` 2026-08-04 20:35–20:55Z: `aws_networkelb_healthy_host_count_minimum` had per-AZ `dimension_AvailabilityZone=us-east-1a/b/c` values 10, 5, 0 and aggregate 15; `NlbNoHealthyHosts` (`charts/platform-alerts/service-observability/aws.yaml:141`) used `min by (account_id, environment, cluster, dimension_LoadBalancer, dimension_TargetGroup)` and paged with value 0 despite 15 healthy targets. `AlbNoHealthyHosts` double-counted with `sum by()` but stayed correct at zero. The pre-ship backtest contained no zero AZ, so it missed the defect. Distinct from #101's omitted RESOURCE dimension: this mixes AGGREGATION LEVELS of the same metric.
    - Upstream cause of the zero AZ: `<cluster-b>`'s `otel-aggregator-collector` (HPA min 8 / max 40) has **NO `topologySpreadConstraints` and NO affinity**, so HPA churn plus Karpenter consolidation let a whole AZ reach zero registered targets (4× 1a, 2× 1b, 1× 1c at sample). Real impact nil — NLB cross-zone is DISABLED but AWS withdraws the zonal DNS record for an AZ with no healthy targets, and `otelcol_receiver_accepted_metric_points_total` held 217–253 k/s straight through.

## Incident triage and telemetry coverage

112. **`opened == 0` AND `closed == 0` AND `failed == 0` on an ambient hop is the signature of a CLIENT-SIDE connection-pool deadlock, not a mesh or network fault.** <cluster-a> `<gateway-service>` → `<auth-service>` served 100% 5xx for ~3h12m (~6134 requests, all 9 replicas) with every call hitting a hard ~10.0s client timeout (`responseTime` 10004-10012 ms). `istio_tcp_connections_opened_total` AND `_closed_total` for that source/destination pair were **EXACTLY 0** for the whole window (normal 0.013-0.035/s either side) while `istio_tcp_connections_failed_total` stayed **0** throughout. **No opens, no closes, no failures = the pool neither cycled nor errored — pooled connections were checked out and never returned, so every request queued and expired WITHOUT EVER HITTING THE NETWORK.** That is why the destination looked perfectly healthy (flat p99 0.40-0.45s, all 200s, request rate unchanged, all 12 pods serving) and why nothing else was affected; it self-healed with NO restart when the wedged connections aged out. **A genuine mesh fault shows `failed > 0`, or at minimum ATTEMPTED opens.** **Tooling notes, as measured on <cluster-a> at the time of the incident**: `istio_requests_total` did NOT exist there (no waypoint on this path ⇒ no L7 mesh metrics), so mesh-telemetry queries returned vacuous empties. **Re-check whether an L7 lens exists on the path; enrollment can change.** The L4 conclusion above is unaffected: it rests on ztunnel metrics, which arm either way — the decisive signals were the ztunnel L4 metrics `istio_tcp_connections_{opened,closed,failed}_total` and `istio_tcp_sockets_open`; and **ztunnel access logs only emit on connection CLOSE** (durations 121-318s on keep-alives), so their ABSENCE over a short window is NOT evidence of no traffic — always negative-control against a healthy window. The hop itself is in-cluster, not a hairpin (`learnings-istio.md`).

113. **A `> 0.5 rps` volume guard on a ratio alert SUPPRESSES exactly the outage it should catch on a low-traffic but user-critical path.** `charts/<gateway-service>/service-observability/<gateway-service>.yaml:88-89` gates the error-ratio on `and … sum(rate(mcp_gateway_request_total[10m])) > 0.5`; the affected path runs at ~0.5 rps, so during a 100%-error outage the gate FLAPPED in and out for over two hours and only sustained the `for: 5m` window once — **the alert under-detected a total outage by 2h20m.** Volume guards exist to stop ratio noise at low counts, but on a path that is *inherently* low-traffic they invert into a suppressor. **Either scale the guard to the path's own baseline, or pair the ratio rule with an absolute-error-count rule that has no volume gate.** **Coverage refinement: an absolute-count rule covers the LOW-volume case, but only an AVAILABILITY rule covers the ZERO case — no pods ⇒ no requests ⇒ empty denominator ⇒ permanent silence, which no count-based rule can see. Whenever you add a volume guard to a ratio alert, name BOTH companions.** Same class as #104: an alert that cannot fire is indistinguishable from healthy. Example observed on 2026-08-19 (`charts/istio-base/service-observability/istio-ambient.yaml`): the waypoint alert family is `WaypointUnavailable{NonProd,Prod}` (`max by (cluster,environment,namespace)(kube_deployment_status_replicas_available{deployment="waypoint"}) == 0`, `for: 10m`, Prod severity critical, runbook `WaypointUnavailable.md`), `WaypointHighL7ErrorRate{NonProd,Prod}` and `ZtunnelHighConnectionFailureRate{NonProd,Prod}`. **The coverage limit worth stating in any waypoint runbook: `WaypointHighL7ErrorRateProd`'s `>0.5 rps` traffic guard makes LOW-VOLUME PAIRS INVISIBLE regardless of their 5xx ratio** — <cluster-k>'s only 5xx pair runs at 0.00056 rps = **0.11% of the guard.** That is correct design (it stops a 1-in-2 error on a 2-req/hour pair paging) but a real hole. **`WaypointUnavailable` is what covers the case a 5xx-RATIO rule is structurally incapable of catching: no pods → no requests → empty denominator → permanent silence.** Generalise: **whenever you add a volume guard to a ratio alert, name the availability rule that covers the empty-denominator case — an absolute-count rule covers low volume, but only an availability rule covers zero.** (Proving such a `== 0` rule is fireable: #150.)

114. **A memory REQUEST with no memory LIMIT gives you the worst of both — and the stock "increase the memory limit" alert hint is then actively wrong.** <cluster-a> `<gateway-service>` had `request = 10GB` (vs a 450MB baseline — massively over-provisioned) and **NO limit at all** (`kube_pod_container_resource_limits` empty for that container while 140 mem-limit series existed in the same namespace). One replica ramped 450MB → 643MB → 849MB → 1.01GB → **16.5GB** over ~20 min and was kernel-OOM-killed under node pressure; nothing capped the growth because there was no cgroup ceiling. **Correct fixes, in order: (1) SET a limit so the cgroup kills a runaway pod early instead of the node killing an arbitrary victim; (2) find the request that drove the allocation and add per-operation guards; (3) right-size the inflated request down.** Distinguish this from the *noisy-neighbor* variant of the same alert — an earlier `<gateway-service>` OOM was caused by `<batch-service>` packing nodes (188 Pending pods, 28/23/21/20 pods per node) where `<gateway-service>` was already 1-per-node with **no** `topologySpreadConstraints` or anti-affinity; **a rollout restart does NOT fix noisy-neighbor OOM** — it is a coin flip that reshuffled fresh pods straight onto the densest nodes. The discriminator is whether the victim's OWN working-set ramped (config defect) or stayed flat while the node filled (scheduling defect). **Logging gap worth closing either way**: `<gateway-service>` ships NO logs to <cluster-a> Loki (0 streams), so the triggering request could not be traced.

115. **An OOMKill can be entirely INVISIBLE at normal dashboard resolution — check the step before concluding memory was fine.** <cluster-b> tempo `metrics-generator` was OOMKilled at its 4Gi limit with both replicas dying in the same second, yet over 24h at **15m step** working-set never exceeded **27%** of the limit. At **30s step** the spike is obvious: 585MB → 3.9GB (91% of limit) in a single sample. **Consequence: any "sustained above 90% for 30m" memory alert structurally CANNOT catch this failure mode** (and the existing `TempoIngesterMemoryNearLimit` does not cover metrics-generator at all). **Driver**: the `local-blocks` processor with `filter_server_spans: false` retains ALL spans in memory (~800MB/replica steady state, `tempo_metrics_generator_processor_local_blocks_bytes`) with `complete_block_timeout` defaulting to 1h; transient allocation on top hits the ceiling. **Memory had ALREADY been doubled** (1Gi/2Gi → 2Gi/4Gi seven days earlier) for this exact symptom and the doubling did not resolve it. **Do not chase cardinality**: `registry_active_series = 0` because only `local-blocks` is enabled, so this memory is block-buffer driven, not series driven.

116. **A brand-new telemetry pipeline can be observable ONLY through its agent's own error logs — verify metric coverage with an explicit empty-`count()` negative control before designing an alert.** The Panther SIEM forwarder (otel `0.124.0+v0.0.3`, <cluster-a> + <cluster-k>) fails with `HTTP Status Code 502` from the Panther gateway; the retry backs up and degenerates to `sending queue is full`. On <cluster-a> that is fleet-wide and hot — ≥25 `otel-alloy-logs` DaemonSet pods each emitting 1,600-22,000 error lines per 2 min, ~95k lines/min of Alloy's OWN error output, sampled ratio 7,326 queue-full : 138 × 502. **`otelcol_exporter_send_failed_log_records_total` and `otelcol_exporter_queue_size` do NOT exist in mimir for either cluster** (verified by an empty `count()`), so there is no metric to alert on. **Two method points that made the diagnosis solid**: the Infisical prerequisite was *proven satisfied* rather than assumed (InfisicalSecret Ready, managed Secret `DATA=1`, and no 401/403 anywhere — a missing token would show auth errors, not 502s); and **<cluster-k> is the negative control** — same component (12 identical `<log-exporter>` refs in the ConfigMap on both) but only 53-76 lines/3min on 2 of 8 sampled pods, which localises the cause to <cluster-a>'s traffic volume rather than a config difference. Fixes to consider: `sending_queue` sizing / `num_consumers`, and scraping the `otelcol_exporter_*` metrics at all.

117. **A selector-splice helper that returns a LEADING-COMMA string makes `metric{ {{ .selector }} }` render INVALID PromQL the moment the selector is non-empty** — `metric{ , cluster="x" }`. The bug is LATENT while the default selector is empty, so it ships and passes every gate. **Rules with a real matcher BEFORE the splice are immune** — `metric{environment!=""{{ .selector }} }` — **and that is the shape to standardise on.** Because such alert-values files typically have no `Chart.yaml` of their own, **validate them through the CONSUMER chart**, and remember there is usually no PromQL parser in CI at all (#149).

118. **`ZtunnelHighConnectionFailureRateProd` on an `envoy-gateway → <svc>` pair during a bundle deploy is a BENIGN rolling-deploy accounting artifact.** A bundle roll replaced all 12 `<auth-service>` pods plus <service-b>/<service-c>/<service-d>/<service-e>/<service-f>/<service-g> simultaneously; in-flight `envoy-gateway → <auth-service>` TCP connections were RST at pod termination, and the destination-side ztunnel buckets those into `istio_tcp_connections_failed_total` — L4 failure ratio 0 → 29.3% for exactly six minutes, back to 0 immediately after. Corroborating: opened rate spiked 1.9 → 5.1 conn/s (pool re-establishment), and the same signature hit every destination that rolled (<service-b> 91, <backend-service> 20, <service-c> 10, <service-d> 8). **Discriminators from a real fault**: the SOURCE workload had 0 restarts (since June), the **ztunnel DaemonSet had 0 restarts** (so it is not a ztunnel roll), and the destination ReplicaSet's `creationTimestamp` lines up to the minute. **This is the same accounting-artifact class the runbook already documents for `source_workload=waypoint` (#98), but the alert expression does NOT exclude `envoy-gateway`** — `charts/istio-base/runbooks/ZtunnelHighConnectionFailureRate.md` says so verbatim.

119. **A chronic node ephemeral-storage shortage evicts the WRONG pods — and the reason is a kubelet ranking rule most people do not know.** Preview/PR-churn lanes pull fresh images continuously, and a node's image cache alone can be a quarter of its allocatable disk; **long-lived nodes accumulate layers faster than kubelet image GC reclaims them**, so evictions concentrate on the OLDEST nodes rather than the busiest. **The perverse part: a workload that sets NO `ephemeral-storage` request is ranked by kubelet as a FIRST eviction candidate** ("request is 0, has larger consumption of ephemeral-storage") — **so ordinary services get evicted before the preview pods that caused the pressure.** Two structural fixes, both worth doing: **node recycling / a max-age on churn-heavy node groups**, and an **`ephemeral-storage` request on preview workloads.** **And check whether you have a fleet node-disk alert at all** — without one this surfaces only as per-service pod-evicted noise, which is a coverage gap, not a known-and-accepted risk.

120. **Ruling a shared network component OUT requires a NEGATIVE CONTROL on the SAME query — otherwise "zero drops" is indistinguishable from a dead query.** A component was correctly excluded from an outage only because the identical query over a WIDER span DOES return drops, which proves the empty incident window is genuine rather than a broken selector, a wrong resource name, or disabled logging. **This is the cheapest control in incident work and the most often skipped**, because an empty result during an incident feels like an answer. **Corollary worth acting on: while you are there, check the component's LOGGING POSTURE** — a peer resource with logging disabled cannot be ruled in or out at all, and you will only discover that during the next incident.

121. **With `labelSelectors` and `labelExpressions` both empty, Alloy discovers `PodMonitor`s with NO label selector and across ALL namespaces — a new PodMonitor needs no discovery label, it only needs to EXIST.** In `k8s-monitoring` v4.1.2, `feature-prometheus-operator-objects` emits a `selector {}` block **only** `if or labelSelectors labelExpressions`; with both empty the rendered `prometheus.operator.podmonitors` block carries only `clustering` + `scrape` + `forward_to`. **The commonly-copied "you must match the `podMonitorSelector` label" assumption is FALSE for that configuration** — it comes from prometheus-operator, not from this agent. **Verify against the RENDERED agent ConfigMap on a live cluster, not against the chart's values**, before adding a discovery label that does nothing (or omitting one that does).

## Dashboard ownership and query identity

122. **Before editing a dashboard, establish whether it is OPERATOR-PROVISIONED or a checked-in artifact maintained in the UI — read the provisioning chart's GLOB, not the directory name.** A dashboards chart commonly globs ONE hardcoded folder, and that folder is the only auto-provisioned category; everything else in a `dashboards/` directory is a hand-maintained EXPORT. **The cheapest proof is commit history**: if the commit that added a dashboard touched only the artifacts directory and a README, it was never provisioned. **Convention for a new checked-in dashboard**: strip `id` and `version`, **KEEP `uid`**, make the datasource a TEMPLATE VARIABLE, pretty-print, and add a row to the directory's README. Merging an export changes NOTHING in Grafana, and live can drift BELOW git. Someone can fix the FILE and never re-import it, so the repo carries a correction that production has never seen — the exact inverse of the drift people expect. **WORKFLOW: push to Grafana FIRST, review the RENDERED result, then commit — and ALWAYS diff live vs git before pushing, so a hand-edit made in the UI is not silently clobbered by an older file.** **MECHANISM (gcx):** `gcx resources pull dashboards/<uid> -p ./dir` gives a byte-exact backup AND the `v0alpha1` manifest shape; swap `.spec` for the new dashboard JSON (**drop `spec.uid` — the uid lives in `metadata.name`**), set `metadata.annotations['grafana.app/message']`, then `gcx resources push dashboards/<uid> -p ./dir`. **The `import-dashboards` skill is the WRONG direction** — it pulls Grafana into Go builder code.

123. **PROMETHEUS JOB-LABEL COLLISIONS silently merge unrelated components — and the damage is worst in the check you trust most.** `istio_build` resolves under `job=istiod`, `job=ztunnel` AND `job=<ns>/waypoint-waypoint` on all 13 clusters; queried WITHOUT `job=`, `count by (tag)` on `<cluster-c>` returned ONE series covering 102 — three mesh components merged into a single vacuous PASS. **RULE: before trusting any PromQL check, run `count by (__name__, job)` FLEET-WIDE for every metric it uses; qualify by `job` unless another label is a proven 1:1 discriminator, and store the resolved job set in the artifact so a later diff detects the job set itself changing.** Other real collisions from the same sweep: `istio_tcp_*` collides with the waypoint job (`reporter=` is a 1:1 discriminator and must NOT be dropped as redundant); an `unless` leg where waypoint series in the RIGHT operand silently SUPPRESS a real STRICT mTLS rejection; and `controller_sync_errors_total`, which is **CROSS-CLUSTER ambiguous** (`job=istio-cni` on one cluster, `job=istiod` on another) — a class a per-cluster verifier structurally cannot see.
    - **(a) A MERGED QUERY CAN BE STRUCTURALLY INCAPABLE OF EXPRESSING THE CHECK, not merely inaccurate.** An istio version-skew gate used unqualified `count by (tag)(istio_build)`. Simulated on live series, the EXPECTED state (control plane at TARGET, data plane at PREV — correct by design) and the INCIDENT it exists to catch (data plane AHEAD of control plane) **BOTH return 2 series** — an identical shape. Qualified per component (`job=istiod,component=pilot` / `job=ztunnel,component=ztunnel`) it correctly PASSes the first and FAILs the second. **Test every gate against BOTH the state it should allow and the state it must catch; if the outputs have the same shape, the query is wrong regardless of what it currently reports.**
    - **(b) ASYMMETRIC collision is the dangerous variant.** `istio_tcp_connections_opened_total` is emitted by ztunnel AND the waypoint job, while `..._failed_total` is ztunnel-only — so a failure RATIO put waypoint connections in a DENOMINATOR they can never reach the numerator of, understating it ~2%. A SYMMETRIC collision inflates or deflates both sides and often cancels; an ASYMMETRIC one silently biases the result in one direction and gets baked into the baseline. **When qualifying a ratio, verify BOTH operands have the same job/label footprint.** Caveat on picking a discriminator: do not pin a single reporter value without checking per cluster — the dominant reporter flipped between clusters (59× source-dominant on one, 83× destination-dominant on another), and pinning would have dropped ~98% of signal on one.

124. **AN ARMING PROOF CAN BE ARMED BY THE MONITORING SYSTEM ITSELF — self-referential liveness is not liveness.** A 5xx-rate check on Envoy carried a "13/13 armed" anti-vacuity proof, so it looked rigorous. The traffic arming it was **Prometheus scraping the admin listener**: on a production cluster every USER-facing listener read 0 rps at `[5m]` while the admin listener read ~1.05 rps × 3 jobs — so the check reported "0 % 5xx, PASS" for a front door carrying NO REAL REQUESTS. **RULE: an arming proof must be armed by the SAME traffic class the check grades.** Exclude scrape/admin/health listeners and self-monitoring paths from any denominator used to prove liveness, and verify the arming series and the graded series share a dimension (listener, route, reporter). **If widening the window fixes a zero, the window was wrong; if excluding the admin listener zeroes it, the check was never testing anything.** Related magnitude data from the same sweep: an unqualified Envoy latency query on `<cluster-a>` returned p99 4570 ms because it merged one proxy fleet at 4727 ms with another at 49.8 ms — grouping by listener NAME did not disambiguate (both fleets reuse listener names); only `job=` did.

## Alert detection and incident attribution

125. **`PodNotHealthy` LATCHES FOREVER on evicted-pod tombstones.** The base profile matches `phase=~'Pending|Unknown|Failed'`, and **Kubernetes never garbage-collects Failed pod objects until `--terminated-pod-gc-threshold` is crossed (EKS default 12500)** — so a single eviction leaves a `phase=Failed` series alerting indefinitely while the Deployment is perfectly healthy. Verified on `<cluster-e>` 2026-08-04: 85 Failed/Evicted pod objects cluster-wide, `<gateway-service>` alerting continuously since 08-03T21:32Z, yet `min_over_time(svc_observability:kube_deployment_status_replicas_available:labeled{deployment='<gateway-service>'}[26h]) == 3` — zero replicas ever lost. **Triage rule: on any `PodNotHealthy`, FIRST check `.status.reason == 'Evicted'` and the deployment's available replicas; if replicas are whole it is a tombstone, not an incident.** Rule-design fix: exclude pods whose `status.reason` is `Evicted` (`PodEvicted` already covers that class), or add a liveness qualifier / age bound.

126. **Mimir's `ruler.evaluation_interval` of 5 m EQUALS PromQL's default `lookback-delta` of 5 m, so every alert reading a recording rule sits exactly on the staleness boundary and FLAPS.** (`charts/mimir/values.yaml:98`.) Any ruler jitter pushes the sample gap past 5 m, the instant vector goes empty, and the Grafana alert flips FIRING→RESOLVED→FIRING. Proven on `<cluster-e>` 2026-08-04 with a negative control: `count_over_time(kube_pod_status_phase{...}[1h]) = 60` (raw KSM, 60 s scrape) versus `count_over_time(svc_observability:kube_pod_status_phase:labeled{...}[1h]) = 12` (300 s rule interval). Symptom: `PodNotHealthy`/`PodEvicted` for `<gateway-service>` flapped ~29 h with 150+ Slack notifications **on ONE static condition that never changed.** Fix: set an explicit shorter `interval` on the `svc-observability` recording-rule groups, or raise `-querier.lookback-delta` above the rule interval. **Do NOT tune the alert's `for:` — it is not a `for:` problem.**

127. **A percentage-only capacity alert cannot catch a FAST leak — it structurally fires AFTER the outage.** `KubePersistentVolumeFillingUp5Percent` (`charts/platform-alerts/service-observability/k8s-platform.yaml:132`, `avail/capacity < 0.05`, `for: 5m`) leaves 3.15 GiB of headroom on a 64 GiB volume. `<cluster-a>` `restate-3` (2026-07-29) leaked at 1.45 GiB/min ⇒ **2.2 minutes of runway, LESS than the `for: 5m`**. Timeline: threshold crossed ~17:08:49Z, ENOSPC 17:10:09Z, notification 17:16:54Z — the disk was 100 % full and crash-looping **seven minutes before anyone was paged.** The `10Percent` sibling has `for: 1h`, so it can never fire first on a fast leak. Two fixes, both worth doing: (1) a rate-based companion, `predict_linear(kubelet_volume_stats_available_bytes[30m], 4*3600) < 0` with a short `for:`, which would have fired ~20 min earlier; (2) alert on the workload's own crash-loop signal, which is always earlier and cluster-comparable. **GENERALISES: for any stateful workload, a per-node restart/stop-rate OUTLIER beats a capacity-percentage threshold as the leading indicator** — here `sum by(node_name)(rate(restate_partition_stop_total[5m]))` ran 4–6 stops/min on `restate-3` from 16:42Z while all four other nodes sat at exactly 0, a clean outlier available **35 minutes** before the PV alert and while the volume was still only ~55 % full (recoverable without wedging). `charts/restate-cluster/service-observability/restate-cluster.yaml` has 16 rules but none on partition-processor restart rate, despite already using that counter elsewhere.

128. **An alert whose DETECTION LATENCY EXCEEDS THE EVENT DURATION cannot be actioned — and lowering `for:` is the wrong fix.** `ZtunnelHighConnectionFailureRateProd` / `IstioMeshConnectionFailuresProd` use `rate(...[5m])` + `for: 5m`, giving a **structural floor of ~7 min from breach onset to notification.** On `<cluster-a>` 2026-08-06 the true breach ran 15:13–15:19Z (6 min); the alert went pending 15:14, fired 15:19, Slack delivered 15:20:23 — **1.4 min AFTER the condition had already returned to 0** — and stayed firing to 15:23 purely from rate-window decay. Any transient shorter than the floor always notifies post-hoc. **Do NOT lower `for:` (deploy transients would then page constantly).** Correct fixes: (a) exclude/inhibit `source_workload=~'envoy-envoy-gateway-system-.*'` the same way `source_workload!="waypoint"` already is, or (b) inhibit while a destination Deployment is mid-rollout (`kube_deployment_status_replicas_updated < spec_replicas`). **Grading the RULE mattered more than the incident** — the incident was a no-op; the rule will misfire on every bundle deploy.

129. **THE SAME-VERSION CONTROL: before concluding "metric X regressed after the upgrade", re-measure X between TWO PRE-UPGRADE instants on the same cluster with the version held constant.** If X swings as much or more with nothing changed, X is noise and the "regression" is not attributable. This single technique settled two disputes on 2026-07-28 that hours of argument had not: (a) p99 latency on `<cluster-l>` swung **71.6×** same-version, killing a p99-based advisory; (b) at 15:30Z still on istio 1.29.1, comparable load (23.30 rps) produced p50 13.54 ms / p99 1888.96 ms versus the post-upgrade window's 30.71 rps / 13.53 ms / **169.50 ms** — same p50 and FAR WORSE p99 BEFORE the upgrade, which flipped a blocking gate FAIL. **It beats every indirect argument (<constant-service> controls, idle-CPU reasoning, cross-lens comparison) because it holds the variable under test fixed instead of reasoning about confounders.**
    - **A "<constant-service> control" must be SOURCE-MATCHED** — `destination_service_name` alone is itself a mixture over callers and can move 17 % while looking constant.
    - **An aggregate quantile is a MIXTURE**, so a traffic-mix shift of total-variation distance `d` can manufacture a ratio up to `Q_ref(min(1, q+d)) / Q_ref(q)` — and once `d >= 1-q` that clamps to 1.0, making an AGGREGATE p99 comparison **mathematically vacuous** on any real cluster (measured mix-band at q=0.99 = 695.9× on `<cluster-l>`). Tail comparisons must be **per-stratum, graded on the MEDIAN ratio across load-matched strata** — a shared proxy moves every stratum, while one bad app cannot move the median.

130. **Cloud-auth-failure log sweeps have recurring FALSE-POSITIVE classes — classify them out BY HAND, do NOT narrow the regex.** Two shapes recur in any estate: **OS-level permission errors nested inside application debug logs** (an `errno 13` "permission denied" is not a cloud IAM denial), and **the platform's OWN internal RBAC** (a GitOps or admin server's gRPC `PermissionDenied` is application-level authz). **Discriminator: a genuine cloud denial names a cloud SDK or service, or an STS/IAM error type.** **Narrowing the regex is what causes a false all-clear** — one narrowing dropped `Error 403: Permission denied` entirely. Keep the pattern broad and classify the hits.
    - **QUERY TECHNIQUE that beats coarse sampling**: once a candidate container is known, run ONE range query filtered to the container at a coarse step across the WHOLE span — the container filter cuts scan volume enough to avoid byte-limit failures and gives complete hour-by-hour coverage. **A 6-hourly coarse SAMPLE misses sparse onsets** (a real onset was never inside a sampled hour). Very high-volume namespaces need 10–20 min sub-chunks.

131. **Three Loki gotchas that make absent data look like healthy data.** (a) **A log store fed by an OTel pipeline uses OTel-style label names (`k8s_namespace_name`, `k8s_cluster_name`, `k8s_container_name`, `k8s_pod_name`), NOT the Prometheus-style `namespace`/`cluster`/`container`/`pod`** — querying the wrong family returns EMPTY, and empty gets misread as "these logs are not shipped". **Before concluding data is absent, verify the LABEL NAMES exist (`list_loki_label_names` / `list_prometheus_label_names`). Empty result ≠ absent data** — and note the two datasources can legitimately differ on which name is correct (#140). (b) **Not every namespace ships container stdout.** A namespace can be shipping Kubernetes EVENTS only, so a window returns entries with no container stream at all and the workload's panics/OOM context are simply unavailable there — fall back to metrics + events, or `kubectl logs`. (c) **Pick the DISCRIMINATOR from the OLDER schema when comparing across a version boundary.** Filtering on a field the new version added MANUFACTURES a zero for the old side, which reads as "the problem started at the upgrade". Filter on a field BOTH versions emit, and **count ALL matching lines including SUCCESSES** — counting successes+failures is what proves a capability did not exist before, rather than "it started failing".

132. **A public internet-facing MCP server with per-request token pass-through is safe only because of a control OUTSIDE the chart — name the load-bearing control, not the deployment shape.** `grafana-mcp` holds NO credential (`GRAFANA_SERVICE_ACCOUNT_TOKEN=0` in the render) and passes the caller's Grafana token through per request. **The load-bearing control is that central Grafana has NO `[auth.anonymous]` section** — anonymous access is disabled by default in the Grafana CR, so a tokenless request gets 401. Verified from `mcp-grafana` v0.17.1 source: an EMPTY `--allowed-origins` **REJECTS** Origin-bearing requests (browser DNS-rebind protection is kept), `--allowed-hosts=*` only disables the Host check (safe behind an ALB), and `--endpoint-path` defaults to `/mcp`. **If anonymous auth is ever enabled on that Grafana, this endpoint becomes an unauthenticated proxy into it** — the chart's own config would not change.

133. **Managed Redis and in-cluster Valkey metrics are different series families.** A `stackdriver-exporter` with `stackdriver.metrics.prefixes` including `redis.googleapis.com/stats` and a configured `projectIds` list can expose Memorystore server metrics. Use `stackdriver_redis_instance_redis_googleapis_com_stats_memory_usage_ratio` (0..1 used/maxmemory), with `instance_id`, `environment`, `cluster`, `project_id` and `region` labels; companions include `…_memory_maxmemory`, `…_evicted_keys` and `…_system_memory_usage_ratio`. Confirm the scrape cadence (one deployment used 5 m). A separate `redis_exporter` job may describe only in-cluster Valkey; where its `maxmemory=0`, a derived ratio is `+Inf`. Establish the resource and exporter before choosing a memory signal.

134. **`external-dns` with NO `domainFilter` manages EVERY zone its credential can reach — including your apex domain — and its records are UNPROXIED by default.** Two consequences people miss. (1) **Blast radius**: with `policy: sync` and no `domainFilter`, a stray hostname annotation on any Service/Ingress in the cluster can create or delete a record in a zone you did not intend to expose to that cluster. **Set a `domainFilter` unless you genuinely mean fleet-wide zone control.** (2) **With a CDN-fronted provider (e.g. Cloudflare), an `external-dns.alpha.kubernetes.io/hostname` annotation creates a GREY-CLOUD (unproxied) CNAME to the load balancer** — so TLS terminates at YOUR load balancer on YOUR certificate and the CDN does not intercept. Proxying requires an explicit `cloudflare-proxied: "true"` annotation. **Prove which one you have by resolving a managed hostname**: direct load-balancer IPs mean unproxied; CDN edge IPs mean proxied.

135. **Three alert-investigation discipline rules, all learned by getting them wrong on ONE alert (<cluster-k> `EnvoyGatewayExtAuthzErrors`, 2026-08-18 14:10-14:50 UTC).**
    - **(a) Cross-check every `rate()` window/step choice against a SECOND finer-resolution query before asserting a metric "went to zero".** A claimed *"12-min total traffic blackout"* was a pure artifact of `rate[5m]` at `step=120s`: at `rate[2m]`/`step=60s`, `downstream_rq_total` **never** reaches zero — it holds 4-26 rq/s throughout. **A 5m-rate at 2m-step can manufacture false zeros that do not reproduce at finer resolution.** What WAS real: `envoy_http_ext_authz_ok{cluster=<cluster-k>}` **sustained a hard 0 for 24 min (14:18-14:42 UTC)** while `downstream_rq_total` and `ext_authz_error` stayed non-trivial — a true ext-authz-check collapse, not a traffic outage.
    - **(b) Never accept a peer-supplied "affected set" framing without independently verifying it against HISTORICAL baselines at the same time-of-day on prior days.** The alert's original 3-cluster set `{<cluster-k>, <cluster-f>, <cluster-h>}` was itself a false premise: only `<cluster-k>` was a genuine outage, and the two test clusters were a benign recurring daily scheduled-job burst. **The full decoy, its proof, and the ratio-vs-rate discriminator are #143.** An alert correlated across multiple clusters at the same wall-clock minute is NOT automatically a shipped-change signature — verify each cluster independently before assuming a fleet-wide sync.
    - **(c) Confirm the cluster-specific root cause with a per-cluster NEGATIVE CONTROL on the log signal, not just on the metric.** The workload signature on <cluster-k> was `<auth-service>` fleet-wide Postgres `cannot execute INSERT/UPDATE in a read-only transaction` on the ext-authz-invoked `/api/<authorization-path>` path (`<authorization-handler>` → `saveAll` upsert of a token record). `count_over_time` of that exact string tracked the total error curve **bucket-for-bucket** (9180/14506/8959/8139/6910/4227/1970 at 14:15-14:45), i.e. it explains ~ALL the elevated errors, not a fraction. **The same string was ABSENT on `<cluster-f>`/`<cluster-h>` in the same window (confirmed via a non-vacuous negative control)** — which is what proved (b).

136. **When a service "errors" with the shape THROUGHPUT COLLAPSES (rather than spikes) + SELF-RECOVERS over tens of minutes + ZERO pod / ReplicaSet / GitOps-sync change in the window, check the BACKING DATASTORE's CLOUD-PROVIDER EVENT LOG next — the change may be entirely outside your GitOps repo.** A managed-database failover is invisible to `git`, to the deploy history, and to the cluster.
    - **THE KEY ASYMMETRY, and why a "failover completed" line is NOT an all-clear: the database failover can complete in SECONDS while the application outage lasts TENS OF MINUTES, because recovery is gated by CONNECTION-POOL CYCLING, not by the failover.** A well-provisioned, correctly-configured service pointed at the right primary endpoint still fails every write per-request until its pool cycles the pre-failover TCP connections to the now-demoted instance — **tapering off pod-by-pod rather than all at once**, which is itself the signature. This is NOT a capacity problem, so scaling is the wrong response.
    - **Diagnostic recipe:** read the workload's DB endpoint out of its own spec, then query the provider's event API (`aws rds describe-events --source-type db-cluster`, `gcloud sql operations list`) — **before** concluding "no root cause found" from git and the GitOps controller alone. Find the right CLI profile by grepping your cloud config for the account id.
    - **Always check for PENDING MAINTENANCE on the same instance before closing the incident** — a queued engine or OS upgrade will trigger ANOTHER failover and recur the outage, which turns a post-mortem into a prediction.

137. **On a connection-exhaustion alert, read `backends_by_state` ACTIVE-vs-IDLE against instance CPU BEFORE blaming a leaky client — `active` high + CPU low means BLOCKED queries or a pool stampede, and the runbook's default "restart the culprit Deployment" would make it WORSE.** <cluster-a> AlloyDB, 2026-08-21 (`<database-instance>`/primary hit **10046/10000**): the shape was a **ROLLOUT-AMPLIFIED POOL STAMPEDE, not a leak.** Discriminator that settled it: `active` went **17 → 5564** while instance CPU stayed **7-14%** — thousands of backends blocked, not computing — with `LWLock` waits 3055 → 210140 and `Lock` waits 2934 → 102415 in the same sample. **A leak shows growth in `idle`; here `idle in transaction` COLLAPSED 663 → 2 at the rollout.**
    - **Chain:** an ArgoCD `<application>` sync at 10:20:35Z started a `<backend-service>` canary (30 replicas; <cluster-a> override `DB_POOL_SIZE=10` + `DB_POOL_MAX_OVERFLOW=30` = **40 write conns/pod**); pods churned (Rollout `AVAILABLE 15/30`), each new pod opened a fresh 40-conn pool while terminated pods' backends were not yet reaped, so **~49 pod identities existed in-window against a ceiling sized for 30**. **Self-amplifying:** a pod that cannot get a connection fails readiness, gets recycled, and its replacement opens another pool. It **SELF-RESOLVED when the rollout finished** (`AVAILABLE 29/30`, connections back to 7378).
    - **Baseline headroom was already thin at ~7300/10000 = 73%** — the alert is as much a capacity-planning signal as an incident.

138. **Two attribution errors caught in review, both from bridging ADJACENT evidence into a causal story — and both cheap to prevent.** (<cluster-a> service, 2026-08-11.)
    - **(1) Never infer same-actor from same-IP.** A claim that *"a second user opened the thread URL"* rested on `user_id <user-a>` appearing at the same client IP — but <user-a> was on **different threads**, and the POST that created the incident thread carried the **SAME** `user_id <user-b>`. **Shared client IP = corporate NAT, and proves nothing.** Verify by querying the CREATING request's `user_id` directly.
    - **(2) Pin the ARTIFACT's own timestamp BEFORE picking a log window.** A 404 burst at 18:48:12 was analysed as "the incident" when the screenshot was created at **18:46:53 — 79 s EARLIER**, and that burst had self-healed. Counting that client's non-2xx **in the screenshot's own minute** showed **all 200s**: the photographed banner had NO backend error behind it at all. Use the screenshot filename / created timestamp, not the nearest interesting spike.

139. **An empty namespace-scoped Loki query can be a labeling or collection gap.** Confirmed on <cluster-k> (and likely other clusters) via a `query_loki_stats` non-vacuity check: that selector yields only the `integrations/kubernetes/eventhandler` stream (Kyverno PolicyViolation scan events) — **14 entries total, all k8s events**. The EG proxy pods DO run in that namespace, but their container logs do not carry that namespace label in Loki (or are not shipped at all). **To find actual Envoy proxy access/error logs, search by `service_name`** — discover values via `list_loki_label_values` on `service_name` (e.g. plain `envoy`, `<proxy-service-a>`, `<proxy-service-b>`). **Do NOT conclude "no proxy-side errors" from an empty namespace-scoped query.**

## Label controls and alert coverage

140. **A label can be PARTIALLY populated by a relabel artifact — and the SPLIT case is far more dangerous than the empty one, because it looks like real data.** When a relabeling pipeline duplicates a value (`"x;x"`), a filter on the clean value returns SOME series on some targets and NONE on others: one target answers with nothing (obvious), another answers with a **plausible-looking number built from a tiny fraction of its series** (invisible). **A positive control that only asserts "returned something" CANNOT catch this.** **RULE: for any label used as a PRIMARY FILTER, check its cardinality DISTRIBUTION — `count by (<label>)` or `count by (<labelA>, <labelB>)` — not just non-emptiness, before trusting any query built on it.** **And note two datasources can legitimately differ on which label is correct for the same concept — do NOT "fix" the one that is right** (see #89/#131 for the OTel-vs-Prometheus label families).

141. **A positive control must use the SAME MATCHER TYPE as the query it is validating — a regex path can be dead while an exact matcher returns data at the same instant.** In one Mimir deployment (<cluster-a> 2026-08-20) three `ALERTS` queries using a REGEX matcher returned EMPTY while an exact matcher returned data: `count by (cluster)(ALERTS)` → empty; `ALERTS{cluster=~'<cluster-a>|<cluster-k>|<cluster-c>|<cluster-b>|<cluster-l>'}` → empty; `ALERTS{alertname=~'.*(Waypoint|Ztunnel|Istio|Mesh).*'}` → empty; while `ALERTS{cluster='<cluster-a>'}` → `MemoryNearRequest` firing. **CONSEQUENCE: the "no waypoint alert firing" check in the waypoint-enrollment-validation playbook is a REGEX query while the control the playbook prescribes is an EXACT matcher — so the control does not validate the path the real query takes, and a genuinely broken regex would pass it.** **Control example, when that alert is known to fire: `count by (cluster, alertname)(ALERTS{alertname=~'MemoryNear.*'})`** — `MemoryNearRequest` fires on most of the fleet, so a working regex path returns ~12 clusters (measured <cluster-a> 35, <cluster-d> 9, <cluster-k> 8, <cluster-f> 5, <cluster-l> 4, <cluster-h> 4, <cluster-c> 3, <cluster-i> 2, plus singles). If that is empty, the regex path is broken and every regex-based absence claim is void. **GENERALISES beyond `ALERTS`: when an absence claim depends on a matcher TYPE you have not exercised — regex vs exact, negative vs positive, a `by()` over high cardinality — the positive control must use that same type.** Same family as #33a (absent label + negated matcher → 1.0) and #140 (partially-populated label passes a non-emptiness control).

142. **Pin an incident ONSET from RAW COUNTER PRESENCE at a 60 s step, never from a long-window `rate()`/`increase()`.** Failure mode (<cluster-j>, 2026-08-20 — the exact mistake that made a pre-existing outage look waypoint-caused): a `[1h]` window on a series younger than an hour returns a SINGLE data point, and "almost no history" reads as "this is new". **CORRECT METHOD: query the bare counter — `sum(metric{selectors})` — as a RANGE at `stepSeconds=60` spanning well before the suspected onset. A counter series is CREATED on first observation, so the first timestamp at which the query returns anything IS the onset, to within one scrape.** Worked: <service-d> 500s — series absent at every 60 s step 19:05:00-19:23:00Z, first sample 19:24:00Z=13, 19:25=181. Waypoint traffic — `istio_requests_total{reporter="waypoint"}` absent every step 19:40:00-20:04:00Z, first sample 20:05:00Z=58. **Separation 41 minutes, versus the 17 minutes the operator estimated.** **SECOND STEP, cheap and strong: run the same selector over the preceding 24 h+ at a coarse step to establish whether the failure is novel or recurring** (the service returned NO DATA from 2026-08-19T18:00Z to 2026-08-20T19:23Z = 25.4 h clean). Treat Kubernetes `resourceVersion` as opaque; it is not a portable incident timestamp.

143. **Before treating a multi-cluster onset as a synchronized fault, REPLAY THE SAME QUERY over the previous 1-7 days at the same wall-clock time — a daily-recurring shape means scheduled workload, not incident.** Decoy that cost a wrong cross-cloud hypothesis on 2026-08-18 (the framing error #135(b) records): `<cluster-f>` and `<cluster-h>` emit a small `envoy_http_ext_authz_error` burst **every day at exactly 14:10-14:30 UTC**, peaking ~0.8/s, always sub-threshold against the `>1/s` rule. On 2026-08-18 it coincided to the minute with a genuine <cluster-k> prod ext-authz outage and looked like a synchronized cross-cloud fault, sending the fan-out chasing a shared root cause that does not exist. **PROOF it is a scheduled job: the per-bucket values are NUMERICALLY IDENTICAL day over day** — <cluster-f> 2026-08-17 read 0.579/0.825/0.833/0.688/0.413 at 14:10/14:15/14:20/14:25/14:30 UTC and 2026-08-18 read 0.558/0.825/0.825/0.688/0.413 at the same wall-clock minutes; also present 08-11, 08-12, 08-13. **SECOND DISCRIMINATOR: use the ERROR RATIO, not the error rate.** <cluster-k> was **61%** of ext-authz decisions (100% for 14:25-14:40) with throughput COLLAPSING, while the test clusters were only **6-11%** riding a traffic burst from 0 to 36-56/s — opposite signatures, so the same absolute rate meant completely different things.

144. **Two log-analysis traps that both produce a confident wrong answer on structured access logs.** (a) **NEVER grep a structured-JSON log stream for a severity word — field NAMES collide with severity vocabulary.** The LogQL filter ``|~ `(?i)(error|warn|panic|fail|reject)` `` over the <cluster-a> waypoint stream returned **1,311,335 of 1,311,341 lines** — a 99.9995% false-positive rate — because every Envoy JSON access-log line contains the field name `upstream_transport_failure_reason` (matches `fail`), and often `connection_termination_details`. The result reads as a catastrophic error rate and is pure artifact. **CORRECT METHOD, two steps: (1) count total lines as the positive control, (2) count NON-access-log lines with ``!~ `.*"upstream_cluster".*` `` — on <cluster-a> that was 6 lines out of 1.31 M — then read those 6 individually.** All 6 were `info xdsproxy connected to delta upstream XDS server: istiod.istio-system.svc:15012`, one per pod, routine xDS reconnects (same shape as <cluster-k>: 6 lines / 46,677). Generalises: filter to non-structured lines first, or parse and filter on `detected_level`/`severity`. (b) **Before concluding a log-based method is unavailable, check whether the logs exist at the SOURCE (`kubectl`) separately from whether they reach the COLLECTOR (Loki) — different failures, different fixes, very different severity.** The some clusters omit the `<workload-namespace>` namespace from `charts/otel/…/podLogsViaLoki.namespaces`, so ZERO <workload-namespace> container logs reach Loki, but the waypoint `istio-proxy` container still writes access logs to stdout (`kubectl --context <c> -n <workload-namespace> logs <waypoint-pod> -c istio-proxy`) — so the overhead method degrades from queryable to manually-captured, not blocked (verified <cluster-i> 2026-08-19). **DIAGNOSTIC that separates the two, because they look identical in Loki: query with `k8s_container_name=~".+"` as the discriminator.** Kubernetes EVENTS (`service_name="integrations/kubernetes/eventhandler"`) carry no container name and still arrive when pod-log shipping is off, so a namespace can show thousands of Loki lines/hour while shipping zero container logs — <cluster-i> `<workload-namespace>` showed 3,098 lines/hr that were ALL Kyverno events; <cluster-k> `<workload-namespace>` showed 3,914,433 real container lines.

145. **Before putting a `for:` duration on an alert, check the SOURCE JOB's SCRAPE RELIABILITY — a flaky target silently makes `for:` unreachable.** Prometheus/Mimir `for:` requires the expression true at EVERY evaluation, so a series gap longer than the lookback resets `pending` and a `for: 15m` alert on that target **may never fire**. Measured: <cluster-c> `policy-reporter` has `avg_over_time(up[24h]) = 0.863` with `max scrape_duration_seconds = 10.05s` against a 10 s timeout (pod has 0 restarts, so it is scrape-side — too many series to serve in 10 s), producing observed 3-6 min series gaps. **Check `avg_over_time(up[24h])` and `max_over_time(scrape_duration_seconds[24h])` vs the configured timeout before choosing a `for:`.** **Fix: wrap the selector in `max_over_time(…[N])` with `N` >> the observed gap (30 m here) to bridge it; the cost is the alert clearing up to N late.** **Diagnostic pair that exposes it: run the alert expr AND its inversion (`unless` → `and`) — if the inversion intermittently drops a cluster, the source is gappy, not the logic.** Generalises #62a (which covers the same reset mechanism for 5 m-cadence Stackdriver gauges) to any unreliable target, and pairs with #100 (offline `for:` simulation) — simulate the `for`, but only after proving the target can sustain it.

146. **Three DETECTION defects worth auditing your own alerts for.** (a) **INVERTED `for:` durations.** If the 80%-warning carries a LONGER `for:` than the 90%-critical, then on a fast ramp the "leading indicator" fires AT OR AFTER the alert it is supposed to lead — measured, both went firing in the same evaluation. **A leading indicator must have a STRICTLY SHORTER `for:` than the alert it leads.** (b) **ABSOLUTE thresholds on an instance whose CEILING MOVED.** A `> 400` / `> 600` connection alert on an instance whose limit is 10000 and whose IDLE BASELINE is ~7300 fires permanently, generating an incident flood that BURIES real signal. This is the same always-on antipattern as a saturation ratio on a workload designed to run at its ceiling (#110) — **audit for it whenever an instance is resized.** (c) **A flapping alert AUTO-RESOLVES its incident MID-INCIDENT.** An alert whose source is sampled far more coarsely than its evaluation can go `pending → firing → absent → pending` while the underlying condition never improves — clearing and re-arming its own `for:` clock — and the incident tool auto-resolves the ticket with the system still breached. **CONSEQUENCE: on-call reads the pager and believes the incident is over when it is not.** **Any coarsely-sampled threshold alert near its trip point needs a longer `max_over_time` window or `keep_firing_for`.**

147. **Two kube-state-metrics SHAPES that break the obvious query.** (a) **`kube_<resource>_annotations` emits ONE SERIES PER OBJECT even when the object carries none of the allowlisted annotations — the allowlist does NOT scope the series set.** Source at v2.18.0: `internal/store/serviceaccount.go:176-196` calls `createPrometheusLabelKeysValues` (`internal/store/utils.go:181-197`), which returns an EMPTY allowed map when no key matches and **still builds `metric.Metric{Value:1}` with just the base labels**. Also: `serviceaccounts` IS a valid KSM collector (`builder.go:355,460`) but is **NOT** in the grafana `k8s-monitoring` v4 chart's default collectors list, so enabling it means restating the whole `--resources` list AND adding `rbac.extraRules` (the chart's `role.yaml` grants only what is in `.Values.collectors`). (b) **`crossplane_xrole_status_condition` (and every `crossplane_{aws,gcp}_*_status_condition` from the KSM custom-resource-state config at `charts/otel/values.yaml` ~line 892) is NOT a StateSet.** It emits ONE series per `(name, type)` where **`status` is a DYNAMIC LABEL carrying the current status** and the VALUE is 1 for True / 0 for False — there are no parallel `status=False/Unknown` series sitting at 0 when healthy. **Two consequences: (1) `sum by (type,status)` is WRONG for counting conditions** — False series have value 0, so a sum draws every failure line flat at ZERO. **Use `count by (type,status)`.** Verified: at 2026-08-08T03:36:33Z `sum` reported `Ready/False = 0` while `count` reported **24 genuinely-broken XRoles**; this defect shipped in the original `crossplane-overview` dashboard panel 31. **(2) A `count(x == 0)` stat returns EMPTY ("No data") on a healthy fleet, not a green 0** — use the subtraction form `count(…{type="Ready"}) − sum(…{type="Ready",status="True"})` so both operands always exist. Same family as #21 (name-index presence is not series presence).

148. **Ambient enrolment makes Beyla start instrumenting the WAYPOINT PODS THEMSELVES, silently dragging every namespace-wide latency aggregate upward.** Observed on <cluster-k> 2026-08-19; Check this when enrolling another cluster. (Beyla label names: #17.)

149. **A render gate that treats PromQL as OPAQUE YAML is not a PromQL gate — mutation testing showed identity-level defects escaping CI at 7 of 7.** A workflow that runs `helm template` plus required-key checks **validates the syntax of the DOCUMENT, not of the QUERY.** Mutation-tested against real alert rules: wrong `by()` grouping label, broken `on()`/`group_left` join label, metric-name typo, comparator flip `==0 → !=0`, workload identity swap, stripped selector splice, altered selector, changed parentheses **including an UNBALANCED PAREN**, whole-rule PRESENCE, `for` duration, `severity`, threshold and environment selector — **every one exited 0, each `cmp`-verified to have changed bytes. Only a malformed-YAML control exited 1.** **Consequence: a semantically-wrong-but-renderable rule reaches production undetected**, and manual live controls (#104) support ONE snapshot but **do not protect future edits**.

It does not prove that joins or selectors can produce rows — use the composed-expression control in #19, plus behavioural and mutation tests (#27). Run one deliberately malformed query to prove the validator can reject it.

150. **Proving a `== 0` availability alert is FIREABLE when the target has never been down — a two-part positive control, plus the stronger join.** The risk is that the exporter **DROPS** the series rather than emitting 0, in which case `== 0` is permanently unfireable and the alert is decorative. **(A)** Run the same expression with a RELAXED comparator (`< N`) to prove the selector and grouping labels resolve on the target. **(B)** Run the identical expression with the identity matcher UNPINNED, to find OTHER objects in the same metric family currently sitting at 0 — **that proves the exporter emits 0 rather than dropping the series.** **A+B together is a valid positive control without needing a historical outage.** **(C) Stronger, for the crashed-workload shape: do not merely count workloads at 0.** Join availability against desired: `(max by(...)(available) == 0) + on(...) group_left max by(...)(spec_replicas) > 0` — a hit means `spec > 0` AND `available == 0`, i.e. a genuinely CRASHED workload, the exact outage the alert targets. **Counting zero-valued workloads alone is weaker, because a scaled-to-zero workload proves nothing about the crash case.** **And check the metric inventory first: if the PDB or ready-replica series you wanted do not exist in your store (#1/#21), fall back to `== 0` rather than hardcoding a per-cluster `minAvailable`, which would silently drift from its source.**

151. **An exclusion on a bidirectional metric is DIRECTIONAL — say which direction it covers, and re-verify what still fires.** A `source_workload != X` exclusion added to a connection-failure alert is **SOURCE-SIDE ONLY: traffic INTO X remains monitored**, which is usually what you want but is almost never written down. **Two verification obligations after adding one**: (1) confirm the alert **STILL FIRES** for the classes you did NOT exclude — measure how many pairs met the condition over a real window, and name them; (2) confirm the excluded class was actually the dominant noise, because a neighbouring benign class (e.g. an ingress gateway's rolling-deploy RSTs, #118) is NOT swept up by it and still needs its own treatment. **An exclusion that silently also removes a class you meant to keep is indistinguishable from a healthy alert.**

152. **A PromQL label-inequality does NOT exclude the LITERAL STRING that spells a missing value.** `exception_status != "401"` correctly stops 401s from firing — and passes through every series whose `exception_status` is the literal `"None"` emitted when the upstream client attaches no HTTP status at all. An alert "fixed" this way keeps paging on a **different** failure mode while the tuning PR reads as merged, synced and working. Two consequences: verify a tuning change against the **firing series' actual label values** over the following days, not against the excluded case; and handle sentinel strings (`None`, `unknown`, `""`) EXPLICITLY, because they are values, not absences.

153. **When a regex log query keeps timing out on your highest-volume target, stop widening the window and switch lenses: the Loki PATTERN INGESTER answers "what error shapes exist here?" without scanning raw logs at all.** The pattern ingester runs the **Drain** algorithm over ingested lines, auto-discovering log-structure templates and their occurrence counts, and serves them from an in-memory index — so a pattern query costs nothing like a `|~` regex `count_over_time` and **is immune to the timeout class that makes 3-day regex queries unusable on a busy cluster** (the same clusters where the documented fallbacks are "shorten to 24 h and run several windows" or "sum `[1m]` windows as a range query with `stepSeconds=60`", `gcx-guide.md`). **Use it as a DISCOVERY pass, never as the assertion.** A hand-maintained "actionable error" regex can only match the failure modes someone already thought of; the pattern list is generated from what is actually there, so it is the only cheap way to find the error classes your classification is silently dropping into the residue. Worked example: a pattern sweep surfaced a proxy **panic** (`thread panicked at <source>:<line>`) and its precursor transport error (`must receive peer addr: Os { code: 107, kind: NotConnected }`) — neither matched the curated "mesh infrastructure error" alternation, so both had been invisible to every run of the deterministic query. **Operating rules.** (a) Most returned patterns are the normal-completion line; filter those and read the rest against a keyword list (`panic`, `fail`, `timeout`, `unwrap`, `backtrace`, `NotConnected`, plus your domain's control-plane words). (b) **Anything the sweep surfaces that deserves attention should be PROMOTED INTO the deterministic regex** — the pattern pass finds it once, the regex is what catches it every run. (c) **Pattern data is EPHEMERAL: it resets on ingester restart and covers only the retention window, so it can never support a historical or "this did not happen" claim** — that is exactly the absence-is-not-evidence trap in #25/#82 wearing new clothes. Treat it as a complement to the deterministic queries, never a replacement. (Discovered running a recurring fleet health playbook, 2026-06; cross-ref `references/gcx-guide.md` for the timeout workarounds and the literal-TAB filter gotcha, `learnings-istio.md`/`#82` for the error-classification scheme this feeds.)

154. **A Prometheus INSTANT query returns a series for one full STALENESS WINDOW (~5 min, `PROM_STALENESS=300s` by default) after the thing it describes is gone — so "two versions present" during and just after a rolling upgrade is the DESIGNED reading of a SUCCESSFUL roll, not evidence of a straddle.** This single mechanism manufactures a whole family of false FAILs in any check that asserts "exactly one value of label X right now": version/tag uniformity, image uniformity, replica identity, endpoint membership. The departed pod's last sample is still within the lookback, so the old label value is still returned — correctly, by design. **The fix is a SETTLE FLOOR, not a tolerance:** do not grade a uniformity predicate until `max(staleness, roll_window)` has elapsed since the last pod replacement, and derive the roll window from the actual rollout rather than assuming it. **Do not "fix" this by shortening the lookback** — you will start losing live series from any target whose scrape interval is close to it. **Two corollaries that catch people out.** (a) **The window is measured from the SERIES disappearing, not from the deployment being marked complete** — a controller reports Ready while the last replaced pod's samples are still inside the lookback, so "rollout status says done" is not the signal to start grading. (b) **A RANGE query does not have this behaviour in the same way**, so an instant query and a range query over the same instant can legitimately disagree about how many values exist — if two lenses disagree at a roll boundary, check which one is instant before theorising. Same family as #95 (exact-count equality between independently-sampled populations) and `learnings-validation-framework.md` (counters that live ON the rolled component stop exporting for 10–20 min afterwards).

155. **`ignoring(<label>) group_left` is a MALFORMED join, not a stricter one — stripping the only label that distinguishes two series collapses them into duplicates and Prometheus errors or silently picks one.** The intuition that `ignoring()` "tightens" a match is backwards: it REMOVES a label from the matching key, so if that label was the discriminator (e.g. the name of the workload, the component, the DaemonSet), both sides collapse to identically-labelled series and the many-to-one contract is violated. The symptom is either an outright `found duplicate series for the match group` error or — worse, when only one side collapses — a join that quietly matches the wrong pair and returns a plausible number. **Rule: `on(...)` and `ignoring(...)` define the match key, and the match key must still contain every label needed to tell the operands apart. Before writing either, run each side alone with `count by (<proposed key>)` and confirm the count is 1 per group on the "one" side.** Adjacent traps in the same family: #19(a) — confirming the component metrics merely EXIST is insufficient for a JOIN-based alert, because a mislabelled join returns empty even when the condition is true; and #5 — a label used only in a selector is dropped from the firing series by `by()`.

156. **Two kubectl query traps that return a confident wrong answer rather than an error.** (a) **JSONPATH CANNOT COMPARE AN ABSENT FIELD, and Kubernetes omits most boolean fields rather than setting them `false`.** `.spec.unschedulable` and `.metadata.deletionTimestamp` are simply **absent** on a normal object — so a filter like `items[?(@.spec.unschedulable!=true)]` matches **nothing at all**, and the "no unschedulable nodes" census it was written to produce comes back empty and reads as a clean zero. **Never filter on a field that is absent in the healthy case.** Project the field into the output (`custom-columns`, or a jsonpath that emits it) and filter downstream in `jq`/`awk`, where absent is representable. **This is the kubectl-side sibling of the absent-label PromQL trap (#82)** and fails the same way — silently, in the reassuring direction. (b) **`managedFields` IS STRIPPED BY DEFAULT and the flag does not apply uniformly across output formats.** Verified live on kubectl v1.33.3: `-o json` / `-o yaml` without `--show-managed-fields` return **0 managers on 6/6 objects — the key is absent entirely, not empty** — while the same objects with the flag return 2 managers on 6/6. So any check that reasons about field ownership (who last applied this, is a controller fighting us, did a manual edit land) reads a structurally empty answer and concludes "no other manager" on every object it examines. **If a check depends on `managedFields`, it must pass the flag AND assert non-empty on a control object it knows has multiple managers** — otherwise the check cannot distinguish "no conflict" from "not asked".

## Exporter semantics and absence proofs

157. **kube-state-metrics `custom-resource-state`: a `StateSet` may point `path` DIRECTLY at a string and omit `valueFrom` — the empty `compilePath` makes `valuePath.Get` return the path value itself, which the registry factory then compares against the list entries to emit 1/0 series.** Verified in **kube-state-metrics v2.13.0** (`registry_factory.go`), and upstream's own `example_config.yaml` and `Test_values` use exactly this shape — so a config that looks like it is missing a required field is idiomatic, not broken. ✅ Companion setting for any `int32` with `omitempty`: **`nilIsZero: true`**, or a genuine zero disappears from the series entirely and every ratio alert built on it silently stops evaluating (see `learnings-agent-sandbox.md` for why absence means zero there). ⚠️ When changing the CRD **version** a `custom-resource-state` config targets, diff the new version's field set first: a field that the new version drops (e.g. a `status.replicas` that moves to a different kind) silently takes its metric with it, while a kind that RETAINS the fields is unaffected — check both kinds, not one.

158. **⚠️ A ratio-based capacity alert (`ready / desired < X`) CANNOT distinguish a BROKEN pool from one DRAINED BY DEMAND — both render as the ratio going to zero.** The discriminator that settles it in one query: **`sum(<desired-replicas metric>)` FLAT while `sum(<in-use/owner metric>)` STEPS UP ⇒ demand, not failure.** Confirm user impact with a `histogram_quantile` on the startup-latency histogram for that pool, and confirm demand with `rate(<creation-total>)`. ⚠️ **And check whether the autoscaling that the alert implicitly assumes is even ENABLED** — if the desired-replica count is static config rather than an autoscaler output, any sustained burst against a small pool **guarantees** this alert, and the alert is measuring your capacity planning, not an incident. That fact belongs in the runbook; without it every burst pages someone who then finds nothing wrong.

159. **VictoriaMetrics retention relief arrives as SCHEDULED CLIFFS, not continuously — so a linear "days until full" ETA is wrong in both directions.** Partitions are **MONTHLY**, so with a 30-day retention the disk holds up to **~61 days** of samples; the previous month's partition drops roughly 31 days after that month ends (observed ~00:30 UTC), and index rotation is its own separate drop at `vm_next_retention_seconds`. **A linear ETA OVERSTATES urgency inside a cycle while understating it across cycles — what matters is the per-cycle PEAK**, which you get by adding the surviving partitions plus the projected growth of the current one. ⚠️ **CORRECTION worth carrying: from v1.148 the index is PER-PARTITION** (`data/indexdb/YYYY_MM`, alongside a small legacy `indexdb/<id>`), so a monthly drop removes that month's data **and** its index together — earlier reasoning that treated index rotation as fully independent under-counts the relief. ✅ **Ground partition sizes read-only from the backup bucket rather than guessing:** `gcloud storage du -s gs://<backup-bucket>/latest/data/{big,indexdb}/YYYY_MM` summed to within 0.1 GB of `sum(vm_data_size_bytes)` in practice. Confirm the disk is real data and not merge scratch with `vm_active_merges == 0` plus the absence of *"additional space needed"* log lines. ⚠️ Query mechanics through a read-only apiserver proxy: **range** queries with a bare `count(up{…})` fail *"invalid: unknown"* — use **instant** queries with `[1d]` rollups. And `ALERTS` may not be remote-written to the storage node at all; read the ruler's `/api/v1/alerts` instead.

160. **A per-pod scrape multiplies series by POD CHURN, not by node count — measure the churn before sizing the keep-list.** CSI/mount-style sidecar pods churn far faster than nodes: one estate saw **~6.5 mount pods per node per day** (13,582 distinct pods across 2,076 nodes in 24 h), which turns a raw 438-series-per-pod exporter into **~6 M new series/day**. Trimming to ~22-24 series per pod brought the same coverage to ~326 k/day. **Measure churn with `count(count by (pod)(last_over_time(<a per-pod metric>{namespace="…",container="…"}[1d])))`** — and note `kube_pod_info` may not cover the namespace at all if kube-state-metrics is namespace-scoped, so do not use it as the census.

161. **⚠️ A LAZY `CounterVec` is absent from an idle exporter, so a single-pod snapshot is NOT an absence proof — sample WIDTH, not depth.** Worked instance: `.items[0]` on each of three clusters showed a metric missing, which read as a dead token in a scrape keep-list; the adversarial lens refuted it from source (a real, correctly named `CounterVec` that only materialises after the pod's first backend GET/PUT), and re-sampling **41 pods** found **28/41** exporting it. **Before calling a metric name wrong or dead, sample ~40 pods, and read the exporter's source to see whether the family is registered eagerly or on first use.** This is the canonical case for the second lens: an independent model with source access overturning a live-verified but statistically underpowered claim.

162. **To prove a metric is genuinely NOT SCRAPED fleet-wide, run refute attempts that rule out DIFFERENT causes — five, not five repetitions of one.** The set that settled one such verdict: **(1)** enumerate the Grafana datasources so you know there is no second metrics backend to check; **(2)** `__name__` values with a **30-day lookback**, plus instant *and* range queries for the exact name (a wider window changing nothing is the point); **(3)** enumerate **every** scrape CRD cluster-wide and confirm the agent is `selectAllByDefault`, so absence is **not** a selection-scope bug, and that no scrape object targets the namespace where the pods actually run; **(4)** prove the ENDPOINT is live — `kubectl get --raw /api/v1/namespaces/<ns>/pods/<pod>:<port>/proxy/metrics` returning a real value shows the gap is target absence, not a dead exporter; **(5)** repeat (2) independently on every other cluster, via its own storage node, so the finding is fleet-wide rather than one environment's. ⚠️ **Note what this costs you: with no scrape, the historical value CANNOT be recovered from any datasource** — so if the question was "how big was it during the incident", the answer is *unavailable*, and saying so is the finding.

163. **`VMSingle` under vm-operator v0.74.0 is a Deployment + a STANDALONE PVC, and the operator expands the PVC in place — it never deletes it.** Path: `factory/vmsingle/vmsingle.go:56` → `reconcile/pvc.go:24` → `updatePVC` in `statefulset_pvc_expand.go:201-208`, an `rclient.Update`. So growing storage is a values change, not a recreate — but check the **promotion path**: if production storage is applied only on a release-branch push, the merge that carries it also fires every other workflow that path-filters that same config file. ✅ Offline proof is a template render at base and head with the untouched environments' diffs empty as the negative control. ⚠️ `kubectl auth can-i --as <sa>` is forbidden without impersonate rights — read the ClusterRole directly instead.

164. **"Grafana has no MCP support" is usually a MISDIAGNOSIS — check the version gates per TOOL, not per server.** Measured against **Grafana 11.2.0** and **mcp-grafana v1.6.0**: the server needs only **Grafana ≥ 9.0**; dashboard tools fall back to the legacy API on 11.2 because `/apis/dashboard.grafana.app` 404s there (`tools/dashboard.go:86-108`, `k8s_client.go:235-256`); **only alert-rule list FILTERS are gated** (folder UID 11.4+, search/matchers 12.4+, `tools/alerting_client.go:98-100`). 165. **Raising search.maxQueryDuration raises vmalert query deadlines too.** VictoriaMetrics v1.148.0 applies this flag to `/api/v1/query` regardless of the caller (`app/vmselect/searchutil/searchutil.go:42`, `app/vmselect/prometheus/prometheus.go:771`). vmalert has no HTTP client timeout (`app/vmalert/datasource/init.go:123`); group evaluation uses `WithCancel`, not an interval deadline (`rule/group.go:426`), and slow evaluations skip intervals (`:484`). ## VictoriaMetrics query cost and dashboard mechanics

166. **`-search.maxMemoryPerQuery` is enforced PER ROLLUP SUB-EXPRESSION, not against a query total — so it is much weaker isolation than the name suggests, and the only cumulative bound is a pre-existing global one.** Verified in **VictoriaMetrics v1.148.0**: `rollupMemorySize` is a **local** declared at `app/vmselect/promql/eval.go:1866` inside `evalRollupFuncNoCache` (opens :1803, called once per sub-expression from `evalRollupFuncWithMetricExpr`), compared at :1875, and **never accumulated into any package-level sum**. The one cumulative limiter is `rml.Get`/`defer rml.Put` (:1885/:1894) against the `rollupMemoryLimiter` singleton, whose `MaxSize = memory.Allowed()/4` (:1913-1917) = `0.6 × limit / 4`. ⚠️ Consequence: setting `maxMemoryPerQuery = limit/8` gives a per-query cap ≈ **83 % of that already-existing global budget** — it barely constrains anything. A much larger divisor is needed for real per-query isolation. ⚠️ Practical consequence for review: a dashboard panel with several heavy sub-expressions is **NOT** rejected at the sum of their estimates, only at the largest one.

167. **The rollup estimate is `points_per_series × series × 16 bytes`, and because BOTH factors grow with the range on a churning selector, the memory cost scales ~QUADRATICALLY with the time range.** Worked arithmetic: a `[7d:5m]` subquery over 69 k pod series = `2017 × 69,000 × 16` ≈ **2.24 GB**. ⚠️ **An instant `count()` of the same selector drastically UNDERCOUNTS it**, because the cost model counts **every distinct series touched across the window**, not the currently-live set — one fleet showed ~783 live series against ~69-84 k over 7 d at ~12 k new series/day. ✅ Levers that actually work, in order: shorten the range; cap `maxDataPoints` to force a coarser step (1000 points at 7 d → a 10 m step, halving the estimate); drop the high-cardinality grouping label; push aggregation down **before** any join. ✅ Because the growth is quadratic, a panel that is safe at 24 h can cross a 1 GiB cap at ~4.4 days and a 2 GiB cap at ~6.2 days — **state the range a dashboard is safe at, not just that it is safe.**

168. **⚠️ BLIND SPOT: neither `-search.maxMemoryPerQuery` nor the global rollup limiter protects an INCREMENTAL-AGGREGATION query, so the cheapest-looking expression is the one that OOMs the node.** At v1.148.0 both gate on the rollup estimate in `evalRollupFunc` (`eval.go:1845-1890`). For incremental-aggregation-eligible expressions — `sum`/`max`/`count` **by (...)** over a rollup — the estimate assumes `GOMAXPROCS × 1000` output series, so `max by (pod)(…)` over 300 k pod series is estimated at ~**64 MB** while it really allocates `groups × points × 16 B` **per worker** (`aggr_incremental.go:98-136`). ✅ Only `-search.maxUniqueTimeseries`, a shorter range, or dropping the `by (pod)` grouping protect against it. (`maxSeriesPerAggrFunc` applies only to `count_values`.) ⚠️ Measured consequence: a 30-day per-pod query OOM-killed a 16 GiB single-node instance — **VM's 30-second query timeout does NOT protect memory.** Keep pod-level dashboards to ≤7 d, and never benchmark a 30 d pod-level query against a shared instance.

169. **For a per-pod PEAK over a long range, set the rate window EQUAL to the subquery step — `max_over_time(rate(x[W])[R:W])`.** It gives the highest sustained W-average with **no sampling gaps and no dropped short-lived pods**, at the same memory cost (points = R/step). ⚠️ `rate[5m]` sampled at a 15 m step leaves **10-minute holes**: measured, it dropped one agent entirely and reported a 24 h peak of 3.74 cores where the gap-free query said 6.99 (and `rate[15m]` said 4.48 — a genuinely different, longer-averaged quantity). ⛔ MetricsQL's `rollup_rate(..., "max")` is cheaper but returns garbage peaks from scrape noise and counter resets (594 "cores" on a 8-core node). ✅ For a stable top-N over a whole dashboard range use **`topk_max(N, q, "label=other")`**, which picks one set for the entire range plus an aggregated `other` series — plain `topk()` in a range query re-picks per step and explodes the legend.

170. **Grafana query timeouts on a browser-facing stack are capped by the LOAD BALANCER, not by Grafana or the TSDB — so raising the datasource and TSDB timeouts changes nothing a user can see.** Measured on both clouds: a GCP ingress whose `BackendConfig` sets only `spec.iap` leaves the backend service at the platform default **`timeoutSec=30`**; an AWS ALB with no load-balancer-attributes annotation sits at **`idle_timeout=60`**. With a `proxy`-access datasource every panel query is browser → LB → Grafana → TSDB, so it dies at 30 s / 60 s regardless. ✅ Raising it is a **separate, ingress-level change** (`BackendConfig spec.timeoutSec`; `alb.ingress.kubernetes.io/load-balancer-attributes`) and may touch a **shared** LB — which makes it a different blast radius and often a different PR. ⚠️ Say this explicitly when reviewing a "raise the query timeout" PR: the knob in the diff is real but **unreachable through the UI** until the ingress changes.

171. **Grafana's two query-timeout knobs, and which one wins.** Verified at **Grafana 13.2.3**: a datasource's `jsonData.timeout` (integer **seconds**) overrides the default in `getTimeout` (`pkg/services/datasources/service/datasource.go:1010-1026`); the default is `[dataproxy] timeout` (`setting_data_proxy.go:15`, **default 30**). Raise **both** when raising a TSDB's max query duration — and then see the entry above, because the LB still wins. ⚠️ A datasource with `jsonData: {}` has no timeout override at all, which is easy to mistake for "configured to 30".

172. **Grafana FILE/sidecar provisioning ADOPTS a pre-existing hand-built dashboard with the same uid — same uid, same URL, same folder, no duplicate and no error.** Verified at **v13.2.3**: `createDashboardJSON` sets `Overwrite=true` (`pkg/services/provisioning/dashboards/types.go:67-83`); `ValidateDashboardBeforeSave` resolves the ID from `existingByUid` and aligns the version (`pkg/services/dashboards/service/dashboard_service.go:805-874`) and only errors *SameUIDExists* when id and uid resolve to **different rows**; `saveProvisionedDashboardThroughK8s` (:1788-1834) does an Update by uid and Creates only on NotFound. With `foldersFromFilesStructure`, a pre-existing folder is looked up by title+parent and **marked managed rather than duplicated**. ✅ Practical consequence: a dashboard built by hand through the API can be committed to a provisioning directory **without deleting the manual copy first**; after adoption it becomes provisioned and UI-read-only (`allowUiUpdates: false`). ✅ Verify live with `/api/dashboards/uid/<uid>` — `meta.provisioned` flips `false → true` and the folder matches the sidecar's. `provisioning/dashboards/types.go:67-83` sets `Overwrite=true` and the provider folder; `file_reader.go:356-358` clears exported numeric IDs; `dashboards/service/dashboard_service.go:826-848` resolves an existing dashboard **by UID** and `:860-863` aligns the version on overwrite; the newer storage path (`:1819-1830`) updates first and creates only on NotFound. ⚠️ This supports UID-preserving adoption **in principle** — it does not establish a live environment's current UID or folder, and it does not rule out a runtime provisioning failure. Check the chart's declared appVersion, not the chart version, when citing source.

173. **Patching a large dashboard through the API is far cheaper than re-inlining its JSON — but the index-based paths are a moving target.** ✅ What works: replace `$.panels[i].gridPos` for shifted panels and append new panels with **explicit stable ids**; Grafana sorts by `gridPos` on render, so array order need not match the generator's. ⚠️ **Three traps.** **(a) Index drift:** Grafana **re-sorts `panels` by `gridPos` on save**, so every array index changes after any layout edit — **always re-read the live id → index map immediately before a patch.** A stale map silently wrote query targets onto a row panel. **(b) Nested arrays are not addressable** — `$.panels[N].targets[2]` fails (*"targets is not an array"*); replace the whole `targets` array. **(c) A patch round-trips the entire dashboard through the server's structs and drops `"value": null` from EXISTING panels' threshold steps** — a semantic no-op, but a before/after diff shows it (measured: the only delta on one panel was `,"value":null`). Newly appended panels keep theirs. ✅ Verify a patch with **per-panel fingerprints** (`del(.gridPos) | tojson`, or description/expr lengths) compared across two saved versions, rather than diffing full JSON. The MCP dashboard tools see panels sorted by `gridPos` (y, x), while `/api/dashboards/uid/<uid>` returns stored order. On one real dashboard a panel sat at index 25 in the legacy map and index 13 in the tool's view, so a 22-op patch wrote `gridPos` one slot off for 13 panels and replaced one panel's `fieldConfig`/`transformations` with another's. ✅ **Build the id→index map with the SAME tool you will patch with, immediately before patching**, and verify with per-panel fingerprints across versions.

174. **A Cloud-Logging-backed Grafana datasource returns LOG LINES, not counts — so an "events per hour" panel must bucket client-side.** Verified at **googlecloud-logging-datasource v1.8.1**: it returns only log-line frames and caps rows at the panel's `maxDataPoints` (`plugin.go:430` sets `Limit = query.MaxDataPoints`; the client orders by timestamp **desc**). ✅ Set `maxDataPoints` high (e.g. 10000) and chain transformations: format time → group by (count id) → convert field type → sort. ⚠️ Two silent biases: a low `maxDataPoints` **truncates the newest N and silently undercounts**, and because the order is descending, the truncation removes the **oldest** part of the window.

175. **kube-state-metrics joins need pre-aggregation, because `kube_node_labels` and `kube_pod_info` carry KSM's own extra labels and a naive `on(node)` / `on(pod)` hits many-to-many.** Wrap each side in `max by (node[,pool])(…)` / `max by (pod,node)(…)` first. ⚠️ Two related counting traps on sandbox-style workloads: **sidecars often carry no requests/limits at all**, so a per-pod sum across containers equals the one real container — true today, silently wrong the day a sidecar gets a limit, so **select the container explicitly**; and **pod NAME prefixes are not a reliable population filter** (one fleet named pods two different ways depending on whether a warm pod was reused, and filtering on one prefix dropped a 340-pod burst, moving a cost-per-pod figure by 37 %). Count by namespace + container name, and read the workload identity from a LABEL, not from the pod name.

176. **CPU THROTTLING can be genuinely unmeasurable on a fleet — check that the series exist before designing around them, and use node saturation as the proxy.** **Method — run this census BEFORE building any analysis on throttling:** count the pods in the namespace, then count the distinct pods actually carrying `container_cpu_cfs_throttled_seconds_total`; separately confirm whether `*_periods_total`, the PSI `container_pressure_cpu_*` family, and `node_cpu_seconds_total` exist at all. Coverage is routinely a tiny MINORITY of pods rather than all-or-nothing, the pods you care about are often the ones missing, and `node_cpu_seconds_total` is absent wherever node-exporter is not deployed — so "the series returned nothing" must be read as *unmeasured*, never as *zero throttling*. ✅ Substitute: `sum by(node)(rate(container_cpu_usage_seconds_total{…}[5m])) / <allocatable cores>` as a contention proxy. ⚠️ Even where it exists, **CFS throttling only measures a pod hitting its OWN limit and never neighbour contention below the limit** — it cannot answer "is bin-packing hurting us". ⚠️ And on gVisor-style sandboxed runtimes, cAdvisor working-set is exposed only at **pod level (`container=""`)**, never per container.

177. **Normalise an efficiency result to COST PER UNIT OF WORK, never to a node count — and check the retention of every series in the comparison before you promise a before/after.** Node count tracks demand, which can swing ~2× day to day, so a before/after node count measures activity. `sum(node_count × price) / count(workload pods)` is what made one packing result legible (0.98 → 1.80 pods/node, \$129.11 → \$104.50 per pod-month). ⚠️ **Retention is per-metric:** the node-label series retained only ~16 days where pod metrics retained 30, so the baseline for a change evaporates in **two weeks**. Measure a change within that window or the comparison is impossible. ⚠️ Use **hourly averages, not snapshots** — a single overnight snapshot of one fleet reported −9 % where the hourly average showed no change at all.

## Grafana auth, provisioning and interpolation (v13.2.x, 2026-10)

178. **Grafana serves `/metrics` with NO auth by default, so removing an identity-aware proxy in front of it publishes the endpoint.** `pkg/api/http_server.go:755-773` registers `metricsEndpoint`; `setting.go:1652` makes `[metrics] enabled` default true; only `[metrics] basic_auth_username`/`password` gates it. Check whether anything actually scrapes it before deciding — in one estate nothing did, and `metrics.enabled=false` under the SSO gate was the clean fix. ⚠️ Same class, same cutover: **public dashboards and external snapshots are enabled by default** (`publicDashboardsEnabled` / `snapshotEnabled` in `/api/frontend/settings`), and any Editor can create one — once the proxy is gone they are internet-reachable without SSO. Set `public_dashboards.enabled=false` under the same gate.

179. **Grafana's OAuth role mapping is evaluated against the USERINFO response, not the ID token — so an identity provider that returns groups only in the ID token silently yields the default role for everyone.** For the Okta connector (`pkg/login/social/connectors/okta_oauth.go:165-183,213,231-236`) the ID token supplies only `sub`/`email`/`name` (and is parsed **unverified** unless `validate_id_token` + `jwk_set_url` are set, `:135-155`). `social_base.go:193-207 searchRole` evaluates `role_attribute_path` **first against the raw userinfo JSON**, then retries against a `{groups:[…]}` object built from userinfo groups. With `role_attribute_strict=false` a missing `groups` claim makes the JMESPath error and everyone falls back to Viewer **with no error surfaced**. ✅ Diagnose with a throwaway role path like `length(groups||[])>0`. ✅ Env override form is `GF_<SECTION>_<KEY>` with dots → underscores (`setting.go:1247,1257`), so `[auth.okta] client_secret` = `GF_AUTH_OKTA_CLIENT_SECRET`. ✅ Break-glass with `auto_login` on: `/login?disableAutoLogin` (`pkg/api/login.go:115`).

180. **Turning off `[auth.basic]` breaks the dashboard sidecar's provisioning-reload call, because that sidecar POSTs `/api/admin/provisioning/dashboards/reload` with ADMIN BASIC AUTH.** The chart passes `REQ_USERNAME`/`REQ_PASSWORD`/`REQ_URL`/`REQ_METHOD` from the release Secret; with basic auth off it 401s. ✅ Pair the change with the sidecar's `skipReload=true` (which removes those env vars) and let Grafana's **file provider** re-walk the directory every `updateIntervalSeconds` instead — the chart default is 30 s, and ≤10 s switches it to fsnotify (`file_reader.go pollChanges`). ⚠️ Service-account / API-key auth is **always registered** (`authnimpl/registration.go:57`) and is unaffected by `auth.basic`; the login *form* is separate again (`disable_login_form`). So "SA tokens still work" is not evidence that basic auth is on.

181. **`${var:regex}` formatting escapes `/` as `\/`, which MetricsQL rejects** (`422 cannot parse string literal: invalid syntax`) — enough to break every panel filtering on a slash-bearing label value. ✅ Use plain `$var` for multi/All inside `=~` matchers: Grafana sends `(v1|v2)` with only regex specials escaped. ⚠️ **Validation must use Grafana's exact interpolated string, not hand-substituted values**, or this whole class of bug is invisible to the check.

182. **Two Grafana edit gotchas worth knowing before you claim a dashboard was scrubbed or diffed.** (a) A dashboard patch can remove `annotations.list[i]`, but **org annotations are separate objects** deleted via `DELETE /api/annotations/<id>` — verify a text scrub with a `jq tostring|match` over the live JSON, not by reading the panel. (b) Grafana **drops `"value": null` on threshold base steps and empty `"targets": []` on save**, each a 13-byte length delta — so a committed-vs-live byte comparison reports a difference that is purely cosmetic.

183. **Compare a committed dashboard against the live copy WITHOUT dumping either into context: per-panel `tojson|length`, an order-independent codepoint sum (`tojson|explode|add`), and a position-weighted hash per target expression** — computed via the API with `jq` on one side and in Python on the other. That reduces a whole dashboard to a few numbers per panel and still localises any real difference. ⚠️ Expect the two cosmetic deltas from #182.

184. **With no image renderer available, validate every panel of a dashboard in ONE call: `POST /api/ds/query` with every panel expression (template variables substituted, instant), plus a `jq` filter returning frame count and first value per `refId`.** Verify a full-JSON upload by comparing `tostring|length` of `panels`/`fieldConfig`/`templating` live vs local. ⚠️ Grafana's backend expands `$__rate_interval` for `/api/ds/query` when the query carries `interval`/`intervalMs`, so that macro can be sent literally — but **dashboard variables must be substituted by hand** as `(v1|v2)`. ⚠️ Do **not** test a multi-target per-pod panel at 7 d in one `ds/query` (see #200).

185. **Two Grafana operational facts that cost a cutover.** (a) Leaving `server.root_url` unset makes `appUrl` `http://localhost:3000/`, so every share link and alert link is wrong; setting it changes the config checksum, which restarts a `Recreate`-strategy Deployment **once per environment** — budget that, and check whether a sibling variable with the same value already exists in the module before adding one. (b) The SSO-settings API (`/api/v1/sso-settings/<provider>`) is **server-admin only**, so a live experiment needs admin basic auth: when simulating "basic auth off", **PUT the settings BEFORE disabling basic auth and restore the environment BEFORE deleting them**, or you lock yourself out of your own test.

## Exporting Cloud Monitoring and Cloud SQL

186. **`stackdriver_exporter` applies `starts_with` to EVERY `metrics-prefixes` value, even complete-looking metric names — so your prefix list silently expands.** v0.19.0 `collectors/monitoring_collector.go:386`. A 17-prefix Cloud SQL/Redis set expanded to **31 descriptors**: a connection-count prefix also matched its `by_application` and `by_state` variants, a disk-bytes prefix also matched `by_data_type`, `database/up` also matched `uptime`, and a CPU prefix also matched `cpu_utilization_main_thread`; a broad `memory/` prefix matched 5 types each. A cold scrape made **48 API calls** (17 descriptor + 31 time-series). ⚠️ The descriptor cache removes the **discovery** calls, not the time-series calls — and prefixes execute concurrently, so 17 prefixes do not multiply single-request latency serially.

187. **With `aggregateDeltas=false`, the exporter publishes DELTA Cloud Monitoring metrics as Prometheus GAUGES holding the newest 60-second delta, stored at scrape time when vmagent ignores source timestamps (see #188) — so `rate()`, `increase()` and `sum_over_time()` are all wrong on them.** `collectors/monitoring_collector.go:496-503`. In a Cloud SQL + Redis set the DELTA kinds are Redis `stats/*` and `cpu_utilization` (+ `cpu_utilization_main_thread`), `stats/evicted_keys`, `stats/reject_connections_count`, `stats/memory/system_memory_overload_duration`, and Cloud SQL `database/uptime`. ⚠️ **A CPU-seconds-per-60s-period value is NOT a 0-1 ratio — divide by 60.** Cloud SQL `cpu/utilization` *is* a true gauge ratio. ✅ Alert on `max_over_time(...[Nm]) > 0` style, or `avg_over_time`, never a counter function. CUMULATIVE descriptors (e.g. Query Insights aggregates) are genuine counters/histograms and `rate()` is correct there.

188. **The exporter emits only the NEWEST point per series **with its source timestamp**, but vmagent IGNORES target timestamps by default — the combination has a specific failure mode.** Exporter: `collectors/monitoring_collector.go:303-304,449-457`, `monitoring_metrics.go:217-226`. vmagent v1.148.0: `lib/promscrape/config.go:299-302`, `scrapework.go:1169-1171`. Net effect: samples land at scrape time, so there are **no lookback gaps** — but **a series whose source stopped keeps reporting its last value until it ages out**, and points repeat across scrapes (which is what makes `sum_over_time` double-count, #187). ⚠️ The chart's ServiceMonitor defaults to `interval: 10s` with `honorTimestamps: true` — **do not enable it**; write your own scrape object. ⚠️ If vmagent runs `replicaCount: 2` per shard, **both replicas scrape the same targets**, doubling every scrape-driven API cost (verified per pod via `/api/v1/targets`).

189. **Cost model for a `stackdriver_exporter` target: a warm scrape is one `timeSeries.list` per MATCHED DESCRIPTOR, billing is per series RETURNED, and the total multiplies by vmagent replicas per shard.** Descriptor listing (one call per prefix) happens only on cache refresh. Shards hash targets, so a 2×2 vmagent is 2 scrapers of a given target, not 4. Cloud Monitoring read pricing since 2025-10-02 is **USD 0.50 per million time series returned**; descriptor lists are free.

190. **Wiring the `prometheus-stackdriver-exporter` chart (5.2.0): the release name does not become the fullname, and the auth can be a direct workload-identity principal with no service account.** Fullname becomes `<release>-prometheus-stackdriver-exporter` unless `fullnameOverride` is set, and the selector label is `app.kubernetes.io/name=prometheus-stackdriver-exporter` (port `http`/9255) — both bite when writing a scrape selector. The auth pattern that works with no GSA and no SA annotation is a project IAM member on `roles/monitoring.viewer` for `principal://iam.googleapis.com/projects/<NUM>/locations/global/workloadIdentityPools/<PROJECT>.svc.id.goog/subject/ns/<ns>/sa/<sa>`.

191. **Cloud SQL Query Insights metrics arrive under a DIFFERENT monitored resource than the rest of the Cloud SQL set, with a different identifying label — and the latency metric is a real histogram.** They land as `…cloudsql_instance_database_…insights_aggregate_*` with `resource_id` (not `database_id`), plus `user`/`database`/`client_addr`, **primary instances only**. `insights/aggregate/latencies` is a CUMULATIVE DISTRIBUTION exported as a genuine histogram (buckets are powers of 4 µs: 1, 4, 16, …), so `histogram_quantile(sum by (le,user)(rate(...)))` is correct; `lock_time` is a cumulative counter. ⚠️ The descriptors carry `client_addr` but it is **empty behind the Auth Proxy**, so it never reaches the TSDB — do not build a dashboard variable on it.

192. **Cloud SQL Postgres publishes NO `max_connections` metric to Cloud Monitoring** (only the MySQL variant exists), so a connection-saturation alert must render the configured per-environment limit into the rule and divide by `sum by (database_id)` of the `num_backends` series — which carries a **per-database** label including the admin and any branch databases. ⚠️ Related trap in the same family: where `storageAutoResize` is on, `disk/utilization` sits at **0.97-0.98 by design**, so a `>0.9` disk alert fires permanently.

193. **Memorystore Redis CPU: `cpu_utilization_main_thread / 60` is the real saturation signal, not total CPU.** `stats_cpu_utilization` carries `relationship=parent|child` and `space=user|sys`; child (forked background-save) series are 0 normally and are separate rusage, so summing all and dividing by 60 gives cores. Main-thread CPU equalled ~99 % of total on every instance measured — it is the analogue of ElastiCache's `EngineCPUUtilization`. ⚠️ `num_backends_by_application` reports `application=Unknown` for asyncpg backends and is useless for attribution; use `num_backends` by database.

194. **`postgres_exporter` on Cloud SQL PG17: the scrape role MUST have `pg_read_all_stats` (via `pg_monitor`), or two collectors silently undercount.** Without it, PG17 **NULLs** `state`/`wait_event`/`xact_start`/`query_start` in `pg_stat_activity` for other users (`pgstatfuncs.c:621-640`), so `collector/pg_stat_activity.go`'s join on `state` drops them; and `pg_stat_statements` NULLs `queryid` (`pg_stat_statements.c:1791-1830`), so everything collapses to `queryid=unknown` and is deduped. The common claim that "`pg_stat_*` views need no grant" is **wrong for this use**. ⚠️ Cloud SQL patches the admin-option check (`pg_has_role(...,'MEMBER WITH ADMIN OPTION')` returns true where vanilla `acl.c:5283` would say false), so the superuser role can grant `pg_monitor` even though `pg_auth_members` shows `admin_option=f`. ⚠️ Chart 8.2.0 **refuses to render without a non-empty password** unless `passwordSecret`/`passwordFile`/`datasourceSecret` is set (`templates/secrets.yaml:1-12`) — for IAM auth via a proxy, feed a placeholder through `passwordSecret`. ⚠️ The exporter opens **2 connections** (`collector/instance.go:58` + `exporter/server.go:79`) and has no reserved slot on Cloud SQL (`reserved_connections=0`), so `pg_up` goes 0 **exactly at** `max_connections` — alert on saturation from the Cloud Monitoring counter, not from the exporter.

195. **Cloud SQL Postgres slow-query logging exposes extended-protocol BIND VALUES in full unless `log_parameter_max_length=0`.** PG17 `tcop/postgres.c exec_execute_message` calls `errdetail_params`, which emits `DETAIL: Parameters` and skips **only** when the flag is 0; the Cloud SQL default is **-1** (unlimited), range -1..1073741823, **no restart required**. Any client using the extended protocol (asyncpg always does) that binds emails or user content therefore leaks them into the log the moment `log_min_duration_statement` is enabled. ⚠️ `log_parameter_max_length_on_error` defaults to 0 but does **not** protect duration logs. ⚠️ Statement text with **inline literals** (a BI tool on a replica) is not covered by the flag at all. ✅ Also useful: `log_min_duration_statement`, `log_lock_waits`, `track_io_timing` and `pg_stat_statements.track` are no-restart flags, while `pg_stat_statements.max` and `track_activity_query_size` require a restart; `pg_stat_statements` being in `shared_preload_libraries` does **not** mean the extension is created in your DSN's database. ⚠️ Basic Query Insights **does** support read replicas (GA 2021-06-17); only *enhanced* Enterprise Plus Insights excludes them — do not confuse instance edition with feature enablement.

## Kubernetes metric plumbing

196. **For kube-state-metrics label metrics, pod labels require the explicit `--metric-labels-allowlist`, so a new high-cardinality pod label is INERT for metrics until someone adds it there.** Verified by counting `by(__name__)` every series carrying the label columns: only `kube_pod_labels` had them. Everything else in a typical pipeline is label-blind — an explicit-relabel pod scrape carries only the fields it names, the cAdvisor node scrape has no pod labels, managed-Prometheus pod monitors have no `fromPod` target labels, and cost-allocation/resource-usage export is a separate opt-in. ⚠️ **This cuts both ways**: it is why a new label is safe to add, and why a dashboard built on it stays empty until the allowlist ships. ⚠️ **An "the label has no series" observation is an ALLOWLIST fact about one cluster, never a portable claim.**

197. **The kube-state-metrics series is `kube_pod_status_container_ready_time` — SINGULAR `container`.** The plural form has zero series. A review bot flagged the singular as wrong; that was a false positive. Pair it with `kube_pod_status_scheduled_time` to get per-pod startup time, which is the metric that still works when the pull-duration metric is measuring a lazy mount (`learnings-gke.md`).

198. **`kubelet_image_pull_duration_seconds` is an ALPHA histogram whose only discriminating label is an `image_size_in_bytes` BAND — there is no image name — and bands only appear after a pull of that size since kubelet start.** Measured per node: **21 series per band** (19 buckets + sum + count), so a large-pool node showed 84 series across 4 bands and a smaller node 63 across 3. On a ~470-550 node fleet that is ~30-46 k series, ~3-4 % of a 1.1-1.3 M active-series TSDB. ⚠️ Because there is no image label, **attributing a large pull requires a join** of `kube_pod_container_info` against recently created pods plus an out-of-band size lookup (`crane`), and an agent/workload filter **cannot** be applied to the size-band panels at all. ✅ Read-only proof path before enabling: `kubectl get --raw /api/v1/nodes/<n>/proxy/metrics` for the per-node series count, and a TSDB query for current active series.

199. **There is no off-the-shelf per-image size metric for a managed-Kubernetes + cloud-registry stack (surveyed 2026-10-05).** kube-state-metrics' custom-resource-state **rejects the core group `""`** (so `Node` is out) by design, and its node store has no image metrics; the registry's own Cloud Monitoring surface has only a per-repository size gauge; a popular security operator has no size metric; and the kubelet metric is band-only (#198). The nearest config-only option is a generic JSON exporter against the registry list API (the size field is a JSON string, which the exporter's `ParseFloat` handles) — but its auth needs a static service-account key, not workload identity.

200. **Two VictoriaMetrics query-shape traps that produce a wrong number or an OOM.** (a) `increase()` over a range that **starts before collection began** counts each kubelet's lifetime counter as one spike (a first point of ~4 k pulls), and is transient for one range-length after enabling a new scrape — do not read the first day as a real rate. (b) A single `/api/ds/query` carrying **5 parallel 7-day range queries, each a per-pod join** of three KSM series, OOM-killed a 16 Gi `vmsingle`; the same expressions at 24 h with a 90 s step were fine. ✅ Evaluate the per-pod join **once per panel** (e.g. `count_values` on a bucket index) and ramp **24 h → 2 d → 7 d one query at a time** while watching `process_resident_memory_bytes`.

201. **Where container logs go to a cloud logging service rather than Loki, ALL pod labels are attached to every log line as `labels."k8s-pod/<key>"` — with dots in the key's prefix rewritten to underscores and the slash kept.** So `agents.x-k8s.io/claim-uid` becomes `k8s-pod/agents_x-k8s_io/claim-uid`. Labels added **after pod start** (e.g. on adoption) appear on later lines within seconds — verified on a real pod where lines before adoption lack the new label and lines after have it, which makes the label a usable **time boundary** in log queries. There is no label-cardinality limit on that path. ⚠️ Log-based metrics are a separate question: a pipeline with no `labelExtractors` does not forward these labels into its log-based metrics.

## Application telemetry

202. **To get structured per-request fields onto a server's own ACCESS log line, write them into the request scope BEFORE forwarding the response-start event, and attach the field-promoting component as a LOGGER-level filter on the access logger.** Two version-pinned facts make it work on uvicorn 0.44.0: each request task gets a **fresh `contextvars.Context`** (`httptools_impl.py:296`, `h11_impl.py:257`), and the access line is logged **inside the same `send`** (`httptools_impl.py:483` / `h11_impl.py:481`) — so the write must precede `await send`. ⚠️ Before such a change, uvicorn's access logger keeps uvicorn's own plain-text handler with `propagate=False` (`uvicorn/config.py:98`), i.e. unstructured output; **naming that logger in the app's `dictConfig` drops that handler** (`logging/config.py:909`) and lets the app's structured handler take it. ⚠️ Known gaps to declare rather than discover: a server-level 503 under a concurrency limit **skips the middleware entirely**, so a pipelined request inherits its predecessor's fields; a different cloud provider path may use a plain `logging.Formatter` and drop the fields; and the access **message** still holds the raw path and query string. Budget the volume — measured **~+230 B per record**, ~50 GB/month per environment at ~40 rps.

203. **OpenTelemetry JS SDK API facts that silently export NOTHING when got wrong** (verified in `node_modules` at sdk-logs 0.223.0 / sdk-trace 2.12.0 / api-logs 0.223.0): the Logs API method is `Logger.emit(record)` (there is no `emitLogRecord`); `SimpleLogRecordProcessor`'s constructor takes an **options object** `{exporter}` — passing the exporter positionally exports nothing and only surfaces as a global-error-handler line; `LoggerProvider`/`TracerProvider` have **no** `addLogRecordProcessor`/`addSpanProcessor` (pass `processors`/`spanProcessors` to the constructor); `Logger.emit` calls `onEmit` then `_makeReadonly()`, so a processor **may** mutate in place during `onEmit`; `LogRecordImpl.body` is a prototype accessor over `_body`; and `Span` has public own fields, so `Object.create(proto) + Object.assign` clones work. ⚠️ **`recordException` puts `exception.message`/`stacktrace` in span EVENTS, not span attributes — a redactor that only scrubs name and attributes leaks them.**

204. **A vendor "mask" hook may be a single option with a fixed signature, and a near-miss option name is silently ignored.** Verified on LangFuse (`langfuse-core@3.39.2` `lib/index.d.ts:7126`, `lib/index.mjs:883,1307`; `@langfuse/otel@5.13.0` identical): the option is `mask`, signature `(params: {data: any}) => any`, applied to input and output; a **throwing** mask makes the SDK substitute `'<fully masked due to failed mask function>'` (so failures are visible, which is good). ⚠️ There is **no `maskInput` option** — a config using it is ignored and the raw data is sent. Confirm a redaction option's exact name in the pinned `.d.ts`, not in a blog post.

205. **On VictoriaMetrics' OTLP ingest, metric names are only SANITIZED (dots → underscores) — no unit suffix and no `_total` is added.** Verified: `worker.tasks.completed` → `worker_tasks_completed`; `http.server.request.duration` → `http_server_request_duration_count`/`_bucket`. So an OTel counter created as `email_send_total` lands as `email_send_total` verbatim, and a dotted name stays dotted-turned-underscored — **pick the name you want in the TSDB at creation time.** Resource attributes become labels: `service_name`, `service_instance_id`, `deployment_environment_name`, `scope_name`.

206. **`sum(last_over_time(x[W]))` over an exporter whose series carry a `pod` label double counts after every exporter pod replacement — collapse the pod label with `max by` BEFORE summing.** `last_over_time` ignores staleness, so the replaced pod's series survives next to the new one for the whole window. Measured on a stackdriver_exporter Cloud SQL `num_backends` connection-saturation rule: 5 exporter replacements in 7 days, the naive ratio peaked at exactly **2x** the deduplicated one and would have paged once at a computed 113%. ✅ `sum by (database_id) (max by (database_id, database) (last_over_time(x[15m])))`. Rules already of shape `max by (...)` are safe. Complements #109 (why the window is long) and #46 (pod churn). ✅ Validate a VMRule before merge with `kubectl diff -f` on a dev cluster: the VM operator admission webhook parses annotation templates and rejects an undefined template func (negative control).
