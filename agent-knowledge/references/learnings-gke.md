# GKE Platform Learnings

See also: `learnings-workload-debug.md` (debugging a workload ON a cluster — probes, startup budgets, drains; this file is the cluster PLATFORM underneath it), `learnings-terraform.md` (how these knobs are expressed in `google_container_node_pool` and what a plan does or does not tell you), `learnings-observability.md` (what the kubelet/cAdvisor pipeline will and will not report about these nodes), `learnings-network-policy.md` (in-cluster policy, versus the VPC-level rules here), `learnings-agent-sandbox.md` (gVisor/RuntimeClass workloads that these node-pool facts constrain).

GKE **cluster-platform** facts: node-pool capacity arithmetic, upgrade mechanics, VPC/subnet design, and the quota/API surfaces that decide them. Every entry is GKE or provider behaviour verified at a named version. Environment-specific pool names, sizes and censuses belong in `orgs/<org>/` notes, not here.

## Capacity arithmetic — allocatable, reservations, quota

1. **Apply the GKE memory-allocatable sliding scale to MEASURED node capacity, never to the machine type's ADVERTISED memory — the advertised figure overshoots the reservation by ~0.3–0.4 GiB.** The scale is **25 % of the first 4 GiB, 20 % of the next 4, 10 % of the next 8, 6 % of the next 112, 2 % above 128 GiB, plus a 100 Mi eviction-hard threshold**; the input must be `kubectl get node -o jsonpath='{.status.capacity.memory}'`. Validated **exactly** against two live pools: `e2-standard-4` (capacity 15.62 GiB → allocatable **12.96 GiB**) and `e2-standard-8` (31.35 → **27.73**), both reconciling with live kubelet `configz` `kubeReserved.memory`. **To predict allocatable for a machine type you do NOT yet run:** estimate its measured capacity from hypervisor overhead, which scales with **total advertised RAM, not vCPU** — so a same-RAM analog already running (`e2-highmem-4`'s 32 GB matches `e2-standard-8`'s 32 GB) gives a high-confidence estimate, while a RAM size with no analog needs linear extrapolation of overhead and is **much** lower confidence. **Say plainly when the target figure is still an extrapolation.**

2. **`kubeReserved.ephemeral-storage` tracks the node pool's `diskSizeGb`, NOT the machine type — so a machine-type-only swap leaves the ephemeral reservation unchanged.** Confirmed on COS_CONTAINERD nodes: 60 GB disk → **27 Gi reserved (45 %)**, 120 GB disk → **48 Gi reserved (40 %)**. `diskSizeGb` is an independent per-node-pool setting. Consequence for a "give the workload more room" change: resizing the machine family buys RAM/CPU and **zero** ephemeral headroom; the disk is a separate edit.

3. **`gcloud compute regions describe --format='table(quotas…)'` reports `E2_CPUS` usage as a stale `0.0` even with thousands of e2 vCPUs live — use the general `CPUS` metric as the binding quota check.** Confirmed with `E2_CPUS usage=0.0, limit=2400` against ~3,472 live e2 vCPUs across two node pools, while `CPUS` was populated correctly and matched reality. The family-specific usage field cannot be trusted from this API; do not plan a fleet expansion against it.

## Upgrades and the autoscaler

4. **Surge-upgrade nodes are created ABOVE the node pool's cluster-autoscaler `totalMaxNodeCount` — they are NOT clamped by it.** Verified empirically: a pool with `totalMaxNodeCount=750` whose three MIG target sizes summed to exactly 750 had **751** GCE instances while an `UPGRADE_NODES` op ran at `maxSurge=1 / maxUnavailable=0`. With `maxUnavailable=0` and zero autoscaler headroom a clamped surge would **deadlock the upgrade permanently**; instead 547 of ~750 nodes had already converted. GKE public docs state neither way (the upgrade-strategies page caps only *parallelism* at `maxSurge+maxUnavailable ≤ 100` for Standard, 20 for Autopilot). **Consequences: do NOT size `maxSurge` against spare autoscaler headroom, and do not treat a pool sitting at its ceiling as a reason to skip raising it. DO size it against regional CPU/GPU quota, which surge nodes really do consume.**

5. **An autoscaling pool's upgrade has a CONVERGENCE THRESHOLD, and surge size is the wrong lever below it — raising `maxSurge` makes it strictly WORSE.** The pool's `version` field stays at the **old** version until enough nodes convert, so every autoscaler-created node during that window is **born stale** and joins the upgrade queue. Measured: `maxSurge=1` on a 751-node pool ran **7 h at 203 % `NODES_COMPLETE` with zero net progress**; raising to `maxSurge=20` went to **−4.8 target nodes/min**, because each batch evicts N nodes' worth of pods, the autoscaler replaces that capacity with old-version nodes, and the loop **amplifies with batch size**. What worked: **cut the churn first** (park idle workloads), let the pool settle, apply the config, then re-trigger at a moderate `maxSurge` on a quiet cluster — conversion hit ~180–330 nodes/hr and the **pool version flipped mid-run**, after which autoscaler nodes arrive already-converted and the effect becomes self-reinforcing. **Manual drain does NOT help** — the replacement still comes from the autoscaler at the old pool version (verified 3×). Watch for CSI mount pods in `kube-system` with **no `ownerReferences`**, which block a drain without `--force`.

6. **A PVC expansion is TWO-PHASE and the second phase needs a POD RESTART — the deploy reports success while the headroom it was meant to add does not exist.** After the resize the GCP disk grows but the filesystem does not: the PVC shows `spec=450Gi / status.capacity=400Gi` with conditions `Resizing=True` and `FileSystemResizePending=True` ("Waiting for user to (re-)start a pod to finish file system resize"), and `df` **inside the pod** still reports the old size. **Fix: delete the pod.** On restart `df` reflects the new size and the conditions clear. **Verify every PVC resize with `df` inside the pod PLUS `status.capacity` — never with the deploy's exit code or `spec` alone.**

## VPC and networking design

7. **Four GKE VPC-design errors that survive a plausible-looking plan — all four were caught by an adversarial review, none by reasoning.** (a) **GKE ≥ 1.29 Standard DEFAULTS to a GKE-managed Services range at `34.118.224.0/20`, consuming ZERO VPC space** — do not carve a custom Services secondary range without a concrete requirement (one such carve burned a whole `/20` for nothing). (b) **Subnet primary-range EXPANSION MUST BE CONTIGUOUS**: expanding a `/20` to a `/19` consumes the *immediately following* `/20`, so whatever you park there is what blocks the expansion — reserve the **adjacent** block, not a convenient nearby one. (c) **LoadBalancer health-check source ranges are FOUR, not two**: `35.191.0.0/16`, `130.211.0.0/22`, `209.85.152.0/22`, `209.85.204.0/22` — and probes hit **TCP 10256** for `externalTrafficPolicy=Cluster` or the `healthCheckNodePort` for `Local`, **not the service port**. (d) **`ip-masq-agent`'s `nonMasqueradeCIDRs` matches DESTINATIONS, not pod sources** — with a non-RFC1918 pod range (RFC 6598 `100.64.0.0/10`) GKE may SNAT unexpectedly, so set `default_snat_status` explicitly and `private_ip_google_access=true`. **Also: a "VPC primary CIDR" DOES NOT EXIST in GCP** — VPCs have no enclosing range, only subnets do; writing one into a design invites someone to create it as a subnet and collide with every child range.

8. **RFC 6598 `100.64.0.0/10` is supported and recommended as a privately-used public Pod secondary range on GKE Standard — but you then own the SNAT policy EXPLICITLY.** Either retain node SNAT plus Cloud NAT, or disable default SNAT and configure Cloud NAT for the **primary and secondary** ranges. This is the positive form of #7(d): the range choice is fine, the silent default is what bites.

9. **A firewall DENY scoped to the pod range must sit at a HIGHER priority NUMBER than 1000, because GKE auto-creates `gke-<cluster>-<hash>-all` at priority 1000 and GCP resolves EQUAL priority in favour of DENY.** Putting the deny at ≤ 1000 severs pod-to-pod traffic cluster-wide. Verified against the `google` provider 6.12.0 schema alongside two adjacent facts worth keeping: `google_compute_firewall.destination_ranges` has **no provider-side restriction to EGRESS** (the schema says only "IPv4 or IPv6 ranges are supported"), so an **INGRESS** deny scoped by `destination_ranges=[pods_cidr]` is valid; and `router_nat`'s `subnetwork.source_ip_ranges_to_nat` is a **SET**, not a list, so a `tftest` assertion comparing it to `["PRIMARY_IP_RANGE"]` fails with *"LHS and RHS values are of different types"* — use a `for` expression with `contains()` + `length()`.

## Tooling

10. **`crane` fails with `docker-credential-desktop not found` on a machine without Docker Desktop — isolate the config rather than installing Docker.** `export DOCKER_CONFIG=<empty dir>; echo '{}' > $DOCKER_CONFIG/config.json`, then `crane auth login -u oauth2accesstoken -p $(gcloud auth print-access-token) <registry>` before any `crane manifest`/`crane pull` against Artifact Registry.

11. **⚠️ "Private GKE blocks master→node on non-standard ports, so add a firewall rule for your webhook" is NOT universally true — CHECK BEFORE ADDING ONE, or you ship an inert resource.** Two cluster properties each independently remove the need. **(a) A PSC-style private control plane:** when `controlPlaneEndpointsConfig.ipEndpointsConfig.privateEndpointSubnetwork` is a `gke-<cluster>-<hash>-pe-subnet` **whose `ipCidrRange` IS the `masterIpv4CidrBlock`**, that CIDR is a **PSC endpoint subnet, not a source of node-bound traffic**. **(b) `konnectivity-agent` running in `kube-system`:** the apiserver reaches in-cluster endpoints through a tunnel the **agent opens OUTBOUND from the nodes**, so control-plane→node traffic never transits a VPC ingress rule at all. **Confirming signature: there is NO `gke-<cluster>-<hash>-master` firewall rule and ZERO rules sourcing the master CIDR — and webhooks work anyway. The ABSENCE is the tell, not the problem.** ✅ **DECISIVE EMPIRICAL PROOF, reusable on any cluster and independent of which mechanism is responsible: find an EXISTING admission webhook already served on the port in question with `failurePolicy: Fail`, and show a RECENT SUCCESSFUL WRITE through it** — e.g. a `ValidatingWebhookConfiguration` serving on `:9443` against a Service in another namespace, with `managedFields` timestamps from today on objects it guards. With `failurePolicy: Fail`, a blocked port would have failed those writes **closed**; they succeeded, so the port is reachable. That one check replaces the entire mechanism argument and is what justified **dropping** a drafted firewall resource rather than shipping a duplicate.

12. **Check `gcloud container operations list --location <region>` BEFORE attributing any post-deploy error to a PR — a node/master auto-upgrade produces noise that reads exactly like a regression.** One overlap produced, within hours: AMQP client `RobustChannel._on_close` RuntimeError floods (broker pods rescheduled), apiserver **429 "storage is (re)initializing"**, sandbox pods recreated wholesale, and `NodeNotReady` / image-streaming `UNAUTHENTICATED`. None of it was the deploy. The auto-upgrade sequence is visible (master first, then pools, each with its own timestamp), so the correlation is checkable in one command — and it is far cheaper than bisecting a PR. Pair it with a list of the estate's **known pre-existing error noise** so a post-deploy log scan has a baseline to subtract.

13. **⚠️ A CSI driver's `hostPath` block cache is charged to NO POD, so it fills the node disk invisibly and kubelet then evicts the only evictable workload.** Mechanism: the mount pod caches into a `hostPath` on the node boot disk with the driver's DEFAULTS (for JuiceFS: `cache-size` 100 GiB, `free-space-ratio` 0.1 unless overridden in the mount options). Because `hostPath` usage is charged to no pod, the kubelet summary shows **per-pod ephemeral ≈ 0** while node `fs.used` climbs — and `eviction-hard` on node filesystem is typically **10 %**, i.e. the cache keeps filling **right up to the eviction line**, at which point kubelet evicts the workload pod. ✅ **Attribution proof that works per node: `node.fs.used − imageFs.used − Σ(pod ephemeral)` should match the driver's own cache-size metric** (scrape it read-only via `kubectl get --raw /api/v1/namespaces/<ns>/pods/<mount-pod>:<port>/proxy/metrics`) to within an OS baseline of a few GiB — it matched on 6/6 nodes. ⚠️ **The fix is on the MOUNT OPTIONS (`--cache-size` well under disk headroom, `--free-space-ratio` above kubelet's threshold) or a separate cache disk — NOT on the evicted pod's ephemeral limits**, which is where a naive reading of the eviction event points. Also budget for the image layer: a large container image can itself hold `imageFs` at 48-66 GiB on a 120 GB boot disk.

## Control-plane internals

14. **GKE's `resourceVersion` is HLC-like and its FIRST 10 DIGITS are epoch seconds — which turns it into a usable "was this object written after time T?" clock.** Verified on a live cluster: decoding the first 10 digits of `<resource-version>` as epoch seconds matched the dashboard's wall clock. ✅ Use `min(resourceVersion)` per kind, compared against a known switch time, to prove **every** object of that kind was rewritten after a storage-version migration — particularly when a migration tool's annotations were later wiped by an application that re-applies objects. ⚠️ This is an observed GKE encoding, not a documented Kubernetes guarantee: treat it as a cheap corroborating signal, not as the sole proof, and re-check it on a cluster you have not measured. ⚠️ Whatever time you compare against must be the real switch moment (e.g. a webhook Service's `creationTimestamp`), never "now" — comparing against `now` makes every object look stale. **See also `learnings-agent-sandbox.md`** for storage-version migration and the companion stale-discovery-cache trap; the corroborating-signal limitation above is canonical HERE and must not be restated as proof anywhere else.

15. **Removing a `BackendConfig` `spec.iap` block does NOT disable IAP, and setting `spec.iap.enabled=false` on a backend that had a custom OAuth client FAILS the whole backend sync.** From `kubernetes/ingress-gce` master: `pkg/backends/features/iap.go EnsureIAP` returns early when `Iap == nil` (so the backend keeps IAP on), and `pkg/backendconfig/validation.go validateIAP` **skips the secret lookup when `enabled=false`**, leaving the desired client id `""` → `switchingToDefault` → `Cannot switch to default OAuth once IAP credentials have been set`. ⚠️ The error returns **before** `backendPool.Update` and before `EnsureSecurityPolicy` (`pkg/backends/syncer.go ensureBackendService`), so a `securityPolicy` declared in the same BackendConfig is never attached — the failure is wider than the IAP field. Upstream fixes for this closed unmerged. ✅ **Working path: drop the `iap` block (the security policy attaches, IAP is untouched), then disable IAP out of band** with `gcloud compute backend-services update <k8s1-…> --global --iap=disabled`; expect ~2-3 minutes for the edge to converge. ⚠️ While the BackendConfig still has an `iap` block, ingress-gce **re-enables IAP on the next resync**, so the manual disable must follow the block's removal. A brand-new Service (fresh backend service) is the declarative alternative.

16. **A GKE ingress backend's default `timeoutSec` is 30, and that — not the identity-aware proxy in front of it — is what cuts a long UI query.** Verified on two environments' backends; the cut therefore **survives** removing the proxy. Check `timeoutSec` before attributing a 30-second ceiling to anything else.

17. **Cloud Armor: a `rate_based_ban`'s conform action is TERMINAL, and header lookups are CASE-INSENSITIVE — so "the capital-A header rule is dead" is wrong, and a lower-priority catch-all may be unreachable.** The widely-used Terraform module hardcodes `conform_action = allow` (v6.0.0 `main.tf:354`), and LB logs confirm it: `enforcedSecurityPolicy.priority=<rate rule>` with `outcome=ACCEPT RATE_LIMIT_THRESHOLD_CONFORM`. So two rules of the form `has(request.headers['Authorization'])` and `!has(...)` **partition all traffic**, and any lower-priority rule below them never evaluates. ⚠️ The rules-language docs say CEL header map keys are lowercase, which reads as "a capital-A rule matches nothing"; **measured** over 2 h of real prod LB logs (400 samples) the capital-A rule enforced 377 vs 23 on its complement — the lookup is case-insensitive and the partition is real. ✅ Verify shape: `gcloud logging read 'resource.type="http_load_balancer" AND jsonPayload.enforcedSecurityPolicy.name="<policy>"' --format='value(jsonPayload.enforcedSecurityPolicy.priority,…outcome)' | sort | uniq -c`. ⚠️ LB log reads hit a 60-request/minute quota when chunked in parallel — run them serially; and per-IP logs mix load balancers, so the same priority number can mean different rules.

18. **A WAF rule's match set must MIRROR THE APP'S auth-bypass shape, prefix-for-prefix and exact-for-exact.** Real miss: a rule used `request.path.startsWith('/v0.1/<route>')` while the application exempts that route by **exact membership** in a set (unlike a sibling route, which is in a *prefix* set) — so the rule's widened rate budget admitted `/v0.1/<route>/<anything>` and `/v0.1/<route>Evil`, which the app does **not** exempt and which therefore reach a real auth lookup instead of a cheap rejection. ✅ **Invariant to assert one-directionally: every path the WAF rule admits must be auth-exempt.** ✅ Cheap offline check: lift the app's exempt route/prefix sets out of the source with a regex, evaluate the CEL predicate in Python over a case list, and **re-run against the OLD expression as the negative control**. Fixed by using equality on both slash variants.

19. **With GKE image streaming enabled, `kubelet_image_pull_duration_seconds` measures the LAZY MOUNT, not byte transfer — so a size-reduction win is invisible on that metric in a streaming cluster.** Measured: 10-20 GB "pulls" with median ~5 s / p95 ~18 s where streaming is on, versus real transfer times where it is off. ✅ In a streaming environment, measure the win as **scheduled → container-ready time** (`kube_pod_status_container_ready_time - kube_pod_status_scheduled_time`) instead; size-cut wins show on pull duration only in non-streaming environments. ⚠️ Check the flag per environment before comparing dashboards across them.
