# LLM Provider & Agent-Runtime Learnings

See also: `learnings-agent-workflow.md` (dispatching and orchestrating the agents these models run inside), `learnings-code-review.md` (grading a finding about key handling or a swallowed provider error), `learnings-agent-sandbox.md` (the pods these agents execute in), `learnings-observability.md` (alerting on provider error rates: the rule that a check asserting on a metric your stack does not emit is permanently vacuous applies to per-attempt failure counters), `learnings-helm-ci.md` (the scheduled workflows that run these agents).

Runtime behaviour of LLM SDKs (litellm / lmi), provider APIs and the agent loops built on them: key plumbing, fallback chains, model identity and content-policy refusals. Vendor claims are pinned to the version noted.

1. **A `SecretStr` API key does not survive a config round-trip, so a key, or even an `os.environ/VAR` *reference*, stored in a model spec is LOST wherever that config is serialized and re-read.** `model_dump(mode="json")` masks the field to `**********` via the model's secret serializer, and an agent that boots from a deploy-baked config gets the mask, not the value: a silent 401 or a silent fallback, not an error. ✅ **Carry the ENV VAR NAME as a plaintext pointer in an `extra_params` field instead** (it is a pointer, not a secret, so it survives `model_dump`), leave `api_key = null`, and resolve it to a `SecretStr` **at model-build time** in a function that returns a COPY, popping the pointer so the SDK never sees an unknown kwarg and raising loudly when the env var is unset. ⚠️ Apply it at **every** config-driven model build site in the process (main loop, heartbeat, completion review, each compaction path): one missed site is one silent fallback. The no-leak property rests entirely on the field being `SecretStr`: prove it with a negative control that assigns a plain `str` and must raise a serialization error.

2. **A model-identity-specific parameter must be EXCLUDED from whatever set a "repoint to another model" helper carries forward, or the new model inherits the old one's credential.** A heartbeat repoint to an OpenAI model inherited the Anthropic key pointer of #1 through `carried_params`, and the resolver dutifully injected the Anthropic key into the OpenAI call → 401. The discriminator is **identity-specific vs request-shape**: temperature and max-tokens are request shape and should carry; anything naming a credential, provider or model id is identity and must not. Caught by a correctness lens, a review bot and a behavioural repro independently, which is itself the signal that the carried-params set is under-specified.

3. **An LLM fallback chain may only advance on ONE error class, so a single provider HTTP 400 collapses the entire safety net.** Observed with lmi: it advances on `ModelRefusalError` (an HTTP 200 with `finish_reason=content_filter`), the log line is literally `Advancing from <a> to <b> after ModelRefusalError`, but a provider **400** raises a base LLM exception that is FATAL to the turn, with no advancing line at all. Every model further down the chain is never tried. 🔎 **Read the absence of the advance line as the diagnosis**; and when you configure a chain, verify which error classes it actually advances on rather than assuming "fallback" means "on any failure".

4. **Two different providers will content-block the SAME authorized red-team prompt on cyber-safety grounds, and the two refusals look nothing alike: do not read either as a key, access or model-availability bug.** On one run the primary refused with an HTTP **200** + `finish_reason=content_filter` (an in-band content refusal), and the fallback returned HTTP **400** with a cyber-policy code pointing at an access-program application. Both are policy, not infrastructure. ✅ The remediation is account-level (cyber-permissive safeguards on one vendor, a program enrolment on the other), so **triage it as a policy ticket, not an outage**, and note that #3 means the 400 ends the turn outright.

5. **Every Claude model id uses DASHES, never dots (`claude-mythos-5-1`, not `claude-mythos-5.1`) and a dotted id fails as a 404 `NotFoundError` on the first dispatch, which reads like an access problem rather than a typo.** litellm knows the dashed ids natively and `get_llm_provider` routes `anthropic/<dashed-id>` correctly. ✅ **Verify any Claude model id against the current-models table (the `claude-api` skill), never from memory**: the cost of being wrong is a 404 that you will spend hours attributing to entitlements. ⚠️ A correct id can still 404/403 if the account is not entitled to a restricted model, so fixing the dashes does not by itself prove access.

6. **Registering a model with a litellm-style catalog requires declaring its CAPABILITY flags, or the provider adapter rejects parameters your agent always sends, and the failure is neither retryable nor fallbackable.** An agent sending `tool_choice` + `reasoning_effort` hit `UnsupportedParamsError` from the provider adapter because the registration omitted `supports_function_calling` / `supports_tool_choice` / `supports_reasoning`. ⚠️ Two traps: it is **masked wherever the bundled catalog already has an entry**, so it bites only on the deployments that lack one; and registration **skips when the model is already present**, so you cannot use it to patch an incomplete upstream entry.

7. **A poller that decides "done" from CONVERSATION state instead of job status turns a 17-second server-side failure into a full-timeout hang.** A single-chat driver judged completion by "the agent reached a blocking message" + "no pending tasks", never reading the sandbox rollout status; a turn that fails server-side never emits a blocking message, so the driver returned IN_PROGRESS until the per-run timeout expired: burning a 4-hour budget on a turn that died in 17 seconds. ⚠️ **Raising the timeout therefore makes it worse, not better.** ✅ A completion predicate must have a path to FAILURE that does not depend on the happy-path signal; test it by failing the first turn and asserting the driver returns within seconds.

8. **A shared provider ORGANIZATION quota means a dev batch job can starve production, and the alert will fire in both environments at once, which is the discriminator.** Dev and prod sandboxes using the same provider org share the per-model TPM pool; a ~300-pod dev batch switching models pushed the shared pool to its ceiling and prod 429s began in the same 10-minute window. 🔎 Confirm from the 429 BODY, which names the organization. ⚠️ Compounding it: a failure callback that fires on **every retried attempt** makes the error RATE wildly overstate user impact, one environment showed a 32% "failure" rate while its actual rollouts were 2 failed out of 1,161. Alert on outcomes, not attempts, or at minimum carry a volume floor.
