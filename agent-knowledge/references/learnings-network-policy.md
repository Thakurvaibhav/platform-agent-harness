# Network Policy and Cilium Learnings

Fleet NetworkPolicy strategy, self-managed Cilium (GKE + EKS), Istio-ambient coexistence, FQDN egress.

See also: `learnings-operators.md`, `learnings-agentgateway.md`, `learnings-istio.md`, `learnings-gke.md` (VPC-level firewall and subnet design, versus in-cluster policy here)

## Fleet substrate and provider facts

1. **GKE Dataplane V2 cannot be enabled on existing clusters** -- authoritative GCP docs state it can only be enabled at cluster creation time. Managed-Cilium fleet standard would require cluster replacement/blue-green. If replacement is out of scope, self-managed Cilium on existing GKE clusters is the only viable path. **Scope correction (#30): the create-time restriction is specific to Dataplane V2. Google-managed Calico can enable vanilla NetworkPolicy on an existing non-DPv2 cluster with rolling node recreation; the earlier 'only viable path' wording is too broad.** The DPv2 restriction is documented on the GCP concepts page (`docs.cloud.google.com/.../concepts/dataplane-v2`), not the how-to page.

2. **GKE self-managed Cilium has two modes; the tidy first-party one IS the full-takeover one**: Mode B (official GKE install section) = `gke.enabled=true, ipam.mode=kubernetes, routingMode=native, nodeinit.{reconfigureKubelet,removeCbrBridge}=true` -- preserves GKE-style PodCIDR allocation but takes over the CNI datapath and mutates kubelet/node state. Mode A (generic-veth chaining) preserves existing netd IPAM/routing but is documented only generically (not as a supported GKE integration) and has no persistence remedy when GKE node reboot/upgrade reinstates the default CNI (the warning is on `/en/stable/installation/taints/`, NOT the chaining page). Key insight: "B is better documented" and "B does the dataplane takeover" are the SAME fact -- its NodeInit DaemonSet solves the reboot problem precisely because it owns the CNI. The full GKE Helm shape also includes `cni.binPath=/home/kubernetes/bin` and `nodeinit.enabled=true` in `/en/stable/installation/k8s-install-helm/`. The original generic-veth investigation found no community evidence on GKE VPC-native; that is an unverified negative, not proof of impossibility. Chaining's L7 proxy limitation matters when `toFQDNs` is required. **Persistence correction (#33): NodeInit re-owns the CNI, but does not prove a zero fail-open window on reboot or upgrade.**

3. **EKS Cilium chaining capabilities and limits**: AWS VPC CNI keeps ENI/IPAM/pod interface + base routing; Cilium attaches eBPF after pod networking for L3/L4 policy/LB/observability (`cni.chainingMode=aws-cni, cni.exclusive=false, enableIPv4Masquerade=false, routingMode=native`). Official docs warn advanced features are limited in chaining, especially L7 policy/proxy redirects; transparent encryption is unsupported (cilium#15596). Existing pods must be RESTARTED after enabling chaining before Cilium policy applies. The AWS-managed VPC CNI add-on can overwrite daemonset fields on update cycles -- use add-on `configurationValues` for aws-node settings, keep AWS VPC CNI's own NP enforcement disabled when Cilium owns policy. Managed add-on reconciliation can overwrite EKS-managed fields on roughly 15-minute/update cycles. A full-takeover alternative replaces aws-cni IPAM with Cilium ENI IPAM rather than overlay; this is a separate design choice, with the acceptance and rollback costs in #35.

## Istio-ambient coexistence

4. **Cilium + Istio-ambient + kube-proxy + autoscaler coexistence facts** (Cilium v1.17+): (1) KEEP kube-proxy, `kubeProxyReplacement=false` -- Cilium-Istio integration requires `socketLB.hostNamespaceOnly=true` if KPR is on, else Cilium socket-LB rewrites connections inside the pod socket BEFORE ztunnel redirection sees them, breaking ambient. (2) `cni.exclusive=false` so Cilium doesn't remove the Istio CNI chained plugin. (3) No Cilium L7 on ambient workloads -- Cilium HTTP proxy + Istio mTLS = split-brain connection failures. (4) CRITICAL: ANY NetworkPolicy on an ambient-enrolled pod MUST allow TCP/15008 (HBONE) or it severs ztunnel tunnel traffic. (5) agent-not-ready taint applies at node-CREATE time only; existing clusters need new born-tainted node pools + cordon/drain/migrate; taint key MUST start with `ignore-taint.cluster-autoscaler.kubernetes.io/` or autoscaler refuses scale-up. (6) Policy Audit Mode allows traffic and logs would-drops (`hubble observe -t policy-verdict`); per-endpoint via `cilium-dbg endpoint config PolicyAuditMode=Enabled`; RESETS on cilium pod restart; NOT recommended for production steady-state; distinct from `enable-policy=never` (no enforce AND no verdicts). (7) Tetragon+Cilium dual-eBPF same-node is vendor-aligned but NOT conformance-documented; combined kernel/BTF floor unpinned -- validate in pilot. Node auto-provisioning pools may not inherit the agent-not-ready taint; verify inheritance or disable that provisioning path. The coexistence research covered Cilium v1.17/v1.19 docs. An incorrect socket-LB ordering can make ambient treat all traffic as direct-to-workload. The shared sandbox-runtime knob and residual node-lifecycle window are detailed in #14 and #33.

5. **Policy-plane boundary with ambient**: For ambient-enrolled mTLS traffic, Kubernetes/Cilium NetworkPolicy still applies to the encrypted L4 HBONE tunnel entering/leaving Istio-managed pods, but Cilium has NO visibility into actual source/destination workload identity or L7. Therefore: Cilium/K8s NP owns pod selection, non-mesh/plaintext ingress, health-probe/link-local exceptions, infra boundaries, and coarse default-deny; Istio AuthorizationPolicy owns service-to-service identity/L4 and ALL L7 for ambient workloads. Cilium L7 policy requires removing the workload from ambient. HBONE uses TCP/15008. Removing a workload from ambient or disabling its redirection is required before applying Cilium L7 policy to that workload; in-pod `nsenter`/`ss` debugging follows ztunnel's `setns`/HBONE model.

## FQDN egress

6. **`toFQDNs` / FQDN deny REQUIRES `l7Proxy=true`** (cilium#7109): the in-agent DNS proxy is gated by the L7 proxy flag -- FQDN policy is silently ineffective with `l7Proxy=false`. Tension: ambient coexistence posture is "no Cilium L7 on ambient workloads," but `l7Proxy` is a GLOBAL agent flag. Non-ambient workloads on dedicated pools CAN use FQDN deny (the DNS proxy runs in the Cilium agent, not in the workload), but squaring global-on with ambient-off needs per-pool design. Do not claim FQDN deny works with `l7Proxy=false`. Per-pool agent configuration or DNS-rule scoping still requires pilot validation; the global flag does not itself establish safe coexistence with ambient.

7. **FQDN egress default-deny landscape**: Solo Enterprise for Istio ztunnel-native L4 egress matches CIDR only (not FQDN), and CIDR-deny has the same churning-anycast-IP problem as IP allowlists. FQDN/hostname egress in Istio ambient requires the L7 waypoint egress gateway (extra proxy hop) and wildcard hostnames are unsupported. NET: Cilium `toFQDNs` (with `l7Proxy=true`) is the cleanest FQDN-deny primitive for Kubernetes. **Correction to the historical wildcard claim: `DYNAMIC_DNS` adds wildcard support through a ServiceEntry labelled `istio.io/use-waypoint`; the client must be ambient-enrolled (#25).** The June 2026 research described the ztunnel-native Enterprise L4 feature as alpha, with namespace+CIDR matching. Ambient OSS does not implement `REGISTRY_ONLY` and has no OSS default-deny egress (maintainer correction in istio/istio discussion #53021); do not treat that knob as a boundary. A scoped Cilium deployment on an isolated workload pool is lighter than a fleet-wide deployment but does not provide one fleet-wide policy plane.

## Principles

8. **Failure MODE matters as much as steady-state coverage**: A VPC firewall is fail-CLOSED (cloud fabric, no fail-open window); a node-local CNI policy (Cilium/Calico) is fail-OPEN during node lifecycle (agent not yet running). For untrusted-egress workloads, replacing a firewall with a CNI at equal rule coverage is a failure-mode REGRESSION. Keep the fail-closed backstop until replacement proves zero fail-open window. The acceptance gate is fail-closed parity, including lifecycle events, before retiring the cloud-firewall backstop; equivalent steady-state rules alone do not establish it (#33, #35).

9. **Cilium+Istio+ambient adoption has THREE stacked maturity layers -- don't launder L1 evidence as L3 proof**: L1 Cilium+Istio coexistence (sidecar era) = well-trodden. L2 Cilium+ambient/ztunnel specifically = thin but documented. L3 = Cilium primary CNI via IPAM takeover on existing non-DPv2 clusters + ztunnel + Tetragon (triple eBPF) = near-pioneering, no public reference; native Cilium-ztunnel datapath integration is an open upstream epic at low completion. General form: external evidence for layer N does not validate layer N+1. The Cilium v1.17+ ambient demo recommends chaining with `cni.exclusive=false`, not primary-CNI takeover. The deeper combination is existing GKE Standard non-DPv2 plus ztunnel and Tetragon. The recorded native-integration investigation identified cilium/cilium#38548 at roughly 9% completion; this is a historical maturity observation, not current issue status.

## Enforcement evidence chain

11. **A NetworkPolicy object existing — or even network-policy-shaped CRDs being present — is not evidence of enforcement; the enforcement chain has several independent links, and confirming the object exists proves only the first one.** The full chain is: provider enforcement switch enabled -> the enforcing agent's DaemonSet present, Ready, AND running with enforcement actually on in its own container arguments -> policy objects exist -> a policy's selector actually matches both ends of the traffic in question. Two ways this fails silently and still looks fine: (1) a managed CNI's own policy-enforcement add-on setting can be disabled while policy objects are still accepted by the API server and enforced by nothing, and CRD groups can impersonate an enforcer — an observability-only DaemonSet can ship CRDs in the same API group as a real network-policy engine, so "matching CRDs are present" is not proof an enforcing agent exists at all; (2) an enforcing agent's own container can run with enforcement explicitly disabled in its startup flags while a sibling container's environment variable independently reads as "enforcing" — that variable is inert while the flag is off, so a config dump shows "enabled" and nothing is enforced, with the relevant CRDs present too. Second-order trap: a NetworkPolicy drop is indistinguishable on the wire from an mTLS/authorization rejection, so any probe claiming to prove one enforcement layer must first rule out the other. Third-order trap: deny logs written by a node-local agent are sometimes written to a file a container-log collector never tails (pod-discovery-plus-file-matcher configs read container stdout/stderr only) — so deny events can exist and still be unqueryable anywhere. Concrete signatures: GKE `addonsConfig.networkPolicyConfig.disabled: true`; `kube-system/netd` is not an enforcer, and observability-only `tetragon/tetragon` can ship `cilium.io` CRDs `tracingpolicies`/`tracingpoliciesnamespaced`. AWS VPC CNI's `aws-eks-nodeagent` can run `--enable-network-policy=false`, `--enable-policy-event-logs=false`, and `--enable-cloudwatch-logs=false` while `aws-node` has `NETWORK_POLICY_ENFORCING_MODE=standard` and the CRDs `policyendpoints`, `clusternetworkpolicies`, and `applicationnetworkpolicies` exist. A policy selecting neither end of a probe is not a confounder. Budget for operational debugging practice before making a previously dormant policy layer load-bearing.


## Cilium version-specific risks

12. **An open, attacker-triggerable memory-DoS in Cilium's `toFQDNs` DNS cache affects `>=1.19.5 <1.20.0` and 1.18.8/1.18.11, with no fix as of this writing (`cilium/cilium#47128`).** A workload that resolves continuously-fresh subdomains under a `toFQDNs` policy grows `cilium-agent` RSS unboundedly — measured growth from roughly 100 MiB to several GiB within hours in a lab, and a similar trajectory over a few days in production. The retainer is the FQDN DNS cache's lookup-by-time index; the CLI command to clean the cache drops the majority of stale entries but releases no memory — only an agent restart or endpoint deletion actually frees it. DNS resolution latency and throughput degrade as the cache grows. Any workload that is not fully trusted (or that resolves attacker-influenced hostnames) can trigger this deliberately with a pattern like `<random-subdomain>.attacker-controlled-domain`. If `toFQDNs` cannot be avoided for such a workload, budget for cache-size alerting and a restart/rotation plan; the cleanest mitigation is designing DNS resolution out of the untrusted workload entirely rather than relying on an FQDN allowlist to contain it. The issue was opened 2026-07-13; the no-fix/open status is a historical finding and must be rechecked before use. Recorded measurements were 103 MiB to 3.4 GiB in 12 hours in a lab and 350 MiB to 8 GiB over 66 hours on EKS. `pkg/fqdn.(*DNSCache).lookupIPByTime` retained 75% of live heap; `cilium-dbg fqdn cache clean` removed more than 94% of entries without releasing memory. DNS throughput fell from 195 to 50 queries/s, p99 reached 1.4–1.9 seconds, and clients hit 5-second timeouts. At the stated versions, this supplanted the closed restart-outage issue as the leading FQDN-policy risk (#19).


## FQDN egress (continued)

13. **GKE `FQDNNetworkPolicy` and Cilium NetworkPolicy resolve conflicting rules in opposite directions — GKE's is union-only (a controller's own allow-rule can never be overridden by anything else), Cilium's deny always wins regardless of policy type.** Per GKE's own documentation, verbatim: "When both a FQDNNetworkPolicy and a NetworkPolicy apply to the same Pod, egress traffic is allowed as long as it matches one of the policies. There is no hierarchy between egress NetworkPolicies" — meaning any additional allow-rule from a third-party controller or operator only ever widens access; nothing you add can subtract from it. GKE `FQDNNetworkPolicy` has further limits worth knowing before relying on it: caps at 50 resolved IPs (100/hostname quota), matches wildcards only one level deep, does not follow CNAMEs, is not enforced with any L7 protocol information, cannot target a ClusterIP or headless Service as a destination, and discards results from any DNS resolver that isn't in-cluster. Cilium, by contrast, states (v1.19 docs, verbatim): "Deny policies take precedence over allow policies, regardless of whether they are a Cilium Network Policy, a Clusterwide Cilium Network Policy or even a Kubernetes Network Policy." Consequence: if a third-party controller creates its own allow-NetworkPolicy on pods you don't fully control, only a Cilium deny policy can override it — plain Kubernetes NetworkPolicy and GKE `FQDNNetworkPolicy` are both purely additive and cannot. The recorded comparison was pinned on 2026-08-02. GKE requires Dataplane V2 plus kube-dns/CloudDNS, explicitly states Cloud Service Mesh is unsupported, and ignores non-cluster resolvers from `resolv.conf`; `*.example.com` does not cover `eu.api.example.com`. Cilium's overriding primitive is `egressDeny`. At Cilium v1.19, Helm defaults `l7Proxy` to `true`, so `toFQDNs` works by default where no ambient workloads impose coexistence constraints.


## Sandboxed-runtime interactions

14. **Cilium's socket-level load-balancing (`socketLB`) breaks ClusterIP access for any sandboxed runtime with a userspace network stack — gVisor, Kata, KubeVirt — and `kubeProxyReplacement=true` force-enables it regardless of `socketLB.enabled`.** Socket-LB translates a ClusterIP to a pod IP inside the `connect()`/`sendmsg()` syscall via a cgroup/connect eBPF hook; a sandboxed runtime's userspace netstack (e.g. gVisor's `runsc`) never triggers that hook, so a sandboxed pod simply cannot reach ClusterIP services when socket-LB is active. The deciding code path (Cilium v1.19.5, `pkg/kpr/kpr.go:47-49`): if `KubeProxyReplacement` is true, `EnableSocketLB` is forced true regardless of its own setting. With `kubeProxyReplacement=false`, `socketLB.enabled` defaults false and ClusterIP DNAT happens in the packet path at the veth instead — which a sandboxed runtime's netstack does traverse. Cilium documents this gVisor interaction by name and ships the fix: `socketLB.hostNamespaceOnly=true` bypasses socket-LB for non-root network namespaces and falls back to the tc-based load balancer at the veth. Worth checking on any cluster running sandboxed workloads under self-managed Cilium. At v1.19.5 with `kubeProxyReplacement=false`, the configmap template wires `bpf-lb-sock` directly from `socketLB.enabled`, with no other coupling; kube-proxy iptables performs DNAT on the veth path. `socketLB.hostNamespaceOnly=true` is also the ambient-coexistence knob (#4); setting it unconditionally protects sandboxed workloads if kube-proxy replacement is later enabled. The chart describes it as enabling Istio routing rules. cilium/cilium#15626 (eBPF masquerading breaking Kata/gVisor ClusterIP) closed in 2022: pilot-check `bpf.masquerade`, but do not cite that closed issue as an unresolved risk.


## Tooling gotchas (continued)

15. **The long-standing assumption that `kind` clusters don't enforce NetworkPolicy is false as of `kindest/node` v1.36.1 / kind 0.31.x — `kindnet` enforces it.** Verified with a negative control rather than by reading docs: a pod in a namespace with default-deny plus an egress allow restricted to one TCP port got connection timeouts to a raw IP and to the cloud metadata IP, and DNS resolution failures for hostnames; an identical pod in a namespace with no policy at all got a normal HTTP response from the same raw IP. This means NetworkPolicy designs can be smoke-tested locally in `kind` today — don't skip local testing on the old assumption that `kind` can't enforce it. Re-verify against the specific `kindest/node` tag in use, since enforcement support is a relatively recent addition and may not be present on an older pinned node image. The recorded allow was TCP/3000 only. `1.1.1.1` and `169.254.169.254` returned curl exit 28 (timeout), hostnames returned exit 6, and the no-policy control returned HTTP 301 from `1.1.1.1`. These controls make gateway-containment experiments locally testable.


## Egress allowlists for untrusted workloads

16. **When choosing an egress-allowlist mechanism for short-lived or untrusted workloads, weight debuggability above policy-language elegance — a denial is indistinguishable on the wire from an application bug, and the pod is often gone before anyone investigates.** Compare candidate mechanisms on whether a denial is answerable *after the fact*, by someone who doesn't know the enforcement stack: an L7 proxy's access log is structured, ships through the normal logging pipeline, and typically carries authority/SNI, response code and flags, upstream host, and a request id — a named-host deny is one query and survives pod deletion. A kernel-level eBPF flow-observability layer is often absent until specifically deployed — no dashboards, no alerts, no retention on day one — and its verdicts are frequently a live stream requiring an exec into an agent on the right node, so a short-lived pod's flows are gone the moment it's deleted. Node-local deny-log files are frequently not tailed by a container-log collector at all, and managed-dataplane policy logs can land in a cloud logging product with no dashboard wired to it. Net: inventory what your own observability stack already ingests before picking a mechanism — the right answer is a property of what you already run, not of which mechanism is more elegant. Include response-code details as well as response flags in proxy logs; request/connection counters are ordinary metrics. A live gRPC verdict stream without retention cannot explain a deleted pod's denial after the fact.

17. **A literal no-DNS pod is not expressible in Kubernetes — the closest implementable form needs explicit `dnsConfig.options`, or every failed lookup blocks for roughly ten seconds.** The API server's own validation (`pkg/apis/core/validation/validation.go`, `validatePodDNSConfig`) rejects `dnsPolicy: None` with an empty nameserver list, requiring `dnsConfig` with at least one DNS nameserver whenever `dnsPolicy` is `None`. The implementable pattern is `dnsPolicy: None` plus a `nameservers` entry pointing at an address that will never answer (an IANA documentation-range IP works) plus `dnsConfig.options` setting a short `timeout`, a low `attempts` count, and `ndots: 0`, with port 53 denied by NetworkPolicy as the actual block. Without those options, every `getaddrinfo` call blocks for the resolver's default timeout-times-attempts (glibc's default is roughly ten seconds total) instead of failing fast — turning a policy meant to prevent DNS exfiltration into a pod that hangs on every accidental hostname lookup. One concrete configuration is `nameservers: [192.0.2.1]` with timeout `1`, attempts `1`, and ndots `0`; glibc defaults are 5 seconds times 2 attempts. The recorded validation path is `pkg/apis/core/validation/validation.go:4280-4287`, which emits 'at least one DNS nameserver when dnsPolicy is None'.

18. **A CONNECT forward proxy that trusts the SNI/authority on the tunnel it just opened is not sufficient to contain hostile code — HTTP/2 connection coalescing lets a client reuse that connection for a different, unauthorized destination with no detectable mismatch.** RFC 7540 SS9.1.1 permits a client to reuse one TLS connection for a different `:authority` whenever the server is authoritative for both, and shared-SAN CDN certificates make this common in practice; SS9.1.2 only says a non-authoritative server *should* respond 421, it isn't required to. The proxy sees a legitimate SNI matching a legitimate certificate that also happens to cover the disallowed destination, and a later HTTP/2 stream on that same connection silently carries a different `:authority` the proxy never validated. The equivalent hole exists on HTTP/1.1 via a CDN edge's inner `Host` header. Closing it requires the proxy to actually terminate TLS and inspect the real request authority per-request — SNI-based routing/allowlisting alone cannot detect this class of bypass, even though it is often assumed sufficient for "compromised but not actively adversarial" workloads. The earlier source search found no Envoy leaf-certificate-minting extension; treat that absence as unverified rather than a permanent impossibility. Squid `ssl_bump generate-host-certificates` is a mature TLS-termination option. A MITM-free alternative is plaintext-to-proxy plus `envoy.filters.http.dynamic_forward_proxy`, `auto_sni`, and `auto_san_validation`, but it works only when the HTTP client is controlled, not for hostile code. This coalescing hole is distinct from wildcard-authority DNS tunnelling (#23).

## Historical DNS-proxy risk and egress-gateway placement

19. **`cilium#35080` is CLOSED — do not cite it as a live risk at the v1.19 pin — but the structural concern survives the correction.** 35080 (3+ min DNS outage on agent restart with FQDN policies) closed 2024-11-12, labelled release-blocker/1.16, reported against v1.16.0–1.16.2, unaffected v1.15.9. At **1.19 the DNS proxy is still EMBEDDED in the cilium agent**, so an agent restart (upgrade, OOM, config change) still disrupts DNS for every pod on that node holding an FQDN policy — that is the stated motivation for **Standalone DNS Proxy** (alpha, 1.20+), whose docs say it "can continue to proxy DNS requests when the agent is down," implying the embedded one cannot. **Ask "what is the disruption window at 1.19", not "is 35080 unfixed".** These issue states and the 1.20+ alpha status are historical observations to recheck at the deployment version. Design corollary: if the FQDN allowlist lives in an **L7 forward proxy** instead of Cilium `toFQDNs`, `l7Proxy` stays `false`, no DNS proxy is engaged, and this whole problem class is *designed out* rather than mitigated (see #16, #23).

20. **Cilium Egress Gateway is SNAT, not an allowlist — but do not dismiss it either.** It masquerades matching traffic to "selected, predictable IPs associated with gateway nodes"; its destination selectors are **CIDRs**, so it cannot express "only these hostnames." `toFQDNs` is a **separate** feature (DNS-proxy / L7-gated), not an egress-gateway property. Where it *is* the right tool: it makes the **cloud-firewall** gate precise. Cloud firewall rules match on source address and pod IPs are ephemeral, so the rule is otherwise unwritable and you fall back to coarse "this whole subnet has no route out"; egress gateway gives a deterministic source identity at the cloud layer — which is also how a managed SWP / AWS Network Firewall attributes traffic to an estate. **Placement is counterintuitive**: if a kernel gate already restricts sandboxes to the egress proxy only, sandbox traffic never leaves the cluster directly, so the egress gateway applies to the **proxy/broker's** egress, not the sandbox's. Cost: gateway nodes become a chokepoint with their own HA characteristics; interaction with `socketLB.hostNamespaceOnly` and sandboxed runtimes is **UNVERIFIED** — pilot it.

## Transparent and explicit proxy design

21. **Per-hostname synthetic VIPs for egress allowlisting are usually OVER-ENGINEERING — single-gateway-IP + SNI/Host steering is the right default.** The *only* thing per-host VIPs buy is identifying the intended hostname for **non-TLS, non-HTTP TCP** (plain Postgres, Redis, SSH, SMTP) where there is no SNI and no Host header; TLS (via SNI) and HTTP (via Host) a gateway can already identify against **one** shared IP. Costs for that narrow case: VIP IPAM + collision validation, append-only-forever allocation, VPC route plumbing for the VIP CIDR, unallocatable wildcards, and a scannable cross-tenant range. **A useful design signal: a per-host VIP requirement disqualifies BOTH evaluated off-the-shelf candidates (agentgateway and iron-proxy)** — both do single-IP + SNI/Host recovery, and iron-proxy returning one shared `proxyIP` for every intercepted A query is the **correct design, not a defect**. Dropping VIPs also removes the need for kernel transparent capture (`SO_ORIGINAL_DST`/TPROXY) entirely, since the resolver already steers traffic to the gateway address — ordinary listeners suffice. Correct fallback for hostname-less protocols: put them in the same explicit IP/CIDR tier already used for UDP, or require their TLS variants (Postgres `sslmode`, Redis TLS), returning them to the SNI path. **General form: when one requirement disqualifies every existing implementation of a mature category, suspect the requirement before concluding you must build.**

22. **If you nonetheless build DNS→synthetic-VIP steering, four properties are load-bearing and each fails silently.** The mechanism — a controlled authoritative resolver returns a per-hostname VIP and the gateway recovers the intended host from the VIP it was contacted on — is the way to get **transparent egress capture without a mesh, a sidecar, or in-pod iptables**: it works for non-TLS TCP where SNI does not exist and needs zero client cooperation (no `HTTPS_PROXY`).
    1. **GLOBAL map, not per-tenant.** Per-sandbox views at 10³ sandboxes × 10³ hosts = 10⁶ mappings and defeat client DNS caching.
    2. **STATIC + APPEND-ONLY.** A reclaimed/reassigned VIP means a client caching past TTL sends host-A traffic to a VIP now meaning host-B. TLS catches it via SNI cross-check, but **plain HTTP/Postgres is silently misrouted — a confidentiality bug.**
    3. **TENANT ENFORCEMENT AT THE GATEWAY**, on (authenticated sandbox identity, VIP). A kernel netpol admits the **whole** VIP range to every pod, so the resolver's per-tenant answers are **advisory only**; without gateway-side checks a hostile sandbox scans the range, reaches the union of all tenants' allowlisted hosts, and enumerates which hosts other tenants use.
    4. **NAMED DELIVERY MECHANISM.** VIPs are neither pod IPs nor ClusterIPs and **nothing routes them by default** — pick one explicitly: VPC route entry to gateway nodes / one Service per host with pinned `clusterIP` / Cilium LB-IPAM.
    - Gotchas: do **not** use `10.96.0.0/16` (conventional k8s Service CIDR — `ipBlock` becomes ambiguous); use a `100.64/10` CGNAT slice. **AAAA for an allowlisted name must return NOERROR/NODATA, not NXDOMAIN** (RFC 2308 — NXDOMAIN negates the **name**, not the type, so glibc/musl parallel A+AAAA resolvers treat the name as dead). Suppress or synthesize HTTPS(65)/SVCB records — `ipv6hints` and ECH inside them bypass the VIP. Wildcards cannot be statically pre-allocated (expand at config time or allocate-on-first-query and never reclaim), which collides with (2). IP-literal and SNI-less clients break by construction — an accepted functional limit.

23. **Explicit-proxy egress — three non-obvious mechanics, and two NetworkPolicy YAML traps nothing validates.**
    1. **Internal destinations are routing keys, not hostnames.** In an Envoy CONNECT forward proxy you can expose names like `llm.example` / `mcp.example` that exist **only** as `:authority` matches in the route table, routed to a `STRICT_DNS` cluster pointing at the real Service (e.g. `agentgateway.egress.svc.cluster.local`). Nothing ever serves an `.example` zone, no `hostAliases` needed, and **the sandbox needs no DNS to reach them**. External destinations use a separate `dynamic_forward_proxy` cluster resolved at request time — so the **proxy** pod needs kube-dns for both cluster types even though the sandbox needs none.
    2. **The proxy pod's own NetworkPolicy is the real confused-deputy control.** Its destination is by definition arbitrary internet, so the rule is `0.0.0.0/0` with `except` `169.254.0.0/16` (metadata + link-local), RFC1918, **and `100.64.0.0/10`** (CGNAT — EKS custom networking uses it). Without that except-list a sandbox aims the proxy at the metadata endpoint or in-VPC services. **Duplicate the same denial inside Envoy** so a broken CNI does not expose metadata.
    3. **A wildcard/suffix allowlist entry (`*.example.com`) reintroduces DNS tunnelling THROUGH the proxy's own `dynamic_forward_proxy` resolver** — the sandbox controls the left labels and Envoy resolves them. "No DNS in the sandbox removes DNS exfil" holds **only for exact-match authorities**. Log the full `:authority` (not the matched route/virtual_host name) or the exfil is invisible in the access log. Also: with CONNECT the `:authority` is `host:port`, so an allowlist entry `github.com` will **not** match `github.com:443` — match exact/anchored, normalise first, reject non-DNS characters (a real bypass came from a null byte defeating a naive `endsWith('.example.com')`).
    - **YAML traps**: (a) `namespaceSelector` and `podSelector` MUST be under a **single `to` list item** — a stray `-` before `podSelector` silently changes the meaning to "any pod in that namespace **OR** any pod anywhere with that label", a serious widening; (b) multiple `to` entries are a **UNION, not an intersection**, which is why a kube-dns allow still works alongside an `ipBlock` rule that excludes RFC1918 — it looks wrong, it is correct, **comment it**.

## Runtime deployment and ambient containment

24. **gVisor on EKS is NOT a blocker — the real delta is AMI ops cost, not capability; but the no-egress node pool is a genuine constraint on one install path.** `runsc` needs exactly: two binaries on `$PATH` (`runsc`, `containerd-shim-runsc-v1`), a containerd runtime handler entry (`[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]`), and a RuntimeClass. On AL2023 EKS nodes, bootstrap goes via `nodeadm` reading a NodeConfig from MIME-multipart userdata, so Karpenter `EC2NodeClass` userdata can merge the containerd fragment. Two install paths (AWS-authored guide, Jun 2026): (a) userdata shell script fetches the binaries at boot — ~10-20s boot overhead, minimal maintenance; (b) Packer custom AMI on the EKS-optimized AL2023 image — fast boot, but you own rebuild cadence for K8s **and** gVisor versions. **Non-obvious interaction: path (a) downloads over the internet at boot, so it is UNUSABLE on a node pool that deliberately has no default route** — exactly the untrusted-workload design where the sandbox subnet has no NAT/IGW. Such designs must bake a custom AMI or stand up an internal mirror; **the constraint is the no-egress node pool, not gVisor.** Also: gVisor will not run on Bottlerocket without a custom variant; requires x86_64/ARM64 on 4.14.77+ kernel; its KVM platform needs virtualization extensions EC2 nitro guests do not expose (the default non-KVM platform is unaffected — confirm the platform in a pilot). Contrast GKE, which ships a managed `gvisor` RuntimeClass + `sandbox.gke.io/runtime` node pools at zero maintenance.

25. **Istio egress waypoint + NetworkPolicy is a valid egress-control pattern, but it is NOT a drop-in alternative to a forward proxy for UNTRUSTED code — it forces mesh enrollment, and that is the whole decision.** The pattern is Istio's own recommendation over mesh-level `outboundTrafficPolicy`, and 2026's `DYNAMIC_DNS` resolution added real **wildcard** hostname support (`*.wikipedia.org`) via a `ServiceEntry` labelled `istio.io/use-waypoint` with `istio.io/waypoint-for: all` (egress targets are ServiceEntries, not Services — hence `all`). **The deciding mechanism**: ZTUNNEL performs the redirection ("traffic will be forwarded by ztunnel to that waypoint", applying to "any requests from any pods using the ambient data plane mode"), so **the CLIENT POD MUST BE AMBIENT-ENROLLED**. A non-mesh pod cannot address a waypoint directly — a plain TCP connection carries no original-destination metadata for the waypoint to route on. **Enrollment harms, for a hostile workload**: ztunnel is ONE PROCESS PER NODE serving every enrolled pod, so a sandbox that exploits or exhausts it crosses the tenant boundary; the sandbox receives a first-class SPIFFE SVID, i.e. an assertion of trustworthiness issued to code you assume hostile; the first-layer NetworkPolicy widens from one hole to HBONE `:15008` plus link-local; and istio-cni manipulates the pod netns. **The tempting trade**: capture is TRANSPARENT, which deletes the "proxy-aware HTTP(S) only" workload contract — Node `fetch` and proxy-unaware SDKs just work. **Tradeoff for untrusted code: weigh the structural enrollment exposure against transparent client compatibility.** Proxy-awareness can be addressed in the base image and documentation; enrollment exposure remains structural. **Open question if this is ever revisited**: the branch reintroduces a resolver (ambient DNS capture), and whether ztunnel's DNS refuses to recurse for UNREGISTERED names — i.e. whether the QNAME exfil channel stays closed — is UNVERIFIED and is the make-or-break test. See #18 and #23 for the forward-proxy branch this was weighed against.

26. **Containing an ambient-enrolled untrusted workload: use NETWORK POLICY for the namespace boundary, NOT Istio `AuthorizationPolicy` — AuthorizationPolicy is enforced BY ZTUNNEL, so using it to contain a workload whose adjacency to ztunnel IS the concern is circular.** NetworkPolicy is kernel-enforced below the app and is the actual boundary; AuthorizationPolicy is defence in depth. **What namespace isolation does NOT fix**: ztunnel is ONE PROCESS PER NODE shared by every enrolled pod, so the residual threat is a sandbox exhausting or exploiting ztunnel itself — no ztunnel-evaluated policy can prevent that — plus the workload holding a mesh SVID. Those residuals are bounded by a sandboxed runtime plus PSA `restricted`, so the mitigation narrows the gap a lot; **the remaining delta is availability/adjacency risk, not a lateral-movement hole.** **Cilium + ztunnel coexistence (verified 2026-08) needs five things**: (a) `kubeProxyReplacement=false` — otherwise Cilium's socket-LB rewrites the connection INSIDE the pod socket before ztunnel's redirect sees it and ambient treats all traffic as direct-to-workload; (b) `socketLB.hostNamespaceOnly=true`; (c) `cni.exclusive=false` so Cilium does not remove the chained istio-cni plugin; (d) **NO Cilium L7 policy on ambient pods** (Cilium's HTTP proxy + Istio mTLS = split brain); (e) NetworkPolicy on enrolled pods MUST allow `:15008` or HBONE is severed. **Convergence worth knowing**: `socketLB.hostNamespaceOnly=true` is ALSO required for gVisor/runsc, because socket-LB's cgroup/connect hook is invisible to a userspace netstack — two unrelated constraints, one knob (see #14, #24). **Historical maturity flag (2026-08)**: `cilium#38548` "Add support for ztunnel" was OPEN and PINNED since 2025-03-27 and unresolved in that review — coexistence at that review meant keeping the two out of each other's way, NOT native integration. Cilium-as-primary-CNI + ztunnel + a sandboxed runtime on the same nodes has little public precedent: **pilot it, do not assume it.**

27. **gVisor pods are subject to egress NetworkPolicy where normal pods are NOT — and simultaneously miss socket-level service translation.** `runsc` runs its own userspace netstack (gonet), so the host kernel's cgroup/connect eBPF socket hooks **cannot see socket creation inside the sandbox**. A normal pod gets NodeLocal-DNS/ClusterIP redirection in memory at the socket layer, bypassing `eth0` and egress NetworkPolicy entirely; a gVisor pod assembles real L3 packets out of `eth0`, so it IS subject to egress netpol AND it misses socket-LB translation. **Two consequences**: (1) the link-local `169.254.20.10` NodeLocal DNS needs an EXPLICIT netpol allow for gVisor pods but not for normal pods — a rule set validated on normal pods proves nothing here; (2) **any design that hands a gVisor sandbox a ClusterIP VIP (e.g. an egress-proxy Service) must be pilot-verified under self-managed Cilium** — socket-LB will not translate it and only tc/LXC-hook service translation would; the fallback is a node-IP `hostPort`. This is the same hook-invisibility that makes `socketLB.hostNamespaceOnly=true` a shared requirement (#26). (source: agent-sandbox `examples/policy/network-policy-management/dns_poc_walkthrough.md @79f31750`)

## CNI architecture and dependency checks

28. **Reference shape for self-managed Cilium on EKS alongside Istio ambient and an untrusted workload, with the reasoning each choice follows from.** Full self-managed Cilium CNI **replacing** the cloud CNI's IPAM (ENI IPAM chosen over overlay); **AWS VPC CNI chaining is rejected in this design because of the L7/FQDN gap** (#2, #3); a dedicated **born-tainted node pool** for the untrusted workload, since the agent-not-ready taint applies at node-CREATE time only (#4); **global `l7Proxy: true`** because FQDN policy is silently ineffective without it (#6) — **with mesh L7 policy prohibited on ambient workloads and the combination marked UNPROVEN pending a pilot**; `kubeProxyReplacement: false` and `cni.exclusive: false` for mesh coexistence (#4); and eBPF-observability-agent coexistence likewise UNPROVEN. **Pilot on the lowest-tier cluster first.** This is a candidate architecture, not an estate's adopted policy; managed L3/L4 enforcement plus a forward proxy is another option (#30). Note the whole shape is downstream of the precedence finding in #13.

29. **`ipBlock: 0.0.0.0/0` with `except: [RFC1918]` on a gateway/data-plane pod STRANDS EVERY IN-CLUSTER DEPENDENCY — and the dependency set is easy to enumerate incompletely, because each omission's failure signature points somewhere else.** Extends #23(2), which gives the except-list from the *confused-deputy* side; this is the cost side. For an agentgateway data plane the set is **at least**: (1) **kube-dns** — it resolves upstream hostnames on the client's behalf; (2) **the xDS dial back to the controller — without which the pod gets NO CONFIG AT ALL**; (3) any **extAuthz / extProc callout** service. **Each failure MISLEADS: no-DNS looks like a broken allowlist, no-xDS looks like a control-plane outage, no-callout looks like a token-service outage.** NetworkPolicy is union-of-allows, so each needs an explicit re-admit rule. **Do not enumerate by reading — apply the policy in a throwaway cluster and watch what breaks** (now cheap, per #15).

## Managed enforcement and rollout acceptance

30. **A managed NetworkPolicy dataplane you can enable IN PLACE is a third option between "no enforcement" and "self-managed-CNI takeover" — and on GKE it is the one that gets missed, because the DPv2 immutability rule (#1) gets over-generalized into "GKE cannot get NetworkPolicy without a rebuild".** Both are true at once and they are different products: **GKE Dataplane V2 is create-time only (#1), but the older Google-managed Calico NetworkPolicy addon can be turned on for an EXISTING non-DPv2 cluster** — `gcloud container clusters update --update-addons=NetworkPolicy=ENABLED --enable-network-policy` — at the cost of a rolling node recreation, not a cluster replacement. It has been GA since 2018, is **iptables-based rather than eBPF-primary** (so it does not contend with an eBPF observability agent the way a Cilium takeover does), and on EKS the native `aws-cni` path is the equivalent. **Price it honestly, though — "in place" is not "free":** enablement **recreates every node pool** via the provider's node-upgrade strategy (a rolling node replacement across the cluster, not a cluster rebuild), and GKE documents roughly **128 MiB + 300m CPU** of additional `kube-system` footprint. Two asymmetries to carry into policy authoring: **GKE-Calico includes pod ranges in `ipBlock` unless you exclude them, and DPv2 differs** — so an `ipBlock` rule is not portable between the two GKE dataplanes; and **disabling enforcement later removes the managed `ip-masquerade-agent`**, which changes pod-to-external NAT behaviour, so the rollback is not a clean no-op either. Both speak the **vanilla `networking.k8s.io/v1` API**, so *author vanilla NetworkPolicy only and avoid the vendor CRDs* (Calico `GlobalNetworkPolicy`) and the policy set stays portable across clouds. **The limit that decides whether this is enough: OSS Calico is L3/L4 only — no FQDN** (contrast #6/#7), so pod-to-external hostname containment still needs the L7 forward proxy or an egress gateway. **The generalization: before pricing a CNI replacement to obtain a policy primitive, enumerate the managed enforcement your provider will switch on in place — "the CNI does not enforce today" is a statement about a FLAG, not about a capability the platform lacks.** Constraints on ambient coexistence still apply unchanged: a policy on an enrolled pod must allow TCP/15008 and the health-probe link-local (#4(4), #26(e)).

31. **⚠️ Turning on a NetworkPolicy dataplane ACTIVATES every dormant policy object at once — inventory before you flip the switch, because on a never-enforcing cluster those objects were free to write and nobody validated them.** This is the operational consequence of #11: while the enforcement flag is off, `NetworkPolicy` objects are accepted by the API server and enforced by nothing, so they accumulate — preview experiments, copy-pasted templates, chart defaults left enabled — and **every one of them becomes live in the same instant**. Because NetworkPolicy is union-of-allows *but pod-selection is what triggers isolation*, a single stale object whose `podSelector` matches a workload flips that workload from "all traffic allowed" to "only what this stale object permits". **Pre-flip checklist: (1) `kubectl get netpol -A` and adjudicate every object — audit or delete the stale no-ops BEFORE enabling; (2) add explicit allows for the paths nothing declares; (3) enable on the lowest-tier cluster at real scale first, with the observability agent already running.** The exception list for step (2) is longer than people expect, and on GKE the addresses are specific: **HBONE `TCP/15008` ingress AND egress wherever pods are isolated** (#4(4)); the **ambient health-probe link-local `169.254.7.127/32`** plus its IPv6 equivalent on dual-stack; **Workload Identity metadata egress — `169.254.169.252/32` ports `988` and `987` on GKE ≥ `1.21.0-gke.1000`** (DPv2 differs, and dropping this is a fleet-breaker because every pod loses its cloud identity); **provider ingress/ALB health checks**; the node-local DNS link-local address; and hostNetwork/node-origin paths. Related fail-open at the other end: AWS VPC CNI's `standard` enforcement mode is **default-allow during pod startup until the policies are programmed**, so a pod can complete its first outbound calls before the policy exists — an enforcement gap distinct from the node-lifecycle one in #8.

32. **When a design doc claims "capability X is already covered by the service mesh", the review that matters is not whether the mesh is good — it is the RESIDUAL-EXPOSURE list, and there are eight standard entries.** The claim is almost never wrong; it is *scoped* wrong, and the correct edit is always the same shape: from *"in-cluster segmentation is covered by the mesh"* to **"covered for audited, mesh-ENROLLED, TCP traffic"**. Enumerate what falls outside that, because each item is a real path and each is invisible to the mesh's own telemetry: (1) **non-enrolled / opt-out namespaces and pods** — pods outside the mesh do not use a source ztunnel, so only destination-side policy applies; (2) **hostNetwork and node-origin traffic** — Kubernetes itself leaves hostNetwork-pod policy behaviour largely undefined; (3) **kubelet / health probes** — plaintext, node-originated, carrying no cryptographic identity, admitted via a link-local SNAT exception; (4) **non-TCP traffic** — ambient capture is TCP via ports 15001/15006/15008 inside the pod netns, so UDP and raw IP are simply not in the mesh's path; (5) **the waypoint source-identity shift** — once a waypoint is in the path the observed source identity becomes the waypoint's, not the client's, which silently changes what an identity-based rule means; (6) **any workload where ztunnel capture failed** — it fails to a working, unenforced datapath; (7) **missing default-deny AuthorizationPolicy** — with no AuthZ present the default is ALLOW, so "the mesh segments us" is false by default and true only where someone wrote the deny; (8) **L7 conditions at ztunnel** — it cannot enforce them; that requires a waypoint. **Two framing corrections that follow: the mesh is explicitly NOT a CNI and does not enforce or manage NetworkPolicy, so the two are not redundant layers but different enforcement points (host kernel vs mesh proxy); and pod-level L3/L4 default-deny is the artifact auditors ask for, which makes "we have the mesh instead" a defensible engineering answer but a weak compliance one.** (Istio 1.29 "Add workloads" / "L4 policy" / "Ambient and Kubernetes NetworkPolicy" / "traffic redirection"; Kubernetes "Network Policies" — "The two sorts of pod isolation", "NetworkPolicy and hostNetwork pods".)

33. **The `agent-not-ready` taint does NOT close the CNI-takeover fail-open window on node REBOOT or UPGRADE — it closes it only at node CREATE, and the residue is a NoSchedule-vs-NoExecute distinction plus a node-object-reuse case.** Refines #4(5) and #2, which establish that the taint is create-time and that a GKE reboot/upgrade reinstates the default CNI; this is the part that decides whether the window is acceptable. **New-node provisioning is genuinely clean**: only the CNI agent tolerates the taint and it is removed once the node is configured, so nothing schedules early. **The residual window is on an EXISTING node**: after a reboot or upgrade the provider can reinstate its default CNI, and the operator re-applies the taint as **`NoSchedule`, not `NoExecute`** — so **already-running pods are not evicted and keep running on the reinstated default dataplane with no policy enforcement** (`cilium#21594`). Separately, **preemptible/Spot recreation can retain the node object without re-applying the node-pool taint**, so the taint's protection is not guaranteed to survive the node's own lifecycle. **Do not write "NodeInit provably closes the fail-open window" into a design — it bounds it. Prove the width in a pilot** by rebooting a node with running pods and observing whether policy is enforced throughout, which is the acceptance test #8's fail-closed-parity gate actually demands.

34. **Enforcement STRENGTH and rollout COVERAGE are independent axes, and the mesh-global knob usually wins on coverage while losing on strength — so replacing it with NetworkPolicy silently trades a fail-closed default for a fail-OPEN one.** A mesh-global egress setting is *one field*: it applies everywhere and a namespace nobody has touched is still covered. **NetworkPolicy is per-namespace, so a namespace with no policy fails OPEN** — and the failure is invisible, because nothing reports "this namespace has no egress policy". A migration that reasons only about strength ("kernel enforcement beats a userspace proxy setting") therefore ships a coverage regression it never measured. **The fix is not to keep the weaker control — it is to replace its coverage GUARANTEE with an admission policy** ("every mesh-enrolled namespace must carry an egress NetworkPolicy"), so the guarantee moves from a global default to a gate. Generalizes past networking: **whenever you replace a global default with a per-object opt-in, the global default's implicit coverage is a thing you owned and are now deleting — name what re-establishes it, or accept the gap explicitly.** (Related: #31's other half, where a per-object control is dormant rather than absent.)

35. **Acceptance gates for a primary-CNI takeover, both clouds — the list is long because every item is a way the takeover looks successful while being broken, and the rollback is heavier than the install.** Persistence is the first gate and it is not one test: prove the node-init mechanism re-owns the datapath **through reboot AND drain AND autoscale-add AND provider auto-upgrade**, with **zero unmanaged-pod window and policy still enforced at every point** — a single reboot test passes trivially and proves almost nothing (see #33 for why the window survives the taint). Then: **a negative control on the mesh tunnel** — confirm HBONE/`15008` survives a test NetworkPolicy *and* that a deliberate 15008-deny actually breaks the harness, because a green result from a harness that cannot fail is vacuous; **both eBPF agents healthy after reboot with no attach/map collisions** if an observability agent shares the node (#4(7)); masquerading, DNS, and health probes; FQDN enforcement actually denying (#6); and **audit mode explicitly turned off** — Cilium's Policy Audit Mode allows traffic while logging would-drops and resets on agent restart (#4(6)), so a cluster left in audit reads as "policy applied, no drops". Cloud-specific gates: on **EKS**, prove the cloud CNI daemonset cannot race or flush routes on the new nodes, that managed-node-group create/update/recycle **keeps the `NoExecute` gate until the agent is ready**, and that **pod-IP renumbering is acceptable for stateful/long-lived connections**; note also that **self-managed Cilium on EKS cloud nodes is explicitly NOT AWS-supported — you own the support path** — and that the operator needs EC2 **ENI describe/create/attach/assign/tag** IAM privileges under `ipam.mode=eni`. On **GKE**, test **autoscaler scale-from-zero** and confirm **node-auto-provisioning pools inherit the gate taint, or disable NAP on those clusters** (#4(5)). **Rollback weight is the part designs understate: unwinding an IPAM + kubelet + bridge takeover means recreating the old CNI's capacity, unwinding ENIs/routes/rules, and renumbering every pod IP — materially heavier than a chaining rollback would have been, which is a cost of the takeover choice (#2), not a surprise.**

36. **An egress containment claim is only worth what its NEGATIVE controls prove — and there are five, each aimed at a different bypass.** "The gateway allowlists the declared hosts" is a statement about the happy path. Run instead: (1) **kill the gateway** — does traffic fail closed, or does the pod route around it; (2) **remove one entry from the allowlist** — does that specific host actually become unreachable, or was the allowlist never load-bearing; (3) **raw-IP HTTPS to an arbitrary address** — the hostname layer cannot see it (#7, and #18 for why even SNI checking is not enough against hostile code); (4) **UDP outside any declared range** — usually the forgotten protocol, since the whole design is reasoned about in HTTP terms; (5) **the cloud metadata endpoint** — the confused-deputy target (#23(2)). Everything *except* declared internal dependencies, DNS, and declared media ranges must fail. **The design corollary that makes this testable: express egress intent as ONE object per workload — selector + `httpsHosts` + `udpIpRanges` + `tcpPorts` + `internalDeps` + explicit `metadataAccess: deny` — and RENDER the proxy allowlist, the NetworkPolicy, any cloud-firewall backstop, and the dashboards/log queries from it.** Split across hand-maintained layers, the five probes above each test a different file and drift apart; rendered from one object, "what is this workload allowed to reach" has a single answer and the negative controls test the thing that is actually deployed.

## Port-scoped egress and live-policy drift

37. **A NetworkPolicy that allows `0.0.0.0/0` on a port list gates PORTS, NOT DESTINATIONS — and if the real domain enforcement is an OPT-IN proxy env var, any process that ignores proxy env vars egresses unfiltered.** Example shape for an untrusted-workload sandbox: `to: 0.0.0.0/0` on 443/80/21/20 plus an app range, with domain enforcement done entirely by a sidecar proxy reached via `HTTP_PROXY=localhost:3128` — **not** an iptables `REDIRECT`. **The env-var form is advisory: a subprocess, a statically linked binary, or any library that does not honour `*_PROXY` walks straight past it.** Compounding trap: a live `NO_PROXY` that excludes the very upstreams the control exists to meter means the workload's own process holds the credentials and bypasses the proxy, while only a *subset* of calls (a separate `*_NO_PROXY` for a child process) is forced through it for budget enforcement. **Run the five negative controls of #36 against this shape specifically, including (3) raw-IP HTTPS and (4) UDP.** Raw-IP HTTPS bypasses hostname checks on an allowed TCP port. The port-only description does not establish that UDP passes; check the rendered protocol rules and run the probe. ⚠️ **And verify this per environment before assuming prod is tighter: policy objects can be byte-identical across development, staging, and production** (verify by diffing `kubectl get -o yaml`), if they are identical, a development finding about the egress boundary **applies to production unchanged**.

38. **A hand-applied NetworkPolicy is invisible to your IaC and UNIONS with the declared ones — so "the repo says the policy set is X" is never the policy set.** A live object can carry a `kubectl.kubernetes.io/last-applied-configuration` annotation dated months earlier with **zero source anywhere in the repo**; Terraform will not remove an object it does not manage. **For a pod already isolated in that direction, k8s UNIONS the matching policies' allows, so an additional allow object can widen access** — which is why it never shows up as a connectivity failure and can sit undetected indefinitely. Selecting a previously unisolated pod can instead trigger isolation (#31), so inspect selectors before judging the effect. Two practical consequences: **(a) any policy audit must diff LIVE objects against the repo, not read the repo; (b) the only environment safe to test a removal in may be the one that LACKS the object** — which is exactly the environment where the test proves nothing. Cheap detector alongside it: `helm list -A` cross-referenced against the repo finds the same class of drift for whole releases -- successful IaC applies do not prove those releases are managed.

39. **A link-local DNS-cache allowance in a policy can be INERT in one environment and LOAD-BEARING in another — never conclude a rule is unused from a single-environment test.** For a rule allowing `169.254.20.10`, check whether the node-local DNS-cache DaemonSet actually exists in each environment and is declared in IaC. An out-of-band enablement can make the rule essential only where that DaemonSet runs; a removal test elsewhere proves nothing about that environment. **Check the rule's DEPENDENCY per environment — not the rule — before calling it dead.**

40. **⚠️ A rate-based ban keyed on "requests WITHOUT an `Authorization` header" turns a SHARED NAT EGRESS IP into a fleet-wide self-DoS.** Example: an edge WAF rule (`rate_based_ban`, 1000 req/10 s **per IP**, 300 s ban, deny 429) matched any request lacking `Authorization`. If all sandbox egress shares one NAT IP and the platform's internal calls authenticate by **other** headers (a shared-secret header for the ext-authz proxy, a config-refresh endpoint called by an infra sidecar) — every one of those calls counts toward the ban. Under load the NAT IP can be banned for 5 minutes, with scattered and misleading symptoms: LLM/embedding proxy calls 429, proxy-config refresh failing, and the workload returning 503 on its own dispatch endpoint. **Two review rules follow: (1) an allow/deny predicate written in terms of an ABSENT header silently includes every internally-authenticated path that uses a different scheme — enumerate them; (2) a per-IP rate limit is a per-EGRESS-IDENTITY rate limit, so shared NAT collapses your whole fleet into one bucket.** ⚠️ It also mimics a deployment regression closely enough to be blamed on an unrelated upgrade — check the WAF/ban logs before attributing 429s and 503s to the change that happened to land that day.
