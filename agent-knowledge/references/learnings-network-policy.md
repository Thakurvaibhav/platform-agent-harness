# Network Policy and Cilium Learnings

Fleet NetworkPolicy strategy, self-managed Cilium (GKE + EKS), Istio-ambient coexistence, FQDN egress.

See also: `learnings-operators.md`, `learnings-agentgateway.md`, `learnings-istio.md`

## Fleet substrate and provider facts

1. **GKE Dataplane V2 cannot be enabled on existing clusters** -- authoritative GCP docs state it can only be enabled at cluster creation time. Managed-Cilium fleet standard would require cluster replacement/blue-green. If replacement is out of scope, self-managed Cilium on existing GKE clusters is the only viable path.

2. **GKE self-managed Cilium has two modes; the tidy first-party one IS the full-takeover one**: Mode B (official GKE install section) = `gke.enabled=true, ipam.mode=kubernetes, routingMode=native, nodeinit.{reconfigureKubelet,removeCbrBridge}=true` -- preserves GKE-style PodCIDR allocation but takes over the CNI datapath and mutates kubelet/node state. Mode A (generic-veth chaining) preserves existing netd IPAM/routing but is documented only generically (not as a supported GKE integration) and has no persistence remedy when GKE node reboot/upgrade reinstates the default CNI (the warning is on `/en/stable/installation/taints/`, NOT the chaining page). Key insight: "B is better documented" and "B does the dataplane takeover" are the SAME fact -- its NodeInit DaemonSet solves the reboot problem precisely because it owns the CNI.

3. **EKS Cilium chaining capabilities and limits**: AWS VPC CNI keeps ENI/IPAM/pod interface + base routing; Cilium attaches eBPF after pod networking for L3/L4 policy/LB/observability (`cni.chainingMode=aws-cni, cni.exclusive=false, enableIPv4Masquerade=false, routingMode=native`). Official docs warn advanced features are limited in chaining, especially L7 policy/proxy redirects; transparent encryption is unsupported (cilium#15596). Existing pods must be RESTARTED after enabling chaining before Cilium policy applies. The AWS-managed VPC CNI add-on can overwrite daemonset fields on update cycles -- use add-on `configurationValues` for aws-node settings, keep AWS VPC CNI's own NP enforcement disabled when Cilium owns policy.

## Istio-ambient coexistence

4. **Cilium + Istio-ambient + kube-proxy + autoscaler coexistence facts** (Cilium v1.17+): (1) KEEP kube-proxy, `kubeProxyReplacement=false` -- Cilium-Istio integration requires `socketLB.hostNamespaceOnly=true` if KPR is on, else Cilium socket-LB rewrites connections inside the pod socket BEFORE ztunnel redirection sees them, breaking ambient. (2) `cni.exclusive=false` so Cilium doesn't remove the Istio CNI chained plugin. (3) No Cilium L7 on ambient workloads -- Cilium HTTP proxy + Istio mTLS = split-brain connection failures. (4) CRITICAL: ANY NetworkPolicy on an ambient-enrolled pod MUST allow TCP/15008 (HBONE) or it severs ztunnel tunnel traffic. (5) agent-not-ready taint applies at node-CREATE time only; existing clusters need new born-tainted node pools + cordon/drain/migrate; taint key MUST start with `ignore-taint.cluster-autoscaler.kubernetes.io/` or autoscaler refuses scale-up. (6) Policy Audit Mode allows traffic and logs would-drops (`hubble observe -t policy-verdict`); per-endpoint via `cilium-dbg endpoint config PolicyAuditMode=Enabled`; RESETS on cilium pod restart; NOT recommended for production steady-state; distinct from `enable-policy=never` (no enforce AND no verdicts). (7) Tetragon+Cilium dual-eBPF same-node is vendor-aligned but NOT conformance-documented; combined kernel/BTF floor unpinned -- validate in pilot.

5. **Policy-plane boundary with ambient**: For ambient-enrolled mTLS traffic, Kubernetes/Cilium NetworkPolicy still applies to the encrypted L4 HBONE tunnel entering/leaving Istio-managed pods, but Cilium has NO visibility into actual source/destination workload identity or L7. Therefore: Cilium/K8s NP owns pod selection, non-mesh/plaintext ingress, health-probe/link-local exceptions, infra boundaries, and coarse default-deny; Istio AuthorizationPolicy owns service-to-service identity/L4 and ALL L7 for ambient workloads. Cilium L7 policy requires removing the workload from ambient.

## FQDN egress

6. **`toFQDNs` / FQDN deny REQUIRES `l7Proxy=true`** (cilium#7109): the in-agent DNS proxy is gated by the L7 proxy flag -- FQDN policy is silently ineffective with `l7Proxy=false`. Tension: ambient coexistence posture is "no Cilium L7 on ambient workloads," but `l7Proxy` is a GLOBAL agent flag. Non-ambient workloads on dedicated pools CAN use FQDN deny (the DNS proxy runs in the Cilium agent, not in the workload), but squaring global-on with ambient-off needs per-pool design.

7. **FQDN egress default-deny landscape**: Solo Enterprise for Istio ztunnel-native L4 egress matches CIDR only (not FQDN), and CIDR-deny has the same churning-anycast-IP problem as IP allowlists. FQDN/hostname egress in Istio ambient requires the L7 waypoint egress gateway (extra proxy hop) and wildcard hostnames are unsupported. NET: Cilium `toFQDNs` (with `l7Proxy=true`) is the cleanest FQDN-deny primitive for Kubernetes.

## Principles

8. **Failure MODE matters as much as steady-state coverage**: A VPC firewall is fail-CLOSED (cloud fabric, no fail-open window); a node-local CNI policy (Cilium/Calico) is fail-OPEN during node lifecycle (agent not yet running). For untrusted-egress workloads, replacing a firewall with a CNI at equal rule coverage is a failure-mode REGRESSION. Keep the fail-closed backstop until replacement proves zero fail-open window.

9. **Cilium+Istio+ambient adoption has THREE stacked maturity layers -- don't launder L1 evidence as L3 proof**: L1 Cilium+Istio coexistence (sidecar era) = well-trodden. L2 Cilium+ambient/ztunnel specifically = thin but documented. L3 = Cilium primary CNI via IPAM takeover on existing non-DPv2 clusters + ztunnel + Tetragon (triple eBPF) = near-pioneering, no public reference; native Cilium-ztunnel datapath integration is an open upstream epic at low completion. General form: external evidence for layer N does not validate layer N+1.

## Tooling gotchas

The node-reboot warning is on `/installation/taints/`, not the chaining page. Policy Audit Mode is on `/security/policy-creation/`, not policy/intro. ## Enforcement evidence chain

11. **A NetworkPolicy object existing — or even network-policy-shaped CRDs being present — is not evidence of enforcement; the enforcement chain has several independent links, and confirming the object exists proves only the first one.** The full chain is: provider enforcement switch enabled -> the enforcing agent's DaemonSet present, Ready, AND running with enforcement actually on in its own container arguments -> policy objects exist -> a policy's selector actually matches both ends of the traffic in question. Two ways this fails silently and still looks fine: (1) a managed CNI's own policy-enforcement add-on setting can be disabled while policy objects are still accepted by the API server and enforced by nothing, and CRD groups can impersonate an enforcer — an observability-only DaemonSet can ship CRDs in the same API group as a real network-policy engine, so "matching CRDs are present" is not proof an enforcing agent exists at all; (2) an enforcing agent's own container can run with enforcement explicitly disabled in its startup flags while a sibling container's environment variable independently reads as "enforcing" — that variable is inert while the flag is off, so a config dump shows "enabled" and nothing is enforced, with the relevant CRDs present too. Second-order trap: a NetworkPolicy drop is indistinguishable on the wire from an mTLS/authorization rejection, so any probe claiming to prove one enforcement layer must first rule out the other. Third-order trap: deny logs written by a node-local agent are sometimes written to a file a container-log collector never tails (pod-discovery-plus-file-matcher configs read container stdout/stderr only) — so deny events can exist and still be unqueryable anywhere.


## Cilium version-specific risks

12. **An open, attacker-triggerable memory-DoS in Cilium's `toFQDNs` DNS cache affects `>=1.19.5 <1.20.0` and 1.18.8/1.18.11, with no fix as of this writing (`cilium/cilium#47128`).** A workload that resolves continuously-fresh subdomains under a `toFQDNs` policy grows `cilium-agent` RSS unboundedly — measured growth from roughly 100 MiB to several GiB within hours in a lab, and a similar trajectory over a few days in production. The retainer is the FQDN DNS cache's lookup-by-time index; the CLI command to clean the cache drops the majority of stale entries but releases no memory — only an agent restart or endpoint deletion actually frees it. DNS resolution latency and throughput degrade as the cache grows. Any workload that is not fully trusted (or that resolves attacker-influenced hostnames) can trigger this deliberately with a pattern like `<random-subdomain>.attacker-controlled-domain`. If `toFQDNs` cannot be avoided for such a workload, budget for cache-size alerting and a restart/rotation plan; the cleanest mitigation is designing DNS resolution out of the untrusted workload entirely rather than relying on an FQDN allowlist to contain it.


## FQDN egress (continued)

13. **GKE `FQDNNetworkPolicy` and Cilium NetworkPolicy resolve conflicting rules in opposite directions — GKE's is union-only (a controller's own allow-rule can never be overridden by anything else), Cilium's deny always wins regardless of policy type.** Per GKE's own documentation, verbatim: "When both a FQDNNetworkPolicy and a NetworkPolicy apply to the same Pod, egress traffic is allowed as long as it matches one of the policies. There is no hierarchy between egress NetworkPolicies" — meaning any additional allow-rule from a third-party controller or operator only ever widens access; nothing you add can subtract from it. GKE `FQDNNetworkPolicy` has further limits worth knowing before relying on it: caps at 50 resolved IPs (100/hostname quota), matches wildcards only one level deep, does not follow CNAMEs, is not enforced with any L7 protocol information, cannot target a ClusterIP or headless Service as a destination, and discards results from any DNS resolver that isn't in-cluster. Cilium, by contrast, states (v1.19 docs, verbatim): "Deny policies take precedence over allow policies, regardless of whether they are a Cilium Network Policy, a Clusterwide Cilium Network Policy or even a Kubernetes Network Policy." Consequence: if a third-party controller creates its own allow-NetworkPolicy on pods you don't fully control, only a Cilium deny policy can override it — plain Kubernetes NetworkPolicy and GKE `FQDNNetworkPolicy` are both purely additive and cannot.


## Sandboxed-runtime interactions

14. **Cilium's socket-level load-balancing (`socketLB`) breaks ClusterIP access for any sandboxed runtime with a userspace network stack — gVisor, Kata, KubeVirt — and `kubeProxyReplacement=true` force-enables it regardless of `socketLB.enabled`.** Socket-LB translates a ClusterIP to a pod IP inside the `connect()`/`sendmsg()` syscall via a cgroup/connect eBPF hook; a sandboxed runtime's userspace netstack (e.g. gVisor's `runsc`) never triggers that hook, so a sandboxed pod simply cannot reach ClusterIP services when socket-LB is active. The deciding code path (Cilium v1.19.5, `pkg/kpr/kpr.go:47-49`): if `KubeProxyReplacement` is true, `EnableSocketLB` is forced true regardless of its own setting. With `kubeProxyReplacement=false`, `socketLB.enabled` defaults false and ClusterIP DNAT happens in the packet path at the veth instead — which a sandboxed runtime's netstack does traverse. Cilium documents this gVisor interaction by name and ships the fix: `socketLB.hostNamespaceOnly=true` bypasses socket-LB for non-root network namespaces and falls back to the tc-based load balancer at the veth. Worth checking on any cluster running sandboxed workloads under self-managed Cilium.


## Tooling gotchas (continued)

15. **The long-standing assumption that `kind` clusters don't enforce NetworkPolicy is false as of `kindest/node` v1.36.1 / kind 0.31.x — `kindnet` enforces it.** Verified with a negative control rather than by reading docs: a pod in a namespace with default-deny plus an egress allow restricted to one TCP port got connection timeouts to a raw IP and to the cloud metadata IP, and DNS resolution failures for hostnames; an identical pod in a namespace with no policy at all got a normal HTTP response from the same raw IP. This means NetworkPolicy designs can be smoke-tested locally in `kind` today — don't skip local testing on the old assumption that `kind` can't enforce it. Re-verify against the specific `kindest/node` tag in use, since enforcement support is a relatively recent addition and may not be present on an older pinned node image.


## Egress allowlists for untrusted workloads

16. **When choosing an egress-allowlist mechanism for short-lived or untrusted workloads, weight debuggability above policy-language elegance — a denial is indistinguishable on the wire from an application bug, and the pod is often gone before anyone investigates.** Compare candidate mechanisms on whether a denial is answerable *after the fact*, by someone who doesn't know the enforcement stack: an L7 proxy's access log is structured, ships through the normal logging pipeline, and typically carries authority/SNI, response code and flags, upstream host, and a request id — a named-host deny is one query and survives pod deletion. A kernel-level eBPF flow-observability layer is often absent until specifically deployed — no dashboards, no alerts, no retention on day one — and its verdicts are frequently a live stream requiring an exec into an agent on the right node, so a short-lived pod's flows are gone the moment it's deleted. Node-local deny-log files are frequently not tailed by a container-log collector at all, and managed-dataplane policy logs can land in a cloud logging product with no dashboard wired to it. Net: inventory what your own observability stack already ingests before picking a mechanism — the right answer is a property of what you already run, not of which mechanism is more elegant.

17. **A literal no-DNS pod is not expressible in Kubernetes — the closest implementable form needs explicit `dnsConfig.options`, or every failed lookup blocks for roughly ten seconds.** The API server's own validation (`pkg/apis/core/validation/validation.go`, `validatePodDNSConfig`) rejects `dnsPolicy: None` with an empty nameserver list, requiring `dnsConfig` with at least one DNS nameserver whenever `dnsPolicy` is `None`. The implementable pattern is `dnsPolicy: None` plus a `nameservers` entry pointing at an address that will never answer (an IANA documentation-range IP works) plus `dnsConfig.options` setting a short `timeout`, a low `attempts` count, and `ndots: 0`, with port 53 denied by NetworkPolicy as the actual block. Without those options, every `getaddrinfo` call blocks for the resolver's default timeout-times-attempts (glibc's default is roughly ten seconds total) instead of failing fast — turning a policy meant to prevent DNS exfiltration into a pod that hangs on every accidental hostname lookup.

18. **A CONNECT forward proxy that trusts the SNI/authority on the tunnel it just opened is not sufficient to contain hostile code — HTTP/2 connection coalescing lets a client reuse that connection for a different, unauthorized destination with no detectable mismatch.** RFC 7540 SS9.1.1 permits a client to reuse one TLS connection for a different `:authority` whenever the server is authoritative for both, and shared-SAN CDN certificates make this common in practice; SS9.1.2 only says a non-authoritative server *should* respond 421, it isn't required to. The proxy sees a legitimate SNI matching a legitimate certificate that also happens to cover the disallowed destination, and a later HTTP/2 stream on that same connection silently carries a different `:authority` the proxy never validated. The equivalent hole exists on HTTP/1.1 via a CDN edge's inner `Host` header. Closing it requires the proxy to actually terminate TLS and inspect the real request authority per-request — SNI-based routing/allowlisting alone cannot detect this class of bypass, even though it is often assumed sufficient for "compromised but not actively adversarial" workloads.
