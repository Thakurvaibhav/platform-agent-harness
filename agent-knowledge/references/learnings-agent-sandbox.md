# Agent Sandbox Learnings

`kubernetes-sigs/agent-sandbox` (Sandbox / SandboxClaim / SandboxTemplate / SandboxWarmPool, `agents.x-k8s.io/v1beta1`) — upstream behaviour that defeats a naive isolation design, plus the credential-authority model that a network boundary alone does not cover. Source claims verified at commit **`79f31750`** (main, 2026-07-30) unless stated otherwise; re-verify at your pinned commit before relying on any `file:line` below.

See also: `learnings-network-policy.md`, `learnings-operators.md`, `learnings-k8s-sa.md`, `learnings-crossplane.md`, `learnings-agentgateway.md`, `learnings-gke.md` (node-pool and runtime facts that constrain sandboxed workloads).

## Upstream Networking Traps

1. **The controller ships its own NetworkPolicy and it allows the OPEN INTERNET — and because k8s NetworkPolicy is union-of-allows, your default-deny does not subtract it.** `SandboxTemplate.spec.networkPolicyManagement` is an enum `Managed|Unmanaged` with `kubebuilder:default=Managed`; under `Managed` with `spec.networkPolicy` nil, `buildDefaultNetworkPolicySpec()` (`extensions/controllers/sandboxtemplate_controller.go:192-256`) creates one shared NetworkPolicy per Template: ingress only from `app=sandbox-router` in `agent-sandbox-system`, egress to `0.0.0.0/0` + `::/0` **minus** RFC1918 / `169.254.0.0/16` / `fc00::/7` / `fe80::/10`. This is the OSS controller, not just the GKE managed addon. Plain NetworkPolicy **cannot** override it — overriding needs a deny-capable layer: `CiliumClusterwideNetworkPolicy` `egressDeny`, or an Admin-tier `ClusterNetworkPolicy` (EKS `networking.k8s.aws/v1alpha1`, needs VPC CNI ≥ 1.21.0 — fleet is on 1.22.4; GKE DPv2 equivalent), where a Deny match stops evaluation. Note the corollary: "the CRD has no networking fields" is true only of **core** `api/v1beta1` Sandbox; the fields live in `extensions/api/v1beta1` SandboxTemplate.
   - **Set `networkPolicyManagement: Unmanaged`** (the API comment names Cilium as the intended external manager) and Kyverno-enforce it at `validationAction: Deny`, not Audit — a template flipped back to `Managed` instantly punches a `0.0.0.0/0` hole through an operator default-deny.
   - **Two silent couplings via `isSecureByDefault = isManaged && networkPolicy == nil`**: `ApplySandboxSecureDefaults` (`extensions/controllers/utils.go:42-47`) sets `DNSPolicy=None` with nameservers `8.8.8.8`/`1.1.1.1` only under that condition — so setting **any** custom `networkPolicy`, or going Unmanaged, silently disables the public-DNS injection too (going Unmanaged this is what you want; setting a custom policy under Managed it probably is not).
   - Upstream **changed this default policy between 0.5.x releases**, so a version bump silently changes our enforced posture. Pair adoption with a Kyverno ValidatingPolicy rejecting NetworkPolicy objects in the sandbox namespace not authored by us.

2. **There is no constant, trustworthy pod label to select on — a policy written against `sandbox: true` matches ZERO pods and silently fails open** (an unselected pod is *non-isolated*, not default-denied). The controller **strips** user-supplied `agents.x-k8s.io/*` labels and stamps its own (`controllers/sandbox_controller.go:601-613, 1141-1154`). What actually exists:
   - `agents.x-k8s.io/sandbox-name-hash` = `NameHash(sandbox.Name)`, an 8-hex-char **per-sandbox** value (`sandbox_controller.go:52,586,1154`) — useless as a stable selector.
   - `agents.x-k8s.io/sandbox-template-ref-hash` (`api/v1beta1/sandbox_types.go:92`) **is** propagated to the Pod by `computeExtensionPodLabels` (`sandbox_controller.go:625-653`) and **is** a stable per-template hash — but **only when the Sandbox is owned by an extensions controller** (SandboxClaim / SandboxWarmPool). A raw Sandbox gets no such label. (Corrects an earlier claim that only `sandbox-name-hash` is stamped — that claim is stale.)
   - User-supplied `podTemplate.metadata.labels` are propagated unless system-reserved, but they are **caller-controlled** and therefore not a trustworthy basis for a security policy.
   - **Correct selector: `podSelector: {}` scoped to a dedicated namespace per sandbox tier**, or — on the SandboxTemplate path only — `sandbox-template-ref-hash`, which upstream's own default policy uses.

3. **The auto-created Service is headless**, `ClusterIP: None` (`sandbox_controller.go:795`), with the same per-sandbox selector. `status.serviceFQDN` therefore resolves straight to the pod IP with no kube-proxy DNAT — which is good for policy: netpol ingress sees the true client.

4. **PodTemplate admission hardening is the real launch gate, ahead of any CNI, proxy, or gVisor-vs-Kata work.** The controller copies **all** caller-supplied `Sandbox.spec.podTemplate` annotations verbatim onto the Pod (`sandbox_controller.go:1168-1176` create, `:1331-1339` update), filtering only the `agents.x-k8s.io/` and `extensions.agents.x-k8s.io/` prefixes (`isSystemAnnotation`). It **never sets or validates** `runtimeClassName`, `hostNetwork`, `hostPID`, `hostIPC` or `nodeSelector` (zero non-test occurrences at `79f31750`) and ships **no validating webhook**. Consequences, each a one-field bypass:
   - `hostNetwork: true` — NetworkPolicy does not apply to host-network pods, so every network gate is bypassed by one boolean.
   - omitting `runtimeClassName` — you get plain `runc`, not the sandboxed runtime you designed for.
   - `io.katacontainers.*` annotations reach Kata CVE-2026-50540 / CVE-2026-44210 / GHSA-7fhf-v3p3-rp56.
   - Gate: PSA `restricted` + Kyverno pinning `runtimeClassName` + an annotation-key allowlist.

5. **`AutomountServiceAccountToken` defaults to `false` only via the extensions / SandboxTemplate path** (`ApplySandboxSecureDefaults`). A **directly-created** Sandbox gets the Kubernetes default `true`. Secure-by-default is a property of the path taken, not of the CRD.

6. **`sandbox-router` ships a default `AllowAll` authorizer** — pin a version with the scoped-token authorizer and set it explicitly.

## Warm Pool

7. **The warm pool is a fail-open window and a hard limit on per-tenant identity, both from the same fact: only metadata is mutable at adoption.** `SandboxWarmPool` pre-creates running pods later **adopted** by a Sandbox/SandboxClaim, and adoption propagates only pod **labels/annotations** to an already-running pod (`controllers/sandbox_controller.go:1242 updatePodMetadata`, comment "e.g., after warm pool adoption").
   - **Fail-open**: label+annotation propagation at adoption is an open upstream issue (**agent-sandbox#174**), and 0.5.x release notes moved sandbox names from labels into annotations. Any NetworkPolicy whose `podSelector` keys on a sandbox label selects **nothing** for the whole pre-adoption warm window → an unpoliced running pod. Fix is #2's fix: key on the namespace (`podSelector: {}`) with a dedicated namespace per tier.
   - **Identity**: the Pod **spec** — env vars, volumes, projected Secrets — is fixed at warm-pod creation, *before the tenant is known*. A per-tenant egress-proxy credential injected as env or a mounted Secret is therefore **impossible** on the warm-pool path. Per-session identity must arrive over an API the running agent calls, never via `podSpec`.

## Credential Authority

8. **An egress allowlist and a credential broker solve different problems and neither substitutes for the other.** An allowlist controls **where** traffic goes; it says nothing about **what authority** it carries. If the sandbox holds an MCP/tool credential, hostile code never has to defeat the network boundary — it uses a valid credential against an already-allowed destination. Framework: IETF **`draft-hartman-credential-broker-4-agents-00`** (CB4A, Mar 2026), three models: **A** = proxy injects the credential on egress, agent *never* holds it; **B** = broker mints a short-lived scoped token and hands it to the agent (the draft's RECOMMENDED default); **C** = hand over the real long-lived credential + scheduled revocation (draft: "WEAKEST … NOT RECOMMENDED").
   - **Judgement call that departs from the draft: pick A, not B, when the code is hostile from t=0** rather than merely compromisable. A hostile agent will fully exercise a 1-hour scoped token inside the hour.
   - **They are mutually dependent, not alternatives** — CB4A's own threat model **TM-11** states brokering is not self-enforcing ("relying solely on the agent's cooperation to use the broker is insufficient") and *requires* network-level enforcement blocking direct agent-to-service access.
   - Architecture: **PDP** (decides, zero credential access) strictly separated from **CDP** (mints, no policy authority); SPIFFE/SPIRE SVID for workload identity, non-renewable — re-attest, don't refresh; **DPoP (RFC 9449)** sender-constrains so a stolen token is useless from another network position.
   - **MCP spec (2025-11-25) is normative and constrains broker design**: OAuth 2.1, PKCE S256 only, RFC 8707 resource indicators in **both** authz and token requests, audience validation, and "MCP servers MUST NOT accept or transit any other tokens" — token passthrough is banned outright as the confused-deputy mitigation. A broker must mint/exchange per-audience tokens and never relay the caller's.
   - **Honest limit**: brokering fixes credential **theft**, not credential **abuse** — the agent can still request any operation policy permits. So **authorize per OPERATION, not per connection**: "you may call `createIssue` on repo X" beats "you may reach `api.github.com`". A broker that only injects credentials without an operation-level PDP has *relocated* the secret, not reduced the authority.

9. **The upstream scoped-token is a verifier, not a system — "just set `authz-mode: scoped-token`" is half a fix.** `sandbox-router/authz/scopedtoken.go`: HMAC-SHA256 over `{ns,name,exp}`, domain-separated, `v1`-prefixed. The source comment at `scopedtoken.go:112-117` states that **minting** in production belongs in the Sandbox controller and that "surfacing the result via Sandbox status or a controller-managed Secret is tracked as a follow-up" — i.e. the mint+deliver path **does not exist upstream**. The token also has no `jti`/`aud`/`kid`: not revocable before `exp`, not rotatable without a flag day, and replayable by anyone who reads it.

## Egress Allowlisting: Options Survey and Source-Verified Limits (2026-08)

10. **Egress hostname-allowlist options for untrusted workloads — what is genuinely managed, what is portable, and the two very common misconceptions.** **GENUINELY MANAGED (removes data-plane ownership):** **GCP Secure Web Proxy** — CAVEAT: explicit-proxy mode **CANNOT match HTTPS hostnames without TLS inspection**; only next-hop mode can use the visible SNI. **AWS Network Firewall** — HTTP `Host` + TLS SNI domain lists with no decryption, but needs an `aws:drop_established` default action; the **AWS Network Firewall *Proxy* is PREVIEW** (single-region, HTTP/1.1). Cost at survey: SWP $1.25/gw-hr + $0.018/GB; NFW $0.395/endpoint-hr/AZ + $0.065/GB. **PORTABLE SELF-HOSTED:** `agentgateway` v1.4.1 genuinely does egress (DynamicForwardProxyBackend + CONNECT tunnel mode + CEL over `request.host`) — **it is NOT inbound-MCP-only** — but its k8s APIs are `v1alpha1` and it is Linux Foundation AAIF, **not CNCF** (kgateway is the CNCF one). Istio ambient egress waypoint now does wildcard external hosts via `DYNAMIC_DNS`. **NOT CANDIDATES, and both are commonly mistaken for candidates:** **Cilium Egress Gateway is source-IP SNAT with CIDR destinations — it is NOT hostname authorization**; and **Gateway API has NO off-mesh egress story at all** (GEP-1324 explicitly defers it; GAMMA is east-west mesh only).
    - **THE GAP NONE OF THEM CLOSES: no option provably binds the outer CONNECT authority to the inner TLS SNI or the later HTTP `:authority`**, so **HTTP/2 connection coalescing over a shared-SAN CDN certificate defeats SNI-pinning everywhere** (RFC 7540 §9.1.1 permits it, and AWS documents the bypass for its own service). **Only TLS terminate-and-re-originate closes it, at the cost of holding customer plaintext** — decide that trade explicitly rather than assuming a proxy solves it.

11. **`agentgateway` v1.4.1 traffic handling, source-verified — hostname routing is TLS-ONLY, which decides what an egress design can route by name.** `ListenerProtocol` (`crates/agentgateway/src/types/agent.rs:612-622`) = `HTTP` | `HTTPS` (terminate then treat as HTTP) | `TLS` (passthrough OR termination) | `TCP` (opaque) | `HBONE` — so **per-entry passthrough-vs-terminate IS supported** via the TLS listener variant, satisfying a "passthrough by default, terminate only where credentials are injected" requirement. **CRITICAL LIMIT, from the source comment on `TCPRoute.hostnames` (`agent.rs:1031`): "Can be a wildcard. Not applicable for TCP, only for TLS."** Opaque TCP has **no hostname selector** — a TCP listener routes by listener/port to a backend. **CONSEQUENCE for a DNS-steering design where every allowlisted name resolves to one gateway IP: TLS routes by SNI and HTTP by `Host`, both fine — but two different external Postgres/Redis/SSH hosts pointed at `gateway:5432` are INDISTINGUISHABLE** (no SNI, no Host, same port). Workarounds: one dedicated listener port per destination (breaks transparency — the client expects the standard port), or put hostname-less protocols in an explicit IP/CIDR NetworkPolicy tier that bypasses the gateway. **This is precisely the capability per-host synthetic VIPs would have bought** (the destination address disambiguates opaque TCP) — a real trade against dropping VIP IPAM / append-only allocation / route plumbing. **Mitigation that mostly dissolves it: prefer the TLS variants** (Postgres `sslmode=require`, Redis TLS), which return those protocols to the SNI path. Also verified: **agentgateway has NO DNS server** — `Cargo.toml` carries hickory-**resolver** (client) only, no hickory-server and no `:53` bind — so DNS steering needs a separate CoreDNS.

12. **Transparent per-host-VIP capture is a BUILD — neither off-the-shelf candidate qualifies, and the marketing suggests otherwise.** Source-verified at pinned commits. **`agentgateway` v1.4.1 (`163ea214`): NO `SO_ORIGINAL_DST` / `IP_TRANSPARENT` / TPROXY anywhere**; listeners use ordinary `TcpListener::bind` (`crates/agentgateway/src/store/binds.rs:564-610`). It CAN consume original src/dst from a trusted upstream PROXY-protocol sender (documented for ztunnel) — **but that sender is an extra capture component you must supply.** Destination-VIP-to-service lookup lives in the HBONE waypoint branch (`proxy/tcpproxy.rs:287-386`), so off-mesh it routes by configured listener, not by received VIP. It DOES select a TLS listener by SNI then splice or terminate per listener config (`gateway.rs:1043-1087`), and its credential injection + MCP handling are native. **`iron-proxy` v0.49.0 (`c8724937`): the README mentions TPROXY needs `IP_TRANSPARENT` but NO Go code sets it**; critically **its DNS server returns THE SAME shared proxy IP for all intercepted A queries** (`internal/dns/server.go:168-175`) — that is Host/SNI recovery, **not per-host VIP** — and its TLS mode is **PROCESS-WIDE** mitm or sni-only (`internal/config/config.go:135-153`), so no per-entry passthrough/terminate. Its bundled resolver is UDP-only, recurses for passthrough globs, **intercepts unlisted names instead of returning NXDOMAIN**, and debug-logs full QNAMEs. **CONCLUSION: a transparent per-host-VIP + selective-TLS gateway is a BUILD (Envoy `original_dst`/TPROXY + per-VIP routes), or you add a trusted L4 capture shim in front of agentgateway — an explicit architectural concession, not a detail.** Keep agentgateway for the terminated/brokered subrange where its credential injection is native.

13. **SNI-based egress enforcement WITHOUT TLS MITM has an all-stable Envoy filter chain — the one alpha filter is the one you must avoid.** Stable and `robust_to_untrusted_downstream_and_upstream`: `envoy.filters.listener.tls_inspector`; stable and `robust_to_untrusted_downstream`: `envoy.filters.network.rbac`, which **matches on `requested_server_name`** (`config/rbac/v3/rbac.proto:309`); stable and robust both ways: `envoy.bootstrap.internal_listener`, `envoy.filters.http.dynamic_forward_proxy`, `envoy.filters.http.ext_authz`. **The one filter that IS alpha with `security_posture: unknown` is `envoy.filters.network.sni_dynamic_forward_proxy`** (`source/extensions/extensions_metadata.yaml:1008-1014`) — **so avoid SNI-DFP, not SNI enforcement itself.** KEY DESIGN MOVE: **decide the upstream from the OBSERVED ClientHello SNI, never from the CONNECT authority** — then a CONNECT-authority-vs-SNI mismatch is moot without terminating TLS. Our live Envoy access-log JSON already emits `requested_server_name` alongside `authority`, `response_code_details` and `response_flags`, so the mismatch check is a LogQL one-liner on the format we ship today.

14. **A no-resolver ("DNS blackhole") sandbox is sound only under an EXPLICIT proxy-aware HTTP(S)-only workload contract.** Managed proxy-side DNS is prior art (GCP SWP, AWS Network Firewall Proxy), but **no official Kubernetes standard for a `127.0.0.1` blackhole resolver was found.** The main risk is compatibility with arbitrary runtimes and non-HTTP protocols; the PodTemplate admission gate (#4) and route isolation already provide the core containment, so treat no-DNS as a hardening step rather than a launch gate.

## Runtime Isolation and Adjacent Upstream Projects

15. **Kata Containers is effectively UNAVAILABLE on EKS for cost reasons — any "use Kata for sandbox isolation" recommendation must price a bare-metal node fleet.** EC2 Nitro guests do not expose nested-virtualization extensions, so Kata (QEMU/Firecracker) requires `.metal` instance types. **gVisor/runsc on EKS needs a custom AL2023 AMI with a pinned `runsc` + containerd shim** (no managed offering; it will not run on Bottlerocket without a custom variant), whereas **GKE ships a managed `gvisor` RuntimeClass for free.** Practical sequencing: **launch GKE-first so the runtime-isolation gate is satisfied day one, and make runsc-on-EKS a scheduled hardening item rather than a launch blocker.** (UNVERIFIED at source: the Nitro nested-virt claim is from general AWS knowledge — re-read before quoting it as a source-level fact.)

16. **Agent Substrate is NOT a drop-in under `kubernetes-sigs/agent-sandbox` — it BREAKS per-sandbox network policy.** Verified at `3ed6aa07`: it maps many "actors" onto fewer pre-warmed "worker" pods, bypassing the k8s API in the activation hot path. **CRITICAL CORRECTION to the obvious reading: this is TEMPORAL reuse (one active actor per worker at a time, snapshot suspend/resume), NOT concurrent multi-tenancy inside one worker.** Either way it is design-breaking for a per-sandbox boundary: **NetworkPolicy is documented at WorkerPool scope**, and the actor gets an inner veth/netns but **untunneled traffic INCLUDING DNS is masqueraded through the Worker Pod**, so successive actors inherit one externally-visible identity and a rule on the worker cannot express different allowlists for actor A vs actor B. The source has the beginnings of an actor-aware tunnel (`internal/ateomnet/net.go`, `internal/atunnel/client.go` — mTLS CONNECT + actor headers) but destination validation is still IP-oriented, actor auth is not fully wired, and per-actor L7 egress is explicitly roadmap. Maturity: *"not production ready, APIs almost guaranteed to change"*, only a `v0.0.0` tag. **RULE: if you adopt Substrate, enforcement must move INSIDE its control plane — a Kubernetes-native netpol+proxy boundary no longer applies.** Contrast: an `agent-sandbox` `Sandbox` is one pod with no `replicas` field, so **1 sandbox = 1 policy subject.**

17. **`agent-sandbox` upstream re-verification at `79f31750` — four facts that change a hardening plan.** (a) The NetworkPolicy default is `Managed` (`+kubebuilder:default=Managed`, `sandboxtemplate_types.go:126ff`) and it opens **`0.0.0.0/0` minus RFC1918 and 169.254** (`sandboxtemplate_controller.go:~225-253`) — i.e. the open internet (#1). (b) **Zero non-test occurrences of `RuntimeClassName` / `HostNetwork` / `NodeSelector`, and NO `ValidatingWebhookConfiguration`** — the admission hardening in #4 is entirely ours to add. (c) The router default is `AllowAll` (`cmd/main.go:194`), **but scoped-token is an `AuthzMode` CONFIG option (`config.go:55`), not a separate build** — so #6/#9 is a config flip plus the verifier work, not a fork. (d) **The label strip applies ONLY to the `agents.x-k8s.io/*` and `extensions.agents.x-k8s.io/*` prefixes — plain PodTemplate labels DO propagate to pods**, which is what makes any label-based policy selector attacker-controllable (#2).

18. **`dnsPolicy: None` still REQUIRES at least one `dnsConfig.nameservers` entry — a "no DNS" sandbox is expressed as a loopback BLACKHOLE resolver plus an enforced UDP/TCP 53 deny.** Use `127.0.0.1` as the nameserver and deny port 53 egress; with sandbox egress restricted to a literal proxy `IP:port`, **Cilium `toFQDNs` and `l7Proxy` become unnecessary** (`learnings-network-policy.md`). Common proxy-aware clients keep working while direct DNS and custom transports **fail closed** — which is the desired shape, but it is exactly why #14's explicit workload contract is a prerequisite. **Envoy's explicit-HTTPS CONNECT matcher / `connect_config` and the SNI dynamic-forward-proxy are documented ALPHA, so a TLS-intercepting Envoy must NOT be accepted as a production security boundary without a pinned-version config proof plus hostile negative controls** (#13 lists the all-stable alternative chain).

19. **A shared synthetic-VIP pool is UNSAFE unless every flow is authorized by an AUTHENTICATED sandbox/customer identity in addition to destination VIP, port and TLS SNI — and DNS resolution CANNOT be the authorization event, because hostile code can scan the literal VIPs directly.** This is the security review that closes out #11/#12: passthrough TLS enforcement by outer SNI alone is vulnerable to malicious `Host`/`:authority` fronting on shared endpoints — **a broader problem than standards-compliant HTTP/2 connection coalescing (#10)**, because it does not need a shared-SAN certificate, only a shared endpoint.

20. **The "proxy-aware HTTP(S)-only workload contract" of #14 is only implementable if you enumerate the per-runtime proxy knobs — `HTTPS_PROXY` alone covers roughly none of a real base image, and each runtime fails silently and differently.** The base-image environment that actually works: `HTTPS_PROXY=http://<proxy-host>:<port>`, `NO_PROXY=localhost,127.0.0.1,::1,<any host dialled directly>`, `NODE_USE_ENV_PROXY=1` for Node, **`JAVA_TOOL_OPTIONS=-Dhttps.proxyHost=… -Dhttps.proxyPort=…` because the JVM ignores `HTTPS_PROXY` entirely**, and a wrapper passing `--proxy-server=` to Playwright/Puppeteer, whose bundled browsers do not read the env vars either. **Deliberately leave `HTTP_PROXY` UNSET**: with it set, clients emit **absolute-form requests** rather than `CONNECT`, which is a different proxy protocol path and will not match a CONNECT-only gateway. **The framing that keeps this honest: these env vars are CONVENIENCE, NOT ENFORCEMENT.** A client that ignores them connects directly and the kernel-level NetworkPolicy drops it — so the env is what makes compliant clients *work*, and the netpol is what makes non-compliant ones *fail*. Never present the env-var set as the containment boundary; if it were, every unset knob above would be a hole. Corollary for the compatibility argument in #14: the runtimes that "just work" under a transparent-capture design (see `learnings-network-policy.md`) are exactly the ones needing a bespoke knob here — that is the real content of the transparent-vs-explicit trade, and it is a base-image/doc problem solved once, not a per-service tax.

## Warm-pool readiness, adoption and the timeout loop (v0.4.3 -> v1.0.2)

21. **The warm-pool readiness gate lives in `getCandidate`, NOT in `isAdoptable` — and it did not exist before v0.5.0, so a "warm pool hit" on v0.4.3 is not a guarantee of a warm pod.** The obvious-looking function is the wrong one to read. `isAdoptable()` has **no readiness check at any version** (v0.4.3 through v1.0.2), and that is **deliberate**; upstream documents it directly above the function (`extensions/controllers/sandboxclaim_controller.go`, v1.0.2): *"isAdoptable evaluates static ownership and validity only. Transient runtime conditions (e.g., waiting for PodIPs or image pulling) MUST NOT be checked here; failures in isAdoptable trigger permanent queue eviction and premature claim unassignments. Transient checks belong in getCandidate."* It accepts a candidate on four static label/ownership checks (not-deleting, `agents.x-k8s.io/warm-pool-sandbox` label, template-ref-hash label, `controllerRef.Kind==SandboxWarmPool`). **v0.5.0 added the transient check to `getCandidate`** — it scans the queue for a Ready candidate and adopts that immediately, keeping the first unready one only as a last-resort fallback when the queue holds none. Per-tag scan for `isSandboxReady` inside `getCandidate`: **v0.4.3 = absent; v0.5.0–v0.5.6, v1.0.0, v1.0.2 = present** (latest tag v1.0.2, which additionally skips candidates with empty `Status.PodIPs`, adds a readiness grace period and unschedulable detection, and prioritises unready sandboxes for excess-deletion in `sandboxwarmpool_controller.go`). **On v0.4.3 the failure is real and measurable:** `getCandidate` adopts whatever pops off the queue; a replacement pod is stamped with the warm-pool label at creation (`sandboxwarmpool_controller.go:110,:317,:331`) and is adoptable the instant its Sandbox CR exists, while still `ContainerCreating`. `isSandboxReady(adopted)` is called only at `:697-700`, **after** adoption, to set the `pod_condition=ready|not_ready` label on `agent_sandbox_claim_creation_total` — upstream instrumented not-ready adoption as a normal outcome rather than preventing it. Compounding on v0.4.3: `SandboxWarmPool.reconcilePool` (`sandboxwarmpool_controller.go:145-147`) computes `currentReplicas` from `len(activeSandboxes)`, NOT ready ones, and `ReadyReplicas` (`:159-165`) is status-display only, never gating replenishment. Measured in production at v0.4.3: `pod_condition=not_ready` was **405 of 3094 warm adoptions (13.1 %)** on one pool over an 11 h counter window. The real readiness gate that *does* exist at v0.4.3 sits downstream in the caller — `controllers/sandbox_controller.go:285-305` requires Pod `phase==Running` AND `PodReady==True` AND `len(PodIPs)>0` before setting `Sandbox .status.conditions[Ready]` — which is what the SDK waits on (#23), not what adoption consults. **Upgrade cost sits at the v0.5.0 boundary, not at the target version: v0.4.3 is `extensionsv1alpha1`, v0.5.0 is `extensionsv1beta1`, so it is a CRD migration either way**; v0.5.6 carries explicit handling for warm sandboxes still holding v1alpha1 owner refs after upgrade, so upstream expects the transition to be bumpy.

22. **A readiness TIMEOUT destroys the pod it was waiting on, which makes the miss self-amplifying — and it survives until the #21 upgrade.** Adoption transfers ownership before readiness is ever established: `completeAdoption()` (`extensions/controllers/sandboxclaim_controller.go:719-733`) sets `adopted.OwnerReferences=nil`, then `SetControllerReference(claim, adopted)`, and **deletes the warm-pool labels**. So the Sandbox is owned by the Claim; **deleting the Claim garbage-collects the Sandbox and its pod.** A client that reacts to `TimeoutError` by deleting the claim (create → best-effort-delete → raise) therefore kills a pod that was mid-startup. Net effect in production: a pod ~29 s into a measured p50 38 s startup is killed **~9 s before it would have gone Ready**; the pool's `currentReplicas` drops (the labels were removed at adoption); `SandboxWarmPool` creates a replacement that is itself immediately adoptable while `ContainerCreating` — feeding the next miss. **Retry semantics compound it:** the retry builds a brand-new client and a new `claim_name` (the SDK generates `sandbox-claim-<uuid8>` per `create_claim`), with **no backoff**. So "the second attempt usually succeeds" means *a different, older, already-Ready pod got picked*, NOT *the image pull finished* — and those two readings imply different fixes. Gating adoption on readiness (#21, upstream ≥ v0.5.0) fixes it; a bigger image cache does not.

23. **The client SDK waits on the Sandbox CR's Ready CONDITION, never on the Pod — and one timeout budget is SPLIT across two sequential waits, so the number in the error message is not the number you configured.** `k8s-agent-sandbox` (pinned `==0.4.3`) watches `.status.conditions[type=Ready,status=True]` on the `Sandbox` CR (`k8s_helper.py:158` / `async_k8s_helper.py:193`) and raises `TimeoutError("Sandbox {name} did not become ready within {timeout} seconds.")` on expiry (`k8s_helper.py:140` / `async_k8s_helper.py:174`) — that exact string is the production error format. `async_sandbox_client.py:148-155` spends the budget on `resolve_sandbox_name()` first (~1 s), then passes `remaining_timeout = max(0, int(budget - elapsed))` to `wait_for_sandbox_ready()`, **whose message prints its OWN parameter** — which is why a 30 s configured budget surfaces in logs as "29 seconds". **Whether that CR condition reflects true Pod readiness is decided entirely by the upstream Go controller (#21), whose source is typically NOT vendored** — a Terraform `data "http"` fetching `manifest.yaml`/`extensions.yaml` straight from GitHub Releases at apply time stores no CRD YAML and no Go source locally, so the predicate is **not answerable from the repo or the cluster alone**. Clone `kubernetes-sigs/agent-sandbox` at the pinned tag to read it.

24. **A `SandboxClaim` NAME is not an object identity, and it is not even per-kind — so any delete-by-name is a delete-by-guess.** `k8s-agent-sandbox` (pinned `==0.4.3`) generates `f"sandbox-claim-{uuid.uuid4().hex[:8]}"` in `async_sandbox_client.py:143` — **32 bits, drawn blind, no conflict retry** — so a consumer that passes no name has its **job**, **chat** and **env** claims all drawing from that one space in one namespace (`DEFAULT_NAMESPACE = "agent-sandbox-system"`). The trap is that a DB uniqueness argument does **not** save you: if only one of the three kinds carries a DB row, a stale row whose name has since been reused by a live claim of another kind resolves to **exactly one** row — `scalar_one_or_none()` raises no `MultipleResultsFound`, nothing fails closed — and the delete then destroys a different user's running sandbox. Deleting the claim GCs the Sandbox and its pod (#22), so this is irreversible. **Fix pattern: read-then-pin, both halves.** `delete_claim(..., expect_kind=<Kind>)` reads the live claim, refuses unless the `<org>/claim-kind` label matches (raising `SandboxClaimKindMismatchError`, made a **subclass of `SandboxClaimDeleteError`** so every existing handler keeps working), and issues the delete with `body=V1DeleteOptions(preconditions=V1Preconditions(uid=...))` carrying the UID from that same GET. **Neither half alone is enough** — the check and the delete are two API calls, so without the precondition a claim replaced in the window still dies; and a UID precondition alone happily deletes a claim of another kind whose UID never changed. **Rejected: persisting the UID in the DB** — it needs a migration and only moves the staleness, since a UID written at create time can still name an object replaced since. ⚠️ **CORRECTION — this entry previously said "fail closed on a missing label too". That is WRONG in the form a reader would act on, and shipping it broke two production routes; see #25.** An **ABSENT** label must be **PERMITTED**; only a **present-but-different** one may be refused. Keep the DB row on refusal so the anomaly stays visible rather than being swallowed. Generalizes to any controller-generated name: if the generator is short, shared across kinds, and retry-free, the only safe delete is read-verify-then-delete-with-UID-precondition. `kubernetes_asyncio` types `body` as a required `V1DeleteOptions` and rejects `**kwargs` unpacking under mypy — always construct one; an empty `V1DeleteOptions` serialises to `{}` (verified via `ApiClient.sanitize_for_serialization`), identical on the wire to sending no body.

25. **A destructive guard keyed on a LABEL must distinguish ABSENT from DIFFERENT — conflating them fails closed on every object produced by a CONDITIONAL labelling path, and conditional labelling is exactly where such paths hide.** The `expect_kind` guard of #24 originally refused an **absent** `<org>/claim-kind` label, which broke two delete/deactivate routes with **HTTP 500 instead of 204** (the caller catches `SandboxClaimNotFoundError` but not `SandboxClaimKindMismatchError`, so it escaped to the route's generic `except Exception`). Root cause: the chat creation path builds `claim_labels` **only when `job_name` is set**, so a chat claim without a job name carries **no labels at all**. The safety argument that licenses permitting absent is an ENUMERATION, not a hunch: of the three `create_claim` call sites, two pass `SandboxClaimLabels(...)` **unconditionally** and that type requires both fields with `to_k8s()` always emitting both — so a labelled claim is never partially labelled, and **an unlabelled claim created by current code can only be a chat claim**. Residual risk accepted and documented in-code: a *legacy* pre-labelling job/env claim is also unlabelled and deletable this way, but that needs a 32-bit name collision **and** a pre-label claim still alive. **The UID precondition is independent of labels and must stay UNCONDITIONAL** — it guards the read-then-delete race, not the kind. **Before shipping any such guard, enumerate EVERY creation site and check whether the label argument can be `None` — not just the ones the reviewer named.**

## Upgrading the controller: v0.4.3 -> v1.0.3 (source-verified)

26. **v0.4.3 → v1.0.3 is NOT a direct hop — a stop at v0.5.x is STRUCTURALLY REQUIRED, and it is the kube-apiserver that enforces it, not convention.** **CRD served versions by tag** (verified by parsing the release assets for all 14 tags): `v0.4.3–v0.4.6` serve **only `v1alpha1`** (storage); `v0.5.0–v0.5.6` serve **both** `v1beta1` (storage=true) **and** `v1alpha1` (served=true) with `spec.conversion.strategy=Webhook` → service `agent-sandbox-webhook-service/agent-sandbox-system` path `/convert`; `v1.0.0–v1.0.3` serve **only `v1beta1`, with NO conversion block**. **The gate:** apiextensions `ValidateCustomResourceDefinitionStoredVersions` (k8s `staging/src/k8s.io/apiextensions-apiserver/pkg/apis/apiextensions/validation/validation.go:276-277`, called from `ValidateCustomResourceDefinitionUpdate:250`) errors *"must appear in spec.versions"* for any `status.storedVersions` entry absent from the new `spec.versions` — so with live CRDs at `storedVersions=[v1alpha1]`, **applying the v1.0.3 CRDs is REJECTED before anything else can go wrong**. Upstream agrees in `docs/api-migration-guide.md` at v1.0.3. **The migration tool is `helm/files/migrate.sh` (v0.5.x only), two idempotent phases:** `--phase=bootstrap` pre-creates a `shadow-pool-<template>` `SandboxWarmPool` at `replicas=0` per template referenced by a cold-start claim; `--phase=migrate` stamps `agents.x-k8s.io/storage-migrated-at` on every object to force an etcd rewrite in v1beta1 form. **`storedVersions` is NOT auto-pruned** — a manual `kubectl patch crd <name> --subresource=status --type=merge -p '{"status":{"storedVersions":["v1beta1"]}}'` is the actual precondition for the v1.0.x apply. **GKE-specific:** the conversion webhook listens on **port 9443 on worker nodes** and GKE private clusters block master→node traffic on non-standard ports, so a firewall rule for 9443 is needed or the migrate phase fails with dial-tcp timeouts. `shadow-pool` exists in Go source **only at v0.5.x** (zero hits at v1.0.0/v1.0.2/v1.0.3), so **bootstrap MUST run while a v0.5.x controller is installed** — it cannot be done afterwards. All four CRDs (`sandboxes`, `sandboxclaims`, `sandboxtemplates`, `sandboxwarmpools`) go single-version. **The reverse is worse than the forward:** once objects are stored as `v1beta1`, re-applying the v0.4.3 `v1alpha1`-only CRD **strands them** — so the CRD leg is **not cleanly revertible** and a rollback plan that says "just re-apply the old version" is wrong. Check before attempting: `kubectl get crd sandboxclaims.extensions.agents.x-k8s.io -o jsonpath='{.status.storedVersions}'` plus a server-side dry-run of the new CRD.

27. **`SandboxClaim` v1beta1 makes the TEMPLATE-ONLY CLAIM IMPOSSIBLE — this is the deepest behavioural break, and it changes the provisioning MODEL, not just the imports.** The claim **loses `spec.sandboxTemplateRef`** (which was its only required field) and **loses `spec.warmpool`**; it **gains `spec.warmPoolRef`, now the only required field**, plus `spec.volumeClaimTemplates`. The controller enforces it — `extensions/controllers/sandboxclaim_controller.go:2169-2173` at v1.0.3 GETs the pool by `claim.Spec.WarmPoolRef.Name` and returns `ErrWarmPoolNotFound` (condition message *"SandboxWarmPool %q not found"* at `:710`). **There is NO template fallback and NO shadow-pool code at v1.0.3.** Also moving: `Sandbox` loses `spec.replicas` and gains `spec.operatingMode` + `spec.service`; `SandboxTemplate` gains `spec.service` + `spec.volumeClaimTemplatesPolicy`; `SandboxWarmPool.spec` is otherwise **unchanged**. **Survivable if you already create a warm pool per agent** — the fix is to pass the pool name where you pass the template today. **What still bites: a POSITIONAL call site.** The SDK renames `create_sandbox`'s first positional parameter `template` → `warmpool` *and changes its meaning*, so a positional call still **binds** — no `TypeError`, it just sends a template name as a warm-pool name and every claim fails `WarmPoolNotFound`. **Silent-wrong, not loud.**

28. **On v0.5.x, whether a converted claim reaches its REAL warm pool or a `replicas=0` SHADOW pool depends on STATUS, not spec — so existing bound claims survive and every NEW claim from an old SDK cold-starts.** `sandboxclaim_conversion.go:151-168` (v0.5.6): if `spec.warmpool` `IsSpecificPool()` use it; **else if** `status.sandbox.name` is set and ≠ the claim name → warm start, `WarmPoolRef = stripRandomSuffix(status.sandbox.name)` = the real pool; **else** → `shadow-pool-<template>`. `IsSpecificPool` (`sandboxclaim_types.go:58-60`) excludes `''`, `'none'` **and `'default'`** — so a `warmpool` key present on 100 % of live claims is the **CRD default**, never a specific pool. A **new** claim has empty status at admission and therefore routes to the shadow pool. **Worse, the bootstrap does not cover it:** `migrate.sh --phase=bootstrap` (`helm/files/migrate.sh:193-249, 277-350`) creates shadow pools **only** for `(namespace, template)` pairs represented by default/none claims whose `status.sandbox.name` is empty or equals the claim, at a **single one-shot LIST** — it skips warm-bound claims and **never enumerates SandboxTemplates**. Where every claim is warm-bound, bootstrap creates **ZERO** shadows, and a later old-SDK claim points at a missing pool and sits in `WarmPoolNotFound`, requeued every 60 s with a nil error — **there is no cold-start fallback**. Against a 30 s readiness budget that is **failed claim creation, i.e. an outage, not a slowdown**. ✅ **THE DE-RISKING MOVE: set `spec.warmpool` to the real per-pool name WHILE STILL ON v0.4.3, and the whole conversion window disappears.** It is **not literally a no-op on v0.4.3** — the field exists there with `kubebuilder:default=default`, a pool name is a documented value (`sandboxclaim_types.go:33-38,136-140`), and the v0.4.3 controller honours it by filtering warm candidates to that pool's label hash (`sandboxclaim_controller.go:626-632`), i.e. it **NARROWS** adoption rather than breaking it. ⚠️ **Verify on a non-production cluster first:** if your pool naming and `warmPoolSandboxLabel`'s `NameHash` disagree, narrowing selects nothing and *everything* cold-starts — which is exactly why this lands on v0.4.3, where it is trivially revertible. Note the obvious seam does **not** work if your integration monkeypatches the 0.4.3 helper: that helper has no `warmpool` parameter and builds the spec internally, so the create call must be replaced with your own manifest POST, atomically at creation.

29. **The Python SDK has ZERO controller-version skew tolerance in EITHER direction, because the API version is a HARDCODED MODULE CONSTANT, not negotiated — which FORCES the staged rollout order.** `k8s_agent_sandbox/constants.py`: at 0.4.3 `CLAIM_API_VERSION`/`SANDBOX_API_VERSION` are `'v1alpha1'` (lines 21, 25); at 0.5.6 and 1.0.3 both are `'v1beta1'` (same lines). The SDK passes these straight to `custom_objects_api.create_namespaced_custom_object(group=…, version=…)`, so SDK 0.4.3 against a v1.0.3 controller hits a path the CRDs no longer serve → **404**, and SDK 1.0.x against a v0.4.3 controller → **404**. **Consequence: you CANNOT run controller v1.0.3 in one cluster while another stays on v0.4.3 if both share ONE service image**, because that image carries exactly one pinned SDK with exactly one hardcoded version. **The ONLY window where one image works against two controller versions is v0.5.0–v0.5.6**, where both versions are served. **So the order is forced: (1) BOTH clusters to a v0.5.x controller — the old SDK keeps working untouched; (2) run `migrate.sh` bootstrap+migrate and prune `storedVersions` on both; (3) THEN bump the shared image's SDK to 1.0.x, which still works against v0.5.x controllers; (4) only then move controllers to v1.0.3 — and that step can finally be staged per-cluster.** Trying to stage at step 4 first inverts the dependency and breaks whichever cluster the image does not match. **Release boundaries for the individual SDK deltas** (verified across tags v0.4.3..v1.0.3): claim/sandbox `v1beta1` plus `create_sandbox(template→warmpool)` and `warmPoolRef` first appear in **stable v0.5.0**; `AsyncSandboxClient cleanup=True` in **v0.5.1**; `create_sandbox_claim` returning the API response in **v0.5.4**; `RETRYABLE_METHODS` excluding POST in **v1.0.0** — so "all introduced in v0.5.6" is imprecise wording. `FileEntry` also changes `mod_time: float` → `modified: datetime` at v1.0.0. The dependency pin is unbounded through stable v0.4.6 and `<34.0.0` at every stable v0.5.0–v1.0.3 tag.

30. **v0.5.0 and v0.5.1 BREAK warm-pool adoption for pre-existing v0.4.x sandboxes, SILENTLY — land on v0.5.2+.** `isAdoptable` at v0.5.0 (`sandboxclaim_controller.go:1885-1890`) and v0.5.1 (`:2021-2026`) compares `ownerRef.APIVersion` to the **full v1beta1 GroupVersion**, so v0.4.x warm Sandboxes whose `SetControllerReference` ownerRefs remain `v1alpha1` are **not adoptable**. v0.5.2/v0.5.3 switch to group+kind, and v0.5.4+ use `utils.MatchesGroupKind`. ⚠️ **LOGGING CORRECTION — in the normal controller-restart/upgrade path these are rejected with NO `V(1)` reason log at all.** The sandbox event handler computes `newAdoptable := isAdoptable(newSandbox)==nil` and adds only *true* candidates to the fresh in-memory queue (v0.5.0 `:1815-1850`; v0.5.1 `:1951-1986`) **with no else branch and no log**; the *"sandbox candidate can't be adopted"* message exists only in `getCandidate` **after** a key was already queued (`:713-745`), which cannot happen for pre-existing v1alpha1-ownerRef sandboxes after a process restart, because the event handler is the sole initial queue seeder. **Operational effect is zero warm hits and universal cold starts, with the diagnostics quieter than a reader would expect.**

31. **The SDK's v1.0.3 API deltas include three that are DANGEROUS rather than merely breaking — and one hard gate that is loud.** **Loud gate first:** an integration may pin a version guard that raises at **import** time on an unexpected SDK version, which crashes pytest **collection** across every module that transitively imports it — so CI cannot silently pass a bump. ⚠️ **But a green unit suite after a bump means "collection succeeded and the guard string was edited", NOT "behaviour preserved"**, because dispatch paths are typically mocked wholesale. **(1) `AsyncSandboxClient.__init__` gains `cleanup: bool = True`, registering an `atexit` hook that TERMINATES EVERY TRACKED SANDBOX at interpreter exit.** In a long-lived server that constructs one SDK client per claim and relies on fire-and-forget TTL, an instance scale-down would **delete live sandboxes**. **Must pass `cleanup=False`.** **(2) `async_connector.RETRYABLE_METHODS = {GET, PUT, DELETE}` is NEW — POST is no longer retried on 500/502/503/504.** If every dispatch in your system is a POST, you silently lose five retries. **(3) `_create_claim` now RETURNS the created claim** so `create_sandbox` can read `metadata.resourceVersion` to seed a single-watch readiness read — a monkeypatch that awaits the original and **discards** its return degrades that to a resourceVersion-less quorum read rather than crashing. Also renamed: `AsyncSandbox._close_connection` → `close_connection`. **Unchanged and safe to key off:** the claim-name shape `f'sandbox-claim-{uuid4().hex[:8]}'`, `SandboxRequestError(.status_code/.response)`, `ExecutionResult`, `SandboxDirectConnectionConfig`, `AsyncSandbox(...)`, `get_pod_name`/`terminate`/`connector.send_request`/`commands.run`/`files.read+write`.

32. **Four integration-surface breaks that a "bump the version string" change misses entirely — check all four on any release-asset-driven install.** **(1) THE RELEASE ASSET WAS RENAMED.** `manifest.yaml` is HTTP 200 for v0.4.3–v0.5.1 and **404 for v0.5.2 and every later tag**; the assets became `sandbox.yaml`, `sandbox-with-extensions.yaml`, `extensions.yaml`. Anything fetching the old name (e.g. a Terraform `data.http`) **fails at PLAN time, before any k8s object is touched** — the URL must change in the same commit. **(2) STRING-MATCH ARG PATCHING SURVIVES.** The quoted pair `- "--leader-elect=true"` + `- "--extensions"` in `extensions.yaml` and the unquoted `- --leader-elect=true` in `sandbox.yaml` are **byte-identical at v0.4.3 and v1.0.3**; the Deployment stays `agent-sandbox-controller` in `agent-sandbox-system`, not split, and there is no webhook Service in the v1.0.3 manifests (the webhook exists only in the v0.5.x transition manifests). All six tuning flags still exist (`cmd/agent-sandbox-controller/main.go:114-132`). **(3) ⚠️ BUT THE TUNING ARGS INVERT MEANING.** At v0.4.3 the concurrency defaults were **1**, so `--sandbox-concurrent-workers=10` RAISED throughput 10×. At v1.0.3 the defaults are **100 and 50** (`main.go:129-130`), so the SAME flags now **CUT** concurrency 10× and 5×. **Re-tune or drop them; keeping them silently is a throughput regression.** v1.0.3 also adds an optional ConfigMap `agent-sandbox-config` at `/etc/sandbox-config`. **(4) THE ROUTER LOOKS REPLACED AND IS NOT.** v1.0.x adds a full Go rewrite at top-level `sandbox-router/` published as `registry.k8s.io/agent-sandbox/sandbox-router-go`, but the **Python router is still present at v1.0.3** at `clients/python/agentic-sandbox-client/sandbox-router/sandbox_router.py` — the Go router is opt-in. `registry.k8s.io/agent-sandbox/sandbox-router` has **zero tags**: upstream never published the Python image, which is why downstreams build it. **BONUS DEAD CONFIG:** `sandbox-router.yaml` sets `env DEFAULT_NAMESPACE=agent-sandbox-system`, but in the Python router `DEFAULT_NAMESPACE` is a hardcoded module constant `'default'` (`sandbox_router.py:27`) never read from the environment at **either** version — the env var has always been a no-op, and routing works only because callers send `X-Sandbox-Namespace` explicitly.

## Stranded claims: the existence-vs-readiness defect

33. **A bound claim's sandbox lookup checks EXISTENCE and OWNERSHIP, never READINESS — and the Sandbox controller NEVER recreates an evicted-but-undeleted Pod. Upgrading to v1.0.2 does NOT fix this.** Verified by diffing the tags. **(a)** `getOrCreateSandbox` is **functionally identical** at v0.4.3 (`extensions/controllers/sandboxclaim_controller.go:1064-1075`) and v1.0.2 (`:1952-1968`): it accepts the cached Sandbox on Get-succeeds + `IsControlledBy` **alone**. `isSandboxReady` exists in both files but is used **only** for warm-pool candidate filtering (v0.4.3 `:788`, v1.0.2 `:1502`), never here. **(b)** `reconcilePod` creates only when Get returns `NotFound`; a Pod present in **Failed** phase falls to `reconcileExistingPod`, which fixes ownership/metadata and **never inspects `pod.Status.Phase` nor deletes it**. The only `r.Delete` paths are scale-to-zero and (new in v1.0.2) `Suspended` OperatingMode — neither applies. ⚠️ **`kubelet` node-pressure eviction sets `phase=Failed` WITHOUT deleting the Pod object**, so it lands exactly in the non-recreating branch. **(c)** The only v1.0.2 change is **cosmetic**: `computeReadyCondition` gained an early return giving Reason `PodFailed` (`v1.0.2:616-627`) where v0.4.3 falls through to the generic `DependenciesNotReady`. Clearer string, identical behaviour. **(d) TTL cannot rescue it:** `NeedsCleanup`/`ExpireAt` in `internal/lifecycle/expiry.go` factor the `Finished` condition **only when `TTLSecondsAfterFinished` is set** — a consumer that only ever patches `spec.lifecycle.shutdownTime` makes expiry **wholly independent of sandbox health**, so whether a stranded claim self-clears depends entirely on whether the owning service keeps refreshing `shutdownTime` blindly. ⚠️ **AND READ `claim-kind`, NEVER INFER KIND FROM THE SANDBOX NAME.** One sibling analysis concluded the stranded claims were *"all job-type and will self-clear"* — a misread of the AGENT-NAME prefix, which is uniform across kinds in some deployments. The authoritative label is the claim-kind label; the live split of 15 stranded claims was **2 chat / 13 job**, not 15 job. **Method note for reproducing:** join `sandboxclaims`' `status.sandbox.name` against the sandbox list and test the **Sandbox's Ready condition** — do NOT look for claims pointing at a MISSING sandbox; that count is **0**, because nothing is ever deleted and **readiness is the only thing lost**.

34. **⚠️ RECURRING DEFECT SHAPE, found independently three times in one day — a guard gates on EXISTENCE when the real failure mode is STATE DEGRADATION, so the error path never fires and the failure is SILENT.** Instances: warm-pool adoption accepting a still-`ContainerCreating` candidate (#21); bound-claim reuse accepting an evicted pod (#33); and a client-side claim lookup that resolves `.status.sandbox.name` and even **falls back to the claim name** rather than raising, so its `NotFound` and generic-except recovery branches only fire if the OBJECT is deleted — and it never is. **DIAGNOSTIC HEURISTIC worth reusing: when a failure is silent and "the retry should have caught it", do NOT start by hunting for a missing or dangling object. First ask what the recovery branch is KEYED on.** If it is keyed on `NotFound` / absence / an exception from a lookup, and the real-world failure only degrades a **status condition** while every object stays present, **the branch is unreachable by construction**. **The live tell is a census that returns ZERO dangling references while the symptom is widespread** — one such census returned 0 of 344, and the zero **was the finding**, not a refutation. **Corollary for fixes in this stack:** prefer gating on the **Ready condition** (already fetched in every one of these three paths, so it costs no extra API call) over gating on object existence.

35. **A client's terminal-reason set can DIVERGE from upstream's retry semantics, and the divergence fails claims upstream expects to recover.** `TemplateNotFound` is treated as **terminal** by one downstream reaper but has **ALWAYS** been **retryable** upstream — v0.4.3 `sandboxclaim_controller.go:264-271` and v0.5.6 `:387-401` both requeue after 1 minute with a nil error (comment: *"Requeue if dependency is missing, but don't return error to avoid log spam"*). The same applies to the new v1.0.3 reason **`WarmPoolNotFound`**, emitted from the identical retry branch (`:705`) — **do not add it to a terminal set either.** ⚠️ **And upstream's own `constants.TERMINAL_CLAIM_READY_REASONS` (v1.0.3 `constants.py:49`) is NOT a drop-in replacement**: it omits `TemplateNotFound` and adds `EnvVarsInjectionRejected` + `VolumeClaimTemplatesError`. A second-order effect worth naming: if the same set also gates an active-claim COUNT, terminal-vs-retryable disagreement under-counts or over-counts capacity.

36. **Warm-pool vs claim REVISION semantics: a new deploy recreates UNCLAIMED warm pods and never touches CLAIMED ones — which is precisely why a claimed sandbox stays on an old revision until its claim dies.** (a) With `spec.updateStrategy.type=Recreate`, `filterActiveSandboxes` in `extensions/controllers/sandboxwarmpool_controller.go` deletes stale sandboxes (staleness = pod-template-hash label mismatch over `template.Spec.PodTemplate`); **the default when unset is `OnReplenish`**, so this behaviour is opt-in. (b) `completeAdoption` (`sandboxclaim_controller.go` ~`:724-730`) **DELETES** the warm-pool label, `templateRefHash` and `podTemplateHash`, and reassigns `OwnerReferences` to the claim — so the pool's label-selector LIST never sees an adopted sandbox again. (c) **Revision identity on a live pod must come from the pod SPEC (an env var), NOT from labels**, because the controllers re-sync current-template labels onto live pods — reading a label tells you what the template says *now*, not what the pod was built from.

37. **Priority classes buy NOTHING for sandbox pods, and three independent blockers each settle it — measure before proposing one.** **(1) Co-tenancy:** a sandbox pod's only neighbours are system daemonsets at `system-node-critical` (2000001000) or `gmp-critical` (1000000000). The sandbox is **already** correctly the lowest-priority pod on its node and **should** be evicted first; raising it above `system-node-critical` would evict the CNI and `kube-proxy` instead and break the node. **(2) Warm-vs-active differentiation is IMPOSSIBLE:** `spec.priorityClassName` is **immutable**, and a warm pod becomes an active session by **in-place adoption** (`completeAdoption` patches labels and ownerRefs, it never recreates the pod) — so one pod cannot be low-priority while idle and high-priority once claimed. **(3) The CRD does not expose it:** grep for `PriorityClassName` across `api/`, `extensions/`, `controllers/` at v0.4.3 returns nothing, so `SandboxTemplate` cannot set it without an upstream change. Separately, **required `podAntiAffinity` means idle and active sandboxes never share a node**, so there is no idle neighbour to shed under pressure anyway. v1.0.2 *does* prioritise deleting unready sandboxes on scale-down (`sandboxwarmpool_controller.go` ~`:723-735`), but that is **scale-down ordering, not node-pressure relief**.

38. **Implementing #28's `spec.warmpool` de-risk: the SDK 0.4.3 helper cannot carry the field, so REPLACE the method rather than wrap it — and the replacement must return the created object.** `AsyncK8sHelper.create_sandbox_claim(name, template, namespace, annotations, labels, lifecycle)` (`async_k8s_helper.py:60-102`) has **no `warmpool` parameter, builds `spec` internally, and returns `None`**, so a pre-existing `*args/**kwargs` forwarding wrapper is a dead end — the field has to go in a manifest you build yourself and POST through `helper.custom_objects_api.create_namespaced_custom_object`, **atomically at creation** (a post-create patch races the controller, and post-upgrade also the conversion webhook). Keep the original in a local and restore it in `finally`; the method is swapped for exactly one `create_sandbox` call.
