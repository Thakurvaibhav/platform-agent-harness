# ArgoCD Learnings

See also: `learnings-helm-ci.md`, `learnings-progressive-delivery.md`, `learnings-operators.md`, `learnings-crossplane.md`, `learnings-terraform.md`

Numbered, append-only. **Update the existing entry — never duplicate.**

## Sync & ordering

1. **`ignoreDifferences` requires `RespectIgnoreDifferences=true` in `syncOptions`.** Without this option, ArgoCD still overwrites the live value during sync even though the diff is hidden in the UI. Symptom: live values keep resetting after each sync.

2. **Sync-waves on Application objects only enforce ordering during app-of-apps sync.** They do NOT control when Applications sync their own contents. For guaranteed ordering between independent child Application syncs, use a multi-PR phased approach.

    **Stale failure diagnostic:** a `Failed` `.status.operationState.message` can predate the dependency it complains about. Compare `finishedAt` with when the CRD/XRD landed before diagnosing a schema bug; in one case the new enum arrived fourteen seconds after retries were exhausted. A server-side dry-run of the exact object (`kubectl patch <the exact object> --dry-run=server`) returned `patched`, proving current admission accepted it and only the sync needed to retry. For an SSA diff reproduction, use #35. Separate schema-owning and claim-owning Applications have no inherent ordering guarantee, so close-together schema and consumer merges can trigger this race.

3. **Sync-wave `"5"` is the right default for CRD-dependent resources.** Wave 0 installs the operator and CRDs; wave 5 gives time for CRDs to be Established before the dependent resources sync. Do NOT use `"1"` — too close to default and races with CRD installation.

## Values & naming

4. **Values key naming must be lowercase kebab-case** when keys become Helm release names downstream. Avoid camelCase. Use `index .Values "key-name"` for hyphenated keys in templates.

5. **GKE-targeted ArgoCD apps need a `values/providers/gcp.yaml`.** When an argo-apps entry targets a GKE cluster, always include the GCP provider values file alongside the app entry. Check existing entries for the pattern — omission causes silent platform-detection mismatches downstream.

## Drift & ignoreDifferences

6. **SSA + API-server-injected fields cause sync loops on DaemonSets.** The `deprecated.daemonset.template.generation` annotation causes perpetual OutOfSync diffs with `ServerSideApply=true`. Fix: `ignoreDifferences` with `jsonPointers: [/metadata/annotations]` scoped to the specific resource with `name:` and `kind:`. `jqPathExpressions` does not work for this case in ArgoCD v2.12 — the `jsonPointers` form scoped by name should be the default pattern for any DaemonSet annotation drift.

7. **Operator webhook `failurePolicy` drift.** Operators (Istio, others) that dynamically patch `failurePolicy` on ValidatingWebhookConfigurations at runtime will always cause ArgoCD drift. Add `ignoreDifferences` with `jsonPointers` for `/webhooks/0/failurePolicy`.

## Rendering caveats

8. **ArgoCD does NOT pass `--kube-version` to `helm template`.** `.Capabilities.KubeVersion.GitVersion` is empty in ArgoCD rendering, so charts that auto-detect platform (e.g. checking for the `-gke` suffix) silently fail. Always set platform-specific values explicitly in provider files rather than relying on capability detection.

## Namespace & sync options

9. **Create namespaces in the chart, not via `CreateNamespace=true`.** Platform/infra charts (policy engines, runtime security agents, cert managers, service meshes, gateway controllers, progressive-delivery controllers) must include a `templates/namespace.yaml` that renders the Namespace. This makes the namespace declarative, version-controlled (labels/annotations), and cleanly pruned on app deletion. Only legacy/simple services may still use `CreateNamespace=true`. New charts must always follow the chart-managed pattern.

10. **`ApplyOutOfSyncOnly=true` reduces noise and apply churn** on large applications. Most repos should set it. Don't combine with aggressive self-heal on stateful workloads.

11. **`ServerSideApply=true` is required for any chart that installs CRDs.** CRDs are large and routinely exceed the 262KB `metadata.annotations/last-applied-configuration` limit with client-side apply. Charts without CRDs do not need it.

12. **`CreateNamespace=true` conflicts with charts that include a Namespace template.** Before adding to `syncOptions`, check:
    ```bash
    grep -r "kind: Namespace" charts/<chart-name>/templates/
    ```
    If found, omit `CreateNamespace=true`.

## Tag-based rollouts

13. **SUPERSEDED in part by the immutable-promotion guidance below — do not use the older mutable-promotion-tag recommendation.** **For tag-based rollouts**, never use commit SHAs as `targetRevision` in production. Use named tags (e.g. `stable-v1.2.3`) plus a mutable promotion tag. ArgoCD tag-based sync is eventually consistent — recheck after 2–5 minutes before troubleshooting.

    **Prod pinned to an IMMUTABLE GIT TAG *plus* `autoSync` + `selfHeal` is the combination to recommend, because it separates RECONCILIATION from DELIVERY.** Auto-sync scoped to a pinned revision **cannot pull in an unpromoted change** — the revision only moves when a promotion PR merges — while `selfHeal` still corrects hand-made drift on prod continuously. **You get continuous reconciliation WITHOUT continuous delivery.** People reflexively argue `autoSync` is unsafe for prod; **that objection only holds when `targetRevision` tracks a BRANCH.** **Prefer bumping `targetRevision` to a NEW immutable tag via PR over force-moving a floating `prod` tag:** the former leaves an auditable PR record and **the promotion PR becomes the approval artifact that replaces `terraform plan`**; the latter makes a force-push the deploy. **Mandatory consequence to socialise: once prod is tag-pinned, a change merged to the trunk is live on dev/staging and INVISIBLE on prod until the tag moves** — tooling must report pinned clusters as **DEFERRED, not FAILED** (`learnings-k8s-sa.md`), and expect 2–5 min sync lag after the revision moves (as above). **This model also structurally closes a "staging does not gate prod" gap** where staging and prod deploy from the same merge: staging becomes a stage because the structure makes it one, not because a policy asks people to wait.

    **READ-TIMING trap when verifying a `targetRevision` bump landed: an Application queried moments after merge can still report the OLD `spec.source.targetRevision` while its `status.sync.revision` already shows the NEW tag's SHA.** Observed reading one value on a first query and the next on a re-read minutes later with nothing done in between. **Do not conclude "the bump did not land" from a single read of `spec.source.targetRevision`** — cross-check `status.sync.revision` against the tag SHA (`git rev-list -n1 <tag>`) and re-read after the reconcile interval before reporting a lag.

## Drift & ignoreDifferences (continued)

14. **Setting only `ServerSideApply=true` (without also setting `ServerSideDiff=true`) engages server-side-apply for the actual sync, but diffs still use client-side diff logic — the two syncOptions are independent, not a package deal.** That means: syncs use the SSA field manager for apply (so you get past the ~262KB last-applied-configuration annotation limit that breaks client-side apply on large objects like CRDs), but the drift/diff view keeps computing differences the old client-side way rather than switching to full SSA-diff semantics (which would show every server-owned field as a diff and over-report). This is usually the combination you want: SSA apply where you need it (large or CRD-installing resources) without SSA diff turning on cluster-wide over-reporting. (argoproj/argo-cd#22151.)


## Health status & sync-wave gating

15. **ArgoCD's own `Application`-of-`Application`s health customization was removed upstream, and its absence has a silent failure mode that a green-looking parent app can hide entirely.** Two facts compound: (1) Application health assessment was removed upstream (Argo CD v1.8, argoproj/argo-cd#3781) and there is no shipped `health.lua` for it anywhere in argo-cd's own resource-customization tree — the only surviving trace is a documentation snippet under the operator manual's health-assessment page, in the *flattened* `argocd-cm` key form; a Terraform- or Helm-managed `resource.customizations` block using the *nested* map form must transpose that snippet, not paste it verbatim. Without ANY override, a child `Application`'s health is `nil` and every non-hook sync task auto-succeeds — sync waves never actually gate on child health at all, silently defeating the entire reason for using sync waves in an app-of-apps layout. Verified at Argo CD v3.3.6 / gitops-engine `sync_context.go:477-492` + `sync_tasks.go:274-276`: with the override correctly in place, a `Progressing` child BLOCKS wave progression and a `Degraded` child FAILS the whole app-of-apps sync — but (2) the parent's own health ROLLUP ignores `Unknown` children when aggregating (`controller/health.go:73-75`), and any child whose own `status.health.status` is empty, missing, or not a recognized enum value becomes `Unknown`. The net effect: a wave can stall forever on an `Unknown` child while the PARENT still reports fully `Healthy` — nothing goes `Degraded`, nothing pages, nothing looks wrong from the top. When adding or debugging this customization, assert that every child health script only ever emits a recognized enum value, and treat "a wave that never advances, with a green parent" as this exact signature.

    **Source and rollout scope:** the recorded verification used gitops-engine `v0.7.1-0.20250908182407-97ad5b59a627`; `controller/sync.go:309` feeds the customization into the engine, and `util/lua/lua.go:590-595` validates health codes. Both `Progressing` and `Unknown` keep sync tasks `Running`. The upstream snippet is in `docs/operator-manual/health.md` under "Argocd App", using `resource.customizations.health.argoproj.io_Application`; nested configuration uses `<group>/<kind>` plus `health.lua`. Before enabling this globally, inventory every Application with a `sync-wave` annotation and define intended gating, timeout and escape semantics. Review the change as sync ordering, since an unhealthy child can stall later waves. See #34 for bundled Crossplane health checks.


## Sync policy & autosync semantics

16. **Checking `.spec.syncPolicy.automated != null` to detect whether auto-sync is enabled is wrong — the block EXISTS on a disabled app too.** A disabled application carries `{"enabled": false, "prune": true, "selfHeal": true}` rather than an absent block, so a presence check reports `true` (auto-sync enabled) when it is actually off; `== true` on the whole object is equally wrong for the same reason. The correct predicate checks the `enabled` sub-field specifically against `false`: `.spec.syncPolicy.automated.enabled != false`. This is the same "presence read as OK" bug shape that shows up anywhere a nested optional block can exist-but-be-disabled rather than exist-or-not; it produces confidently wrong diagnoses in ad-hoc tooling, not just in formal checks.

    **Per-cluster pre-flight:** auto-sync can differ between a workload Application and its app-of-apps parent, and between clusters. Inspect each app's actual sync policy before expecting a merge to converge. In the recorded setup, an out-of-band `syncPolicy.automated.enabled: false` remained absent from desired config and was not removed by parent self-heal, but a direct sync cleared it; samples an hour apart differed after manual syncs during a rollout. Treat that as observed transient drift, not standing cluster policy: it can block delivery while the app reports `Healthy`, and can recur. Recheck before a gated rollout. For an existing automated block, testing the `enabled` key with `== true` also misses its enabled-by-default absent-key form. See #19 for the decisive effect of explicit `false`.


## Drift & ignoreDifferences

17. **Duplicate entries in an associative-list field (a list field keyed by a merge-key like `name`, e.g. container `env`, `volumes`) are accepted by Kubernetes API validation but dangerous under Server-Side Apply — and the resulting error names the wrong thing.** Any field carrying a Kubernetes list-map merge-key annotation has no uniqueness check in the API server's own validation, so a manifest with two same-keyed items in that list applies fine under plain client-side apply. Under Server-Side Apply, the structural merge treats duplicate-keyed entries as ONE logical item and merges their fields together — which can set mutually-exclusive fields on the same merged item and fail with an error message that looks completely unrelated to duplication (e.g. a "may not be specified together" error on two fields that were never meant to coexist). This can also differ from how a DOWNSTREAM consumer resolves the same list (e.g. a process reading env vars via a last-write-wins map), so reading only one layer's source code can look authoritative while a different, earlier layer (the apiserver's own SSA merge) actually gates the behavior first. Whenever the question is "does my new value override the built-in one," resolve it against the ACTUAL apply path in use (client-side vs Server-Side Apply) and confirm empirically with a read-only diff against the live object, not by reading source alone.

    **Concrete signals:** the merge-key schema includes `x-kubernetes-patch-merge-key`; the misleading env error can be `valueFrom: may not be specified when value is not empty`, while kubelet's downstream map resolution is in `pkg/kubelet/kubelet_pods.go`. Inspect the Application's `syncOptions` for `ServerSideApply=true` and reproduce that path with the exact non-mutating diff command in #35.


## Pruning semantics

18. **Pruning a `CronJob` through GitOps CASCADE-DELETES its spawned `Job`s and their pods — the standard claim "in-flight Jobs are unaffected and will finish" is false for any CronJob removal.** Jobs spawned by a CronJob carry an owner reference to it with `blockOwnerDeletion: true`, so deleting the parent takes every Job it owns with it — including manually-triggered ones that still carry the CronJob as an owner even without a controller-managed label. Retained Jobs kept around by a job-history limit are garbage-collected the same way and are not separately tracked by the GitOps tool as "its" resources. Before writing a claim like "removing this CronJob is safe, in-flight runs will complete," verify the actual owner references on any running Jobs with a direct read (`kubectl get jobs -o json` and inspect `ownerReferences`) — don't assume Kubernetes ownership semantics match the intuitive claim.

    **Ownership check:** even a manually created Job with `controller: null` in its owner reference can still belong to the CronJob. Inspect `ownerReferences`, not labels; `successfulJobsHistoryLimit` does not detach retained Jobs.


## Sync policy & autosync semantics

19. **`automated.enabled: false` wins over `selfHeal`/`allowEmpty` unconditionally — adding those flags to an application whose sync policy already carries `enabled: false` is completely inert.** At Argo CD v3.3.6, the sync-policy predicate that gates automated sync (`SyncPolicy.IsAutomatedSyncEnabled`, `pkg/apis/application/v1alpha1/types.go:1488-1493`) returns false whenever `automated.enabled` is explicitly false, and never consults `selfHeal` or `allowEmpty` at all — so an app in that state will not self-heal no matter what else is set on the same policy block. If the disabling was applied out-of-band (manually, not through the GitOps source), it also cannot necessarily be fixed by re-applying the desired config through your normal IaC path if that path never explicitly sets `enabled` itself — check whether your provisioning code emits the `enabled` key at all, or whether it's silently relying on the default.

20. **`ignoreDifferences` combined with `ApplyOutOfSyncOnly=true` can report an application fully `Synced` while a changed desired value NEVER actually lands.** If a field is covered by `ignoreDifferences`, a git-side change to that field produces no visible diff, so the app shows `Synced`; with `ApplyOutOfSyncOnly` enabled, a resource showing no diff is never re-applied at all — so the new desired value silently never reaches the live object, even though git and the sync status both look correct. Concretely: a chart change that lowers a workload's replica count can leave the live replica count completely unchanged while the app reports `Synced`. Fixes, in order of preference: remove the now-obsolete `ignoreDifferences` entry so the real diff surfaces again; make a one-time manual change to match the new desired value (it then "sticks" because git and live agree); or wait for an unrelated full apply (e.g. an image bump) to happen to also carry the field through. Whenever a chart change makes an existing `ignoreDifferences` entry obsolete, remove the entry in the SAME change, not as a follow-up.


## Drift & ignoreDifferences

21. **Under `ServerSideApply=true`, a SPECIFIC-KEY `ignoreDifferences` jsonPointer does not suppress a controller-injected annotation — only the WHOLE-BLOCK form does.** A per-key pointer targeting one specific annotation key fails to clear an out-of-sync status when a different controller injects that exact annotation at runtime and the app uses Server-Side Apply — even combined with `RespectIgnoreDifferences=true` and a hard refresh. The whole-block form (pointing at the entire `/metadata/annotations` subtree on the affected resource kind) does work. Root cause: the desired manifest renders an empty annotations block while live carries the injected key, and under SSA the per-key normalization doesn't clear a key that desired never declared at all, while the whole-subtree ignore does. This is the SSA-specific counterpart to the same whole-block pattern needed for injected annotations under plain client-side apply — the reason (a controller injecting a key the chart never declares) is the same, but the mechanism that fails to suppress it differs by apply mode. Always verify an `ignoreDifferences` fix against the LIVE application (patch it, hard-refresh, confirm it goes fully synced) before claiming it works — a correctly-rendered `ignoreDifferences` entry is not proof it actually suppresses the diff under your apply mode.

    **Recorded scope:** the Service case was verified on ArgoCD v3.3.6 with `/metadata/annotations/cloud.google.com~1neg`, an empty desired annotations map, `RespectIgnoreDifferences=true` and a hard refresh. The working per-app rule used `jsonPointers: [/metadata/annotations]` on `kind: Service`. The DaemonSet case in #6 also explicitly used `ServerSideApply=true`; the earlier client-side characterization above is not evidence of a separately verified client-side case.

    **GKE example:** the NEG controller can inject `cloud.google.com/neg={"ingress":true}` on a ClusterIP Service whose chart renders `annotations: {}`, creating cosmetic drift. This specific annotation is GKE-related; EKS has no GKE NEG controller. For affected Services across a GKE fleet, prefer a global `argocd-cm` `resource.customizations` rule over repeating per-app rules. For the recorded per-app SSA case, use the whole-block form above.


## Server extensions, values & sync phases

22. **`server.extensions` Helm values use `extensionList` not `contents`**: argo-cd chart v9.5.0 (ArgoCD v2.13.x) uses `extensionList` with an `env` list containing `EXTENSION_URL` (and optionally `EXTENSION_CHECKSUM_URL`). The older `contents` + `url` structure is deprecated and silently ignored, making extensions a no-op. Correct form:
    ```yaml
    server:
      extensions:
        enabled: true
        extensionList:
          - name: argo-rollouts
            env:
              - name: EXTENSION_URL
                value: https://github.com/argoproj-labs/rollout-extension/releases/download/v0.3.6/extension.tar
    ```

23. **Argo Rollouts UI extension repo is singular `rollout-extension`**: The GitHub repository is `argoproj-labs/rollout-extension` (singular), not `rollouts-extension` (plural). The plural URL returns 404. v0.3.6 and v0.3.7 both release only `extension.tar` — no checksums file is published, so `EXTENSION_CHECKSUM_URL` cannot be set for either version. The v0.3.7 extension.tar URL is confirmed valid (HTTP 302 redirect to release asset).

24. **ArgoCD Application `valueFiles` entries must reference existing files**: When adding a cluster-specific `valueFiles` entry in `charts/argo-apps/values.<cluster>.yaml` (e.g., `values-<cluster>.yaml`), the referenced file MUST exist in the chart source directory (e.g., `charts/<chart>/`). ArgoCD fails sync with "value file not found" if missing. Minimum content: one valid key-value pair matching the chart's values schema.

25. **Argo Rollouts UI extension needs server-side proxy backend**: Installing the Rollouts extension tarball (via `server.extensions.extensionList`) only provides the UI panel. Promote/Abort buttons are non-functional without server-side proxy config: (1) `configs.params.server.enable.proxy.extension: "true"` in `argocd-cmd-params-cm`, (2) `configs.cm."extension.config"` (quoted key) with `|` literal block pointing to `http://argo-rollouts-dashboard.argo-rollouts.svc.cluster.local:3100`, extension name `rollout` (singular). HTTP is correct for in-cluster `svc.cluster.local`. Workaround: port-forward to rollouts dashboard on port 3100.

26. **Do NOT use `group: ''` (empty string) for core API resources in `ignoreDifferences`**: ArgoCD API server normalizes by stripping the empty group field entirely, but the rendered manifest includes it, causing a perpetual OutOfSync diff on the Application resource itself. Simply omit the `group` field for core API resources (Service, ConfigMap, etc.). Only specify `group` for non-core APIs (e.g., `group: apps`, `group: gateway.networking.k8s.io`).

27. **To validate one argo-apps Application template, isolate it with `--show-only`**: A full-stream `helm template charts/argo-apps -f values.<cluster>.yaml` can hit an unrelated YAML parse artifact from another app in the stream. To verify a single Application renders correctly, use `helm template ... --show-only templates/services/<app>.yaml`. (See `learnings-k8s-sa.md` for the provider-specific `imagePullSecrets` rule on the rendered `helm.values` block.)

28. **Independent infra charts inject `global.clusterName` via inline `helm.values`**: Infrastructure charts deployed as their own ArgoCD apps (istio-base, istio-cni, ztunnel, argo-rollouts — rather than through an umbrella) cannot inherit `global.clusterName` from an umbrella values file. Inject it per-cluster through the `source.helm.values: |-` inline block in the argo-apps values file. The Application templates (e.g. `charts/argo-apps/templates/services/istio-base.yaml`) already support this via the `{{- if .Values.<app>.source.helm.values }}` block.

29. **DANGER: do NOT use a conditional `jqPathExpression` keyed on a field that is itself added/removed by the controller**: E.g., a `jqPathExpression` that does `select(.metadata.labels["rollouts.argoproj.io/gatewayapi-canary"] == "in-progress") | .spec.rules` silently STRIPS the entire HTTPRoute when the label is absent (no-canary state), because jq select on a missing field returns empty. ArgoCD then diffs the live resource (with rules) against the "empty spec" normalized version and reverts it. The safe pattern: use `jsonPointers` for the label itself AND a separate unconditional `jqPathExpression: .spec.rules` (no select guard). See `learnings-progressive-delivery.md` for the HTTPRoute-specific fix. **Apply-mode caveat:** a whole-list jq ignore under client-side apply can make three-way merge delete the live list while reporting Synced. Validate the normalized output and actual apply path before using the unconditional whole-list form.

30. **A sync operation triggered just BEFORE a merge stays PINNED to that old revision and keeps retrying the stale manifest**, even after `.status.sync.revision` advances to the new merge commit. Diagnose via `.status.operationState.operation.sync.revision` (the OP target) vs `.status.sync.revision` (synced): if opTarget != merge commit and opPhase=Running/retrying, it's a stale op masking a correct merge. Example: `<app>` on `<cluster>` keeps retrying an old route with 21 rules, exceeding the Gateway API 16-rule cap, while sibling clusters sync the merge commit. Fix: `argocd app terminate-op <app>` → autoSync re-runs at the latest revision. The merged manifests were correct; only the stale op was the blocker.

31. **PreSync Jobs cannot consume secrets created by a TRACKED operator CR — phase-ordering deadlock**: A PreSync migration Job that references keys from an operator-managed Secret (e.g. an Infisical-managed `<secret>`) deadlocks when a NEW key is added: the InfisicalSecret CR is tracked and only reconciles in main-sync, which runs AFTER PreSync, so the new key literally does not exist in the Secret when the Job's container starts (`couldn't find key <X>` / CreateContainerConfigError). Polling inside the Job cannot fix it. Two approaches from the recorded case: (a) stamp `optional: true` on the migration container's secretKeyRefs (safe when the Job only needs always-present DB creds + a waitFor gate; implementable as an env-helper param, default strict, only the migration container opts in); (b) make the operator CR itself an UNTRACKED PreSync hook. For hook CRs that must PERSIST between syncs for continuous operator reconciliation, use a PreSync hook with NO hook-delete-policy (contrast: use `BeforeHookCreation,HookSucceeded` when the CR should be recreated each sync). Order early waves: InfisicalSecret at wave -10, before namespace (-3), ServiceAccount (-2), migration Job (-1); ArgoCD advances on CR apply (not operator reconciliation), so the race mitigation is probabilistic but reliable in practice with a ~10s operator resync.

## SSO, health customization & apply semantics

32. **ArgoCD Okta (OIDC) SSO gotchas.** Okta may **not return `groups`** in the ID token even when requested — ArgoCD works around this with `enableUserInfoGroups: true` + `userInfoPath` (fetches groups from the userinfo endpoint) and caches groups up to token expiry. Also, `policy.default` is a **non-revocable baseline for every authenticated user** — setting it to `role:readonly` conflicts with strict least-privilege (there is no way to deny it to a subset); leave `policy.default` empty (no access) and grant via explicit group→role bindings if you need least-privilege.

33. **A Terraform Helm-values heredoc may not be valid YAML until interpolation, so static ArgoCD ConfigMap validation must extract-and-dedent the subtree.** `modules/aws_eks_cluster/argocd.tf` contains pre-existing unquoted Terraform ternaries whose `:` is YAML-invalid pre-evaluation. To lint `resource.customizations` / `resource.exclusions` offline, pull the `configs` subtree out, dedent it, and parse `configs.cm` on its own rather than trying to parse the whole heredoc.

34. **ArgoCD v3.3.6 already BUNDLES the Crossplane health checks as compiled-in wildcards — they are not in `argocd-cm`, and the only real gap is CUSTOM composite groups.** `resource_customizations/_.upbound.io/_/health.lua` covers **all** `*.upbound.io` provider MRs (including Crossplane v2 namespaced `cloudplatform.gcp.m.upbound.io` / `iam.aws.m.upbound.io`), and `_.crossplane.io/_/health.lua` covers `*.crossplane.io` (XRD/Composition) plus `pkg.crossplane.io` (Functions/Providers). Both read `status.conditions` (Ready / Synced / LastAsyncOperation) → `Degraded` on failure, and special-case `ProviderConfig`/`ProviderConfigUsage` → `Healthy` (they carry no status). **So: no custom Lua for provider MRs, XRD, Composition or Functions, and no `ProviderConfigUsage` exclusion needed for correctness.** The **gap**: a custom composite XR group (e.g. `platform.example.com/XRole`) matches NEITHER wildcard, and ArgoCD defaults unknown resources to **Healthy** — a false-green. One `resource.customizations.health.<group>_<Kind>` copying the bundled Ready/Synced logic fixes it, and because `function-auto-ready` makes the composite `Ready` a truthful aggregate (True only when every composed MR is Ready), that single composite Lua fully backstops sync-wave ordering. **Do NOT add an `observedGeneration` gate to it**: the bundled Lua deliberately omits one (Crossplane recomputes composite `Ready` each reconcile, and composite conditions do not reliably stamp `observedGeneration`), so gating risks a false-RED pinned `Progressing` forever until sync timeout. Verify the bundled set for any version with `gh api repos/argoproj/argo-cd/contents/resource_customizations?ref=<tag>`. See `learnings-crossplane.md`.

    **Wildcard coverage and proof:** use one generic wildcard in the unified `resource.customizations` key for a composite API group with a shared Ready/Synced contract. The flattened `.health.<group>_<kind>` form cannot hold a `*`. The old glob-eval bug `argoproj/argo-cd#16905` was fixed by `argoproj/argo-cd#20232`, released in v2.13.0. Verify the customization is active by reading the node's health message: it should equal the Lua's `ready.message`, rather than merely showing default-green. If `resource.exclusions` intentionally excludes `ProviderConfigUsage`, confirm zero nodes of that kind in the tree; as above, that exclusion is not required for bundled health correctness.

    **Sampling caveat:** in one comparison, AWS IAM `Role` + `RolePolicy` (2 managed resources) reconciled in ~1–3 s, while GCP service account → workload identity → N× `ProjectIAMMember` took ~58 s. A 4 s poll captured GCP `Progressing` but missed AWS's window. This is a sampling artifact, not proof of a coverage gap or a universal provider latency guarantee; use ~1 s polling or a longer-provisioning profile when capturing that transition matters.

35. **`kubectl diff -f` FALSE-FAILS against an ArgoCD-managed object when your change REMOVES a mutually-exclusive field — you must diff the way ArgoCD applies.** Objects applied by ArgoCD carry `manager=argocd-controller`, `operation=Apply` (server-side apply) and **no** `kubectl.kubernetes.io/last-applied-configuration` annotation, so a plain `kubectl diff -f` falls back to a 2-way merge that **KEEPS the field you deleted**. Concrete case: swapping a `Telemetry` from `spec.selector` to `spec.targetRefs` returned `only one of targetRefs or selector can be set`, even though the rendered manifest contains no `selector`. **The correct, still non-mutating reproduction of ArgoCD's real apply**: `kubectl diff --server-side --field-manager=argocd-controller --force-conflicts -f <rendered>` — SSA relinquishes the unowned field and the diff is accepted. Check ownership first with `kubectl get <obj> -o json --show-managed-fields | jq '.metadata.managedFields[].manager'`, and run **that** command unprefixed because rtk strips `managedFields` from `kubectl -o json` output.

## Live state, fleet proofs & values-file retirement

36. **Before deleting a template from a BRANCH, check whether a hand-made ArgoCD Application tracks that branch — `git grep` in `charts/argo-apps` cannot prove a cluster has no app for a chart.** A cluster values file may have no `<app>` block while a live Application was manually created on `<cluster>` and tracks `feature/<test-branch>`. A PR that deleted a static template from that same branch made **PUSHING the branch — not merging it — the destructive act**: with auto-sync + prune, the app would have deleted the live XRole and torn down the backing IAM role. **Safe cutover shape**: point the app at the templated values with the feature enabled FIRST, so the templated object is spec-identical to the static one (same `metadata.name`/`namespace`, same spec fields) and replaces it **in place with no teardown**; only then remove the static template.

37. **A bundle Application showing `OutOfSync` on preview-owned resources is pre-existing preview drift, NOT a chart defect — read the `argocd.argoproj.io/instance` label on the LIVE object before blaming the chart.** When PR-preview Applications and a bundle render the SAME resource names in the SAME namespace, they fight for ownership across resources such as ServiceAccounts, CronJobs, Services and Deployments. The live object carrying `argocd.argoproj.io/instance: <chart>-pr-<N>-preview` instead of the bundle's own instance label is the tell. See `learnings-crossplane.md` for preview lanes reachable from a host-cluster change.

38. **Re-check sync state before concluding a diff is PERMANENT on a freshly-synced app.** A `ClusterProviderConfig/default` on `<cluster>` read `OutOfSync` when checked at ~78 s of object age, mid-`selfHeal`; it self-healed to `Synced/Healthy` within 1–2 min via ServerSideApply. It was NOT a persistent defaulted-field diff and an `ignoreDifferences` entry would have been wrong. **A transient OutOfSync during initial sync is normal; give the app a settle window (or check `.status.operationState`) before adding a permanent workaround.** Related: ArgoCD poll lag can make a cluster look un-updated post-merge — compare `.status.sync.revision` to the merge commit before diagnosing a failure, and hard-refresh (`learnings-crossplane.md`).

39. **The strongest proof for a per-cluster `argo-apps` values PR is a FLEET SWEEP with a negative control, not a diff of the target cluster.** Render EVERY `values.<cluster>.yaml` before and after from a bash script, diff each, and report an UNCHANGED/CHANGED table with one row per cluster — that proves both that the intended cluster moved AND that the shared default in `values.yaml` was untouched and every sibling frozen cluster stayed put. Extract per-app revisions with `yq eval 'select(.kind == "Application") | .metadata.name + " => [" + (.spec.source.targetRevision // "<KEY-ABSENT>") + "]"' render.yaml | sort -u`. **NOTE: `yq eval-all` mangles this into a cartesian mess — use `yq eval` (per-document).** Render the **ArgoCD Application**, not the underlying Helm chart: for an `argo-apps` values PR the Application manifest is the artifact under test.

40. **A `targetRevision` anchor-bump's negative control FLIPS POLARITY as the rollout progresses — never copy the previous bump PR's control blind.** The payload behind an anchor tag is **host-cluster-scoped**, so WHICH clusters render new objects at the new tag changes every time a chart PR adds a host-cluster values block. Two traps in the same family: (a) "render an out-of-scope cluster at old-tag vs new-tag, expect EMPTY" is valid only while that cluster has no values block for the payload — once a chart PR adds one, the render is non-empty, **and that non-emptiness is precisely the right control for a deliberately EXCLUDED cluster: it proves the payload exists at the tag and only the un-bumped pin holds it back**; (b) "render the already-bumped clusters across old-tag vs new-tag, expect empty" is wrong once they carry the block. **The containment-meaningful render is each cluster's CURRENT pin vs the new tag** (expect 0 added / 0 removed / 0 changed). **Rule: derive the control from what that cluster's values actually contain at each tag, and report the measured result even when it contradicts the brief.** Also **re-read the `valueFiles` stack per cluster rather than inheriting it** — sibling clusters can differ on the provider values file.

41. **When rendering uses LIVE Application `valueFiles`, retire a referenced values file in two phases.** A CI job that renders the PR branch's chart content against the **LIVE cluster Application spec's `valueFiles`**, rather than the PR branch's `argo-apps` values still passes the now-deleted path to `helm template` and dies with `Error: open <cached>/charts/<chart>/values/environments/<env>.yaml: no such file or directory`. A PR cannot mutate live cluster state, so no amount of same-PR `argo-apps` editing fixes it. **CORRECT PATTERN:** (phase 1) empty the file to a placeholder **and** remove the `argo-apps` references in one PR; (phase 2) delete the file in a follow-up PR once `argo-apps` has reconciled and the live Application specs no longer list it — verify per cluster with `kubectl -n argocd get application <app> -o jsonpath='{.spec.sources[*].helm.valueFiles}'`, **never from the repo**. **Placeholder content matters**: a comment-only YAML file FAILS `yamlfmt --lint` (it strips comments to nothing), so the tombstone needs a literal `{}` body plus the comments. **Second-order win**: the placeholder also eliminates a post-merge `ComparisonError` window — apps pinned to `targetRevision: main` resync the moment main moves, while their live spec only drops the stale `valueFiles` entry once `argo-apps` reconciles (for example, ~7 min with a 300s interval + 120s jitter, or ~3 min with 120s + 60s). No workload impact in that window (cannot render ⇒ cannot sync ⇒ running resources untouched), but it shows as `ComparisonError`. **REJECTED FIX: `ignoreMissingValueFiles`** — it makes every typo'd `valueFile` silently no-op fleet-wide. **And note prod clusters passing that CI job prove NOTHING about a prod change when they pin an anchor tag** (both sides of the diff render the same tag); prod proof must come from local rendering at the anchor. Complements #24 (the file must exist); a diff-viewer CI job is not necessarily a deployment gate.

42. **A branch-deploy leaves an untracked live override that OUTLIVES the branch, and the breakage surfaces later on an unrelated PR.** For example, a schema-owning Application was hand-pointed at `feature/<schema-change>` for testing. The PR merged, GitHub deleted the branch, and the app went `sync=Unknown` with `unable to resolve <branch> to a commit SHA`. The cluster kept serving the last-rendered manifests, so **everything looked Healthy**. A later consumer PR failed admission with `Unsupported value: <new-enum-value>` because that cluster had never received the XRD from the schema PR. **`selfHeal` did NOT repair it**: the child Application spec was hand-edited and the app-of-apps parent did not revert `targetRevision`. Rules: (1) after merging a branch you deployed, repoint the app to `main` **in the same breath** — treat it as part of the merge, not a separate task; (2) `sync=Unknown` / `ComparisonError` is NOT benign — it means desired state is FROZEN at the last successful render; (3) when a claim is rejected for an unknown enum/field value, suspect a **stale CRD/XRD on that cluster** before suspecting the claim.

## Fleet enumeration, image pins & destructive tests

43. **A fleet-matrix script that reads a values gate BY KEY NAME fails SILENTLY when the key is not what you think — it returns `None` for every pair, which reads as "nothing is enabled" rather than erroring.** Enumerate `(cluster, app)` pairs from a STRUCTURAL marker (e.g. the presence of `.<app>.source.helm.valueFiles`) rather than a boolean key, and **assert the expected pair count** so a key rename cannot silently empty the matrix. **Corollary, and the more general one: value inheritance is NOT uniform across a layer stack — never assume a key resolves from the layer you expect; resolve it PER PAIR.** An audit that assumes uniform inheritance will report confident wrong answers for the pairs that pin their own value, for the pairs whose layer does not exist at all, and for the pairs carrying a malformed value that is currently inert.

44. **In a pin-to-values propagation workflow, bumping `argocd-image-updater/<bundle>/<env>/.argocd-source-<svc>.yaml` does NOT change what ArgoCD renders for an umbrella-bundle member — that file is only the PIN.** The tag ArgoCD actually renders lives in `charts/<bundle>/dev.yaml` (or `release.yaml`), and a separate bot PR titled `build: bulk image update` propagates pins → values files. **Bundle apps have no `.argocd-source-*` in their source path and no Helm parameters, so the pin alone is INERT.** To unblock a bundle member immediately you must edit `charts/<bundle>/dev.yaml`; the `.argocd-source` file only matters for standalone apps whose source path contains it. Example on `<service>`/`<cluster>`: the pin said `1.0.54-dev` while the deployment rendered `1.0.53-dev` from `dev.yaml`, with the app `Synced` at current main.

45. **A destructive teardown test against an ArgoCD-managed claim with `automated.selfHeal=true` RACES recreation and can mask a wedge.** The claim is re-applied within seconds, so the test measures nothing. Remove `spec.syncPolicy.automated` from the Application first, and **restore it BYTE-EXACT from a pre-change snapshot** afterwards — the block carries a newer `enabled: true` field that is easy to drop when reconstructing by hand. (Complements `learnings-crossplane.md`, which makes the same point for delete-with-no-orphan verification and adds "drive the teardown through git, not `kubectl`".)

## Rollout impact, ownership & adoption

46. **Any `argocd-cm` data change made THROUGH the argo-cd Helm chart ROLLS three components — it is not a hot-reload-only edit.** Chart 9.5.0 stamps a `checksum/cm` annotation on `argocd-application-controller` (StatefulSet), `argocd-server` and `argocd-repo-server` (Deployments), so a values change to `configs.cm` restarts all three. Verify with `helm template argo-cd --version 9.5.0` and diff the `checksum/cm` annotations. Budget for it when the change lands on a large or self-observing cluster (#47), and state it in the PR body — reviewers read `argocd-cm` edits as config-only.

47. **The ArgoCD instance that hosts your observability stack is the highest-blast-radius sync-ordering target in a fleet, and the reason is SCALE + SELF-OBSERVATION, not stack complexity.** **Consequence for any sync-ordering change (#15): a sync paused behind an unhealthy child on that cluster pauses delivery of the systems used to observe everything else.** Raise it as a reviewer **CONSIDERATION, not a blocker** — accurate reporting is the point of the change. **Sizing lesson from the same cluster: an ArgoCD repo-server serving ~100+ Applications needs its probes retuned well above chart defaults** — a chart-default **1 s** liveness probe produced a repo-server **kill loop**; the working shape was `timeoutSeconds: 15` / `failureThreshold: 5` with replicas and requests raised, plus a longer repo-server timeout and backed-off reconciliation with jitter. **Record those numbers in the stack that owns them, and treat the in-repo comment as the canonical home.**

48. **Extracting one service out of a monolithic umbrella Application into its own Application: a five-step, individually-reversible sequence — and the two steps people combine are the two that cannot be un-combined.** Motivation is blast radius, sync time, and image-update contention: a 50-service umbrella means one bad value blocks every service's deploys, ArgoCD reconciles the whole tree on every change, and per-service image automation contends across the set. **Sequence, one PR per step:** (1) create the new chart + Application **disabled**; (2) **enable it with `autoSync: false`** and validate what it renders against the live cluster; (3) **deep-compare configs** old-vs-new (below); (4) disable the service in the umbrella; (5) strip its config from the umbrella; then pin and enable `autoSync`. **Never combine (2) with (4)** — for a window both charts render the same objects, and if the umbrella is disabled in the same change that arms the new app, a rollback has no owner for the objects at all. **The predictable collision in that overlap window is shared-object ownership**: any object *named the same* in both charts — a preview/PR-lane ConfigMap is the classic — gets two owners and flaps. Find them before step (2) by diffing rendered object names, and disable the loser explicitly. **Step (3) is the one that actually catches production bugs and it must be key-by-key across EVERY cluster, not chart-level**: real drifts found this way were a feature flag enabled on one cluster and disabled on its sibling, an image tag differing between the release manifest and the values, and a secrets block silently absent on `main` because an earlier environment's cleanup pattern had stripped it. **These are invisible at chart level and invisible in a per-cluster spot check — the comparison has to be exhaustive to be worth running.** If the migration spans a release branch and `main`, state per PR which branch it targets; inferring it from context is where this goes wrong. (Related: `learnings-helm-ci.md` on umbrella nesting; `learnings-fleet-campaigns.md` on first-PR-establishes-the-pattern.)

49. **The ArgoCD takeover diff is NEVER EMPTY — do not write "`argocd app diff` must be empty" as a migration gate; it will be wrong on first contact and a reviewer will catch it.** Verified at `argo-cd` `docs/user-guide/resource_tracking.md` plus live objects. Adopting a Helm-managed object produces exactly **three** classes of difference: (1) **ArgoCD's own tracking metadata** — the default `resourceTrackingMethod` is `annotation` (`argocd.argoproj.io/tracking-id`), with `label` (`app.kubernetes.io/instance`) and `annotation+label` as alternatives; (2) **Helm's ownership metadata that ArgoCD's rendered output does NOT reproduce** — the label `app.kubernetes.io/managed-by=Helm` and the annotations `meta.helm.sh/release-name` + `meta.helm.sh/release-namespace`; (3) **API-server-injected fields** such as `deprecated.daemonset.template.generation`, which need `ignoreDifferences` + `RespectIgnoreDifferences=true` or the app perma-`OutOfSync`. **Correct gate wording: "the diff contains NOTHING BUT ownership metadata — no spec, image or replica change."** **Adoption corollary: prefer the default `annotation` tracking over `label` when adopting Helm releases** — charts already set `app.kubernetes.io/instance` themselves, and label tracking would overwrite it.

50. **ArgoCD reports a churning DaemonSet `Progressing` forever — but unlike `helm --wait` it BLOCKS NOTHING, and knowing the difference decides the design.** Verified at source: `gitops-engine` `pkg/health/health_daemonset.go` `getAppsv1DaemonSetHealth` returns `Progressing` while `status.numberAvailable < status.desiredNumberScheduled` (and while `updatedNumberScheduled < desiredNumberScheduled`). **On an autoscaling cluster that condition is permanently true, so the app never reports `Healthy`.** The crucial contrast with `helm_release wait=true` (`learnings-helm-ci.md`): **the SYNC OPERATION still completes, other Applications are unaffected, and no state diverges.** It becomes a real gate in exactly two places: **(a) SYNC-WAVES** — a later wave gates on earlier-wave health, so a permanently-`Progressing` DaemonSet in a gating wave **stalls the fleet forever** (same shape as #15 with child Applications); **(b) CI running `argocd app wait --health`.** **Design rule: churn-scale DaemonSets get their OWN Application, never a gating sync-wave, and CI waits on `--operation`, not `--health`.** Optional `health.lua` reporting `Healthy` at `updatedNumberScheduled == desiredNumberScheduled`.
