# Terraform / OpenTofu Learnings

See also: `learnings-crossplane.md`, `learnings-argocd.md`, `learnings-helm-ci.md`, `learnings-agent-workflow.md`

Terraform/OpenTofu monorepo mechanics -- apply-on-merge CI topology, plan-reading discipline, module version-bump rider audits, and PR/branch hygiene traps. Written for any GitOps-with-CI IaC setup, not one vendor's pipeline.

Numbered, append-only. **Update the existing entry — never duplicate.**

## CI topology — what runs, and what merging applies

1. **An IaC repo can auto-apply on merge to its default branch, with no manual apply step -- so merging applies the WHOLE plan, including any unrelated drift the plan happens to carry.** Check for it explicitly: a workflow job running `apply` (Terraform/OpenTofu) or `up` (Pulumi) on `push` to the default branch. Consequence: review the full plan before merge, not just your diff -- the plan summary line is part of the review surface, and any shared singleton resource whose provider replaces rather than merges deserves its own scan of every resource in the plan, not just the ones your diff touches.

2. **A modules-only change can get zero plan/lint/apply coverage in file-based CI routing -- a green check set is not evidence it plans cleanly anywhere.** Where CI maps changed files to deployable units, a diff touching only shared module code matches no unit, and plan, lint, and apply all report "skipping." Everything that stays green is generic -- title validation, `fmt`, docs generation, YAML formatting, security scanners -- and none of it evaluates the IaC semantics. The module change is first exercised later, when a follow-up PR bumps a consumer's version pin.
    - **Consequence for review:** a modules-only PR must carry local proof in the body (render or extract the changed config, diff it, prove error-count parity against merge-base), and the risk conversation belongs on the pin-bump PR, not on this one.
    - **Sequencing corollary:** merging a modules-only PR is safe by construction where the release workflow only cuts new module tags and nothing live moves until pins are bumped. Say so, rather than treating the absent plan as a gap.
    - **Module-level `terraform validate` can be broken at HEAD for reasons unrelated to any PR** -- e.g. a module pinning a provider at an unbounded `>= X` resolves a new major locally where a block became an attribute, while CI never hits it because CI plans consumers, which carry their own provider lock. Method: never report a validate result as pass/fail in absolute terms -- stash the diff, count `^Error:` at merge-base, restore, re-count, and assert the counts are equal. Also check whether the module tracks a `.terraform.lock.hcl`: if not, a local init leaves an untracked lock file that must be deleted before committing.

3. **Plan-as-PR-comment CI mechanics: the plan is not a gate, and you have to go find it.**
    - **Find the plan by HEAD SHA, not by branch.** Where per-stack plans post as PR comments rather than named checks, `gh pr checks` does not list them -- enumerate via `gh api repos/.../actions/runs/<id>/jobs`, and locate the run with `gh api repos/.../actions/runs?head_sha=<sha>`.
    - **Check what branch protection actually requires.** If it requires only formatting checks, the plan workflow is not a required check, and a PR can be merged with the plan never having run or having failed. Reading plans is a human/agent discipline, not a gate -- always confirm plans ran and say so in the PR body.
    - **A docs bot can auto-commit to the PR branch**, turning a 3-file change into 6 files and making the reported head SHA stop matching your local HEAD -- see #17 for the full mechanics.
    - **Read plans for pre-existing drift.** Every stack can carry unrelated in-place changes -- a stale GitOps-controller annotation, an addon version picked up by a `most_recent`-style data lookup, a database parameter flip -- that ride along on the next apply. Disclose them: not caused by your change, but they do apply with it.

4. **CI containment can be proven offline, before opening the PR -- run the repo's own matrix-discovery logic against your diff instead of asserting containment from the discover job's output afterwards.** Feed it the event type and `git diff --name-only origin/main` and read the matched-unit count and list.
    - **Structural backing is what makes the proof sound rather than merely empirical.** Read the matcher: if a unit is selected iff a changed file is under its own directory or matches one of its positive watch globs, then inspect the watch-glob set -- if every glob is root-level or rooted outside the unit tree, a diff confined to unit directories provably yields a matrix of exactly those units. That is a proof, not an observation.
    - **Verify both ways: static (grep the watch-glob set) plus observed (the discover job's matrix).** Use this instead of "CI dispatched only N jobs" as the containment claim -- it works pre-PR and does not depend on a runner picking the job up.
    - **The offline run cannot see a freeze or any other default-branch-side config change** (#5) -- it only proves containment against your checkout.

5. **A CI freeze (or any default-branch-side config change) can invalidate a dispatch mid-flight, and an offline matrix run will not show it.** CI evaluates the PR merge commit -- i.e. the default branch's config, not your branch's -- so a freeze merged minutes before your run silently drops units from the matrix, and an offline containment count taken earlier is now stale. Always re-fetch the default branch and read the discover job's freeze warnings before trusting an offline count, and re-check after every push.
    - **Why a freeze is a hard blocker, not a nuisance:** a frozen unit is dropped from the matrix on every trigger type -- pull request, push, and manual dispatch -- no lint, no plan, no apply. Merging a change for a frozen unit lands unapplied drift on the default branch that no plan evaluated; the first apply after unfreeze is somebody else's unrelated state-catch-up PR, so your change rides into their apply, in their plan, owned by nobody.
    - **Counter-rule -- a knowingly-frozen unit can be a valid, requester-approved shipment, and "helpfully" reverting it out of the PR overrides a decision already made.** When a unit is knowingly shipped frozen, the deliverable is documenting the consequence in the PR body -- skipped by CI, merges unapplied, first apply is whatever run ends the freeze -- not narrowing scope. Confirm the freeze scope from the default branch's own config (it can be per-entry, so a sibling entry for the same target may be unfrozen) and quote the verbatim CI warning in the body.

## Planning locally, and reading the plan

6. **Most production stacks cannot be planned locally even with fresh cloud auth -- do not promise a local plan; defer to the CI plan job and do not fake it. The blockers are structural and independent, so fixing one gets you nowhere.** Taxonomy worth checking against before you start:
    1. A secrets provider whose token is exchanged from the runner's CI OIDC JWT -- unobtainable outside CI, by design.
    2. A private control-plane API reachable only through a VPN/exit node, which a Kubernetes provider needs at plan time.
    3. Encrypted config data sources that decrypt via a cloud KMS at plan time, needing live application-default credentials -- including on stacks for a different cloud, which still carry cross-cloud remote-state and secret data sources.
    4. A cross-account `sts:AssumeRole` into a customer-owned role that only the CI role may assume -- `init` succeeds (the state backend is reachable) and `plan` fails, which reads as a fixable credential problem and is not.
    - The correct workflow for a plan-gated change: open a draft PR, let CI plan, verify, then mark ready. Confirm first that CI actually runs on drafts (it commonly does; only some review bots skip them). Where the repo's documented plan is the CI plan job, using it is not a workaround -- it is the process.

7. **Reading a plan when Application Default Credentials are dead: push the branch and read the plan out of the CI run log instead -- that is read-only and approves nothing.** A local `terraform init` on a GCS-backed stack failing with oauth2 `invalid_grant` / `reauth related error (invalid_rapt)` means the ADC token expired, and refresh (`gcloud auth application-default login`) is interactive-only, so it cannot be fixed from a non-interactive session. **`gcloud` CLI auth and ADC are separate credential planes** -- read-only `gcloud` commands (`gcloud projects describe`, `gcloud iam policies list`) keep working while ADC is dead, which can mislead you into thinking auth is fine overall. Do not try to bridge them by printing a CLI access token and exporting it as an ADC-shaped environment variable -- treat that as out of bounds, not a workaround. The correct move is `gh run view <id> --log` against the run for your own commit (find it with `gh run list --json status,conclusion,headSha` filtered to your workflow and SHA -- a run gated on manual approval because it was triggered by a bot-authored commit does not mean the run for your own push also needs approval; check each run's own trigger). A quick drift check from the log: `grep -cE 'will be (updated|destroyed|replaced)|must be replaced|~ update in place|- destroy'` should be 0 outside of an intentional change, and any suspected drifting resource should appear only in the refresh/read phase of the log, never in a planned-change phase. Caveat: some log-fetching paths mask literal `{` and `}` characters (e.g. as `***`) -- restore braces by hand before pasting a plan block anywhere.

8. **A CI system that posts a plan as a PR comment can silently truncate it from the FRONT, with no marker anywhere in the body -- and the tell is the comment's byte size sitting right at the platform's size limit.** Observed pattern: plan comments landing at roughly 65,000 bytes, within a few hundred bytes of GitHub's 65,536-character comment limit, and near-identical in size across comments with very different plan content -- that near-limit, near-constant size is the signal that something got cut, not that the plans happened to be similar. When truncated, the body starts mid-structure -- e.g. a dangling closing brace with no opening context a few lines in -- because the workflow keeps the TAIL of the plan output and drops the head (the `Refreshing state...` preamble and the early resource blocks). **Danger: an agent reading the comment top-down assumes it saw the whole plan, and a grep for `will be replaced` (or any other marker) over a partial body returns a false clean.**
    **How to validate completeness anyway, without the missing head:**
    1. The authoritative `Plan: X to add, Y to change, Z to destroy.` summary line lives in the retained tail. `0 to add` + `0 to destroy` proves no resource replacement occurred, since a replacement always reports as both an add and a destroy.
    2. Cross-check the COUNT of `# <resource> will be updated in-place` headers visible in the truncated comment against `Y` from the summary line. If the counts match, your enumeration of changed resources is complete even though the head was cut -- you are only missing read-only `Refreshing state...` noise, not a changed resource.
    3. If the header count is LESS than `Y`, changed-resource blocks are missing from what you can see -- read the raw CI job log instead, since the log is not subject to the comment size limit.
    - **General rule: any PR-comment-based generated output sitting within a few hundred bytes of the platform's comment size limit should be treated as truncated until proven otherwise** -- this generalizes past Terraform to any CI system that posts long output as a PR comment.

9. **Reading a `helm_release` resource's plan: a huge block of `-` (removal) lines can be the provider's COMPUTED `metadata` attribute being recomputed, not an actual removal.** A `helm_release ... will be updated in-place` block can span hundreds of lines where most are `-` -- the entire OLD chart metadata (`app_version`, `chart`, `notes`, `revision`, the whole prior `values` jsonencode) being replaced because the attribute is computed. **The giveaway is the terminator: `] -> (known after apply)`** on the attribute -- that marks it computed, not user-supplied. The real config diff lives in a SEPARATE `~ values = [` attribute further down in the same resource block. Two traps: (1) counting `-`/`+` lines naively, or difflib-reconstructing the two sides of the block, produces a diff that looks like the whole release is being rewritten when it is not; (2) grepping `^\s*-` inside the values heredoc false-positives on every YAML list item, since those are list markers, not diff markers. **Method that works: the plan renderer emits diff markers at a fixed column, so anchor the grep to that column** -- something like `grep -cE "^ {14}[+] "` / `grep -cE "^ {14}- "` scoped to the values region only (the exact column depends on nesting depth -- calibrate it on one line you know changed). Pair this with the plan-summary cross-check in #8 -- the two together turn "no unexpected riders, no replacement" into a proof rather than an impression.

10. **`kubernetes_namespace` owns the ENTIRE `metadata.labels` map, so a plan that only ADDS one label to a live namespace will also show REMOVALS for any label applied out-of-band -- and that plan still reads as "one resource, in-place update" and looks green to a fast reviewer.** (`hashicorp/kubernetes` SDK resources behave this way, e.g. `kubernetes_namespace` in provider v2.37.x.) Out-of-band sources include a manual `kubectl label`/`kubectl annotate` and any admission-controller or policy-engine mutation. **When reviewing a namespace-label plan on a production cluster, the stop condition is additive-only: the intended `+` line and nothing else in the labels block. Any removal or change means live drift that predates your PR -- stop and report rather than approving.** A similar trap applies to annotations when a module merges a fixed set of "managed" annotations on top of whatever already exists.

11. **A managed cluster-addon module with `most_recent = true` (or any "resolve latest version at plan time" setting) carries structural, self-regenerating drift that EVERY unrelated PR touching that stack sweeps up.** Because the addon version resolves from the cloud provider's addon catalog at PLAN time rather than being pinned, any PR that puts that stack in the CI matrix inherits whatever addon releases the provider has cut since the last apply -- observed with cluster-DNS and CSI-driver addons picking up new build versions on an otherwise-unrelated one-line change. That is real operational blast radius (a rolling restart of the affected controller or DaemonSet), even with zero IAM/network changes. If the addon's conflict-resolution mode is set to overwrite-on-update, out-of-band addon configuration is clobbered by the same apply. **Distinguish this from ordinary unapplied drift sitting on the default branch: this kind regenerates itself on every plan and cannot be "landed first" permanently -- it can only be pinned.** Call it out at merge time so the reviewer is not surprised by an addon bump riding inside an unrelated small PR. **UNVERIFIED at source level** -- this rests on the general resolve-at-plan-time mechanism; confirm against `hashicorp/terraform-provider-aws`'s `aws_eks_addon` (or your provider's equivalent) before treating the conflict-resolution half as settled.

## Module pins and rider audits

12. **Auditing a module-version bump for unintended riders: scope every diff to the module subdirectory, and re-read the CURRENT pin from the target branch first, not from a brief written earlier.** A pin can move between when a task is written and when it is executed, shrinking what looked like a multi-version hop down to a single small change, or eliminating it. Three techniques that compose:
    - **Scope with `git diff --stat <from-tag> <to-tag> -- modules/<module>/`.** In a monorepo where module tags are repo-wide, an unscoped tag-to-tag diff shows every file in the repo, most of which the consuming stack never references via its module source pin.
    - **`git log <tagA>..<tagB> -- modules/<module>/` lists every commit that touched the module path AT ALL, including doc-generator churn** -- a commit whose only touch is an auto-generated README table (a provider-version column regenerated from constraint ranges) is a false alarm; the functional change, if any, lived in a different file. Always diff the module's actual source files before treating a commit as a real rider. Watch for name collisions between unrelated resources sharing a substring in their identifiers.
    - **The audit method is empirically trustworthy, but still read the resulting plan.** A source-level prediction ("this resource will not change because X is not consumed here") should be confirmed by the resource appearing as a read-only refresh line, or not at all, in the actual plan -- reading the plan is what converts a PR-body claim from inference into evidence.

13. **Proving a module-version-bump rider is inert on a given consumer: check the feature's enable/disable flag FIRST -- it is cheaper and more conclusive than tracing a null-guard chain.** Three layers, strongest first:
    - **Layer 0 (strongest): a component-level `<component>_enabled` flag.** If a module gates a sub-resource with `count = local.<component>.enabled ? 1 : 0`, a consumer that has disabled that component has literally no resource for the rider to attach to, regardless of any variable it sets. This generalizes: after any migration that flips a component's enable flag to false on a consumer, every future module change touching that component is structurally inert there. **The strongest plan tell is that the resource appears ZERO times, not even as a read-only refresh line** -- that proves the resource is absent from state entirely, not merely unchanged.
    - **Layer 1: the optional-variable null-guard chain.** If a new knob is added as an OPTIONAL variable with `default = null` (not a new required variable, so omitting it cannot error at plan time), and the module's resource block only sets the corresponding attribute when the variable is non-null, and any per-key resolution falls back to the pre-existing default when null -- then a consumer that does not set the new variable gets a byte-identical plan.
    - **Layer 2 (rules out a different failure mode): diff the set of variables WITHOUT a default at both tags.** One command settles whether the bump introduced a new REQUIRED variable a consumer does not set -- a scenario the null-guard trace does not cover.
    - **Gotcha to keep in sync:** some Helm-values-shaped module attributes merge a whole list as one unit rather than by key, so a partial override is not possible and any downstream block touching that attribute must mirror the module's full default set. Re-check on every bump of that module.

14. **A module-level Helm `values` block is erasable by any downstream consumer, because the Terraform Helm provider applies `set`/`set_string` entries AFTER `values`.** Verified in `hashicorp/terraform-provider-helm` source (the release-update path in `helm/resource_release.go`, v2.17.0): a consumer-level `set` entry targeting the same dotted key as a module-level `values` heredoc entry REPLACES the whole heredoc value at that key -- it does not merge into it. **Any module-level Helm-values invariant is erasable unless every consumer is checked.** Before claiming a module-level values change is live on a given consumer, grep that consumer's `set`/`set_string` block for the exact key path -- a sibling key under the same parent object is safe (no collision), but the same key is not.

15. **`terraform-aws-modules/terraform-aws-iam` v6.x renamed the wildcard-OIDC-subject variable, and the old name silently does nothing.** In the v6 `iam-role-for-service-accounts-eks` submodule there is no `oidc_subjects_with_wildcards` variable; wildcard subject matching comes from `trust_condition_test = "StringLike"` (the module default is `StringEquals`, applied to both the `:sub` and `:aud` OIDC trust conditions). `oidc_subjects_with_wildcards` only ever existed in the v5 `iam-assumable-role-with-oidc` submodule (last seen v5.60.0); its v6 successor, in the plain `iam-role` submodule, is a differently-named `oidc_wildcard_subjects`. **Copying a v5 snippet into a v6 module reference silently produces exact-match trust instead of the intended wildcard match -- no error, just a role that never assumes.**

## Stack layout

16. **A Kubernetes namespace's labels can be owned by IaC rather than by the Helm release that appears to manage the workload in it -- and which one owns it can differ by consumer and by cloud, so grepping the repo for the namespace's literal name can find nothing.** The grep trap: a namespace map can be keyed by an interpolated local (`${local.some_namespace_name}`) rather than a literal string, so a text search for the namespace name finds no config while the rendered PLAN address still shows the literal name (`module.cluster[0].kubernetes_namespace.namespaces["<name>"]`). **Search the plan address and the interpolated local, not the literal string, before concluding a namespace is not IaC-managed.** Separately: a label edit inside one stack cannot leak into other consumers when the module is pinned by tag rather than consumed from a local path -- worth stating explicitly in a PR body since it is not obvious from the diff alone. And watch for parallel directories that share an identifier but serve unrelated purposes (one holds a cluster stack, a same-named sibling holds an unrelated side-stack with no cluster or namespaces at all) -- editing the wrong one is a silent no-op.

## PR hygiene and branch mechanics

17. **A PR's head SHA can move twice after you push -- once from an automated bot commit, once from an automated merge-from-default-branch -- and the resulting diff confusion looks like a bug in your tooling and is not.** A bot commit (a docs generator) followed by an automated sync-from-default-branch makes a naive `git diff <your-last-commit> <current-head>` show hundreds of unrelated lines and read like scope leakage that is not yours. **Two correct checks instead: the platform's own PR-file-list API (`gh pr view <n> --json files`) and a merge-base diff** (`git diff --stat $(git merge-base origin/main origin/<branch>) origin/<branch>`). A merge-commit-aware log listing (`git log --no-abbrev-commit` plus `git show --stat <sha>`) is more reliable for identifying a surprise head SHA than a range-diff that may not surface merge commits at all. **Operational rule: a moved head SHA invalidates any plan you already read** -- re-read the newest plan comment (match it by timestamp) and re-run your completeness check against it. Never force-push to undo a bot's commit.
    - **A bot commit gates the workflow, it does not fail it.** Where an automated bot push re-triggers every workflow, those re-runs can land in a "manual approval required" state with zero jobs run, because the platform requires approval for runs triggered by a bot-authored commit -- while standalone lightweight workflows (plain formatting checks) run fine on the same push. Do not read "no plan on the head SHA" as "the plan failed." The earlier plan on the pre-bot-commit SHA remains the meaningful evidence, provided you verify the SHA-to-SHA delta is bot-generated-content-only, and you state in the PR body which commit the plan actually covers. Check whether the pending-approval state is the bot-trigger gate or a real environment-protection gate by reading the job's own declared environment (a plan job usually has none; an apply job usually does). **Never self-approve a pending run -- approving a workflow run is a mutating action indistinguishable from a human's in the audit trail. Report the gate; do not work around it.**

18. **A PR reporting "behind the default branch" and a PR's head SHA actually moving are different events with different obligations, and conflating them burns a full CI cycle per false alarm.** Under a strict branch-protection setting, a PR opened before any unrelated sibling merge will report BEHIND, and it flips back to BEHIND again minutes after every unrelated merge to the default branch lands -- independent of anything on your branch. **Correct stop condition: a moved HEAD SHA invalidates your existing checks and must be re-verified (#17); "the default branch moved" does NOT invalidate anything on your own head** -- your checks still hold, and BEHIND is merge-time bookkeeping, not a signal your plan is stale. Re-verify on the former, document-and-leave-alone on the latter, with an explicit note for whoever merges to use an ordinary merge rather than a rebase. When you do need to catch up: merge the default branch into your branch and push -- never rebase or force-push, since an earlier bot commit is often already on the branch and a force-push would silently drop it. **Useful confirmation once you do merge: a re-run plan that is byte-identical to the pre-merge plan is positive proof that the intervening default-branch commits do not affect your stack** -- which holds when your stack consumes a shared module by a pinned tag rather than by live path, since tag-pinned consumption makes upstream module churn inert by construction for your stack specifically.

19. **Sibling repos in the same org have separate conventions, and cross-repo policy transfer is a real failure mode -- a dispatch or checklist written against one repo's conventions will name labels, templates, and process steps that do not exist in another.**
    - Applying a label from another repo's convention can fail outright if the label does not exist here -- always list the repo's actual labels before applying one from a remembered convention, and expect the equivalent gating label, if any, to have a different name.
    - A PR template path can be lowercase in one repo's `.github/` directory where you would expect the commonly-documented uppercase convention; searching for the uppercase form can fail to expand under a strict shell rather than just finding nothing. Read the actual template file rather than assuming its sections from memory.
    - A process rule that lives in one repo's own contributor instructions is that repo's rule, not the org's rule. Do not import another repo's release-plan, handoff, or post-apply-watch process into a different repo's PR bodies just because both are IaC repos -- and do not apply a gating label as a reflex on production-affecting PRs unless it is this repo's actual convention.

20. **Unapplied IaC drift that WIDENS ACCESS is a latent hazard with a fuse, not a resolved finding -- "the live resource is currently clean" and "the config is safe" are different claims, and only the second one survives the next full apply.**
    - **Record the date with the finding.** A live read showing no exposure today is true only as of that read -- without a date attached, the next person either re-panics unnecessarily or, worse, assumes the wider grant was already applied and is therefore fine.
    - **The exposure that remains is the CONFIG, not the current cloud state.** While the widening change sits in the IaC config -- even unmerged, and especially once merged-but-unapplied on a frozen or dormant unit -- it lands on whoever next runs a full apply on that unit. On a repo where merging IS applying, that can be one unrelated PR away.
    - **A finding like this must never be closed on a live read alone -- it closes only when the widening change actually leaves the config**, whether by revert or by a deliberate, reviewed re-scope.
    - **General rule: grade a not-yours resource that widens access by its CONFIG state, not its current live state, and hand it to the resource's owner as an explicitly open item** -- a review that only checks resources you touched can pass cleanly while a grant two resources away sits armed.
