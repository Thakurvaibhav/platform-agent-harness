# Terraform / OpenTofu Learnings

Terraform/OpenTofu monorepo mechanics -- apply-on-merge CI topology, plan-reading discipline, module version-bump rider audits, and PR/branch hygiene traps. Written for any GitOps-with-CI IaC setup, not one vendor's pipeline.

## CI topology — what runs, and what merging applies

1. **An IaC repo can auto-apply on merge to its default branch, with no manual apply step -- so merging applies the WHOLE plan, including any unrelated drift the plan happens to carry.** Check for it explicitly: a workflow job running `apply` (Terraform/OpenTofu) or `up` (Pulumi) on `push` to the default branch. Consequence: review the full plan before merge, not just your diff -- the plan summary line is part of the review surface, and any shared singleton resource whose provider replaces rather than merges deserves its own scan of every resource in the plan, not just the ones your diff touches.

2. **A modules-only change can get zero plan/lint/apply coverage in file-based CI routing -- a green check set is not evidence it plans cleanly anywhere.** Where CI maps changed files to deployable units, a diff touching only shared module code matches no unit, and plan, lint, and apply all report "skipping." Everything that stays green is generic -- title validation, `fmt`, docs generation, YAML formatting, security scanners -- and none of it evaluates the IaC semantics. The module change is first exercised later, when a follow-up PR bumps a consumer's version pin.
    - **Consequence for review:** a modules-only PR must carry local proof in the body (render or extract the changed config, diff it, prove error-count parity against merge-base), and the risk conversation belongs on the pin-bump PR, not on this one.
    - **Sequencing corollary:** merging a modules-only PR is safe by construction where the release workflow only cuts new module tags and nothing live moves until pins are bumped. Say so, rather than treating the absent plan as a gap.
    - **Module-level `terraform validate` can be broken at HEAD for reasons unrelated to any PR** -- e.g. a module pinning a provider at an unbounded `>= X` resolves a new major locally where a block became an attribute, while CI never hits it because CI plans consumers, which carry their own provider lock. Method: never report a validate result as pass/fail in absolute terms -- stash the diff, count `^Error:` at merge-base, restore, re-count, and assert the counts are equal. Also check whether the module tracks a `.terraform.lock.hcl`: if not, a local init leaves an untracked lock file that must be deleted before committing.

3. **Plan-as-PR-comment CI mechanics: the plan is not a gate, and you have to go find it.**
    - **Find the plan by HEAD SHA, not by branch.** Where per-stack plans post as PR comments rather than named checks, `gh pr checks` does not list them -- enumerate via `gh api repos/.../actions/runs/<id>/jobs`, and locate the run with `gh api repos/.../actions/runs?head_sha=<sha>`.
    - **Check what branch protection actually requires.** If it requires only formatting checks, the plan workflow is not a required check, and a PR can be merged with the plan never having run or having failed. Reading plans is a human/agent discipline, not a gate -- always confirm plans ran and say so in the PR body.
    - **A docs bot can auto-commit to the PR branch**, turning a 3-file change into 6 files and making the reported head SHA stop matching your local HEAD -- see #17 for the full mechanics.
    - **Read plans for pre-existing drift.** Every stack can carry unrelated in-place changes -- a stale GitOps-controller annotation, an addon version picked up by a `most_recent`-style data lookup, a database parameter flip -- that ride along on the next apply. Disclose them: not caused by your change, but they do apply with it.

4. **CI containment can be proven offline, before opening the PR -- run the repo's own matrix-discovery logic against your diff instead of asserting containment from the discover job's output afterwards.** Feed it the event type and `git diff --name-only origin/main` and read the matched-unit count and list.
    - **Structural backing is what makes the proof sound rather than merely empirical.** Read the matcher: if a unit is selected iff a changed file is under its own directory or matches one of its positive watch globs, then inspect the watch-glob set -- if every glob is root-level or rooted outside the unit tree, a diff confined to unit directories provably yields a matrix of exactly those units. That is a proof, not an observation.
    - **Verify both ways: static (grep the watch-glob set) plus observed (the discover job's matrix).** Use this instead of "CI dispatched only N jobs" as the containment claim -- it works pre-PR and does not depend on a runner picking the job up.
    - **The offline run cannot see a freeze or any other default-branch-side config change** (#5) -- it only proves containment against your checkout.

5. **A CI freeze (or any default-branch-side config change) can invalidate a dispatch mid-flight, and an offline matrix run will not show it.** CI evaluates the PR merge commit -- i.e. the default branch's config, not your branch's -- so a freeze merged minutes before your run silently drops units from the matrix, and an offline containment count taken earlier is now stale. Always re-fetch the default branch and read the discover job's freeze warnings before trusting an offline count, and re-check after every push.
    - **Why a freeze is a hard blocker, not a nuisance:** a frozen unit is dropped from the matrix on every trigger type -- pull request, push, and manual dispatch -- no lint, no plan, no apply. Merging a change for a frozen unit lands unapplied drift on the default branch that no plan evaluated; the first apply after unfreeze is somebody else's unrelated state-catch-up PR, so your change rides into their apply, in their plan, owned by nobody.
    - **Counter-rule -- a knowingly-frozen unit can be a valid, requester-approved shipment, and "helpfully" reverting it out of the PR overrides a decision already made.** When a unit is knowingly shipped frozen, the deliverable is documenting the consequence in the PR body -- skipped by CI, merges unapplied, first apply is whatever run ends the freeze -- not narrowing scope. Confirm the freeze scope from the default branch's own config (it can be per-entry, so a sibling entry for the same target may be unfrozen) and quote the verbatim CI warning in the body.

## Planning locally, and reading the plan

6. **Most production stacks cannot be planned locally even with fresh cloud auth -- do not promise a local plan; defer to the CI plan job and do not fake it. The blockers are structural and independent, so fixing one gets you nowhere.** Taxonomy worth checking against before you start:
    1. A secrets provider whose token is exchanged from the runner's CI OIDC JWT -- unobtainable outside CI, by design.
    2. A private control-plane API reachable only through a VPN/exit node, which a Kubernetes provider needs at plan time.
    3. Encrypted config data sources that decrypt via a cloud KMS at plan time, needing live application-default credentials -- including on stacks for a different cloud, which still carry cross-cloud remote-state and secret data sources.
    4. A cross-account `sts:AssumeRole` into a customer-owned role that only the CI role may assume -- `init` succeeds (the state backend is reachable) and `plan` fails, which reads as a fixable credential problem and is not.
    - The correct workflow for a plan-gated change: open a draft PR, let CI plan, verify, then mark ready. Confirm first that CI actually runs on drafts (it commonly does; only some review bots skip them). Where the repo's documented plan is the CI plan job, using it is not a workaround -- it is the process.
    - **Private-endpoint failure signature:** a laptop plan against a private Kubernetes/Helm API address hangs and times out even with valid credentials; this is a provider timeout, not a permission error. Use the PR's CI plan job or a bastion/VPN, and pin the local orchestration-tool version to CI's -- a different minor can reformat or re-resolve.

7. **Reading a plan when Application Default Credentials are dead: push the branch and read the plan out of the CI run log instead -- that is read-only and approves nothing.** A local `terraform init` on a GCS-backed stack failing with oauth2 `invalid_grant` / `reauth related error (invalid_rapt)` means the ADC token expired, and refresh (`gcloud auth application-default login`) is interactive-only, so it cannot be fixed from a non-interactive session. **`gcloud` CLI auth and ADC are separate credential planes** -- read-only `gcloud` commands (`gcloud projects describe`, `gcloud iam policies list`) keep working while ADC is dead, which can mislead you into thinking auth is fine overall. Do not try to bridge them by printing a CLI access token and exporting it as an ADC-shaped environment variable -- treat that as out of bounds, not a workaround. The correct move is `gh run view <id> --log` against the run for your own commit (find it with `gh run list --json status,conclusion,headSha` filtered to your workflow and SHA -- a run gated on manual approval because it was triggered by a bot-authored commit does not mean the run for your own push also needs approval; check each run's own trigger). A quick drift check from the log: `grep -cE 'will be (updated|destroyed|replaced)|must be replaced|~ update in place|- destroy'` should be 0 outside of an intentional change, and any suspected drifting resource should appear only in the refresh/read phase of the log, never in a planned-change phase. Caveat: some log-fetching paths mask literal `{` and `}` characters (e.g. as `***`) -- restore braces by hand before pasting a plan block anywhere.

8. **A CI system that posts a plan as a PR comment can silently truncate it from the FRONT, with no marker anywhere in the body -- and the tell is the comment's byte size sitting right at the platform's size limit.** Observed pattern: plan comments landing at roughly 65,000 bytes, within a few hundred bytes of GitHub's 65,536-character comment limit, and near-identical in size across comments with very different plan content -- that near-limit, near-constant size is the signal that something got cut, not that the plans happened to be similar. When truncated, the body starts mid-structure -- e.g. a dangling closing brace with no opening context a few lines in -- because the workflow keeps the TAIL of the plan output and drops the head (the `Refreshing state...` preamble and the early resource blocks). **Danger: an agent reading the comment top-down assumes it saw the whole plan, and a grep for `will be replaced` (or any other marker) over a partial body returns a false clean.**
    **How to validate completeness anyway, without the missing head:**
    1. The authoritative `Plan: X to add, Y to change, Z to destroy.` summary line lives in the retained tail. `0 to add` + `0 to destroy` proves no resource replacement occurred, since a replacement always reports as both an add and a destroy.
    2. Cross-check the COUNT of `# <resource> will be updated in-place` headers visible in the truncated comment against `Y` from the summary line. If the counts match, your enumeration of changed resources is complete even though the head was cut -- you are only missing read-only `Refreshing state...` noise, not a changed resource.
    3. If the header count is LESS than `Y`, changed-resource blocks are missing from what you can see -- read the raw CI job log instead, since the log is not subject to the comment size limit.
    - **General rule: any PR-comment-based generated output sitting within a few hundred bytes of the platform's comment size limit should be treated as truncated until proven otherwise** -- this generalizes past Terraform to any CI system that posts long output as a PR comment.

9. **Reading a `helm_release` resource's plan: a huge block of `-` (removal) lines can be the provider's COMPUTED `metadata` attribute being recomputed, not an actual removal.** A `helm_release ... will be updated in-place` block can span hundreds of lines where most are `-` -- the entire OLD chart metadata (`app_version`, `chart`, `notes`, `revision`, the whole prior `values` jsonencode) being replaced because the attribute is computed. **The giveaway is the terminator: `] -> (known after apply)`** on the attribute -- that marks it computed, not user-supplied. The real config diff lives in a SEPARATE `~ values = [` attribute further down in the same resource block. Two traps: (1) counting `-`/`+` lines naively, or difflib-reconstructing the two sides of the block, produces a diff that looks like the whole release is being rewritten when it is not; (2) grepping `^\s*-` inside the values heredoc false-positives on every YAML list item, since those are list markers, not diff markers. **Method that works: the plan renderer emits diff markers at a fixed column, so anchor the grep to that column** -- something like `grep -cE "^ {14}[+] "` / `grep -cE "^ {14}- "` scoped to the values region only (the exact column depends on nesting depth -- calibrate it on one line you know changed). Pair this with the plan-summary cross-check in #8 -- the two together turn "no unexpected riders, no replacement" into a proof rather than an impression.

10. **`kubernetes_namespace` owns the ENTIRE `metadata.labels` map, so a plan that only ADDS one label to a live namespace will also show REMOVALS for any label applied out-of-band -- and that plan still reads as "one resource, in-place update" and looks green to a fast reviewer.** (`hashicorp/kubernetes` SDK resources behave this way, e.g. `kubernetes_namespace` in provider v2.37.x.) Out-of-band sources include a manual `kubectl label`/`kubectl annotate` and any admission-controller or policy-engine mutation. **When reviewing a namespace-label plan on a production cluster, the stop condition is additive-only: the intended `+` line and nothing else in the labels block. Any removal or change means live drift that predates your PR -- stop and report rather than approving.** A similar trap applies to annotations when a module merges a fixed set of "managed" annotations on top of whatever already exists.

11. **A managed cluster-addon module with `most_recent = true` (or any "resolve latest version at plan time" setting) carries structural, self-regenerating drift that EVERY unrelated PR touching that stack sweeps up.** Because the addon version resolves from the cloud provider's addon catalog at PLAN time rather than being pinned, any PR that puts that stack in the CI matrix inherits whatever addon releases the provider has cut since the last apply -- observed with cluster-DNS and CSI-driver addons picking up new build versions on an otherwise-unrelated one-line change. That is real operational blast radius (a rolling restart of the affected controller or DaemonSet), even with zero IAM/network changes. If the addon's conflict-resolution mode is set to overwrite-on-update, out-of-band addon configuration is clobbered by the same apply. **Distinguish this from ordinary unapplied drift sitting on the default branch: this kind regenerates itself on every plan and cannot be "landed first" permanently -- it can only be pinned.** Call it out at merge time so the reviewer is not surprised by an addon bump riding inside an unrelated small PR. **UNVERIFIED at source level** -- this rests on the general resolve-at-plan-time mechanism; confirm against `hashicorp/terraform-provider-aws`'s `aws_eks_addon` (or your provider's equivalent) before treating the conflict-resolution half as settled.
    - **The same mechanism affects latest-machine-image data sources.** A module that resolves the newest image can update a launch template or replace an instance on an unrelated PR whenever the vendor publishes an image. Pre-label that drift in the PR comment; pin the image version, or deliberately ignore the consuming resource's image change where appropriate.

## Module pins and rider audits

12. **Auditing a module-version bump for unintended riders: scope every diff to the module subdirectory, and re-read the CURRENT pin from the target branch first, not from a brief written earlier.** A pin can move between when a task is written and when it is executed, shrinking what looked like a multi-version hop down to a single small change, or eliminating it. Three techniques that compose:
    - **Scope with `git diff --stat <from-tag> <to-tag> -- modules/<module>/`.** In a monorepo where module tags are repo-wide, an unscoped tag-to-tag diff shows every file in the repo, most of which the consuming stack never references via its module source pin.
    - **`git log <tagA>..<tagB> -- modules/<module>/` lists every commit that touched the module path AT ALL, including doc-generator churn** -- a commit whose only touch is an auto-generated README table (a provider-version column regenerated from constraint ranges) is a false alarm; the functional change, if any, lived in a different file. Always diff the module's actual source files before treating a commit as a real rider. Watch for name collisions between unrelated resources sharing a substring in their identifiers.
    - **The audit method is empirically trustworthy, but still read the resulting plan.** A source-level prediction ("this resource will not change because X is not consumed here") should be confirmed by the resource appearing as a read-only refresh line, or not at all, in the actual plan -- reading the plan is what converts a PR-body claim from inference into evidence.

13. **Proving a module-version-bump rider is inert on a given consumer: check the feature's enable/disable flag FIRST -- it is cheaper and more conclusive than tracing a null-guard chain.** Three layers, strongest first:
    - **Layer 0 (strongest): a component-level `<component>_enabled` flag.** If a module gates a sub-resource with `count = local.<component>.enabled ? 1 : 0`, a consumer that has disabled that component has literally no resource for the rider to attach to, regardless of any variable it sets. This generalizes: after any migration that flips a component's enable flag to false on a consumer, every future module change touching that component is structurally inert there. **The strongest plan tell is that the resource appears ZERO times, not even as a read-only refresh line** -- that proves the resource is absent from state entirely, not merely unchanged.
    - **Layer 1: the optional-variable null-guard chain.** If a new knob is added as an OPTIONAL variable with `default = null` (not a new required variable, so omitting it cannot error at plan time), and the module's resource block only sets the corresponding attribute when the variable is non-null, and any per-key resolution falls back to the pre-existing default when null -- then a consumer that does not set the new variable gets a byte-identical plan.
    - **Layer 2 (rules out a different failure mode): diff the set of variables WITHOUT a default at both tags.** One command settles whether the bump introduced a new REQUIRED variable a consumer does not set -- a scenario the null-guard trace does not cover.
    - **Gotcha to keep in sync:** some Helm-values-shaped module attributes merge a whole list as one unit rather than by key, so a partial override is not possible and any downstream block touching that attribute must mirror the module's full default set. Re-check on every bump of that module.

14. **A module-level Helm `values` block is erasable by any downstream consumer, because the Terraform Helm provider applies `set`/`set_string` entries AFTER `values`.** Verified in `hashicorp/terraform-provider-helm` source (the release-update path in `helm/resource_release.go`, v2.17.0): a consumer-level `set` entry targeting the same dotted key as a module-level `values` heredoc entry REPLACES the whole heredoc value at that key -- it does not merge into it. **Any module-level Helm-values invariant is erasable unless every consumer is checked.** Before claiming a module-level values change is live on a given consumer, grep that consumer's `set`/`set_string` block for the exact key path -- a sibling key under the same parent object is safe (no collision), but the same key is not.

15. **Wildcard OIDC trust at `terraform-aws-modules/iam` v6.2.3 uses `trust_condition_test = "StringLike"` in `modules/iam-role-for-service-accounts`.** The default is `StringEquals`; `main.tf:65,72` apply the condition test to both `:sub` and `:aud` conditions built from `var.oidc_providers`. There is no `oidc_subjects_with_wildcards` input in that submodule. That input existed in v5's `modules/iam-assumable-role-with-oidc` (v5.60.0 `variables.tf:91`), not the `-eks` variant; its v6 successor is `oidc_wildcard_subjects` in `modules/iam-role` (`variables.tf:119`). Copying an exact-match trust configuration from the wrong module variant can leave wildcard subjects unmatched. Check the exact module path and version before transferring an OIDC snippet.

## Stack layout

16. **A Kubernetes namespace's labels can be owned by IaC rather than by the Helm release that appears to manage the workload in it -- and which one owns it can differ by consumer and by cloud, so grepping the repo for the namespace's literal name can find nothing.** The grep trap: a namespace map can be keyed by an interpolated local (`${local.some_namespace_name}`) rather than a literal string, so a text search for the namespace name finds no config while the rendered PLAN address still shows the literal name (`module.cluster[0].kubernetes_namespace.namespaces["<name>"]`). **Search the plan address and the interpolated local, not the literal string, before concluding a namespace is not IaC-managed.** Separately: a label edit inside one stack cannot leak into other consumers when the module is pinned by tag rather than consumed from a local path -- worth stating explicitly in a PR body since it is not obvious from the diff alone. And watch for parallel directories that share an identifier but serve unrelated purposes (one holds a cluster stack, a same-named sibling holds an unrelated side-stack with no cluster or namespaces at all) -- editing the wrong one is a silent no-op.

## PR hygiene and branch mechanics

17. **A PR's head SHA can move twice after you push -- once from an automated bot commit, once from an automated merge-from-default-branch -- and the resulting diff confusion looks like a bug in your tooling and is not.** A bot commit (a docs generator) followed by an automated sync-from-default-branch makes a naive `git diff <your-last-commit> <current-head>` show hundreds of unrelated lines and read like scope leakage that is not yours. **Two correct checks instead: the platform's own PR-file-list API (`gh pr view <n> --json files`) and a merge-base diff** (`git diff --stat $(git merge-base origin/main origin/<branch>) origin/<branch>`). A merge-commit-aware log listing (`git log --no-abbrev-commit` plus `git show --stat <sha>`) is more reliable for identifying a surprise head SHA than a range-diff that may not surface merge commits at all. **Operational rule: a moved head SHA invalidates any plan you already read** -- re-read the newest plan comment (match it by timestamp) and re-run your completeness check against it. Never force-push to undo a bot's commit.
    - **A bot commit gates the workflow, it does not fail it.** Where an automated bot push re-triggers every workflow, those re-runs can land in a "manual approval required" state with zero jobs run, because the platform requires approval for runs triggered by a bot-authored commit -- while standalone lightweight workflows (plain formatting checks) run fine on the same push. Do not read "no plan on the head SHA" as "the plan failed." The earlier plan on the pre-bot-commit SHA remains the meaningful evidence, provided you verify the SHA-to-SHA delta is bot-generated-content-only, and you state in the PR body which commit the plan actually covers. Check whether the pending-approval state is the bot-trigger gate or a real environment-protection gate by reading the job's own declared environment (a plan job usually has none; an apply job usually does). **Never self-approve a pending run -- approving a workflow run is a mutating action indistinguishable from a human's in the audit trail. Report the gate; do not work around it.**

18. **A PR reporting "behind the default branch" and a PR's head SHA actually moving are different events with different obligations, and conflating them burns a full CI cycle per false alarm.** Under a strict branch-protection setting, a PR opened before any unrelated sibling merge will report BEHIND, and it flips back to BEHIND again minutes after every unrelated merge to the default branch lands -- independent of anything on your branch. **Correct stop condition: a moved HEAD SHA invalidates your existing checks and must be re-verified (#17); "the default branch moved" does NOT invalidate anything on your own head** -- your checks still hold, and BEHIND is merge-time bookkeeping, not a signal your plan is stale. Re-verify on the former, document-and-leave-alone on the latter, with an explicit note for whoever merges to use an ordinary merge rather than a rebase. When you do need to catch up: merge the default branch into your branch and push -- never rebase or force-push, since an earlier bot commit is often already on the branch and a force-push would silently drop it. **Useful confirmation once you do merge: a re-run plan that is byte-identical to the pre-merge plan is positive proof that the intervening default-branch commits do not affect your stack** -- which holds when your stack consumes a shared module by a pinned tag rather than by live path, since tag-pinned consumption makes upstream module churn inert by construction for your stack specifically.

19. **Sibling repos in the same org have separate conventions, and cross-repo policy transfer is a real failure mode -- a dispatch or checklist written against one repo's conventions will name labels, templates, and process steps that do not exist in another.**
    - Applying a label from another repo's convention can fail outright if the label does not exist here -- always list the repo's actual labels before applying one from a remembered convention, and expect the equivalent gating label, if any, to have a different name.
    - A PR template path can be lowercase in one repo's `.github/` directory where you would expect the commonly-documented uppercase convention; searching for the uppercase form can fail to expand under a strict shell rather than just finding nothing. Read the actual template file rather than assuming its sections from memory.
    - A process rule that lives in one repo's own contributor instructions is that repo's rule, not the org's rule. Do not import another repo's release-plan, handoff, or post-apply-watch process into a different repo's PR bodies just because both are IaC repos -- and do not apply a gating label as a reflex on production-affecting PRs unless it is this repo's actual convention.

20. **Unapplied IaC drift that WIDENS ACCESS is a latent hazard with a fuse, not a resolved finding -- "the live resource is currently clean" and "the config is safe" are different claims, and only the second one survives the next full apply.**
    - **Record the date with the finding.** A live read showing no exposure today is true only as of that read -- without a date attached, the next person either re-panics unnecessarily or, worse, assumes the wider grant was already applied and is therefore fine.
    - **The exposure that remains is the CONFIG, not the current cloud state.** While the widening change sits in the IaC config -- even unmerged, and especially once merged-but-unapplied on a frozen or dormant unit -- it lands on whoever next runs a full apply on that unit. On a repo where merging IS applying, that can be one unrelated PR away.
    - **A finding like this must never be closed on a live read alone -- it closes only when the widening change actually leaves the config**, whether by revert or by a deliberate, reviewed re-scope.
    - **General rule: grade a not-yours resource that widens access by its CONFIG state, not its current live state, and hand it to the resource's owner as an explicitly open item** -- a review that only checks resources you touched can pass cleanly while a grant two resources away sits armed.

21. **`terraform init -backend=false` REWRITES `.terraform.lock.hcl` in any stack carrying a stale provider entry -- revert it before committing, or a one-file PR becomes a two-file PR.** Observed dropping a provider entry the config no longer referenced at all. It is stack-dependent: a sibling stack with no such entry sees a genuine no-op, so a clean lockfile in one root proves nothing about another. Either way, run `git status` after any `init` and confirm exactly the files you intended.

22. **A stack's `locals` can be evaluated WITHOUT backend credentials by assembling a throwaway config from grep-extracted lines -- and the negative control is what makes it a proof rather than a reading.** `terraform console` cannot run in a stack whose backend needs credentials. Instead, extract the relevant `locals`/resource lines from the real `main.tf` and its companion files with `grep`, assemble them into a scratch config with no backend block, and evaluate there. **Add a MUTATED copy whose input token is changed, and confirm the derived value changes as predicted** -- without that twin, the evaluation only proves the file parses. This is how a derived account id's length and a workload-identity `principalSet` project number were both settled ahead of any plan.
    - **Whole-module `templatefile(...)` variant:** copy the module directory (base via `git archive <ref> <path> | tar -x --strip-components=N`, head via `cp`), lift the real expression into a `zz_render.tf` local, substitute resource-attribute references with literals because console cannot know them, and run `terraform console -var-file` with `nonsensitive(local.zz_render)`. Diff base versus head for each case. Dashboard locals also work: `echo 'jsonencode(local.dashboard_json)' | terraform console -var-file=...`.
    - Set every required variable, including unrelated ones consumed by `coalesce`, and satisfy each input's validation regex. `terraform validate` does not evaluate cross-variable validation with unknown inputs; use `plan` for those conditions. A remote-backend root needs a local `backend_override.tf` for console, and data sources remain "known after apply". If a formatter collapses short JSON arrays, compare generated JSON with `jq -S`, not bytes. For conditional-template whitespace, see #59.

23. **Pre-existing drift is not always "extra stuff that will apply" -- it can be config the default branch CANNOT apply, which converts YOUR merge into a wedged stack and misattributes the failure to your PR.** Observed: a stack's standing drift included a bucket IAM binding rejected by `constraints/iam.managed.allowedPolicyMembers` and a bucket rejected by `constraints/storage.uniformBucketLevelAccess`. The merge commit's own apply failed on both -- neither authored by the PR -- leaving the stack stuck and the PR looking responsible. **Before merging into a stack with standing drift, read the plan TOTAL and separately check whether each drift item is org-policy-legal.** A drift item that has sat unapplied for weeks is a candidate for "cannot apply," not for "nobody got round to it."

24. **An apply reaches later resources only after earlier ones, so a merge CAN succeed at creating YOUR resources and still exit 1 -- verify against the live cloud API, never against the CI badge.** On a stack wedged by an unappliable grant, the apply creates the earlier resources, fails on the offending one, and returns red. Reading the badge as "my change did not land" is wrong in both directions: your resources may exist despite the failure, and someone else's may not exist despite a green on a previous run. A `gcloud`/`aws` describe on the specific object is the only answer.

25. **Two module patterns turn ANY merge into an unrelated production upgrade: `most_recent = true` on managed addons, and any credential that rotates faster than your merge cadence.** Extends #11 with the second class. Measured on a production EKS stack: `aws_eks_addon` for CoreDNS and kube-proxy both set `most_recent = true`, so the version resolves from the cloud provider at PLAN time and every plan carries an addon bump; separately, a Helm `repository_password` sourced from a public-registry authorization token that rotates every 12 h is a perpetual diff. Neither is drift anyone introduced and neither will ever go away on its own. **Enumerate both classes once per stack and name them in the PR body at merge time** -- merging an IAM-only change should not silently ship a CoreDNS upgrade to a multi-tenant production cluster.

26. **`&&` is NOT a portable guard for an unsafe collection access across Terraform 1.9-1.11; use a conditional, or require Terraform >= 1.12.** Reproduced with `length(list) > 0 && list[0].field > 0`: Terraform 1.9.0, 1.10.0 and 1.11.0 all raise `Invalid index`, while 1.12.0 and 1.14.0 return the filtered empty collection. HashiCorp's short-circuit diagnostic change landed in Terraform PR #36224 for the 1.12 line. Modern HCL still obtains BOTH operand values before its `ShortCircuit` hook discards diagnostics from the inactive side, so "the right operand is not evaluated" is an inaccurate explanation even when the expression succeeds. **A module declaring `required_version = ">= 1.9"` therefore has a real compatibility bug if it relies on `&&` to protect `[0]`; write `length(list) > 0 ? list[0].field > 0 : false`, or raise the minimum version.**
    - **Nullable validation expressions need the same version-aware guard discipline.** One portable pattern is `id == "" ? secret == null : (other != "" && try(trimspace(secret), "") != "")`, which protects `trimspace(null)` instead of assuming `||` or `&&` will suppress its diagnostic on every supported version. Cross-variable validation requires Terraform >= 1.9; check the remote workspace's version as well as the local CLI.

27. **A variable default that NO environment overrides is a silent, per-environment apply bomb: it plans a change against whatever the live resource actually is, and the environment whose live value differs is the one that breaks.** On a shared root, a managed-Redis memory-size variable defaulted to `32` and none of the per-environment config files set it; dev and prod happened to run 32, staging ran 10, so every staging apply planned a `10 -> 32` scale-up and died on it -- while dev and prod stayed green forever. **Grep the variable across EVERY environment config before trusting "the default is fine": an unset key is not agreement, it is N environments that have never been compared.** The fix that changes nothing in the cloud is to pin the outlier environment to its *live* value; removing the default instead forces the other environments to declare values too, which is tidier and far riskier. **Prove it with a negative-control plan** -- re-run the identical plan with the key reverted and show the resource reappears (here `0 to add, 2 to change` with the pin, versus `0 to add, 3 to change` plus `~ memory_size_gb = 10 -> 32` without it). A green plan alone cannot distinguish "the pin worked" from "the plan was green anyway."
    - **A deliberate managed-Redis resize still needs an operational window and a timeout check.** The recorded resize preserved data but reset connections for up to ~2 minutes with `READONLY` write errors; it took 23 minutes against a 20-minute Terraform timeout, failing the deploy even though the resize completed. A `--failed` rerun then applied cleanly. Pin the variable to the live value or schedule the resize deliberately.

28. **When a cloud resource update fails inside `terraform apply`, the provider surfaces ONE error but the cloud may have logged several attempts with DIFFERENT causes -- read the service's own operations list before calling the failure flaky or structural.** `gcloud redis operations list --region=<r> --project=<p>` plus `operations describe` on each showed that a single failing CI run had fired **two** update operations: the first returned code 8 `Not enough zonal resources are available to fulfill the request.` (genuinely transient) and the second code 9 `No free IP addresses are available in the instance's IP range.` (structural). Reading only the Terraform error would have called it purely structural; reading only the first operation would have called it flaky. **Specific to Memorystore for Redis:** `reserved_ip_range` is `ForceNew: true` (`google/services/redis/resource_redis_instance.go:466-470`, provider v7.32.0), so widening a too-small range REPLACES the instance -- unacceptable when it backs a live metadata store. A `/29` is the documented minimum only for instances *without* read replicas; it is in spec at rest but has no slack for a scale operation, which provisions new-size nodes against the same range. **The half-finished scale is visible in metrics and nowhere else:** `redis.googleapis.com/stats/memory/maxmemory` broken out by `resource.labels.node_id` showed the replica node stepping `10 GiB -> 32 GiB` seconds after the first failed operation ended, while the instance API still reported `memorySizeGb: 10, state: READY`. Per-node metrics are the only place that partial state shows up.

## Provider syntax, plan replay and deletion proofs

29. **The `helm_release` `set` syntax is pinned by the PROVIDER MAJOR, not by style -- and two roots consuming the same chart at the same version can require DIFFERENT syntax.** Helm provider `~> 3.x` requires the v3 list attribute `set = [{ name = ..., value = ... }, ...]`; `~> 2.x` requires the v2 repeated block `set { name = ... value = ... }`. Proved by negative control: writing the v3 list form under a v2 provider fails `terraform validate` with *"An argument named `set` is not expected here. Did you mean to define a block of type `set`?"*. **So any change to a chart that two roots consume must be made TWICE, in two syntaxes.** Second consequence, for reading plans: **v3's list is POSITIONAL**, so inserting entries in the MIDDLE renders every later entry as a `~ name = old -> new` index shift -- a +2-entry change plans as ~9 modified elements and reads as a rewrite. **Read the name/value PAIRS, not the arrows**: each shifted entry keeps its own pair and the net is exactly +2. Append at the end of the list for a clean plan; mid-list insertion is only a cosmetic cost. v2's `set` is unordered and plans the same change cleanly as +2. Also expect `metadata`/`values`/`revision -> (known after apply)` on EVERY `helm_release` update, always.

30. **When a `helm_release` apply errors during its post-upgrade WAIT, helm has already pushed the new revision but Terraform never recorded the config -- so the NEXT PR's plan REPLAYS the previous PR's changes as if they were yours.** On the following plan, `metadata` (computed) has been refreshed from the LIVE new revision and already shows the new values, while `set` (configured) is still shaped from the last SUCCESSFUL apply. The result is the earlier PR's `set` entries appearing as additions, plus a full positional index-shift cascade (#29), ending with `status = "failed" -> "deployed"`. **Those replayed entries are a STATE ARTIFACT of the earlier failed apply, not part of your branch diff -- name them explicitly when posting the plan, and cross-check by grepping the base branch: if they are already merged there, they are not yours.**

31. **`terraform validate` as a deletion gate is real but VACUOUS WITHOUT A NEGATIVE CONTROL, and two mechanical "proofs" people substitute for it are unsound.** Extends #21. (a) **Always pair a green `validate` with re-adding ONE deleted reference and confirming `validate` FAILS** -- otherwise a green result cannot distinguish "the references are gone" from "validate never looked." (b) **`grep -c '<name>'` as a "this survived" check is unreliable: the pattern can match COMMENTS INSIDE the block you deleted.** On one PR a `grep -c` on a pool identifier dropped 3 to 2 purely because a comment mentioning that identifier sat inside the *other* block that was removed. **Prove survival by extracting the block from base and from HEAD and diffing it byte-for-byte.** (c) `validate` needs `.terraform/providers`; copy an already-initialised `.terraform` from a sibling worktree (it is gitignored -- remove it before commit) rather than running `init`, or use `TF_PLUGIN_CACHE_DIR=<scratch> terraform init -backend=false -input=false` (~2 min) on a root with no backend block. (d) **macOS trap in the same workflow:** `sed -i "" -e A -e B file` can PARTIALLY APPLY and then error *"sed: can't read : No such file or directory"*; a following `perl` pass then operates on already-mutated line numbers and silently shreds the file. Use ONE `perl -ni` pass with all ranges, and re-verify resource counts afterwards.

32. **A RED `terraform apply` is NOT evidence that a destroy did not land -- grep the run log for `Destruction complete` before concluding.** A multi-environment rollout showed one environment's deploy run as `FAILURE` while all four node-pool destroys had completed minutes earlier; the run died later, on an unrelated resource and a permissions error further down the graph. Reporting "the destroy did not apply in that environment" from the run's exit status alone would have been wrong in the most expensive direction -- someone would have re-run a destructive apply.

33. **`google_logging_project_exclusion.filter` has NO `DiffSuppressFunc`, while `google_logging_project_sink.filter` (and the nested sink `exclusions.filter`) DO -- so a heredoc filter permadiffs on a project exclusion and not on a sink.** Verified at provider source: `resource_logging_exclusion.go:34-38` (no suppressor) versus `resource_logging_sink.go:27-29,46-51,81-86` (`OptionalSurroundingSpacesSuppress`, a `strings.TrimSpace` comparison), provider v7.32.0. The Cloud Logging API **strips a filter's trailing newline** -- proved by reading back a deployed sink written from a `<<-EOT` heredoc -- so a bare heredoc on a *project exclusion* re-diffs on every plan. **Wrap it in `trimspace()`. The sink precedent does not transfer**; check for a `DiffSuppressFunc` per resource rather than assuming a resource family behaves alike.

34. **`format("%d", ceil(<float>))` is safe in Terraform -- verified live on 1.16.1: `format("%d", 638.0)` yields `"638"`, no `.0` suffix, no error.** `%d` truncates float to integer cleanly. Relevant whenever a PromQL threshold string, or any other integer-typed literal, is built from Terraform arithmetic, where a stray `.0` would silently produce an invalid expression.

35. **Patching a CLOUD-MANAGED custom resource from Terraform: `kubectl_manifest` with `server_side_apply=true`, `force_conflicts=true`, `apply_only=true` owns exactly ONE field while the cloud keeps the rest -- and `apply_only` means `terraform destroy` never deletes the provider's object.** (gavinbunney/kubectl 1.19.0.) Prove the blast radius offline with `kubectl diff -f <manifest> --server-side --force-conflicts`: it runs the server-side dry-run, persists nothing, and dodges a `kubectl apply` denylist. **The caveat that makes this technique dangerous on its own: it proves the OBJECT changes, not that the component HONOURS it.** Exactly this recipe produced a clean diff on a managed CNI's config CR whose value was already pinned by a higher-precedence env var on the DaemonSet -- it would have shipped a confident no-op. Pair it with a source-level precedence check (`learnings-workload-debug.md`).

36. **A remote-execution TFC workspace rejects `terraform console`, but a transform can still be verified OFFLINE: copy the `.tf` file VERBATIM into a scratch dir with a local backend, mechanically swap ONLY the resource wrapper for an `output {}`, and diff the two files to prove nothing else changed.** That diff *is* the proof -- it converts "I reasoned about this expression" into "the expression is byte-identical except for the wrapper." Companion auth trick: if ADC is stale (`invalid_rapt`) but the cloud CLI still works, pass `access_token = <cli token command>` to the provider instead of re-authenticating.
    - **Heredoc ConfigMap variant:** copy the `<<-EOT` block into a scratch module as a `local` plus `output`, feed each environment's inputs from committed config, run `terraform apply` without providers and `output -raw`, then `cmp` base versus head per environment. Check the config loader's treatment of absent keys: a loader that writes integers bare and skips `None` silently falls back to the variable default.
    - Check the consuming workload's reload mechanism too: a StatefulSet mounting the file via `subPath` with no checksum annotation does not roll on a ConfigMap change, so an apply can succeed while the workload keeps the old content until a manual rollout restart.

37. **A blocking HTTP endpoint's real ceiling is the LOAD BALANCER's backend timeout, not the serverless runtime's request timeout -- and the two can differ by 40x.** On a GCP external HTTPS LB in front of a Cloud Run service, `google_cloud_run_v2_service.template.timeout` was `1200s` while the `lb-http/serverless_negs` module's `backends.default.timeout_sec` was the module/provider default `30`. An endpoint designed to block for up to 300s would have been cut off at 30s with the handler none the wiser -- the design read as sound in every file that mentioned the app. **Check the edge, not just the compute, BEFORE designing any long-poll / wait-for-ready / streaming endpoint**, and verify against the live resource rather than the `.tf`: `gcloud compute backend-services list --project=<p> --format="value(name,timeoutSec)"`. Then map the public hostname to that backend to be sure it is the path clients actually take -- resolve the host, and match the IP against `gcloud compute forwarding-rules list --format="value(name,IPAddress)"`. **The blast-radius consequence is why this belongs in the design, not the fix:** a GCP backend service's `timeout_sec` is per-backend-service, NOT per-path, so raising it for one route raises it for every route and every domain sharing that LB. That makes it a separate change with its own review, and it will not ride along in the feature PR -- discover it early or ship an inert feature.

38. **A provider field that is NOT `ForceNew` can still trigger a full fleet node recreation server-side -- the plan's VERB is not the blast radius.** GKE's `gcfs_config` (Image Streaming) is not `ForceNew` in `google-beta` 7.32.0 (`schemaGcfsConfig`, `node_config.go:241`; the update path at `:4048-4078` uses `UpdateNodePoolRequest.GcfsConfig`), so `terraform plan` reads a reassuring "0 to add, 3 to change, 0 to destroy" -- while GKE's own docs say that exact API call *"immediately begins recreating the nodes ... regardless of active maintenance policies."* In practice that in-place plan hid a roll of over a thousand nodes and their pods across every environment at once. **Rule: for any managed-service resource, the destroy count in the plan describes TERRAFORM's object lifecycle, not the CLOUD's -- check the provider's update path AND the service's documented behaviour for that specific field before grading a chart/infra PR's blast radius.** Second half, and the reason it matters here: **check for auto-apply workflows before grading blast radius at all** -- per-environment deploy workflows triggered on push to a deploy branch and filtered on the service's Terraform path mean merge == apply, with no window to attach a canary. (Same "merging APPLIES" hazard as #1 and #3, on a different repo and a different trigger shape.) The node-side verification technique for the same change is in `learnings-workload-debug.md`.

39. **Deleting a resource is never a one-file diff, and `terraform validate` is the cheap, non-vacuous gate that proves it -- you do NOT need a plan, credentials, or a backend.** A `validation` block, a `locals`, or a `depends_on` elsewhere in the root frequently interpolates the resource you removed; the diff looks surgical and the config does not parse. Observed: a `google_container_node_pool` was deleted from a root's `main.tf`, and a `validation` block in `variables.tf` interpolated EVERY node pool's autoscaling maximum -- so the "one file, deletions only" instruction in the dispatch brief was simply wrong, and following it literally would have shipped a config that fails `validate`.
    - **Offline proof, ~2 min, no cloud credentials:** `TF_PLUGIN_CACHE_DIR=<scratch> terraform init -backend=false -input=false`, then `terraform fmt -check -diff` and `terraform validate`. `-backend=false` skips backend and cloud entirely; the only cost is the provider download, which the cache dir makes one-time. **Delete `.terraform/` afterwards** so it cannot reach the commit.
    - **Run the negative control:** re-insert the single interpolation line and confirm `validate` emits `Error: Reference to undeclared resource`. Without it, "validate passed" only proves the binary ran -- this class of change is exactly where a green check is otherwise vacuous.
    - **Grep with the right TWO spellings.** The HCL address (`example_pool`) and the cloud-side name (`"example-pool"`) are different strings, and a resource's name can survive in unrelated places that must NOT be touched -- e.g. a secondary IP range named after the pool, which cannot be removed until the pool actually is. `grep -c '"<cloud-name>"'` going to 0 while `grep -rn '<hcl_address>'` still returns hits is the expected end state, not a miss.
    - **When N sibling PRs each remove one member of a shared list, the shared prose is a conflict farm.** A single description string naming three pools was left untouched deliberately and called out in the PR body, rather than edited by all three PRs. Reconcile it in whichever lands last.

40. **A remote-backend `plan` you run to evidence a PR WILL contain changes that are not yours -- label them in the comment before a reviewer reads them as collateral damage.** Wrapper `make` targets regenerate tfvars from CLI inputs, so anything whose value comes from an input you did not supply shows as a diff. On one root, a pool-deletion-only branch planned as `0 to add, 1 to change, 1 to destroy` -- and the ENTIRE "1 to change" was a plan-input artifact: a `launch_stage GA -> BETA` standing config-versus-live drift, plus an image-tag variable being dropped because the target falls back to the provider default when that variable is not passed (it even prints *"will use its provider default"*). Pass the CURRENTLY-LIVE image tag, or the plan also invents an image rollback.
    - **The wrapper's `init -reconfigure -upgrade` rewrites `.terraform.lock.hcl`.** `git checkout` it and `rm -rf .terraform/` before committing; the generated `backend.config` and tfvars usually clean themselves up, the lockfile does not. Check `git status` after every evidence plan.
    - **The destroy block is free live-state evidence -- mine it.** A `- resource` block prints the API's view, so `effective_taints = []` and the `labels` map corroborated "nothing can target this pool" from the cloud rather than from the HCL, and `node_count = 1` read correctly as PER ZONE (3 zones = 3 nodes). That is stronger than the repo-side claim it confirms, and it costs nothing extra.
    - **Plan-wrapper hygiene:** use an existing plan-only target before assembling `init` plus `plan` by hand, pass live image tags, and set `TF_INPUT=0`. An `init -upgrade` can bump several providers at once; report that the local plan used upgraded providers while CI uses the committed lock. Child-module validation with `init -backend=false` can also leave an untracked lock file; remove that generated artifact.
    - **Remote speculative-plan recipe:** generate the pipeline's tfvars, pin every live image/tag explicitly, run `terraform init -reconfigure` with an explicit `backend.config` for the org/workspace, then `terraform plan -lock=false`. On the remote-execution workspace this is a speculative run that cannot be applied and holds no lock. Use an environment variable for the cloud project rather than a wrapper's `gcloud config set project`, which mutates global CLI state. Check for the access blockers in #6.
    - Pre-label recurring baseline changes such as a service's `launch_stage` GA-to-BETA, a connection resource's `deletion_policy`, or a load-balancer backend no-op. A missing CI-computed variable is a plan-input artifact. For apparent deletion of an entire computed Helm `metadata.values` document, inspect the separate values delta as in #9.

41. **`terraform fmt -diff` WITHOUT `-check` REWRITES THE FILES -- it is a mutating command wearing a read-only name, and it silently destroys a surgical diff.** Used to compare formatting between base and head on one PR, it reformatted an entire root `main.tf`; a deliberate `+4 / -0` change committed as `+19 / -15`, sweeping in unrelated `depends_on`, `dns_name` and `for`-expression realignments across the file. Only the `git diff --stat` on the commit caught it. **Always `fmt -check -diff`** (verified read-only: `git status` stays clean) -- `-check` is what suppresses the write, `-diff` only controls whether the diff is printed. Same trap as `gofmt`. Recovery is `git reset --hard <base>` and re-apply the change; do not hand-unpick it.
    - **On a root that is ALREADY not fmt-clean, "fmt -check clean" is an unachievable acceptance criterion -- measure the DELTA instead and say so.** The root failed `fmt -check` on the base branch with 30 changed lines, so the honest report is base-30 versus head-32, where the +2 is the new entry written to match its siblings byte-for-byte. Reformatting the file to go green would bury a 4-line IAM diff under 30 lines of noise. Match the neighbours and report the pre-existing failure with numbers.

42. **Adopting an environment into a shared Terraform `for_each`/`setproduct` IAM map: grade it in PERMISSIONS, not role names, and enumerate EVERY consumer of the map.** Adding a new environment key to `locals.environments` read as "5 net-new roles" -- but the permission-level delta against the union of the 25 roles the service account already held told a very different story: `gkehub.gatewayAdmin` contributed 0 net-new permissions and `gkehub.admin` only 3 (`*.setIamPolicy`), while `iam.serviceAccountTokenCreator` (5: `getAccessToken`/`signBlob`/`signJwt`/`getOpenIdToken`/`implicitDelegation` -- SA impersonation) and `iam.workloadIdentityPoolAdmin` (25) were the real grants. Recipe: dump the module's role list, dump live bindings with `gcloud projects get-iam-policy <p> --flatten="bindings[].members" --filter="bindings.members:<sa>" --format="value(bindings.role)"`, `comm -23`/`-13` for the role delta, then expand every already-held role via `gcloud iam roles describe --format="value(includedPermissions)"` into one sorted union and `comm -23` each net-new role against it.
    - **`roles/editor` is far wider than reviewers assume and will hide most of a delta.** It carries the COMPLETE `gkehub.gateway.*` set (`generateCredentials/get/post/put/patch/delete/stream`) and `gkehub.memberships.*`, so a project with `editor` can already drive GKE Connect Gateway -- do not infer "Connect Gateway must have been failing there" from a missing `gkehub.*` role. It does NOT carry `logging.exclusions.create`, any `iam.serviceAccounts.*` token minting, or workload-identity-pool mutation.
    - **`grep -n 'local.<map>'` before writing the blast radius.** The map had FOUR consumers, not the two named in the task: beyond the two `google_project_iam_member` resources, a `google_project_iam_custom_role` and its binding also iterate it -- so adoption additionally CREATES a custom role in the new project (net-new `secretmanager.secrets.setIamPolicy`). A privilege write-up that misses a consumer understates the grant.
    - **Nothing is removed, and say so unprompted:** `google_project_iam_member` is additive and non-authoritative, so roles the project holds out of band survive adoption. Only `google_project_iam_policy` / `google_project_iam_binding` would strip them. Reviewers reliably worry about this.
    - **A role the target already holds plans as a CREATE, not an import** -- Terraform has no state for it -- but the resulting policy is unchanged. Call it a no-op create; "import-in-place" is wrong and will confuse whoever reads the plan.

43. **A Terraform root can have NO deploy path at all -- check the TFC workspace, not just `.github/`, before telling anyone what "merged" means.** One root had zero references under `.github/` (only `make init-<root>` / `apply-<root>` in a deploy makefile), and its HCP Terraform workspace turned out to be CLI-DRIVEN: `vcs-repo: null`, `auto-apply: false`, `execution-mode: remote`. So merging the PR granted nothing -- a human had to run the apply. Read it without printing the token: `curl -sS -H "Authorization: Bearer $(python3 -c "import json;print(json.load(open('$HOME/.terraform.d/credentials.tfrc.json'))['credentials']['app.terraform.io']['token'])")" https://app.terraform.io/api/v2/organizations/<org>/workspaces/<ws>` and read `attributes.{vcs-repo,auto-apply,execution-mode,terraform-version}`. **Absence of a CI workflow is NOT proof of manual-apply** -- a VCS-connected workspace auto-plans on push with no GitHub Actions involvement at all, so the workspace attributes are the decisive evidence. State this prominently in the PR body of any privilege change that does not self-deploy.

44. **`google_container_node_pool.node_config.machine_type` is NOT `ForceNew` at provider 7.32.0 -- a GKE machine-type change is an IN-PLACE rolling update, not a pool recreate.** Verified at source in both `hashicorp/google` and `hashicorp/google-beta` (byte-identical `node_config.go` at the same tag, only line offsets differ): `machine_type` is declared `Type/Optional/Computed` with NO `ForceNew` (`node_config.go:504-508` in google-beta, `:485-489` in google) -- **contrast the ADJACENT `metadata` (`:509-515`) and `min_cpu_platform` (`:518-523`), which DO carry `ForceNew: true`, so the omission is deliberate rather than an oversight.** The update path is `nodePoolNodeConfigUpdate` (`:3679-3683`), which batches `disk_size_gb`/`disk_type`/`machine_type`/`storage_pools`/`boot_disk` into one `container.UpdateNodePoolRequest` and waits via `ContainerOperationWait`. The only registered `CustomizeDiff` is accelerator-related, so **there is no dynamic `ForceNewIfChange` path either.** Consequence: the plan renders `~` in-place, `create_before_destroy`/`prevent_destroy` are irrelevant, and the pool never goes to zero capacity from Terraform's side -- transient capacity is governed by `upgrade_settings`. **Second, harder finding: `kubelet_config` at 7.32.0 does NOT EXPOSE `eviction_hard` OR `kube_reserved` AT ALL.** The sub-schema has only `cpu_manager_policy`, `memory_manager`, `topology_manager`, `cpu_cfs_quota(_period)`, `insecure_kubelet_readonly_port_enabled`, `pod_pids_limit`, `max_parallel_image_pulls`, `container_log_max_size/files`, `image_gc_*`, `allowed_unsafe_sysctls`, `single_process_oom_kill`, `eviction_max_pod_grace_period_seconds`, `eviction_soft`, `eviction_soft_grace_period`, `eviction_minimum_reclaim`. **So "tune the hard eviction thresholds or the reservations via Terraform" is not merely unwise -- it is INEXPRESSIBLE at this version.** Caveat kept honest: only the provider's CALL PATH was verified at source; the GKE control-plane behaviour behind `NodePools.Update` was not. **Pairs with #38 -- a non-`ForceNew` field can still roll the whole fleet, so "in-place" in the plan is a statement about Terraform, not about your nodes.** (See `learnings-gke.md` for what that roll then does on an autoscaling pool.)

45. **A root using `backend "remote"` in CLI-DRIVEN mode CANNOT source a module from OUTSIDE its own directory -- the CLI uploads ONLY the config dir.** Verified empirically on a real TFC run and then read at source: `internal/backend/remote/backend_plan.go:205-240` (v1.16.1) computes `configDir = Clean(TrimSuffix(Clean(abs(ConfigDir)), Clean(w.WorkingDirectory)))` and uploads THAT. A `source = "../modules/<x>"` therefore fails in TFC with *"Unable to evaluate directory symlink: lstat ../modules: no such file or directory"*, while working fine locally. **The fix is the WORKSPACE's working-directory setting, not the module path:** setting it to the root's own leaf name makes the CLI upload the PARENT, which is where `modules/` lives -- and that is far smaller than setting the full path, which uploads the whole repo. This is WHY a repo with several TFC-remote roots will have every one of them keeping `modules/` INSIDE its own directory, and why the only `../../../` traversals you find are under a Terragrunt-driven tree instead. Add a parent-level `.terraformignore` if the upload gets large.

46. **Before collapsing N resources into a `for_each` over an EXISTING `local`, verify the local is actually the SOURCE OF TRUTH -- rebuild it MECHANICALLY from the resources rather than trusting it.** One `local.<x>_apis` list was purely decorative: it named an API with no resource and never enabled, and it OMITTED eight APIs that did have resources. Nothing consumed the list, so the drift was invisible -- and it would have become real the moment the `for_each` shipped. **And `google_project_service` with `disable_on_destroy = true` makes a MISSED `moved` block genuinely DISABLE LIVE APIs** -- so the migration gate is a plan showing 0 destroy, PLUS a negative-control plan at the prior commit to prove plan-neutrality.

47. **When a regex has multiple alternatives, test each one IN ISOLATION against wrapped terraform output -- the assembled regex can pass via one alternative while another is dead.** A fixture table showed MATCH for the assembled regex `(Failed to install provider|the request failed after [0-9]+ attempts)`, which passed exclusively via the Summary anchor `Failed to install provider`. The second alternative was dead: terraform's 78-column wrap fell between `after 3` (end of one line, 73 chars) and `attempts,` (start of the next), and `grep` is line-based. The assembled-regex test was vacuously green -- it proved the change worked, not that both alternatives worked. **Rule: for a multi-alternative regex over terraform output, test each alternative against the WRAPPED fixture in isolation.** Fix for the dead alternative: `please try again later` is the adjacent fragment on its own wrapped line (67 chars in the observed output), sourced from the same `maxRetryErrorHandler` string in `internal/getproviders/registry_client.go`, and absent from every deterministic-failure Detail, so it does not over-match.

## Provider ownership, plan hygiene and offline proofs

48. **`gavinbunney/kubectl` `data.kubectl_file_documents` keys its `manifests` map by a GENERATED SELF-LINK, and that key string is a load-bearing plan-time guard.** At **v1.19.0**, `yaml/manifest.go` `buildSelfLink()` (`:56-96`) builds `/apis` + `/<apiVersion>` + `/namespaces/<ns>` + `/<lowercased kind>s` + `/<name>` -- with `/api` instead of `/apis` when `apiVersion` is bare `v1`, and an `es` suffix when the kind already ends in `s`. So an `apps/v1` Deployment `agent-sandbox-controller` in `agent-sandbox-system` is exactly `/apis/apps/v1/namespaces/agent-sandbox-system/deployments/agent-sandbox-controller`. Two properties make this usable rather than fragile: the map **VALUE** is the provider's own re-serialisation (`manifest.AsYAML()`), not the raw source text; and the data source **ERRORS on a duplicate self-link**. **Therefore `merge(documents.manifests, { (selflink) = local.canonical })` is a safe in-place REPLACE of one document inside a `for_each` map** -- same key set in, same key set out, so nothing is added or destroyed. And it is **self-checking**: a one-character mutation of the key fails at plan time with *"Error: Invalid index"* (or shows Terraform **adding** a `for_each` instance rather than changing one), so **"0 to add" in a real plan is sufficient proof the key string is right.** Put the constant in a `local` so a future provider key-format change errors loudly instead of silently leaving two owners.

49. **SUPERSEDED by #53 -- moving the extra instance to a temporary bare address, then removing it with destroy=false, avoids the mandatory manual state rm.** **DUAL Terraform ownership of one Kubernetes object across two `for_each` resources: what it actually costs, and why NORMALIZING beats de-duplicating.** Two assets that both ship the same Deployment produce the **same map key in two different resources**. **The cost of true single ownership is exactly one manual state operation per workspace, and skipping it DELETES the object:** exclude the key from both maps, add one dedicated resource, carry ONE old instance across with `moved` (which accepts an indexed instance address, but `from`/`to` must be **literal** -- no locals, so the self-link string is necessarily duplicated); the OTHER instance cannot be `moved` (destination occupied) and cannot use `removed` (that drops **every** instance of the resource), so it needs `terraform state rm` **before** the apply. **Do NOT reach for `lifecycle.prevent_destroy` as the guard** -- it blocks the very version bump this prepares for, since release assets legitimately add and drop documents between versions. **Prefer #48's merge-override instead when applies run auto-approve with no environment protection:** a mandatory pre-apply `state rm` in N workspaces is a worse risk than two owners writing **identical bytes**, and existing `depends_on` ordering already stops the two applies racing. 50. **What dual ownership costs when the two owners DISAGREE, and why "the copies differ" understates it.** `gavinbunney/kubectl` defaults to **CLIENT-SIDE apply** (`server_side_apply` unset), i.e. a three-way merge against `kubectl.kubernetes.io/last-applied-configuration` with `Overwrite=true` and a single field manager `Go-http-client`. Two owners writing **identical** YAML is a true no-op (empty patch). Two owners writing **different** YAML **actively fight**: each apply patches the other's fields out and triggers a pod restart, **every run, forever**. **So the decisive diagnostic for a dual-owner refactor is not reading the diff -- it is rendering BOTH the old and the new locals as standalone Terraform against the committed provider versions and comparing the produced documents.** On one such review that render showed the dual-owner write was **PRE-EXISTING and already identical** at the current pin, which made the refactor's "two in-place updates" plan shape the **status quo rather than a new symptom** -- a conclusion no amount of diff reading reaches. It also revealed the divergence starts one version EARLIER than reported (an added volumeMount/volume pair at the next tag, not two tags later), i.e. normalization was needed immediately, not eventually.

59. **Terraform's flush heredoc (`<<-EOT`) and `%{ if }` directives interact badly, and the failure is whitespace in the rendered output -- always render base-vs-head per environment as a negative control.** Measured forms: a line beginning `%{~ if` **breaks indent stripping for the WHOLE heredoc** (every line keeps its indent); `%{ if c ~}` with the body on the next line leaves the **body line** indented.
