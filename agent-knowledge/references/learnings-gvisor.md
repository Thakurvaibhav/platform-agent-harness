# gVisor / runsc Learnings

See also: `learnings-agent-sandbox.md` (the `kubernetes-sigs/agent-sandbox` control plane that schedules these pods), `learnings-eks.md` (the self-installed-runsc side: nodeadm/containerd on AL2023), `learnings-gke.md` (GKE Sandbox, where the platform injects what EKS makes you install), `learnings-network-policy.md` (socket-LB and egress-policy behaviour that is *different* under gVisor), `learnings-workload-debug.md` (node pressure, evictions and probe budgets on these nodes), `learnings-observability.md` (the kubelet/cAdvisor metrics that do and do not see a gVisor pod), `learnings-container-images.md`.

Source-verified behaviour of `runsc` and the containerd shim. **Every entry below is pinned to gVisor `release-20260504.0` and containerd `v2.2.7` unless it says otherwise**, because the memory model and the annotation plumbing have both moved across releases. Re-read the cited `file:line` before relying on any of it at another version.

1. **At `release-20260504.0` the sentry's memory is a host `memfd` and is NOT reclaimable or pressure-driven, so a gVisor pod's host footprint behaves unlike a normal container's.** The main `MemoryFile` is memfd `runsc-memory` (`runsc/boot/loader.go:932-944`) and `UseHostMemcgPressure` is deliberately disabled, so the host kernel sees app memory as **shmem-rss of a process named `exe`** and cannot reclaim it. `DelayedEvictionDefault` is `Enabled` (`pkg/sentry/pgalloc/pgalloc.go:423-428`), so eligible pages are evicted when the releaser runs out of waste (`:1276-1279`), not on host pressure; `ShouldCacheEvictable` is false by default (`:1553-1554`). ⚠️ **Reporting is separate from enforcement:** `sandbox.go:1298-1306` derives the boot total-memory from the sandbox host cgroup and `loader.go:674-678` sets reporting bounds, but sentry `cgroupfs` `memory.limit_in_bytes` is a **stub** (`pkg/sentry/fsimpl/cgroupfs/memory.go:87`), so a limit the guest reports is not a limit anything enforces. Subcontainer host cgroups get empty resources (`container.go:1945-1964`); no per-app OCI limit import into the sentry was found. The rootfs overlay default is `root:self` (`config.go:956-958`), a regular host filestore, not the main memfd.

2. **The only enforced memory bound on a gVisor pod is the POD-level memcg, i.e. the SUM of every container limit including native sidecars, and one OOM kills the whole sandbox.** The shim joins the sandbox to the pod cgroup (`pkg/shim/v1/runsc/service.go:696-729`), subcontainer host cgroups are empty compatibility dirs (`runsc/container/container.go:1945-1964`), and there is **one sentry per pod**, so an OOM takes the envoy/infra-manager sidecars down with the app. The sentry cannot use host memcg pressure (`loader.go:940-944`) and has **no internal OOM killer**. ⚠️ **A `RuntimeClass` `overhead` does not fix limit-vs-allocatable overcommit: it RAISES the pod cgroup limit.** Budget sandbox limits against node allocatable directly.

3. **A Unix-socket `bind()` on a gofer-backed volume silently becomes an in-sentry SYNTHETIC socket that other containers cannot see, unless the pod carries `dev.gvisor.spec.mount.<vol>` hints.** With `host-uds=none` (the default), `bind` falls back to a synthetic dentry (`pkg/sentry/fsimpl/gofer/filesystem.go:906-950`; the gofer returns EPERM at `runsc/fsgofer/lisafs.go:913-919`). Without `share=pod`/`type` hints each container mounts the emptyDir through **its own gofer fs instance** (`runsc/boot/vfs.go:778-797`), so a socket created in one container is invisible in the others, while regular files still work through the host dir, which is what makes this so easy to miss. 🔑 **GKE Sandbox injects the hints at admission** (observed `share=pod,type=bind,options=rw,rprivate`); a **self-installed runsc needs BOTH** the pod annotations and a containerd `pod_annotations` allowlist, because hints are read only from the pause (root) container's OCI spec (`runsc/boot/loader.go:763`, `pkg/shim/v1/utils/volumes.go:158-189`) and containerd forwards only allowlisted annotations (`internal/cri/server/podsandbox/sandbox_run_linux.go:192`). Upstream doc: `g3doc/user_guide/containerd/configuration.md:150-248`.

4. **A `dev.gvisor.spec.mount.<vol>` hint fails pod creation only when `<vol>` resolves to 0 or >1 kubelet volume dirs: a non-emptyDir volume is accepted, and an EMPTY emptyDir is rewritten to `tmpfs` in the annotation while the OCI mount stays a disk-backed bind.** `pkg/shim/v1/utils/volumes.go UpdateVolumeAnnotations`. So "the annotation says tmpfs" is **not** evidence the volume is RAM-backed, and the 0-or-many rule is the only validation you get. GKE admission leaves pre-set identical `dev.gvisor.spec.mount.*` keys untouched (live dev-cluster test 2026-10-26).

5. **`pod_annotations = ["dev.gvisor.*"]` forwards far more than mount hints: it opens the runsc FLAG override surface.** At `release-20260504.0` that pattern also carries `dev.gvisor.flag.host-uds/debug/strace/oci-seccomp/overlay2` (the runsc flag `overrideAllowlist`, **no `--allow-flag-override` needed**), `dev.gvisor.internal.nvproxy/tpuproxy/seccomp.*`, `dev.gvisor.spec.cgroup-parent` and `dev.gvisor.tar.rootfs.upper` (`runsc/config/flags.go:183`, `specutils.go:45-85`). ✅ **Narrow the allowlist to `dev.gvisor.spec.mount.*` when mount hints are all you need**: a pod annotation is attacker-reachable wherever pod specs are.

6. **containerd's `pod_annotations` patterns are Go `path.Match`, so `*` crosses dots but not `/`.** `dev.gvisor.spec.mount.*` therefore DOES match `dev.gvisor.spec.mount.<vol>.share`, and does not match any key containing `/`. Verified by executing containerd `v2.2.7` `GetPassthroughAnnotations` verbatim rather than reading the glob and guessing.

7. **A `runsc.toml` change needs NO containerd restart, the shim re-decodes the file at `ConfigPath` on EVERY container create, but every value must be a QUOTED STRING or pod creation fails.** `pkg/shim/v1/runsc/container.go:88-103` (via `service.go:184`) decodes on each create and turns `[runsc_config]` into `--flags` per runsc call (`runsccmd/runsc.go:567-569`). `RunscConfig` is `map[string]string` (`pkg/shim/v1/runsc/options.go:55`), so `systemd-cgroup = true` (unquoted) fails TOML decode and breaks pod creation, while `systemd-cgroup = "true"` works, and the shim compares the literal `"true"` (`container.go:208`).

8. **`systemd-cgroup = "true"` does NOT place the sandbox in a per-pod `pod` cgroup segment on a systemd-driver node; it switches the shim's cgroup mode, and the POD SLICE is what still bounds the sandbox.** `setPodCgroup` (`pkg/shim/v1/runsc/service.go:700-735`) splits `CgroupsPath` on `/` and finds no `pod` segment in a systemd path (`kubepods-….slice:cri-containerd:<id>`), so the sandbox stays in the pause container's scope under the pod slice. The flag's real effect is flipping `cgroupMode` Legacy→Unified (`container.go:208`).

9. **Without `systemd-cgroup=true` on a systemd-cgroup-driver kubelet, the gVisor sandbox lands under CONTAINERD's cgroup instead of the pod's: pod memory limits and `kubepods` allocatable stop applying, and one agent can livelock the whole node.** Reproduced on AL2023/EKS 2026-10-27, with a `runc` control that OOMKilled cleanly as the negative control. 🔎 **Detect it from `stats/summary`: the gVisor pod shows `workingSetBytes` ≈ 0 while `systemContainers` `runtime` grows.** ⚠️ The fix applies only to pods CREATED after the installer rolls: running pods keep the escaped cgroup, so a rollout is not a remediation until the old pods recycle.

10. **Converge a TOML key by DELETING it within the table range and re-inserting, never by an exact-LINE idempotency grep: the grep makes any future VALUE change insert a second key and produce invalid TOML that containerd refuses to start on.** Seen on a `pod_annotations` installer: `grep`-for-the-exact-line is idempotent only while the value never changes, and go-toml/v2 rejects the duplicate outright. Reproduced against a nodeadm fixture with `tomllib` as the oracle. Related shape rule: restart the runtime **inside each editing branch** and log-skip when already converged, rather than guarding on a before/after hash.

11. **Registering a runtime in containerd with only `runtime_type` + `TypeUrl`/`ConfigPath` and NO `pod_annotations` list means pod annotations never reach the OCI spec, so mount hints you believe you set are simply absent.** ⚠️ **Recorded as an UNVERIFIED hypothesis** (self-installed runsc on EKS, 2026-10-27): it follows from #3/#6 but was not reproduced end to end. Check it against containerd and gVisor source at your pinned versions before relying on it either way.

12. **Identifying a runsc victim in an OOM report: the sandbox appears as comm `exe` with the app's memory as shmem-rss (the sentry memfd of #1), not under any recognisable container name.** Multiple victims with `oom_score_adj` 997-999 killed in the same second is the signature of a **parent `kubepods` memcg OOM**, not the pod's own limit being hit: a distinction that changes the fix from "raise this pod's limit" to "stop overcommitting the node". (Node-event proof method: `learnings-gke.md`.)

13. **gVisor stopped publishing standalone `runsc` and the containerd shim in the release bucket, and an installer that copies only the two binaries BREAKS ON UPGRADE.** From release-20260831.0 the per-release directory holds only `gvisor.tar.{bz2,zstd}` plus checksums. The tarball contains `runsc` (19MB, down from 64MB), the shim, and a `gvisor-bin/` directory of sidecars (sentry, checkpoint gofer, proc-umounter, sentry-prewarmer, fd-parking, metric-server). `runsc` resolves sidecars from `<dir of runsc>/gvisor-bin` or `GVISOR_SIDECAR_BINARIES_DIR` (`runsc/gvisorbinaries/gvisorbinaries.go` `resolveDir`), the embedded fallback was removed at 20261012.0, and the usage-policy flag was retired to the graveyard. **Sidecars PANIC on a release mismatch with `runsc` (`GVISOR_ENFORCE_RELEASE`), so `runsc` and `gvisor-bin/` must be swapped TOGETHER.** From release-20261012.0 resolution is against `realpath(/proc/self/exe)`, so a SYMLINKED `runsc` finds `gvisor-bin` next to the TARGET. Criticality differs per sidecar: a missing prewarmer or proc-umounter makes create fail hard, while a missing fd-parking is a warning only. Upstream's own `runsc install --download-sidecars` uses the same move-aside-then-rename swap. Release tarball members are root-owned 0755 static ELF.

14. **`runsc` has NO release or version gate when controlling an EXISTING sandbox, so a cross-release pairing is best-effort and fails by silently zeroing fields rather than erroring.** At release-20261026.0 `container.Load` reads the JSON state file with plain `json.Unmarshal` (`runsc/container/state_file.go` `loadLocked`) and `Sandbox.call` dials the control socket from that state file and sends JSON urpc dispatched by method NAME. Diffing RPC name strings from 20260504.0 to 20261026.0, only one method disappeared (replaced by a differently named one, called only at create and restore); signal, wait, event, exec, process-listing, runtime-state and subcontainer-destroy all persist. So names match but ARG-STRUCT FIELD DRIFT silently zeroes fields. The release-enforcement panic applies only to sidecars `runsc` SPAWNS, not to controlling an old sandbox. **Mitigation: recycle old sandboxes soon after a `runsc` upgrade.** The state-file schema change over the same span is ADDITIVE only and uses the same lock path, and a zero PID-identity matches any PID, so a new `runsc` still kills old sandboxes by PID with no orphan.

15. **gVisor lets ANY uid with ZERO capabilities gain mount, bind and lazy umount inside the sandbox via `unshare(CLONE_NEWUSER|CLONE_NEWNS)`, so dropping `CAP_SYS_ADMIN` is NOT a mitigation for in-Sentry VFS bugs.** Traced at release-20260504.0: `ForkIntoUserNamespace` grants ALL capabilities including the bounding set (`pkg/sentry/kernel/auth/credentials.go:157-175`); `NewChildUserNamespace` checks only depth < 32 and uid mapping (`auth/user_namespace.go:101,114-140`); `Unshare` checks `SYS_ADMIN` against the NEW credentials (`kernel/task_clone.go:798-815`) and the new mount namespace is owned by the new user namespace (`:837`), with `sys_mount.go:37/:143` checking capabilities in that owner; tmpfs sets `AllowUserMount` (`runsc/boot/vfs.go:158-159`). **No `runsc` flag and no `max_user_namespaces` sysctl turns it off**, and the OCI seccomp profile is IGNORED unless `--oci-seccomp` is set (`runsc/boot/seccomp.go:28-34`, `flags.go:108` default false). Live-proven as an unprivileged user with `CapEff=0`, and still working after `PR_CAPBSET_DROP(CAP_SYS_ADMIN)`. The only real mitigations are patching `runsc` or an `--oci-seccomp` profile that denies `unshare`/`clone(CLONE_NEWUSER)`. **Corollary for a managed offering: enabling `oci-seccomp` at the runtime config enforces NOTHING if the pods set no `seccompProfile`, which is worth checking before counting it as a control.**

16. **Mapping a managed-platform `runsc` build to upstream when it reports an internal revision instead of a release tag.** A managed node's `runsc version` can return an internal changelist identifier rather than a `release-*` tag. Map it by searching upstream commit messages for the revision id (`gh api repos/<owner>/<repo>/commits/<sha>`) and comparing the revision numbers of the fix commits you care about: that places the build BETWEEN two fixes, which is enough to grade it affected or not. **Treat 'between' as AFFECTED unless the vendor confirms a cherry-pick**, and note that a vendor may publish no bulletin and no release note naming the CVE at all. `kubectl debug node` plus a chroot onto the host filesystem is a read-only way to get the version off the node, and it works on sandbox node pools because the debug pod runs the default runtime and tolerates all taints.
