# Confluence (Atlassian MCP) Editing Learnings

Surgical-edit mechanics for approved Confluence pages via the Atlassian MCP.

See also: `learnings-code-review.md`, `learnings-agent-workflow.md`

## Edit mechanic

1. **`updateConfluencePage` REPLACES the entire body** (it is not a patch). Safe surgical-edit flow: `getConfluencePage contentFormat=html` -> write the fetched body to a temp file -> `cp` to an `_edited` copy -> make unique-string Edits per change -> update with `contentFormat=html`. On the update call pass ONLY `cloudId`, `pageId`, `body`, `contentFormat=html`, `versionMessage` -- OMIT `title`/`parentId`/`spaceId` so you cannot accidentally rename or reparent (version auto-increments). HTML round-trip is safe for tables/code/panels/mentions/inline-comment annotation spans IF you pass the EXACT fetched HTML back.

2. **Confluence storage stores newlines inside `<pre><code>` blocks as the LITERAL two-character sequence backslash-n, not a real newline.** On round-trip html->html edits you MUST preserve that exact form, or you get phantom diffs / corrupted code blocks. Apply a backslash-n -> real-newline normalization to BOTH sides before diffing, and re-emit the literal form on write.

## Proving the edit (verification integrity)

3. **The structural diff MUST run on BYTES THE SERVER RETURNED, not on your submission.** Trap: `cp page_edited.html page_live.html` then diffing = comparing the submission to itself (circular, proves nothing). Correct: write BOTH the first-fetch body (true vN) AND a RE-FETCH body (true vN+1) to files, apply the same normalization to each, and diff true-vN+1 vs true-vN.

4. **`diff` is useless on a Confluence body -- it is ONE line with no newlines.** Use Python `difflib.SequenceMatcher` on `re.split(r'(?<=>)')` tokens for a structural region diff. Verify round-trip safety for rich content by counting `data-annotation-id` / `data-type=mention` / `data-type=status` / `<table` / `<pre` occurrences before vs after -- they must match.

## Collision-safe anchoring

5. **NEVER replace a bare substring whose text ALSO appears in an already-corrected region.** Anchor each `old_string` on full surrounding context and assert match-count == 1 in Python before `replace()`. When a status word is non-unique (e.g. "Not Started" appears 12 times), combine a row's task + status cells into ONE contiguous `old_string`. Post-edit guard: assert the PROTECTED-string count is unchanged rather than global-absence (which falsely flags the kept copy).

## MCP tool availability

6. **Atlassian/Confluence MCP tools (create AND update) only work in the PARENT agent context -- sub-agents prepare the page body and return it for the parent to make the call.** This is an instance of the general MCP-parent-only rule; canonical statement in `learnings-agent-workflow.md#31`.

## Rich-content round-trip traps

7. **A Confluence page write can return HTTP 200 with an incremented version number and still have silently discarded your edits — for status-chip-style macros, the API reverts your label changes back to the stored value keyed by the chip's own internal id.** Reading a page as `contentFormat=markdown` renders status-chip macros as a tag carrying a `data-id` plus the label text; editing the label in place and writing back as markdown returns success and a new version, but the server restores each chip's label from its stored `data-id`, discarding your edit — and a newly-added chip with a fresh id renders as bare text instead of a chip at all. **Fix: write status-chip changes as `contentFormat=html`, using a span-style status element with the label and a color attribute but no id** — the server then assigns a clean id itself. **General rule this sharpens: after any write to a rich-content page, re-read the page and diff specifically the fields you intended to change** — a byte-diff of your own submission cannot catch this, because your submission was never what got stored.


## Markdown formatting and required fields

8. **An Atlassian content-write API that accepts a `contentFormat` parameter often defaults to Markdown even when the destination system's native format is a different wiki markup — passing the wrong one renders as mangled literal text, not an error.** Legacy wiki-style syntax (heading markers, pipe-delimited table headers, brace-wrapped code spans) doesn't error when submitted as markdown; instead it degrades unevenly — some elements survive by coincidence, tables lose their header row, inline code markers stay as literal characters, and list bullets pick up spurious escape characters. There is no validation step that catches the mismatch — the only symptom is that the rendered page looks broken. Always set the content-format parameter explicitly rather than relying on the default, and use the destination's actual native format (standard Markdown headings/tables/code fences, or the platform's structured-document format for anything Markdown can't express) rather than a format that happens to have originated in a different but similar-looking tool.

9. **A pair of asterisks inside a table cell in Markdown-formatted content is parsed as emphasis and silently removed from the rendered output — a single trailing asterisk (as in a wildcard suffix like `resource:*`) is unaffected, but a paired occurrence (`a:*, b:*`) loses both asterisks and italicizes the surrounding text.** This is a generic Markdown-to-rich-text gotcha, not specific to any one field type — it shows up wherever wildcard-suffixed tokens (IAM actions, glob patterns, permission scopes) get typed into a table cell. Fix: wrap any token containing an asterisk in inline-code backticks, which also renders it in monospace, which is usually what you wanted for that kind of token anyway.

10. **An issue-tracker's create-issue metadata endpoint can fail to report that a custom field is actually required — the create call itself succeeds in telling you, via a plain-English error message, but the structured error/required-fields output doesn't name the field at all.** The create call returns an error naming the field in prose, with the structured error map empty and the field not flagged as required in whatever "get required fields for this issue type" call exists — so the two ways you'd normally discover requirements before submitting both come back clean. Some required fields (team/group-type selectors, in particular) are passed as an opaque id string rather than a nested object, which is also not obvious from the schema. The fastest reliable way to discover a required custom field's id and expected value shape is to read it off an existing, already-valid issue of the same type in the same project — fetch it with an explicit narrow field list (don't fetch full-text fields unscoped; a broad search across many issues can return an unreasonably large payload) and copy the field's id and value shape from a real example rather than guessing from the schema.

11. **Transitioning an issue to a terminal or gating status can require a custom field that isn't present on the transition's own input screen — so setting it in the transition call itself fails, and it must be set as a separate edit beforehand.** The failure has two layers that look similar but need different fixes: first, transitioning with the field omitted fails because the field is required for that transition; then, passing the same field as part of the transition payload fails differently, because that screen doesn't expose the field for editing at all. The correct sequence is an ordinary field edit first (setting the required value), followed by the transition as a separate call. When guessing the field's expected value, matching a sibling issue in the same grouping (same epic/parent) is more reliable than guessing from the schema. Two adjacent gotchas worth checking for: an intermediate status may have no direct transition path to the terminal status you want (you may need to pass through another status first), and the set of valid transition ids itself depends on the issue's current status, not just its type.
