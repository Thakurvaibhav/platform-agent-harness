# agentgateway Learnings

See also: `learnings-agent-sandbox.md`, `learnings-network-policy.md`, `learnings-envoy-gateway.md`

`agentgateway/agentgateway` (Kubernetes CRD mode + Rust data plane) -- CONNECT-tunnel re-entry mechanics, credential-brokering (extAuthz / backendAuth) trust boundaries, CRD config shapes that silently no-op, and status fields that lie. Every claim is version-pinned; re-verify against your own version before relying on one. Unless stated otherwise, agentgateway findings refer to v1.4.1 (`git_revision 163ea214`) and HEAD `25664ff504d8a0752fd9635a1bcfe343011f750a` (2026-08-14).

Numbered, append-only. **Update the existing entry — never duplicate.**

## CONNECT re-entry and egress containment

1. **SUPERSEDED by #4 — frontend connection policies require `targetRefs[].port`; the `sectionName` targeting claim below is CRD-rejected.** **CONNECT re-entry is Gateway-scoped, `mode: internal` does not gate it, and there is no target-allowlist field -- but `ConnectMode::Route` and per-listener `networkAuthorization` are the two mitigations that actually work.** Source-read at v1.4.1 (`git_revision 163ea214`) and HEAD `25664ff504d8a0752fd9635a1bcfe343011f750a`; the re-entry block is byte-identical between the two, and upstream PR agentgateway/agentgateway#3013 did not touch re-entry selection.
    - **Scope.** `terminate_connect_tunnel` (`proxy/gateway.rs:722-835`) parses the CONNECT authority port and resolves it via `binds.find_bind_by_port` / `find_bind` / `find_wildcard_bind` (`store/binds.rs:1569-1614`), which iterate the entire bind store with no reference to the ingress bind and no `BindMode` filter. `BindMode` is consulted only at store insert for socket opening (`binds.rs:898-921`) and in `is_wildcard()`. Upstream's own test `incoming_connect_tunnel_reenters_bind_flow` (`tests/tests/connect.rs:208`) re-enters a standard `0.0.0.0:18080` bind -- "put the credential listener on an internal bind" is not a boundary.
    - **No allowlist field exists at any layer.** The Rust type `frontend::Connect` carries only `mode` (`types/frontend.rs:229-233`); `schema/config.json` defines `Connect = {mode}` with `additionalProperties:false`; the Kubernetes CRD `agentgateway.dev_agentgatewaypolicies.yaml:6513-6528` is `connect={mode}` required, enum `Deny|Route|Tunnel`. `Deny` is the default when no connect policy is set (`httpproxy.rs:799`) and rejects with `MethodNotAllowed`.
    - **Mitigation 1 -- `ConnectMode::Route` makes routes the allowlist.** The three modes differ structurally, not cosmetically: `Tunnel` (`httpproxy.rs:801`; handled earlier at `gateway.rs:620-625`) binds re-entry by port with no route matching, so any bind in the Gateway is reachable; `Route` (`httpproxy.rs:805` falls through) subjects the CONNECT to full normal route matching -- listener hostname match, HTTPRoute rules, backend selection -- before reaching `connect_tunnel` (`httpproxy.rs:934-951`). `mode: Route` plus explicit routes constrains CONNECT targets without a second Gateway; `mode: Tunnel` does not.
    - **Mitigation 2 -- `networkAuthorization` (CEL) is enforced on the re-entered bind and is not forgeable.** `proxy_bind` re-resolves frontend policies for the re-entered bind's own port (`gateway.rs:430,437` -> `frontend_policies_for_bind` `gateway.rs:596-604`, keyed by `gateway_port_ref`, `lib.rs:701`), and both the HTTP path (`gateway.rs:897-911`) and the TCP path (`tcpproxy.rs:98-122`) enforce there. Crucially, `Socket::from_upgraded` (`transport/stream.rs:273-291`) preserves the outer connection's `TCPConnectionInfo.peer_addr` and `TLSConnectionInfo`, so on the re-entered bind `source.address` / `source.identity` are the real, untrusted client. `networkAuthorization` is in the Kubernetes CRD (line 6734, per-listener via `targetRefs.sectionName`); `networkExtAuthz` is standalone-config only (zero matches in the CRD). Upstream discourages relying on either as a substitute for process separation -- see #3.
    - **`source.connectHeaders` is client-supplied -- never use it as a trust signal.**

2. **NetworkPolicy cannot contain CONNECT re-entry inside one Gateway -- a client allowed only the CONNECT port can still reach every credential-bearing listener on that Gateway. The fix that works is two Gateways.** Measured end-to-end on kind v1.36.1 at v1.4.1 (re-entry is port-directed and in-process -- mechanism in #1). A one-Gateway composition (`connect:3000` HTTP Tunnel, `passthrough:443` TLS internal, and `llm`/`mcp:8443` HTTPS Terminate) programs fine -- all four listeners report `Accepted`/`Programmed`/`ResolvedRefs=True`, `Conflicted=False`, and the Service exposes only 3000 and 8443 (`agentgateway.dev/internal-ports` hides 443). But the security property is broken: a client blocked from a terminating listener's port by NetworkPolicy (`curl` exit 28) reached the same listener via `HTTPS_PROXY=:3000` + `CONNECT llm.example.com:8443` and received HTTP 401 from `api.openai.com` naming the injected dummy key, with the gateway's own access log showing the CONNECT client's real source address against the re-entered listener. **NetworkPolicy is an L3/L4 control and the re-entry never leaves the gateway pod.** Both `listener=llm` and `listener=mcp` showed this bypass. Target selection: `:443` reaches the SNI-matched passthrough TLSRoute; `llm.example.com:8443` reaches credential injection; `pypi.org:8443` reaches the terminating bind and fails only on SNI (`no TLS listener match for pypi.org`).
    - **Fix that works -- two Gateways** (CONNECT + passthrough on Gateway A, the credential-injecting listeners on Gateway B, same namespace): containment is fully restored. `CONNECT llm.example.com:8443` now receives `HTTP/1.1 404 Not Found` at the CONNECT stage (`curl` exit 7); direct `:8443` remains blocked (`curl` exit 28), while `pypi.org` CONNECT still returns 200. Also verified: `frontend.connect.mode=Tunnel` on Gateway A still accepts CONNECT and re-enters Gateway A's own internal `:443` bind (kept off the Service and off container ports via `agentgateway.dev/internal-ports: '443'`), and SNI survives the TLSRoute-to-Service hop between the two Gateways -- the terminating side serves the `llm.example.com` certificate and injects the OpenAI credential, as shown by the upstream 401 naming the dummy key.
    - **Silent misconfig at v1.4.1: `AgentgatewayBackend spec.dynamicForwardProxy` cannot be used from a `TLSRoute`/`TCPRoute`.** The data plane logs `error='invalid backend type'` at request time while the TLSRoute itself reports `Accepted=True`/`ResolvedRefs=True` -- the control-plane status gives no signal that the backend type is wrong. Fix: one `AgentgatewayBackend spec.static{host,port}` plus one `TLSRoute` per allowlisted hostname (verified `pypi.org` and `files.pythonhosted.org` return 200 with their real public certificates). Alternative: `connect mode=Route` + `HTTPRoute(hostnames)` + `dynamicForwardProxy` also works and refuses non-allowlisted targets at the CONNECT stage with 404 -- but it matches the CONNECT authority, not the SNI, which matters if the two can diverge (see #10 for the upstream change that affects this).
    - **Compensating control only, not containment:** an `AgentgatewayPolicy spec.traffic.authorization` `action: Require` with CEL `matchExpressions` targeting Gateway `sectionName: llm` returns 403 `authorization failed` for requests without a bearer header -- but it is an application-layer secret, and a client presenting the header is let straight through (verified by an upstream 401). It raises the bar; it does not close the boundary.
    - **Datapath mechanics worth keeping in mind:** the re-entered TLS connection is sniffed from the actual ClientHello -- SNI selects the TLS listener/route while the CONNECT hostname itself is discarded; passthrough rewinds the exact ClientHello (`Socket::new_rewind` + `start.io.rewind()`, `tcpproxy.rs:301-325`) so the second Gateway receives the original TLS/SNI with no re-origination. A missing internal bind is an HTTP 404 before the CONNECT would otherwise return 200. TLS-route `dynamicForwardProxy` dials the sniffed SNI at the original CONNECT port and applies no post-DNS private/link-local/metadata rejection -- there is no Gateway-to-Gateway Service special case and no L4 loop detection. Same-port differing protocols are marked `ListenerConflictProtocol`, but Gateway-owned listener status is **not** updated and stays misleadingly `Accepted=True, Programmed=True, Conflicted=False/NoConflicts` -- only ListenerSet status reports `ProtocolConflict` (#12 covers the wider pattern). Likely operational symptom of a missing companion Gateway's endpoints: CONNECT returns 200 followed by a TLS EOF/reset, while the TLSRoute may still read `ResolvedRefs=True`.

3. **Process separation is upstream's sanctioned answer for untrusted-vs-trusted CONNECT egress -- and the credential gateway's port choice turns a one-mistake failure into a two-mistake failure.** An agentgateway core maintainer, in the project's community chat (2026-08-17): *"I dont think its a bad idea to keep untrusted vs trusted entirely separated for general hygiene and safety. You could have some careful set of authorization rules but I think its probably unnecessary risk."* So the per-listener `networkAuthorization` CEL gate on `source.address` (#1) -- though technically real and non-forgeable -- is discouraged upstream as unnecessary risk, and a target-allowlist field for `frontend.connect` was requested and retired unfiled: separation is the intended mechanism, not a workaround for a missing field. **Port-choice corollary, which generalizes well beyond this project:** put the credential-injecting gateway on a port the untrusted gateway never binds (e.g. `8443`, not `443`). If the untrusted gateway binds `443` for CONNECT passthrough re-entry and the credential gateway also listens on `443`, a single mistake -- allowlisting the credential hostname in the untrusted gateway's TLSRoute -- makes the leak in #2 work again, because the untrusted gateway can dial the credential gateway on the port it already uses. With the credential gateway on a distinct port, the same mistake yields connection-refused instead. **General rule: when a structural boundary rests on "nothing is bound there," pick the port so the adjacent component's default port cannot accidentally satisfy it.**

4. **Kubernetes mode is thin relative to the Rust data plane, and a one-port-one-protocol constraint in the Kubernetes translator is what forces a multi-Gateway design -- evaluate the two layers separately, since conflating them overstates what is supported.** Source-verified at main `25664ff504d8a0752fd9635a1bcfe343011f750a` and v1.4.1.
    - **The data plane (Rust) is richly proven.** `crates/agentgateway/tests/tests/connect.rs` (1458 lines, 12 tokio tests) covers `ConnectMode::Tunnel` re-entry into a normal bind, into a `BindMode::Internal` bind (asserting a direct TCP connect to the inner port is refused), into a wildcard internal bind, `source.connectHeaders` -> CEL, outer-TLS-terminated CONNECT, `incoming_connect_dynamic_forward_proxy`, backendTLS on CONNECT, the authority-port requirement, and a full dynamic-CA MITM + RFC 8693 on-behalf-of + dynamic-backend chain. Provenance is maintainer work across agentgateway/agentgateway#2326, agentgateway/agentgateway#2380, agentgateway/agentgateway#2468, agentgateway/agentgateway#2731, agentgateway/agentgateway#2285, agentgateway/agentgateway#2308 and agentgateway/agentgateway#1943 -- genuine independent upstream precedent.
    - **Kubernetes mode is thin.** `translateFrontendConnect` handles `Tunnel` (`controller/pkg/agentgateway/plugins/frontend_policies.go:389`), and `gateway.rs:617-625` lets the frontend policy override the bind's `tunnel_protocol` so no bind-level `tunnelProtocol` is needed -- but all three golden testdata files (`plugins/testdata/frontendpolicy/connect*.yaml`) use `mode: Route`; zero golden test and zero controller e2e exercise `mode: Tunnel`. The only Kubernetes-mode Tunnel coverage is a CRD-validation unit test (`agentgateway_policy_types_test.go:83`), which also proves `frontend.*` connection fields must target via `targetRefs[].port` and that `sectionName` targeting is CRD-rejected. `controller/test/e2e` has 30 suites, none for connect/egress/tunnel.
    - **The one-port constraint is real and source-verified.** `validateListenerConflicts` (`controller/pkg/agentgateway/translator/gateway_collection.go:417-441`) does a raw string equality `p.protocol == listener.Protocol` per port -- there is no compatibility table -- so an HTTPS-terminate listener and a TLS-passthrough listener on the same port on one Gateway produce `ListenerConflictProtocol`. The pattern in `examples/<traffic-egress-proxy>/config-conditional.yaml` (two HTTPS listeners plus one wildcard `protocol: TLS` listener sharing port 443) is therefore inexpressible in Kubernetes mode; the only ways around it are two Gateway data planes, or standalone/`rawConfig` syntax. Also: backend-auth Secret references are same-namespace only, and `ReferenceGrant` cannot authorize cross-namespace credential Secrets.
    - **Docs and precedent gaps.** At the reviewed versions, `agentgateway.dev` has no Kubernetes egress/CONNECT/passthrough page; its only Kubernetes egress doc (`/docs/kubernetes/main/traffic-management/dfp/`) uses an HTTP listener + HTTPRoute + `Host` header -- a transparent proxy, not explicit CONNECT, no TLS. Upstream PR agentgateway/agentgateway#3014's example docs are standalone YAML with no Gateway/CRD manifests at all (#10). Gateway chaining (a `TLSRoute` `backendRef` pointing at another Gateway's own Service) has zero upstream precedent -- no example, manifest, design doc, issue, or discussion names it; it is an accident of composition, not a supported pattern. Upstream issue agentgateway/agentgateway#2416 (open at review, filed 2026-07-02) raises the same one-port constraint from the standalone-config side; the maintainer's only reply there proposes one internal bind on port 443 with two listeners -- the exact shape the Kubernetes controller forbids. Issue agentgateway/agentgateway#2229 (closed 2026-06-22) is the adjacent cross-Gateway same-port bind bug. Treat the constraint as an upstream-triage candidate; draft any issue for approval rather than filing automatically.
    - **API gaps found while verifying this design:** (1) `AgentgatewayModel` writes no status at all (`status: null`; the controller logs `enqueueStatus unknown external type *agentgateway.AgentgatewayModel`) -- a misconfigured Model gives zero signal, only the parent Gateway listener's `attachedRoutes` count hints it attached. (2) `AgentgatewayBackend spec.mcp` with a `static.backendRef` to a nonexistent Service goes `Accepted=False` for the whole backend, not just that target. (3) The chart-generated controller ClusterRole `agentgateway-agentgateway-system` holds `secrets create/delete/get/list/patch/watch` cluster-wide -- write access, broader than a read-only credential resolver needs. (4) Provider secrets are absent from the data-plane pod's mounted files and generated ConfigMap: there is no Secret volume, only `config-volume`/`xds-token`/`tmp`/`xds-ca`. They are delivered over xDS as documented. (5) The generated ServiceAccount has `automountServiceAccountToken=false`, and pods carry `gateway.networking.k8s.io/gateway-name=<gw>` as documented.

## Credential brokering (extAuthz / backendAuth)

5. **extAuthz credential brokering DOES apply through a CONNECT tunnel when the CONNECT re-enters a TLS-terminating listener on the same Gateway -- the intuitive "brokering does not survive CONNECT" claim is too strong.** Measured on v1.4.1: `CONNECT vendor.example.com:8444` via the `:3000` proxy re-entered the `:8444` HTTPS-Terminate listener, the gateway terminated the inner TLS, saw the plaintext request, called the token service, and rewrote the `authorization` header -- the upstream received the brokered credential and never the client's own token. It also fails closed on that path (403, upstream request count unchanged). **The "the broker does not apply through CONNECT" statement holds only for passthrough tunnels, where bytes are never decrypted** -- including `frontend.connect mode: route`, where the CONNECT request itself is route-matched (and does burn a token fetch) while the tunnelled inner request passes through untouched (verified: a plaintext inner request carrying the client's own bearer token arrived at the upstream unchanged). **Consequence: `NO_PROXY` for brokered hostnames is a routing preference, not a correctness requirement** -- and, read together with #1 and #2, a CONNECT client can reach a credential-injecting listener on the same Gateway, which is exactly why the two-Gateway split exists.

6. **The extAuthz credential-broker pattern works and fails closed, but two config gotchas decide the design, and one of them is a cross-tenant credential leak.** Verified locally on the v1.4.1 darwin-arm64 release binary (`git_revision 163ea214`), adapting `examples/traffic-token-exchange/extauthz/config.yaml` against a stub token service and a stub upstream.
    - **Proven.** (a) The client sends its own bearer token; the upstream receives a different, broker-issued token, and the client's original token appears in no upstream header -- a real credential broker, on a plain HTTP listener and on a TLS-terminating HTTPS listener (port 3443, HTTP/2). (b) Caching works: three identical requests produce exactly one <token-server> call, logged as `inserting CacheKey([String("Bearer CLIENT-TOKEN")]) into cache with TTL 59m54.862s` (test token). (c) A different inbound bearer produces a separate cache entry and a separate token call. (d) It fails closed both ways: a <token-server> 500 returns 500 to the client with the upstream hit count unchanged; a token server that is unreachable returns 403 `external authorization failed` with the upstream unchanged. Nothing is ever forwarded uncredentialed. `failure_mode` defaults to Deny.
    - **Gotcha 1 -- `cache.ttl` treats a bare int/uint/float as an absolute Unix epoch, not a relative duration.** An opaque token whose response carries only a relative `expires_in: 3600` needs the token server to also return an absolute `exp`, or the cache entry is silently not cached -- which presents as "caching is broken" rather than as a config error. The upstream example only works because its token is a JWT with an absolute `exp` claim. Traced to source in #8.
    - **Gotcha 2 -- a CEL parameter used in the token-request body but not in `cache.key` causes a cross-tenant credential leak.** Reproduced: the same bearer token with one tenant header, then with a different tenant header, returns the FIRST tenant's broker-issued credential to the SECOND tenant. Adding `request.headers['x-tenant']` to `cache.key` fixes it, producing a composite cache key per tenant. **One route can serve many tenants only if every CEL parameter feeding the token request is also included in `cache.key`.**
    - **Two more behaviours that matter:** only 401/403 extauthz direct responses are cached (`should_cache_http_direct_response`, line 1379), so a 500 from the token server is never cache-poisoned; but a non-2xx extauthz HTTP response is relayed to the client verbatim (status and body) rather than going through `failure_mode` -- so the token server's own error body leaks to callers.
    - **CONNECT scope and listener API.** The broker requires a listener where the gateway sees the real request: passthrough/`mode: route` tunnels do not broker inner requests, but TLS-terminating re-entry does (#5). Listener protocols are HTTP/HTTPS/TLS/TCP/HBONE; there is no proxy-listener type. Standalone `frontendPolicies.connect.mode` takes lowercase `deny|route|tunnel`, default `deny` -> 405. Plain forward-proxy absolute-form (`curl -x` with an `http://` target, no CONNECT) works fully.
    - **Capability inventory at main `25664ff5` (2026-08-14).** Generic extProc (Envoy gRPC external processing) and extAuthz (gRPC or arbitrary HTTP) are implemented in Rust and exposed by Kubernetes CRDs. Built-in `oauthTokenExchange` takes its subject from header/query/cookie/CEL (default `Authorization` Bearer), caches by SHA-256 of subject/type + actor/type + evaluated extra parameters, and uses `expires_in` (default 300 s) capped by the subject JWT `exp`. A missing subject is HTTP 400 before the cache. Endpoint/audience/scope are static; per-request CEL `additionalParams` cannot override reserved OAuth parameters. The `BackendAuthKind` inventory is in #7; Copilot is standalone-only. There is no runtime Wasm/Rust plugin loader; the Go plugin SDK is compile-time/controller-side.

7. **OSS credential brokering splits cleanly into what it has and what it lacks -- and the one finding that should change any broker design built on it: there is no universal `Authorization`-header scrub.** Verified at source (commit `34610af2`, 2026-08-07, plus the v1.4.1 audit).
    - **What OSS has -- request-time injection/exchange, fully.** `BackendAuthKind` (`crates/agentgateway/src/http/auth/mod.rs:74-111`) covers `passthrough | key | gcp | aws | azure | copilot | jwtSign | oauthTokenExchange` (RFC 8693 plus RFC 7523 jwt-bearer/client-assertion and an Entra-style on-behalf-of flow via generic `additionalParams`) and `crossAppAccess` (Okta ID-JAG, two-leg). Copilot is standalone-only (#6). Secrets are `FileOrInline` via `deser_key_from_file`, with `ser_redact` on serialization, so a mounted Kubernetes Secret works and values stay out of config dumps. Kubernetes credentials may be inline in the CRD or same-namespace core Secret references; the controller resolves `Secret.Data` to plaintext strings delivered over xDS -- the built-in resolver is Secret-only, with no KEK/DEK/KMS envelope implementation in OSS.
    - **Configuring `backendAuth` does NOT remove the caller's own credential.** It is replaced only when the injected credential targets the same header the caller used. Inject into a query parameter, a cookie, or a different header, or run a permissive JWT policy that fails to actually validate, or use the extra `credentials[]` list -- and the caller's own token survives to the upstream, leaking the caller's identity into third-party audit logs. Only `oauthTokenExchange` removes subject and actor locations itself (`oauth/mod.rs:385-399`). **For a broker design this means you must add strict ingress auth-with-removal, or a route-level header-removal step ordered before backend auth.**
    - **What OSS lacks:** any persistent token store keyed by (user subject, resource); browser-based egress-consent elicitation; and `refresh_token` parsing at all (`transport.rs:71-81`). The OAuth exchange cache is `InMemoryTokenCache`, per-replica and keyed by SHA-256 of the subject token rather than by user `sub` (`oauth/cache.rs:13-120`) -- so it is lost on restart and unshared across replicas, at the cost of one extra token-endpoint call, nothing worse. MCP elicitation handling only relays modern MCP `input_required`/elicitation messages -- it does not generate egress OAuth URLs, capture consent callbacks, or store third-party tokens.
    - **Fit for autonomous agents (no human in the loop, one credential scope per tenant):** the static credential kinds (`key`/`gcp`/`aws`/`azure`/`jwtSign`) all work unattended. `oauthTokenExchange` and `crossAppAccess` need a subject token on every call and fail immediately without one (`oauth/mod.rs:349-355`). Elicitation and MCP OAuth client authorization do not work unattended -- they need a browser-capable human, and even when a human is present the credential still ends up with the client, which is why browser-consent-based brokering patterns described in public agent-identity writing do not transfer to a fully autonomous, no-human sandbox regardless of OSS-vs-commercial tier.
    - **Multi-tenancy caution:** a shared gateway using ambient cloud identity gives every tenant the SAME authority; cloud session tags (e.g. AWS AssumeRole session tags in CloudTrail) give audit-log attribution, not authorization isolation.
    - **A commercial tier reportedly adds envelope encryption (KEK/DEK, a KMS master key, a separate unwrap-authorizing broker) plus a persistent credential lifecycle -- UNVERIFIED from the public side; treat any OSS-vs-commercial comparison here as unverified rather than confirmed.**

## CRDs, config and install

8. **The Kubernetes-mode `AgentgatewayPolicy` CRD shape differs substantially from the standalone/config-file shape most design docs are written against -- and its `ttl` field has a silent bare-number-is-an-epoch trap.** Real v1.4.1 CRD: `spec.traffic.extAuth` (not `policies.extAuthz`); `backendRef{group,kind,name,namespace,port}` (not a `host: svc:port` string); `http.{path,body,responseMetadata}` (not `protocol.http.metadata`); `spec.traffic.transformation` is singular (not `transformations`); `transformation.request.set` is a list of `{name,value}` (not a map); `failureMode` enum is `FailClosed|FailOpen`, default `FailClosed`. A cache with a CEL TTL expression like `ttl: 'extauthz.expires - 5'` is verified working (two identical requests produce one token mint).
    - **The `ttl` trap, source-verified identical at v1.4.1 and HEAD.** The cache-TTL resolver matches `Duration`-typed values as relative and `Timestamp`-typed values by subtracting now from the timestamp, but `Int/UInt/Float` values are treated as an absolute Unix epoch, computing `expires_at - now_epoch_seconds`. A bare numeric string like `'300'` is not parsed as a duration (the duration parser requires a unit suffix and errors on a unitless string), so it falls through as a raw integer, produces a negative epoch-delta, and the cache insert is silently skipped with only a warn-level log. There is no CRD-level rejection: `ttl` is typed as a plain string with no pattern, and the CRD's own field description mentions duration-string, CEL-duration and timestamp forms but never the bare-number epoch arm -- the documentation is misleading by omission and the source is the only reliable reference. This is the caching failure in #6. Note also that `failureMode` defaults to `Deny` in code via an explicit default attribute; the CRD states `FailClosed` only in prose with no OpenAPI `default:` key, and the CRD does not expose the underlying Rust `DenyWithStatus(u16)` variant.
    - **Source trace.** `cache_ttl` (`http/ext_authz.rs:703-717`) matches `Value::Duration`, `Value::Timestamp` (`signed_duration_since(now)`), and `Value::Int/UInt/Float`; numeric values call `unix_epoch_ttl` (`ext_authz.rs:1387-1396` at HEAD `25664ff5`, `1364-1373` at v1.4.1). For `ttl: '300'`, `de_duration_or_expression` (`cel/helpers.rs:13-26`) calls `durfmt::parse` (`core/src/durfmt.rs:15-23` -> `go-parse-duration 0.1.1`, pinned in `Cargo.lock:3027-3030`), which returns `Err("missing unit in duration")`. The value is not wrapped as `duration("300")`: it remains a CEL int -> `unix_epoch_ttl(300)` -> `300 - 1.7e9` -> negative -> `Duration::try_from_secs_f64` fails -> `None`; `insert_cache` (`ext_authz.rs:673-679`) skips caching with a Warn log. `failureMode` defaults to `Deny` via `#[default]` at `ext_authz.rs:78-89`.

9. **Two v1.4.1 install/integration gotchas both present as someone else's fault.** (a) CRDs ship in `oci://ghcr.io/agentgateway/charts/agentgateway-crds:1.4.1`; the main `agentgateway` chart has no `crds/` directory. Without the CRD chart the controller CrashLoops on the `9093/readyz` startup probe with `waiting for sync... informer/AgentgatewayModels`, and nothing in the crash output points at the missing chart -- the fix is installing the CRD chart, not debugging the controller. (b) The extAuthz HTTP callout is sent as `method=GET` with a body -- a token service that only implements `POST /token` silently 404s, and agentgateway relays that 404 verbatim to the client while the token service's own hit counter stays at zero. That combination reads as "the gateway never called the broker" rather than "the broker responded with an error," and caused ~40 minutes of misdiagnosis in the reproduction.

10. **Version-scope every CONNECT/TCP-proxy finding against upstream pull requests agentgateway/agentgateway#3013 and agentgateway/agentgateway#3014 -- a release even a few weeks old can predate a real behaviour change, and agentgateway/agentgateway#3013's dynamic-backend fix turns out to be reachable from the Kubernetes TLSRoute path even though the upstream example's own README implies otherwise.** v1.4.1 (chart 1.4.1, `git_revision 163ea214`, published 2026-07-29) predates both pull requests (merged 2026-08-14) by roughly 160 commits; check ancestry with `gh api repos/<org>/<repo>/compare/<prMergeSha>...<testedSha> --jq .status` before repeating any finding from a nearby version.
    - **The v1.4.1 rejection** (the `invalid backend type` error in #2) came from `TryFrom<Backend> for SimpleBackend` rejecting `Backend::Dynamic` (`types/agent.rs:1415-1427`, unchanged at HEAD). `resolve_simple_backend` (`proxy/mod.rs:598`) surfaces `ProxyError::InvalidBackendType` (`proxy/mod.rs:178-179`). The converter still rejects this variant; the TCP path changes below bypass it.
    - **agentgateway/agentgateway#3013 bypassed the narrower backend type entirely rather than extending it**, retyping `TCPRoute.backend` from `SimpleBackendReference` to `BackendReference`, switching `resolve_simple_backend` to `resolve_backend` at `tcpproxy.rs:463`, and adding the `Backend::Dynamic` arm at `tcpproxy.rs:252-272`. Kubernetes reachability is proven by `agent_xds.rs:1519` switching `resolve_simple_reference` to `resolve_reference`; the controller emits `api.Backend_Dynamic` for `AgentgatewayBackend.spec.dynamicForwardProxy` (`controller/pkg/syncer/backend/backend_plugin.go:183-190`), and TLSRoute `backendRefs` use the same `buildAgwDestination` (`translator/conversion.go:308-336`). Dynamic TCP needs a destination hostname, which TLSRoute passthrough supplies through sniffed SNI (`tcpproxy.rs:141-144,191` -> `DestinationContext.hostname` -> `tcpproxy.rs:264-269`). The original rejection survives only for backend-tunnel / LLM / mirror / policy-call / MCP paths, which still go through the narrower backend type.
    - **agentgateway/agentgateway#3014 is a security-relevant read even though it is "just an example."** It adds `examples/<traffic-egress-proxy>/` (`README.md`, `config.yaml`, `config-conditional.yaml`, `config-dynamic-tls.yaml`) documenting CONNECT-proxy egress as a security use case ("control which HTTPS destinations clients can reach") -- as standalone YAML only, with no Gateway/CRD manifests and no controller changes -- and `config-conditional.yaml` co-locates an `OPENAI_API_KEY`-bearing LLM listener with a public passthrough allowlist on the same Gateway port 443. PR agentgateway/agentgateway#3013 itself is Rust-only (`tcpproxy.rs +128/-30`). That is, upstream's own example ships the exact single-Gateway pattern that leaks credentials to untrusted CONNECT clients (#1, #2). **Read example configs from any project as illustrations of syntax, not as vetted security architecture.**

## Labels, xDS and status

11. **`app.kubernetes.io/name=agentgateway` selects the CONTROLLER pods only -- a NetworkPolicy or podSelector written against it, expecting to match the data-plane gateway proxies, silently selects nothing.** Two separate Helm charts are involved: the controller chart at `controller/install/helm/agentgateway/` sets `app.kubernetes.io/name={{Chart.Name}}=agentgateway` via `agentgateway.selectorLabels` (`_helpers.tpl:51-55`) on the controller Deployment (`deployment.yaml:6,31`); data-plane proxies come from the separate `go:embed` chart at `controller/pkg/helm/agentgateway/` (`embed.go:8-9`), rendered per-Gateway by `pkg/deployer/deployer.go:62,90,173`, whose `kgateway.gateway.selectorLabels` (`_helpers.tpl:35-39`) sets `app.kubernetes.io/name=<the Gateway resource's own name>` plus `gateway.networking.k8s.io/gateway-name=<gateway name>`. **Use `gateway.networking.k8s.io/gateway-name` to select data-plane pods.** Controller pods also carry a distinct `agentgateway=agentgateway` label; there is no `app: agentgateway-controller` label anywhere, and the controller's namespace is installer-chosen, not intrinsic to the chart. The controller's xDS endpoint listens on a dedicated TCP port (`9978` in the default chart values) at `XDS_ADDRESS=https://agentgateway.<ns>.svc.cluster.local:9978`, configurable via `controller.service.ports.agwGrpc` (`controller/install/helm/agentgateway/values.yaml:84`). The value feeds container port `grpc-xds-agw` (`deployment.yaml:65-67`), env `AGW_AGENTGATEWAY_XDS_SERVICE_PORT` (`deployment.yaml:115`), and the Service port (`service.yaml:74-77`); it is not hardcoded in templates and has no Rust default under `crates/`.

12. **v1.4.1 status fields lie about at least two classes of failure -- `Programmed=True` / `ResolvedRefs=True` is a liveness hint, never proof the data plane actually has your config.** Two measured instances of the same silent-failure class (a third is the `ListenerConflictProtocol` reporting gap in #2, and a fourth is the Model CRD that writes no status at all, in #4).
    - **Cross-namespace `backendRef` apply-order race.** The controller logged `erroring building agent gateway destination ... RefNotPermitted: backendRef <backend-namespace>/<service> not accessible to a HTTPRoute in namespace <route-namespace> (missing a ReferenceGrant?)` while the HTTPRoute simultaneously reported `ResolvedRefs=True`. Root cause was an apply-order race -- the route and the ReferenceGrant applied in the same batch -- and the grant works on retranslation, but the controller never retried and never surfaced the transient error in status. **Apply `ReferenceGrant` objects before the routes that depend on them, not in the same batch.**
    - **Blocking a data-plane pod's xDS connection with a NetworkPolicy is an invisible failure, not an outage.** Measured: the Gateway and all its listeners stay `Programmed=True`/`Accepted=True`, existing traffic keeps serving from in-memory config, and newly pushed routes report `Accepted=True`/`ResolvedRefs=True` in the API while the data plane never actually receives them (`curl` exit 35, "route not found"). The xDS socket on TCP 9978 stays in `SYN-SENT` with `upstream call failed: Connect: deadline has elapsed`. The failure **only bites on an xDS reconnect** (e.g. a controller restart) -- a data-plane pod that starts up while the network policy is already in place often wins a startup race against the CNI programming its rules (~35 ms), gets a working xDS stream, and conntrack keeps that connection alive indefinitely. So a NetworkPolicy change touching the xDS port can look completely clean for days and then detonate on the next controller rollout.

## Alternatives considered

13. **`paradigmxyz/iron-proxy` v0.49.0 has dial-time CIDR rejection, but its deny-only guard cannot express "block all private destinations except one in-cluster gateway."** Source-verified at `c8724937fbe109b7fbc6ddb21490e15902b187c0` (2026-08-13). The design needs external NetworkPolicy/DNS/port controls or code changes. Related constraints: no `IP_TRANSPARENT` in the Go code, shared-proxy-IP DNS, and process-wide TLS mode.
    - **Post-DNS rejection.** `net.Dialer.Control` rejects CIDRs at dial time, but the defaults cover only exact IPv4/IPv6 IMDS addresses and loopback. RFC1918, the whole IPv4 link-local range, and pod/service CIDRs must be configured explicitly; a configured list replaces rather than extends the defaults. DNS can be disabled. `sni-only` performs opaque TLS passthrough, allowlisting the CONNECT authority before the 200 and the inner SNI separately before dialling fixed port 443.
    - **Matching limitations.** The tunnel listener also accepts SOCKS5 and absolute/plain HTTP; it is not CONNECT-only. Domain matching strips all ports, is case-sensitive, and performs no trailing-dot or IDNA normalization. Go 1.26 rejects raw and percent-encoded NUL. At review, upstream PR paradigmxyz/iron-proxy#229 addresses case matching; issues paradigmxyz/iron-proxy#222 and paradigmxyz/iron-proxy#230 address tunnel denial behaviour.
    - **Routing limitation.** There is no generic hostname-to-upstream map for `sni-only`: `dns.records` serves only intercepted client DNS, and `mcp_gateway` routing needs parsed/MITM HTTP. Private DNS, a hosts file, or a routing shim is required. The deny-only CIDR guard cannot allow one in-cluster agentgateway while blocking every other private destination, so an untrusted-client design with that requirement needs the external controls above.
    - **Operational notes.** Static standalone `sni-only` is stateless across replicas in steady state, but reloads and rolling policy updates can diverge per instance. Project maturity at review: created 2026-04-01, 178 commits / 6 human contributors, 146 commits by one maintainer. `SECURITY.md` offers private email plus PGP.
