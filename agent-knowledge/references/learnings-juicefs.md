# JuiceFS Learnings

JuiceFS CE and CSI driver cache sizing, eviction, metrics, and mount-option behaviour; CE v1.3.1 and CSI v0.31.4 unless stated.

See also: `learnings-gke.md`, `learnings-terraform.md`, `learnings-observability.md`, `learnings-workload-debug.md`.

Numbered, append-only. **Update the existing entry — never duplicate.**

## Block cache, node disk and eviction

1. **The mount pod's block cache is a per-NODE `hostPath`, and its two defaults are set exactly where the kubelet evicts — so the default configuration fills the disk to the eviction line by design.** At **CE v1.3.1** an un-tuned mount (no `mountOptions` on the PV) runs `cache-dir=/var/jfsCache` on the node boot disk with **`cache-size=100G`** and **`free-space-ratio=0.1`**. `free-space-ratio 0.1` means "stop when 10 % of the filesystem is free" — which is numerically **the same line as a typical kubelet `eviction-hard: nodefs.available<10%`**. The cache therefore grows until it *is* the eviction trigger, and because `hostPath` bytes are charged to no pod, the evicted workload's own ephemeral usage can be a few MiB. **The fix is mount options, never the evicted pod's ephemeral limits** — set `cache-size` well under disk headroom and `free-space-ratio` **above** the kubelet threshold (e.g. `cache-size=10240,free-space-ratio=0.25`). The generic mechanism and the per-node attribution proof are `learnings-gke.md`.

2. **The cache trims to 95 % of `cache-size`, not to 100 %, so the steady-state plateau is below the number you set.** `cleanupFull` targets 95 % of the configured size (`pkg/chunk/disk_cache.go:791` @ v1.3.1): with `cache-size=10240` expect a plateau around **9.5 GiB**, not 10. Size alerts and dashboard threshold lines should be drawn against the plateau, not the nominal cap. Related metric trap: **`blockcache_drops` means the WRITE QUEUE was full (slow disk), not that the cache ran out of space** — do not read it as an eviction/capacity signal.

3. **There is ONE mount pod per node, not one per workload pod — so cache sizing is a per-node budget and the cache survives the pods that filled it.** Any "give each sandbox its own cache" reasoning is wrong by construction, and a cache-size change does not take effect for pods already bound to an existing mount pod (see #5).

## Metrics — what you can and cannot chart

4. **The `fuse_ops` / `meta_ops` / `transaction` duration histograms are UNLABELED at v1.3.1, so per-operation latency breakdown is impossible — only fleet/pool averages are.** They are constructed with plain `prometheus.NewHistogram` (`pkg/vfs/accesslog.go:31-32`, `pkg/meta/base.go:320-333`), i.e. **no `method` label**, yielding exactly one `_sum` + one `_count` per mount pod per family. The one exception is **`object_request_durations_histogram_seconds`, which DOES carry `method` × `storage_class`** (`pkg/chunk/cached_store.go:904`; observed `GET`/`PUT` with `STANDARD`, `DELETE` with an empty class) — and it is only emitted **after the first request**, so its absence on a quiet mount is not a scrape failure. Consequence for a scrape-enablement proposal: do not promise "per-op latency" from these histograms; promise aggregate latency plus per-op only on object storage. Budget ~6-12 `_sum`/`_count` series per mount pod against ~92-170 bucket series, so **scraping `_sum`/`_count` only is roughly an order of magnitude cheaper** than scraping buckets.

## PersistentVolume `mountOptions` — the Terraform/CSI contract

5. **Changing a PV's `mountOptions` is an IN-PLACE update, not a replace — and it rolls the mount pods lazily, not at apply time.** Three layers each had to be checked, and all three agree: **(a) Terraform** `hashicorp/kubernetes` **2.38.0** — `mount_options` has no `ForceNew` (`resource_kubernetes_persistent_volume_v1.go:185-191`) and `CustomizeDiff` force-news only `spec.0.persistent_volume_source.*` (`:65-76`); the update is a JSON-patch `replace /spec/mountOptions` (`structure_persistent_volume_spec.go:1282-1287`), which succeeds even when the key is **absent** because json-patch v4.13.0's `partialDoc.get` never errors (`patch.go:393`) — confirmed with a server-side dry-run against a live PV, resourceVersion unchanged. **(b) kube-apiserver** — `ValidatePersistentVolumeUpdate` locks only `persistentVolumeSource` and `volumeMode` (k8s 1.35 `validation.go:2271-2303`), so `mountOptions` is mutable. **(c) the CSI driver** — JuiceFS CSI **v0.31.4** reads PV `mountOptions` only at `NodePublish`, via the volume capability's `MountFlags` (`node.go:211-214`), and feeds them into `GenHashOfSetting` (`setting.go:1245`); a changed hash means **a NEW mount pod per node for NEW sandboxes** (`pod_mount.go:408` skips reuse on hash mismatch) while **existing mount pods and the pods using them are untouched and keep the OLD cache limits until they drain.** So the rollout is gradual and there is no disruptive remount — plan the soak accordingly.

6. **An empty `mount_options = []` is indistinguishable from an absent one in the provider, which is what makes a default-empty, per-environment variable safe to ship everywhere at once.** `mount_options` is a `TypeSet`: `expand` skips an empty set (`structure_persistent_volume_spec.go:1001`) and `flatten` writes only when non-nil (`:377`), so `[]` and absent **never diff**. A `variable "juicefs_mount_options" { default = [] }` therefore renders a zero-diff plan in every environment that does not set it — verified on real plans — so the enablement can be one config line per environment on its own schedule.

7. **The chart's `mountPodPatch` is a second, equal-footing source of mount options, and it OVERRIDES the PV's.** Patch keys win over PV keys (`setting.go:1186-1204`), the global config is hot-reloaded via fsnotify (`config.go:501`), and it selects by **`pvcSelector` only — there is no `pvSelector`**. It produces the same `GenHashOfSetting` roll as #5. Check for it before concluding that a PV edit is the only way options reach a mount, or before concluding that a PV edit took effect.

## PersistentVolume `mountOptions`: the Terraform/CSI contract

8. **The CSI driver hashes the metadata URL into its mount-pod identity, so changing it (e.g. adding a password) rolls mount pods LAZILY: old pods keep the old connection until every workload using them is gone.** Verified at JuiceFS CSI v0.31.4: the `metaurl` from the node-publish secret is serialized into `GenHashOfSetting` (`setting.go:57` `json:metaurl`, `:1245-1300`), so a new `NodePublish` creates a mount pod under a **new** hash while existing mount pods continue running with the previous, passwordless connection. ⚠️ **Consequence for a credential rollout:** enabling authentication on the metadata store while old mount pods are still running cuts them off (or, if the old credential is still accepted, hides the fact that they were never migrated). ✅ Drain or recycle **every** pre-change mount pod before the auth change, including the ones backing pre-warmed/pooled workloads, which are easy to miss because nothing is actively using them. ✅ Also check the secret-sync refresh interval: a managed secret store refreshing hourly means the new credential can be up to an hour behind the change.

9. **Mount pods LOG whether the metadata URL carried a password, which makes a fleet-wide auth audit possible without cluster API access.** At `v1.3.1` the client prints `Meta address: <uri>` at startup through its password-removing helper (`pkg/meta/interface.go:578`, `pkg/utils/utils.go:114-128`), so the line reads `rediss://:****@host` **with** a credential and `rediss://host` **without**, a clean two-state signal. Where the cluster ships node logs to a hosted log service, each mount pod has its own stream and the whole fleet can be audited by filtering that phrase, with **no** access to a private control-plane endpoint. ✅ **Observe BOTH polarities as a positive control** before trusting the audit. ⚠️ **The gate is the SECRET-SYNC refresh, not the secret change.** With an hourly refresh interval, mount pods created between the secret update and the next sync still log no credential, so the correct precondition for enforcing auth is *no live mount pod predates the first sync AFTER the change*, which is up to an interval later than people assume. ⚠️ **The server cannot answer this for you:** a Redis 7.2 client list has no auth field (`networking.c:2842`), and authenticated and passwordless connections both report the default user, use connection AGE against the credential-distribution time instead. Complements #8 (the mount pods roll lazily, which is exactly why old ones are still logging).

10. **Sandbox pods that mount the JuiceFS PVC do so with NO `mountPropagation`, so deleting a MOUNT POD breaks every running sandbox bound to it: recycle the SANDBOX pods, never the mount pods.** This inverts the instinct when rotating a credential or rolling the CSI layer: the mount pod looks like the disposable infrastructure component and is the one thing that must survive. ✅ Sequence a credential change as "drain/recycle the consumers, then roll the mounts", and treat any runbook step that restarts mount pods under load as a data-path outage. 🔎 Mount-time measurement for these pods: `learnings-observability.md`#251` (the kubelet volume-operation metric, since the pod-start SLI excludes PVC pods entirely).

11. **JuiceFS metadata is append-only in practice when nothing deletes workspace data, so the Redis keyspace grows monotonically and `keyspace_keys` is the leading indicator.** Audited one deployment end to end: the application's delete path only sets a storage row to DISABLED in Postgres, and the garbage-collection scripts and reaping CronJob contain ZERO JuiceFS references, so the per-workspace directory on the shared volume is never removed. Memory tracks file count at a near-constant rate per key (about 224 B/key on one environment, 238 B/key on another), which is what makes the key count, not the byte count, the metric to forecast against. **Check for this explicitly before sizing a JuiceFS metadata store: "we delete workspaces" in the product sense does not imply any filesystem deletion.**

12. **A JuiceFS PV's `mountOptions` come back from a Terraform-provider-created object in a DIFFERENT ORDER than the input, because the provider stores them as a set.** Measured: the live order was the reverse of the tfvars order on all three clusters. A chart that renders the tfvars order is therefore a PV spec write (`kubectl diff` shows the list reorder) and can roll mount pods lazily through the settings hash. Render the LIVE order when adopting, not the configured one.

13. **JuiceFS CE v1.3.0 Redis metadata cost per object, read from source, plus the two knobs that do NOT reclaim memory.** At tag `30190ca`: an inode attribute payload is **72 bytes** (80 when ACL IDs are present); each dentry HASH value is **9 bytes plus the filename**; each POPULATED fixed 64 MiB chunk is one LIST key with **24 bytes per slice**. Unshared slices use an IMPLICIT refcount of 1, so they are not individual Redis keys. ⚠️ **Compaction reduces LIST payload, not the live inode or chunk KEY COUNT**, and with trash enabled it retains 12-byte old-slice references in a shared delete-slices HASH until expiry. ⚠️ **Disabling directory stats is NOT a memory reclamation knob:** `doInit` deletes no existing stats on disable, and `doMknod` still writes three per-directory fields. ⚠️ **Whole-volume `gc` is dangerous at scale:** `ListSlices` builds a map of EVERY reachable inode and a map of all slices, so on 100M-plus inodes it risks substantial client memory and metadata scan load. Sources: `pkg/meta/{interface.go Attr.Marshal, redis.go key helpers/doMknod/doCompactChunk/doInit, slice.go marshalSlice, base.go compactChunk}`. ✅ Exact total bytes per inode require MEASURED encoding, key and allocator overhead, not serialized-size arithmetic: report the measured ratio (Redis counter over inode count) instead of deriving one.

14. **A JuiceFS CE v1.3.0 bulk delete does NOT release metadata when you run it, and `trash-days=1` does not mean 24 hours: plan a purge as sustained load, not as a step change.** The SDK's `jfs_rmr` passes `skipTrash=false`, and `Remove`/`emptyDir` WALKS EVERY ENTRY in 10k scan batches rather than moving a tree once. Redis `doUnlink`/`doRmdir` move each inode into HOURLY trash buckets, RETAIN inode and chunk metadata, remove the source dentries, and clear the deleted directory's stats and quota fields. Cleanup runs hourly with jitter, gates globally at 54 minutes, and processes up to 1M entries per read with a 50-minute pass budget; **`TrashDays=1` selects buckets older than now minus 26 hours**, so actual item age depends on the hour bucket and on scheduling. Expiry removes inode, xattr and symlink metadata and queues deleted files; chunk deletion uses 100 in-flight file workers, up to 1000 chunk length commands per pipeline, and a bounded in-process slice queue. **There is no operations-per-second limiter**, so an 18M-entry purge is sustained per-entry transaction load plus later expiry load. ✅ **Stage the deletion and monitor, rather than expecting prompt capacity relief.** ✅ **For a METADATA-ONLY job** (counting or marking, not deleting data) use `no_bgjob=True, max_deletes=0` and verify that a DIFFERENT background-enabled mount purges expired trash, since `no_bgjob` disables periodic cleanup and backup while `NewSession` still starts slice-deletion workers, and a `trash-days=0` unlink CAN trigger object deletion. Sources: `pkg/meta/{utils,base,redis}.go`, `sdk/java/libjfs/main.go:508,544,614,946`, `pkg/meta/base.go:544,2438,2505`.

15. **JuiceFS CE v1.3.0 directory quotas are cheap in Redis KEYS and expensive in REFRESH traffic, which is what decides whether thousands of them are viable.** Exactly 3 shared hashes (`dirQuota`, `dirQuotaUsedSpace`, `dirQuotaUsedInodes`) with 3 fields per quota, and limits packed into 16 bytes. ⚠️ **But every client reload scans ALL quotas and then performs 2 SEQUENTIAL `HGET`s per quota on each heartbeat** (default 12 seconds with 5 percent jitter), with quota deltas flushed every 3 seconds. **There is no global reservation**, so concurrent clients can OVERSHOOT a quota, and a long refresh duration weakens enforcement further. ✅ **Stage any fleet-wide quota rollout and measure refresh duration before scaling it**, rather than reasoning from the key count. API note: the Python `Client.set_quota` capacity is in BYTES while the CLI takes GiB; a zero dimension leaves the old limit unchanged and both zero is an error. Sources: `pkg/meta/quota.go loadQuotas/flushQuotas/checkQuota`, `redis.go doLoadQuotas/doSetQuota`, `base.go refresh`, `pkg/fs/fs.go HandleQuota`.

16. **Migrating JuiceFS metadata off Redis is a QUIESCENCE problem, not a capacity one, which is why a bigger instance is usually the right stopgap.** v1.3.0 source: PostgreSQL (`pkg/meta/sql_pg.go init`) and TiKV (`pkg/meta/tkv_tikv.go init`) ARE built into the Python distribution, because the build produces the shared library without exclusion tags, and cross-engine dump and load is supported including the binary format. ⚠️ **But Redis `dumpMix` explicitly warns the source must be READ-ONLY, and the load command warns never to run the old and new engines simultaneously.** On a shared filesystem with a hundred million inodes that means quiescing every consumer, rehearsing a full dump and load, and remounting them all; changing the CSI secret rolls LAZILY rather than cutting over atomically. ⚠️ Redis CLUSTER sharding is not the alternative it appears to be: `redis.go newRedisMeta` puts a volume in ONE hash slot. ✅ So the honest options are a larger single instance as a capacity stopgap, or a planned outage: say which, rather than presenting migration as a rolling change.

17. **The JuiceFS v1.3.0 Python SDK requires the process UID to EXIST in `/etc/passwd` and grants superuser semantics ONLY when that user's name is root, so a hardened non-root cleanup job cannot work.** `Client.__init__` calls `pwd.getpwuid(geteuid())` and `getgrouplist`, so a pod running as a UID with no passwd entry (which is the common distroless or slim-image case) raises `KeyError` BEFORE any JuiceFS call. And permission checks are bypassed only when that user's name equals the name of UID 0 (`sdk/java/libjfs/main.go` `isSuperuser`/`getOrCreate`); **there is no superuser keyword argument in the Python wrapper.** Since sandbox-written files are typically root-owned, a garbage-collection or cleanup job must run its JuiceFS container as **UID 0 with capabilities dropped and privilege escalation disabled**, which is the defensible shape; a non-root UID fails at import on a slim image and would hit permission errors on recursive delete anyway. ⚠️ Related blind spot: local make targets that run the SDK under `sudo` mean non-root permissions on those directories have never actually been exercised. Check both before planning a non-root SDK job.

18. **A Terraform-managed PersistentVolume's `mount_options` arrive in an order determined by a CRC32 HASH of each string, not input order, which explains an apparently reversed live order and refutes it as a diff. Corrects the observation in `#12`.** terraform-provider-kubernetes v2.38.0 declares `spec.mount_options` as a `TypeSet` with `Set: schema.HashString` (`resource_kubernetes_persistent_volume_v1.go:185-191`) and expands it via `schemaSetToStringArray(set)`, so the API receives the SDK set's `List()` order: elements sorted by the DECIMAL STRING of `crc32(value)`. ✅ **Predict the live order offline:** `sorted(opts, key=lambda s: str(zlib.crc32(s.encode())))`. For one real pair this puts the second input first, because its CRC's decimal string sorts lower as TEXT. **Consequence: a live PV whose options look reversed relative to a chart's list may be byte-equal to the chart default**, so compare option SETS, never sequences, in a parity check.
