# JuiceFS Learnings

JuiceFS CE and CSI driver cache sizing, eviction, metrics, and mount-option behaviour; CE v1.3.1 and CSI v0.31.4 unless stated.

See also: `learnings-gke.md`, `learnings-terraform.md`, `learnings-observability.md`, `learnings-workload-debug.md`.

## Block cache, node disk and eviction

1. **The mount pod's block cache is a per-NODE `hostPath`, and its two defaults are set exactly where the kubelet evicts — so the default configuration fills the disk to the eviction line by design.** At **CE v1.3.1** an un-tuned mount (no `mountOptions` on the PV) runs `cache-dir=/var/jfsCache` on the node boot disk with **`cache-size=100G`** and **`free-space-ratio=0.1`**. `free-space-ratio 0.1` means "stop when 10 % of the filesystem is free" — which is numerically **the same line as a typical kubelet `eviction-hard: nodefs.available<10%`**. The cache therefore grows until it *is* the eviction trigger, and because `hostPath` bytes are charged to no pod, the evicted workload's own ephemeral usage can be a few MiB. **The fix is mount options, never the evicted pod's ephemeral limits** — set `cache-size` well under disk headroom and `free-space-ratio` **above** the kubelet threshold (e.g. `cache-size=10240,free-space-ratio=0.25`). The generic mechanism and the per-node attribution proof are `learnings-gke.md`.

2. **The cache trims to 95 % of `cache-size`, not to 100 %, so the steady-state plateau is below the number you set.** `cleanupFull` targets 95 % of the configured size (`pkg/chunk/disk_cache.go:791` @ v1.3.1): with `cache-size=10240` expect a plateau around **9.5 GiB**, not 10. Size alerts and dashboard threshold lines should be drawn against the plateau, not the nominal cap. Related metric trap: **`blockcache_drops` means the WRITE QUEUE was full (slow disk), not that the cache ran out of space** — do not read it as an eviction/capacity signal.

3. **There is ONE mount pod per node, not one per workload pod — so cache sizing is a per-node budget and the cache survives the pods that filled it.** Any "give each sandbox its own cache" reasoning is wrong by construction, and a cache-size change does not take effect for pods already bound to an existing mount pod (see #5).

## Metrics — what you can and cannot chart

4. **The `fuse_ops` / `meta_ops` / `transaction` duration histograms are UNLABELED at v1.3.1, so per-operation latency breakdown is impossible — only fleet/pool averages are.** They are constructed with plain `prometheus.NewHistogram` (`pkg/vfs/accesslog.go:31-32`, `pkg/meta/base.go:320-333`), i.e. **no `method` label**, yielding exactly one `_sum` + one `_count` per mount pod per family. The one exception is **`object_request_durations_histogram_seconds`, which DOES carry `method` × `storage_class`** (`pkg/chunk/cached_store.go:904`; observed `GET`/`PUT` with `STANDARD`, `DELETE` with an empty class) — and it is only emitted **after the first request**, so its absence on a quiet mount is not a scrape failure. Consequence for a scrape-enablement proposal: do not promise "per-op latency" from these histograms; promise aggregate latency plus per-op only on object storage. Budget ~6-12 `_sum`/`_count` series per mount pod against ~92-170 bucket series, so **scraping `_sum`/`_count` only is roughly an order of magnitude cheaper** than scraping buckets.

## PersistentVolume `mountOptions` — the Terraform/CSI contract

5. **Changing a PV's `mountOptions` is an IN-PLACE update, not a replace — and it rolls the mount pods lazily, not at apply time.** Three layers each had to be checked, and all three agree: **(a) Terraform** `hashicorp/kubernetes` **2.38.0** — `mount_options` has no `ForceNew` (`resource_kubernetes_persistent_volume_v1.go:185-191`) and `CustomizeDiff` force-news only `spec.0.persistent_volume_source.*` (`:65-76`); the update is a JSON-patch `replace /spec/mountOptions` (`structure_persistent_volume_spec.go:1282-1287`), which succeeds even when the key is **absent** because json-patch v4.13.0's `partialDoc.get` never errors (`patch.go:393`) — confirmed with a server-side dry-run against a live PV, resourceVersion unchanged. **(b) kube-apiserver** — `ValidatePersistentVolumeUpdate` locks only `persistentVolumeSource` and `volumeMode` (k8s 1.35 `validation.go:2271-2303`), so `mountOptions` is mutable. **(c) the CSI driver** — JuiceFS CSI **v0.31.4** reads PV `mountOptions` only at `NodePublish`, via the volume capability's `MountFlags` (`node.go:211-214`), and feeds them into `GenHashOfSetting` (`setting.go:1245`); a changed hash means **a NEW mount pod per node for NEW sandboxes** (`pod_mount.go:408` skips reuse on hash mismatch) while **existing mount pods and the pods using them are untouched and keep the OLD cache limits until they drain.** So the rollout is gradual and there is no disruptive remount — plan the soak accordingly.

6. **An empty `mount_options = []` is indistinguishable from an absent one in the provider, which is what makes a default-empty, per-environment variable safe to ship everywhere at once.** `mount_options` is a `TypeSet`: `expand` skips an empty set (`structure_persistent_volume_spec.go:1001`) and `flatten` writes only when non-nil (`:377`), so `[]` and absent **never diff**. A `variable "juicefs_mount_options" { default = [] }` therefore renders a zero-diff plan in every environment that does not set it — verified on real plans — so the enablement can be one config line per environment on its own schedule.

7. **The chart's `mountPodPatch` is a second, equal-footing source of mount options, and it OVERRIDES the PV's.** Patch keys win over PV keys (`setting.go:1186-1204`), the global config is hot-reloaded via fsnotify (`config.go:501`), and it selects by **`pvcSelector` only — there is no `pvSelector`**. It produces the same `GenHashOfSetting` roll as #5. Check for it before concluding that a PV edit is the only way options reach a mount, or before concluding that a PV edit took effect.
