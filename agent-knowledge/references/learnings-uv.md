# uv & Python Packaging Learnings

Version-scoped uv and Python packaging behaviours, dependency-group pitfalls, and validation techniques.

See also: `learnings-validation-framework.md`, `learnings-helm-ci.md`, `learnings-agent-workflow.md`, `learnings-code-review.md`, `learnings-agent-sandbox.md`.

## Sync semantics — exact vs inexact

1. **`uv run` syncs INEXACT, `uv sync` syncs EXACT — and the difference decides whether a dependency-group package survives.** Measured on **uv 0.9.16** with a negative control, in a throwaway venv via `UV_PROJECT_ENVIRONMENT`. Starting from `uv sync --frozen --package <member> --no-dev --group <g>` (the group-only package present): a follow-up bare `uv sync` with NO group left the package **GONE** — that is the negative control proving the test can detect removal; `uv run --frozen` from the repo root left it installed; `uv run` from the member dir left it installed. **So a review finding of the shape *"`uv run` re-syncs without `--group` and uninstalls the grouped package"* is WRONG** (one was, on a real PR). The real, narrower gap: **`uv run` on a FRESH venv never installs a group-only dependency**, so justfile recipes and documented `uv run pytest` commands fail at import from a fresh clone. Rule of thumb: when a dependency lives only in `dependency-groups`, **bare `uv sync` is the dangerous site** (it actively strips it) and **`uv run` is only a fresh-venv gap**. Always include a negative control when testing a strip/remove claim, or a green result proves nothing.

2. **The complete strip/non-strip matrix for a shared workspace root `.venv` (uv 0.9.16), measured rather than reasoned.** **STRIPPERS** (remove a correctly grouped package): bare root `uv sync --frozen`; `uv sync --all-packages` — note this is the exact command a sync-helper script may print as its *fix hint*; `uv sync --frozen --extra dev` run from the member dir with no `--group`; and **any other member's exact sync** (`--package <other>`), which removes the first member's packages entirely. **NON-STRIPPERS:** every `uv run` form (root, member dir, `--group`, `--frozen`), every `uv pip install`, and anything with `--inexact`. **Side effect worth knowing: a grouped EXACT member-scoped sync keeps the group but PRUNES every OTHER workspace member from a shared root `.venv`.** So a local `make` prerequisite that syncs one member into the shared venv **must pass `--inexact`**, or it silently uninstalls the sibling packages for anyone who uses one venv for everything. A no-op `uv sync --frozen --inexact --package <m> --group <g>` on an already-synced venv costs ~0.5 s, so it is cheap enough to be a run-target prerequisite.

## Dependency groups (PEP 735) — where they are and are not honoured

3. **uv ≤ 0.12.1 (including the 0.9.16 pin) IGNORES a workspace member's `[tool.uv] default-groups` when invoked from the workspace ROOT with `--package <member>` — it applies the ROOT's default groups (implicit `["dev"]`) instead.** Fixed in **uv 0.12.2** (astral-sh/uv#20930, *"Avoid including workspace-root default dependency groups when syncing or exporting a selected workspace member"*). Bisect it with `uv export --frozen --package <member> --no-dev` and grep for the group-only package: 0.12.1 absent, 0.12.2 present. **Running from the member directory (`--project` / `--directory packages/<member>`) DOES honour member default-groups even on 0.9.16.** And a root `default-groups` cannot name a member's group — uv errors *"group not defined in the project's dependency-groups table"*.

4. **A plain workspace-root `uv sync` / `uv export` (virtual root, no `--package`) never applies a member's default-groups on ANY version tested (0.9.16 … 0.12.18) — and what the root venv then resolves to is a trap.** If the member keeps a **base range** for a package that its conflicting groups also pin, the no-group fork resolves to the **NEWEST version in range**: with `pkg>=0.4.3,<0.6` plus `groupA`/`groupB`, `uv.lock` marks **0.5.6** for *"extra != groupA"*, so the root `.venv` — which is what pre-commit hooks and local `make run-*` targets use — silently switches to the newest version. Removing the base entry instead makes root sync install **NO** copy of the package at all. **Either way, root-level consumers need an explicit `--group`** (which does work at root on 0.9.16).

5. **`[tool.uv] conflicts` declared in a workspace MEMBER works on 0.9.16, and the lock churn it produces is ~95 % cosmetic — budget for it before the diff scares a reviewer.** `uv lock` records `conflicts=[[{package=<m>,group=A},{package=<m>,group=B}]]`, forks both versions, and `--group A --group B` together errors loudly. Measured churn on a real workspace root lock: **~250 lines (163+/87−)**, almost all impossible-combination markers appended to **unrelated** dependencies (`"or (extra == 'group-12-<m>-A' and extra == 'group-12-<m>-B')"`), plus 2 new package entries. Say this in the PR body or the lock diff reads as an unrelated dependency bump.

6. **Re-lock with the REPO-PINNED uv, never the one on your PATH — a newer uv renormalises markers and silently inflates the diff.** Use `uvx uv@$(cat .uv-version) lock`. Measured: Homebrew **uv 0.12.11** rewrote both `ipython` blocks, dropping `python_full_version < 3.12` / `>= 3.12` from 11 dependency markers each and turning a one-line change into **22 insertions + 22 deletions**. With the pinned **0.9.16** the identical edit (a specifier widened from `==0.4.3` to `>=0.4.3,<0.6`) produced **exactly one changed line** in `requires-dist` and moved **zero** resolved versions — `uv lock` is conservative and keeps an existing in-range pin. Corollary for reverts: revert `pyproject.toml` and then re-run the pinned `uv lock`; do **not** hand-merge the lockfile.

7. **Two `--group` guard gaps that let a bad group name ship a package-less image (uv 0.9.16).** (a) `uv sync --no-dev --group dev` is accepted **silently** (the group is re-added, exit 0); (b) an **undefined** group name errors loudly (*"Group X is not defined"*). So a config-driven group value of `"dev"` passes an empty-string check, passes a `test -n` Dockerfile guard, and `uv sync` succeeds — while the image ships with **none** of the group's packages. The same outcome follows from simply dropping the `--group` flag from the Dockerfile's `uv sync`. **Only a POST-SYNC IMPORT CHECK closes both holes** — and it must import the module that actually needs the package (see #12), not the bare top-level package.

8. **Reverting a dependency-group PR is not free for downstream code.** Once a group name is reverted away, any `uv sync` / `uv run --group <name>` **anywhere** hard-errors *"Group `<name>` is not defined in any project's dependency-groups table"* (0.9.16, verified on a simulated revert). A revert must therefore also sweep every post-merge commit that copied the flag, and must be promoted to the release branch if the merge was. The textual revert itself was clean and tree-identical, and `uv lock --check` passed (negative control: mutate a pin to a different version → rc=1 *"needs to be updated"*). The likeliest revert failure is a `uv.lock` conflict if another PR re-locks in between.

## Harness and experiment mechanics

9. **`UV_PROJECT_ENVIRONMENT` only steers PROJECT commands — `uv run --no-project` and `uv pip install` ignore it** and fall back to `VIRTUAL_ENV` or `.venv` discovery from cwd upward. A test harness that sets only `UV_PROJECT_ENVIRONMENT` therefore reports **false failures** for those two forms, because they silently ran the system Python. Test them in a throwaway **git worktree** with real discovery instead, deleting `<wt>/.venv` and `<wt>/packages/<member>/.venv` between runs. Related trap: a throwaway venv built by `UV_PROJECT_ENVIRONMENT=… uv sync --package <m>` installs that member **EDITABLE from whichever checkout ran the sync**, so a venv built in a shared main checkout silently tests the *other* branch's code — rebuild from the worktree and verify with `<pkg>.__file__`.

10. **Proving a dependency overlay is INERT, offline, with no Docker.** Recipe: `UV_PROJECT_ENVIRONMENT=<dir> uvx uv@<pin> sync --frozen --package <m> --no-dev --no-editable --extra <e>…`, then `uv pip install "A==X" "B==Y"` as **ONE transaction**, then diff `uv pip freeze`. Results that make the claim: overlay at the **current** versions ⇒ uv reports *"Checked N packages"*, installs nothing, freeze byte-identical to baseline (only the venv-path banner differs) — the overlay layer is a provable no-op; overlay to the **target** versions ⇒ exactly **two** lines move, zero transitive churn, confirming the two bounds co-resolve. A second offline proxy, for a Dockerfile-touching change whose image is never built pre-merge: `uv sync --frozen --dry-run --offline --package <m> … --group <g>` into a scratch `UV_PROJECT_ENVIRONMENT` prints the **exact install set the image would get** without a build.

11. **`uv pip check` is the right gate and a bare `uv pip check` is the wrong one, whenever the project declares `[tool.uv] override-dependencies`.** A deliberate override makes the tree permanently "incompatible" — e.g. an override forcing a transitive package to a newer major produces *"The package `aiormq` requires `pamqp==3.3.0`, but 4.0.0 is installed"* on day one, on a clean checkout. A CI gate that runs bare `uv pip check` therefore **fails immediately on a pre-existing condition**, and the tempting fix (grep the line away) also blinds the gate to the override disappearing. **Compare the incompatibility SET against a declared expected set** so a NEW incompatibility fails AND a VANISHED override fails. Related non-vacuity recipe for a version gate: pick a version that **exists and installs cleanly but violates the declared range** — an exact-version assertion and the imports both pass while `uv pip check` alone catches it; a **nonexistent** version fails at RESOLUTION and proves nothing about the gate.

12. **A package whose `__init__.py` wraps an optional import in `try/except ImportError` makes `python -c "import <pkg>"` a VACUOUS smoke check.** Reproduced in scratch venvs: the package substitutes a placeholder class, so the bare import **succeeds** even with the `[async]` extra and its transitive client absent, while `import <pkg>.async_sandbox_client` fails `ModuleNotFoundError`. **Any build-time smoke check must import the SUBMODULE the application actually imports**, not the bare package — read the application's own import line and mirror it. Same principle one layer up: a CI gate that imports only the *libraries* misses a module-level version guard living in *application* code (see `learnings-validation-framework.md`).

13. **PEP 735 `dependency-groups` are invisible to `pip install .`, so moving a package into a group can silently drop it from SCA/vulnerability scanning.** Scanners configured to resolve a Python working directory via **pip** (Frogbot and similar) will not see group-only dependencies. Scope this honestly when you find it: this is **inferred from the scanner config plus pip semantics**, not verified in the scanner's own source or a scan output — the check that settles it is reading the next post-merge security run's reported dependency list. Flagging an unverified coverage gap as *inferred* is the correct output; asserting it is not.

14. **Enumerating what a private index actually publishes: read the simple index, do not probe.** `curl -s --netrc https://<host>/artifactory/api/pypi/<repo>/simple/<package>/` returns the full version list. `uv pip install --dry-run <pkg>==999` does **NOT** enumerate versions and its *"no version of"* message is easy to mis-parse into a wrong list. Getting the true published set is what turns a guessed range into a justified one — e.g. discovering there is no `0.6.x` at all makes `>=0.4.3,<0.6` provably "the 0.4/0.5 corridor and nothing else" rather than an arbitrary ceiling.

## Environment hygiene

15. **`uv sync` with `UV_PROJECT_ENVIRONMENT` pointing at a pre-existing directory that LACKS `pyvenv.cfg` does NOT recreate it — it installs the whole project into the uv-managed BASE interpreter's `site-packages`.** Seen with a stale scratchpad venv left by an earlier session: `bin/python` was a symlink to the uv-managed CPython, so the sync succeeded, imports resolved out of `~/.local/share/uv/python/cpython-<ver>-*/lib/python<ver>/site-packages`, and every test result was measuring a tree nobody intended. It fails silently in the most dangerous direction — a **green** run against the wrong code. Always use a **fresh, uniquely-named** venv path per task (parallel agents share the scratchpad, `learnings-agent-workflow.md`), and before trusting any result assert both `pyvenv.cfg` exists and `python -c 'import <pkg>; print(<pkg>.__file__)'` points inside the venv.

16. **Deleting a `[tool.uv] conflicts` set (one group left) collapses every forked package to ONE version for ALL installs — including syncs with no group.** uv 0.9.16 rejects a one-member conflict set, so removing the second-to-last conflicting group means deleting `conflicts` entirely. The lock then drops the fork markers (`... or (extra == 'group-12-<m>-A' and extra == 'group-12-<m>-B')`, the bulk of a ~+85/−157 diff) and a package the base deps list **unpinned** but the surviving group pins (here `kubernetes-asyncio`) resolves to the group's pin everywhere: a no-group sync moved 35.0.1 → 33.3.0. Prove the change is inert for the real install with `uv export --frozen --group <g> --no-hashes` (per package and `--all-packages`) diffed against the base checkout — byte-identical is the claim; call out the no-group version move separately. Complements #4/#5. Check who actually imports the collapsed transitive dependency before deciding the change is safe; in the measured case exactly one package did.

17. **Collapsing a dependency GROUP into `[project] dependencies` is provably inert when the group was the only home of a pinned package — and the proof is an export comparison, not a test run.** Measured with uv 0.9.16: the relock was +4/-11 with no version moves. The proof of inertness is that `uv export --frozen --no-hashes --no-emit-workspace --package <m>` with **no group** at head equals the previous head's export **with** the group, for the default, image (`--no-dev --extra …`), dev-group and root sets — only `# via` annotations differ. The negative control is the old head's **no-group image export**, which must contain **zero** lines of the package in question. Plumbing that existed only to select the group per environment is best removed by **reverting to the pre-group blobs**: confirm with `git hash-object` vs `git rev-parse <commit>~1:<path>` that the Dockerfile and build config come back hash-identical — a cheap review-grade proof that nothing else rode along. Look for a duplicate **unpinned** entry of the same package in another extra; it should go too.

18. **Prove a "this wheel drops N transitive dependencies" claim offline, with no Docker and no full download: fetch the PEP 658 metadata next to the wheel on the alternate index and diff its `Requires-Dist` against the public index's `requires_dist`.** `curl '<wheel-url>.metadata'` is served (200, `binary/octet-stream`) by at least one major alternate index. The public side doubles as the **extractor's negative control**: it must still report the rows you expect removed. Then prove the resolution without downloading the wheel: `pip install --dry-run --report <f> --no-deps --target <d> --python-version <X> --platform <plat> --only-binary=:all: --index-url <alt> -c <lock> <pkg>`. **Control that the `-c` file is load-bearing** by mutating its single pin in a scratch copy — it must give `ResolutionImpossible`. A `pip download` that 403s may be a client problem, not an index policy: one such 403 was urllib-only and `pip download` worked.
