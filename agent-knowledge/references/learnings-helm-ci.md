# Helm, YAML & CI Learnings

## YAML formatting

1. **Empty YAML override files must be 0 bytes.** When creating an empty values file (e.g. `values/clusters/<cluster>.yaml` with no overrides), the file must be completely empty. Do NOT use `{}` or `---` — most formatters strip both to empty anyway. Use `truncate -s 0 <file>` or `> <file>`. Always run `yamlfmt --lint` to verify.

2. **yamlfmt typically uses `indentless_arrays: true`** in many GitOps repos. When writing values files with list items, use indentless style:

   ```yaml
   paths:
   - "/etc/shadow"    # correct
   ```

   NOT indented style (`  - "/etc/shadow"`). Match what the repo formatter expects.

## Chart dependencies & publishing

3. **Always run `helm dep build` before lint/template.** Charts with dependencies will fail lint and template without building deps first. The CI workflows always do this — match locally. Register every external dependency repository in CI (for example, a `helm_repo_add` input in `.github/workflows/chart_lint.yaml`); dependency tarballs under `charts/**/charts/*` may be gitignored, so local success does not prove CI can fetch them. If changing `Chart.yaml` leaves `Chart.lock` out of sync, run `helm dep update` to regenerate it, commit the intended lock change, then run `helm dep build` as the strict consistency check.

4. **OCI registry: publish the upstream chart, not the wrapper.** When publishing a dependency to an internal OCI registry, always publish the upstream chart (from `helm pull`), NOT the wrapper chart. Publishing the wrapper creates a recursive dependency.

5. **Decouple wrapper chart version from upstream version.** Use an independent versioning scheme for wrapper charts (e.g. `0.1.x`) to avoid collisions when publishing to the same OCI registry.

## Values & overrides

6. **Avoid overriding upstream list/map defaults unless necessary.** Many upstream charts have curated default lists. Setting these in wrapper `values.yaml` **replaces** the entire upstream default rather than extending it. Only override when you explicitly need to, and include the upstream defaults too.

7. **Always verify value overrides render with `helm template`.** After changing value paths or chart dependencies, run `helm template` and confirm the rendered output contains your overrides. Values at the wrong nesting depth will silently fall back to upstream defaults. Pair the intended diff with a deliberately misspelled key under the same subchart alias: an unread key can render byte-identically, so the negative control should remove the intended delta. Wrong nesting, an alias mismatch or a renamed upstream key can all cause this. A sentinel such as Istio's `_internal_defaults_do_not_set:` may be merged to the subchart top level by a profile template; inspect the consumer rather than treating upstream indentation as the override path.

## Git & CI

8. **Reusable workflows cannot use local composite actions** when called via `uses: ./.github/actions/*`. GitHub resolves these paths from the workspace, not the workflow's source ref. Either inline steps or call scripts directly.

9. **Pin tool downloads and third-party Actions.** Use specific versions with checksum verification for tool downloads (yq, kubectl). Pin third-party Actions to commit SHAs with version comments (e.g. `uses: actions/checkout@abc123 # v6`).

10. **When a reusable workflow is referenced by branch name**, the branch gets deleted on merge, causing `startup_failure` in all consumers. Always pin to commit SHA.

## YAML tooling

11. **`yq -i` reformats YAML.** It adds array indentation, breaking `indentless_arrays` yamlfmt configs. Use the hybrid pattern: `yq` for reading/parsing, `sed` for writing — or run `yamlfmt` after `yq -i` to restore formatting.

## Values & overrides (continued)

12. **Sprig's `merge(dst, src)` has the FIRST argument win on key conflicts; the second only fills in missing keys — the opposite of `mergeOverwrite(dst, src)`, where the second wins.** When you want "A always wins, B only fills in what A doesn't have," write `merge(A, B)`. The common bug is reaching for `merge` expecting the thing you pass second (the "override") to win — it will not; the base wins and the override is silently ignored wherever both set the same key. Use `mergeOverwrite` whenever the second argument is meant to override the first.

13. **Helm's `required` function does not reject an empty list or empty map — only `nil` — so a Helm guard fronting a field that a CRD marks `minItems`/`minLength` just moves the failure from render-time to apply-time, and makes it worse.** `{{ required "msg" $x.access }}` passes cleanly when `access: []`, rendering a valid-looking object with exit code 0. If the CRD declares `minItems: 1`, the apiserver then rejects the object at apply — and depending on your GitOps tooling, that can fail the entire application rather than just the one resource, which is strictly worse than the loud render-time failure the guard was meant to produce. Fix that keeps the message and stays one expression: `required "msg" (empty $x.access | ternary nil $x.access)` — `empty` catches `nil`, `[]`, `{}`, and `""` alike. Verify the guard actually fires by rendering WITH the empty value and asserting a non-zero exit — a `required` guard that looks present in the template is not proof it fires on the input you care about.


## Helm template rendering mechanics

14. **Helm renders templates in REVERSE-alphabetical path order, which inverts the naming convention you'd naturally reach for when writing an observation probe.** `helm.sh/v3/pkg/engine` sorts templates by path depth descending, then lexicographically descending, so `templates/zzz-probe.yaml` renders BEFORE `templates/serviceaccount.yaml`, and `templates/aaa-probe.yaml` renders LAST. This silently inverts any probe meant to observe state that an *earlier* template is supposed to have already mutated — for example, proving that a Sprig `merge` call mutates its first argument in place (Sprig's `merge` does mutate its first argument, so if that argument is a pointer into `.Values`, the mutation is visible to every template rendered afterward). A probe named `zzz-*` in that scenario sees clean state both before and after the fix (false negative, the whole harness is vacuous); a probe named `aaa-*` sees the real pre-fix pollution. Name any cross-template observation probe `aaa-*` so it renders last and observes earlier mutations.

15. **`helm template --show-only <target> --output-dir <dir>` together: Helm ignores `--show-only`, prints a spurious `Error: could not find template <target> in chart` to stderr, and still writes ALL rendered templates to the output directory — including the one you asked for.** The error looks fatal but is harmless; the fix is to ignore it and read the specific per-file YAML directly off disk in the output directory rather than trying to combine the two flags. Useful as a general workaround whenever a full-stream render is too large or noisy to grep reliably: render everything to `--output-dir` once, then read individual template outputs natively. **UNVERIFIED at source level** -- this claim carries no version pin or source citation; confirm against the tool's own source at your pinned version before relying on it.

16. **Helm `define` names are global per RELEASE, not per chart — an umbrella chart with unprefixed helper names in sibling subcharts has a latent template-namespace collision.** If two subcharts under one umbrella each `define` a helper with the same bare name, they collide at render time and the last one parsed wins — so a chart can silently render a SIBLING chart's template logic instead of its own. Identical bodies are harmless by coincidence; divergent bodies are a live, silent defect. Detect it structurally, without rendering anything, by hashing the body of every `define` across the whole dependency set and flagging name collisions with differing bodies. Fix direction: prefix every `define` with the owning chart's name. The broader consequence: "this chart's template is correct in isolation" is not a statement about what the umbrella actually renders once it's a dependency.


## Validation depth & testing

17. **In `helm-unittest` 1.1.1, negative assertions are VACUOUS on a path that doesn't exist at all — the common "isNotEmpty + notMatchRegex over a wildcard path" idiom used to prove "no bad values are present" proves nothing if the path is simply absent.** Verified with an isolated probe chart: `isNotEmpty` PASSES against a nonexistent path, `notMatchRegex` over an absent wildcard path PASSES, and `isNull` also passes on an absent path — deleting the entire block the test is supposed to be sweeping leaves all three green. What DOES fail correctly on an absent path: `contains` (both full-object and subset forms) and `lengthEqual`, which both error with an explicit "unknown path" rather than silently passing. Rule: every negative or sweep-style assertion needs a POSITIVE anchor on the same path inside the same test case — a sibling test elsewhere in the suite proves nothing about this one's non-vacuity. Prefer `contains` with a subset match on a stable value (e.g. one field known to always be present) so the anchor doesn't pin an exact count or break on unrelated message rewording. **Wildcard semantics:** `a.b[*].c` reports `ValuesIndex`; `notMatchRegex` fails if ANY element matches, while `matchRegex` requires EVERY element to match, so use an anchored index assertion for "some element". `matchRegexRaw`/`notMatchRegexRaw` return `Actual: <nil>` on ordinary YAML manifests; Raw variants target non-YAML templates such as `NOTES.txt`. Use a path assertion and `lengthEqual` for indexed cases. Go RE2 has no negative lookahead; `(?s)^(?:[^!]|![^h]).*oldSelf` expresses a CEL rule mentioning `oldSelf` without opening with `!has(`. **Absence is a separate assertion:** use `notExists`, paired with `exists` or positive `contains` on a sibling path in the SAME `it:`. `isNull` accepts an absent path but rejects an empty string `''`; an inactive block emitted with empty defaults can therefore fail `isNull` without non-empty fixtures. Prove these gates with valid template mutations: replacing a condition with `{{- if true }}` isolates a policy leak, whereas deleting all `if`/`else`/`end` merely breaks rendering. One suite detected 7/7 such mutations.

18. **Never split a multi-document Helm render on a literal `"---\n"` separator — an embedded YAML block scalar can contain lines that look exactly like a document separator, and a naive split yields bogus scalar chunks.** A multi-line string value (a script, a config blob) inside `|` or `>` block scalar syntax can legally contain a line of three dashes, and any tool that treats that literal string as a document boundary silently mis-splits the stream. Parse the whole stream with a real multi-document-aware YAML loader (e.g. `yaml.safe_load_all`) for semantic validation; if you genuinely need exact source-byte slicing per document, use the loader's node start/end marks rather than string-splitting. Hard-fail on parse errors and on chunks that don't look like a resource, rather than silently skipping them — a silently-dropped chunk is exactly how a render-comparison tool reports "no differences" on a document it never actually read.

19. **Renders-correctly, API-accepts-it, and behaves-correctly are three DIFFERENT properties, and passing the first two proves nothing about the third — for any chart change that creates custom resources or reconfigures controller/GitOps behavior, offline render-level proof is not sufficient.** A shape that passes both `helm template` and `helm lint` (both entirely client-side) can still be REJECTED server-side because the live API enforces structural requirements the client-side tools never check (e.g. a field group requiring two sibling fields together that the client-side schema doesn't itself enforce). Same class: a GitOps-tool-specific diff-suppression setting can render correctly and still fail to actually suppress the diff once the tool applies with a stricter merge strategy — only a live patch-and-refresh proves it. Four-part guardrail: (1) pipe the rendered output into a server-side dry-run against a real (non-production) cluster, which catches schema-level rejections client-side tools cannot; (2) for any diff-suppression or sync-behavior change, verify it against a LIVE managed object (patch it, force a refresh, confirm it reports fully synced) before claiming it works; (3) at design time, read the target CRD's actual required-fields shape (not just its documentation) and dry-run a throwaway object before committing to a resource shape; (4) whenever a change swaps a pattern because of a deprecation warning, dry-run the replacement too — don't assume the replacement is automatically correct.

20. **A mutation harness must assert a CLEAN TREE AT START, not only restore at end — and its backups must live OUTSIDE the chart tree.** Two independent ways the same harness lied: (a) **Helm renders backup files left under `templates/` even when the suffix is `.before`** — copying a policy template to `templates/<name>.yaml.before` silently rendered BOTH the original and the mutant, masking a dropped-policy mutation. Keep mutation backups outside `charts/<chart>/` and assert no backup files exist before invoking Helm. (b) **A harness killed by a TIMEOUT leaves its worktree DIRTY** — restore-in-`finally` does not survive `SIGKILL`. A killed probe left its mutated template in place in the scratch worktree, breaking the PRECONDITION of the next probe (which reported "unable to determine" — but could equally have reported a false green). **After ANY timeout-killed mutation run, and before trusting the next one, run `git status --porcelain` and `git checkout -- .`.** (Read alongside `learnings-crossplane.md`: when the primary change is uncommitted, restore from a `cp` snapshot, never from git.)

21. **Two things that make a naive umbrella render matrix WRONG, both silent.** (1) **A chart that consumes a sibling via `file://` must be re-vendored before EVERY render** — `rm -rf charts/<chart>/charts && helm dep build`. A stale vendored `.tgz` renders the OLD subchart, so a base-vs-head diff shows nothing and the pass is VACUOUS. (2) **A cluster whose GitOps Application pins a vendor release tag does not receive a `main` change at all** — **never claim a production effect from a main-branch render of a tag-pinned app.** Related: the render namespace is the Application's `destination.namespace`, and it is NOT uniform across a fleet — take it per cluster (#22).

22. **A render helper that does NOT pass `--namespace` lets `Release.Namespace` fall back to the KUBECONTEXT's current namespace instead of the Application's `destination.namespace` — and on some targets that makes the render FAIL.** Two things make this hard to diagnose: **WHICH targets fail is not a fixed list** (it depends on the invoking context's namespace, so two operators hit different subsets), and **a chart guard that only runs in some environments MASKS the bug on the others**, so the failures look targeted rather than systemic. **Do NOT mistake it for breakage caused by your own change — verify by rendering the same target at `origin/main`, which fails identically.** Fix: hand-roll the render with `--namespace <destination.namespace>` read from the deploying Application, plus a detached-worktree baseline render and a structural diff.

23. **Fleet render-proof harness — the recipe that actually discriminates, and the three ways a naive version goes vacuous.** Enumerate `(cluster, app)` pairs from the deploying Application's own `valueFiles` (`learnings-argocd.md`). Create **two detached worktrees** (`git worktree add --detach <dir> origin/main` for the merge-base, plus HEAD), run `helm dep build` **once per chart per checkout**, then `helm template <app> charts/<app> -n <destination.namespace> -f <each valueFile>` and hash the stream. **Do NOT loop a per-cluster render skill** — it creates a worktree and dep-builds per invocation (#22). CI's own live-diff jobs corroborate independently.
    - **The right containment assertion is NOT "the value appears"**: assert *"the rendered FILE SET is unchanged AND exactly one file's bytes differ"*, plus *"exactly N data keys added, none removed, no pre-existing key mutated"*. That catches collateral damage a grep for the new value never would. **And know the expected delta before you measure** — for a per-variant-gated block only the matching variant is emitted, so a "one key per variant" expectation is wrong or vacuous.
    - **Render freshly and assert NON-EMPTY before any content assertion**, and render with plain `helm template`, **not through a caching wrapper** — a stale cache burned a whole workstream (`learnings-agent-workflow.md`).
    - Ops notes: run helm from `subprocess.run` with isolated `HELM_{CACHE,CONFIG,DATA}_HOME` + `--output-dir`, **but do NOT isolate `HELM_DATA_HOME` for `helm unittest`** — the plugin lives there and the command fails `unknown command "unittest"`. Compare with Python string equality, never `yq '=='` (it glob-matches — #25). Policy findings are nondeterministically ordered — sorted multiset only.

24. **Two render-proof controls that are strictly better than the obvious ones.** (a) **Hash both sides through the IDENTICAL pipeline.** `printf '%s' "$(helm template …)" | shasum` strips trailing newlines (command substitution) while `helm template … | shasum` keeps them, so the SAME render yields two different digests. Comparing a harness-produced hash against an ad-hoc one-off hash produced a false *"the render changed"* scare on an untouched cluster. **Never mix pipelines, and run the negative control by re-running the WHOLE harness on the perturbed tree — never by hashing one pair by hand.** (b) **For a Helm VALUES-KEY change, the load-bearing negative control is the WRONG NESTING control, not the mutate-the-value control.** Re-render with the key moved one nesting level up (wrong path) and confirm `dyff` returns *no differences*. That proves an all-unchanged dyff is the signature of a wrong key path, and therefore that your real one-field diff proves the template genuinely **CONSUMES** the key. Mutating the value only proves the diff tracks the value — it cannot distinguish "the template reads THIS key" from "the template reads a different key that happens to change too". Use both.

25. **Three `yq` operators and one bash operator GLOB-MATCH or fall through, and every one of them fails OPEN in an assertion. Self-check any detector against known-bad input before trusting a green suite.**
    - **`yq` (mikefarah v4) `==` GLOB-MATCHES**, so `select(. == "*")` is TRUE for **every** string. A test written as `yq '.spec.managementPolicies[] | select(. == "*")'` to assert the wildcard is ABSENT passes vacuously — it returns every element, and an "is it empty" phrasing then fails open. Also **`or` binds loosely**: `select(. == "A" or . == "B")` does not parse as intended — parenthesise. **Fix: extract with `| join(",")` and do membership in bash** (`case ",$joined," in *,Delete,*`). Caught live while writing a Crossplane composition behaviour suite — **5 retain assertions were vacuous**.
    - **`yq`'s `//` alternative operator returns its RHS when the LHS is FALSE, not only when null**, so `.spec.forProvider.forceDestroy // "n/a"` renders `forceDestroy: false` and an absent key **identically**. Any boolean-PRESENCE assertion must use `has("key")`. Hit while proving bucket retain semantics: the summary table read `n/a` for the production `forceDestroy` and looked like the field was missing, when it was explicitly `false`.
    - **`yq` `//` on MULTI-DOC streams (v4.44.x) fires the fallback for EVERY document where `select()` returns null**, not just the matching one. Fix: `| select(. != null)` on the extracted field rather than `// fallback` — per-element, and works on all versions.
    - **Same family, one layer below: bash `assert_eq` MUST use POSIX `[ "$exp" = "$act" ]`, never `[[ "$exp" == "$act" ]]`** — `[[ ]]` treats its RIGHT operand as a GLOB, so an expected value of `*` (the non-production Crossplane `managementPolicies` value) matches EVERY actual string. **Fixing the `yq` selector while leaving `[[ == ]]` keeps the assertion vacuous.** The shipped fix was a `self_check()` that exits 2 **before any assertion runs** unless `[ * = Observe ]` is false, `[ * = * ]` is true, and `member()` both sees a present element and rejects an absent one.

## CI and release hygiene

26. **"The other jobs passed" does NOT prove runners are healthy for the workflow you care about — and you must NOT try to kick a stuck run.** On one Terraform repo's PR the main workflow's stack-discovery job sat `status=queued` / `runner_name=null` on a plain `ubuntu-latest` runner for **56+ minutes**, while every OTHER `ubuntu-latest` workflow on the same PR (terraform fmt check, yaml fmt check, terraform-docs, lint, dependency scan) completed in under a minute. **Diagnose with `gh api repos/<o>/<r>/actions/runs/<id>/jobs --jq '.jobs[] | {name,status,runner_name,labels}'` — `runner_name: null` + `status: queued` means never picked up.** Do NOT close/reopen, push an empty commit, or flip draft→ready: the run already exists and readiness is not the gate, and churn on a production-touching PR only adds noise. **Correct play is a bounded hold (~1h), then hand back with the verification gate written INTO the PR body** so the next person can finish it.

27. **A blind `git add -A` in a job that ALSO authenticates to a cloud sweeps the auth step's credential file into the commit — and `.gitignore` cannot save you, because it does not apply to a path the bot force-adds in the same run.** Shape: a release job runs "cloud auth" and then "commit version bump" with `git add -A`. **`google-github-actions/auth` writes a `gha-creds-*.json` WIF external_account config into the workspace**; a `.gitignore` entry added in an EARLIER commit does not stop a force-add in a LATER one. **What such a file discloses** even without a long-lived key: the cloud project number, the workload-identity provider path, the impersonated service account, and — because `google-github-actions/auth` embeds it — the run-scoped `ACTIONS_ID_TOKEN_REQUEST_TOKEN` in `credential_source.headers`. **FIX belongs in the shared CI workflow: scope the add to the version file (`git add package.json VERSION`), never `-A`.** **GENERAL RULE: in any job that both authenticates to a cloud and commits, enumerate what the auth step wrote to the workspace before staging anything, and NEVER stage by wildcard** — the same shape as a validation script's `Chart.lock` leak (#29). **Same family one layer down: a Dockerfile doing `COPY . .` with no `.dockerignore` is the identical sweep-everything hazard.**

28. **Any tool that round-trips a config file through a Go `map[string]interface{}` will REORDER, ESCAPE and RE-INDENT it on every write — and in a formatting-gated repo that breaks `main` on every release.** Go's `encoding/json` sorts map keys alphabetically and HTML-escapes `<`, `>`, `&` (`&gt;`), and `MarshalIndent` forces its own indent — so a tab-indented, logically-ordered `package.json` comes back 2-space, alphabetical and escaped, and the next formatter check on `main` fails. **Manually reformatting the file is a PROVEN band-aid, not a fix** — the bot clobbers it on the next bump, sometimes the same day. **Local fix that works: a formatter `overrides` entry scoped to that one file, matching the bot's output** (e.g. biome `json.formatter` `indentStyle=space` / `indentWidth=2`) — the formatter then only cares about indent, the bot's output is a FIXED POINT, and release diffs collapse to one line. **Durable fix: a format-preserving targeted value write (sjson-style) in the version tool itself.** **General shape: check for a targeted-write path before adopting any config-rewriting tool into a formatting-gated repo.**

29. **A validate/lint script that runs `helm dep build` as a side effect makes `git add -A` UNSAFE — always add explicit paths, and always `git show --stat HEAD` before pushing.** One repo's `./validate.sh` sweeps every chart and leaves a dozen untracked `Chart.lock` files behind; a subsequent `git add -A` silently swept them into a commit that should have been 3 files / 39 insertions and became **14 files / 381 insertions**. The commit still passes review at a glance because the intended change is present and correct.
    - **Companion fact that makes this worse: the same script EXITS 1 on a CLEAN `origin/main`.** Pre-existing `Template failed` entries (charts templated with no values, e.g. one requiring a cloud selector value, plus charts with unfetched deps) mean the exit code carries no information. **The only meaningful check is a byte-diff of ANSI-stripped output between a detached `origin/main` worktree and your branch.** The same holds for the YAML linter, which has its own standing offenders — **normalize absolute worktree paths and sort before diffing**, or parallel-output ordering plus a timestamp yields a spurious multi-thousand-line diff that is really no diff at all. **Scope the local gate to changed charts.** CI may use a changed-file matrix while a repo-wide `validate.sh` sweep lints/templates everything, exceeds the session budget, and leaves generated `Chart.lock` files plus untarred `charts/<c>/charts/` directories. An aborted sweep left 7 untracked locks and 34 subchart directories without modifying tracked files. Run formatter lint, Helm lint/template and policy checks on explicit changed paths; check that `pre-commit` is installed before claiming it ran. Compare the failing SET against the base revision before attributing required-discriminant or legacy-format failures to the change.

30. **sprig `merge` is FIRST-SOURCE-WINS, so a template doing `merge $specific $local $global` renders identically whether or not the global block exists — which makes removing a superseded global a provable zero-object no-op.** This is the cheap proof that a values-cleanup PR is safe: render every consuming cluster before and after and show a zero-document delta, rather than arguing from precedence rules. It also means the inverse: a global that "looks live" in values may be entirely shadowed and doing nothing. Note the asymmetry with `mergeOverwrite`, which is last-source-wins — read the helper before assuming which one a chart uses.

## `wait=true` at fleet scale, and chart sub-container traps

31. **`helm_release` / `helm --wait` on a fleet DaemonSet fails as a function of CHURN RATE, not node count — and you cannot extrapolate the curve from cluster size.** Measured across three clusters on the same day with the same DaemonSet: a 102-node cluster read desired/available **102/102** (gap 0, gate closes); a **451-node** cluster read **446/444** — a gap of 2, so a gate at `maxUnavailable: 1` needs 445 and **MISSES BY ONE on a perfectly healthy cluster**; a 497-node cluster read 497/489 (gap 8). **The smallest-gap cluster was not the smallest cluster** — the 497-node one was 4× worse than the 451-node one because its autoscaling churns harder. **An estimated table keyed on node count was written first and the live measurement refuted it: always measure per cluster** — `kubectl get ds -A -o custom-columns` with `.status.desiredNumberScheduled` and `.status.numberAvailable`. Note `.status.desiredNumberScheduled` **trails the cluster node count** (446 vs 451) because it counts only nodes the DS targets.

32. **When a `wait=true` gate fails on a churning DaemonSet, RAISING THE TIMEOUT IS THE WRONG FIX — the gate is a race against churn, not a slow rollout — and the fix is `maxUnavailable`.** A chart whose own default was `50%` had been pinned to `1` in one root; at ~1,470 DS pods that makes the gate require `desired−1` pods Ready **SIMULTANEOUSLY**, which measured churn of 70–210 new nodes/hour intermittently prevents. That is what failed an apply with `context deadline exceeded` **while the pods themselves went healthy**. ⚠️ **It is INTERMITTENT, not permanent** — the same DaemonSet re-read 1471/1471 Ready with 0 unavailable under the same churn a day later, so a single green run is not evidence the gate is safe. The fix was `10%` (~147 nodes), still 5× stricter than the chart default. **A small sibling cluster deliberately does NOT set the value at all** — at 21 nodes the chart default is fine, and pinning it there would import the problem.

33. **A chart's `resources` knob often reaches only ONE container in the pod, leaving unbounded sidecars that out-consume the container everyone tunes.** In `juicefs-csi-driver` 0.31.4, `controller.resources` is `toYaml`'d at `templates/controller.yaml:146` into the main plugin container **only**; the `csi-resizer` and `liveness-probe` sidecars in the same StatefulSet declare **no requests and no limits**, and the chart exposes **no values knob for them** — so the pod is permanently `Burstable` no matter what you set, and can never be `Guaranteed`. Measured live: the **unbounded `csi-resizer` at 1021 Mi vs the tuned plugin at 831 Mi**, while only the plugin OOMKills (10 restarts vs 0) precisely because it is the only one with a limit. **Two companions from the same chart: (a) the controller StatefulSet sets no `podManagementPolicy`, so `OrderedReady` applies — replica 1 is never (re)created while replica 0 is unready, turning one crashlooping pod into `0/2`; (b) the node-driver-registrar sidecar's `--v=5` is HARDCODED at `templates/daemonset.yaml:209` (and `controller.yaml:196`) with no values knob**, so the only levers are a log-ingestion exclusion or an upstream PR. **Check what a `resources` block actually reaches before promising a QoS class.**

34. **A misspelled key under a `toYaml`'d values block RENDERS CLEANLY — `helm template` succeeding is NOT proof the key path is right.** Helm happily emits `memry: 2Gi` next to the untouched default; only the API server rejects it, at apply time. **Diff the render against base and confirm the VALUE ACTUALLY MOVED** — this is #29's negative control applied in the other direction, and it is the only cheap check that distinguishes "the key is wrong" from "the key is right and the value is unchanged".

35. **A GitHub Actions `run:` step made of shell + `jq` can be regression-tested offline, and the harness must EXTRACT the step from the committed YAML rather than re-typing it.** Recipe, proven on a nightly garbage-collection step: (a) `yq '.jobs.<job>.steps[] | select(.id=="<id>") | .run' <workflow>` into a file — a hand-copied harness drifts from what ships and then proves nothing; (b) put a `curl` shim first on `PATH` that dispatches on the URL to per-fixture JSON and echoes a fixture-supplied `%{http_code}`; (c) point `GITHUB_OUTPUT` at a tempfile and assert **both the exit code and the exact `summary=` string** — exit code alone misses reporting regressions, and the string alone misses the `continue-on-error` trap in #36. Three shell traps this surfaces: `curl -s -o F -w '%{http_code}'` returns **nonzero on a connection failure**, so under `set -e` it kills the loop mid-sweep unless you write `HTTP_CODE=$(curl …) || HTTP_CODE="000"`; `curl -o` is not guaranteed to truncate on failure, so `: > "$F"` each iteration; and `jq -e 'all(.[]; …)'` is **true on an empty array**, which is the behaviour you want for an empty work list but is worth asserting deliberately. **Extend the same technique to build pipelines:** place one fake binary on `PATH` and run the REAL make target in pristine base/head worktrees. If downstream mirror scripts call the same CLI, that shim captures the whole fan-out. Exercise each environment × option combination and `cmp` the argument logs. For an extracted workflow step, substitute `${{ }}` expressions and execute under `bash -e`. Use a scripting language for in-place harness edits when portability matters: GNU `sed` rejects the BSD `sed -i ''` form.

36. **The negative control that matters for a partial-failure CI step is DELETING THE `exit 1`, not mutating the business logic — and it is invisible without asserting the exit code.** A step that writes `summary=` and then exits nonzero on `failed>0` produces a **byte-identical summary** when the `exit 1` is removed; only `rc` changes, from 1 to 0. That difference is the whole mechanism: with rc=0 `continue-on-error: true` never activates, `steps.<id>.outcome` reads `success`, and every notification colour/title expression keyed on it reports green while the work actually failed. Run both controls — invert the business mapping AND delete the `exit 1` — because they fail different cases: the mapping inversion failed 6 of 9 fixtures, the missing `exit 1` failed exactly the 3 fixtures that had failures, with identical summaries.

37. **When Helm values are set through Terraform's `helm_release`, `terraform validate` is NOT a substitute for a render-level negative control — it does not type-check `set` list elements at all.** Proved at helm provider `~> 3.1` / Terraform 1.14.0: injecting a junk attribute next to `name`/`value` inside a `set = [{...}]` element (`bogus_attr = true`) still returns `Success! The configuration is valid.` — the object type's optional-attribute conversion silently drops unknown attributes. `validate` only catches expression-level errors at that line (an undeclared `var.` reference DOES fail), so use that as your *control's* control if you need to prove validate is even running. **The real negative control stays `helm template` with the key misspelled by one character.** Two bonuses over the plain "diff goes empty" form when the key is one the chart itself defaults: the misspelled render emits the stray key AND the chart's **default** value for the correct key — which simultaneously proves the key is load-bearing and tells you the default you are deviating from, without reading `values.yaml`. Match the provider's typing when rendering: `helm_release`'s `set` defaults to `type = "auto"`, i.e. `--set`, not `--set-string` (a numeric `"1"` renders as `1`, not `"1"`).

## Additional chart and workflow lessons

38. **`values.yaml` docstring examples must match actual label keys**: When a `values.yaml` docstring includes an example configuration (e.g., workload selector labels for PeerAuthentication), the label keys must match the actual implementation. If a fix commit changes label keys in host-cluster files, always update the `values.yaml` comment example to match — it is the canonical copy-paste reference.

39. **Always grep for existing top-level keys before adding blocks in values files**: Before adding a new annotation or config block for a service in a Helm values file, always `grep` for an existing `^<service>:` top-level key. YAML last-wins behavior silently drops the earlier config when duplicate top-level keys exist. Merge new settings INTO the existing block to preserve `enabled`, `env`, and other nested config.

40. **Legacy charts may have separate annotation paths for Deployment vs Pod template**: Non-reference (legacy) charts like `<service-chart>` have independent template blocks for `deployment.metadata.annotations` and `deployment.spec.template.metadata.annotations`. Setting one does NOT propagate to the other. When adding annotations (e.g., Infisical auto-reload), verify both paths in the chart templates and set whichever is relevant (pod template annotations for controller-watched features).

41. **When an umbrella supplies image tags through an environment overlay, a host-cluster overlay alone cannot render**: Rendering an umbrella chart (e.g. `<umbrella>`) with only a host-cluster overlay (`helm template charts/<umbrella> -f values/host-clusters/<cluster>.yaml`) fails with errors like "No valid image configuration found" because image tags are supplied by `values/environments/{dev,test}.yaml` (injected by image-updater), not the host-cluster file. To validate a host-cluster-only change, stack the matching env overlay: `helm template charts/<umbrella> -f values/environments/<env>.yaml -f values/host-clusters/<cluster>.yaml`. Compare the same stack against the base revision before attributing "No valid image configuration found" to a label or namespace edit.

42. **`kubectl diff -f <file>` on an EMPTY manifest returns exit 0 / no output**: This reads as "no diff" (identical to live state) but actually means "empty file, nothing to diff." A validation step that uses `kubectl diff` on an empty file will silently pass even if the resource is missing from the cluster. Always verify the file has non-zero content before treating a zero-exit `kubectl diff` as a pass. Use `[ -s <file> ] && kubectl diff -f <file>` to gate on file size.

43. **Local `file://` subchart dependencies must be built from the umbrella chart, then re-vendored after sibling edits.** For `repository: file://../<service-chart>`, run `helm dep build` from `charts/<umbrella>/`; the resulting `.tgz` files live in `charts/<umbrella>/charts/` and may be gitignored. A bare dependency build from the repo root targets the wrong directory. Local file dependencies are not registry artifacts, so an OCI pull or `helm_repo_add` cannot replace this build. Update the `Chart.yaml` `repository:` path when moving a subchart; stale vendored copies can mask a change (#21).

44. **Older rtk auto-hook configurations truncated `helm template` output and caused silent grep misses; the behavior changed in 0.43.0.** Before that update, the PreToolUse hook truncated `helm template` output at ~41 lines when piped through shell, silently emitting a literal `... (NNNNN lines truncated) ...` in the stream with NO machine-readable error — so the output looks valid and piped `grep` on a large render returns 0 matches even when matches exist. Large renders were affected. Bypasses, in order: (a) `--show-only templates/<file>.yaml` to isolate a single template; (b) `helm template --output-dir <dir>` — rtk does NOT compress files that helm itself writes (per-file YAML on disk), so this is the cleanest bypass for a full multi-resource render, then native-Read the per-template file; (c) `RTK_DISABLE=1 command helm template ... > artifact.yaml` prefix (bypasses the hook for a single invocation — needed when committing a rendered-manifest artifact so the `... (N lines truncated)` marker is not written INTO the file); (d) invoke helm under a neutral binary name so the hook does not pattern-match `helm template`: `ln -sf $(which helm) /tmp/hx && /tmp/hx template ... > out.yaml`; (e) a Python subprocess that skips the hook entirely: `subprocess.run(['helm', 'template', ...], capture_output=True, text=True)`. Before 0.43.0, `tee /tmp/file` and plain `> /tmp/file` redirects were ALSO intercepted and truncated — the truncation is lossy and writes the marker text INTO the file. `RTK_DISABLE`/`RTK_HOOK_DISABLE` env alone did NOT bypass in all harnesses; prefer `--output-dir` or the `RTK_DISABLE=1 command helm ...` form. Full render is also logged at `~/Library/Application Support/rtk/tee/<...>.log`. **UPDATE (rtk 0.43.0, 2026-07-24): the auto-hook now SKIPS commands containing a redirect (`> file`, `tee`)** — verified: real `rtk hook claude` returns no-rewrite for `helm template … > out.yaml`, and a plain redirect preserves full output (3000-line control passed). So on the Claude auto-path a plain `helm template … > file` is no longer rewritten or truncated — **the `RTK_DISABLE=1` workaround is no longer needed when you redirect to a file** (a runtime without that auto-hook does not need the workaround). Cleanest full-render path now: plain `helm template … > out.yaml` or `--output-dir`. Still avoid MANUALLY typing `rtk helm template …` on a full render (rtk's per-command filter may still compact that specific command); the hook won't do it for you.

45. **A blanket `optional: true` stamp on secretKeyRefs also covers non-operator secrets — guard with an explicit `optional: false` in values**: A Helm helper that conditionally stamps `optional: true` on secretKeyRef entries (e.g. for the Infisical PreSync deadlock, `learnings-argocd.md`) will also stamp refs to always-present static k8s Secrets (e.g. postgres creds). A template guard of the form `not (hasKey $ref "optional")` only skips refs that ALREADY set the field explicitly — so add `optional: false` in values.yaml to the secretKeyRef of any always-present secret, making the blanket stamp skip it. Applies to any helper that conditionally injects `optional` into env secretKeyRefs.

46. **`helm template` on an UMBRELLA can silently drop workloads on a full render — validate per-template with `--show-only`**: A full render of an umbrella (no `--show-only`) can silently emit only the PreSync-hook ServiceAccounts (~41 lines, 3 SAs) and drop all Deployments/Rollouts/Services — exit 0, no error, only benign nodeSelector-coalesce warnings. **UNVERIFIED cause:** the original observation attributed this to umbrella/local-file-subchart coalescing, but the same symptom can arise from output truncation or stale rendering (#44, #49, #50). Isolate those causes before blaming Helm. When validating rollout/deployment enablement on an umbrella, ALWAYS render per-template: `--show-only charts/<svc>/templates/{rollout,deployment}.yaml` (or render the STANDALONE subchart `charts/<service-chart>` before/after). Do NOT trust the full-render kind count. Corollary: rendering a DISABLED subchart's template via `--show-only` errors `could not find template ... in chart` (NOT empty output) because helm excludes an `enabled:false` subchart entirely — that error is the CORRECT confirmation that the block is a pure no-op, not a failure.

47. **Committed rendered-manifest artifacts must be EXCLUDED from yamlfmt** (`.yamlfmt` exclude `rendered-manifests/**`): yamlfmt reflows `toYaml` list indentation and drops the leading `---` document-start, diverging the committed artifact from the true helm render. The same rationale applies to generated `templates/**` and `reports/**` content. GOTCHA observed in a wrapper script: `yamlfmt.sh <explicit-subdir>` IGNORES the exclude globs (it scopes to that dir); the exclusion only applies when run from repo root (`yamlfmt.sh --lint .` or the CI `yamlfmt -conf .yamlfmt -lint -dstar **/*.yaml`), so check the actual `yaml_fmt_check.yaml` invocation before treating a local subdirectory failure as a CI failure. (Note: whether to commit a rendered manifest at all is a per-team convention — some rollout-enablement PRs put the render in the PR DESCRIPTION only to avoid this entirely; if you DO commit it, add the exclude.)

48. **Never pre-quote a value that a chart template already pipes through `| quote`** — it double-encodes into an immutable field and wedges ArgoCD permanently. `cloudnative-pg` `storage-class.yaml` renders `StorageClass.parameters` with `{{ $value | quote }}`. A host-cluster values file that pre-wraps a param in single quotes (e.g. `"'true'"`) gets double-encoded into the literal string `'true'` (quotes included). Since `StorageClass.parameters` is immutable in k8s, the apply is rejected permanently → `ArgoCDApplicationSyncFailed` loop. Fix: use plain strings in values and let `| quote` add the quoting.

49. **rtk's read-only output CACHE poisons `helm template` after a chart edit — identical byte counts across different inputs is the tell.** Distinct from the truncation gotcha in #44: here the render is *complete* but STALE or wrong. Two observed shapes: (a) after editing a chart, a repeated `helm template` returns the pre-edit render (a newly-added alert group silently absent); (b) rendering a chart with `-f values.yaml -f host-clusters/<X>.yaml` returned ONLY the XRD — 1441 bytes, BYTE-IDENTICAL for two *different* `-f` files — masquerading as a chart bug where the Composition/EnvironmentConfig/Functions had vanished. Proof it was cache and not chart: `--show-only templates/composition.yaml` (a different command STRING = cache miss) rendered every template perfectly. Busting it: `RTK_DISABLE=1` alone did NOT always work, nor did piping; what reliably works is **changing the command string** — long-form `--values` instead of `-f`, plus `RTK_DISABLE=1 command helm …`. A third shape hits FILE output: the truncation marker `... (N lines truncated)` written INTO a redirected file produced a FALSE `yaml.ParserError` and a FALSE admission-policy "empty expression" dry-run rejection (pre-rtk-0.43.0; see the #44 update). Safest render path when validating a just-edited chart: `--output-dir`, or invoke helm from a Python `subprocess.run(capture_output=True)` which skips the hook entirely. Always sanity-check the render's LINE COUNT against a known-good baseline before trusting a clean grep.

50. **Concurrent `helm dep build` across worktrees that SHARE the default Helm cache silently truncates the render.** `HELM_CACHE_HOME`/`HELM_CONFIG_HOME`/`HELM_DATA_HOME` default to one shared location, so parallel dep-builds race the repo cache and the extracted-subchart `.tgz`: `helm template` then exits 0 with no stderr but emits only the first few manifests (istiod rendered 41 lines instead of 3844, dropping the Deployment and the pilot image). Not a chart defect, and indistinguishable from the rtk truncation in #44 by symptom alone. FIX: give each render an isolated cache — export all three `HELM_*_HOME` to a per-run temp dir, `helm repo add` the needed repos there, then `dep build` + `template`. Verified: the isolated re-render produced the full 3844-line output. Corollary: sanity-check render line count vs a known-good baseline before trusting a "clean" grep result.

51. **Read-only "does this old tag still render?" proof: `git archive` + a fully isolated Helm home + `--skip-refresh` — NEVER `git checkout`/`worktree add` to reach the tag.** Extends #50 (isolated cache) with the two things that make an ANCHOR-TAG render actually work. (a) `helm dep build` at an old tag ABORTS under the default `HELM_REPOSITORY_CONFIG` because an unrelated STALE repo entry in the shared config fails to refresh (a long-dead `bitnami-labs` URL now 404s). The subchart is then never downloaded and `helm template` returns ~2 lines — which reads as "the anchor tag does not render" when the tag is fine. Pass `--skip-refresh`, and point `HELM_CACHE_HOME`/`HELM_REPOSITORY_CACHE`/`HELM_REPOSITORY_CONFIG` all under one scratch dir so the stale global config is not consulted at all. (b) Reach the tag with `git archive <tag> charts/ | tar -x -C $SCRATCH` — it needs no working-tree mutation, so it is safe to run against a checkout someone else is using; `git checkout <tag>` and `git worktree add` both touch shared state. An observed anchor render produced 3819 lines and `pilot:1.29.1-distroless`; record the expected baseline for the tag under test. **The LINE COUNT is the anti-vacuity guard** — a truncated or dep-less render also exits 0, so compare against a known-good baseline before concluding anything from a grep (same tell as #44/#49/#50).

52. **A ConfigMap-only value change is INERT until the consuming pods restart, and GitOps reports it as fully applied — worse, it then drifts NODE-BY-NODE as pods restart individually**: When a value reaches containers via `envFrom: configMapRef` (or a mounted ConfigMap read at startup) and the pod template carries NO `checksum/config` annotation, merging the change flips the ConfigMap while every running pod keeps the old value. ArgoCD reports `Synced`/`Healthy` throughout, so the app-level signal is actively misleading. **Confirmed live**: the ConfigMap value flipped between two syncs 33 seconds apart while `oldest_pod_start` was unchanged on both samples. **The inertness is not stable**: from that moment every pod that restarts for any unrelated reason (node rotation, scale-up, the next upgrade) comes up with the NEW behaviour while unrestarted pods keep the old one — a DaemonSet silently ends up in mixed state across nodes. Benign on dev; on prod the rollout MUST include an explicit `kubectl rollout restart <workload>` so all replicas flip together. Two fixes, in order of preference: add a `checksum/config` pod-template annotation so the value change re-rolls the workload automatically, or make the explicit restart a mandatory step in the runbook. Detection predicate: the ConfigMap's `resourceVersion` moved but no pod's `startTime` did.

53. **A "hold"-style label is ADVISORY unless the merge automation names it — and the gates that actually hold are structural.** Merge-automation configs gate on specific label NAMES, so the label a team habitually applies for sequencing may block NOTHING: manual merge bypasses it and a concurrent "merge when ready" still makes the PR eligible. **If the ordering is load-bearing, enforce it structurally: stack the branches so the second is BASED on the first, or add a required status check.** When you cannot stack (the leading PR does not exist yet), the strongest unilateral gate is to **open the follower as a DRAFT — the forge itself refuses to merge a draft.** Layer it: draft (hard) → the blocking label the automation actually reads → **a COMMENT containing an agreed marker**, which survives someone stripping the label. Note automation ignore-blocks commonly support `comment_substrings` but NOT `pr_body_substrings`, so the marker must be a comment, not the PR body. **Separate trap, and it is silent: `gh pr create --label "<name>"` with a label that does not exist FAILS `not found` and ABORTS THE WHOLE CREATE, leaving no PR behind.** Always **create-then-label**, never `gh pr create --label`, and **re-read with `gh pr view --json labels` after adding** — a failed `--add-label` exits quietly enough to miss.

54. **A chart-lint workflow can auto-detect `charts/<chart>/ci/lint-values.yaml` — an exact filename convention — and pass it as `-f` to `helm template`, `helm lint` AND `polaris --helm-values`.** This is a workflow convention, not built-in Helm behavior; verify the workflow implements it. So a chart whose base `values.yaml` intentionally fails to render (e.g. `crossplane-compositions`, where `.Values.cloud` is `required`) can ship a minimal `ci/lint-values.yaml` fixture and keep lint green without masking real errors. **The fixture must be checked**: confirm it renders real objects, not nothing — a fixture that renders an empty document passes every gate while proving zero.

55. **Helm chart SCHEMA-DESIGN principles — make invalid states unrepresentable, then fail fast.** For a single-cloud composition chart: (1) **One discriminant, not twin booleans.** `cloud: aws|gcp` per cluster instead of `compositions.aws.enabled` + `compositions.gcp.enabled` — one field cannot hold two values, so a dual-cloud cluster becomes structurally impossible rather than merely discouraged. Derive everything downstream from it: which Composition renders, `XRD.enforcedCompositionRef: xrole-<cloud>`, and which `EnvironmentConfig` facts are emitted. (2) **Fail-fast on a required selector**: `{{ if not (has $c (list "aws" "gcp")) }}{{ fail … }}` in `_helpers.tpl` gives a clear render-time error instead of a silent empty render — and when the required value makes base `helm template` intentionally fail, ship `charts/<c>/ci/lint-values.yaml` (see #54) so CI stays green. (3) **Values as single source of truth**: generate the CRD CEL enum/allowlist from `keys(profiles)` + `keys(packages)` so adding a capability is one values entry and the SAME object feeds the composition function input, the XRD CEL, and the Kyverno allowlist — no cross-chart drift. (4) **Passthrough over re-mapping**: `toYaml (index $ec $cloud) | nindent 2` means adding a fact is one values line, no template edit; keep the flat data-key names the consumer already reads so proven template bodies stay untouched. (5) **Parameterize ONE template on the discriminant** instead of N near-identical per-variant files. (6) Prefer `required` + explicit error over a silent default for any security-relevant selector. (7) README and PR body must show the SAME example manifest, its rendered fan-out, and explicit "to add a thing, do this" steps. **Conditional sync-wave simplification**: because only the active block is emitted there is no cross-cloud key leak, and the intra-app sync waves could be dropped safely (the crossplane CORE app registers the `apiextensions`/`pkg` CRDs and app-of-apps sequences it first, so the intra-app waves only ordered instances against each other; cross-refs self-heal via ArgoCD bounded retry + SSA + `SkipDryRunOnMissingResource`).

56. **Any claim about an EFFECTIVE value in a layered values stack must merge ALL layers, in order — checking a subset produces confident false "unset" findings.** The failure is symmetric and both directions are common: reading a flag off CHART DEFAULTS when a host-cluster layer sets it everywhere, and reading it off the host-cluster/global/environment layers while a PROVIDER-scoped layer sets it in the middle of the stack. **Enumerate the stack from the deploying Application's own `valueFiles` list, not from memory**, and resolve per target. **And check what CONSUMES the key before calling a change inert** — a provider/discriminant key is typically read far beyond the helper you found it in (certificate issuers, DNS objects, preview ApplicationSets, and any `if eq` branch in any chart). Same failure mode a review bot hits from the other direction (`learnings-code-review.md`). A chart default describes the standalone render, not the deployed umbrella; a no-change diff using defaults can therefore be vacuous. For a chart that already nests its values under its own name, an umbrella needs BOTH levels: `<chart-name>: {<valuesKey>: {components: {<comp>: {...}}}}`. Document and label chart-local and umbrella examples separately. Pasting a chart-local security feature into the umbrella at the wrong depth silently produces no policy and no shadow-mode telemetry. Prove enablement with the real umbrella stack, not the subchart alone.

57. **Chart root files OUTSIDE `templates/` are inert under an ArgoCD Helm source only if you PROVE it — four checks, all of them.** A synthetic CR under `charts/<chart>/tests/` is not applied merely because the Application's `source.path` points at the chart root, but "not applied" is a claim about the whole repo, not about Helm. Prove it with: (a) repo-wide exact **and** generic apply/glob searches for automation that might pick the path up; (b) a `templates/` search for any `.Files` consumer; (c) a zero-count of the target Kind in `helm template` output; (d) a base-vs-head render hash comparison. Any one alone is insufficient.

58. **A stacked PR needs explicit repair and fresh validation after its parent squash-merges.** The parent lands under a new SHA; the child may retain duplicate-content commits, undo later review fixes, or roll back an image tag that a bot advanced on the target branch. A 3-dot diff can therefore include the parent as well as the child. Replay only the child with `git rebase --onto origin/<base> <old-parent-tip> <branch>`, then retarget the PR and update it with `--force-with-lease`; alternatively rebuild from the target and re-apply only the child delta. Verify `git merge-base --is-ancestor origin/<base> origin/<child>` and a 2-dot diff containing exactly the intended files. A plain `git rebase origin/<base>` may replay the already-squashed parent. A measured rebase had zero conflicts, including the lock file, and `uv lock --check` passed without regeneration; do not hand-edit unrelated pre-parent file states that the rebase should update. Before the parent lands, the child must still be self-consistent: carry required parent settings until the target contains them. **Workflow selection is a separate gate:** with `on.pull_request.branches: [main]`, a feature-branch base can run metadata/security checks while chart lint, unittest, release, formatting, policy and automated review skip. Validate locally and state this in the PR body. Check matrix selection with `echo <changed-path> | bash ./helpers/scripts/build_chart_matrix.sh unittest` and a negative-control chart without its enablement flag. In a runtime-matrix workflow, `createUnittestWorkflow` in `workflows.yaml` may be the only required change; `helpers/scripts/workflow_generator.sh` can validate directories without generating workflow files. Verify the repository implementation and confirm chart jobs run after retargeting.

59. **Four `helm-unittest` harness gotchas hit adding the first tests to a chart (plugin v1.1.1).** (1) `failedTemplate.errorPattern` is a **regex evaluated against the raw Helm error** — do NOT escape quotes (`\"` matches a literal backslash); `must be "aws" or "gcp"` works as-is inside a single-quoted YAML scalar. (2) **Suite-level `set:` works and is the right place for a required value** (e.g. a cloud discriminant); a per-test `set` merges over it. (3) **`set` has `helm --set` MERGE semantics for MAPS, so you CANNOT replace a catalog map to test generation-from-catalog** — instead ADD a fixture entry and assert the generated enum/CEL/`maxItems` all move. **LISTS ARE REPLACED**, so `set: packages.standard: [kms, bogus]` does exercise a catalog-integrity `fail()`. (4) Combine with the mutation-coverage discipline in `learnings-crossplane.md` — a suite that passes against broken input is worse than none.

60. **A CI step that loops over optional per-chart scripts must NOT gate on the EXEC BIT — `[ -x "$script" ] || continue` turns a script that EXISTS but lost its mode into "not found", and the job stays permanently GREEN having run zero tests.** One forgotten `chmod +x` is enough. **Fix: glob regardless of `-x` and invoke `bash "$script"` — existence is the trigger, not the mode.** Two related traps in the same block: (1) `echo "::endgroup::"` after a bare `"$script"` call is **UNREACHABLE** under GitHub's default `bash -e {0}` shell, so failing output renders inside a group that never closes and stays COLLAPSED in the Actions UI — capture with `bash "$s" || rc=$?`, close the group, THEN `exit $rc` with an `::error::` line; (2) shipping a `tests/*_behaviour_test.sh` is not enough for it to run at all — a matrix builder such as `helpers/scripts/build_chart_matrix.sh` can drop charts without `createUnittestWorkflow: true` from the unittest matrix entirely. **Verify a new test actually ran by grepping the job log (`gh run view --job <id> --log`)**, because the step exits 0 either way.

61. **A pull-through cache changes both image paths and authentication, and may be empty until first use.** Set `image.registry` to the cache host/path and keep `repository` as `<dockerhub-org>/<image>`. Authenticate to the CACHE, not Docker Hub: an `imagePullSecrets` credential or an appropriately configured node identity must be able to read every mirrored image. Verify permissions when migrating images; cloud-provider identity alone does not establish access to an arbitrary cache. Check the upstream registry for a tag before treating an empty cache as a failure. A same-named repository without the cache prefix may be a stale non-cache leftover. If a mirror job refreshes mutable tags by deleting cached images and forcing redeploy, a digest resolved minutes earlier may no longer represent the tag; inspect that job before assuming freshness.

62. **Running repo gate scripts as a base-vs-head control — three ways to produce a difference unrelated to your change, and one way to leak an untracked file into your commit.**
    - **A `--changed-files auto` mode is NOT comparable across a base/head switch, and the vacuous result LOOKS CLEAN.** On a REBASED branch `merge-base == origin/main`, so `auto` resolves to ZERO targets and still prints a clean-looking *"differing: none"*; across a `git stash` it sees no changed files and audits EVERYTHING, so the two sides differ by thousands of lines for a reason unrelated to the change. **Run BOTH sides with the SAME EXPLICIT changed-files list.**
    - **Policy/lint tools often emit findings in NON-DETERMINISTIC order** (especially inside a container), so a byte-compare of two runs over the same tree false-fails. Compare the **SORTED MULTISET of finding lines** per section, normalising any path/timestamp header — never as an ordered diff.
    - **`git ls-files` reads the INDEX and will LIE to you about whether a file is tracked** — it reports your own just-`git add`-ed file as tracked. **Check against the merge-base: `git ls-tree <merge-base> --name-only <path>`.** This matters because a mandatory `helm dep build` writes `Chart.lock` files for charts whose lock is untracked, and a blanket `git add -A` then sweeps them into an unrelated commit. **Stage by explicit path; never by wildcard** — the same shape leaks credentials at #27. This is the concrete detection recipe behind `learnings-crossplane.md`'s "stage by explicit path" rule.

63. **`helm-unittest` suite files MUST keep the snake_case `*_test.yaml` name — the filename is load-bearing for DISCOVERY, and renaming drops the suite while CI stays green.** The plugin's default glob is `tests/*_test.yaml` unless the repository configures a different discovery pattern. Renaming to kebab-case silently drops the suite: **58 tests / 5 suites → 41 tests / 4 suites, and `helm unittest` still exits 0 / green** — 17 tests gone with no signal. A kebab-case convention for manifests must not override filenames parsed by the test runner; check discovered test and suite counts after any rename.

64. **Any `.Capabilities.APIVersions`-gated template is INVISIBLE to a bare `helm template`, so an absence assertion over one proves nothing about the live cluster.** `charts/crossplane/templates/podmonitor.yaml` is gated on `.Capabilities.APIVersions.Has "monitoring.coreos.com/v1/PodMonitor"`, so a plain render **without `--api-versions` produces ZERO PodMonitors on EVERY cluster** even where they are live. A **fleet render-DIFF harness stays valid** (the suppression is uniform on both sides), but any per-cluster claim that "`metrics.podMonitor.enabled: true` works" is VACUOUS unless you re-render with `--api-versions 'monitoring.coreos.com/v1/PodMonitor'`. A discriminating proof pair: with the flag → 2 PodMonitors; with the flag **and** `--set metrics.podMonitor.enabled=false` → 0. (Related: `learnings-argocd.md` — ArgoCD does not pass `--kube-version` either.)

65. **`helpers/scripts/yamlfmt.sh --lint <path>` can PASS while the bare repo-wide `yamlfmt.sh --lint` — when that is what CI runs — FAILS on the same file. Match CI's invocation before pushing.** Failure mode observed: commenting out a YAML key leaves its comment block orphaned, and yamlfmt re-indents orphaned comments to the indent of the **preceding real key**, silently reparenting them under a sibling block. Fix: place a commented-out block **ABOVE a real sibling key at the same level**, never trailing the last key.

66. **A required `workflow_call` input interpolated into a PATH-FILTER GLOB makes the whole build FAIL OPEN, and an independently gated deploy may still run.** Shape: a reusable workflow builds `infrastructure/config_${{ inputs.environment }}.json` and feeds it to a paths-filter action. A wrong or empty value names a nonexistent file, the filter returns **false**, the build job is **SKIPPED**, and the observed deploy job still ran; inspect its `needs` and `if` conditions rather than assuming skipped builds always block deploys — confirmed on a real run where `build-image: skipped` sat alongside `deploy: success`, and the deploy then applied Terraform referencing an image tag that was **never built**. **`required: true` on a `workflow_call` `type: string` input does NOT reject an empty string — only an omitted one.** Note the asymmetry that hides it: on `workflow_dispatch` an `if: … || github.event_name == 'workflow_dispatch'` short-circuits the filter so the build fails loudly; only the push/`workflow_call` path is silent. **GENERAL RULE: never let a user-supplied value become part of a path-filter GLOB without validating it first — a glob that matches nothing is indistinguishable from "nothing changed".**

67. **Turning a required status check into a MATRIX renames it and silently blocks every merge.** A ruleset requires the check name exactly (`<service>-tests`); a matrix renames it to `job (x)`. **Keep the bare name for one leg:** `name: ${{ matrix.x == 'a' && 'job' || format('job ({0})', matrix.x) }}`, plus `fail-fast: false`. **The converse is the real reviewer trap: the OTHER legs are then NOT required checks**, so a regression that only the non-required leg catches does not block merge. Say so explicitly rather than letting a green matrix imply coverage. Read the live rules via `gh api repos/<org>/<repo>/rules/branches/<branch>` — the classic branch-protection endpoint 404s on rulesets. Moving the bare name to a new leg can make a migration self-contained without a human ruleset edit, and retiring the old leg becomes a deletion. **The check name does not prove which leg ran:** selecting a wrong EXISTING leg still emits the required name and can gate the wrong dependency group; only a typo or a removed matching leg leaves it missing. Expand the matrix against live rules and test both wrong-existing-leg and missing-leg mutations. Also assert the intended commands execute: an inverted `mypy` condition can leave the required lint check green without type checking the gated group.

68. **Job logs are unavailable until the WHOLE run completes, even for an already-finished job.** `gh run view --job <id> --log` and `/actions/jobs/<id>/logs` both return **404 `BlobNotFound`** while any sibling job is still running. For live evidence from a long deploy pipeline, read the **build system's own logs** instead (e.g. `gcloud builds list` + `gcloud builds log <id>`), whose substitutions also show the exact parameters the job passed.

69. **Two ways a `pre-commit` gate passes VACUOUSLY on an empty file list.** (a) **pre-commit 4.5.1 treats `--files` with zero following paths as "no explicit file list"** (`args.files` is falsy) and **falls back to staged files** — which on clean CI is nothing, so it exits green (`pre_commit/commands/run.py:168-177, 264-270`). (b) **GNU `xargs` invokes the command once on empty input unless `-r`, while BSD `xargs` invokes nothing** — so `git ls-files … | xargs pre-commit run … --files` is vacuous on both, by two different routes. **Guard the list explicitly whenever emptiness is possible.**

70. **A PR that touches ANY path in a deploy workflow's `paths:` filter OWNS every pre-existing drift in that workspace at merge time — whether or not it caused it.** Merging is itself the trigger for the apply, so an unrelated hand-edit that the apply will revert becomes a **merge gate for your PR**, not a follow-up: merging first and deciding later silently reverts it. Check the deploy workflow's `paths:` against your diff, then run a real plan for that workspace and read the destroys/removals before merging. The same shape propagates on the promotion to the release branch.

71. **For any Dockerfile- or build-config-touching PR, CHECK WHETHER AN IMAGE WAS ACTUALLY BUILT before calling it validated.** PR CI in many repos runs tests and lint but never builds the image, so the first real exercise of a build-arg change is the post-merge deploy. `gh api 'actions/runs?head_sha=<sha>'` settles it in one call. Then state the failure mode explicitly — if the deploy target runs the build **before** migrations and the infrastructure apply, a build failure is safe-by-ordering, and saying so is the difference between "unverified" and "unverified but fail-safe". An offline proxy for the install set is in `learnings-uv.md`.

72. **Cherry-picking a squash commit onto a release branch works even when its PARENT change is absent — but check for the parent by FILE CONTENT, not by ancestry.** When `dev` and `main` differ only on the line a hotfix touches, `git cherry-pick -x <dev squash sha>` applies cleanly onto a `--no-track` worktree off `origin/main`. `git merge-base --is-ancestor` is the WRONG check for "did the parent land", because in a squash-merge repo the parent arrives on the release branch under a **different SHA** — read the file (`jq` the key you care about) instead. Budget for the CI cost: a one-line config change still ran the **full** ~48-check suite, with the slowest job (~8-10 min) setting the floor.

73. **A break-glass `kubectl set env` on a Helm-managed Deployment is NOT reverted by re-applying Terraform or Helm.** helm v3's `createPatch` uses `strategicpatch.CreateThreeWayMergePatch(old, new, live)` (`pkg/kube/client.go:699`), so env entries that are present live and absent from **both** the old and the new manifest survive an upgrade — and `helm_release` with unchanged values does not upgrade at all. Revert explicitly with `kubectl set env … VAR-`. Useful for an emergency, dangerous as an undocumented state: nothing in the repo shows the override exists.
