## Operators & CRDs

1. **eBPF-based kprobes must be validated against all target kernel versions.** Kernel function names change across versions; mixed node pools can have different kernels. Before adding kprobes, check `/proc/kallsyms` on nodes of each kernel version in the target cluster. Applies to runtime security tools that hook kernel functions.

2. **ServiceMonitor `jobLabel` takes a label key, not a value.** `jobLabel: app` means "use the value of the `app` label on the Service as the `job` label in Prometheus." The Service must have that label set, or the resulting `job` is empty.

3. **Transient operator errors may self-heal.** External-API timeouts on operator reconciliation (e.g. a secrets operator hitting `i/o timeout` against its backend) can show CRs as unhealthy. Recheck after 5 minutes before escalating — most self-heal on the next reconciliation cycle.

## Policy engine patterns (Kyverno-style)

Policy engines deployed cluster-wide are a core platform capability. When onboarding new tools or infrastructure, proactively consider whether policies can enforce safety invariants, gate rollouts, or provide audit visibility. Three common patterns:

- **Guard policies** — prevent unsafe config (e.g. require runtime security agents to start in monitor mode, not enforce).
- **Mutation-assisted rollouts** — inject labels/annotations at admission (e.g. service mesh enrollment, sidecar injection).
- **Audit policies** — track compliance via a policy reporter (e.g. missing probes, missing resource requests).

4. **Kyverno ValidatingPolicy background scanning is enabled by default; set `evaluation.background.enabled: false` explicitly to disable it.** This corrects the earlier claim here that existing resources were unscanned unless `evaluation.background.enabled: true` was set. In the CRD inspected on 2026-08-22, `kubectl get crd validatingpolicies.policies.kyverno.io -o json` showed `spec.evaluation.background.enabled` with `default: true` on every served version (`v1`, `v1alpha1`, `v1beta1`), described as "Optional. Default value is \"true\"." A policy with `spec.evaluation: {}` therefore still produced background-scan results. For missing results, check wildcard API versions (#12), controller RBAC (#13), reports-controller age (#22), and whether the policy can read its resources (#13).

5. **Policy Reporter `uncontrolledOnly` must be `false` to see pod reports.** By default, Policy Reporter filters to "uncontrolled" resources (not owned by a ReplicaSet/Deployment). This hides nearly all pod-level policy results since most pods are Deployment-managed. Set `uncontrolledOnly: false` in `sourceFilters`. Also add `KyvernoValidatingPolicy` to `sourceFilters.selector.sources` to include the CEL-based policy type, and enable `periodicSync` for timely report refresh.

6. **MutatingPolicy for zero-disruption rollouts.** When onboarding infrastructure that requires pod-level labels or annotations (service mesh enrollment, sidecar injection, runtime-security namespace labels), use a MutatingPolicy to inject at admission rather than hot-labeling running pods. This piggybacks on natural CI/CD rollout cadence and avoids disrupting existing workloads. Pair with a ValidatingPolicy (audit + background) to track progress in the policy reporter.

7. **Admission-controller discovery-cache restart advice applies to the deprecated Kyverno ClusterPolicy path; it is superseded for CEL ValidatingPolicy at v1.17.1 by #11.** The historical symptom when a policy preceded its CRD was CREATE/UPDATE denial with `resource <name> not found in group <group>/<version>`, even with `failurePolicy: Ignore`, because the webhook denied the request rather than failing to answer. The recorded workaround was:
   ```bash
   kubectl rollout restart deployment <policy-engine>-admission-controller -n <policy-engine-ns>
   ```
   That workaround concerned first enablement of a CRD-based component; installing its CRD before its policy avoided the discovery-cache problem. CEL ValidatingPolicy compilation does not require that discovery, so do not apply the restart advice to that engine.

## CEL ValidatingPolicy (Kyverno-style CEL policy engines)

8. **A policy engine reporting zero results for a resource kind is indistinguishable from that policy passing on every instance — treat "no results" as unverified, never as a pass, and check the controller logs.** The acceptance check for any new policy guard is not "no violations show up"; it is "the report actually lists the kinds and objects I expect it to have evaluated." A silent scoping bug, an RBAC gap, or a version-matching failure all produce the identical, reassuring-looking empty report as a policy that is working correctly and finding nothing wrong.

9. **Kyverno ValidatingPolicy fail-open/fail-closed behavior splits three ways; `failurePolicy: Ignore` does not make validation-expression errors fail open.** Source-verified at v1.17.1 and unchanged at v1.18.2:
    - **Validation-expression error with `validationActions: [Deny]` rejects the write.** In `pkg/webhooks/resource/vpol/handler.go:144-157`, `admissionResponse()` appends both `RuleStatusFail` and `RuleStatusError` to `errs` when `policy.Actions.Has(Deny)`; `pkg/utils/admission/response.go:11-14` sets `Allowed: err == nil`. A failed `resource.List()` lookup caused by API downtime, RBAC changes, or an XRD being removed/renamed therefore denies matched writes. At Audit, neither outcome blocks writes; evaluation errors can leave no AdmissionReport.
    - **A matchCondition error under `failurePolicy: Ignore` is a non-match:** the request is admitted with no report. Match conditions and validations do not fail the same way.
    - **Webhook invocation failure (unreachable or timeout) fails open when `forceFailurePolicyIgnore` is enabled.** The invocation setting does not protect against an evaluation error inside a webhook that answered.
    - **Before Audit-to-Deny promotion, verify the availability cost of every live lookup** (`resource.List`, `globalContext.Get`, or external API dependency). RBAC or API-pressure failures then block every matched write. `matchConditions` run before `variables`, so narrowly gating the policy prevents unmatched objects from reaching the lookup.
    - **Background-scan `skip` results can keep a liveness alert armed without proving any validation ran.** When `matchConstraints` select a resource but `matchConditions` return nil, `engine.go`'s `handlePolicy` emits `RuleSkip`; reports map `RuleStatusSkip` to `skip`, and `allowedResults` defaults to `pass,fail,error,warn,skip`. If Policy Reporter retains `skip`, an alert on `policy_report_result` without a status filter still has samples when zero objects satisfy the match condition. Filter status deliberately; #8's empty-report warning still applies.
    - Independent review lenses disagreed on this behavior until the upstream source resolved it. No matching upstream issue/PR was found as of 2026-08-10; that is a dated triage finding, not permission to auto-file.

10. **CEL authoring requires guards at every field level, explicit dynamic conversion for Kyverno extension results, and fixtures that expose error masking.** Compilation and evaluation need separate checks:
    - **`has()` guards only the last path element.** `has(object.spec.forProvider.tags)` errors if `spec.forProvider` is absent. Likewise, `has(x.status) && has(x.status.identity) && x.status.identity.ref == variables.claimed` still needs `has(x.status.identity.ref)`. A schema allowing `identity` without a required `ref` permits `result=error` / `failed to load context: no such key: ref`. Validation errors can be silently dropped on Audit but reject writes on Deny (#9). Label checks such as `has(object.metadata.labels) && k in labels && labels[k] != ""` short-circuit safely.
    - **Kyverno extension functions `resource.List`, `resource.Get`, and `globalContext.Get` return `any`.** List operations (`exists`, `filter`, `size`, `all`) need `dyn()` around those results. Missing conversion can fail compilation with `expression of type any cannot be range of a comprehension (must be list, map, or dynamic)` or evaluation with `failed to load context: no such overload: size`, depending on the extension path. See #21 for the working lookup and CLI loop.
    - **`exists()` masks another element's error when one element matches.** A half-populated object plus a matching sibling passes; the fault appears only when nothing matches, precisely on the intended violation path. A clean-pass/clean-violation soak is insufficient. Test the rendered policy for every cloud branch with match / mismatch / none-in-namespace / no-status / status-without-child / child-without-leaf / mixed fixtures. The mixed case proves masking. A recorded live soak with 68 passes and a negative control still missed the missing-leaf case. `spec.resources: []` in a CLI context file causes a spurious error; exercise the empty-list path using an object in a different namespace.
    - **Uniformly indent continuation lines in YAML `>-` folded CEL scalars.** Extra leading spaces can break folding and produce `spec.validations[N].expression: Invalid value: "" ... Syntax error mismatched input <EOF>`. `helm template` and `helm lint` pass; server-side registration dry-run catches this compilation failure. Successful compilation does not establish runtime evaluation correctness.
    - **`matchConstraints` on a kind select all objects of that kind cluster-wide.** Before promotion beyond Audit, add a provenance `matchCondition` (for example, a composition-resource-name annotation) to avoid blocking unrelated objects. Match conditions run before variables, bounding live lookup traffic to already-matching objects; one observed gate limited it to approximately 69 service accounts per cluster.

11. **A CEL-based ValidatingPolicy can compile and register successfully against an API group or CRD that does not exist yet; it does not match until requests for that GVR exist.** Verified for Kyverno v1.17.1: `pkg/cel/policies/vpol/compiler` compiles without consulting `MatchConstraints`, `pkg/cel/matching` compares admission attributes literally, and `kubectl diff --server-side` accepted a resource rule naming a nonexistent API group. This supersedes #7's discovery-cache assumption for the CEL engine. Prefer defensively over-matching kinds a future provider/CRD bump may introduce over guarding only those installed today; an absent kind cannot receive an unguarded request, while an unguarded future kind creates a gap. Re-check `kubectl api-resources` after every provider bump. Background scans can still log `no matches` for uninstalled kinds (#12); this does not prevent policy registration.

12. **Wildcard or mismatched API-version lists silently break Kyverno background scanning while admission can remain operational.** At admission, requests carry concrete versions; background scanning resolves each `(group, version, resource)` triple through the RESTMapper:
    - **`apiVersions: ["*"]` never maps and is skipped during background scan.** In one incident, 30 of 33 rendered triples were wildcards: one policy reported only on its concrete rule and two had never produced a PolicyReport. Reports-controller logs (`logger=validatingadmissionpolicy`) showed `failed to resolve kind for group <g>, version *, resource <r>` / `no matches for <g>/*, Resource=<r>`. Results confined to the one concrete rule uniformly across clusters point to rule-specific resolution; rule out RBAC, `resourceFilters`, and controller health before concluding that.
    - **Explicit lists also fail when a rule combines resources with different served versions.** A rule's `apiVersions` list applies to every resource in it. For example, `bucketpublicaccessblocks.s3.aws.upbound.io` served only `v1beta1` while five other legacy S3 kinds served `v1beta1` and `v1beta2`; bundling them invented `s3.aws.upbound.io/v1beta2/bucketpublicaccessblocks`.
    - **Derive concrete served versions from live CRDs and split rules wherever version sets differ.** Use `kubectl get crd <r>.<group> -o json | jq '[.spec.versions[] | select(.served) | .name]'`. Either group resources with identical version sets or use one rule per version containing only resources that serve it. In one provider installation, `iam.aws.{m.,}upbound.io` roles/rolepolicies and `cloudplatform.gcp.m.upbound.io` resources served `v1beta1`; legacy `cloudplatform.gcp.upbound.io` serviceaccounts served only `v1beta1`, while its IAM-member kinds also served `v1beta2`, requiring separate rules. Re-derive these sets for the installed provider version.
    - **Test exact triples, not independent unions of versions and resources.** The wildcard was originally chosen to prevent a version-split bypass when adding legacy and `.m` provider groups; it introduced a different coverage gap. Re-verify reporting after every `matchConstraints` change.
    - **An intentionally matched but uninstalled CRD still logs `no matches` at any version.** That is the expected discovery limit of defensive matching (#11), not a recurrence of the wildcard defect.


## Policy engine patterns (Kyverno-style) (continued)

13. **Grant custom-CRD read RBAC to all three Kyverno controllers: admission, background, and reports.** A matching ValidatingPolicy can evaluate admission requests with `WebhookConfigured=True` yet show `READY=false` / `RBACPermissionsGranted=False` and never scan pre-existing resources. `helm lint` and server-side dry-run both pass; neither verifies runtime RBAC completeness.
    - Add `get/list/watch` grants for custom groups such as `*.upbound.io`, `*.m.upbound.io`, `platform.example.com`, and `cilium.io/tracingpolicies`. Use the Kyverno chart's `backgroundController.rbac.clusterRole.extraResources`, `reportsController.rbac.clusterRole.extraResources`, and admission equivalent in `charts/kyverno/values.yaml`; let the chart produce aggregated ClusterRoles rather than adding a separate role to the policy chart. Inspect rendered `kyverno:{admission,background,reports}-controller:additional` roles.
    - **Group grants by policy family and ship them with the policy change**, even if policy and controller charts are separately version-pinned. When following a family-scoped layout, add a new `- apiGroups:` entry rather than extending one whose comment describes another family; retain the existing legacy-before-`.m` ordering, `resources: ['*']`, and `get/list/watch` shape.
    - **Unreadable resources produce `error`, not `fail`, so clean violation counts can conceal an inert policy.** Check each controller account with `kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<sa>`; for example, `kubectl auth can-i list <res> --as=system:serviceaccount:kyverno:kyverno-reports-controller`. Include a known-granted resource as a positive control so a `no` cannot mean the check itself is broken.


## Validation guard-script design

14. **A guard script that force-enables a feature must fail if no artifact renders and assert exact sets in both directions.** A warning on empty output permits broken helpers, renamed keys, or wrong values paths to ship inert safeguards while CI remains green.
    1. Assert equality of expected and actual artifact names; unexpected extras can reveal wrong-cloud or missing gates just as missing artifacts reveal broken templates.
    2. Keep a known-policy map from values key to rendered name. Error if `values.yaml` declares a `policies.*` key the guard does not verify, if a guard key is stale, or if no cloud's expected set covers a known name. A new default-off policy must not escape the check.
    3. Assert `validationActions` explicitly. For per-overlay Audit-to-Deny promotions, use a per-`(overlay, policy-name)` allowlist: `expected = ['Deny'] if listed else ['Audit']`, checked both ways. Accepting either action removes the protection; a mistyped overlay key already fails when the real overlay unexpectedly renders Deny.
    4. Negative-test missing / extra / wrong-action / unknown-key / brand-new-overlay-at-Deny cases. To exercise the extra-policy check itself, choose a policy without its own earlier render-failure guard, such as a required ARN that would fail first.
    - **Read the guard's own exit code.** A script writing `[FAIL]` to STDERR and `[pass]` to STDOUT can have its status hidden by `python3 guard.py 2>&1 | tail`; redirect stderr to a file and inspect `$?` directly.
    - **Force-enabled output is not deployed output.** Check actual actions separately with `helm template -f <overlay>`.
    - **Hardcoded exact sets couple chart and guard revisions.** Update them atomically; `guard@new + chart@old` fails even if PR CI on the merged change passes. A partial revert needs the guard reverted too. Making the expected set chart-conditional removes fail-closed coverage. Document that tradeoff and test temporal compatibility explicitly against both `HEAD` and the repository's resolved pre-change/default-base ref: decide whether backward compatibility or stale-key rejection is the contract.


## Operators & CRDs (continued)

15. **When a CRD schema declares default values for a field, the API server can materialize that default onto the live object even when your manifest omits it — and a GitOps reconciler that diffs the manifest against the live object will report a permanent, unfixable drift for that field.** Rather than reaching for a broad `ignoreDifferences` rule, render the CRD's own default explicitly in the source manifest for any narrow, no-op field — this keeps the rendered manifest byte-identical to the live object without changing runtime behavior, and avoids widening what the reconciler is blind to on that resource. A broad `ignoreDifferences` entry can mask a real drift on the same field later; an explicit default cannot. For example, Tetragon `TracingPolicy.spec.kprobes[].selectors[].matchBinaries[].followChildren` defaults to `false`; explicitly rendering `followChildren: false` in a network-connections policy removed the observed ArgoCD OutOfSync difference without changing runtime behavior.

## Policy engine patterns (Kyverno-style) (continued)

16. **CEL probe policies can exclude infrastructure sidecars that intentionally omit probes.** For policies such as `require-{readiness,liveness,startup}-probe`, use a CEL `variables` block containing excluded container names and skip those containers. Expose the list through Helm values, for example `policies.platform.require<X>Probe.excludedSidecarContainers`; a deployment can default it to `[alloydb-proxy]` and override it per environment. The values path and default are chart conventions, not built-in Kyverno behavior.

17. **`failurePolicy: Ignore` can leave brief mutation gaps during admission-controller restarts.** In one GKE node-pool rotation, the controller rescheduled at 08:41:08Z and 10 pods created at 08:41:09–10Z missed the ambient label. Ignore preserves pod creation while the webhook is unavailable. In that rollout, namespace-level ambient enrollment was the intended end state: ztunnel read namespace labels, so switching to namespace enrollment resolved the concern without increasing replicas or changing to Fail. That harmlessness depends on the namespace-level enrollment design; assess the required label's role before generalizing it.

18. **Upbound v2 family providers can install both namespaced `.m.upbound.io` and legacy cluster-scoped `*.upbound.io` groups using the same controller credentials.** A guard matching only the composition's namespaced output misses out-of-band managed resources under the legacy group. On two clusters, API discovery and server-side dry-run demonstrated an unguarded `iam.aws.upbound.io/v1beta1` Role without a permissions boundary and an authoritative `cloudplatform.gcp.upbound.io/v1beta1` IAM object. Match both groups or deny legacy CRDs through RBAC, then verify served-version coverage and background scanning (#12). Kubernetes labels do not become AWS IAM tags: an owner-attribution guard for AWS must assert `spec.forProvider.tags.owner`, not only a metadata label.

## Local policy evaluation

19. **Offline Kyverno fixtures need CRD discovery data; supply individual CRD documents and prove a positive match.** The recorded v1.17.1 `kyverno apply --resource <file>` path failed for provider/Crossplane kinds with `failed to map gvk to gvr ... no matches for kind` when the offline RESTMapper lacked their CRDs. `--context` / `--kubeconfig` did not enable discovery without `--cluster`, while `--cluster` ignored `--resource` and evaluated live objects instead. `kyverno json scan` handles `json.kyverno.io` policies, not `policies.kyverno.io` ValidatingPolicy.
    - **Later local fixtures used `kyverno apply <policy> --resource <r> --context-file <c> --crd-path <crd.yaml>` with CLI v1.18.2 (#21).** The CRD argument needs a file, not a directory. A `kind: List` file, as produced by `kubectl get crd A B -o yaml`, silently fails GVK mapping with `failed to map gvk to gvr … failed to get resource from <Kind>`. Split it into documents with `yq eval '.items[] | split_doc'`. Use the same CRD file for a known-matching positive control; a non-match alone cannot prove the harness works.
    - **Where local discovery is unavailable**, translating compatible CEL to native ValidatingAdmissionPolicy and server-side dry-run on a cluster with those CRDs provided empirical proof. If that would require an unauthorized mutation, use rendered group membership plus server-side registration dry-run (compilation only) and identical-CEL reasoning across groups; label those limits rather than claiming runtime proof.
    - **Render each policy separately:** `helm template --show-only templates/policies/<p>.yaml -f <overlay>`, checking return code and line count. The observed `rtk` Bash hook mangled `grep -c` / `wc -l` / piped grep on template output into bogus zero matches, and an embedded `function-go-templating` gotmpl block broke `yaml.safe_load_all` on a combined multi-document render. Include a policies-off fixture that renders zero.

## Operators & CRDs (continued)

20. **Restate disk exhaustion has distinct undersizing and snapshot-import leak signatures, with different remedies; readiness can miss both.**
    - **Undersizing:** a recorded incident on 2026-07-26 had three PVCs flat at 99.0–99.2% for about 12 hours. RocksDB L5→L6 compaction failed with `IO error: No space left on device`, pods exited 1, and shutdown timed out after 60 seconds (`Timeout waiting for graceful shutdown`). Usage was 3–5.7Gi against a 24Gi memory request, not an OOM. Compaction needs scratch space to free space, so near-full disks can deadlock without self-healing. Increasing `RestateCluster spec.storage.storageRequestBytes` from 12Gi to 64Gi resolved the capacity limit in the observed setup: its `standard-rwo` StorageClass used `pd.csi.storage.gke.io` with `allowVolumeExpansion=true`, allowing online growth. Verify those properties for the target StorageClass. The StatefulSet `volumeClaimTemplate` is immutable; use the operator's CR.
    - **Restart fallout can recover separately:** truncated snapshots across about 10 partitions produced `component file X.sst has unexpected size: expected 900530, actual 63111`. The 2-second retry loop recovered through log replay within roughly 30 minutes; do not delete snapshot objects merely because this transient error appears.
    - **Snapshot-import leak, observed on Restate 1.6.2 on 2026-07-29:** scaling replicas 3→5 bootstrapped both new pods to about 21GiB. One stayed flat at 22GiB while the other grew linearly at 1.45GiB/min to a 63GiB ceiling in 30 minutes. Three partitions hit `open failed due to rocksdb error: Invalid argument: Column family already exists`; each 30-second processor retry re-downloaded the full GCS snapshot, re-imported, and collided again, leaving orphaned import data. There were 121 imports for about 44 assigned partitions, roughly 77 redundant downloads. The leaking pod had only 42–44 open partitions versus 53–54 on the flat pod but used three times the bytes.
    - **Expanding `storageBytes` does not repair that leak:** the same growth continues to the new ceiling. The recorded recovery cleared the affected pod's RocksDB column-family state by wiping/recreating its PVC in a replication-2 setup; that recovery depended on replication, not merely on the error string. This remains an upstream-triage candidate, not an instruction to auto-file.
    - **Readiness hid both incidents:** pods reported `1/1 Running` and `up == 1`; ingress completion ratio only dipped from 1.000 to 0.981 against a 0.9 alert threshold, and sequencer append p99 stayed flat. Monitor disk-utilization slope and partition-processor stop rate rather than relying on pod readiness.

## CEL cross-object policy evaluation

21. **Use Kyverno's `kyverno.resource` library for cross-object CEL lookup, with `dyn()` on returned collections.** A working loop used cluster v1.17.1 with CLI v1.18.2 on 2026-08-10:
    - Variables: `variables: [{name: xroles, expression: 'resource.List("platform.example.com/v1alpha1", "xroles", object.metadata.namespace)'}]`; validation: `validations: [{expression: 'dyn(variables.xroles.items).exists(x, …)'}]`. Extension results are `any`; see #10 for the compile-time and runtime failures without `dyn()`.
    - **Registration and health do not prove evaluation:** lint, rendering, server-side registration dry-run, `READY=true`, and a registered webhook were all green while a policy produced 68 errors for 68 service accounts. A Kyverno extension policy stays on Kyverno's own webhook with `status.generated=false`; it is not compiled into native ValidatingAdmissionPolicy. See #9 for the three failure paths.
    - **Evaluate fixtures locally:** `kyverno apply <policy> --resource <r> --context-file <c> --crd-path <crd.yaml>`. Context files accept only `spec.resources` and `spec.images`; the CRD argument must name a file containing separate CRD documents (#19).
    - **The recorded `GlobalContextEntry.spec.kubernetesResource` attempt failed.** The entry had no status or useful logs; `Get()` returned null and subsequent `filter` / `size` operations failed with `failed to load context: no such overload: size`. RBAC was ruled out: all three controllers had `get/list/watch` on `*`, including the custom API group. Both JMESPath projections (`items[?…]` for a List and `[?…]` for a bare array) produced 69 hits locally yet failed live. That failed approach does not invalidate the working direct-resource loop.
    - **Do not diagnose empty printer columns as a fault:** GlobalContextEntry is cluster-scoped; `kyverno.io/v2alpha1` is deprecated in favor of `kyverno.io/v2`. `REFRESH INTERVAL` / `LAST REFRESH` read `.spec.apiCall.refreshInterval` / `.status.lastRefreshTime`, which apply only to `apiCall`; empty columns are expected for informer/watch-backed `kubernetesResource`.

22. **PolicyReport soak evidence needs controller-age and coverage checks; zero reports is not zero violations.** In one cluster, a policy had no reports across roughly 29 hours of Audit. All six policy-system pods (admission / background / cleanup / reports plus policy-reporter) had restarted together at 2026-08-12T01:42:44Z, and every PolicyReport regenerated about 25 minutes later. The cause was reports-controller staleness rather than a policy fault.
    1. Inspect `kubectl get pods -n kyverno -o jsonpath` for `startTime` and compare it with the ValidatingPolicy's `metadata.creationTimestamp`. Use the creation timestamp rather than merge time to establish policy age, then account for controller interruptions before treating the interval as a continuous soak.
    2. Assert each cluster's `pass` count equals the live number of objects that actually satisfy `matchConditions` (for example, claiming service accounts). Equality proves in-scope evaluation. A large `skip` bucket alongside passes can demonstrate correct gating, while a skip-only liveness signal is weaker evidence (#9).

## Operators & CRDs (continued)

23. **`Established=True` on an XRD/CRD proves health, not revision freshness.** An observed XRD satisfied establishment and a CEL cost-estimator check while still having a stale 29-value enum missing `object-store-read`: the feeding application was pinned to a deleted branch. The known-current cluster had 30 values. Diff the relevant live field against the intended source revision or a known-synced cluster; for example, inspect `kubectl get xrd <name> -o json | jq '…items.enum | length'`. Join the delivery-state evidence and schema requirement in the same validation pass; independent successful checks can otherwise conceal staleness.

24. **Admission-time image-signature enforcement requires legacy-image coverage, an explicit provenance claim, and a verified compliance rationale.**
    1. Inventory and manually sign valid images that have not been rebuilt within the signing window before enforcement. Adding signing to a deployment pipeline signs future pushes; already-running images may remain unsigned until an unrelated restart, node drain, or HPA scale-up makes enforcement reject them hours or days later. Roll out Audit → observe → Enforce per environment, scoped to the namespaces where application images run.
    2. Deploy-time signing avoids service-repository changes but proves "this pipeline deployed this digest," not "this digest was built from this source." Record the builder-to-deployer provenance gap and an owner for stronger follow-up attestation.
    3. Verify the cited compliance control before using it to fix scope. The recorded CASA / OWASP ASVS assessment found no explicit container-image-signing requirement; the closest cited controls were 14.1.1 (secure build) and 14.1.5 (configuration integrity). Treat that as a control-specific finding to verify against the applicable standard/version, not a universal audit mandate; supply-chain risk reduction is a distinct justification.
