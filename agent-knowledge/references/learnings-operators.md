## Operators & CRDs

1. **eBPF-based kprobes must be validated against all target kernel versions.** Kernel function names change across versions; mixed node pools can have different kernels. Before adding kprobes, check `/proc/kallsyms` on nodes of each kernel version in the target cluster. Applies to runtime security tools that hook kernel functions.

2. **ServiceMonitor `jobLabel` takes a label key, not a value.** `jobLabel: app` means "use the value of the `app` label on the Service as the `job` label in Prometheus." The Service must have that label set, or the resulting `job` is empty.

3. **Transient operator errors may self-heal.** External-API timeouts on operator reconciliation (e.g. a secrets operator hitting `i/o timeout` against its backend) can show CRs as unhealthy. Recheck after 5 minutes before escalating — most self-heal on the next reconciliation cycle.

## Policy engine patterns (Kyverno-style)

Policy engines deployed cluster-wide are a core platform capability. When onboarding new tools or infrastructure, proactively consider whether policies can enforce safety invariants, gate rollouts, or provide audit visibility. Three common patterns:

- **Guard policies** — prevent unsafe config (e.g. require runtime security agents to start in monitor mode, not enforce).
- **Mutation-assisted rollouts** — inject labels/annotations at admission (e.g. service mesh enrollment, sidecar injection).
- **Audit policies** — track compliance via a policy reporter (e.g. missing probes, missing resource requests).

4. **ValidatingPolicy requires `evaluation.background.enabled: true` to score existing resources.** By default, ValidatingPolicy only evaluates on admission (CREATE/UPDATE). Without background scanning enabled, the Policy Reporter UI shows no results for resources created before the policy was deployed.

5. **Policy Reporter `uncontrolledOnly` must be `false` to see pod reports.** By default, Policy Reporter filters to "uncontrolled" resources (not owned by a ReplicaSet/Deployment). This hides nearly all pod-level policy results since most pods are Deployment-managed. Set `uncontrolledOnly: false` in `sourceFilters`. Also add `KyvernoValidatingPolicy` to `sourceFilters.selector.sources` to include the CEL-based policy type, and enable `periodicSync` for timely report refresh.

6. **MutatingPolicy for zero-disruption rollouts.** When onboarding infrastructure that requires pod-level labels or annotations (service mesh enrollment, sidecar injection, runtime-security namespace labels), use a MutatingPolicy to inject at admission rather than hot-labeling running pods. This piggybacks on natural CI/CD rollout cadence and avoids disrupting existing workloads. Pair with a ValidatingPolicy (audit + background) to track progress in the policy reporter.

7. **Admission controller must be restarted after new CRDs are installed.** When a ValidatingPolicy watches a CRD-based resource (e.g. a custom resource provided by another operator) and the policy is deployed before the CRD exists, the admission controller caches resource discovery at startup. It will actively deny CREATE/UPDATE with `resource <name> not found in group <group>/<version>` — even with `failurePolicy: Ignore` (because the webhook is denying, not failing). Fix:
   ```bash
   kubectl rollout restart deployment <policy-engine>-admission-controller -n <policy-engine-ns>
   ```
   Only needed on first enablement of the CRD-based component per cluster. To avoid this entirely, ensure the CRD is installed before the policy that watches it.

## CEL ValidatingPolicy (Kyverno-style CEL policy engines)

8. **A policy engine reporting zero results for a resource kind is indistinguishable from that policy passing on every instance — treat "no results" as unverified, never as a pass, and check the controller logs.** The acceptance check for any new policy guard is not "no violations show up"; it is "the report actually lists the kinds and objects I expect it to have evaluated." A silent scoping bug, an RBAC gap, or a version-matching failure all produce the identical, reassuring-looking empty report as a policy that is working correctly and finding nothing wrong.

9. **A CEL-based admission policy engine's fail-open/fail-closed behavior can split three ways for the same policy, and a blanket "fail-closed" or "fail-open" claim is usually wrong for at least one path.** Verified in Kyverno's `ValidatingPolicy` at v1.17.1/v1.18.2, source-traced: (1) a validation-expression runtime error (e.g. a broken cross-object lookup) produces an error status that, when the policy's action is Deny, **rejects the write** — the admission-response builder treats a rule error the same as a rule failure when Deny is configured; (2) a matchCondition evaluation error under an ignore-on-invocation-failure setting is instead treated as **non-match** — the request is silently admitted with no report at all, which is the asymmetry that surprises people who assume matchConditions and validations fail the same way; (3) the webhook being unreachable or timing out is the only path actually governed by the "ignore vs fail" webhook-invocation setting — that setting does not cover an evaluation error inside a webhook that *did* respond. Consequence: before promoting any policy whose validation depends on a live lookup (a cross-object query, an external API call) from audit to enforce, verify explicitly that an RBAC change, API pressure, or a renamed/removed dependency on that lookup will now **block writes**, not silently pass them — enforcement mode inherits the live-lookup's own failure modes.

10. **Three CEL authoring traps recur across any CEL-based Kubernetes policy engine, and none of them are caught by `helm template`, `helm lint`, or a passing dry-run — only a live evaluation against real objects catches them.** (a) **`has()` only guards the single path element it's given** — a nested `has()` check on a deep field still errors if an intermediate parent field is absent, and a chained `has()` that checks two levels but then dereferences a third leaves that third level unguarded; the fix is a `has()` check at every level down to the actual leaf being read, not just the levels someone remembered to check. (b) **CEL extension functions that return a dynamic/`any` type (a generic "get related resource" or "get from cache" call) cannot be ranged over by list macros (`exists`, `filter`, `size`, `all`) without an explicit `dyn()` wrapper** — omitting it fails either at compile time ("cannot be range of a comprehension") or at evaluation time ("no such overload"), depending on which extension function is used, and both read as a policy bug rather than a syntax bug. (c) **`exists()` swallows a runtime error from any OTHER element in the same collection as long as one element matches** — so a policy that dereferences an unguarded field inside an `exists()` predicate can pass cleanly on a fixture with one healthy sibling object, and only errors out (converting a would-be violation into a silent error) when nothing else in scope happens to match. Build a fixture matrix that includes a "some objects healthy, one object exactly violating" case — a soak test with only clean-pass and clean-violation fixtures cannot see this.

11. **A CEL-based ValidatingPolicy can compile and register successfully against an API group or CRD that doesn't exist yet — it isn't rejected at creation time, it simply never matches until that CRD is installed.** Because the policy engine's admission-time compilation doesn't consult live API discovery, a matcher naming a not-yet-installed kind is a harmless no-op rather than a validation error. Consequence: prefer defensively over-matching (name kinds you expect a future provider or CRD bump to introduce) over minimally matching only what exists today — a matcher for a kind that never arrives costs nothing, while a kind that arrives with no matching guard is a real gap. Pair this with a standing note to re-check the live API resource list after every provider/CRD version bump.

12. **Wildcard or mismatched API-version lists in a policy's resource matcher fail in two different, both-silent ways depending on whether the wildcard is a literal `*` or an explicit list spanning resources that don't all serve the same versions.** (1) A literal `apiVersions: ["*"]` is silently **not enforced during background/periodic scanning** even though admission-time enforcement (which always sees a concrete version from the live request) is unaffected — because the background scanner has to resolve `(group, version, resource)` triples through the API server's REST mapping, and a literal `*` never resolves to anything. A policy can look fully operational (webhook registered, admission working) while having never produced a single background-scan result on any cluster. (2) Explicitly listing versions is not safe either: if one resource-matcher rule bundles several kinds that don't all serve the same version set, the rule names a `(group, version, resource)` tuple that no CRD actually serves for at least one of those kinds, which errors the same way and produces an incomplete background scan. **Fix for both: derive the served-version list from the live CRD (inspect `.spec.versions[].served`), pin concrete versions rather than wildcards, and split one matcher rule per version set rather than bundling resources that diverge.** The diagnostic tell for (1): every background-scan result belongs to the one concrete-version rule and none to any wildcard rule, uniformly across every cluster running the policy — that pattern rules out an RBAC or controller-health explanation and points specifically at version resolution.


## Policy engine patterns (Kyverno-style) (continued)

13. **A validating-admission policy engine that runs admission, background-scan, and reporting as separate controllers needs the CRD-read RBAC granted to all three separately — granting it to only the admission controller leaves the policy "ready" and enforcing on new writes while silently never scanning any pre-existing resource.** The failure is easy to miss because admission-time behavior looks completely correct: the webhook is registered, and writes are validated. Only background scanning of already-existing resources is blocked, and the missing-RBAC condition typically renders as an internal "not ready" / "permissions not granted" status rather than a visible error — `helm lint` and a server-side dry-run both pass regardless, because RBAC completeness isn't something either check verifies. When adding a policy that matches a new custom-resource group, grant the read RBAC to every controller (admission, background, reporting) in the same change, and verify with an explicit `kubectl auth can-i` check per controller's ServiceAccount, including one already-known-good resource as a positive control so a "no" can't be blamed on the check itself being broken.


## Validation guard-script design

14. **A validation/guard script that force-enables a feature to test an invariant must itself assert the artifact actually rendered — not just log when it didn't — and must check for both missing AND unexpected extras, in both directions.** A guard that only logs a warning when the thing it's testing produced zero output will pass in CI even if the underlying template broke entirely (wrong values path, renamed key, broken helper) and the safeguard it exists to protect shipped completely inert. The hardened contract: (1) assert set-equality between expected and actual rendered artifact names, not subset — an unexpected *extra* artifact (something rendered under the wrong condition, or force-enabled without its intended gate) is exactly as real a bug as a missing one, and a subset check lets it through silently; (2) derive the expected set from the same source of truth the templates read from, and fail if that source declares a key the guard doesn't know to check for — a new config key otherwise evades every check by construction; (3) when an artifact has more than one meaningful state (e.g. audit-only vs enforcing), assert the specific state explicitly rather than just presence, so a mode promotion that wasn't supposed to happen still fails the guard; (4) negative-test every direction deliberately (missing, extra, wrong-state, unknown-key) — a guard that has never been proven to fail is not proven to catch anything.


## Operators & CRDs (continued)

15. **When a CRD schema declares default values for a field, the API server can materialize that default onto the live object even when your manifest omits it — and a GitOps reconciler that diffs the manifest against the live object will report a permanent, unfixable drift for that field.** Rather than reaching for a broad `ignoreDifferences` rule, render the CRD's own default explicitly in the source manifest for any narrow, no-op field — this keeps the rendered manifest byte-identical to the live object without changing runtime behavior, and avoids widening what the reconciler is blind to on that resource. A broad `ignoreDifferences` entry can mask a real drift on the same field later; an explicit default cannot.
