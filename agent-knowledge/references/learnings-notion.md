# Notion Learnings

See also: `learnings-confluence.md` (the same class of lessons for the other wiki — rendering traps, safe edits, and when an update silently no-ops), `learnings-agent-workflow.md` (§"Docs, Reporting & Knowledge-Base Craft" — what to write; this file is only about the tool that writes it).

Markdown-rendering traps and safe-edit mechanics for the Notion MCP (`notion-update-page` / `notion-fetch` / `notion-get-comments`). Every entry is observed tool behaviour; page titles, ids and authors are generalized out.

## Markdown rendering traps

1. **Inline `` `code` `` inside `**bold**` renders as literal `****` — and the same happens inside `*italics*`.** Backticks in an italic closing line also emit `****`. **Fix: choose one or the other.** Put the bold on plain words and leave the identifier as bare code *outside* the bold span — write `**An undeclared NetworkPolicy is live.** \`name\` exists…` rather than `**\`name\` is live.**`. **Verify by re-fetching the page after writing: the raw markdown round-trips, so the stray `****` is visible.**

2. **A bare `+` between two inline code spans renders as a BULLET character.** Use the word "and"/"plus" between code spans. Combined with #1, the working rule for footer/caption lines is: **drop inline code entirely from italic lines, and never put a bare operator between two code spans.**

## Safe editing

3. **Never use `replace_content` to delete a section — it destroys author edits.** Delete a whole section with `update_content` by anchoring `old_str` from the section heading **THROUGH the next heading**, and setting `new_str` to just that next heading. This avoids an empty-string `new_str` and keeps the boundaries exact. **Batch low-risk plain-text anchors separately from backtick-bearing ones**, so one bad anchor cannot fail the whole call.

4. **`update_content` matches on PLAIN TEXT and preserves the underlying rich-text ANNOTATIONS, so a replacement that only changes markdown markers is a SILENT NO-OP.** Stripping `**bold**` from around `` `code` `` returns success, `page_last_edited_at` does not move, and the fetch is unchanged — and re-adding the backticks re-inherits the bold. **Only a real TEXT change sticks**; fixing bold-wrapped inline code otherwise needs a manual edit in the UI. ⚠️ **`notion-fetch` can return a CACHED snapshot with an identical timestamp right after an update — verify with `page_last_edited_at`, not just by reading the content back.**

5. **Changing a `<table>` opening-tag ATTRIBUTE (e.g. adding `fit-page-width="true"`) REBUILDS the table and re-IDs its cell blocks, ORPHANING any block-anchored comment thread inside it.** The thread data survives — still fetchable by discussion id — but it **drops off the page's discussion list and is not re-anchorable via MCP.** **Check tables for comment anchors BEFORE editing table tags, and warn the user instead of editing if a thread is anchored inside.**

6. **Targeted `update_content` search/replace does NOT orphan discussion anchors on SIBLING blocks — only #5's structural rebuild does, and only an edit whose `old_str` OVERLAPS the anchored block is dangerous.** Verified on a reviewed page: edited 4 `Notes` cells in a table whose last row carried an anchor, replaced a whole 4-column table with a 2-column one, and deleted 6 sibling list items — **all 5 discussions survived intact**, because an anchor lives on the specific row/paragraph block. ⚠️ **Always list anchors FIRST with `notion-get-comments include_all_blocks:true AND include_resolved:true` — resolved threads still hold anchors and do not appear in the default listing**, so the default view will tell you a page is safe to edit when it is not. `include_all_blocks` returning only `{suggested_edits_status}` means **zero** discussions, i.e. no block is anchored and tables/diagrams are safe.

7. **A paragraph carrying an INLINE comment is stored as a RUN of adjacent `<span discussion-urls="…">` segments all sharing one discussion URL — editing it piecemeal leaves orphan segments concatenated with no spaces (the classic "mangled paragraph").** Fix: fetch with `include_discussions:true`, copy the **entire span run verbatim** as one `old_str`, and replace with plain text. Never guess an anchor. Use `\n` in `new_str` to split into two blocks. Note the anchored discussion then **disappears from the page entirely** (not merely unresolved) once its spans are gone — confirmed via `get_comments include_resolved:true`. `replace_content` is not needed for this.

8. **Structural edits to a table OR a mermaid diagram silently orphan comment threads anchored inside — #5 generalised beyond table attributes.** Notion rebuilds the block and reassigns cell/block IDs; the comments survive but detach from the page and **MCP cannot re-anchor them**. Cost two reviewer threads on one page (one from adding `fit-page-width` to a commented table, one from rewriting a diagram a comment was anchored to). **Run `notion-get-comments --include_all_blocks` BEFORE any table/diagram edit on a reviewed page, and skip or escalate the specific commented block.**

9. **Code-block display mode (code vs PREVIEW) is NOT settable through the write path — preview is UI-only, per block.** Tested by writing ```` ```mermaid {preview="true"} ```` via `update_content`: Notion silently drops the attribute on save and the fence round-trips as plain ```` ```mermaid ````. The enhanced-markdown spec agrees — code blocks accept only a **language tag**, no attribute list (unlike markdown blocks, which take `{color=…}`). Do not promise a user a rendered diagram you cannot set.

10. **`update_content` anchors containing backticks, `**bold**` and inline markdown LINKS DO match reliably — the real failure mode is STALE CONTENT after a concurrent author edit, not anchor normalisation.** ~40 replacements across two pages matched with zero normalisation failures, which supersedes earlier page-specific "anchors with backticks don't match" folklore. Two residues to clean up in a final pass: deleting a whole bulleted list by replacing each bullet with `""` can leave a stray `.` text block where the last bullet was, and the now-empty section heading plus its `---` separators survive. Fetch after the batch and sweep.
