## Ambient mode architecture

1. **SUPERSEDED IN PART by #196 — Revision canaries do not apply, but surge rollouts temporarily run two ztunnel processes on one node.** **ztunnel and istio-cni are node-level DaemonSets, not per-workload sidecars -- they cannot run two versions side by side on the same node, so revision-based (canary) upgrades do not apply to them.** Revision-based/canary upgrades work for istiod and waypoint proxies because those are per-workload or per-namespace resources; ztunnel and istio-cni are one DaemonSet per node, and a canary rollout would require two versions coexisting on the same node, which the architecture does not support (true since ambient's 1.24 GA and unchanged through 1.29.x). Treat data-plane (ztunnel + istio-cni) upgrades as an in-place DaemonSet rolling update, gated separately from the istiod control-plane upgrade rather than folded into the same canary mechanism.

    **Full evidence and detail:**

    **SUPERSEDED by #196 — Revision canaries remain inapplicable, but surge rollouts temporarily run old and new ztunnel processes on the same node.** **Istio ambient mode is fundamentally different from sidecar mode for upgrades**: ztunnel and istio-cni are node-level DaemonSets that CANNOT run two versions simultaneously on the same node. Revision-based (canary) upgrades only apply to istiod and waypoint proxies. Never recommend revision-based upgrades for ztunnel or CNI.

2. **Ambient's packet-interception mechanism changed from TPROXY to iptables REDIRECT at 1.24 -- that change is why enrolling a namespace with running pods resets their TCP connections.** Pre-1.24 ambient used TPROXY, which preserves already-established connections via conntrack when interception activates mid-connection. 1.24+ uses REDIRECT (NAT), which does not: enrolling a namespace live (applying `istio.io/dataplane-mode=ambient` to a namespace with pods already running) invalidates existing NAT state and resets open TCP connections during the window before ztunnel becomes the intercepting path. Prefer per-pod gradual enrollment -- label pods before they start, or roll them shortly after labelling the namespace -- over a bulk namespace-label flip against a live, traffic-serving namespace.

    **Full evidence and detail:**

    **Ambient namespace enrollment causes traffic disruption**: Labeling a namespace with `istio.io/dataplane-mode=ambient` while pods are running causes iptables REDIRECT injection that resets existing TCP connections. The race between redirect injection and ztunnel readiness creates a ~1-2 minute disruption window. Recommend per-pod gradual enrollment with rolling restarts instead.

    **Full evidence and detail:**

    **Istio 1.24+ uses REDIRECT (NAT) instead of TPROXY**: Pre-1.24 used TPROXY which preserved established TCP connections via conntrack. Post-1.24 REDIRECT invalidates NAT state, resetting existing connections during enrollment.

## mTLS and metric semantics

3. **ztunnel is an L4-only proxy -- it has zero visibility into HTTP status codes, paths, or any request-level data, and no ambient deployment gets L7 metrics without a waypoint.** `istio_requests_total` (the L7 request-rate/latency metric) is emitted only by a waypoint proxy; a ztunnel-only ambient mesh can produce only `istio_tcp_connections_opened_total` and its siblings, with `connection_security_policy` as the sole mTLS-relevant label. Building an L7 SLO, error-rate dashboard, or request-latency alert against an ambient mesh with no waypoints deployed will silently have no data source to query -- waypoints are not an optional add-on for L7 telemetry, they are the only source of it.

    **Full evidence and detail:**

    **Istio ztunnel is L4 only -- no HTTP metrics**: Ztunnel has zero visibility into HTTP status codes, paths, or request-level data. `istio_requests_total` requires an L7 waypoint proxy. For L4 traffic visibility, use `istio_tcp_connections_opened_total` with `connection_security_policy` label for mTLS status.

4. **Counting "workloads enrolled in ambient" by filtering `istio_tcp_connections_opened_total` on `connection_security_policy="mutual_tls"` undercounts -- use `reporter="source"` instead.** `mutual_tls` only appears once BOTH sides of a connection are mesh-enrolled and have successfully negotiated HBONE; a workload whose peer is outside the mesh, or has not yet negotiated, never shows `mutual_tls` even though ztunnel is actively intercepting its outbound traffic. `reporter="source"` counts any workload whose outbound traffic ztunnel captures at all, independent of the destination's enrollment state, and is the correct signal for "is this workload's traffic being intercepted by ztunnel."

    **Full evidence and detail:**

    **`reporter="source"` identifies mesh-enrolled namespaces**: `istio_tcp_connections_opened_total` includes both source and destination namespaces, but destination namespaces appear even when not enrolled. Filter on `reporter="source"` to see only namespaces where ztunnel is actually intercepting outbound traffic. Filtering instead on `connection_security_policy="mutual_tls"` undercounts enrolled workloads: it requires active pod-to-pod mTLS with both endpoints in the mesh. `reporter="source"` includes intercepted traffic regardless of destination. (merged from #28)

5. **`istio_tcp_connections_{opened,failed}_total` double-counts intra-mesh connections unless you pin the `reporter` label -- and the inflation factor is traffic-mix-dependent, not a fixed constant.** Both ends of a connection report independently in Istio's telemetry model: an intra-mesh connection is recorded once by the source-side ztunnel and again by the destination-side ztunnel, so a query without `reporter` sums both. Measured inflation (no-reporter vs `reporter="destination"`) varied roughly 1.05x to 1.8x across clusters with different traffic mixes -- it is a property of how much traffic is intra-mesh on a given cluster, not something you can hardcode as a correction factor. Always pin `reporter="destination"` for a destination-side view (or `reporter="source"` for a source-side view), and **never compare a baseline taken without the label against a later reading taken with it** -- the delta alone can manufacture a large fictitious improvement or regression that has nothing to do with real traffic change.

    **Full evidence and detail:**

    **`istio_tcp_connections_{opened,failed}_total` DOUBLE-COUNT intra-namespace connections unless you pin `reporter` — and the reporter factor is per-cluster, so it cannot be reused as a constant.** The published playbook W1b queries omit the `reporter` label, so an intra-namespace connection is counted once by the source ztunnel and again by the destination ztunnel. Measured inflation with no reporter vs `reporter="destination"`: **<gke-prod-cluster> 56.57 vs 32.144 conn/s = 1.76×; <aws-prod-cluster> 8.201 vs 4.936 = 1.66×; <gke-tenant-test> 1.0563×** — so the factor is a property of the traffic mix, not of the metric. **ALWAYS pin `reporter="destination"` for the dest-side view.** **THE DANGER IS NOT THE ABSOLUTE ERROR: a baseline taken with the published query and a post-enrolment reading taken with a corrected one manufactures a fictitious ~43% "improvement".** (For the companion Loki-label defect in the same playbook — labels are `k8s_cluster_name`/`k8s_pod_name`/`k8s_namespace_name`/`k8s_container_name`, and `cluster` exists only as structuredMetadata — see #106(b) and #67, which already carry it, together with the general rule: **never report an absence without pairing it with the same query against a target where the answer must be non-empty.**)

## Waypoint proxies and the Telemetry API

6. **The `istio.io/waypoint-for` label on a waypoint Gateway only accepts `service`, `workload`, `all`, or `none` -- `namespace` is not a valid value, and setting it produces no validation error while the waypoint silently intercepts nothing.** The label controls which traffic *type* the waypoint captures: `service` for traffic addressed to a Service ClusterIP, `workload` for traffic addressed directly to a pod IP, `all` for both, `none` to disable capture. This is an easy mistake because enrollment *breadth* -- which namespaces or services route through the waypoint at all -- is a completely separate mechanism, the `istio.io/use-waypoint` label applied to a namespace or individual services. There is no `namespace` scope value because `waypoint-for` describes traffic type, not enrollment breadth. (Istio 1.29.x Gateway API waypoint model.)

    **Full evidence and detail:**

    **`istio.io/waypoint-for` valid values are `service`, `workload`, `all`, `none` -- not `namespace`**: The `istio.io/waypoint-for` label on a Gateway resource controls which traffic type the waypoint intercepts (`service` = traffic to Service VIPs, `workload` = traffic to pod IPs, `all` = both). `namespace` is NOT a valid value and the waypoint may silently do nothing. For a namespace-scoped waypoint that handles HTTP service traffic, use `scope: service`. Namespace enrollment is separate -- apply `istio.io/use-waypoint: <gateway-name>` to the namespace or individual services.

7. **Before pointing a namespace or service at a waypoint with `istio.io/use-waypoint`, verify the waypoint's actual configured name and the Gateway's namespace -- a mismatch on either one fails completely silently.** If the label's value does not match any existing waypoint Gateway name, nothing errors: the namespace is simply never routed through a waypoint, and traffic flows exactly as it did before the label was applied. If the waypoint Gateway lives in a different namespace than the one being labelled, an additional `istio.io/use-waypoint-namespace` label is required -- omit it and you get the same silent no-op. Separately, a waypoint Gateway is stamped `istio.io/waypoint-for: service` by default (#6), meaning it only intercepts Service-VIP-addressed traffic; direct pod-IP traffic -- a metrics scraper hitting a pod's target port, or any client that resolves and dials the pod IP -- bypasses the waypoint regardless of whether the label is correct. **UNVERIFIED at source level:** the label/namespace-mismatch failure mode is recorded from observed behaviour with no `file:line`; confirm against the waypoint-attachment controller source at your pinned version.

    **Full evidence and detail:**

    **Before writing an `istio.io/use-waypoint` label, check TWO things: the waypoint's configured NAME and the Gateway's NAMESPACE.** A name mismatch silently points the namespace at a non-existent waypoint — nothing errors, traffic simply never traverses. And if the Gateway lives in a DIFFERENT namespace from the labelled one, the extra `istio.io/use-waypoint-namespace` label is required; when they are the same namespace it is not. **Read both from the chart source rather than the docs, since the defaults are what actually ship.** **The load-bearing default: the waypoint Gateway is stamped `istio.io/waypoint-for: <scope>` with `scope=service` by default — which is EXACTLY why pod-IP-addressed traffic (a gateway addressing pod IPs, a metrics scraper hitting a target port) bypasses the waypoint.** That is the source-level proof of the 'Service-addressed only' claim relied on throughout `learnings-istio.md#168`, `learnings-istio.md#173` and `learnings-istio.md#175`; contrast `learnings-istio.md#12`, where an egress waypoint must instead use `scope: workload`.

8. **Never set a static `deployment.spec.replicas` inside the ConfigMap a waypoint's `infrastructure.parametersRef` points at if an HPA also manages that Deployment -- istiod's own reconciliation will fight the HPA on every restart or config change.** istiod's waypoint auto-deployment controller patches the waypoint Deployment from the `parametersRef` ConfigMap's `deployment` key on every reconcile (istiod restart, config change). If that patch includes a static `replicas` value, each reconciliation resets the replica count back to it, silently undoing whatever the HPA had just scaled to -- no error, just a Deployment that never holds its HPA-assigned replica count. Omit `replicas` from the ConfigMap when HPA is enabled (a conditional in the chart template works); set a static `replicas` only when there is no HPA and the goal is a non-default count (Istio's own default is 1 replica). **UNVERIFIED at source level:** recorded from observed istiod behaviour with no `file:line`; verify against the istiod waypoint-controller source at your pinned version.

    **Full evidence and detail:**

    **Omit `deployment.spec.replicas` from the Istio waypoint parametersRef ConfigMap when HPA is enabled**: Istio's istiod patches the waypoint Deployment with the `deployment` key from the `infrastructure.parametersRef` ConfigMap. If that patch contains `spec.replicas`, every istiod reconciliation (on restart or config change) resets replica count to the static value, fighting the HPA controller. Pattern: wrap `replicas` in `{{- if not .configMap.hpa }} replicas: ... {{- end }}` in the Helm template so it is omitted when HPA is configured. Without HPA, replicas is useful to set a non-default static count (Istio defaults to 1).

## Egress

11. **Ambient mode has no built-in default-deny-egress primitive -- this is a maintainer-confirmed gap in upstream Istio, not a missing feature you failed to find.** Per an Istio maintainer on the project's own GitHub Discussions (`istio/istio#53021`, 2026-05-29): *"Ambient mode does not support default-deny egress. L4 AuthorizationPolicies can deny specific traffic, but there's no single policy that denies all egress."* A default-deny egress posture in ambient requires L7 waypoint proxies fronted by an explicit DENY-all-then-ALLOW-specific `AuthorizationPolicy` per service; for cluster-wide egress enforcement without deploying waypoints everywhere, rely on a VPC/cloud firewall or NetworkPolicy instead of expecting Istio itself to provide it.

    **Full evidence and detail:**

    **Istio ambient default-deny egress is NOT in OSS Istio**: Maintainer an upstream maintainer (istio/istio discussion #53021, 2026-05-29): "Ambient mode does not support default-deny egress. L4 AuthorizationPolicies can deny specific traffic, but there's no single policy that denies all egress." Default-deny egress requires L7 waypoint proxies with `AuthorizationPolicy` (DENY all + ALLOW specific) per service. For cluster-scoped egress enforcement without waypoints, rely on VPC firewall rules or NetworkPolicy, NOT Istio AuthorizationPolicy.

12. **SUPERSEDED by #195 — ServiceEntry attachment, DNS capture and auto-allocated VIPs govern ambient egress capture; source-namespace scope alone does not capture raw-IP traffic.** **Egress waypoints must be scoped `scope: workload`, not the ingress-waypoint default `scope: service` -- external egress targets are pod-to-raw-IP, and a `service`-scoped waypoint only intercepts Service-VIP-addressed traffic.** There is no ClusterIP for an arbitrary external host, so a waypoint left at the default service scope captures nothing on the egress path. The source namespace additionally needs `istio.io/use-waypoint: <egress-gateway-name>` set at the namespace or workload level, and must itself be ambient-enrolled, or egress traffic never reaches the waypoint to be captured in the first place. **UNVERIFIED at source level:** recorded from observed behaviour with no `file:line`; verify the `scope` field's effect on ztunnel's egress-capture matching against the ztunnel/istiod source at your pinned version.

    **Full evidence and detail:**

    **SUPERSEDED by #195 — Use ServiceEntry attachment and DNS capture; source-namespace scope alone does not capture arbitrary egress.** **Egress waypoints use `scope: workload`, not `scope: service`** — external egress targets are pod-to-raw-IP, not pod-to-ClusterIP, so a `service`-scoped waypoint captures nothing. The SOURCE namespace must be labelled `istio.io/use-waypoint: <egress-gw-name>` at the namespace or workload level **and** must itself be ambient-enrolled. Compare `learnings-istio.md#7`, where the ingress waypoint's `istio.io/waypoint-for: service` default is exactly what makes pod-IP-addressed traffic bypass it.

## Control-plane alerting metrics

13. **At Istio 1.29.1 there is no always-present xDS reject/error counter, and a production alert on xDS errors must be data-plane-agnostic or it will silently never arm on waypoint-less clusters.** Source-confirmed at `istio/istio` tag 1.29.1: `pilot_xds_push_errors` does not exist in this release line (removed/renamed) -- an alert built on it is a permanent false negative. The startup gauges `pilot_conflict_inbound_listener` and its outbound-listener counterpart are always-present and are the better choice for a data-plane-agnostic control-plane alert.

## CNI chaining and upstream bugs

## AuthorizationPolicy semantics

17. **Several AuthorizationPolicy authoring mistakes at Istio 1.29 are silent -- they do not error, they just deny every caller or scope far wider than intended.** Confirmed against `release-1.29` source and live traffic.
    - **`principals` never take a `spiffe://` prefix -- Istio prepends it itself** (`pilot/pkg/security/authz/model/generator.go`). Copying a value straight out of `istio_tcp_connections_opened_total{source_principal=...}` (which reports the full `spiffe://cluster.local/ns/X/sa/Y`) into a policy's `principals` field produces a double-prefixed string that matches nothing. An ALLOW policy whose `principals` match nothing denies every caller once enforced -- with no error at apply time.
    - **`to.operation.hosts` matches the literal `:authority` HTTP header, not a resolved FQDN** (`model.go`, `generator.go`). Measured across tens of thousands of live in-cluster requests, callers sent short Service names or `svc:port`, essentially never the fully-qualified `svc.namespace.svc.cluster.local` form -- an FQDN-only `hosts` list matches close to zero real traffic.
    - **`targetRefs: [{kind: Gateway}]` pointed at a waypoint attaches the policy to every service routed through that waypoint**, not just the one intended (`policyattachment.go`, the waypoint listener builder) -- a namespace-wide blast radius the moment the namespace carries `istio.io/use-waypoint`. Scope to one service instead with `targetRefs: [{group: "", kind: Service, name: <svc>}]`.
    - **A `DENY` policy keyed on `notPrincipals` is NOT bypassable by sending plaintext -- the opposite of the intuitive reading.** Istio compiles it as `NOT(principal match)`; an unauthenticated/plaintext caller has no principal, so the inner match is false, the negation is true, and the DENY matches -- plaintext gets denied, not waved through. The bypassable form is the reverse: a DENY keyed on *positive* principals, which an identity-less caller trivially fails to match and therefore evades.
    - **ztunnel silently discards any AuthorizationPolicy that carries `targetRefs`** (`ambient/authorization.go`) -- a Gateway- or Service-targeted L7 policy never falls back to L4 enforcement at ztunnel, and conversely a selector-based policy is ignored by waypoints entirely. The L4 (ztunnel) and L7 (waypoint) enforcement layers each need their own separate policy resource; one policy cannot cover both.

    **Full evidence and detail:**

## Operational hardening

19. **ztunnel's graceful-drain behaviour is governed by two separate settings that must agree, and the upstream chart default for both is short relative to long-lived connections.** The podSpec's `terminationGracePeriodSeconds` (the kubelet's SIGKILL timer) and the container env `TERMINATION_GRACE_PERIOD_SECONDS` (ztunnel's own internal drain timer) are meant to carry the same value. If a values refactor overrides one and not the other, the kubelet can SIGKILL ztunnel mid-drain while ztunnel's own drain logs still look clean and uneventful -- silently reopening a connection-reset window on every rolling restart. The upstream chart default is 30 seconds for both, which is short for connections with multi-minute keepalives; treat any override of either setting as incomplete until you have confirmed the other moved with it.

    **Full evidence and detail:**

    **ztunnel drain configuration: TWO places must agree, and the upstream default is far too short.** The podSpec `.spec.template.spec.terminationGracePeriodSeconds` (the kubelet SIGKILL timer) and the container env `TERMINATION_GRACE_PERIOD_SECONDS` (ztunnel's own internal drain timer) both render from the same value — **if they diverge the kubelet kills ztunnel mid-drain while the drain logs still look healthy.** The upstream chart default is 30 s, so a refactor that drops an override silently re-opens the long-lived-TCP RST window. **A general rule this instance teaches: a per-tier value written into a plan document is not a value that shipped — read the values files, and never build a check against a recommendation you have not confirmed was implemented.** **Related DaemonSet asymmetry that produces guaranteed false FAILs:** the ztunnel DaemonSet is `maxSurge: 1 / maxUnavailable: 0` (availability designed never to dip) while the istio-cni DaemonSet is `maxUnavailable: 1` (one node legitimately has no CNI mid-roll) — applying ztunnel's zero-dip rule to istio-cni fails every roll. 56. **A two-source split between a moving-tag-pinned app and an app-of-apps on `main` makes BOTH `kubectl delete` and 'move the tag back' the wrong rollback — and it also wedges on MERGE.** When the file that carries a resource's content is rendered by an app pinned to a moving tag, while the `valueFiles` reference that activates that file is rendered by an app-of-apps tracking `main`, three consequences follow. (a) If the content app has selfHeal+prune on, a bare `kubectl delete` of the resource is reverted within minutes — any 'delete = instant rollback' runbook does not apply. (b) Moving the tag back ALONE wedges the app: `main` still carries the `valueFiles` entry, the referenced file is ABSENT at the old tag SHA, `helm template` fails file-not-found, ArgoCD goes ComparisonError and cannot prune — so the resource persists. The correct durable rollback is to revert the `valueFiles` reference on `main`; break-glass during an outage is to disable the content app's auto-sync FIRST, then delete, then follow up with the revert. Deploy gating is the inverse two-step: merging to `main` activates the reference, moving the tag activates the file. (c) **The same wedge fires on MERGE, not just rollback, and it is easy to mis-classify as a non-event.** When the PR ADDS a file that did not previously exist at the pinned tag, merging makes the app-of-apps reconcile the new `valueFiles` entry onto a live app that still sources the old tag where the file is absent → ComparisonError on a production app the instant the PR merges, before the tag is moved. No resources render, so nothing breaks — it just leaves a red app until someone moves the tag. Discriminator: `git cat-file -e <tag>:<path>` returns 0 for siblings whose file was already present when the tag was cut, non-zero for the not-yet-promoted cluster. **Permanent fix: set `ignoreMissingValueFiles: true` on the helm block** — the missing path is then skipped, the app renders without the overrides (= current healthy live state), the layers decouple, and the tag move alone activates the change. This removes the merge↔tag-move ordering fragility entirely for every future tag-pinned cluster. See `learnings-argocd.md` for the app-of-apps targetRevision split, and `learnings-istio.md#183` for the merge-time analogue from the missing-file direction. 62. **tcpdump directional asymmetry in ambient mode**: tcpdump on `dst port <app-port>` captures plaintext on **inbound** (server-side) pods but captures **zero packets** on **outbound** (client-side) pods. Root cause: outbound connections get fwmark'd (`0x111`) and policy-routed via `table 100` to loopback, hitting ztunnel's `:15001` listener. ztunnel wraps in HBONE/mTLS and sends out on `:15008`. By the time packets hit the wire, the destination is `:15008` (encrypted), not the original app port. Inbound: ztunnel receives HBONE on `:15008`, decrypts, and delivers plaintext into the pod's netns on the app port. This is why backend pod tcpdump works but Envoy proxy pod tcpdump for outbound traffic does not.

63. **SUPERSEDED by #197 — Ambient also installs outbound ISTIO_OUTPUT NAT REDIRECT rules; fwmark routing does not imply their absence.** **ztunnel outbound interception uses fwmark + policy routing, not iptables REDIRECT**: Unlike the sidecar model (which uses iptables REDIRECT/TPROXY), ambient ztunnel uses `ip rule` fwmark-based policy routing. This means `iptables-save` won't show REDIRECT rules for ztunnel interception. Check `ip rule list` and `ip route show table 100` instead.

Measured at the SAME `--since=1h`: ztunnel 280 → **68,020** lines with `--tail=-1` (243×), istio-cni 280 → 1,608, istiod 30 → 1,145. Fingerprint: **any log-line count that is a round multiple of the pod count IS the tail cap** (280 = 10 × 28 pods). The resource-ref form (`logs daemonset/ztunnel`) is NOT subject to the cap but resolves to exactly ONE pod — on a 183-node cluster that under-samples 182/183 nodes and cheerfully returns 0. Always `-l <selector> --tail=-1`. (b) `--tail=N --previous` is worse than it looks for crash forensics: `--tail` keeps the LAST N lines but `fatal error:`/`panic:` are the FIRST lines of a goroutine dump, so a bounded tail preferentially discards the very signature you grep for. A process that panics then DIES is only visible via `--previous` over every pod with `restartCount>0`; also grep the `goroutine N [running]:` header since some pipelines drop the `fatal error:` line. (c) `kubectl logs -l` defaults to `--max-log-requests=5` and ERRORS above it — the common `2>/dev/null | grep -c … || echo 0` idiom swallows that error into a `0`. An errored command is ERROR, never PASS. (d) **Any grep alternation token ≤4 chars must be word-bounded or drop `-i`.** `grep -iE 'cert|CA|expir'` case-insensitively substring-matches `cached`/`cannot`/`cluster.local`: <test-cluster> 28 hits → 6 with `\bCA\b`, <dev-cluster> 759 → 6, and every "error-shaped" hit was an istiod optimistic-concurrency retry with zero cert content — i.e. a blocking check that FAILs a healthy CA. Same class: bare `zds` matches pod names (`example-operator-migration-6dzds`, `otel-alloy-logs-zds5d`), bare `429`, `id`, `up`, `eof`. `\b` works on both BSD and GNU grep. (e) Timing: at a post-upgrade checkpoint the pods are minutes old, so `--since=1h` covers only minutes — normalise to errors-per-pod-minute before comparing against a pre-upgrade 1-hour baseline.

115. **Grading a *varying gauge* with a fixed or zero tolerance is the IFV framework's most-repeated defect class (SPEC §9c M2), and the fix is a per-cluster MEASURED BAND, never a bigger constant**: One check FAILed a cluster at P1 on `pilot_eds_no_instances` `10 → 15` under "any increase → FAIL". Disproof from one range query: the same gauge read **15 twenty-eight hours BEFORE the control-plane merge**, 22 earlier that day, 0 later that day, and **0 fourteen minutes after the sample that FAILed on 15**. Root cause: it is a **per-replica gauge over endpoint-less Services** recomputed on every push-context init, so the cluster sum quantises to multiples of the per-replica value and any istiod restart re-rolls it; non-multiples (`1,11,16,22`) are old/new ReplicaSet overlap during a Deployment roll. **The right axis is metric CLASS, not tolerance width.** Of the four `pilot_*` "config-error" metrics, `pilot_vservice_dup_domain` and `pilot_duplicate_envoy_clusters` are deterministic functions of the *config set* (measured flat `0` on 13/13 across 37.5 h) and keep strict zero-tolerance-on-increase; `pilot_eds_no_instances` and `pilot_dns_cluster_without_endpoints` are functions of the *endpoint population* (measured over a 37.5 h window, per-cluster bands ran from flat 0 up to 0→**150**) and get a sustained band: `ref_ceiling = max_over_time(sum by(cluster)(M)[24h:5m] @ $BASELINE_AS_OF)`, `now_floor = min_over_time(sum by(cluster)(M)[30m:60s] @ $AS_OF)`, FAIL iff `now_floor > ref_ceiling`. Three things are load-bearing: **`min_over_time`** (the peak re-imports the false FAIL — pick the extreme a healthy transient cannot avoid touching, the same construction as `L1.01`'s `max_over_time(up[10m])` sustained *deficit*); the **baseline-anchored** reference window (`now − 24h` lets a sustained rise raise its own ceiling); and the fact that a band measured at `0` **is** zero tolerance, so quiet clusters keep full teeth automatically. Why a constant fails: `+5`, `+10` and `×2` all pass a `10→15` move yet all still false-FAIL a cluster whose healthy band is 0→150 *and* blind a cluster whose genuine value is 0. Beware also that a documented "pre-existing non-zero" may itself be a single draw from an oscillation — check the range before enshrining a point as a level. 116. **A phase-window predicate needs three branches, not one — a check that hardcodes the transient state FAILs by construction once the window closes, and `INFO` for "no-longer-evaluable" needed a SPEC change to be legal**: Two data-plane version checks asserted `tag == $PREV_VERSION` at P1. Once the data-plane merge landed, that row FAILed on the state the upgrade exists to reach — 4 blocking FAILs across two clusters in one sweep, with leg 1 (uniformity) PASSing on every pod, one digest each, and istiod having merged *first*. The tell that it was a catalog defect rather than a mesh fault: **the authoritative P1 skew gate PASSed identical data at the same instant** — two checks disagreeing with the gate on one input is always the catalog, not the cluster. The skew gate's idiom is the model: admit `tag ∈ {$TARGET, $PREV_VERSION}` as a *set* and let a separate **direction** predicate do the grading. Fix: read the control plane too (`count by (tag)(istio_build{job="istiod",component="pilot"})`, the same row the authoritative gate's first predicate uses, so the three checks cannot disagree) and split P1 into DP=`$PREV` → PASS · DP=`$TARGET` & CP=`$PREV` → **FAIL** (the real skew inversion — never delete this branch, it is the row's only P1 value) · DP=`$TARGET` & CP=`$TARGET` → **INFO** (window closed, re-run as P2). **Framework gap this exposed:** the framework's status vocabulary permitted `INFO` only for *not-yet*-evaluable predicates, and its result validator hard-errored on `INFO` at any non-initial phase. Declare it in the **catalog**, never infer it from the result's `notes`: `notes` is written by the agent under test, so prose-derived INFO is a self-service escape from FAIL. Do not repurpose an existing key that means something else, and when the window-closed branch and a genuine failure share an observable (`tag == $TARGET` is *both* half the inversion and the closed window), the discriminator must be a second, independent read. 138. **When a validation catalog's skew gate and its target-state siblings disagree about a legal intermediate state, preserve the separate results — do not launder one into the other.** A CP-first promotion deliberately leaves the data-plane applications on the old pin. The skew gate correctly PASSes (control plane ahead, data plane not ahead), while any sibling requiring *all* roles on the target matrix, or *all* applications on a supplied expected revision, correctly FAILs. **These are different predicates, not alternative interpretations of one predicate: do not override their statuses from the campaign narrative, and do not weaken the inversion gate, which is the check that actually matters.** Separately, and sharpening `learnings-istio.md#128`: after a control-plane roll, per-process counters can have **zero current series** while root-expiry gauges and historical range deltas still return data — **a range window containing departed pods is not a live arming proof**, so an arming check must ERROR until current series return rather than passing on historical data.

139. **An anchor promotion can UNFREEZE a security-relevant flag as a rider — and the 'a forward flip is inert until an explicit restart' rule (`learnings-istio.md#118`(a)) DOES NOT HOLD on such a promotion.** The inertness rule depends on the change being ConfigMap-only: the value reaches containers via `envFrom: configMapRef` and the pod template carries no config checksum, so running pods keep the old value. **But if the same diff ALSO changes the container image or adds an env var, the pod template changes, the DaemonSet rolls, and the flag flip lands *with* the roll.** So: treat such a flip as an ACTIVE behavioural change on any promotion that touches the image or the env, and as inert only on a genuinely ConfigMap-only PR. Where the flip is a security improvement — closing a fail-open window (`learnings-istio.md#117`, `learnings-istio.md#15`) — do not strip it; put it in the PR body and the roll runbook, and note that the rollback is NOT a clean revert (`learnings-istio.md#118`(b)). Verify what a promotion actually flips by rendering both refs (`learnings-istio.md#136`), and note that a values file present at one ref and absent at another is itself the rider (`learnings-istio.md#153` corrects a recurring mis-statement of exactly this).

143. **A public route existing for a path proves the path CAN be reached externally — never that a given client DOES reach it that way.** In one investigation every circumstantial signal pointed at an external hairpin and all of it was a red herring: the endpoint WAS routed publicly by an HTTPRoute on the shared gateway; the public hostname DID resolve to the CDN from inside the cluster (the kube-dns ConfigMap had zero data keys, so no stubDomain rewrite); and the caller carried a domain-shaped environment variable with no explicit service-URL override. 144. **Tailscale k8s-operator proxies come in TWO modes and only ONE is at risk — discriminate on the pod label `tailscale.com/parent-resource-type`, and never count `ts-*` pods without splitting.** `svc` = **KERNEL** mode (`TS_USERSPACE=false`, `TS_DEST_IP` set): brings up a `tailscale0` TUN with a `100.64/10` CGNAT address **after** pod start and DNATs its own tailnet address to the parent Service ClusterIP in its own netns — vulnerable to BOTH the ztunnel re-attach blackhole (#16, `istio/istio#61027`) and STRICT-mTLS rejection (#44). `ingress` = **USERSPACE** mode (`TS_USERSPACE=true`): serves via `tailscale serve` in netstack, NEVER creates `tailscale0`, presents ONE address — **immune to both**. **Any census of these is a SNAPSHOT, not a property** — any new Service annotated for tailscale mints an `svc`-type proxy, and counts drift with preview churn (one cluster went 79 → 85 within a day). A fleet reading "zero kernel-mode proxies in prod" is true only at the instant it was taken; re-check at roll time (`learnings-istio.md#157`). **Two counting traps that both bit**: (1) counting all `ts-*` pods without splitting by type overstates blast radius ~8x (one cluster was reported as "17 at risk" when it was 2); (2) **an EXPIRED AWS SSO SESSION makes `kubectl` return empty, so every AWS cluster silently reports `svc=0`** — including the very cluster the investigation started from, which would have been recorded as immune. **Any fleet census must ERROR on an unreachable cluster, never report zero.** The example organization's measured census: `orgs/<org>/istio.md`.

145. **Triage playbook for "Tailscale-exposed service unreachable" — discriminate by TIMING before theorizing, then avoid three false-positive traps.** **Signatures**: (1) ~10-12s hang with 0 bytes = the ambient/ztunnel inbound blackhole (#16/#146); (2) fast RST ~0.1-0.5s **with healthy backend endpoints** = STRICT mTLS rejecting the proxy's forwarded plaintext (#44); (3) fast RST with **0 ready** backend endpoints = service scaled to zero, pre-existing and unrelated; (4) hang against a peer that `tailscale status` shows as `offline` = stale tailnet device with no backing pod, pre-existing cruft. **False-positive traps that cost real time on 2026-07-28**: (a) **do not probe every proxy on port 80** — kiali serves 20001/9090, application-db is postgres 5432; take the port from the Service spec or you will report healthy services as broken; (b) **do not derive tailnet hostnames from service names** — the operator appends numeric suffixes on device collision (`example-cluster-default-protocol-gateway-4`), so resolve per-pod with `kubectl exec <pod> -c tailscale -- tailscale status --json | jq -r .Self.DNSName`; (c) **do not treat `tailscale status` peers as live proxies** — many are stale devices whose Service no longer carries the `tailscale.com/expose` annotation; cross-check against live pods labelled `tailscale.com/parent-resource-type=svc`. **Useful commands**: ztunnel state via `kubectl port-forward -n istio-system <ztunnel-pod> LOCAL:15000` then `curl /config_dump | jq .workloads`; per-pod netns addresses via `ip -o addr show` inside the `tailscale` container; discriminate locally-originated vs forwarded traffic by `wget`-ing `TS_DEST_IP` from inside the proxy pod (works) versus hitting the tailnet hostname (may be denied).

146. **CORRECTION to the ztunnel re-attach mechanism (#16): the "ztunnel registers the tailscale0 address as a second workloadIp" story is NOT supported by the source and misled a later investigation — the mechanism is UNKNOWN, do not assert one.** **Verified in source at our pinned version**: (1) `cni/pkg/nodeagent/ztunnelserver.go:258` — the ZDS `WorkloadInfo` carries ONLY `{Namespace, Name, ServiceAccount}`; **no addresses ever cross ZDS**; (2) `ztunnel/src/inpod/netns.rs` does **no** address enumeration; (3) `ztunnel/src/proxy/inbound.rs:368` — `destination_workload = local_workload_information.get_workload()`, i.e. the **netns owner**, not a lookup on `dst.addr`. **So `dst.workload=` in the access log is expected for ANY inbound on that pod's listener and proves nothing**, and `workload_ips` comes from XDS and is identical at first-attach and re-attach — meaning "the healthy dump shows the pod IP only" is consistent with BOTH states and is not a discriminator. **What remains true and measured**: an istio-cni restart blackholes inbound to the SECONDARY address of already-running kernel-mode Tailscale proxies (0.13s → 10.14s → 0.14s across restart and recycle, reproduced and reversed on <gke-sandbox-test>); fresh pods are unaffected; userspace/ingress proxies in the same namespace on the same nodes are unaffected; recycling the pod is the only fix. **Untested candidates**: surviving conntrack entries, or in-pod redirection applying to the pod's own DNAT'd traffic once the listener is re-established. Upstream `istio/istio#61027` was rewritten to drop the claim. **Consequence: any check built on "ztunnel registers extra workloadIps" is VACUOUS and can never fire** — IFV L2.24 was removed for exactly this reason.

147. **WHY STRICT mTLS breaks kernel-mode Tailscale proxies — the mechanism, the discriminating test, and the consequence that makes enrollment pointless.** A kernel-mode `ts-*` proxy (`TS_USERSPACE=false`, `TS_DEST_IP` set) **FORWARDS** traffic rather than originating it: inbound hits PREROUTING, is DNAT'd to `TS_DEST_IP`, then traverses FORWARD and exits `eth0`. **Istio's `ISTIO_OUTPUT` chain only captures LOCALLY-GENERATED packets**, so forwarded traffic is never captured by ztunnel, never gets HBONE, and never carries the pod's SPIFFE identity. Under STRICT `PeerAuthentication` the destination ztunnel drops it: `connection closed due to policy rejection: explicitly denied by: istio-system/istio_converted_static_strict`, bytes 0/0, duration 0ms — presenting as a **FAST RST (~0.17s)**, NOT the ~10s blackhole of the re-attach bug (#16/#146). Observed on <aws-sandbox-test> (`app-namespace/strict-mtls=STRICT` + 3 envoy STRICT policies); <dev-cluster>, <aws-sandbox-dev> and <gke-sandbox-dev> are `istio-system/default=PERMISSIVE` and unaffected. **Discriminating test on the SAME pod**: `wget http://<TS_DEST_IP>:80/` from inside the proxy pod SUCCEEDS (locally-originated → `ISTIO_OUTPUT` → identity → allowed) while the same destination reached via the tailnet is DENIED (forwarded → bypasses capture → plaintext). **Consequence: being enrolled in ambient does NOT give a Tailscale proxy mesh identity for the traffic it proxies — so removing `ns/tailscale` from ambient costs nothing, even under STRICT.** Any cluster moving to STRICT will break its Tailscale-exposed services this way. Sharpens #44 (which states the blocker) and #144 (which tells you which proxies are affected).

148. **"Tailscale TLS completes then hangs" is a hostname-COLLISION serve-config mismatch, not a backend or ambient problem — and Tailscale never auto-reclaims a freed canonical name.** On <dev-cluster> the `<key-service>` Ingress (class `tailscale`) showed `Address=example-cluster-default-key-service-1` while `TLS: SNI routes example-cluster-default-key-service` (canonical). The device got the `-1` suffix because the canonical name was taken by a since-removed `preview-<id>` preview when the proxy first registered; **the operator's serve config is bound to the canonical name the device never got**, so connecting to `-key-service-1` completes TLS and HTTP/2 and then hangs — no serve route matches the actual device hostname. **The backend was 100% healthy** (Service 80→4000 with 3 ready endpoints, 3 pods 2/2 Running, ambient-enrolled with a healthy waypoint, logs showing live 200/201 traffic to internal mesh callers), which is exactly what makes this look like a mesh fault. **The control that proves it**: `<test-cluster>`'s `<key-service>` has no collision (device == canonical == serve host) and works end-to-end. **Fix**: force the live proxy to re-register so it reclaims the now-free canonical name — delete the Ingress and let ArgoCD recreate it, or delete the `ts-*` proxy StatefulSet plus its state Secret in `ns/tailscale`. **Tailscale's unique-hostname dedup appends `-N` and never reclaims once the original frees up**, so a stale preview can poison a real service's name indefinitely. Add this as signature (5) to the triage playbook in #145.

153. **Four mechanics for split control/data-plane promotion campaigns, each of which costs a cycle.** (1) **`mergeable: MERGEABLE` from `gh` does NOT prove the pair composes** — it is computed against the base branch, not against the sibling PR, and two PRs editing adjacent blocks of the SAME file have overlapping diff-context regions. **Prove it non-destructively with `git merge-tree --write-tree HEAD origin/<other-branch>`, then read the tree back with `git show ${tree}:<path>` and confirm every affected block landed as intended.** A cheap offline proof that a production merge sequence will not conflict mid-campaign. (2) **A merge-automation gate marker must NOT be pasted on the LEADER PR.** If your merge bot ignores PRs containing a marker substring in a comment, putting the same gate text on both PRs **blocks the very PR you need merged FIRST and deadlocks the campaign.** Use the marker only on the follower; the leader gets a plain 'this PR goes FIRST' comment. See `learnings-istio.md#157`, where describing the gate in the leader's BODY nearly reproduced this. (3) **The anchor promotion carries riders beyond the version bump — render both refs and disclose them** (`learnings-istio.md#136`). (4) **A registry-hub rider is usually a DATA-PLANE rider too, not just a control-plane one** — rendered at both refs it typically moves every image, and on a cluster using an explicit image-pull secret that is a real risk rather than cosmetic: the secret must be able to read the new path (though see `learnings-istio.md#185` — a dockerconfigjson is host-scoped, so a path-segment change usually needs no secret edit; confirm the scope rather than assuming either way). **General correction worth internalising: 'the provider values file does not exist at the old ref' and 'the file exists but gains a key' are different claims with different rollback consequences — verify with `git diff <old-ref> <new-ref> -- <path>` before repeating either in a PR body.**

158. **A feature payload gated on a per-target values block is HOST-TARGET-scoped, not tag-scoped — which changes what a non-vacuous negative control for a pointer-bump PR actually is.** Bumping a target's pinned ref deploys the feature's objects only if that target's own values file carries the enabling block. **The control a dispatch usually asks for — 'render an out-of-scope target at merge-base vs branch' — is VACUOUS on a values-only branch**: such a branch touches zero chart files, so that render is byte-identical for *every* target including the ones being bumped, and it proves only that the diff is values-only. **The load-bearing control varies the REF, not the branch:** render an out-of-scope target at ITS CURRENT PIN vs the new ref, which asks the question that actually matters — 'does the new ref change anything where I do not want it to?'. **And that control has a shelf life, because the fact it rests on is itself a file that PRs change — re-derive it every bump (`learnings-istio.md#161`), and when every target has gained the block, substitute the block-isolation control (`learnings-istio.md#191`), which is strictly stronger.** Paste the weak form if asked, but label it weak and carry the ref-varying control alongside. 161. **A 'load-bearing' negative control has a SHELF LIFE — re-derive it every time, because the fact it rests on is itself a file that PRs change.** A control of the form 'render an out-of-scope target across the two refs → zero feature objects, because it carries no enabling block' DIES the moment a PR adds that block to the out-of-scope target: the same render then returns a positive delta and **reads as a containment leak if you paste the old conclusion.** Verifying the premise is a one-liner (`git grep -l <block-key> <ref> -- <values dir>` at each ref) and will show the enabled set growing bump by bump. **The control that does NOT rot: render each out-of-scope target at ITS CURRENT PIN vs the new ref** — which asks the question that actually matters, 'does the new ref change anything where I do not want it to?'. Note that rendering those same targets across a wider ref span will also show a positive delta, and **that is not a leak** — those are objects they already run from earlier bumps. **And once the sibling targets DO carry the block, containment rests entirely on the POINTER render (their pinned ref does not move), not on the payload render at all — say so explicitly rather than reusing the previous PR's wording.** When every target has gained the block, the substitute is the block-isolation control in `learnings-istio.md#191`.

162. **A Terraform plan-review gate built from 'is our resource changing correctly' checks needs a FIFTH check those four miss: scan every OTHER resource in the plan for full-replace list semantics on a shared singleton.** The first four gates (one resource / `~` not `-/+` / additive-only attribute changes / one-stack matrix) are all aimed at *your* resource and can pass cleanly while the same plan carries a cross-stack ownership defect two resources away. **The shape to look for: several resources — possibly in different stacks — managing the SAME external object, identified by an identical plan `id`, each declaring a single-element, full-replace list attribute for what is actually a multi-purpose field on that object.** The plan then shows live entries being swapped for one new entry. **The provider will not fail safe:** at least one such provider issues its update with a hardcoded, unconditional force flag on the update path, so the upstream API's own in-use check is bypassed. **Severity calibration matters and the live system is the arbiter — do not overclaim.** The tempting headline ('this evicts the resources backing production') can be WRONG: existing allocations may survive removal and keep serving. The true exposure is usually (a) permanent oscillation, since each stack rewrites the other's intent on every apply so neither ever plans clean, (b) the in-use guard being off, and (c) future allocations or resizes in an unlisted entry failing later, far from the cause. **`0 to destroy` in the plan summary does NOT cover this — nothing is destroyed, a field is replaced.** **Generalisable rule: whenever two Terraform resources share a plan `id`, or a list attribute is declared as a single-purpose slice of a multi-purpose external field, a `~ update in-place` is a CONTESTED OVERWRITE, not a benign diff — then go measure the live blast radius before you name a severity.** Also expect such drift to be per-target, not per-tenant: a sibling target's plan may be entirely clean.

(3) **The chart's default memory request is empirically under-provisioned** — measure a loaded pod and size against it, not against the default. (4) **On small clusters the extra pod is CHEAP, not unnecessary** — three modestly-sized pods were 0.2–0.4% of cluster memory on 22–39 node clusters. 166. **The waypoint-overhead access-log method (`duration − upstream_service_time`) has THREE false-FAIL generators, and the mean alone catches none of them: report mean AND p50/p90 AND mean `bytes_sent` AND mean `bytes_received`, always.** `upstream_service_time` stops at response headers and starts only once the request is fully forwarded, so the metric charges **held-open connections, response-body transfer AND request-body transfer** to the proxy.
    - **(a) RESTATE (or any durable-execution / long-poll upstream) — mechanical exclusion, not a judgement call.** Verbatim line, path anonymised: `duration=13368, upstream_service_time=7, path=/restate/invoke/<service>/<method>, source_principal=<durable-execution SPIFFE principal>`. **Filter by the durable-execution component's own SPIFFE principal AND its path prefix; both, because either alone leaks.** Effect on one measured cluster: two services fell from 108.118 → 0.220 ms (n 3208→82) and 62.261 → 0.289 ms (n 306→291). **The exclusion stays MANDATORY where the smoking-gun line is absent** (on one fleet the component's max duration was only 69/45 ms) — bucketing the 84 Restate requests by `bytes_received` exposes the same artifact in miniature, because the invoke protocol sends a TRIPLE per tick and the MIDDLE leg is held while the workflow step runs: small (<500 B) n=30 mean 2.23/2.33 ms; **MID (500–900 B) n=34 mean 14.03/12.91 ms**; large (≥900 B) n=20 mean 1.95/2.10 ms. Where the workload is the only one a cluster has, retaining it turned a real 0.2–0.3 ms into a 6.9 ms false FAIL against a 2 ms bar.
    - **(b) RESPONSE-body transfer.** Proven by mean `bytes_sent`: on one cluster `<file-service>` at 61,005 B → 3.268 ms, `embedding-service` at 289,683 B → 2.565 ms, `billing-service` at 5,878 B → mean 1.978 ms but **p50 exactly 0 and p90 2 ms**.
    - **(c) REQUEST-body transfer — the form that p50/p90 does NOT rescue.** `duration` starts at the first REQUEST byte. Measured on <file-service> (`POST /api/gateway-api/files`, mean `bytes_received` 1,817,354 B): unfiltered mean **11.593 ms** (n=5,440) = false FAIL, with p50 9 / p90 27 because the payload distribution is **bimodal-heavy, not a thin tail**. Bucketed by `bytes_received`: <10 KB n=1,519 mean **0.563 ms** p50 1 p90 1 max 3; 100 KB–1 MB n=123 mean 4.455; 1–5 MB n=3,458 mean 13.836; ≥5 MB n=333 mean 41.483 max 114 — monotonic, with implied throughput FLAT at ~145–170 MB/s across the large buckets = wire time, not proxy time. At <10 KB <file-service> is indistinguishable from every other service on the cluster.
    - **P50/P90 IS THE PRIMARY DISCRIMINATOR for the thin-tail cases.** On one cluster, grading on the mean alone would have failed eight services (2.950 ms at n=140,905, 2.471, 3.829, 5.364, 38.7, 222.3, 249.3 and 1,240.9) — **all eight show p50 of 0–1 ms and p90 of 1–2 ms.**
    - **RULE, better stated than "grade only short-RPC services": grade only SMALL-PAYLOAD REQUESTS** — a single service mixes both, and the <10 KB subset of a large-body service is perfectly gradeable. **DIAGNOSTIC that generalises: a high mean with a ~2 ms p50 means bucket by `bytes_received` (protocol legs) or `bytes_sent` (body transfer) before concluding anything.**
    - **Expect a residual the framework does not explain, and record it as OPEN rather than rationalising it.** In one fleet a family of small-payload NLP services showed p50 1–3 ms **AND** p90 5–6 ms at payloads under 1.5 KB — overhead 1.7–10.3% of total request time — which none of (a)/(b)/(c) accounts for. Hypothesis to test at T+24h: high-fanout burst queueing rather than per-request CPU; bucket by `bytes_received` and split by calling workload. **Also beware low-n anomalies that do not reproduce at scale** — one cluster's 13.8 ms outlier vanished on another at 11× the sample size. **⚠️ The example organization's instance of this residual is still OPEN — the measured services, the numbers and the hypothesis are in `orgs/<org>/istio.md`.**
    - **One query grades every service**: `upstream_cluster` has the form `inbound-vip|80|http|<svc>.<ns>.svc.cluster.local`, so `| label_format svc=`{{ regexReplaceAll ".*\\|([a-z0-9-]+)\\.<ns>\\.svc\\.cluster\\.local" .upstream_cluster "${1}" }}`` + `by (svc)` works.

169. **LAND THE ENROLMENT LABEL IN A REVISION THAT CHANGES NOTHING ELSE — a sync that also rolls applications destroys the server-side control, which is the single most important row of the validation.** In one run the release that applied the label also rolled three Deployments ~90 s before waypoint traffic began: one took a real IMAGE BUMP, two got new ReplicaSets with identical images (restart-only, but cold JIT, caches and connection pools). The highest-traversal service on the cluster was among them, so its server-side delta was confounded by an application version change; the run survived only because ~20 other services plus two 0%-traversal negative controls were untouched. **DETECTION METHOD — run this BEFORE grading any delta:** list ReplicaSets sorted by creation timestamp, then for each one created near the enrolment timestamp **diff ALL container images old-vs-new RS, not just `containers[0]`** — a database-auth-proxy or similar sidecar frequently occupies index 0, so a `containers[0]`-only check reports 'identical' and misses a real version bump. Also check whether new pods belong to a NEW ReplicaSet or an OLD one: pods appearing at the enrolment minute whose RS dates from months earlier are a scale or reschedule, not a confounder. **ON SOME CLUSTERS THE LABEL CANNOT BE LANDED ALONE, so plan for it** — where one infrastructure stack owns BOTH the namespace label and the application release, the enrolment apply may bump the release and roll the namespace with it (`learnings-istio.md#170`). Impact when that happens: the server-side control is destroyed for every redeployed service, and any criterion resting on a 0%-traversal control goes VOID if that control also moved. It also ACCELERATES waypoint coverage, which flatters the coverage row. **MITIGATION: read the ReplicaSet list FIRST, and if a release rode the apply, pre-select control services that were NOT redeployed before grading anything.**

172. **Any access-log-based method is UNOBTAINABLE on a cluster whose collector uses a namespace ALLOWLIST that omits the target namespace — and it fails as a plausible-looking empty result, not an error.** If the workload deploys into an excluded namespace, its logs are dropped at the collector and never reach the log store, so the whole method and any cross-check built on it silently return nothing. **MEASURED PROOF PATTERN, with a positive control, using the container-name label as the discriminator** (container logs carry it, Kubernetes-event streams do not): `sum by (cluster, namespace) (count_over_time({cluster="<c>", container_name=~".+"}[1h]))` and confirm the target namespace appears. Beware a namespace that shows a *small* line count but is entirely Kubernetes **events** with zero pod stdout — that reads as coverage and is not. **WORKAROUND: read the container log directly** (`kubectl -n <ns> logs <pod> -c <container> --since-time=<RFC3339>`, per pod across all replicas, parsed locally). At under ~1 rps the container log buffer trivially holds a full hour; at high volume it will not. **PREFERRED FIX is a narrow container-name filter, NOT admitting the whole namespace** — a busy application namespace can be a multi-million-lines-per-hour firehose. **GENERAL RULE: before promising a log-based method on any cluster, run the namespace-coverage query with a known-good control.** On clusters where the namespace is already admitted it silently passes, so the method itself gives you no reason to check. This is the same class as the standing rule in `learnings-istio.md#5`: **never report an absence without pairing it with the same query against a target where the answer must be non-empty.**

177. **EVERY Beyla sub-10 ms latency QUANTILE on this fleet is a linear-interpolation ARTIFACT, not a measurement — and Beyla is the app-time CONTROL, not the waypoint-hop detector.** (TICKET-NN, verified <gke-prod-cluster> + <aws-prod-cluster> 2026-08-18. Extends #113, which establishes Beyla is fleet-wide and names the `http_response_status_code` label trap.)
    - **ROOT CAUSE:** the `http_server/client_request_duration_seconds_bucket` series **omit the `le=0.005` (and `le=0.0`) buckets entirely** — the lowest present boundary is `le=0.01` — so `histogram_quantile` treats `[0, 10 ms]` as ONE bucket and interpolates linearly inside it. **REPRODUCE EXACTLY:** <aws-prod-cluster> `job=app-namespace/app-namespace/<identity-service>` 24h has `le=0.01` cumulative 1.8144 of `+Inf` 1.8911 = 95.9%; `0.01*(0.5/0.959) = 5.21 ms` = the reported p50 to 3 s.f. <gke-prod-cluster> `job=default/default/<auth-service>`: `le=0.01` = 165.60 of 203.42 = 81.4%; `0.01*(0.5/0.814) = 6.14 ms` = the reported p50 exactly. **The aggregate giveaway:** dozens of <aws-prod-cluster> service pairs report p50 EXACTLY 5.000 ms and p99 EXACTLY 9.9 ms.
    - **INDEPENDENT CONFIRMATION that the quantiles are wrong and the mean is not:** <aws-prod-cluster> `<identity-service>` mean (from `_sum`, exact) = 2.10 ms while its reported p50 = 5.21 ms. `mean ≥ 0.5 × median` always holds for non-negative data, so `2.10 < 2.6` is arithmetically impossible — the median must actually be below 5 ms.
    - **CONSEQUENCE: the playbook's "Beyla p99 delta < 5 ms" success criterion is UNMEASURABLE for any service under 10 ms** — a full 5 ms shift moves entirely inside one bucket and can be invisible or wildly overstated. **USE INSTEAD, in order:** (1) MEAN = `rate(_sum)/rate(_count)`, exact and sensitive to small shifts; (2) the bucket-honest fraction `rate(_bucket{le="0.01"})/rate(_count)`, i.e. share of requests ≤10 ms, which shifts cleanly; (3) the waypoint access log (`duration − upstream_service_time`, #166). Quantiles remain valid only ABOVE 10 ms where real boundaries exist (0.025/0.05/0.075/0.1/0.25…).
    - **STRUCTURAL LIMIT that decides what Beyla can be used for at all:** `http_server_request_duration` is **SERVER-side** (arrival→response inside the server process), so it is **blind to a waypoint hop added in FRONT of the server**; its before/after delta reads ~0 even if the hop costs real milliseconds. **It is the app-time CONTROL, not the hop detector.** For the client-observed side use `envoy_cluster_upstream_rq_time` per destination cluster, or the waypoint access log.
    - **COVERAGE CAVEAT on <gke-prod-cluster>:** ztunnel/istio-cni DaemonSets are 179/179 but `otel-beyla` is **176/176**, so 3 nodes have no Beyla eBPF coverage — Beyla L7 there is ~98.3% of nodes, not 100%.

184. **The control-plane half of a promotion can carry a COUPLED PAIR of riders that must not be split across PRs — an argument for keeping that half ATOMIC, not for splitting it further.** When one component gains a REFERENCE (e.g. an access-log provider name) whose DEFINITION lands in a sibling component in the same promotion, the two never straddle a merge boundary *as long as both components are promoted in one PR* — but they would if someone split them, **and the failure is SILENT: a consumer naming an absent provider emits no access log at all rather than erroring** (`learnings-istio.md#9`, `learnings-istio.md#159`, `learnings-istio.md#163`). 185. **A registry pull-through/hub rider that changes only the PATH SEGMENT needs NO imagePullSecret change — a `dockerconfigjson` secret is HOST-scoped (`https://<registry-host>`), not repository-path-scoped.** This is the concrete resolution of the risk usually flagged as 'on the cloud that uses an explicit pull secret this is a real risk, not cosmetic' (`learnings-istio.md#153`): the risk is real in principle and empirically zero for a host-preserving path change. **But confirm the SCOPE of the secret rather than assuming either way** — inspect the secret's registry key, and prove the positive with the secret list rather than reasoning from the identity model (`learnings-istio.md#157`). Related: because the host is unchanged, a host-level grep passes on both the old and new path and proves nothing — assert the full path ROOT with both halves (`learnings-istio.md#124`). **Also beware that the wiring path for such secrets in a wrapper chart is commonly stated wrongly** — it is usually a per-component `global.imagePullSecrets` in the provider values layer, not a top-level service-account field; read the chart.

193. **Sizing a waypoint from a measured soak: the equilibrium is arithmetic, the diurnal peak is nearly free, and COVERAGE GROWTH is the variable that actually breaks the ceiling.** From one graded window: `equilibrium_replicas = total_mcores / (hpa_target × cpu_request)` predicted where the HPA settles and how it oscillates, and `max_replicas × target × request` gives the sustainable RPS ceiling. Two things to project against, in this order:
    - **DIURNAL PEAK IS NEARLY FREE and is measurable in advance.** Measuring the namespace's own L7 curve at 30 m step over ~40 h gave a peak factor of only **~1.06×** over the graded window (enrolment happened to land at the daily peak) with an overnight trough at ~26% of peak. A 30-minute soak plus that curve is a stronger sizing basis than a longer soak without it.
    - **COVERAGE GROWTH IS UNBOUNDED BY THE WINDOW and is the real risk.** The waypoint carried only ~45% of namespace L7 traffic and was still climbing at window close (42 → 46 destination services). Projecting to ~90% coverage put required replicas ABOVE the configured max. **Raise `maxReplicas` before the next coverage step, not after.** Not an outage risk in itself — the CPU LIMIT was 4× the request, so saturating the HPA target degrades gracefully.
    - **Per-pod load is UNEVEN by cohort**: pods that existed before enrolment carry substantially more than pods added by the enrolment scale-up, because existing connections stay pinned to pods already in the Endpoints list. Do not read a per-pod mean as a per-pod expectation.

195. **What ambient egress control can and cannot express at 1.29 — six API-level facts that decide the design, and the one that CORRECTS `learnings-istio.md#78`.** The DNS-hostname ALLOW path and the raw-IP/default-deny path are different traffic paths, and conflating them is how a waypoint gets sold as a firewall replacement. **(1) `AuthorizationPolicy` HAS NO DESTINATION-IP MATCH.** The `Operation` message (`to.operation`) fields are exactly `hosts, ports, methods, paths` (+ their `not*`); `ipBlocks`/`notIpBlocks`/`remoteIpBlocks` exist ONLY in `Source` (`from`) and are source-side. **"DENY egress to 1.2.3.0/24" is not expressible**, at any maturity level. **(2) AMBIENT DOES NOT IMPLEMENT `REGISTRY_ONLY`** — an upstream maintainer, istio/istio discussion **#53021**: *"Ambient mode does not implement `REGISTRY_ONLY`."* He adds that even in sidecar mode it *"does not provide security guarantees"* — it merely fails to configure handling for unknown hosts. **This retires the fallback suggested in `#78`.** A true default-deny ztunnel egress policy (`Deny`/`Passthrough` modes) is a **Solo / ambientmesh.io Enterprise** feature, not upstream. **(3) `ServiceEntry.addresses` NO LONGER ACCEPTS CIDR** (restricted/removed since **1.23**, istio/istio **#52944**; a `ServiceEntry` may not mix single IPs and CIDR) — so pinning a churning anycast CDN range needs one entry per /32, which is not a design. **(4) THE CAPTURE PATH IS DNS, NOT IP.** A `resolution: DNS` `ServiceEntry` gets an auto-allocated VIP (**240.240.x.x**); the ONLY thing that lands a pod's connection on that VIP is DNS capture answering the lookup with it. A pod that `connect()`s straight to a public IP never touches the VIP, never matches the `ServiceEntry`, and is **passed through uncontrolled** — ztunnel's documented behaviour for unknown addresses. **(5) LINK-LOCAL AND UDP ARE STRUCTURALLY OUT OF REACH.** `169.254.0.0/16` (cloud metadata server) is not a mesh address and is never captured into a waypoint; ztunnel/waypoint are TCP/HTTP only, so **UDP/STUN/TURN/WebRTC media is never captured** either. Any threat model naming metadata-server exfiltration or UDP media needs a network-layer control, full stop. **(6) THE POLICY MUST CO-LOCATE WITH THE `ServiceEntry`, EVEN THOUGH THE WAYPOINT NEED NOT.** `AuthorizationPolicy(targetRefs → ServiceEntry)` must live in the **same namespace as the ServiceEntry**; cross-namespace *waypoint use* is separately GA (1.23+) via `istio.io/use-waypoint` + `istio.io/use-waypoint-namespace` + the waypoint Gateway's `allowedRoutes.namespaces.from`. So "cross-namespace `targetRefs` does not bind" is true as stated but is a **deployment-shape constraint, not a hard blocker** — co-locate the pair in the egress namespace and label the consumer namespace across. Also: wildcard-host `ServiceEntry` for TLS egress (`DYNAMIC_DNS`, `ENABLE_WILDCARD_HOST_SERVICE_ENTRIES_FOR_TLS`) is **alpha / flag-gated** and ambient wildcard egress is a known gap (istio/istio **#54540**) — do not plan on it. **NET DESIGN RULE: the egress waypoint is an excellent L7 hostname/SNI ALLOW + visibility plane and a poor enforcement boundary. It cannot retire an L4 default-deny.** Layer it: waypoint owns hostname allow + `istio_requests_total` + access logs on the DNS-captured HTTPS path; a network layer (VPC firewall, or NetworkPolicy/Cilium *where the CNI actually enforces it* — verify, several managed-Kubernetes defaults do not) owns IP default-deny, UDP media, link-local containment and non-HTTP TCP. **This also corrects the "block external domains / IPs" framing** in any waypoint-vs-alternative comparison: the domains half holds, the IPs half does not. See #77, #78, #11, `#103`, `learnings-network-policy.md#8`, `learnings-agentgateway.md`. (Source: research 2026-06-15 reconciling a chart comment against a waypoint research doc; refs istio/istio #53021, #52944, #54540, `architecture/ambient/ztunnel.md`, `istio.io/docs/reference/config/security/authorization-policy/`, `istio.io/docs/ops/configuration/traffic-management/dns-proxy/`.)

196. **Istio ambient upgrade mechanics: the component ORDER, why the ztunnel roll is genuinely zero-downtime, and the one connection class that is not.** **ORDER IS FORCED BY THE SKEW POLICY** — control plane must be **≥** data plane, and istiod supports data-plane components at most **one minor older**; a newer data plane than control plane is unsupported. So: **`istio-base` (CRDs, first — new istiod may require them) → `istiod` → `istio-cni` and `ztunnel` (order between these two does not matter)**. Under GitOps this is sequenced by MERGE ORDER, not by a deploy tool. **Rollback runs the sequence in REVERSE: data plane first, then control plane** — reverting the istiod bump while the data plane is still ahead creates the illegal skew. **WHY THE ZTUNNEL ROLL IS SAFE — the mechanism, not the vibe.** The new ztunnel starts on the node while the old one is still running and both bind the same port via **`SO_REUSEPORT`**; the kernel hands NEW connections to whichever socket is accepting, so **new connections never fail during the roll**. The old ztunnel then stops accepting and drains for `terminationGracePeriodSeconds`. **The ONLY casualty is a connection that outlives the drain window, which is RST'd** — i.e. long-lived gRPC streams, WebSockets, and persistent pool connections. Short-lived HTTP is structurally unaffected. Measured: 18 EKS nodes rolled in ~60 s with two ztunnel pods observed simultaneously Running+Terminating on ≥8 nodes, and 1000/1000 requests succeeded across the full window. **SIZE THE GRACE PERIOD FROM THE LONGEST-LIVED CONNECTION, not from the default** (upstream 30 s is far too short — and see `#19` for the two places the value must agree). **The escape hatch and its trap:** `updateStrategy.type: OnDelete` + cordon/drain gives per-node control for a strict zero-disruption window, but **GitOps will report the app Synced and Healthy while no pod has actually restarted** (the spec changed; the DaemonSet controller is deliberately not acting), and **you must switch back to `RollingUpdate` afterwards or every future upgrade silently requires manual draining.** **istio-cni is NOT in the data path** — it writes iptables at pod creation — so a CNI restart affects only pods being CREATED in the restart window; existing pods and their new connections are unaffected and `maxUnavailable: 1` is fine (contrast ztunnel's `maxSurge: 1 / maxUnavailable: 0`, per `#20`). **Pre-upgrade, the disruption-relevant checks are exactly four:** longest-lived TCP connection in enrolled workloads; the ztunnel DaemonSet's current `terminationGracePeriodSeconds`; istiod already at or above the target version; and the DaemonSet `maxUnavailable`. (Sources: an upstream maintainer, *ztunnel Shutdown Behavior*, blog.howardjohn.info/posts/ztunnel-shutdown/, Dec 2024; istio/istio **#51126** for the OnDelete/cordon-drain discussion; istio.io ambient Helm upgrade guide for the skew policy; live validation 2026-04-05 on an 18-node EKS cluster. Campaign-shaped siblings: `#135`, `#153`, `#182`.)

197. **Hot-labelling a namespace into ambient resets ESTABLISHED TCP connections, upstream has REJECTED the fix as a deliberate security position, and the disruption you measure afterwards is usually NOT the mesh.** Sharpens `#30`/`#31`/`#2` with the mechanism, the pins, and the attribution rule. **THE RACE:** labelling a namespace makes istio-cni inject the redirect rules into every running pod's netns (API-watch driven) while ztunnel is separately entering each netns to listen, driven by xDS. If the rules land before ztunnel listens, new connections get TCP RST. Since **1.24** moved from TPROXY (mangle) to **NAT REDIRECT** (istio/istio PR **#52622**), *existing* connections are reset too — the kernel invalidates flows that do not match the new NAT state, which conntrack ESTABLISHED/RELATED used to preserve under TPROXY. Tail latency across a 100+-pod namespace is **~1–2 minutes** (API-watch→xDS ~1–5 s; xDS→ztunnel ~5–30 s; then ~200–500 ms per pod, sequential per node, on both the iptables and the netns legs). **The rules, for recognising them in a netns dump:** inbound `iptables -t nat -A ISTIO_PRERT ! -d 127.0.0.1/32 -p tcp ! --dport 15008 -m mark ! --mark 0x539/0xfff -j REDIRECT --to-ports 15006`; outbound `ISTIO_OUTPUT … -j REDIRECT --to-ports 15001`. (Note `0x539` here is the redirect-exclusion mark and is a different mark from the `0x111` policy-routing fwmark in `#61`/`#63`.) **DO NOT WAIT FOR AN UPSTREAM FIX: PR #49106, which proposed preserving established connections, was REJECTED** — maintainers treat immediate enrolment as a security requirement. **Open issues worth knowing before you blame yourself:** #58514 (503 spikes during ambient pod rollout), #55937 (connection failures during namespace enrolment), #59135 (increased ambient latency at 1.29), #54544 (CNI stuck in "no ztunnel connection"), #55968 (iptables missing after node reboot). **THE ATTRIBUTION RULE, which is the durable half.** A born-enrolled rollout measured 6 failures in 950 requests (0.63%), clustered in ~1 s — and **none were mesh-caused**: the target had **no readiness probe and no `preStop` hook**, so kube-proxy had not removed the dying pod's IP from the Service endpoints when it began shutting down. That failure occurs identically with the mesh absent, and `preStop: sleep 5` eliminates it. **Before attributing ANY rollout-window failure to mesh enrolment, rule out the standard Kubernetes endpoint-propagation race — check for a readiness probe and a `preStop` hook first.** The same run is the positive evidence for the Kyverno born-enrolled strategy (`#31`): pods born with the label take the CNI init path, so there is no race and no reset, and it piggybacks on natural CI/CD cadence with no forced rollouts and no GitOps drift (Pod-level mutations are invisible to a controller that manages Deployments). (Verified 2026-04-01/03 at 1.29.1 on one GKE and one EKS cluster.)

198. **PriorityClass for the ambient components: the two DaemonSets are hardcoded and cannot be configured, istiod is the only gap, and the platform has a ResourceQuota rule that decides which class you may use.** Adds the source pins and the platform constraints to `#29`. **Upstream defaults at 1.29.1, read from the charts:** `ztunnel/templates/daemonset.yaml:191` and `cni/templates/daemonset.yaml:82` both set `priorityClassName: system-node-critical` **hardcoded — not exposed as a value, so there is nothing to configure and nothing that can be lost in a values refactor**; `istiod/templates/deployment.yaml:89-90` renders `global.priorityClassName` only `{{- if }}` it is set, and `istiod/values.yaml:328` defaults it to `""`, so **istiod ships at priority 0 — level with application workloads during node pressure.** Upstream's own values comment recommends setting it. **Set `system-cluster-critical` on istiod, NOT `system-node-critical`:** node-critical is for per-node infrastructure that must never be evicted (CNI, ztunnel); cluster-critical is for control planes whose brief absence does not immediately break traffic — istiod's caches and issued certs keep the data plane running, and the real exposure is cert expiry (~24 h default TTL) rather than instant outage. **THE PLATFORM CONSTRAINT THAT DECIDES THIS:** GKE requires a `ResourceQuota` in any namespace running `system-node-critical` pods (already needed for ztunnel/CNI), but **`system-cluster-critical` requires no ResourceQuota** — so adding it to istiod is a one-line values change with no companion object. Both classes are built-in on GKE and EKS (values 2,000,001,000 and 2,000,000,000, both `PreemptLowerPriority`), so no custom PriorityClass and no provider-specific override is needed. **GKE Autopilot reserves `system-node-critical` for Google system pods and forbids it for user workloads — `system-cluster-critical` is safe on both Standard and Autopilot**, which is another reason not to reach for the higher class. **Upstream provenance:** ztunnel was hardcoded at **1.21** after istio/istio **#47867** (an upstream maintainer: *"Agreed - CNI and ztunnel should both be critical"*; the failure it fixed was ztunnel stuck `Pending` during upgrades with *"0/8 nodes are available … No preemption victims found"*), earlier PR **#45960**; istio-cni since 2021 via **#32341**; the istiod recommendation is **#12786** (an upstream maintainer: *"+1 that works as the default"*), left at `""` upstream only for backward compatibility. **Blast radii, for sizing the argument:** evicting ztunnel breaks ALL mesh traffic on that node immediately; evicting istio-cni breaks only pods newly scheduled there; evicting istiod stops config pushes and cert issuance while existing traffic continues. `istio-base` deploys no pods, so it is not applicable. (Researched 2026-04-01 at 1.29.1 across one GKE and one EKS cluster.)

199. **A "which namespaces can we enrol?" audit needs a NEVER-ENROL taxonomy with a stated blast-radius rationale per category — and the highest-risk category is the one that looks most harmless.** The categories, and why each is excluded, transfer to any mesh on any estate: **(a) the mesh's own namespace** — the data-plane proxy intercepting its own control-plane traffic is a circular dependency that breaks the mesh; **(b) Kubernetes core** (`kube-system`, `kube-node-lease`, `kube-public`) — breaking cluster DNS or kube-proxy is a cluster-wide outage; **(c) ADMISSION WEBHOOKS** (policy engines, autoscaler webhooks, cert issuers) — **this is the one to be strict about: if the proxy has a momentary blip, webhook calls fail and ALL pod creation cluster-wide is blocked.** The blast radius is the entire cluster, and the benefit is one hop of mTLS; **(d) node-level agents** (security/monitoring DaemonSets) — they report node events, not in-cluster application traffic, so interception adds latency to exactly the telemetry you need during an incident, for no mTLS gain; **(e) outbound-only operators** (DNS controllers, backup, secrets sync) — they talk to external cloud APIs, not in-cluster services, so enrolment buys nothing; **(f) cloud-managed namespaces** — not your workloads, and the provider reconciles labels off them; **(g) single-pod CRD controllers** whose only peer is the API server — minimal benefit, non-zero risk. **A namespace is enrollable only if ALL of: standard Deployment/StatefulSet workloads (not DaemonSets, webhooks, or node agents); no admission-webhook or control-plane role; pods currently healthy; observed traffic with other enrolled namespaces; and not ephemeral** (PR-preview and throwaway namespaces churn faster than the audit). **THE STRICT-mTLS COROLLARY that makes this audit load-bearing rather than cosmetic:** for every namespace you leave unenrolled, ask whether any ENROLLED service depends on it — if yes it MUST be enrolled before STRICT or the dependent breaks; if its only inbound is a metrics scraper, it is safe to leave out, **because the scraper is the initiator and simply skips unreachable targets**. Derive that answer from a per-namespace caller/callee query over a window long enough to catch infrequent connections (24 h minimum; see `#122` for why the principal set accumulates and short windows silently omit callers). **Also classify SKIP separately from NEVER**: zero-pod, crash-looping, and being-decommissioned namespaces are not policy exclusions and should not be enshrined in one — they are "come back later". (Playbook Part A, `docs/istio-ambient/playbooks/namespace-enrollment-analysis.md`; sharpens `#108`, which covers why the audit must be namespace-scoped before the pod loop.)

200. **Choosing between a mesh-native waypoint and a gateway-controller waypoint (the "sandwich" model) is decided by ONE capability, not by the feature count — and the count is misleading in both directions.** Both controllers commonly already run, so this is not a deployment-cost decision (`#55` covers the sandwich mechanics). **The decider: only the mesh-native waypoint processes `ServiceEntry` and `AuthorizationPolicy`.** A gateway-controller waypoint has no `ServiceEntry` handling at all, so the egress hostname-allow pattern (`ServiceEntry(resolution: DNS)` + auto-VIP + `AuthorizationPolicy(targetRefs)`, see `#195`) has **no equivalent** — reproducing it means hand-built Services pointing at external IPs with no DNS auto-allocation, a different policy CRD with no SPIFFE awareness, per-host route rules, and no TLS-origination path. That is a DIY stack with no upstream documentation. **Second decider, easy to miss: the metric families differ.** A mesh-native waypoint emits `istio_requests_total` and therefore feeds existing mesh dashboards and alerts unchanged; a gateway-controller waypoint emits only its own proxy stats, so adopting it silently obsoletes every L7 dashboard and alert keyed on the mesh metric names. **Where the gateway controller genuinely wins** — circuit breaking (a first-class policy CRD vs. mesh-side Lua/Wasm at alpha), richer edge auth (OIDC/JWT/API-key/basic in one CRD vs. `RequestAuthentication`), and global rate limiting — are all *additions*, and the two can coexist per-service, so **none of them is a reason to choose it as the default**; adopt it later for the specific service that needs them. **Where the mesh-native one is simply simpler:** one policy language across L4 and L7 with SPIFFE identities, fault injection as a route filter rather than a low-level xDS patch, and a five-line `Gateway` instead of a proxy CRD plus an HBONE port arrangement. **Equivalent, so not decision-relevant:** Gateway-API routing, retries/timeouts, request mirroring, Wasm extension. **Prerequisite to check before assuming the egress pattern works at all:** DNS capture must be on — the CNI's ambient DNS-capture flag (set by the ambient profile) and the control-plane IP-autoallocate flag (defaults on) — because without it nothing lands on the 240.240.x.x VIP. **Sizing, for either:** a waypoint hop costs roughly ~0.5–1.0 ms p99 against ztunnel's ~0.1–0.3 ms, and enrolment should start per-service via the use-waypoint label rather than namespace-wide, because east-west volume is much larger than ingress. **Do not carry those two numbers as measurements** — they are vendor-doc figures; `#165`/`#180` carry ours, which were measured. (Comparison 2026-06; see `learnings-envoy-gateway.md`, `learnings-progressive-delivery.md`.)

201. **Enrolling a namespace onto a waypoint changes the CALLER CENSUS by construction, because the waypoint becomes a `source_workload` in its own right — a post-enrolment rise in "mesh-sourced share" is an accounting shift, not a new caller.** The waypoint terminates the connection and **re-originates** upstream, so every hop it proxies is now attributed to it rather than to the original client on the destination-side series. Measured: the mesh-sourced share of destination-side connections (with the non-mesh `unknown` / metrics-scraper / gateway families excluded) moved **2.9% → 6.96% over 24h** across one enrolment, with no change in who was actually calling. **Consequences.** (1) **Any caller inventory taken before and after enrolment is not comparing like with like** — a `source_workload` allowlist derived pre-enrolment will suddenly see an unfamiliar principal, and one derived post-enrolment loses the original clients behind the waypoint. Re-derive rather than diff (`#122` gives the two-lens method and the window trap; `#174` gives the query). (2) **Do not open an incident on the share moving at the enrolment boundary** — check whether the delta is explained by the waypoint's own new series before looking for a cause. (3) This compounds with `#168`: coverage keeps GROWING for hours afterwards as established keep-alive connections finally recycle onto the waypoint, so the share is still climbing when a T+1h reading is taken. **Take the caller census either entirely before or entirely after, and say which.**

202. **Inspecting host or pod iptables from another namespace REQUIRES `--pid`, because `iptables-save` reads `/proc/self/net` — an `nsenter` that enters only the mount and network namespaces silently reads the INVESTIGATOR'S tables and reports them as the target's.** This is the most dangerous shape of netns debugging because it never errors: you get a full, well-formed ruleset that belongs to the wrong context, and on a host where the investigating pod has no istio rules it reads as "the rules are missing" — the exact conclusion the investigation was trying to test. **Always `nsenter --target <pid> --mount --net --pid ...`**, and **prove the entry** by asserting something you know is true only inside the target (a rule chain name, an interface, a hostname) before trusting anything you read. **Two related facts for ambient specifically.** (a) Since 1.24 the interception is fwmark policy routing, so for ztunnel capture the things to read are `ip rule list` and `ip route show table 100`, NOT `iptables-save` — see `#61`/`#63`; `iptables-save` is the right tool for the istio-cni-written in-pod REDIRECT rules (`ISTIO_PRERT`/`ISTIO_OUTPUT`, `#197`) and for the node-level chains, and those are what needs the pidns. (b) **Ephemeral debug containers do not get `CAP_NET_ADMIN` by default, so `iptables-save` fails there for a reason unrelated to namespaces** — `ip rule`, `ip route show table <N>` and `ss -tlnp` all work without root and should be the first reach.

203. **The istio `krt` controller-framework memory leak is CONTROL-PLANE side, and the thing that TRIGGERS it is a data-plane label change — so watching the waypoint pod misses it entirely.** `krt` leaked when the key used in a `Fetch` filter changed — **relabelling a pod to point at a different waypoint is exactly such a change** — leaving stale reverse-index entries that were never reclaimed. **Fixed upstream in 1.29.5**, so anything at 1.29.1–1.29.4 that does waypoint re-enrolment or waypoint renaming is exposed. **The operational consequence is the one to remember: the container to watch is `discovery` in `istio-system`, NOT `istio-proxy` in the waypoint's namespace.** A memory check scoped to the waypoint Deployment — the intuitive place, since the waypoint is what changed — is structurally incapable of seeing it. **Generalises beyond this bug:** in a control-plane/data-plane architecture, a data-plane configuration change is executed by the control plane, so the resource cost of churning data-plane config lands on the control plane. **Whenever a plan involves repeated relabelling, re-enrolment, or renaming of data-plane objects, put the control-plane process's own memory on the watch list before starting**, and take the reading before the churn begins — it is another quantity that is unobtainable afterwards (`#167`). See `#7` for the waypoint name/namespace mismatch class that leads people to relabel repeatedly in the first place.

204. **Roll STRICT mTLS out as PER-NAMESPACE OPT-IN, never as mesh-wide STRICT with carve-outs — the two are not equivalent risk, and the asymmetry is in what a MISTAKE costs.** Both reach the same end state, so the choice looks like taste. It is not. **Mesh-wide STRICT + exceptions fails OPEN on your enumeration:** any namespace you forget to exclude loses non-mesh traffic the moment the policy lands — external load-balancer health checks, ingress from outside the mesh, webhook callers, tunnel traffic — and it fails *silently* from the mesh's point of view, because rejecting plaintext is the policy working. The blast radius is every namespace you did not think of, simultaneously, and **rollback is a mesh-wide config change made under pressure.** **Per-namespace opt-in inverts every one of those:** blast radius is one namespace, ingress paths are untouched unless explicitly targeted, and **rollback is deleting a single object** — with the caveat that under a self-healing GitOps controller a bare delete is reverted within minutes, so establish the real rollback per target before you need it (move the pinned tag, or disable auto-sync first; `#182`, `orgs/<org>/istio.md#7`). **Order the namespaces by how well you can predict their inbound set, not by importance:** fully-internal test workloads first, then application namespaces with no external ingress. **The namespaces to defer, and why — this is the same taxonomy as the enrolment audit (`#199`) but the test is different:** enrolment asks "does this benefit from mTLS?", STRICT asks "**does anything reach this from outside the mesh?**". Gateway/ingress namespaces receive plaintext from the load balancer; telemetry namespaces may receive pushes from non-mesh sources; tunnel/VPN namespaces carry traffic from a control plane you do not run; anything hosting a webhook receiver is called by the API server, which is not in the mesh (`#37`/`#69`/`#73`). **Per namespace, the gate is one query, not an opinion:** decompose inbound by security-policy class over a window long enough to catch batch callers, and confirm the only classes present are mesh-encrypted and the known probe floor. Then apply, watch for rejected plaintext, and graduate — one namespace at a time, with the previous one soaked. **The mesh-wide default stays permissive throughout;** it is the thing that makes every step reversible.

205. **PERMISSIVE mTLS is a MIGRATION state, not an enforcement posture — but the "identity policy is bypassable under PERMISSIVE" framing is only true for ONE policy shape, and #17(5) already settled which.** Promoted 2026-08-28 from a project-scoped memory (research dated 2026-06-27, asserted stable across 1.29/1.30) and **reconciled against `#17`, which is source-pinned and wins wherever the two differ.** The memory's premise is correct and is the part to keep: **a plaintext connection carries an EMPTY principal**, so any rule keyed on `source.principals` / `source.namespaces` cannot match it. Istio's own reference states it verbatim — *"The principal will be empty if plain text is used."* — and the best-practices page says it is *"strongly recommended to always use principal and namespace fields … with strict mutual TLS … to avoid … policy bypass when plain text traffic is used with the permissive mutual TLS mode."* **What that empty principal DOES depends entirely on the policy shape, and the three cases do not agree:** (a) **`ALLOW` + `principals` FAILS CLOSED** — a non-match under ALLOW semantics is a denial, and `#17` confirms it at source: an unauthenticated/plaintext caller (empty identity, `ztunnel/src/rbac.rs:88-92`, principals matched with `spiffe://` stripped at `rbac.rs:266-274`) **can never be admitted** by an ALLOW-with-principals policy. (b) **`DENY` keyed on POSITIVE principals FAILS OPEN — this is the actual bypass.** Plaintext matches no listed principal, the DENY does not fire, and the request proceeds. (c) **`DENY` + `notPrincipals` FAILS CLOSED**, and this is the one that is *"exactly backwards from the intuition"* per `#17(5)`: Istio builds it as `NOT(principal match)` (`pilot/pkg/security/authz/model/model.go:316-340`), so plaintext's absent principal makes the inner match false, the negation true, and **the DENY matches**. **NET RULE: under PERMISSIVE, ALLOW-list segmentation still holds but DENY-list segmentation leaks — so a mesh whose segmentation is expressed as denials is not enforcing anything until mTLS is STRICT.** The `DENY` + `notPrincipals: ["*"]` guard pattern is worth knowing but is not a substitute: it *forces* mTLS on the workloads it covers (effectively strict for them), it does not make a plaintext client safe. **⚠️ UNVERIFIED, carried as-is from the memory:** the version claim "stable across 1.29/1.30" and the two doc quotes above are DOC-sourced only — no `file:line` was recorded for them, and per R2 docs are secondary. The mechanism claims in (a) and (c) are NOT unverified; they carry `#17`'s source pins. Scope limit worth restating: all of this governs **mesh** traffic only — non-mesh, UDP and raw-IP egress need the network layer regardless of mTLS mode (`#195(5)`, `learnings-network-policy.md#9`).
