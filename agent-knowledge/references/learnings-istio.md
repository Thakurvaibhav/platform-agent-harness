# Istio (Ambient Mode) Learnings

See also: `learnings-network-policy.md`, `learnings-observability.md`, `learnings-envoy-gateway.md`, `learnings-operators.md`

Istio ambient-mode and service-mesh mechanics -- ztunnel/istio-cni DaemonSet architecture, waypoint proxies, PeerAuthentication/STRICT mTLS migration, AuthorizationPolicy semantics, Telemetry API attachment, and mTLS metric interpretation traps. Pinned to Istio 1.24-1.29.x source and public upstream issues where possible; re-verify against your own version.

## Ambient mode architecture

1. **ztunnel and istio-cni are node-level DaemonSets, not per-workload sidecars -- they cannot run two versions side by side on the same node, so revision-based (canary) upgrades do not apply to them.** Revision-based/canary upgrades work for istiod and waypoint proxies because those are per-workload or per-namespace resources; ztunnel and istio-cni are one DaemonSet per node, and a canary rollout would require two versions coexisting on the same node, which the architecture does not support (true since ambient's 1.24 GA and unchanged through 1.29.x). Treat data-plane (ztunnel + istio-cni) upgrades as an in-place DaemonSet rolling update, gated separately from the istiod control-plane upgrade rather than folded into the same canary mechanism.

2. **Ambient's packet-interception mechanism changed from TPROXY to iptables REDIRECT at 1.24 -- that change is why enrolling a namespace with running pods resets their TCP connections.** Pre-1.24 ambient used TPROXY, which preserves already-established connections via conntrack when interception activates mid-connection. 1.24+ uses REDIRECT (NAT), which does not: enrolling a namespace live (applying `istio.io/dataplane-mode=ambient` to a namespace with pods already running) invalidates existing NAT state and resets open TCP connections during the window before ztunnel becomes the intercepting path. Prefer per-pod gradual enrollment -- label pods before they start, or roll them shortly after labelling the namespace -- over a bulk namespace-label flip against a live, traffic-serving namespace.

## mTLS and metric semantics

3. **ztunnel is an L4-only proxy -- it has zero visibility into HTTP status codes, paths, or any request-level data, and no ambient deployment gets L7 metrics without a waypoint.** `istio_requests_total` (the L7 request-rate/latency metric) is emitted only by a waypoint proxy; a ztunnel-only ambient mesh can produce only `istio_tcp_connections_opened_total` and its siblings, with `connection_security_policy` as the sole mTLS-relevant label. Building an L7 SLO, error-rate dashboard, or request-latency alert against an ambient mesh with no waypoints deployed will silently have no data source to query -- waypoints are not an optional add-on for L7 telemetry, they are the only source of it.

4. **Counting "workloads enrolled in ambient" by filtering `istio_tcp_connections_opened_total` on `connection_security_policy="mutual_tls"` undercounts -- use `reporter="source"` instead.** `mutual_tls` only appears once BOTH sides of a connection are mesh-enrolled and have successfully negotiated HBONE; a workload whose peer is outside the mesh, or has not yet negotiated, never shows `mutual_tls` even though ztunnel is actively intercepting its outbound traffic. `reporter="source"` counts any workload whose outbound traffic ztunnel captures at all, independent of the destination's enrollment state, and is the correct signal for "is this workload's traffic being intercepted by ztunnel."

5. **`istio_tcp_connections_{opened,failed}_total` double-counts intra-mesh connections unless you pin the `reporter` label -- and the inflation factor is traffic-mix-dependent, not a fixed constant.** Both ends of a connection report independently in Istio's telemetry model: an intra-mesh connection is recorded once by the source-side ztunnel and again by the destination-side ztunnel, so a query without `reporter` sums both. Measured inflation (no-reporter vs `reporter="destination"`) varied roughly 1.05x to 1.8x across clusters with different traffic mixes -- it is a property of how much traffic is intra-mesh on a given cluster, not something you can hardcode as a correction factor. Always pin `reporter="destination"` for a destination-side view (or `reporter="source"` for a source-side view), and **never compare a baseline taken without the label against a later reading taken with it** -- the delta alone can manufacture a large fictitious improvement or regression that has nothing to do with real traffic change.

## Waypoint proxies and the Telemetry API

6. **The `istio.io/waypoint-for` label on a waypoint Gateway only accepts `service`, `workload`, `all`, or `none` -- `namespace` is not a valid value, and setting it produces no validation error while the waypoint silently intercepts nothing.** The label controls which traffic *type* the waypoint captures: `service` for traffic addressed to a Service ClusterIP, `workload` for traffic addressed directly to a pod IP, `all` for both, `none` to disable capture. This is an easy mistake because enrollment *breadth* -- which namespaces or services route through the waypoint at all -- is a completely separate mechanism, the `istio.io/use-waypoint` label applied to a namespace or individual services. There is no `namespace` scope value because `waypoint-for` describes traffic type, not enrollment breadth. (Istio 1.29.x Gateway API waypoint model.)

7. **Before pointing a namespace or service at a waypoint with `istio.io/use-waypoint`, verify the waypoint's actual configured name and the Gateway's namespace -- a mismatch on either one fails completely silently.** If the label's value does not match any existing waypoint Gateway name, nothing errors: the namespace is simply never routed through a waypoint, and traffic flows exactly as it did before the label was applied. If the waypoint Gateway lives in a different namespace than the one being labelled, an additional `istio.io/use-waypoint-namespace` label is required -- omit it and you get the same silent no-op. Separately, a waypoint Gateway is stamped `istio.io/waypoint-for: service` by default (#6), meaning it only intercepts Service-VIP-addressed traffic; direct pod-IP traffic -- a metrics scraper hitting a pod's target port, or any client that resolves and dials the pod IP -- bypasses the waypoint regardless of whether the label is correct. **UNVERIFIED at source level:** the label/namespace-mismatch failure mode is recorded from observed behaviour with no `file:line`; confirm against the waypoint-attachment controller source at your pinned version.

8. **Never set a static `deployment.spec.replicas` inside the ConfigMap a waypoint's `infrastructure.parametersRef` points at if an HPA also manages that Deployment -- istiod's own reconciliation will fight the HPA on every restart or config change.** istiod's waypoint auto-deployment controller patches the waypoint Deployment from the `parametersRef` ConfigMap's `deployment` key on every reconcile (istiod restart, config change). If that patch includes a static `replicas` value, each reconciliation resets the replica count back to it, silently undoing whatever the HPA had just scaled to -- no error, just a Deployment that never holds its HPA-assigned replica count. Omit `replicas` from the ConfigMap when HPA is enabled (a conditional in the chart template works); set a static `replicas` only when there is no HPA and the goal is a non-default count (Istio's own default is 1 replica). **UNVERIFIED at source level:** recorded from observed istiod behaviour with no `file:line`; verify against the istiod waypoint-controller source at your pinned version.

9. **A Telemetry resource that targets a waypoint proxy via `selector` is silently accepted by istiod and never takes effect -- waypoints only honour `targetRefs`.** At Istio 1.29.x, `ShouldAttachPolicy` (`pilot/pkg/model/policyattachment.go`) special-cases waypoints: for a Gateway-API workload, `if p.IsWaypoint { return false }` whenever `len(targetRefs)==0`. A Telemetry with `providers: [{name: envoy}]` and a `selector` matching the waypoint pod is accepted by the API server, reports healthy, and does nothing -- `push.Telemetry.AccessLogging()` returns empty for that proxy, and the waypoint falls back to whatever `meshConfig.accessLogFile` happens to be (`pilot/pkg/networking/core/accesslog.go`). Fix: attach with `spec.targetRefs: [{group: gateway.networking.k8s.io, kind: Gateway, name: <waypoint-gateway-name>}]`, matched by istiod against the pod's own `gateway.networking.k8s.io/gateway-name` label -- and drop the selector entirely, since the CRD only permits one of the two.
    - **A custom `envoyFileAccessLog` extensionProvider that no Telemetry references is inert and harmless to ship** -- but the inverse is a silent trap: a Telemetry naming a provider that does not exist in that cluster's `meshConfig.extensionProviders` makes istiod's provider lookup return nil, and the waypoint emits **no access log at all**, with nothing surfaced as an error anywhere. Keep the extensionProvider declaration and any Telemetry referencing it in the same rollout scope so the two cannot drift apart.
    - **On a waypoint's own access log, `%DOWNSTREAM_PEER_URI_SAN%` is always empty.** The per-request HTTP access log is emitted by the `main_internal` Envoy listener, an internal listener with no downstream TLS context. The caller's SPIFFE identity is available instead as `%FILTER_STATE(io.istio.peer_principal:PLAIN)%`, populated by istiod's own `connect_authority` network filter on the adjacent `connect_terminate` listener (`pilot/pkg/xds/filters/filters.go`). A log format copied from a sidecar-proxy example will silently print an empty caller-identity field on a waypoint.

10. **Changing `meshConfig` (`accessLogFile`, `accessLogEncoding`, `extensionProviders`) only edits the `istio` ConfigMap in `istio-system` -- it does not touch ztunnel or istio-cni at all.** istiod hot-reloads its own ConfigMap, but ztunnel and istio-cni are separate DaemonSets that never read `meshConfig`, so an operator expecting a mesh-wide config change to visibly affect ztunnel logs or behaviour will correctly see nothing change there. Registering a brand-new `extensionProvider` name may additionally require an istiod restart before the Telemetry API recognises it, even though the ConfigMap already contains the new entry. **UNVERIFIED at source level** for the restart half of this claim -- worth a source pass against istiod's config-reload path before treating it as settled.

## Egress

11. **Ambient mode has no built-in default-deny-egress primitive -- this is a maintainer-confirmed gap in upstream Istio, not a missing feature you failed to find.** Per an Istio maintainer on the project's own GitHub Discussions (`istio/istio#53021`, 2026-05-29): *"Ambient mode does not support default-deny egress. L4 AuthorizationPolicies can deny specific traffic, but there's no single policy that denies all egress."* A default-deny egress posture in ambient requires L7 waypoint proxies fronted by an explicit DENY-all-then-ALLOW-specific `AuthorizationPolicy` per service; for cluster-wide egress enforcement without deploying waypoints everywhere, rely on a VPC/cloud firewall or NetworkPolicy instead of expecting Istio itself to provide it.

12. **Egress waypoints must be scoped `scope: workload`, not the ingress-waypoint default `scope: service` -- external egress targets are pod-to-raw-IP, and a `service`-scoped waypoint only intercepts Service-VIP-addressed traffic.** There is no ClusterIP for an arbitrary external host, so a waypoint left at the default service scope captures nothing on the egress path. The source namespace additionally needs `istio.io/use-waypoint: <egress-gateway-name>` set at the namespace or workload level, and must itself be ambient-enrolled, or egress traffic never reaches the waypoint to be captured in the first place. **UNVERIFIED at source level:** recorded from observed behaviour with no `file:line`; verify the `scope` field's effect on ztunnel's egress-capture matching against the ztunnel/istiod source at your pinned version.

## Control-plane alerting metrics

13. **At Istio 1.29.1 there is no always-present xDS reject/error counter, and a production alert on xDS errors must be data-plane-agnostic or it will silently never arm on waypoint-less clusters.** Source-confirmed at `istio/istio` tag 1.29.1: `pilot_xds_push_errors` does not exist in this release line (removed/renamed) -- an alert built on it is a permanent false negative. The correct proxy-NACK counter is `pilot_total_xds_rejects` (`pkg/xds/monitoring.go`, incremented by `IncrementXDSRejects` in `pkg/xds/server.go`'s `ShouldRespond()`), but it is a lazy `NewSum` -- absent from the metrics index until the first real NACK, so `absent()==1` in a healthy steady state is expected, not a bug. Critically, it is an Envoy-NACK metric: on a waypoint-less ambient cluster the only xDS client is ztunnel over the custom WDS path, which never increments it, so the counter is structurally unarmable there regardless of cluster health. **Validating an alert on this metric against a cluster that has waypoints deployed proves nothing about a cluster that does not** -- gate any check on it to "waypoint deployed" and re-derive that scope per cluster rather than inheriting the premise from a prior note. The startup gauges `pilot_conflict_inbound_listener` and its outbound-listener counterpart are always-present and are the better choice for a data-plane-agnostic control-plane alert.

14. **The config-validation-webhook REJECT counter is `galley_validation_failed`, and unlike an Envoy-NACK metric it IS data-plane-agnostic -- it arms even on an ambient cluster with no Envoy proxy anywhere.** Source-confirmed at 1.29.1: the counter incremented when istiod's validating webhook rejects a config admission is `galley_validation_failed` (`NewSum` "Resource validation failed", `pkg/webhooks/validation/server/monitoring.go`, incremented by `reportValidationFailed()` with a dry-run guard so only real admissions count). Do not confuse it with `galley_validation_config_update_error` (a different file, `controller/monitoring.go`) -- that one counts Kubernetes webhook-configuration update errors, not rejected user configs; same-sounding name, wrong signal. Because `galley_validation_failed` is control-plane-intrinsic rather than an Envoy NACK, it can arm on a cluster whose only xDS client is ztunnel, unlike `pilot_total_xds_rejects` (#13). It is itself a lazy counter, absent until the first reject -- confirm it is actually wired up by checking that its success sibling, `galley_validation_passed`, is live and non-lazy on the same cluster before trusting `absent()==0` as "healthy" rather than "never fired."

## CNI chaining and upstream bugs

15. **A CNI plugin that rewrites its host conflist file wholesale on every restart (rather than merging into it) will silently un-enroll every pod from a chained CNI like istio-cni -- and Istio's fix for this is a real, shipped, default-OFF flag.** The failure mode: `containerd`'s `go-cni` picks whichever `.conflist` file in `/etc/cni/net.d/` sorts lexically first (`opts.go`, stable since containerd v1.7.0). If the primary CNI's config file (a numerically-prefixed vendor conflist) is regenerated from a baked-in template on every container restart, and that regeneration does not preserve a chained plugin's stanza, the chained plugin silently drops out of pod networking from that point on -- no error, no event, just pods that stop being captured. Istio's fix, `cni.istioOwnedCNIConfig` (`istio/istio#56156`, shipped in 1.27, present unchanged through 1.29.x, default `false` in `manifests/charts/istio-cni/values.yaml`), makes istio-cni write its own lexically-earlier `02-istio-cni.conflist` instead of depending on chaining into the primary. Cilium and Antrea solve the identical problem the same way (their own lexically-earlier conflist plus a watch-and-reassert loop). **Scope the flag to whichever CNI provider in your fleet actually rewrites its conflist wholesale on restart** -- enabling it elsewhere trades a real fail-open security window for a stale-config-drift window where the risk it closes does not exist.

16. **Restarting ztunnel or istio-cni breaks every already-running kernel-mode network proxy on that node -- a confirmed live upstream bug (`istio/istio#61027`), not a problem in the proxy.** On restart, ztunnel loses its in-pod inbound state; istio-cni's startup reconcile then re-feeds every already-running pod to the fresh ztunnel instance. For a pod that was already serving traffic, this re-attach produces a broken inbound path: connections hang for the full negotiated timeout with zero bytes transferred, then fail with a deadline-elapsed error. Only kernel-mode proxies -- those that create their own tunnel interface -- are affected; userspace-mode proxies never create that interface and are immune. The only known fix is to recycle the affected pod (`kubectl rollout restart` on its StatefulSet/Deployment) after any ztunnel or istio-cni restart. The same shape -- fresh pods are fine, already-running ambient-enrolled pods break on a data-plane restart, fix is to recycle them -- recurs across multiple separate upstream reports. **Treat "recycle affected pods after any ztunnel/istio-cni restart" as a general mitigation for any long-lived, kernel-mode network proxy running under ambient**, not a vendor-specific workaround.

## AuthorizationPolicy semantics

17. **Several AuthorizationPolicy authoring mistakes at Istio 1.29 are silent -- they do not error, they just deny every caller or scope far wider than intended.** Confirmed against `release-1.29` source and live traffic.
    - **`principals` never take a `spiffe://` prefix -- Istio prepends it itself** (`pilot/pkg/security/authz/model/generator.go`). Copying a value straight out of `istio_tcp_connections_opened_total{source_principal=...}` (which reports the full `spiffe://cluster.local/ns/X/sa/Y`) into a policy's `principals` field produces a double-prefixed string that matches nothing. An ALLOW policy whose `principals` match nothing denies every caller once enforced -- with no error at apply time.
    - **`to.operation.hosts` matches the literal `:authority` HTTP header, not a resolved FQDN** (`model.go`, `generator.go`). Measured across tens of thousands of live in-cluster requests, callers sent short Service names or `svc:port`, essentially never the fully-qualified `svc.namespace.svc.cluster.local` form -- an FQDN-only `hosts` list matches close to zero real traffic.
    - **`targetRefs: [{kind: Gateway}]` pointed at a waypoint attaches the policy to every service routed through that waypoint**, not just the one intended (`policyattachment.go`, the waypoint listener builder) -- a namespace-wide blast radius the moment the namespace carries `istio.io/use-waypoint`. Scope to one service instead with `targetRefs: [{group: "", kind: Service, name: <svc>}]`.
    - **A `DENY` policy keyed on `notPrincipals` is NOT bypassable by sending plaintext -- the opposite of the intuitive reading.** Istio compiles it as `NOT(principal match)`; an unauthenticated/plaintext caller has no principal, so the inner match is false, the negation is true, and the DENY matches -- plaintext gets denied, not waved through. The bypassable form is the reverse: a DENY keyed on *positive* principals, which an identity-less caller trivially fails to match and therefore evades.
    - **ztunnel silently discards any AuthorizationPolicy that carries `targetRefs`** (`ambient/authorization.go`) -- a Gateway- or Service-targeted L7 policy never falls back to L4 enforcement at ztunnel, and conversely a selector-based policy is ignored by waypoints entirely. The L4 (ztunnel) and L7 (waypoint) enforcement layers each need their own separate policy resource; one policy cannot cover both.

18. **A `dry-run` AuthorizationPolicy's safety depends entirely on every ztunnel's version, not on the policy itself -- istiod's fail-safe only protects clusters where the whole fleet has already upgraded.** Contrary to the natural worst-case assumption, when the feature flag enabling ambient dry-run policies is unset, istiod does not ship a policy carrying `istio.io/dry-run: "true"` to ztunnel at all (`ambient/authorization.go` returns nil with an unsupported-value status) -- a dry-run policy is a pure no-op on a flag-less cluster. But once that flag is turned on, **older ztunnel builds will accept the same dry-run policy and hard-enforce it instead of only logging it** -- documented directly in the flag's own docstring in istiod's feature-flag source (`pilot/pkg/features/ambient.go`). That makes "every ztunnel in the cluster is Ready and at or above the version istiod assumes" a load-bearing precondition to check before enabling the flag, and again before any ztunnel upgrade or rollback while dry-run policies exist -- a mixed-version rollout window can silently turn a shadow-mode policy into a live enforcement outage.

## Operational hardening

19. **ztunnel's graceful-drain behaviour is governed by two separate settings that must agree, and the upstream chart default for both is short relative to long-lived connections.** The podSpec's `terminationGracePeriodSeconds` (the kubelet's SIGKILL timer) and the container env `TERMINATION_GRACE_PERIOD_SECONDS` (ztunnel's own internal drain timer) are meant to carry the same value. If a values refactor overrides one and not the other, the kubelet can SIGKILL ztunnel mid-drain while ztunnel's own drain logs still look clean and uneventful -- silently reopening a connection-reset window on every rolling restart. The upstream chart default is 30 seconds for both, which is short for connections with multi-minute keepalives; treat any override of either setting as incomplete until you have confirmed the other moved with it.

20. **A DaemonSet's `.status.numberReady` cannot be read as node coverage during a surge rollout -- it will under-report true coverage.** ztunnel's upstream chart ships `maxUnavailable=0, maxSurge=1`: the new pod on a node must go Ready before the old one is removed, so every node keeps a working ztunnel throughout the roll. But mid-surge a node briefly hosts two ztunnel pods (one starting, one still serving), so `numberReady` reads low relative to true readiness -- observed showing roughly half the expected ready count on a fleet where the actual node-level coverage gap was zero. **The correct coverage measure during a surge roll is a set difference, not the status field:** (nodes with a schedulable, Ready kubelet) minus (nodes with at least one Ready ztunnel pod) should equal zero. istio-cni, by contrast, typically ships `maxUnavailable=1, maxSurge=0` -- applying ztunnel's zero-node-gap expectation to a DaemonSet with that rollout shape will fail every roll by design, since one node legitimately has no CNI pod mid-roll.
