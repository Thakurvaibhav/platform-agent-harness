# Kubernetes ServiceAccount & Identity Learnings

Read this file when working on ServiceAccount separation, cloud Workload Identity (GKE WI, EKS IRSA, AKS WI), image-pull secrets, or cloud-IAM bindings.

See also: `learnings-crossplane.md`, `learnings-workload-debug.md`

Numbered, append-only. **Update the existing entry — never duplicate.**

## SA separation patterns

1. **Per-service SAs should inherit cloud IAM from a global default, not per-service config.** When all services in a namespace share the same cloud IAM role, set `global.serviceAccount.annotations` at the umbrella / host-cluster level. Individual charts merge global + per-service annotations via the `merge` Helm helper. This avoids duplicating the same IAM annotation across N charts and makes per-service overrides (a service that needs its own dedicated cloud SA) a simple values addition.

2. **AWS-style image-pull secrets are needed on EKS — GCP/Workload-Identity is not.** On EKS, the shared SA typically carries `imagePullSecrets: [{name: <pull-secret>}]` for private-registry access. New per-service SAs on EKS must replicate this or pods fail to pull images. GCP clusters using Workload Identity for registry auth don't need `imagePullSecrets`. Model this as a per-cluster setting (`global.serviceAccount.imagePullSecrets`) alongside the cloud IAM annotations.

3. **PR-preview deployments must not create SAs.** When a chart adds `serviceAccount.create` support, PR-preview values must explicitly set `create: false`. Previews deploy into the same namespace as the dev app — creating a duplicate SA causes conflicts or overwrites the dev SA's annotations.

4. **Namespace-level `principalSet://` bindings replace per-SA WI bindings at scale.** GKE Workload Identity normally requires a per-SA IAM binding (`serviceAccount:<project>.svc.id.goog[<ns>/<sa>]`). With many services getting dedicated SAs, this doesn't scale. Use:
   ```
   principalSet://iam.googleapis.com/projects/<project-num>/locations/global/workloadIdentityPools/<project-id>.svc.id.goog/namespace/<namespace>
   ```
   to cover all SAs in a namespace with one binding.

5. **Services with dedicated cloud SAs need per-SA WI bindings — namespace-level `principalSet` is unsafe for them.** Any service with a dedicated cloud SA (e.g. a service that needs database admin permissions distinct from the shared role) cannot rely on the namespace-level binding — that would grant every SA in the namespace those elevated permissions. When renaming such a K8s SA, an explicit per-SA WI binding must be added in Terraform for the new name.

6. **Batch SA template rollout is safe when `create: false` is the default.** Adding `templates/serviceaccount.yaml` to many charts in a single PR is a no-op change — no SA is created until `create: true` is explicitly set per component per cluster. Pilot one service end-to-end first, then batch the template addition.

7. **Production SA renames need a Terraform-first sequence.** When renaming an SA that has a dedicated cloud binding, apply the new IAM binding (Terraform) BEFORE enabling the new K8s SA. Make the IAM binding additive (do not replace the old binding) so the previous SA keeps working during the transition.

## Validation operations

8. **Enumerate every host-cluster file explicitly in batch dispatch prompts.** Sub-agents will silently skip clusters they weren't told about. List all N host-cluster files by full path, then verify:
   ```bash
   git diff --name-only origin/main | grep host-clusters | sort
   ```
   shows exactly N lines before pushing.

9. **Local `helm template` for prod overlays may require stacking multiple values files.** If the chart layers `environments/<env>.yaml` and `host-clusters/<cluster>.yaml`, both must be passed when rendering locally — otherwise template errors are misleading. Mirror the ArgoCD app's full values-file list when validating locally.

10. **Tag-pinned clusters defer all changes until the tag is bumped.** When ArgoCD `targetRevision` is pinned to a specific chart version, changes merged to `main` are invisible on-cluster. Validation status for pinned clusters should be recorded as **DEFERRED**, not **FAILED**.

11. **Disabled services (`enabled: false`) are NO_DEPLOY — skip in validation.** Many services are enabled on only a subset of clusters. A "missing" SA on a cluster where the service is disabled is expected, not a regression.

12. **Per-service SA validation is a 4-step check.** (1) SA exists with the correct cloud IAM annotation. (2) Deployment `serviceAccountName` matches and all replicas Ready. (3) Pod health — all Running, 0 restarts, no old-ReplicaSet stragglers. (4) Logs spot-check for IAM auth regressions.

13. **Bundle-enablement matrix determines actual blast radius.** A host-cluster values-file edit is a no-op if that cluster doesn't have the corresponding ArgoCD Application (bundle) enabled. Check the matrix before dispatching.

14. **Resolve an EKS cluster's IRSA OIDC provider ARN even when `iam:ListOpenIDConnectProviders` is DENIED** (a scoped SSO role often lacks it): (1) get the issuer — `aws eks describe-cluster --name <cluster> --query cluster.identity.oidc.issuer`, strip `https://` → issuer host; (2) the provider ARN is deterministically `arn:aws:iam::<acct>:oidc-provider/<issuer-host>`; (3) CONFIRM authoritatively by reading an existing IRSA role's trust policy — `aws iam get-role --role-name <role> --query Role.AssumeRolePolicyDocument.Statement[].Principal.Federated` (its `StringEquals` condition keys give `<issuer-host>:sub` / `:aud`). Useful for filling an OIDC block (e.g. a Crossplane `EnvironmentConfig`) without the list permission.

## Cloud IAM / Terraform verification

15. **`terraform plan` does not validate IAM role strings against the cloud provider's API.** A `google_project_iam_member` (or equivalent AWS/Azure resource) referencing a misspelled or nonexistent role name passes `terraform plan` cleanly and only fails at `apply` time, because `plan` treats the role name as an opaque string it never checks against a live API. Before trusting a green plan as proof a role reference is correct, verify predefined roles independently — e.g. `gcloud iam roles describe <role>` — especially for roles with easily-confused, near-identical names.

16. **GCP Memorystore for Valkey IAM authentication requires `roles/memorystore.dbConnectionUser`, granting `memorystore.instances.connect` — a permission named `memorystore.instances.connectWithIamAuth` does not exist despite being the obvious-looking match.** Confirmed against the live IAM roles API (`gcloud iam roles describe roles/memorystore.dbConnectionUser`), not from documentation alone. Do not confuse this with the separate Redis Cluster role `roles/memorystore.redisClusterConnectionUser` — same product family, different role, different granted permission.
    - If binding this via a GKE cluster's Workload-Identity default GCP service account, project-scoped binding is intentionally broad when other instances in the project use a different auth mode — the grant is only effective for instances actually configured for IAM auth.
    - Where a cluster module exposes a namespace/SA-keyed identity map, resolve the principal through that output instead of constructing its email: `module.cluster.workload_identity_default_gcp_service_account_names["<namespace>-<ksa>"]`. In the source module example, this output is available in `gcp_gke_cluster` >= 3.5.1. Verify the module's output contract before using it.

17. **Memorystore for Valkey IAM_AUTH without TLS sends the OAuth bearer token over the wire in plaintext, and the field that fixes it is immutable after creation.** GCP's own documentation states the AUTH command (carrying the IAM token) is unencrypted unless in-transit encryption is enabled. `transit_encryption_mode` is set at creation time only — changing it later requires destroy/recreate, and the commonly-used Terraform module for this resource (`terraform-google-modules/memorystore/google//modules/valkey`, `~> 15.2`) defaults it to disabled. Any instance using IAM authentication should set `transit_encryption_mode` to the server-authentication value explicitly at creation time — the empty-instance window before applications connect is the only low-cost moment to make this choice.
    - The explicit values are `authorization_mode = "IAM_AUTH"`, default `transit_encryption_mode = "TRANSIT_ENCRYPTION_DISABLED"`, and TLS override `transit_encryption_mode = "SERVER_AUTHENTICATION"`.

18. **General pattern for changing an immutable field inside a Terraform `for_each` map without replacing every sibling resource: pin the default to the CURRENT live value, then override only the single entry you actually want to change.** A defaults-plus-per-entry-override map (e.g. an `instance_defaults` block merged with per-entry `instances`) that sets the new value directly as the default force-replaces every existing resource in the map, because the module then compares every entry against a value that differs from what is actually live. Instead: (1) set the default to match what is already live — this produces zero diff on existing resources; (2) override only the target entry to the new value; (3) wire the field through as `each.value.<field>` rather than a shared default. Verify via `terraform plan`: an existing target should show the intended replacement, or a new target only an addition, while every sibling shows only a refresh with zero changes.

    - For a Valkey two-pass merge, set `valkey_instance_defaults.transit_encryption_mode = "TRANSIT_ENCRYPTION_DISABLED"`, override only the target in `valkey_instances` to `"SERVER_AUTHENTICATION"`, and pass `transit_encryption_mode = each.value.transit_encryption_mode` into the module. The recorded plan for a new target was `1 to add` with `SERVER_AUTHENTICATION`; its existing sibling was refreshed with `0 to change`.

## SA separation patterns (continued)

19. **A Helm "merge global + local annotations" ServiceAccount template with fill-in (last-write-wins-only-if-unset) semantics gives a component no way to opt OUT of a bundle-wide annotation.** If the template is `merge $localAnnotations $globalAnnotations` (Sprig `merge`: first-source-wins per key, but fills in anything absent from the first map), a component setting `annotations: {}` (or `""` / `null`) is indistinguishable from not setting the key at all — the global value always fills in. An `identity.source`-style enum of two states (e.g. managed/unmanaged) doesn't add a real "none" state either.
    - **Fix idiom:** guard with `hasKey` plus a length check and render nothing in that branch. Use `if`/`else`, not a ternary (Go templates evaluate both branches of a ternary expression), and merge into a freshly-allocated dict — `merge` mutates its first argument in place, and pointing that first argument at `.Values` corrupts the source data.
    - **Don't generalize across resource kinds** — a CronJob's ServiceAccount template is often local-only with no global merge at all, so a finding on a Deployment's SA template doesn't automatically apply to a CronJob's.


## GKE Workload Identity credential caching

20. **On GKE Workload Identity, `google-auth`'s Python client library self-pins to a resolved GSA email on first token refresh — the pin lives inside the library, not application code, so whether a client survives a bound-identity change is decided by which auth library it uses, not by anything grep-able in its own source.** Traced in `google-auth` (confirmed stable across three recent minor releases): `google.auth.default()` constructs `compute_engine.Credentials()` with no `service_account_email`, defaulting to the safe `"default"` alias. The first `refresh()` call resolves account info and then **rebinds** the credentials object's stored email to the concrete resolved address — from that point on, every subsequent refresh hits the email-specific metadata path instead of the safe alias. When the underlying KSA's bound GSA changes, that email-specific path 404s forever, eventually raising a transport/refresh error. A repo-wide grep for `service_account_email` in application code finds nothing, because the pin happens entirely inside the library at runtime. For contrast: some other Python metadata-client libraries hardcode the `default` alias path and never pin, and are genuinely immune. For any Python service using this class of library, decide "will this break on the next identity change" from which auth library it uses, not from its own code.
    - **A parallel, harder-to-see variant hits signed-URL / signBlob paths.** A Java/Scala-ecosystem auth library's compute-engine credentials class caches the resolved account email for process lifetime the same way, then passes it as an explicit **API parameter** to a blob-signing call rather than a URL path. Because the *token* is still fetched via the safe default alias, the client stays healthy-looking and emits no email-specific metadata request at all — it fails silently, signing as the OLD principal (impersonation) until that principal is revoked, visible only in the cloud IAM-credentials service's own signing audit logs, never in the metadata-server audit trail used to detect the first variant. Detection requires a dedicated audit-log query for the signing API, comparing the resolved target principal against the actual caller, resolved by a stable numeric identity rather than email (emails get renamed/reused).
    - **Pinned Python evidence:** the recorded source comparison covers `google-auth` 2.52.0, 2.55.0 and 2.56.3. In the traced chain, `_default.py:413` constructs the credentials; `compute_engine/credentials.py:69,92` supplies `"default"`; `refresh()` at `:476-482` reaches `_perform_refresh_token` at `:143-152` and `_retrieve_info` at `:112-116`. The assignment at `:122,124` stores `info["email"]`; subsequent `_metadata.py:457,460,463` requests use `instance/service-accounts/<email>/?recursive=true`. A 404 becomes `TransportError` at `_metadata.py:385-391`, then `RefreshError`. Traceback frames `credentials.py:114` and `_metadata.py:463` matched 2.55.0. The token fetch at `credentials.py:146-151` already uses `service_account="default"`; account-info refresh is the pinning step. This was an upstream-triage candidate against `googleapis/google-auth-library-python`, not a claim about releases beyond those examined.
    - **Alias-only comparison:** `gcloud-aio-auth` 5.4.4, `token.py:60-67`, hardcodes `/service-accounts/default/token` and `/default/identity`, avoiding this metadata email-path defect. This comparison alone does not certify every signing or impersonation path.
    - **Pinned Java evidence:** `google-cloud-storage` 2.64.0, `StorageImpl.java:810-817,864,866`, uses ADC as `ServiceAccountSigner` for `storage.signUrl(..., withV4Signature())` when no `signWith()` is supplied. In `google-auth-library-oauth2-http` 1.43.0, `ComputeEngineCredentials.getAccount():695-704` caches the principal for process lifetime; `sign():720-737` passes it to `IamUtils.sign`. `IamUtils.java:72,125-126` builds `https://iamcredentials.%s/v1/projects/-/serviceAccounts/%s:signBlob`. The initial email lookup at `ComputeEngineCredentials.java:635-638` uses `/instance/service-accounts/default/email`, so an email-path metadata audit cannot detect the stale signing target. Continued impersonation succeeds only while the new caller retains `serviceAccountTokenCreator` on the old principal. Other name-parameter paths, such as `GenerateAccessToken`, warrant the same caller-versus-target check.
    - **Detection and verification:** run `gcloud logging read 'protoPayload.serviceName="iamcredentials.googleapis.com" AND protoPayload.methodName="SignBlob"' --format='value(protoPayload.authenticationInfo.principalEmail,protoPayload.request.name,protoPayload.resourceName)'`. Compare the caller with `request.name`; resolve identity by `uniqueId` (`resourceName` is numeric, `request.name` carries email). Enumerate each cluster and split time windows to check census completeness. Pre-change and post-change replicas in one Deployment provide an A/B control: one observed process switched from old-principal caller to new-principal caller targeting the old principal within 14 milliseconds, proving authentication and target resolution are separate.
    - **Revocation gate:** recycle affected pre-change pods and exercise the signing path again. Zero old-target calls and positive proof of signing as the new principal are separate claims; no signing calls means **UNEXERCISED**. A recorded 28-minute silent window proved only absence of old-target calls. Revoking the old principal can break signed URLs that still depend on it even with no application change. Recycling repairs the current cached target; it does not remove the library's caching behavior.

21. **A silent identity-cutover break can leave a fully healthy-looking pod and zero IAM denials — the three signals people reach for each give a confident false negative.** When a client's stale-cached-credential path fails, the failure mode is typically an unavailable/timeout error on the *data* call, not a permission denial. Consequence: (1) pod logs are a false negative once the failure is more than a log-rotation window old — check centralized/cloud logging, not the live pod's own log tail; (2) a `PERMISSION_DENIED`-style audit-log query returns clean by design, because a vanished credential path yields "unavailable/unresolvable", never an authorization error, so a clean denial query is not evidence of a healthy cutover; (3) a backlog/queue-depth minimum-over-window metric is not proof of a live consumer — the minimum observed can be a stale pre-failure value rather than evidence of current throughput. The reliable discriminators are activity-rate metrics for the specific dependency (an ack/throughput rate rather than a backlog minimum) and confirming there is no code path at all in this failure class that would produce a denial — absence of denial errors is exactly what this failure looks like when supposedly healthy.

    - **Concrete Pub/Sub failure signature:** an email-specific metadata lookup becomes gRPC `UNAVAILABLE`, `google.api_core.exceptions.ServiceUnavailable` 503, then `RetryError: Timeout of 300.0s exceeded`; it does not produce IAM `code=7`. A pod can remain `Running`, `1/1 Ready`, with `0 restarts`, and return 200 on `/health` and `/metrics` after its consumer thread dies. Centralized logs can retain the brief failure burst after kubelet rotation removes it locally.
    - Check `ack_message_count` and `oldest_unacked_message_age`, not a historical minimum of `num_undelivered_messages`. Missing Monitoring API datapoints are not zeros. A rising age, or a roughly 3600-second sawtooth as messages expire without acknowledgements, can reveal a dead consumer. Count pods started before their own adoption batch to size the at-risk population; a healthy current snapshot does not exercise cached clients.
    - **Independent application failure:** an unguarded `while not shutdown.is_set(): service.pull_messages()` loop in a daemon `threading.Timer` can die permanently on any propagated exception. Trace every layer down to the subscriber's `pull()`; exception handling around `acknowledge()` or `modify_ack_deadline()` does not protect `pull()`, and `Retry(deadline=300)` eventually exhausts. An unconditional `up=True` health endpoint or readiness checks limited to other dependencies cannot observe the dead thread. Recovery must recreate the event processor and `SubscriberClient` so new credentials resolve through the default alias; retrying the same pinned credential object does not heal it. Add a last-successful-pull timestamp signal to readiness. This fixes recovery from a failed identity change; the library issue in #20 still needs separate treatment.

## SA separation patterns

22. **Whether `imagePullSecrets` is needed is a property of the cloud provider, and cluster names are not reliable evidence of provider — verify from the actual provider configuration, never infer from naming.** EKS clusters typically need an explicit `imagePullSecrets` entry for private-registry pulls; GKE clusters using Workload Identity typically don't. A cluster can be historically mislabeled in tooling or reference tables — named as if it were one provider, later migrated, or simply never accurately classified. Confirm the provider from the per-cluster values file's actual cloud include, or from a rendered ServiceAccount's IAM-annotation shape (a Workload-Identity-style annotation key versus an IRSA-style one) — never from the cluster's own name or a table that could be stale.
    - For an infrastructure chart deployed as its own ArgoCD Application, pass the pull-secret list in `source.helm.values` rather than assuming an umbrella propagates it: `imagePullSecrets: [{name: <pull-secret>}]`. Check both the provider include and the host-cluster ServiceAccount annotations; `iam.gke.io/gcp-service-account` identifies the GCP annotation shape.

## Identity adoption and verification (continued)

23. **GCP SA naming follows module inputs, not the presence of a local variable.** Defining `local.gcp_sa_prefix` in `main.tf` does not pass it into a cluster module. In a module with default `gke-${var.name}` and SA pattern `${gcp_sa_prefix}-${namespace}-${name}`, inspect both the local definition and the module argument before deriving an SA email. Verify those patterns against the module in use.

24. **Managed identity annotations can override an explicit component-level identity.** For a chart using `merge $identityAnnotations $localAnnotations $globalAnnotations` in `charts/<chart>/templates/serviceaccount.yaml`, Sprig `merge` keeps the first source's value and mutates that first map. A fresh identity dict must be first because the local annotations can point into `.Values`. Setting `serviceAccount.identity.source: managed` therefore supersedes a dedicated identity in `serviceAccount.annotations`, not just the global default.
    - Removing a superseded annotation block can be a rendered no-op, but changes rollback: reverting `managed` to `unmanaged` falls back to the shared principal instead of the former dedicated identity. Prove byte-identical renders across every affected overlay, include a mutation negative control, and explicitly agree on that rollback consequence before removing the block. A recorded three-block removal was identical across 26 renders / 13 clusters. Treat prior keep-or-remove decisions as deployment-specific policy.

25. **Validate annotation values and object sets when adopting an identity; render sizes are not evidence.** A value overwrite can leave line counts and even byte counts unchanged. Compare each leaf's rendered cloud-identity annotation against its own baseline: some leaves already use dedicated identities, so a blanket assertion that every base equals the shared principal is wrong. Assert that object key sets are unchanged and only the target ServiceAccounts differ. Use `helm template` output values, not file sizes, as the oracle.

26. **Derive the ServiceAccount name from the rendered identity claim.** A service named `<service-name>` can render SA `<short-sa-name>` on one cluster and `<service-name>` on another. Read `spec.serviceAccountName` from the rendered `XRole`; do not assume it equals `serviceName`. A hash oracle keyed by service name while object lookup uses SA name can silently look up no object and report a vacuous pass. Require the expected object to exist.

27. **ArgoCD runtime health and wave behavior must be checked in live configuration.** If ArgoCD is deployed from a different repository, a clean `grep -rn "resource.customizations" charts/ host-clusters/` only proves the customization is absent from that repository. Read `kubectl --context <cluster> -n argocd get cm argocd-cm -o jsonpath='{.data.resource\.customizations}'` before concluding how health assessment, sync-wave gating or `ignoreDifferences` behaves.
    - In a recorded ArgoCD `v3.3.6` deployment, a wildcard custom-group `health.lua` returned `Progressing` until `Ready=True` and `Degraded` on `Synced=False`. The XRole at sync-wave `-15` therefore had to become Ready before wave 0 advanced. The empty repository search alone had suggested apply ordering without readiness gating; the live customization disproved that inference.

28. **A wrapper must own the ServiceAccount when an upstream subchart cannot annotate it.** `ealenn/echo-server` v0.4.0 exposes only `serviceAccount.{create,name}` and renders `templates/serviceaccount.yaml` with name and labels, so values cannot inject IRSA or Workload-Identity annotations. With subchart alias `echoserver`, set `echoserver.serviceAccount.create=false` and `echoserver.serviceAccount.name=echo-server-echoserver`, supply a wrapper `templates/serviceaccount.yaml`, and add a `fail()` guard if both create flags are true, which would render the same object twice.
    - The explicit name is required: with `create=false` and no name, the upstream helper falls back to `default`. The generated KSA name uses the alias (`.Chart.Name` becomes `echoserver`), not the original chart name.
    - Verify the ownership move separately from identity adoption. The recorded flags-off diff kept the SA name and namespace, changed `app.kubernetes.io/name` from `echoserver` to `echo-server` and `helm.sh/chart` from `echoserver-0.4.0` to `echo-server-1.16.0`, and added explicit `namespace` and `automountServiceAccountToken: true`. That was an in-place metadata/spec update, with no SA recreation, token rotation or pod restart.

29. **Reuse an existing Memorystore ServiceConnectionPolicy for the same network and service class.** When the first Valkey module has already created the project's network policy for `service_class = "gcp-memorystore"`, additional instance modules must omit `service_connection_policies` rather than create the same policy again; the duplicate apply fails with HTTP 409. Preserve the 409 reason next to the omission so it is not mistaken for a missing configuration block.

30. **Prove the running workload's GSA through metadata and data-plane audit evidence.** The KSA annotation alone does not prove which principal a running process sees. Query the metadata endpoint from the pod: `kubectl exec <pod> -- sh -c 'curl -s -H "Metadata-Flavor: Google" http://<metadata-host>/computeMetadata/v1/instance/service-accounts/default/email'`. If the image lacks `curl` or `python3`, try `wget -qO- --header=Metadata-Flavor:Google <metadata-url>`; inspect which client is present.
    - Independently query rows under the newly minted principal after the new pod's start: `gcloud logging read 'protoPayload.authenticationInfo.principalEmail="<new-gsa-email>"'`. Per-service identities and removal of the old pod make attribution clearer. Prefer data-plane evidence such as BigQuery `AppendRows` or AlloyDB `GenerateClientCertificate`; `GenerateAccessToken` proves token minting, not that the workload successfully used the token.

31. **Allow consumer startup and monitoring lag before grading a Pub/Sub recovery.** A recorded GKE recovery took roughly 4–6 minutes after pod start: restart at 23:04Z, first acknowledgements at 23:08Z, and a 3.3-hour backlog (42 messages, `oldest_unacked_message_age` 12029s) cleared by 23:10Z. Pub/Sub monitoring series also lagged 1–2 minutes, so T+3-minute checks still showed the pre-restart plateau. These are observed timings, not a universal startup guarantee.
    - A dead consumer's `oldest_unacked_message_age` can climb 1:1 with wall-clock time (60 seconds per minute); flat backlog alone does not distinguish a stall from a consumer keeping up without catching up. Query `https://monitoring.googleapis.com/v3/projects/<project-id>/timeSeries` with an access token when needed; the recorded `gcloud monitoring` interface had no `time-series` subcommand.

32. **Compare pre-restart warnings using retained logs, not a deleted pod's empty log stream.** A zero from `kubectl logs` for a removed pod does not establish that a warning is new. Query retained history: `gcloud logging read 'resource.type="k8s_container" AND resource.labels.container_name="<container>" AND textPayload:"<pattern>" AND timestamp<"<cutover>"'`. A recorded 160-line `ManagedChannel … garbage collected without being shut down` startup burst matched one emitted 48 seconds after the older pod's start five days earlier. A static count of startup warnings supports a startup-hygiene interpretation rather than an ongoing leak; compare the pattern and its growth before calling it a regression.

33. **Read metadata-server logs from jsonPayload.message and require a positive control.** `gcloud logging read '…container_name="gke-metadata-server"' --format='value(textPayload)'` produced 7,930 blank lines in one sweep: `wc -l` looked populated while every `grep -c` returned zero. Use `--format='value(jsonPayload.message,textPayload)'`. Before accepting zero email-path requests or 404s, confirm known-good traffic in the same query, such as `grep -c 'service-accounts/default/'`; in that sweep it should have returned thousands. A missing positive control means the query or field is wrong, or traffic is unexercised, not that the cluster is clean. Also apply the cluster filter in #41.

34. **A stale email can affect a secondary path while default-alias token requests succeed.** In one observed workload, default-alias token requests returned HTTP/200 at 20:44Z and 22:36Z, followed by one `service-accounts/<old-gsa-email>/?recursive=true` HTTP/404 at 00:01:46Z. That directory-enumeration failure was non-fatal; another consumer emitted 133 email-path 404s in an hour and died. Triage the request ratio, workload impact and code path: one 404 beside healthy token traffic is partial contamination requiring remediation, not by itself proof of an outage. The underlying library mechanism is #20.

35. **A clean post-cutover sweep proves only the window sampled.** The common roughly one-hour token-refresh expectation is a floor for some observed failures, not a deadline after which clients are safe. One client's first email-path 404 arrived at merge+3h24m (20:37:35Z merge, 00:01:46Z failure); a Valkey path failed at merge+5h22m. Workload activity determines when a cached-email code path runs, so a merge+90-minute sweep can miss it. Recycling pre-adoption pods clears stale cached identities for the current cutover; separate library remediation is needed to survive a future identity change (#20, #37).

36. **Valkey IAM credential failures can surface as Redis AuthenticationError with no IAM denial.** A shared Valkey-auth utility can expose `google-auth`'s email pin even when no GCS or Pub/Sub client is involved. The recorded chain was the credential utility → `google.auth.compute_engine.credentials._retrieve_info` → `_metadata.get_service_account_info` → `TransportError` → `GCP IAM credential refresh failed` → `redis.exceptions.AuthenticationError: Authentication required.` An HTTP/404 on `/computeMetadata/v1/instance/service-accounts/<old-gsa-email>/?recursive=true` preceded exit `code=1` by one second at merge+5h22m.
    - A vanished metadata path yields 404/503 rather than IAM `code=7`, so a clean denial query is expected. Include every consumer of the shared credential utility in the assessment and investigate Redis/Valkey authentication errors as possible identity-cutover symptoms. The pin is inside the auth library (#20), not evidence that each application explicitly pinned its email.

37. **Recycling an email-pinned client repairs the current cutover but leaves the next one vulnerable.** One restarted consumer continued making 134 email-specific metadata requests over 14.6 hours, all HTTP/200 against its current GSA. For the metadata-path defect, distinguish **broken** (email path → 404), **latent** (email path → 200 against the current identity), and **alias-only** (`service-accounts/default/`). Durable remediation must address the library or client behavior that rebinds the alias to a concrete email (#20).
    - Alias-only metadata traffic is not proof of complete identity-change immunity: a signing or impersonation target can be cached separately and remain invisible to the metadata audit. Check IAM-credentials caller/target audit rows as well (#20).

38. **Prove an IAM promotion through rendered policy JSON when the full stack cannot plan locally.** Copying a reference body with `tail -n +N ref >> new` and seeing only a header hunk in `diff new ref` establishes source parity, not parity after interpolation. A production stack may depend on CI GitHub-OIDC→`INFISICAL_TOKEN` exchange for `ephemeral "infisical_secret"` values and an S3 backend role.
    - Extract only the `aws_iam_policy_document` data blocks into an isolated scratch directory, bind the target cluster's locals literally, and configure dummy AWS credentials (`access_key` and `secret_key` set to `"x"`) with `skip_credentials_validation`, `skip_requesting_account_id` and `skip_metadata_api_check`. In this data-only setup, policy-document sources compute client-side and `terraform apply` emits JSON without cloud API calls. Keep managed resources and the original backend out of this isolated harness.
    - Diff the JSON against the live reference from `aws iam get-policy-version --policy-arn <policy-arn> --version-id <version>`, normalizing only account ID and cluster name. Check that the reference source revision corresponds to the live default version using its last-commit date and `DefaultVersionId` / `UpdateDate` from `aws iam get-policy`; a stale ancestor is not a valid mirror. Seed a mutation negative control by dropping an action or widening a `Resource`, so an identical result is falsifiable.

39. **A permissions boundary on minted roles does not automatically constrain the controller role.** For a Crossplane controller, inspect `aws iam get-role --role-name <controller-role> --query Role.PermissionsBoundary` and the controller's Terraform module inputs. In the recorded `terraform-aws-modules/iam/aws//modules/iam-role-for-service-accounts` 6.2.3 setup, the query returned `null` and no `permissions_boundary` argument was passed. The boundary capped minted application roles, not the controller.
    - In that setup, `DenyBoundaryTampering` restricted future edits to an existing application boundary; it did not require a separate human apply before creating the boundary and referencing controller policy together on a fresh cluster. Confirm the cluster is fresh with `aws iam list-roles` and `aws iam list-policies --scope Local`, filtered on the deployment's role prefix. Do not generalize this result to a controller that actually has its own boundary.

40. **Distinguish token expiry from pod recycling when attributing an identity cutover.** One old shared principal went silent for 15.4 hours, but its last audit row at 23:08:50Z preceded the first deliberate recycle at 23:18Z by roughly nine minutes. The final adoption merge was 22:14:33Z; a 60-minute token lifetime would expire by 23:14:33Z. That timeline supports expiry and refresh through the default alias, not recycling, as the cause of the earlier silence.
    - Require a positive control: the same principal and query over 20:00Z–23:35Z returned 86 rows (58 AlloyDB `GenerateClientCertificate`, 28 `GenerateAccessToken`). A Go AlloyDB-proxy pod started five days before the identity changes and never restarted, yet metadata logs showed a token for the new identity and subsequent data-plane rows under it. That observed client followed the alias without a restart; Python email-path caching and signing-target caching are separate behaviors (#20).
    - Silence is insufficient for pods still annotated to the old identity that make no audited GCP calls. Classify silence as exercised-clean or unexercised before declaring a cutover complete.

41. **Filter metadata-server logs by cluster in projects hosting multiple clusters.** Without `resource.labels.cluster_name`, project-wide metadata logs blend clusters and can attribute one cluster's email-pinned clients to another. Use `gcloud logging read 'resource.labels.cluster_name="<cluster>" AND resource.labels.container_name="gke-metadata-server" AND jsonPayload.message=~"service-accounts/(<old-identity-prefix>|<new-identity-prefix>)"' --format='value(timestamp,jsonPayload.message)'`. Pair the cluster filter with #33's correct payload field and positive control; either omission can produce a plausible wrong answer.
