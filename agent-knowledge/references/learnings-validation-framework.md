# Validation Framework Learnings

Distilled from building and hardening a large fleet-validation suite (~90-check catalog, runner, spec, result validator). The lessons are about validation-suite *design* — they hold for any check catalog run across many targets. Drawn from a phased fleet upgrade campaign (Istio 1.29.1 → 1.29.6, 2026-07/08); almost every lesson generalises to **any** phased, multi-target, catalog-driven validation suite — the Istio specifics are the exemplar, not the point.

See also: `learnings-agent-workflow.md` (framework *architecture*: prompt-generator runners, negative controls, SKIP composition, tamper proof), `learnings-observability.md`, `learnings-code-review.md`.

## The Headline

1. **Across 4 clusters and 10 phase runs the suite found ZERO real mesh faults and 9+ catalog defects — every single failure was a CORRECT MEASUREMENT GRADED AS A FAULT.** That is the defining failure mode of a validation suite, and it is far more dangerous than a missed detection, because **a suite whose nominal state is amber cannot signal a real fault**: it trains the reader to dismiss exactly the class of alarm that will one day be real. Two structural responses came out of the postmortem:
   - **Codify anti-false-positive rules as SPEC clauses (M1-M11), not as reviewer instinct**: set difference not count equality; no zero-tolerance on varying counters; presence ≠ activity; an armed census missing a label class is EVIDENCE, not blindness; every Delta branch must NAME a status; never grade a countdown against a fixed tolerance; per-pod counters cannot span a roll; settling guards age `state.running.startedAt`, not the pod; a remedy in Gotchas is not a fix; SKIP ≠ declined-to-compute; payload sort clauses must be `;`-separated with the backticked subject BEFORE "sorted by" or only the first binds.
   - **Add a depth axis (`core` | `deep`, default `core`) as a third selection gate** — 75 core / 18 deep. Make the default the **inclusive** fallback so an unannotated check is *noisy, not invisible*. And **a deep run may not be graded against a core baseline**: missing payload rows read as "no change" rather than "no data", so `run.sh` must refuse the comparison outright.
   - **Every one of the eight blocking defects was found by running against a REAL cluster, never by review.** Budget for catalog defects to surface per-cluster for the first 2-3 clusters of a **new promotion SHAPE** (here: `tracks:pinned` + `waypoint:false`), and expect the rate to drop to zero once the shape is covered — the fourth cluster of the shape needed zero new fixes.

## Defect Taxonomy: Correct Measurement Graded As A Fault

2. **Live quantity graded against a fixed single-sample baseline band** — 4 false FAILs in one sweep. (a) `L5.05` required `ratio <= baseline*1.5` **AND** `<= baseline+0.005` while its own prose claimed the additive floor prevented false FAILs on near-zero baselines — **ANDing makes the floor structurally inert**, so 1 error in 1535 requests failed a blocking check; fixed to OR (FAIL needs BOTH exceeded). (b) `L4.03` graded live HPA replica count vs baseline ±1; a cluster autoscaled 4→2 on falling load and FAILed while measuring a healthy 2/2 — band removed, since real HPA failure modes (`ScalingActive=False`, can't-actuate on 2 reads, thrash, missing objects) already cover it. (c) `L4.05` graded waypoint RPS vs P0 ±25% unconditionally while its prose mandated "comparable time-of-day"; the anchors were 14h06m apart.
   - **Two diagnostic tells, stronger than any argument**: the **SAME measurement graded differently across two runs** (HPA 2/2 PASS then FAIL), or a **BETTER measurement graded worse** (65.7 rps PASS, 72.5 rps FAIL). **Always diff run-N vs run-N+1 per check before believing a new FAIL.** Second tell: **check prose contradicts its own delta-rule table** — grep for preconditions stated only in prose.

3. **Asserting fleet-wide uniformity across a window the spec deliberately makes NON-uniform.** `L0.04` (image hub/tag), `L0.09` (targetRevision tracks pinned) and `L7.04` (targetRevision matches track) each FAILed on all three promoted prod clusters = **NINE false blocking FAILs**, every one an accurate description of the designed CP/DP split state. **Fix: grade BY PLANE at P1, not by count** — CP on target/`$EXPECTED_REV` + DP on prev = PASS; CP not moved = FAIL; **DP ahead of CP = FAIL (the INVERSION — the actual hazard)**; a third revision or unknown hub = FAIL. The pass condition is "the right two revisions on the right two planes", not "one revision".
   - **Two generalisable rules.** (1) **When you fix a "correct measurement reported as a fault" exemption in one check, GREP FOR SIBLINGS ASSERTING THE SAME INVARIANT** — they almost always exist and will fire on the next cluster. `L7.05` had already been given this exact shape and the three siblings never got it. (2) **Name one authoritative predicate per invariant** (`L0.02` here for P1 skew); when other checks disagree with it *on the same input at the same instant*, **it is the catalog, not the cluster** — that tell has now been correct 4 times.

4. **A check grading a fleet-wide MOVING POINTER must grade against a run-scoped `$EXPECTED_REV`, never against the pointer's NAME.** `L7.05` hardcoded "every `tracks:pinned` cluster references `<stable-ref>`" and FAILed two prod clusters with "stable equals <old-anchor> at 1.29.1 while this cluster is intentionally anchored at <target-anchor>" — an accurate description of the designed staged promotion. Staged rollout deliberately pins some clusters to an immutable anchor **ahead** of the moving pointer, which is force-moved only at the end; `$EXPECTED_REV` is the per-run operator input (SPEC 8b) that exists to state this. Record the divergence from `stable` as notes context, not as a verdict. **Left unfixed, this class fires on every cluster of a tier and then falls silent exactly when the invariant becomes real.** (Related: a per-cluster *immutable* `EXPECTED_REV` override conflicts with any static `tracks:pinned` expectation — the override is the authority.)

5. **A check that sums a residual CLUSTER-WIDE has sensitivity that scales INVERSELY with cluster traffic — it fires first on the QUIETEST cluster, rarely the one at risk.** `L2.07` (ztunnel excess closes) FAILed on a low-traffic prod EKS cluster with `excess_beyond_allowance=8108` vs a threshold of 500, **two hours after** the roll, with `connections_failed_in_window=0` and `drain_log_lines=0`. Decomposed by `source_workload` the excess was two app workloads with **zero restarts** (up 28h) and a flat-zero `istio_tcp_connections_failed_total` across 6h — i.e. **clean closes from a connection-pool cycle, not RSTs**. Two compounding defects: `p0_excess_beyond_allowance` **clamps P0's NEGATIVE residual to 0** (the 15m residual was negative in all 72 hourly samples, −1113..−5550), so the bar is a flat 500 for a **signed** quantity that natively swings ±thousands; and the branch graded a cluster-wide residual with **no temporal or causal link to the roll**.
   - **Fix (2026-08-04): require `connections_failed_in_window` to have stepped above its P0 value as a CO-SIGNAL before excess can FAIL.** `closes_minus_opens` is a signed churn residual, not a fault count — any connection opened before the window and closed inside it is an unmatched close. A reset moves the failure counter; a clean pool cycle does not. **The co-signal was ALREADY BEING COLLECTED and simply never consulted — look for that pattern elsewhere: a check that measures the discriminating signal but does not gate on it.**
   - **Deliberately did NOT re-tune the threshold**: the floor is structurally 0 whenever P0 is negative (the normal case), so widening the multiplier cannot help. **Gating on the co-signal is the fix; moving the number just relocates the false-positive rate.**
   - Also added: mandatory `top_excess_sources` attribution (topk by `sum by (source_workload)`) whenever excess steps, and `p0_connections_failed_in_window` so the FAIL row has a floor instead of silently degrading to zero. **Always decompose a cluster-wide aggregate BY SOURCE before theorising about mechanism** — three plausible hypotheses (window length, the probe perturbing its own measurement, pod/series churn) were all ruled out by that one decomposition.
   - **Window states**: `L2.07` originally had only two (roll wholly inside / wholly outside) and **no branch for a window that CLIPS the roll**, where closes-minus-opens arithmetic is invalid because opens preceding `window_start` are missing → added a third state as INFO. **Widening the window is the wrong escape**: the predicate is relative to an EQUAL-LENGTH P0 window, so widening trades a visible not-gradeable for an invisible wrong number. Related gap: `$ROLL_WINDOW` is node-dependent and the frozen catalog supplied **neither a formula nor a per-run binding** — the sole exemplar was 15m. Record the ambiguity explicitly rather than silently inventing a rule.

6. **Never flatten a SELECTOR × SCOPE pair into two independent sets.** `L3.09`'s STRICT-probe target derivation unioned PeerAuthentication exception *selectors* and *ports* independently and excluded any candidate matching **either** axis — catastrophic over-exclusion. A PA port exception is inherently one pair ("port 80 is PERMISSIVE **for pods labelled app=X**"); splitting it discards the binding. Five narrowly-scoped exception PAs flattened to ports `{80,8081,8085,9901}`, excluding ALL 64 port-80 Services and leaving **zero probe candidates** — so `L3.09` recorded ERROR at P1 on a prod cluster and **STRICT enforcement went unproven**.
   - **Fix**: emit pairs `{name, selector, ports}` plus a separate `nsWidePorts` set for selector-less (namespace-wide) PAs whose ports *do* apply globally; exclude a candidate only when ONE pa matches on **both** axes. Selector-matching rule: two label selectors match overlapping pods **unless they conflict on a shared key**, so `any(k in svc_sel and svc_sel[k] != v for k,v in pa_sel.items())` is the only proof a PA cannot apply — everything else counts as covering, the conservative direction **for a NEGATIVE test where you need a target that is PROVABLY STRICT**. Result: 0 → 62 candidates, excluding exactly the 2 genuinely-excepted services (64−2).
   - **General rule**: whenever a check derives an exclusion set from objects pairing a selector with a scope (ports, paths, verbs), never flatten the axes — **and always log the candidate count plus which rule ate each exclusion, or a zero result is undiagnosable.**
   - **Istio detail worth keeping**: `portLevelMtls` applies only to the *selected workload* and keys the **workload/target port**, not the Service port.

7. **SELECTION and APPLICABILITY are different gates — conflating them produces false blocking ERRORs.** `run.sh` resolves selection **statically** from `applies_to`/`phases`/`depth` and has no view inside the cluster, so a check with no `applies_to` restriction is selected on **every** cluster by design; each check then resolves its own **runtime** applicability internally, which **must resolve to SKIP, never ERROR**. In one run an agent graded `L2.25` ERROR on one cluster ("0 svc-parent Tailscale pods; applicability false — catalog defect: selected despite runtime applicability=false") while another cluster hit the identical condition in the same run and correctly graded SKIP. **Same input, two statuses is the reliable tell that the defect is in the READING, not the cluster.** Second trap in the same check: it also has a legitimate ERROR branch (log stream dead), so an agent can mistake "nothing to measure" for "measurement path dead" — the check must state the difference explicitly.
   - **Consequence that cost a baseline**: `baseline_usable()` had only two legitimate reasons a `baseline_compare` check could lack a payload — profile-inapplicable (`cluster_matches(applies_to)`) and phase-inapplicable (`phases`). The missing third is **RUNTIME inapplicability, which `applies_to` structurally CANNOT express** (it holds static profile keys — tier/cloud/mtls/waypoint/tracks — and cannot say "only if a pod carrying label X exists"). `L2.25`'s correct SKIP therefore **rejected an otherwise clean 94-row P0 that could never be retaken** once those prod clusters upgraded — a correct check fix invalidating an irreplaceable baseline. **Fix: an optional catalog key `runtime_applicability: true`** plus a fourth `continue` in `baseline_usable()` exempting SKIP **only when the check declares it**. Declare it in the **CATALOG, not inferred from `notes`** — `notes` is agent-written, so a prose-excused SKIP lets an agent talk past a missing payload. **Verify both directions**: baseline became usable, AND a negative control (nulling a payload on a check *without* the key) still returned NOT USABLE, proving it did not blanket-accept. **Keep outcome meanings distinct:** PASS means measured and healthy; FAIL means measured and faulty; INCOMPLETE/ERROR means the required measurement was not completed; SKIP means nothing applicable existed; INFO means measured but not yet (or no longer) evaluable. Incompleteness must block without being reported as a fault in the target.

8. **Counters that live ON the rolled component stop exporting for 10-20 min after a roll — grade that as INFO, and require a CONJUNCTION, not mere emptiness.** `L3.10` graded empty Citadel counters (`citadel_server_csr_count`, `citadel_server_success_cert_issuance_count`) as ERROR when a P1 anchor happened to land in the post-roll scrape-settle gap; proven on one cluster as count=3 at 14:50-15:05, **0 at 15:10-15:20**, 3 from 15:25, with the anchor at 15:07:59. Root-cert **expiry gauges stayed live** and 15m range deltas still showed 1/1 — so **historical range data must not be mistaken for a live series**, and an arming proof over a range window is not a proof of current export. The exemption must require **empty counters AND a fresh restart AND other legs still measurable** (also seen as 1/3 istiod series shortly after a roll recovering to 3/3 later). Same class: a settling guard must age `state.running.startedAt`, and `POD_SETTLE` is needed because **a pod whose containers started seconds ago satisfies every other guard** (phase Running, all containers running, restart delta 0) while being legitimately not-ready-*yet* — a 3-minute-old mid-deploy pod false-FAILed a check. **Correct form is always `eligible → covered → settling`.**

9. **Three catalog-hygiene rules that each cost a run.** (a) **INFO must be legal at whatever phase ESTABLISHES the anchor a predicate needs**, not only at P0 — the SPEC listed only two legal INFO cases, both at P0, so a check whose Delta rule is P3-vs-P2 had **no legal status at P2** and was forced to ERROR despite measuring perfectly. **A successful measurement must never be reported as an execution failure.** (b) **An unnamed status is an unspecified check**: one Delta rule said a uniform backend change was "a finding worth reporting" and never named a status — three agents graded identical input three ways (WARN/WARN/FAIL). (c) **Non-vacuity thresholds must be concrete and per-unit**: `L7.03` said each chart renders "in the thousands", which contradicts valid output (base 18000, istiod 3844, **CNI 462, ztunnel 219**); and "sorted arrays" without a named key is correctly rejected as unverifiable — with a **parser gotcha: the backticked SUBJECT must PRECEDE the sort keyword in the same clause** (`hits sorted by (node, pod)` parses; `Sort key: ascending lexical by src_ns...` does not). Where the catalog genuinely prescribes no order contract (`L7.02` `ignoreDifferences` nesting), **record the catalog defect explicitly rather than inventing an order contract**. (d) **Treat each check body and its layer preamble as independently authoritative and reconcile them** — one snapshot's L0 preamble said no other L0/L1 check emits INFO while four selected L1 bodies explicitly required INFO at P0. (e) **Amending a check into a phase at DISPATCH time does not amend its frozen header** — a check dispatched into P3 whose frozen `phases` header omits P3 makes `validate-result` emit a phase-mismatch finding. Edit the catalog header, don't paper over it in the prompt.

## Baselines

10. **An agent can silently FABRICATE a baseline and the validator cannot tell.** On one run the supplied P0 payload was an aggregate `{window:15m, http_5xx_ratio:0.001533}` with **no per-listener rows**, while the check grades per `(job,listener)`. Instead of recording "no baseline available" and letting the SPEC resolve the run to INCOMPLETE, the cluster agent **RE-MEASURED P0 from Prometheus at grading time** and graded against that — silently converting a P0→P2 comparison into P2→P2, producing first a FAIL then a WARN that were **never validly graded**. `validate-result.py` passed both with 0 errors **because the baseline result field is FREE TEXT: a fabricated baseline is indistinguishable from a real one.**
    - **Three defences, none of which existed**: (1) **structure** the baseline field and have the validator cross-check it against the actual baseline payload joined on `check_id`; (2) when a P0 payload's **SHAPE does not match the graded unit, that is "no usable baseline" → INCOMPLETE**, never an invitation to re-derive; (3) run an **INDEPENDENT aggregator pass** — this was caught only because a fresh agent recomputed the verdict from the frozen artifacts and applied the SPEC's first-match rule, which both the cluster agent and the hand summary missed.
    - **Meta-lesson**: the same payload-contract drift had been documented in the baseline provenance as "cosmetic in the diff and load-bearing nowhere." **That was wrong — it was load-bearing precisely here. Do not dismiss payload-contract drift as cosmetic without checking whether the widened keys ARE the graded unit.**

11. **A P0 baseline's payload-shape staleness is IRREDUCIBLE once its cluster is upgraded — document it, do not "fix" it.** One cluster's only pre-upgrade P0 predated ~38 checks widening their Payload contract. **Re-running P0 to refresh it would capture the POST-upgrade state and silently destroy the comparison it anchors** — a P0 is by definition pre-upgrade, so the stale run is the only record that can ever exist. The cost is confined to the P0→P2 diff (newly-present keys are **catalog edits, not cluster changes**) and is not a false red: the framework degrades a missing baseline key to INFO / "no baseline available". **Tell the cluster agent explicitly in its dispatch prompt or it will report the key delta as drift.** Related hard deadline: measuring a retrospective row against the ORIGINAL anchor window is bounded by log retention — one window was ~46h old and one more day of Loki retention would have made it unrecoverable.

12. **A multi-cluster sweep needs ONE MERGED baseline dir, and merging exposes latent validator findings.** `run.sh baseline_disqualify()` calls `validate-result.py --baseline-usable` with `--require-cluster` per roster entry, and the aggregator reads a single `<run>/results/*.json` → one `fleet-report.md` — so an N-cluster sweep **cannot** use N separate P0 dirs (`run.sh` dies with "this run covers N cluster(s) the baseline never included"). **Merging is safe**: a baseline manifest is read for exactly two fields, `depth` and `catalog_fingerprint`; `as_of` is **never** read from it and payloads resolve per-cluster by filename, so a merged baseline may legitimately carry two different anchors, preserved per-cluster. **Gotcha**: validating carried results against the CURRENT catalog before trusting them surfaced 3 unpredicted severity-mismatch findings (blocking vs advisory) — an older run predated a blocking→advisory demotion. **`severity` is catalog-owned metadata, not a measurement, so syncing it is not a re-grade — but check STATUS first** (all three were PASS/SKIP, so the demotion could not convert a FAIL, which is exactly what the rule guards). **Always run `validate-result.py --base-dir <live>` against every carried result before merging.**

13. **Re-query a rate/ratio FAIL at 15m resolution before calling it transient OR real, and compare against the listener's OWN multi-day distribution, not just the P0 hour.** One `L5.05` read 0.88% then 0.95% on a `[1h]` window and looked like an escalating regression; **at 15m it was a single 4.10% burst with 0% for the following 45 min**. A `[1h]` average smears a 15-min burst across the whole window, so **a rising 1h number can mean the burst is entering the window more fully, not that it is worsening**. Worse, the same listener had pre-upgrade bursts of 11.44% and 5.01% and a pre-upgrade mean of 0.489% vs 0.066% post-upgrade — **5xx got 7× BETTER after the upgrade while the check reported a regression**, because P0 happened to sample a quiet hour at the 70th percentile of a high-variance distribution. **Single-sample baselines of high-variance quantities are the trap.**

## Coverage, Scope & Operations

14. **A phase that grades none of the health its own hazard can break costs you ATTRIBUTION, not detection.** P1 (the version-skew gate) selected only 38/93 checks and deferred **every CP-sensitive BLOCKING check** to P2 (ztunnel error rate, ztunnel connection health, istiod restart delta, app 5xx rate, pod health delta, pull-through image source, legacy-hub-absent). **P1 is the ONLY moment of intentional version skew** (new istiod pushing xDS to old ztunnels) yet graded no data-plane health. P2 catches the fault — but P2 runs *after* the DP PR merges, so **a P2 failure cannot be blamed on CP vs DP, which defeats the entire reason for splitting the PRs.** Extra sharp when the CP PR also changes the image hub in the same PR: both hub checks are P2+, so the re-point rides through the skew window ungraded. Fix: add P1 to the phases of CP-sensitive blocking checks, or **accept and document that CP-vs-DP bisection requires a rollback.**

15. **Coverage gaps a lower-tier sweep structurally CANNOT close — do not read an N-row test PASS as N rows of prod assurance.** Three recurring shapes: (a) checks gated on a profile key no swept target carries have **NEVER executed anywhere**, so the mechanism they validate (typically the rollback/anchor path) is wholly unexercised, and the first promotion of a target carrying that profile is **a deliberate rehearsal, not a formality**; (b) a capability present in the lower tier and absent in prod means every check for it SKIPs in prod — prod's effective check count is materially lower than the lower tier's table implies; (c) a cloud- or platform-gated slice stays unexercised until a target of that shape is swept. See `learnings-agent-workflow.md` for the general SKIP-composition discipline.

16. **Any check whose command touches a security boundary (secrets, exec, port-forward) MUST carry an explicit in-check authorization note, or agent-side caution becomes a nondeterministic false FAIL.** `L6.02` decodes `.dockerconfigjson` to assert the pull secret is scoped to the right registry. The command was already safe **by construction** — it emits `sorted(auths.keys())`, registry **host names only**, never `.auth`/`.username`/`.password`/`.email` — but the check never *said* so, so **one agent ran it (PASS) and another refused it and recorded a false blocking ERROR on a PROD cluster. Two agents, same command, opposite calls.** The note must state: that the decode is authorized, **why it is bounded**, **why it is necessary** (a pull secret scoped to the wrong registry is invisible from the secret's type/annotations alone — decline the decode and the check cannot answer its own question), that the prohibitions remain explicit so it does not read as blanket permission, and that **if harness policy genuinely blocks it the correct status is INCOMPLETE naming the policy — NEVER ERROR, which wrongly asserts the cluster is at fault.**

17. **Two `run.sh` preflight gates BOTH fire when you resume a rollout after editing the catalog — and a REFUSED run creates no run directory, which makes diagnosis actively misleading.** (a) **Catalog drift vs baseline** — the baseline's fingerprint no longer matches the live catalog; `run.sh` dies with "refusing to compare against a baseline built from a different catalog". Fix with `--allow-catalog-drift`, but **PROVE the drift is additive first** (same check count, no IDs added/removed, zero YAML-header changes, no payload key lost, diff confined to named checks) **with a negative control that detects a dropped key**. (b) **Stale metric attestation** — any `checks/**` edit invalidates it; re-run the verifier `--final` and retry. **Both gates are correct; do NOT bypass with `--skip-preflight`.**
    - **The trap**: because a refused run creates no directory, `ls -dt runs/*-P1 | head -1` silently returns the **PREVIOUS** run's dir and manifest — which reads as if the wrong roster was selected. **Compare the run-dir COUNT before and after, or grep the "Prompts written to" line for the new timestamp; never trust `ls -dt`.**
    - `$EXPECTED_REV` **flips mid-rollout and is per-PHASE, not per-cluster**, whenever a freeze is being lifted (one cluster needed the anchor tag for its P0 and `main` for its P1).

18. **Two check-authoring traps around probe targets and out-of-band workloads.** (a) **Choose a probe target whose failure mode is unambiguous.** Do not probe a non-HTTP service with an HTTP client: `clamd:3310` can close a malformed HTTP request **independently of any policy**, false-PASSing a negative test. Prefer a target with ready ambient-redirected endpoints, an HTTP readiness path, **zero NetworkPolicy/AuthorizationPolicy on the path**, and live mTLS opens — and remember that a netpol drop is indistinguishable on the wire from an mTLS rejection (`learnings-network-policy.md`). A good STRICT proof pairs the reset (`rc=56`) with a **same-pod PERMISSIVE control returning HTTP 200**, plus a post-cleanup re-query returning zero. (b) **L2/L3 checks that only inspect mesh-internal traffic will miss breakage of workloads that own out-of-band netns rules** (e.g. Tailscale proxies). A full clean P0-P3 was reported while an `istio-cni` iptables-backend flip was almost certainly breaking eight such proxies; an unrelated fleet-wide roll healed it before anyone looked. **Add an explicit check for the out-of-band class** — here, CGNAT-destined ztunnel timeouts (`{namespace="istio-system", container="istio-proxy"} |= "dst.addr=100." |= "deadline has elapsed"`) plus "istio-cni logs show only one iptables backend, zero `iptables-legacy-restore`".

19. **A metric that is an expiry / countdown / remaining-time must NEVER be delta-compared against a fixed tolerance — grade the RESIDUAL after subtracting elapsed time, or use a floor predicate.** the suite L3.10 graded `citadel_server_root_cert_expiry - time()` (which decays exactly 1s/s by construction) with `current >= baseline - 3600s`. The rule's own prose stated the 1s/s decay and then failed to subtract elapsed time, so it really encoded "P0 and the current phase must be less than 1h apart" — impossible for any real upgrade run, i.e. a **guaranteed fleet-wide false FAIL**. It fired on all 3 dev clusters at P1 with deltas −8179 / −7180 / −8204s against 8179s elapsed (residual −25s = 0.3% error) on a CA with **9.7 years** of headroom. **Fix**: `residual = current − (baseline − elapsed)`; PASS if `abs(residual) <= 900s`; `residual < −900` means the cert was re-issued shorter or the CA secret was replaced (FAIL); `residual > +900` means a CA rotation (record, re-check the CA-identity check). L3.11 was already correct because it used a floor predicate instead of a delta. **Second-order trap, nearly introduced**: the natural fix — requiring a new `sampled_at` field in the payload — would have converted a false FAIL into a guaranteed **ERROR** at every later phase, because the existing baselines predate the field. **When a fix needs a new input, always add a fallback derivable from data that already exists** (here `manifest.as_of`) rather than a hard requirement that invalidates every stored baseline.

20. **Verify an upstream "possibly fixed in vNext" claim by TAG CONTAINMENT, never by maintainer word or a changelog scan — and check for a REVERT reachable from the same tag.** On `argoproj/argo-rollouts#4847` a maintainer said "possibly fixed in 1.10". The source proved the opposite: the mitigation PR argoproj/argo-rollouts#4074 is **IN v1.9.0**, and argoproj/argo-rollouts#4553 — a **REVERT of argoproj/argo-rollouts#4074** — is in **v1.10.0-rc1 only**. Upgrading would have REMOVED a protection we already had. **Method**: clone upstream, get each relevant PR's merge SHA with `gh api pulls/<n> --jq .merge_commit_sha`, then `git tag --contains <sha>`, and additionally diff the specific reconcile files between our tag and the candidate tag. **Generalize: before any "upgrade to fix X" recommendation, verify (a) the fix commit is reachable from the target tag AND (b) no revert of it is also reachable.** (This is reflex R2 — read the source at our pinned version — applied to a version-selection decision; see `learnings-progressive-delivery.md` for the outcome.)

21. **Verify a Go-module CVE fix INSIDE a container image without the Go toolchain — and the negative control is what makes the green read non-vacuous.** `crane export <img> - | tar xO <binpath> | strings -a | grep -E 'golang.org/x/<mod>@v[0-9.]+'` reads the embedded Go build info directly, because `module@version` paths are baked into the binary; `grep '^go1\.'` gives the compiler version. **Always run the same read against the CURRENT (pre-bump) tag to prove the old build was actually vulnerable** — e.g. `install-cni` 1.29.1 = `x/crypto@v0.46.0` vs 1.29.6 = `v0.54.0`. A green new-version read alone proves nothing. **Two Istio-specific gotchas found doing this**: (a) **GAR pull-through repos (`<remote-repo>`) serve ANY upstream tag on demand, NOT only what the image-warming manifest warms** — proven by resolving 1.29.6 tags that were never in the batch config; that YAML is a keep-warm floor, not an allowlist. (b) **Istio chart image tags are NOT uniform**: a helm-template render shows istiod/pilot and install-cni using `<ver>-distroless` while **ztunnel uses the PLAIN `<ver>`** with no variant — never assume one suffix, render to confirm. (ztunnel is Rust, so Go `x/crypto` CVEs never apply to it at all.)

22. **Verifying a PROD chart-pin promotion: render the PINNED CHART ITSELF at both anchors with that cluster's exact 5-layer value stack and diff — confirming argo-apps renders the new tag is not enough.** Detached worktrees make this cheap: `git worktree add <dir> --detach <tag>`. **Two payoffs on one prod chart-pin promotion** (otel v0.0.1/v0.0.2 → v0.0.3 on <cluster> + <cluster>): (1) proved the delta was purely additive (154 added / 0 removed — the existing aggregator log path untouched); (2) proved that <cluster>'s extra hop across v0.0.2 (a Bedrock-guardrail `_helpers.tpl` change) rendered as a genuine **NO-OP on that cluster**, which reading the source diff alone could not establish. **The negative control that makes the green result non-vacuous: cross-diff the TWO clusters' deltas against each other** — it should reduce to only the legitimately cluster-specific lines (here cluster name and Infisical `secretsPath`). **If it reduces to ZERO, the value stack was not actually applied** and your whole render is unparameterised.

23. **"ABSENCE READS AS PASS" RECURS AT EVERY LAYER OF A VALIDATION SYSTEM — fix it at each one explicitly, because fixing it at one layer does nothing for the others.** Seven instances found while building ONE framework, all the same shape: (1) **METRIC** — a nonexistent metric returns empty and empty evaluates as "no errors", so the check passes forever (examples: a metric absent at the pinned version; a lazy per-object counter; readiness/waiting metrics omitted by the exporter; a mistyped status-code label; a validation counter present on only part of the target roster); (2) **QUERY** — a negated matcher on a MISTYPED label matches EVERY series instead of returning empty, yielding a ratio of exactly 1.0 that reads as steady state; (3) **LOG** — `kubectl logs` with a selector silently caps at 10 lines/pod, so "0 errors in 1h" means "0 in the last 10 lines"; (4) **RESULT** — a `baseline_compare` check emitting a null payload produces a P0 baseline the later phase cannot diff, presenting as "no baseline available" rather than as a failed run; (5) **FLEET** — an aggregator deriving its denominator from `ls results/*.json` reports 12/12 PASS when 13 clusters were dispatched and one agent died silently, **because the evidence of the missing cluster's absence IS its absence**; (6) **LINTER** — a command-safety rule reported 0 findings across 93 checks because its escape-hatch keyword scan ran over FILE-WIDE prose, so one unrelated sentence containing "version skew" at line N of a 2400-line file silently cleared every check in that file; (7) **TEMPLATING** — a runner injected three new run inputs into an agent prompt whose template had no matching placeholders, so all three substitutions were NO-OPS and nothing errored (one was the probe-authorisation line gating the only check able to prove STRICT mTLS had not silently dropped — the feature read as shipped while being completely inert). **UNIFORM COUNTERMEASURE: never let the system infer completeness from what it happens to find.** Require an explicit expected-set at every layer — a metric arming proof, a positive existence matcher, `--tail=-1`, a declared payload, a NAMED roster of clusters, a per-check-scoped lint window, a pre-write placeholder assertion — and **FAIL CLOSED when it is missing**. **A count is never sufficient where a NAMED LIST is possible: a count cannot tell you WHICH one is missing.** The shape is always the same — *the mechanism reports success because nothing objected.*

24. **Prove non-vacuity; never infer it from a clean run — and plant one known-bad input PER QUESTION the tool asks.** (a) **Every lint rule must ship with a self-test that injects a positive instance and asserts detection.** A rule that has never fired has not been shown capable of firing. (b) **A single negative control validates a single CODE PATH, and the untested path is where the bug lives.** A metric-existence verifier ran two independent probe types — one for metric names, one for label names. Injecting a fake METRIC (`istio_definitely_not_a_real_metric` → ABSENT) proved only that the metric probe discriminates and said NOTHING about the label probe — which is exactly the probe that would have caught `http_status_code` (real name `http_response_status_code`), passing silently for weeks. The fix was a second control: an injected fake LABEL (`up{ifv_definitely_not_a_real_label}` → ABSENT). **Enumerate every distinct question your tool asks and plant one known-bad input per question.** (c) Two false-positive traps from the same build, both cry-wolf in a form that teaches people to disable the linter: PromQL fences may carry BOTH `#` and SQL-style `--` comments, so a linter stripping only `#` flagged a comment literally reading "Do NOT use `increase()`" as an `increase()` usage — **strip every comment syntax the embedded language allows before pattern-matching**; and a line-scoped name scan needs a line WINDOW, not a line, because an arming-proof comment sits ABOVE its expression. (d) Finally, `helm repo add` / `helm dep build` mutate LOCAL state, not the cluster — they are WARN, not a read-only violation.

25. **JUSTIFICATION MUST BE DECLARED AND VERIFIED, NEVER INFERRED FROM COINCIDENCE — and a declaration must not launder an unverified claim.** A metric verifier classified a metric as ARCHITECTURAL (absent for a structural reason, therefore fine) whenever its presence set happened to equal a cluster-profile predicate such as `cloud=aws`. **That turns the most reassuring category into the best hiding place for real gaps**: a metric genuinely missing from 6 clusters is waved through because the 7 it is present on happen to share a label. **Fix that worked: delete the inference entirely.** A partial presence set is explained ONLY by (a) the owning check's `applies_to` already narrowing to exactly the present clusters; (b) an allowlist entry declaring structural absence and NAMING `expected_absent_on`, with the observed missing set required to be a SUBSET so a NEW gap still gates; or (c) an allowlist entry declaring laziness and naming `armed_by`, with the tool verifying that arming proof is itself present everywhere. The coincidence computation survives only as a hint string explicitly labelled "a HYPOTHESIS to check, not a justification". **PROVE THE GATE BITES**: running with a nonexistent allowlist must revert every justified row to gating; an under-declared structural entry must fail while NAMING the omitted clusters; a lazy entry armed by a partially-present sibling must fail. **If deleting the justification file does not turn the report red, the justifications were never load-bearing.** **Scope every exemption by the same selector the CONSUMER uses** — an exemption keyed on a bare metric NAME is job-blind: `controller_sync_errors_total` reads 3/13 as a union across `job=istio-cni` (1 cluster) and `job=istiod` (2), while the owning check only ever queries `job=istio-cni`, so real presence is 1/13 and the exemption would survive on an unrelated counter even if the right one aged out entirely.

26. **WHEN AN EXEMPTION MECHANISM CANNOT EXPRESS A CASE, RAISE THE BAR — DO NOT RELAX THE EXISTING PATH.** An allowlist could justify only a PARTIAL (n/N) presence; a 0/N lazy counter could not be declared at all, and the tempting fix is to loosen the existing rule so 0/N slips through. **Correct fix: a SEPARATE, HIGHER-bar path** — `kind: lazy` + `absent_everywhere: true` + an EXACT metric name (a regex pattern is refused as an allowlist defect, so one wildcard cannot exempt an unbounded family from having to exist) — landing in its own class `LAZY_DECLARED_ABSENT`, deliberately NOT merged into the existing `LAZY_DECLARED` bucket. **Rationale worth reusing: a 0/N metric has NOTHING live corroborating that its name is even spelled correctly, so folding it into the reassuring category recreates the exact "best hiding place" failure the allowlist exists to prevent. Weaker evidence deserves its own visibly-weaker class, never promotion into a stronger one.**

27. **WRITING A PRINCIPLE DOWN IS NOT AUDITING EVERY READ OF THE FIELD — and a rule that REPORTS a discrepancy while still acting on the untrusted value is the most convincing form of the bug.** A validator module carried the sentence "self-reported fields are inputs to be verified, not facts" **in its own docstring**, and its core verdict-recompute path still read the untrusted self-reported severity with the catalog only as a fallback. Net effect: a result that downgraded a blocking FAIL to advisory **recomputed as PASS** — the exact hole the documented principle existed to close, inside the file that documented it. A separate rule dutifully REPORTED the severity mismatch, which is what made it look handled. **RULE: when you adopt a trust rule, grep EVERY read of the untrusted field and check each one individually — the doc comment proves intent, not coverage.** And **fail closed on unresolvable inputs**: an unknown check id must be treated as blocking, not skipped.  **The recompute must read severity ONLY from the catalog and may only move a verdict DOWNWARD (harden), never upward — a correction that can soften is an attack surface.** The same system shipped three further self-grading inputs: **IDENTITY** — a truncated or near-miss id silently fails baseline joins and reads as benign "no baseline available", whereas an invented id fails membership loudly; require catalog ids verbatim and treat near-misses as harder errors than unknowns. **DENOMINATOR** — deriving the expected set from `ls results/*.json` hides a dead worker because it writes no file; freeze a named roster at dispatch, aggregate fail-closed against it, and refuse any verdict without it. **LEGALITY** — a claim that a predicate was legitimately not evaluable must be checkable from a declared contract field, never the producer's prose; otherwise a plausible paragraph can excuse a failure. **For every result field ask who wrote it and whether the grader has an independent source: a producer-written field without one is a hole.**

28. **AGENT JUDGMENT IS NOT A CONTROL, and a DIFFERENT MODEL is the cheapest way to find your contract bugs.** (a) The same broken check produced **2 false PASSes and 1 correct ERROR across 3 agents** on an identical catalog: a PromQL check whose join was structurally unarmed (`sum by (…)` dropped `cluster` while the join matched `on(cluster, …)`) was run against three clusters; two agents reported PASS reasoning "the join returned empty, therefore no violations", one reported ERROR reasoning "the expression is structurally unarmed, empty proves nothing". **When a check CAN be misread, some non-zero fraction of executors WILL misread it, even capable ones with an explicit spec** — so encode a STRUCTURAL control (a join-key-resolves arming query that must return rows) which errors deterministically rather than depending on who ran it. (b) **Fixing one instance of a defect class does not fix its siblings**: that exact join bug was found, fixed and written up for check L3.06, while L3.07 — the adjacent check in the same file with the same shape — was never audited and shipped broken. **After fixing any structural defect, mechanically sweep every expression of that shape and report the count CHECKED, not just the count fixed.** (c) **CROSS-MODEL EXECUTION EXPOSES CONTRACT BUGS THAT SAME-MODEL RUNS ABSORB SILENTLY**: a framework generated per-check line ranges starting at the opening YAML fence while its prompt demanded the range "begin at that check's own `id:` line" — one line later. Three Claude agents silently absorbed the off-by-one and proceeded; a Codex worker on the identical prompt followed the rule literally and recorded ERROR on **all 69** selected checks, producing zero payloads. **Codex was RIGHT — the rule as written was unsatisfiable by the generator.** Lessons: an over-strict contract clause plus a tolerant executor is a latent bug that surfaces only when you change executor, so **run a different model against your own contract before trusting it**; write validation rules to their INTENT, not an exact offset ("the range must CONTAIN its `id:` line within the first 3 lines" proves the range points at the right check, while "must begin at" pins a brittle offset for no extra safety); and **when an agent refuses en masse rather than proceeding, suspect the CONTRACT before the agent — a 69/69 failure with a single uniform cause is a spec defect, not 69 execution failures.**

29. **MECHANICAL LINTING BEATS CAREFUL REVIEW, with numbers — and a lint rule that fires repeatedly is describing a DESIGN FLAW, not author carelessness.** (a) The the suite framework was built, then fixed across two rounds by five specialist agents each verifying live against clusters, plus a full single-cluster live smoke test that found 17 defects. **After all of that, the first run of a conformance linter found 45 MORE errors**: 30 section-order violations, 10 decorated headings that broke name-based section lookup, 4 instances of `baseline_compare: true` without P0 in `phases` (so the baseline being diffed was never produced), and 1 check declaring an aggregation-only phase while invoking cluster commands. **40 of the 45 were fixable by a deterministic script in one pass.** **Careful agents reliably catch SEMANTIC defects (wrong metric, wrong predicate, wrong scope) and reliably MISS STRUCTURAL ones (ordering, naming, phase-set consistency, cross-field invariants) — because structure is invisible while you are reasoning about meaning.** Build the linter EARLY, not as a finishing touch, and make every recurring defect a lint rule the moment it recurs. (b) The `baseline_compare`-without-P0 bug shipped **THREE separate times** across different authors and files, before AND after a lint rule existed. **Root-cause diagnosis worth reusing: the attribute names a CONSEQUENCE ("a baseline exists") rather than an ACTION ("produce one"), and the author writes it while thinking about the phase they care about — the grading phase — while the baseline belongs to someone else's run. Nothing in the authoring flow walks them back.** **FIX HIERARCHY, best first: (1) normalise at LOAD time so every consumer sees the corrected value and the bad state cannot exist; (2) enforce at DISPATCH time so the runner refuses; (3) lint after the fact — which only tells you it already happened.** Keep the lint rule as belt-and-braces, but **a rule firing 3× means you fixed the instances and not the class.** Same "make invalid states unrepresentable" principle as `learnings-helm-ci.md`.

30. **STATIC-ANALYSING MARKDOWN-EMBEDDED COMMANDS: two parsing rules, both learned by getting them wrong — and when a naive grep and a careful agent disagree, suspect the GREP.** (1) **Scan ONLY fenced code blocks, never prose.** A raw grep across a 93-check catalog reported 49 `increase()` usages and 12 "`kubectl logs` without `--tail`"; restricted to fenced `bash`/`promql` blocks the true figures were **16 and 0**. The entire difference was Gotchas prose DISCUSSING those traps — including text explicitly warning against them. **A linter that flags the documentation of a trap as an instance of the trap is worse than no linter.** (2) **Join shell line-continuations before matching**: a line-based scan flagged a `kubectl logs` invocation as missing `--tail` when `--tail=-1` sat on the backslash-continuation line. **General lesson: rebuild the count with a parser that respects document structure BEFORE concluding anything or dispatching rework** — I nearly re-dispatched three agents to fix 49 problems that were actually 16. **Also strip every comment syntax the embedded language allows before matching**: PromQL fences in the catalog carried both `#` and SQL-style `--`; stripping only `#` falsely flagged "Do NOT use increase" as executable usage. Join trailing-pipe continuations as well as backslash continuations. See `learnings-agent-workflow.md` for the extended parsing rule.

31. **FREEZE THE PLAN AND SNAPSHOT THE EXECUTABLE DEFINITION — freezing METADATA is not freezing what the agents actually ran.** (a) **Freeze the plan.** With no frozen plan file, an aggregator derived the catalog total by reading the check catalog at aggregation time; the catalog was being edited concurrently and the selected-check count moved **77 → 78 → 79 across successive reads WITHIN A SINGLE aggregation run**. Two aggregations of the same run could disagree and neither was wrong. **Fix: the runner emits a plan snapshot at generation time containing (1) the roster of dispatched units BY NAME, (2) the catalog total, (3) per-unit selected/skipped id lists, (4) any flags a later stage needs, and (5) a CATALOG FINGERPRINT** — item 5 is what turns this from tidy into trustworthy, because it makes generation-time-vs-read-time drift VISIBLE instead of silently producing two different reports. (b) **But a fingerprint is not enough — TOCTOU bites the definition too.** A manifest carried a catalog fingerprint, roster and per-check flags, and the aggregator was told "on drift the manifest wins, because it records what the agents were told to run". **That premise was FALSE**: the agent prompt sent agents to the LIVE catalog and explicitly instructed them to re-locate a block BY ID when line ranges moved. So a mid-run edit meant agents faithfully executed the NEW text while the manifest described the OLD — a run graded against something it never executed, with internally plausible ids, counts and verdicts throughout. **Note the by-ID fallback WAS the mechanism**: it existed to make prompts robust to line drift, and that robustness is precisely what let stale prompts succeed against changed text. **Fix: atomically SNAPSHOT every input the agents read (spec, config, check bodies) into the run directory, generate prompts and manifest FROM the snapshot, have agents read ONLY the snapshot, and record snapshot + per-prompt hashes — then make the downstream stage PROVE the binding (snapshot present, hashes match, no result claiming it read live) and REFUSE the current gate when unproven, not defer it as a next-run defect.** (c) **Validate any AUTO-DISCOVERED input against what makes it USABLE, not against a glob.** A runner auto-selecting "newest directory matching `runs/*-P0`" picked `runs/TEST-aggregator-P0` — a test fixture — as the baseline for a real run, and would equally pick a P0 whose `results/` is EMPTY. **An empty baseline is WORSE than no baseline**, because the run proceeds believing it has one and every baseline-relative check silently degrades to "no baseline available" instead of failing loudly. Validate on non-empty results, roster satisfied, matching fingerprint, conforming name pattern — and refuse rather than fall back. (d) **Inventory every PARSER of a source before changing parse-time semantics.** The same framework parsed its catalog twice — a Python loader used by all the tools, and an independent `awk` selector inside the bash runner that decides what actually gets DISPATCHED. Applying a new normalisation rule to only the Python loader would have made every TOOL report the catalog as correct while the RUNNER still dispatched the wrong set — **reports saying the bug is fixed while it remains in the execution path, which is worse than not fixing it.** Apply to all parsers and add a test asserting they agree; best is to consolidate so the divergence is unrepresentable.

32. **Comparing a kubectl-derived count against a PromQL-derived count is SAMPLING-SKEW SENSITIVE, and quantile windows are ASYMMETRICALLY sensitive — store both timestamps and the window as mandatory payload fields.** A three-way equality read `active_proxy_count=183` vs `redirection_annotated=182` purely because the pod dump and the metric scrape were ~10 minutes apart; co-sampled five minutes later it was 182 == 182 == 182. **Any check equating a live API snapshot to a scraped metric must co-sample at the same instant or declare a bounded skew tolerance, and must store BOTH sampling timestamps so a later diff is interpretable.** Separately: a waypoint p99 read **24.8 ms at `[5m]` vs 7865 ms at `[1h]` AT THE SAME INSTANT** — i.e. **the SHORT window MISSES the tail rather than smoothing it**, which is the opposite of the intuition. Store the window as a mandatory payload field and **refuse cross-window diffs**. For this check family the skew rule was refined to a ~120 s ceiling, ±1 beyond one scrape interval: excess skew warrants WARN and re-sampling, not FAIL. Co-sampling does not by itself align two independently scraped exporters, and a run-wide frozen anchor is distinct from a per-check co-sampling window. See `learnings-observability.md` for the refined skew and exact-count rules.

## Coverage, Scope & Operations (continued)

33. **A diff/compare loop that short-circuits on a cumulative failure counter silently stops checking after the first real finding, and the truncated report still ends in a confident-looking summary.** A byte-compare harness over N targets carried a per-target existence guard shaped like "if not exists: fail += 1" followed by "if fail: continue" — where `fail` was the *run-wide* counter, so the moment ANY target differed, the continue fired for every remaining target too. A three-target sweep reported "N-1/N identical, 1 differs," naming only the alphabetically-first differing target and silently skipping the others, which genuinely differed. It was caught only because an independent per-object spot-check contradicted the file-level verdict — nothing in the output itself looked wrong. The class: a loop variable meaning "this iteration is unusable" was sharing storage with the accumulator meaning "the run has findings." A per-iteration skip/missing flag must be local to the iteration; only the accumulator may be run-wide. Cheap structural countermeasure: count iterations actually compared and assert that count equals the number discovered, before printing any summary — and report the named set of identical/differing targets, never just a count, so a truncated run is visibly short. This bug is intermittent by construction (it depends on which target differs first in sort order), so it can pass a green test suite and a negative control and only misfire on the one real run that matters.


## Measurement Windows & Probe Construction

34. **Choose a measurement-window anchor so that neither a rollout's tail nor any operator action falls inside it — and when one does anyway, preserve the anchored grade rather than re-anchoring to make the number look nicer.** Three instances of the same defect recur in any phased rollout validation: (a) a draining pod or workload still mid-termination at the exact anchor instant produces a spurious advisory failure that clears itself at the next check — prevent it by confirming the workload is fully settled (desired == ready == updated, nothing terminating) before generating the measurement plan; (b) a terminating old instance can remain the sole "down" scrape target while the live census is otherwise homogeneous — the correct handling is to preserve the anchored grade, name the offending object, exclude it from the live census, and add a follow-up check, never silently re-grade the artifact; (c) an operator action (a manual restart, a recycle) taken inside the measurement window contaminates attribution even when it is operationally correct and harmless, because churn from the operator action becomes indistinguishable from churn caused by whatever you're validating. Rule: any required post-change recycle happens before the plan is generated or after the phase completes — never inside the window — and any drain/reset finding gets checked against the recycle timestamp first. Before plan generation, `kubectl get ds ztunnel -n istio-system` should show `N/N/N` desired/ready/updated with no terminating pod. A clipped roll-tail can legitimately yield INFO in one check and FAIL in another with different predicates. **Record adjudication in a separate addendum; preserve the original measured rows byte-verbatim if re-issued and leave the source untouched.**

35. **A negative-test probe built with a JSON merge patch silently loses its command the "obvious" way — a merge patch REPLACES the whole array it targets, so adding a `securityContext` by nesting a `containers` array wipes whatever command/args were already there.** Never put a full `containers` array inside a `kubectl run --overrides` merge patch when you only need to add pod-level security context — the merge patch replaces the entire array wholesale rather than merging into it. Correct form: put `securityContext` at the *pod* level, inside the existing overrides' `spec` object, alongside (not replacing) the existing container spec. This matters more than it looks when the negative test's whole point is a single authorized probe attempt with no retry budget — a probe that silently loses its command consumes the sole authorized attempt and turns a real security-enforcement test into a false blocking error with no correctness signal at all. If you genuinely need a full container spec, include the complete command and args in the same override rather than assuming the merge is additive. For a restricted-PSS curl probe, the pod-level context can be `{"runAsNonRoot":true,"runAsUser":100,"runAsGroup":101,"seccompProfile":{"type":"RuntimeDefault"}}`: `curlimages/curl` names its `USER`, so `runAsNonRoot` without numeric `runAsUser` can fail with `CreateContainerConfigError`. A missing catalog security-context recipe must be corrected deliberately: editing `checks/` mid-campaign changes the fingerprint and forces `--allow-catalog-drift` for later baseline comparisons (#17). The runner requires the FULL check id: `--authorize-probe L3.09` fails with "does not match any check id in `<catalog-snapshot>/checks`"; use `--authorize-probe L3.09-strict-enforcement-negative-test`. Apply that full-id convention to all check-id inputs; refusal before prompt generation is safer than a silent `PROBE AUTHORIZED: no`.

36. **Adjudicating an aggregate error-rate or latency "regression" needs a three-part method, because a single aggregate number can be worse in three structurally different ways.** (1) Sweep the same ratio across the pre-change baseline period at the same resolution and ask whether the baseline anchor itself would have failed its own threshold — a baseline that happened to land in a quiet trough sets an unrealistically tight bar; extend the sweep across multiple weeks to establish whether a burst pattern is chronic before arguing about mechanism. (2) Decompose the aggregate by upstream/constituent and by error class before attributing a move to the thing you're validating — a handful of targeted queries (error rate by constituent, error class split, connection-level failure counters) usually settles whether the aggregate move is real, is one constituent, or is entirely elsewhere. (3) Check for a Simpson's-paradox mix shift — an aggregate can worsen while every individual constituent improves or stays flat, if a low-latency/low-error constituent's traffic share simply drops; reproduce the aggregate as a weighted sum of per-constituent rate times share before believing the aggregate number at all. Always state the honest anti-claim: name the one constituent that genuinely did get worse, and check it against its own historical band at the same time of day before calling it a regression. Concrete decomposition: `sum by (envoy_cluster_name) increase(envoy_cluster_upstream_rq_xx{envoy_response_code_class="5"}[1h])` locates the upstream; `sum by (envoy_response_code)` on `envoy_cluster_upstream_rq` separates 500/503/504; near-zero `cx_connect_fail`/`none_healthy`/`pending_overflow`/`rx_reset`/`retry` counters argue against data-plane connection failure. Sweep the sliding 1h ratio across the pre-change day, then a 1d-step `increase()` over 2+ weeks for chronicity; compare each upstream p50 at the same clock hour a day earlier. Reproduce `downstream_5xx = Σ per-upstream_500_rate × share`. **State the attribution limit:** this metric has no upstream-pod label, so it cannot identify a pod. Targeted remeasurement is a separate addendum; keep the anchored FAIL immutable.


## Negative Controls & Independent Comparators

37. **A negative control is only a control if it has its own positive check that the intended perturbation actually applied — at both the source-file level and the rendered/executed level — or it silently degenerates into exactly the failure mode it exists to catch.** A control's pass condition is "the output moved," so a control that no-ops looks exactly like the healthy-but-unperturbed case, and a control aimed at an "expect no change" assertion that also no-ops looks exactly like success. Concretely: mutating a values path that doesn't exist on the target leaf produces a byte-identical render — a green-looking result from a control that tested nothing; a values change can alter the source file's hash while leaving the render completely unchanged because it targets the wrong key. Every control therefore needs BOTH a file-level change gate and a rendered-effect gate, and any text substitution needs an exactly-one-match assertion so an ambiguous or absent target hard-fails instead of silently editing nothing. Further hardening: pair every "the output moved" control with an over-sensitivity control (an inert, semantically-void edit like a comment insertion must leave the render byte-identical) — otherwise "it moved" only proves the harness reacts to *any* edit. For a set-membership assertion, add a wrong-shape control (a value shaped for the wrong schema variant) that must leave the target unchanged rather than silently accepted. **Perturb an object the assertion can see.** A stream deliberately excluding ServiceAccounts cannot be tested by changing a ServiceAccount. Change a Deployment `nodeSelector`: the stream hash must move, the differing kinds must gain `Deployment`, no ServiceAccount may move, and other targets must stay byte-identical. For a component-keyed path mistakenly applied to a flat chart, the rendered object must remain un-adopted and the adopted count fall by exactly 1.

38. **When auditing a self-reported result from a harness whose author has already disclosed a bug in it, do not re-run the author's harness — build an independent comparator from scratch, and give it these five structural properties.** (a) Any per-iteration "this one is unusable" flag must be local to that iteration, never shared with a run-wide accumulator (the short-circuit class above). (b) Assert that the count of items actually compared equals the count discovered, BEFORE printing any summary. (c) Emit named sets of what matched/differed, never bare counts. (d) Parse with a real multi-document-aware loader, never a line-based or single-document tool applied to multi-document output. (e) Treat any parse or render error as a hard failure, never as "zero objects found." A correct comparator finds every differing target; a short-circuiting one silently reports only the first. For an isolated claim that removing an inert block is a no-op, compare HEAD against HEAD with only that block restored (`git apply -R` of the removal commit, verified as head +N/−0); base-vs-head mixes it with other changes. Pair this with a negative control removing a LIVE annotation from a leaf with an explicit annotation and no managed identity: exactly one object on one target must move.

39. **Proving that a code-path change is genuinely inert/dormant — where the path is gated off so every renderable input should be byte-identical — needs four independent controls, because "the render looks the same" is the textbook vacuous-evidence shape.** (1) A byte-identical control against a baseline captured BEFORE the edit, with the render's exit code AND non-emptiness asserted before any content check — a failed render returns empty output and satisfies every "does not render X" assertion by accident. (2) Re-run the same control with an input that actually exercises the changed code path — a control whose input never enters the affected branch can pass even after the "dormant" change is reverted, proving nothing. (3) A dormant-path proof: unblock the gated path in an isolated fixture only, render before and after unblocking, and diff the two — pick the environment/variant that actually discriminates, since some environments collapse every variant to the same output regardless of the change. (4) A negative control proving the SHIPPED artifact still blocks the path, plus a committed static assertion for any set-membership fact that no render-level check can see (a dropped member of a set that never composes into rendered output is invisible to any render diff). Capture the baseline with `git show` before editing and assert the fixture mutation changed its source (`cmp` gate). A discriminating production input may be necessary when dev/test collapse every class to `["*"]`; include the relevant provider spec so the changed routing branch is actually entered. The static control should assert exact set equality.

40. **A live-environment verifier can be proven non-vacuous without touching the live environment at all: factor every live-readback assertion into a pure function of `(observed, expected)` so a self-test mode can feed it synthetic good fixtures plus one mutation per assertion.** A verifier built this way shipped with dozens of mutations and zero undetected, run entirely offline before its own PR was opened — each mutation flips exactly one field the assertion is supposed to catch, and the self-test fails loudly if any mutation goes undetected. Two further controls make it trustworthy rather than just thorough: (a) have the script read the derivation logic out of the template it's supposed to mirror and hard-fail if it doesn't match the exact rule implemented elsewhere — a source-level agreement check that no finite input matrix can substitute for; (b) verify the live-readback field NAMES against an actual live resource, never from memory or documentation — a cloud API's read-back shape commonly differs from its write shape (different casing, different key names) and omits keys that are unset, so absence must be asserted as a failure, never read as a pass. The worked verifier used 22 mutations with zero undetected. Its source-agreement check exited 2 when `trunc 20` was changed to `trunc 16`. For `gcloud storage buckets describe --format=json`, the inspected readback used snake_case keys: `uniform_bucket_level_access`, `public_access_prevention`, `versioning_enabled`, `default_kms_key`, `default_storage_class`, `lifecycle_config.rule[]`. Unset keys were omitted. When a CLI proxy truncates piped JSON, redirect the raw response to a file before parsing.

## Further Validation Controls

41. **Two discrimination controls that use REAL state rather than a synthetic corruption, and are therefore stronger than one.**
    - **PRE-SYNC BASELINE.** For a post-merge verifier, run the batch's OWN prediction table **before the targets sync**. It returns 0/N while the **previous** batch's table returns N/N **in the same session** — same tool, same session, opposite verdicts on real live state. That exercises the genuine not-yet-created condition, so a later N/N cannot be the checker returning green by construction. Cheap: extract the table the moment the PR merges, before the GitOps controller polls.
    - **CALIBRATE THE DERIVATION AGAINST ALREADY-LIVE OBJECTS BEFORE TRUSTING IT ON THE NEW ONES — an uncalibrated formula scoring N/N proves nothing.** Re-derive every batch's identities against all previously-live objects first. **Quote the WRONG variants rather than re-deriving them**: keep both a variant that scores **zero** and one that scores a near-miss, because a 0-scoring control and a near-miss control test different things.

42. **The four controls that make a "the render does NOT contain X" claim non-vacuous.** A negative assertion is the easiest thing in validation to fake, and all four of these have been observed passing on nothing.
    - **(1) VACUITY GUARD FIRST.** Templating a chart that requires values with **no values** exits 1 and emits **0 lines** — and 0 lines satisfies every `does not contain X` grep. **Assert `exit == 0 && lines > 0` before trusting any negative.**
    - **(2) SUBSTRING GREPS ARE UNSAFE whenever names are prefix-related.** `storage-<cluster>` matches inside `storage-<cluster>-test`, so a grep-based check reports success against the sibling. Assert **full-path EQUALITY** or an exact segment match (`split('/')[1]`), never a substring. The same trap governs SA names: `controller-<cluster>` is a strict prefix of `controller-<cluster>t` — compare parsed tuples with `==`, never `in`. Splitting on `@` is the cheap anchor.
    - **(3) EVERY negative control needs a PROVEN-ABLE-TO-FAIL TWIN.** For each "renders 0 of X" claim, exhibit a sibling input where the same check returns non-zero: absent storage family → the same grep returns 5 on another cluster; zero policies → a second cluster renders 3, **and** `--set <policy>.enabled=true` against *this* cluster's own file renders 1 (which is what proves the overlay SUPPRESSES rather than the gate being dead); `targetRevision: main` → the same extractor returns pinned values for pinned apps.
    - **(4) STRUCTURAL SIBLING EQUIVALENCE catches key drift a line diff hides.** `json.dumps(obj, sort_keys=True)` with the varying token replaced by a placeholder, compared against the sibling.

43. **Render-proof recipe for policy/exception edits whose effect is computed by code rather than declared in YAML — three negative controls make it non-vacuous.** Import the rendering function directly, render every rule against a fixed list of contexts **plus an empty context `{}`**, dump to a file, and diff before-file against after-file. The three controls: **(1) retarget the new entry to the PREFIX-SIBLING** and confirm the diff shows the principal landing in the WRONG block — substring matching passes this and exact/block-diff does not, which is what makes the control discriminating; **(2)** render the `<base-ref>` version of the file and confirm it is **BYTE-IDENTICAL** to the "before" capture; **(3)** assert the **empty context** renders NO templates, which is the direct offline proof that a project-scoped template only fires on the project-attached code path. Two mechanical traps: importing an uninstalled in-repo package needs `PYTHONPATH=<repo root>` (a bare `uv run python script.py` outside the repo root fails `ModuleNotFoundError`), and **`uv run pytest` rewrites `uv.lock` every time** — `git checkout uv.lock` before committing or a one-file PR silently becomes two.

44. **To separate YOUR diff from standing drift in a large plan/preview, count FIELD-LEVEL change lines — counting resource KINDS is not enough.** On a preview reporting `~476 to update`, the kind-level breakdown (473 alert policies + 1 endpoint + 1 packet-mirroring + 1 the-actual-PR) still left the reviewer asserting rather than proving that the 475 were inert. Counting field-level change lines yielded `474 + deletionPolicy / 1 ~ rules / 1 ~ denyRule / 1 ~ exceptionPrincipals` — i.e. **the only SEMANTIC change in a 476-resource plan was the one field the PR added**, and the 475 others shared a single provider-version-migration field delta. Extraction: `gh run view --job <id> --log > f` then `grep -oE` for the `~ <type>: (update)` and `[+~-] <field>:` shapes. **The log is ~500 KB — redirect to a file, never pipe to `head`.** Corollary: where merging runs an apply, any merge sweeps up all standing drift — flag it in the PR body, do not fix it there.

45. **A post-change observation window SHORT relative to the workload's slowest cadence has two sides; report BOTH.** After a cutover whose batches landed 25 minutes to 21 hours before measurement, a 48-hour log window has: **(a) STRENGTH — COMPLETE coverage of the post-change era; nothing the change broke can predate it**, stronger than a longer window on an older change; **(b) WEAKNESS — low-cadence paths (daily, weekly, month-end jobs) have not yet cycled**, so "nothing broke" does not yet mean "nothing can break." Reporting only (a) overclaims; reporting only (b) discards a real result. Judge the ratio of window length to the slowest scheduled job, not the window length alone.

46. **When two NORMALIZATIONS of the same raw signal move in OPPOSITE directions, that divergence independently disproves a proposed driver — and it is invisible if you only track the raw counter.** A panic rate tracked across a version upgrade rose in raw terms (1372 → 1896 → 1824 → 1981 per hour) and per-1k-TCP-opens, while **per-1k-application-requests FELL** (65.1 → 34.1) across the same step. Since the hypothesised driver (version skew) had by then been closed, and traffic-normalized incidence moved the wrong way, both skew and aggregate load were ruled out by arithmetic rather than by argument. **Carry at least two denominators — one transport-level, one application-level — for any chronic-rate investigation**, and record the full normalized series, because a raw counter alone cannot distinguish "more of it" from "more traffic."

47. **A guard that collects objects by `kind` and never asserts `apiVersion` is FAIL-OPEN: it reads as coverage it does not have.** A policy-presence gate matched `d.get('kind') == 'ValidatingPolicy'` and never checked the group/version, so mutating a policy's `apiVersion` from the served version to a non-existent one left the guard **GREEN (rc=0)** — the policy counted as present while it would install nothing and never reach admission. Found by an **identity mutation**; the value-level mutation set the author derived from the assertions never reaches this class. **For any gate that asserts an object exists, mutate its `apiVersion` as a first-class control**, and treat "the guard is green" as evidence only once you have seen it go red.

48. **Before building an in-cluster runner for a recurring validation playbook, know that the honest ranking is decided by what the checks NEED TO CALL — and for infrastructure validation that rules out the entire synthetic-probe category, however well it integrates.** Surveyed six shapes against the requirement "run kubectl reads, HTTP calls and metric-store queries on a schedule, report out, work on more than one cloud, be GitOps-managed". **The disqualifier is capability, not weight:** hosted/private-probe synthetic monitoring and Prometheus blackbox-style exporters can only do HTTP/TCP/DNS/ping, so **they cannot read pod state, namespace labels, or CRD status, and cannot query the metric store** — they covered 2–3 of a 12-check playbook and are a complement, never the runner. Likewise, E2E/conformance test harnesses (operator-test frameworks, cluster-conformance suites) are **CI-shaped with no scheduling primitive** and are the wrong tool for a runtime loop. **The answer for a bounded check set is the boring one: a scheduled Job running a purpose-built image with the cluster CLI, an HTTP client and a JSON tool, deployed per target, with a read-only ServiceAccount, the check scripts in a ConfigMap and credentials in a Secret.** Zero new CRDs, zero new controllers, ephemeral footprint, and the check logic is versioned in the same repo as everything else. Its real costs are the ones to plan for: **no execution history or dashboard** (so reporting must be pushed out — a chat webhook, an annotation, a ticket comment — from the job itself) and shell that gets unwieldy past a couple of dozen checks (move to a real language before that, not after). **Escalate deliberately, on a named trigger, not on aesthetics.** A per-check CRD operator earns its keep only past ~20 independent checks, where per-check scheduling and per-check metrics start to matter — and check whether it is mid-rewrite before adopting. A DAG workflow engine is justified only by genuine step dependencies or artifact passing; independent checks do not need it, and each step costs a pod. A full test-orchestration platform that drags in a database and object storage fails the "lightweight" requirement on its dependency list alone. **And the LLM-agent-in-cluster option is a category error for this job:** it has no scheduler of its own (you wrap it in the same scheduled Job anyway), it costs tokens per run, and **it is non-deterministic — the same input can produce different checks, which is disqualifying for a gate whose entire value is that a red result means the same thing every time.** The reasoning that makes an agent good at *investigating* a failure is what makes it unfit to *be* the assertion. (Survey 2026-05-25; the deterministic-gate-vs-adaptive-agent split is the same boundary `learnings-agent-workflow.md` draws for fan-out work, and `references/learnings-observability.md` for discovery-vs-assertion.)

49. **When TWO parsers read the same artifact, they WILL diverge, and the divergence is silent in the worst possible direction: the item lints clean, vanishes from execution, and leaves the denominator — every tool reporting green.** A runner's `awk` selected check blocks by **exact string compare** against the fence line while the Python linter/loader accepted the near-misses (`yml` instead of `yaml`, an indented fence, a trailing space). A check written in any of those forms **passed the linter and was then never selected, never run, and never counted as missing** — because the same loose parser that accepted it also produced the total it was compared against. Nothing was red. **THE FIX IS TWO-PART AND BOTH PARTS ARE LOAD-BEARING.** (a) **Make DETECTION deliberately WIDER than ACCEPTANCE.** A permissive "anything trying to be a fence" pattern finds candidates; a strict rule then **rejects every candidate not byte-identical to the one canonical form.** The loose regex exists precisely so the strict rule has something to reject — a strict-only parser cannot see what it is failing to see. **Widening ACCEPTANCE without changing the other parser reopens the hole**, so say so in a comment at the acceptance site. (b) **Assert the two parsers agree on the COUNT, and make the mismatch fatal.** One cheap integer comparison at generation time catches the entire class regardless of which construct caused it. **GENERALISATION: any time a format is consumed by two independently-written readers — a shell selector and an application loader, a linter and a runtime, a CI job and a local script — the artifact has an unowned contract, and the only durable guards are a single canonical form, asymmetric detect/accept, and a cross-parser count assertion.** The instinct to "just make both parsers lenient" is exactly backwards: it makes the divergence bigger and unobservable. (Same family as #23 — absence reading as pass — but here the absence is manufactured by the tooling itself, so no amount of arming proof at the check level would have caught it.)

50. **N agents sharing one datastore must be pinned to ONE FLEET-WIDE OBSERVATION ANCHOR — per-agent anchoring fixes drift WITHIN a target and does nothing ACROSS targets, which is the comparison you actually publish.** Thirteen agents each evaluating "the last 15 minutes" at their own start instant, across a dispatch wave plus spillover, were measured **~40 minutes apart end to end.** Every individual result is internally consistent and correctly labelled; the fleet table built from them compares windows that do not overlap, and no single row looks wrong. **Fix: the runner computes one absolute UTC instant, injects it into every prompt, and every time-windowed query is expressed as an absolute window against it** (in PromQL, the `@` modifier). **Two corollaries.** (a) **Cost discipline produces the anchor for free:** instructing agents to take ONE broad dump per resource kind and slice it locally — instead of N narrow calls — collapses the sampling instants by construction, so the cheap approach and the correct approach are the same approach. (b) **Concurrency hygiene on a shared host is part of the same problem.** Claim any per-run output directory with a **bare `mkdir` (atomic, fails if it exists), never `mkdir -p`** — run ids commonly have one-second resolution, and two invocations in the same second silently share a directory, producing a run whose results belong to a different dispatch than its own roster and manifest describe **while every individual integrity check still passes, because only the PAIRING is wrong.** Retry with a random suffix on collision. Likewise give every concurrent agent a **private scratch dir (`mktemp -d`, `chmod 700`, deleted before it emits)** — a shared or predictable path lets one target's dump leak into another agent's analysis. (c) **Set an explicit redaction boundary in the prompt, because agent output is published output:** permit existence and metadata only, never values; require anything credential-shaped to be emitted as a fingerprint or a count (`3 keys: tls.crt, tls.key, ca.crt`); cap free-text evidence to a short single line. Redaction that depends on the agent noticing something is sensitive is not a control.

51. **A RULE THAT A MACHINE WILL PARSE OUT OF PROSE NEEDS A DECLARED GRAMMAR — and the failure mode is that the author writes the rule correctly and it silently does not bind.** Two instances from one system. **(a) THE HEURISTIC THAT INVENTED ITS OWN RULE.** An order-stability check implemented as "serialise both sides with keys sorted and compare the strings" does not test what it appears to test: it silently **demands that every array be ordered by its alphabetically-first key.** On the first real run it fired **23 times across three targets and was a false positive all 23.** The proof case is exact: a payload was specified as sorted by `svc` *precisely because* the natural rate ordering reshuffles every run — but `rps` sorts before `svc`, so the heuristic demanded the very ordering the specification forbids. **Compare against the artifact's OWN DECLARED sort key, never against a general-purpose canonicalisation** — a canonicaliser is a rule you did not write and cannot see. **(b) THE CLAUSE SEPARATOR NOBODY DOCUMENTS.** Where the declared key is itself parsed out of a prose sentence, the separator is load-bearing: a parser splitting on `;` sees a comma-joined list as **one clause, binds the FIRST subject, and silently drops every subsequent one** — three separate authors hit this in a single sitting, each having correctly identified the missing key and then written it in a form that did not bind. Equally, a subject-less "Sorted by `x`." reads as a rule for **every** collection in the document, not the one the author meant. **THE GENERAL RULE: if a human writes it and a machine reads it, (1) specify the exact accepted form with an example, (2) make an unparseable or unbound declaration a LOUD error rather than a no-op, and (3) test the parser against a correctly-worded-but-differently-punctuated variant.** A rule that quietly binds to nothing is worse than a missing rule, because the author has already ticked it off.

52. **"EMPTY READS AS HEALTHY" HAS TWO SHAPES THAT SURVIVE AN ARMING PROOF, AND BOTH SHIPPED.** #23 fix the case where a query returns nothing; these two return something, or return nothing for a reason the arming proof does not cover. **(a) THE LAZY NUMERATOR.** A ratio whose numerator is an **error-only series that has never armed** evaluates to EMPTY — and empty is read as a clean pass, not as an error. The arming proof on the *check* can be satisfied while the *ratio inside it* is structurally unevaluable. **Discriminator: a ratio with two always-present sides (usage / limit) is fine; a ratio whose numerator only exists after a fault is the defect.** Lint for it: an error-shaped metric name in a numerator position is a mechanical signature. **(b) INDEXED_BUT_EMPTY — the name is real, the data is not.** A metric can be present in the metric-name index and yield **zero series**, because something upstream in the collection path drops it while the name persists — canonically, a metrics exporter's own allowlist. This is strictly worse than a name that does not exist: a name lookup succeeds, so the check looks verified, and an expression of the form `count(<metric> == 0 and on(…) …)` reports the reassuring answer ("no bad instances") across **every** target at once. **This survived a static linter, human review AND a metric-existence verifier**, all of which consulted the name index. **RANK `INDEXED_BUT_EMPTY` ABOVE PLAIN `ABSENT` in any metric-inventory triage** — plain absence is at least honest. **The verification that actually works: establish a non-zero SERIES COUNT over a window, on every target the check applies to** (`references/learnings-istio.md`), **and verify LABEL names the same way, not just metric names** — a filter on a label that does not exist is the loud-wrong sibling of this class (`references/learnings-observability.md`). **And when a metric is absent everywhere, you cannot tell "never fired" from "name is wrong" using telemetry alone — go read the vendor source at the version you run and cite it**, which is also why a broad regex may never stand in for a named exemption: one pattern can excuse an unbounded family from having to exist.

53. **A SETTLING / MATURITY GUARD MUST AGE THE CONTAINER, NOT THE POD — and `Running` + `Ready` + `restarts == 0` does not mean what it looks like.** A guard that excuses freshly-started workloads from a check needs an age, and the obvious anchor — the pod's creation timestamp — is wrong in both directions. **Forward:** a container that restarted inside a long-lived pod is aged from the pod's creation, so a genuinely fresh process is graded as settled and its startup noise is scored as a fault. **Backward:** a pod satisfying `Running` + `Ready` + `restartCount == 0` can be **thirty seconds old and simply not-there-yet** — none of those three fields is an age, and the combination reads as "healthy and established" when it means "nothing has gone wrong yet." **Anchor on the container's own start time (`.status.containerStatuses[].state.running.startedAt`), which moves on restart.** The trap is that this field is missing for a container that is not currently running, so the fix invites a fallback — and **falling back to the pod's creation timestamp re-imports the exact false FAIL you were fixing.** Treat the missing case as not-yet-gradeable, never as "use the other timestamp". **GENERALISATION: whenever a guard needs "how long has this been true?", find the timestamp attached to the thing that actually restarts, and reject any convenient parent-object timestamp that survives the restart** — the parent's age answers a different question, and answers it confidently. (Adjacent: #8 for why counters living on a rolled component are legitimately absent for 10–20 min after a roll, `references/learnings-observability.md` for node-churn settle windows.)

54. **Write ONE VERSION-AGNOSTIC proof script and run it at the base commit AND on each branch — and make it EMIT the capability flag it branched on.** For a behaviour change that must be byte-identical in some environments: use `inspect.signature(fn).parameters` to pass the new kwarg only when it exists, and **emit that boolean into the dump** (e.g. `builder_accepts_environment: true`). It is free, and it is **built-in evidence that the new code path was actually exercised — which is exactly what an "IDENTICAL" result otherwise cannot show.** Pin every nondeterministic input (revision ids, image tags, timestamps) or the whole diff is noise, and **diff only the payload sub-key, not the whole dump**, so the marker flag does not read as a manifest change. **Pair with an INVERSION control (flip the guard predicate) and confirm the PROTECTED cases move** — an inversion is stronger than a sentinel, because it proves the guard runs on the protected path rather than merely that some code ran. A shape-specific companion: if a symbol changes kind across the branches (a `@property` on one side, a method on the other), branch on `isinstance(type(obj).__dict__['<name>'], property)` rather than on the commit.

55. **Do NOT hand-roll a project's import-time environment variables for a proof harness — put the repo's OWN test-config module on `sys.path` and import it first.** Modules that fail fast at IMPORT on three or four required settings will kill a harness four imports deep, one variable at a time, and a hand-written list **drifts away from the repo silently**. The repo's `conftest`-adjacent patch module exists precisely to set them and is the repo's own source of truth, so it cannot drift. Then **drive the PUBLIC entry point with the settings singleton patched** — never the private builder — and dump with the serializer the object actually supports (**a `dataclass` has `dataclasses.asdict` and NOT `model_dump_json`**; getting this wrong reads as a missing dependency). **Scrub the nondeterministic fields AND the env var that seeds them, or every run diffs against itself.** And always pair the render with a **negative control that flips a known-load-bearing constant** and confirm the expected cases move — if they do not, the harness is not reading what you think it is.

56. **When a private package index blocks the real environment, three escalating fallbacks give real executable proof — and they differ in what they can prove.** In order of fidelity: **(a) FULL SUITE via a public-index re-resolve** — drop the lockfile pin so the resolver can use the public mirror, stub the one genuinely private package (a 10-line package exposing its single import surface is usually enough — check with a grep for its import), and restore the lockfile and manifest before committing. **(b) SINGLE-MODULE LOAD BY PATH** — `importlib.util.spec_from_file_location` with a stubbed `sys.modules` entry for its app-config import, using only the one or two light dependencies its own import chain needs from public PyPI. This bypasses a heavy package `__init__` chain entirely and gave a real base-vs-head proof across a 4×7 matrix plus a negative control. **(c) AST EXTRACTION** of the real definitions (`learnings-code-review.md`) when even the module cannot load. **Two traps: `uv sync … | tail` MASKS FAILURE — the pipeline's exit code is `tail`'s, so check the output TEXT for "Failed to download", not `$?`. And a stub's `__getattr__` must return a dynamically created CLASS, not a `SimpleNamespace`**, because pydantic uses these as type annotations and an instance raises *"unhashable type"*.

57. **To render the BEFORE side of a proof without a second worktree, extract the pre-change tree from the VCS object store into a temp dir and put it FIRST on the interpreter's path.** `<vcs> archive <pre-change-sha> <subtree> | tar -x -C /tmp/before`, then run the identical harness with `PYTHONPATH=/tmp/before/<pkg-root>`. **`PYTHONPATH` outranks an editable install — confirm it by printing the imported module's `__file__`**, which is the one line that turns "I set the variable" into "the old code is what ran". This avoids the branch-checkout dance entirely and makes the before/after runs differ in exactly one variable.

58. **A local run's pass/fail COUNTS are meaningless as evidence when the environment is missing services — compare the sorted set of FAILING TEST IDS against a baseline captured with the identical command.** A suite run without its datastore reported thousands of errors, every one an environmental connection failure, and the handful of "failures" were equally environmental. **Capture a base-revision baseline with the SAME command and diff the extracted test IDs, not the raw logs** (parallel-runner log lines interleave differently between runs, so a raw diff is pure noise). **And know what the baseline CANNOT see: if the missing service is the one the change's tests depend on, the regression is invisible locally and the matching baseline set gives FALSE CONFIDENCE.** When a change alters ambient behaviour under the default configuration, grep the affected tests for the assertion strings by hand rather than relying on the local run.

59. **A gate that reads POLICY out of SOURCE TEXT with a regex FAILS OPEN on the idiomatic singleton — and it fails exactly when the policy is first narrowed.** A CI gate extracted an accepted-version prefix tuple with `re.search(r'not _SDK_VERSION\.startswith\(\(([^)]+)\)\)')` and split the captured group on `,`. For the current two-element form it yields `('0.3.','0.4.')` and works. For `startswith(("0.5.",))` — **the normal way to write a one-element tuple** — it yields `('0.5.','')`, and **every string `startswith('')`**, so the gate accepts **every** version. The trailing-comma form is precisely what someone writes when narrowing the guard to a single supported line, i.e. **the gate fails open the first time it matters**. `re.search` also silently takes the FIRST match, so a commented-out or obsolete guard earlier in the file validates against the wrong policy. **FIX: drop empty prefixes after parsing; use `re.findall` and require exactly one match (more than one fails CLOSED); reject an empty parsed tuple.** **GENERAL RULE: when a gate reads policy out of source text rather than EXECUTING it, enumerate the syntactic forms that policy can legally take and test the gate against each — a gate that only handles today's formatting is a gate that expires silently.**

60. **A gate that imports the LIBRARY misses a module-level guard living in APPLICATION code — and that is vacuous for exactly the failure the change makes newly possible.** Worked instance: widening a dependency specifier from `==0.4.3` to `>=0.4.3,<0.6` was correct at the **packaging** layer, but the application's own module raised at **import** time on anything outside `0.3.x`/`0.4.x`. The range admitted a version the application refuses; the gate stayed green because its final check imported the two *libraries*, never the module carrying the guard. **When a gate verifies installed versions, make it import the code that actually CONSTRAINS those versions.** **Corollary worth stating in the PR: widening a declared RANGE and widening a runtime COMPATIBILITY GUARD are different claims** — the first is packaging, the second asserts tested compatibility and belongs with the real upgrade, not with plumbing that ships every environment unchanged. (Parsing the guard out of source is the fallback when the application's transitive dependencies are too heavy for a gate venv — and #59 is what that fallback costs.)

61. **Proving a FALLBACK arm (`A // B`, `coalesce`, `lookup(x, default)`, a values.yaml override chain) does not leak the wrong side: assert on a CO-CHANGED SIBLING FIELD, not on the new field.** Asserting the new field is empty is weak evidence — it is empty in **both** worlds when the key simply does not exist anywhere. Instead pick a **sibling** field that the same changeset moved in **only one arm** and read it back: if the builder emits the value that exists only in the arm you claim was taken, the arm was taken — independently of the new key. **Pair it with the inverse control** (inject the key into the arm you claim is NOT read, confirm it surfaces) so neither direction is vacuous. And record the **latent** half honestly: a fallback that is safe today only because every current entry has an explicit value is an **unguarded invariant** — name it, say no CI check enforces it, and describe the future entry that would silently inherit the wrong side.

62. **`actionlint`'s `[workflow-call]` rule is the decisive OFFLINE proof for reusable-workflow input wiring — and it is silently VACUOUS outside a git repository.** actionlint locates the project root by walking up for `.git`; without one it **skips local reusable-workflow resolution entirely and reports nothing**. Reproduced on **1.7.7 darwin/arm64**: stripping a required `with:` input in a NON-git scratch copy of the workflows tree produced **no finding** (an invented bogus input was also not flagged), while the identical mutation **inside the real worktree** produced `input "environment" is required by "./.github/workflows/<x>.yaml" reusable workflow [workflow-call]`. **So any actionlint gate run against a copied or exported workflows tree is vacuous for this rule — a green result means nothing.** **Recipe that works: `git worktree add <scratch> origin/<base>`, add a `with: <input>:` line WITHOUT declaring the input, run actionlint, confirm it names the undefined input and lists the defined ones. Silence at HEAD then really means the declaration landed on the `workflow_call` block.** Two further gotchas: compare finding **COUNT and normalised text** head-vs-merge-base, because inserting lines shifts the inner `line:col` numbers of other rules and a raw diff looks like new findings when it is the same set; and in zsh an unquoted `$FILES` variable does **not** word-split, so pass paths literally or actionlint reports *"could not read"* one giant filename.

63. **When every environment holds the SAME value, a per-environment plumbing render proves nothing — make the values DISCRIMINATING first.** A plain dry render cannot distinguish "dev read dev's key" from "dev read prod's key" if both keys hold the same string. **Method: in a throwaway worktree set distinct per-environment sentinel values (`gDEV`/`gSTG`/`gPRD`), render each environment's real path with fake binaries first on PATH, and confirm each environment's OWN sentinel reaches the final command line. Then delete ONE environment's key as the negative control** and confirm only that environment's variable goes empty and its guard fires. Same principle as #61 one layer down: the evidence has to be able to come out wrong.

64. **ALWAYS assert the clean baseline suite is GREEN before the first mutation, inside the same driver — otherwise a mutation run can report 100 % CAUGHT while proving nothing.** Worked failure: a crashed shell driver left the module under test **already mutated**; the next driver copied that mutated file as its "original", so every mutation ran against a baseline that was already failing 21 tests, and the run reported **15/15 CAUGHT — fully vacuous**. `filecmp`-gating each mutation does **not** catch this (the files differ exactly as expected); only a green-baseline assertion does. Restore the original with the VCS (`git checkout -- <file>` in the worktree), never from a copy the driver made, because the copy may be the corrupted one.

65. **A guard test over a YAML/JSON manifest needs VALUE and IDENTITY assertions — "key in dict" over a dict keyed by a name field has four distinct ways to pass while the real gate fails.** All four shipped in one guard suite: **(a)** a null value (`cpu:`) passes `key in dict` while the workflow's `-z` test rejects it; **(b)** the obvious fix is still wrong because `str(None).strip()` is `'None'` and truthy — use `str(v or "").strip()`; **(c)** keying the test's view by `base_name` **discards a duplicate row** that the real `jq` matrix still deploys, so an unsized duplicate agent is invisible to the guard; **(d)** `gpu: "false"` is a truthy Python string — compare `is not True`. **Compare the RAW list rows and the EXECUTED workflow output, not only the keyed guard view.** Measured: 18 spec-derived, comparison-gated mutations, 16 caught after the fixes — and a deliberate duplicate-row mutation passed 24 resource tests before (c) was fixed.

66. **Reviewing a pure-code resolver change has a direct analogue of a rendered-manifest proof: transcribe the PRE-change logic verbatim into an `old_resolve()` and diff old-vs-new over the FULL parameter cross-product.** Worked instance: stage × profile-shape × explicit-override × backend × gpu = **500 cells**, diffed old vs new, plus a **negative control that neuters the new predicate and asserts CHANGED goes to 0**. This catches *"the change is inert"* and *"the change is wider than claimed"* in one artifact and is far stronger than reading the diff. Transcribe from the **merge-base worktree**, not from memory. Extracting the caller's own parameter set matters too: pull each workflow's `jq` program out of the committed YAML and execute the real resolution block from source, so the matrix is the one that actually ships.

67. **A value rendered into TWO places from one source is a two-sided contract, and a unit test of the PRODUCER proves nothing about either consumer.** Worked instance: one computed limit flowed to both a container `resources.limits` field and an environment variable; the test asserted only one dimension, so **reverting either wiring point passed 197/197**. Assert **both** at the rendered-manifest level, parametrised over every environment. The generalisable smell: grep for every reader of the producing function before trusting its test.

68. **Mutation survivors that change only BYTE REPRESENTATION are not test gaps — do not add an assertion unless the representation is contractual.** Worked instance: a guard's `>` → `>=` mutant survived 242/242, and the only observable difference was that an exactly-equal input rendered `26Gi` at head and `26624Mi` under the mutant. Record it as a **deliberate non-finding with the reason**, and add the exact-equality assertion only if some downstream parser depends on the literal form. Conversely, treat every mutation that **changes a threshold, a comparison direction, or the order of parsing vs selection** as a required kill — those are the ones that shipped elsewhere in the same review.

69. **A test for a per-source EXCLUSION predicate must seed a parent that is otherwise ELIGIBLE and vary exactly ONE activity source — reusing a shared fixture makes the test vacuous without failing.** Worked instance: a stale-record query had an outer age-eligibility predicate plus several per-activity `NOT EXISTS` predicates. Using the suite's shared, freshly-created fixture meant the **outer age predicate rejected the row before the exclusion under test ever mattered** — the test passed and tested nothing. Seed old-and-otherwise-eligible, then add exactly one recent activity per test.

70. **Fail-CLOSED consumed fields and schema COUPLING are different problems, and a fix that narrows the schema does not fix the first one — grade them separately.** Worked instance: a capacity accounting routine validated **every** object in a namespace before joining them. Moving to field-only projections correctly isolated unrelated schema churn (container/probe/status/updateStrategy fields stopped mattering), but **both** the base and the projected version still failed the whole namespace on one malformed *consumed* field — an orphaned object missing a required name/selector. When grading such a fix, state which of the two it addresses. And never "fix" it by silently skipping a referenced object: that under-counts the allocation the routine exists to compute, which is worse than a loud failure.

71. **Pytest teardown runs LIFO, so `monkeypatch.setattr` set up BEFORE a fixture's `patch()` is restored AFTER it — and the fixture's mock is left permanently installed on the class.** Worked instance: one test monkeypatched a model method on top of a fixture's `patch(...)` of the same attribute; the monkeypatch restore put the fixture's `AsyncMock` back onto the real class, and **later tests on the same parallel worker** received the canned reply. It only surfaces when the scheduler co-locates them, so **adding an unrelated test file can make it appear or vanish** — reproduce with the two tests pinned to one worker (`pytest -n 1 <offender> <victim>`). Fix: use a `patch.object` **context manager inside the test**. Rule: **never stack `monkeypatch.setattr` over a fixture's `patch()` of the same attribute.**

72. **Set a comparison bound from the SPREAD of the baseline, not from a single baseline run — and if the metric swings 2× day-over-day, a 1.5× bound is a guaranteed false FAIL.** Worked instance: a validation playbook bounded post-upgrade pod setup time at **1.5 × the C0 baseline**, while the same metric read 96.6 s and 176.9 s on consecutive days with a 5-minute-window range of 35 s-4500 s. Take at least two baselines separated by a day, bound on the **observed range**, and prefer a **signature/shape comparison** over a scalar ratio for any metric with a long tail. Related: a C0 baseline captured **after** a regression already started **hides that regression** from every later comparison — in one case the pre/post compare was clean because the baseline already contained the fault. Always sanity-check the baseline against a longer historical window before adopting it.

73. **A read-only snapshot collector has four failure modes that all present as a CLEAN result — design against each explicitly.** From one collector's post-mortem: **(1) Blank-variable false zeros** when a date/time helper fails under `set -uo pipefail` (mechanism: `learnings-agent-workflow.md`). **(2) Non-atomic sequential reads** of related resources produce **cross-resource mismatches that are artefacts of collection order**, not real inconsistency — re-read the pair before reporting a mismatch, or capture a single list call per reconciliation. **(3) Summaries that drop OBJECT IDENTITY** (grouping errors by message, summarising a router's requests without the subject id) make a count un-auditable and prevent per-object bounding — keep the identity column. **(4) A filter plus stderr suppression** can both false-zero a known error class and **hide an entirely new one**; assert on the total line count as well as on the filtered classes. Also save the raw event JSON: it is cheap and it is the thing you wish you had when a number is challenged.

74. **A ZERO-ERROR COUNT over a soak window proves nothing if the window carried no traffic — count the EVENTS the feature produces, per revision, before quoting the error count.** Worked instance: a staging soak reported 24 h with zero errors on the path under test, while that environment had handled **zero jobs of that kind in the preceding 24 h**. What made the evidence real: group the *success* events by the **deployed revision/build identifier** and show that the revision built after the fix actually did the work — e.g. 15 "ready for trajectory" events and 0 errors on the revision built 9 minutes after the hotfix. The one-line shape is a log query that emits the revision label and `uniq -c`s it. Generalise: for any "N hours clean" claim, state the **denominator** in the same sentence, or the claim is unfalsifiable.

75. **A numeric validation that bounds a RATIO or a DERIVED size must reject the values that derive ZERO — "0 means unlimited/disabled" is the most common silent hole.** Worked instance found by an adversarial lens: a new input validation accepted small values (e.g. `0Gi`, `7Mi`) that computed through to a **0 MiB cap**, which the consuming system interprets as **the limit being disabled** — the exact outcome the validation was added to prevent. When reviewing or writing such a validation, enumerate the derived value's boundary cases (`0`, the rounding floor, the type's maximum) and assert on the DERIVED number, not on the input. Same review also found the mirror of this: a timeout raised on one component was silently inherited by a second consumer that has **no client-side timeout of its own**, so the change had a blast radius outside the diff.

76. **A negative control can FAIL TO FAIL because the code is defended TWICE — when a mutant survives, first ask whether a second guard absorbed it.** Real case: one function was guarded both by an `if`/`then` (instead of `[ test ] && cmd` as a loop's last command) **and** by a `|| true` on the enclosing pipeline, so reverting only the first left the mutant indistinguishable from clean. The control only became informative after disabling **both**. A surviving mutant is evidence of defense in depth **or** of a vacuous test — and those have opposite remedies, so resolve which before touching anything.

77. **A fixture must be WIDER than the index the selector uses, or the property under test is structurally unprovable.** A fixture with only TWO forwarded-for hops cannot test an extraction that indexes from the END, because position −2 coincides with index 0 — so the mutant "take the spoofable first hop" passes every assertion and the change's **headline anti-spoofing property is untestable**. The same shape silently neutered two more mutants on the same PR ("append the query string" — no fixture had a query string; "widen the range into 5xx" — no 5xx case). **The cheapest fix is fixture width, not more tests.** And run both lenses' mutation batteries: on that PR one lens ran 18 mutations (3 escaped) and the other ran its own 15 (7 escaped), but the **union was 8 distinct escapes** — two independent mutation sets were worth more than either doubled.

78. **A rendered-proof procedure must render the BASE artifact from the merge-base worktree, not the current artifact with a base inputs file.** A review step did the latter, so a template-only change produced byte-identical base and head renders and **vanished from its own proof**. The working form renders the base directory out of the merge-base tree (and resolves dependencies in **both** trees, or the base renders empty). **An unchanged-input comparison is NOT a negative control**: a control must MUTATE one input of the kind the change touches and require the sentinel to appear in the diff. Empirically, on a template-only fixture the old form exited 0 (clean) while the corrected form caught it, and the old "control" **passed on a deliberately broken render path** where the mutation control correctly failed.

79. **A search or report script needs BOTH a positive query and a NO-MATCH negative control, because only the empty case proves the script still completes.** The no-match run is what shows every section still prints `(no matches)` rather than the script aborting mid-way — something a positive query can never show. Related: when the twin of a script runs only `set -o pipefail` and the original runs `set -euo pipefail`, a guard that looks unnecessary in the twin is still load-bearing. **Keep it, and prove it with a patched strict copy** (`sed 's/^set -o pipefail$/set -euo pipefail/'` into a scratchpad, `chmod +x`, run) rather than by reading.

80. **Testing an import-time guard at its REAL consumer: popping both modules from `sys.modules` is NOT enough, so the test passes vacuously.** `importlib`'s `_handle_fromlist` **skips re-importing a submodule that is already an ATTRIBUTE of the parent package**, so a consumer doing `from pkg import submodule` never re-executes the guard. Working pytest form: `monkeypatch.delitem(sys.modules, consumer)`; `monkeypatch.delitem(sys.modules, guard_mod)`; `monkeypatch.delattr(<parent pkg>, '<submodule>')`; patch whatever the guard reads; then `importlib.import_module(consumer)` under `pytest.raises`. `monkeypatch` restores all of it and is safe under xdist — **prefer it over `patch.dict(sys.modules)`, which `clear()`s `sys.modules` on exit.** Verified non-vacuous against two separate mutations (deleting the side-effect import, and removing the module-level check), each giving exactly 1 failed / 368 passed.

81. **A CI YAML step is testable offline — extract the block scalar, resolve substitutions with the file's own defaults, replace `$$` → `$` (in that order), `bash -n` it, then run it with stubbed binaries on `PATH` driven by env knobs for fault injection.** Used to exercise 8 scenarios on one real build step including a build-fails negative control. **The trap that produced three FALSE GREENS:** a `docker run` stub that picked the image with `"${@: -3:1}"` grabbed the interpreter name, not the image, because the real call appends `python3 <script> <arg>` after the image — so the stub never failed and three failure scenarios all passed. **Index the image positionally, and always include a control that MUST go red.**

82. **To verify a behaviour-preserving refactor, a golden snapshot of live output is weak — give the component a `parse <file>` mode and drive it from synthetic fixtures.** Live API data moves, so before/after is never exact. Fixture-driven output is byte-deterministic, so the comparison is **exact equality**, and fixtures also reach branches live data never hits. **Negative controls must perturb a rule the FIXTURE actually exercises** — a first attempt did not fire because the fixture's rows were already dropped by an *earlier* rule, so the mutation was unobservable. Document the test environment knobs (config-file and cache-dir overrides) alongside the fixtures, or the harness is unreproducible.
