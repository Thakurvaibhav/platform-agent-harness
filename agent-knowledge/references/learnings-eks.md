# EKS / Managed Node Group Learnings

See also: `learnings-gke.md` (the GKE sibling: node pools, allocatable, upgrade semantics), `learnings-gvisor.md` (self-installed runsc on these nodes), `learnings-terraform.md` (the modules and `terraform test` harnesses that build them), `learnings-network-policy.md` (VPC-CNI / branch ENI behaviour), `learnings-workload-debug.md` (what an evicted or rebalanced node does to a workload), `learnings-k8s-sa.md` (IRSA).

AWS-managed Kubernetes node-platform behaviour: managed node groups, their EKS-owned ASGs, and the AL2023/`nodeadm` bootstrap. Vendor claims here are pinned to the AWS doc or source noted in the entry.

1. **An EKS managed node group's ASG terminations evict pods but IGNORE PodDisruptionBudgets and hard-terminate after 15 minutes, so "EKS drains the node" is not literally true.** Per AWS `managed-node-groups.html`: AZRebalance and desired-count terminations evict without honouring PDBs. Plan capacity changes as if the pods get 15 minutes and no budget protection, not as if a drain is in progress.

2. **EKS syncs only the ASG's SCALING CONFIG back to the node group: there is NO documented reconcile of ASG *suspended processes*, so a manual `suspend-processes` survives.** It persists until the ASG is replaced, and whether a node-group update resumes it is **UNVERIFIED** (see #3 for one negative observation). Treat a suspension as durable-but-unguaranteed: re-assert it rather than assuming it held.

3. **A managed node group `update-nodegroup-version` (AMI release bump) did NOT resume a user-suspended `AZRebalance` on the EKS-owned ASG**: no `ResumeProcesses` in CloudTrail and the suspension reason was unchanged (observed 2026-10-27 on a node group at **0 nodes**). ⚠️ **Untested with live nodes**, which is exactly where the interesting path is: AWS docs say MNG version/launch-template updates use AZRebalance to land upgraded nodes in the same AZ (`managed-node-update-behavior`), and resuming AZRebalance on an unbalanced ASG triggers an *immediate* rebalance. So suspending it can interact with a node-group roll: verify a roll on a non-prod cluster before relying on the suspension.

4. **EKS allocatable is DETERMINISTIC per instance type + AMI type, which makes a "dev allocatable == the customer's allocatable" provenance claim verifiable IN-REPO rather than needing access to the other cluster.** The check: instance types hardcoded in the node-group module (not tfvars), `ami_type` unset in both (same EKS default), no prefix-delegation or `max_pods` override (so the default ENI-based `max_pods` is deterministic per type), and the module published to the shared registry rather than forked. If all four hold, the two environments **cannot** diverge via configuration, which is a much stronger argument than comparing two measurements. ⚠️ It does **not** validate that the measurement itself was right; see `learnings-terraform.md` on why a plan-time fit precondition over a hardcoded allocatable is only a guard against future hand-edits.

5. **AL2023 `nodeadm` + containerd 2.x writes `/etc/containerd/config.toml` at `version = 3` with SINGLE-quoted plugin keys (`[plugins.'io.containerd.cri.v1.runtime'…]`) and `config_path = "/etc/containerd/certs.d:/etc/docker/certs.d"`.** Any DaemonSet that patches containerd by matching the OLD v2 schema will mis-detect: a registry-mirror DS grepping for `certs.d"` matched and wrote a **v2-schema** `io.containerd.grpc.v1.cri.registry` block onto every node at boot, then restarted containerd (reload is unsupported), so two installers ended up fighting over one config file. ✅ Parse the file with `tomllib` in a fixture, don't pattern-match the schema you remember.

6. **A `terraform_data` whose `triggers_replace` includes a node group's launch-template VERSION shows N add plus N destroy on ANY launch-template bump, and that is expected rather than destructive.** Pattern: a resource that re-runs `aws autoscaling suspend-processes AZRebalance` after each node-group update. Because `triggers_replace` includes `launch_template[0].version`, any tag, AMI or user-data change bumps the version and shows every pool's helper being replaced. Read such a plan by checking WHAT is being replaced: a helper that re-asserts a suspended process is not a node replacement. Pools with one ASG per AZ are typically excluded from the helper and so do not appear.

7. **A self-hosted runner agent version that the platform has deprecated takes the whole pool offline at once, and self-update cannot save a `--jitconfig` pool.** Symptom: the agent gets HTTP 403 on the broker's message endpoint and exits with 'Runner version vX is deprecated and cannot receive messages'. Registering with `--jitconfig` sets `disableUpdate=true` in the broker URL, so the PINNED version in the launch template is the ONLY lever. **The fix cannot ship through the pool's own CI** when the Terraform workflow pins `runs-on` to that runner label: the PR's own required plan check queues forever and merging changes nothing. Delivery is a human apply from a workstation, or a temporary switch of that job to a hosted runner. Once the launch template is updated the pool self-heals in minutes, because user-data downloads the agent tarball at boot. **Diagnose before waiting:** `gh api repos/<o>/<r>/actions/runners --paginate` distinguishes 'slow' from 'will never run' in one call, and `gh run view <id>` showing `status=queued` with no job started is the tell. A large count of stale OFFLINE registrations is itself a symptom, because teardown does not deregister.

8. **An ALB stuck in `provisioning` with `State.Reason` null and zero ENIs is usually NOT your configuration: check the cloud provider's own health events FIRST.** `aws health describe-events --region us-east-1 --filter regions=<r>,eventStatusCodes=open` costs one call. During a regional launch-failure event that listed ELB as impacted, two consecutive ALB recreates both hung and self-hosted EC2 runners could not launch either, so CI queued indefinitely; the health check would have avoided a needless ALB delete plus controller restart.

9. **ECR cross-account pull needs BOTH sides, and the IAM half is the one that is missed.** The repository policy on the SOURCE account grants `arn:aws:iam::<dest>:root`, but the token minted by `ecr:GetAuthorizationToken` carries the CALLER's IAM identity, so that caller ALSO needs `ecr:BatchGetImage` and `ecr:GetDownloadUrlForLayer` in its OWN identity policy, or every pull 403s against a repository policy that looks correct. **A role holding `GetAuthorizationToken` alone can AUTHENTICATE (docker or helm login succeeds) and then fail every pull, which reads as a credentials problem and is not one.** `ecr:GetAuthorizationToken` is REGISTRY-level: it cannot appear in a repository policy at all and must be granted in the caller's account IAM on `"*"`. For a Helm OCI chart specifically, the two repository-policy actions are the same `BatchGetImage` plus `GetDownloadUrlForLayer` that AWS's own AllowPull example uses: ECR stores a chart as an ordinary OCI artifact (`artifactMediaType application/vnd.cncf.helm.config.v1+json`) and a chart pull is a manifest GET plus a blob GET, so NO chart-specific action exists or is needed. **Caveat: an unpinned semver chart RANGE would additionally need `ecr:ListImages`; pinned versions need no listing.** A pull-through cache adds two more on the FIRST (uncached) pull: `ecr:CreateRepository` and `ecr:BatchImportUpstreamImage`, both scopable to `repository/<prefix>/*` even though the repository does not exist yet, so no widening to `"*"` is needed. `ecr:GetImageCopyStatus` is source-side only.

10. **`aws_ecr_repository_creation_template` applies ONLY at repository creation and never updates an existing repository's policies.** Proven live: a template listing eight destination accounts against repositories created when it listed five leaves the older repositories granting five. The fix for real drift is a REGISTRY-level policy, not a creation template. Related trap in the same family: a replica-region registry policy built from an explicit repository list must enumerate EVERY creation-template prefix, not just the primary list, or a newly added prefix is covered in the home region only and a consumer whose cache region is a replica region is denied on import.

11. **Self-hosted runner starvation presents as a QUEUED required check, not a failed one, so a PR can look "still running" for hours with nothing wrong in the diff.** `gh run view <id>` showing `status=queued` with no job started is the tell, and `gh api repos/<o>/<r>/actions/runners` gives the online count in one call. This compounds with a workflow that pins `runs-on` to a caller-supplied label: a second caller consuming the one online runner blocks the first indefinitely, and the PR gets NO validation of whatever that job was meant to check. Extends `#7`, which covers the deprecation that empties such a pool in the first place: there the fix cannot ship through the pool's own CI, here the symptom is the same queue with a healthier cause. A large count of stale OFFLINE registrations alongside one online runner is normal and not itself the fault.

12. **An internal NLB with IP targets under AWS Load Balancer Controller v2.7.2: the documented 'VPC CIDR default' does NOT apply, `externalTrafficPolicy` is INERT, and client-IP preservation is safe only because of the security-group gate.** (1) **Source ranges:** the `NLBSecurityGroup` feature gate defaults TRUE (`pkg/config/feature_gates.go:61`), so the managed FRONTEND security group takes `loadBalancerSourceRanges` and defaults to `0.0.0.0/0` WHEN EMPTY (`pkg/service/model_build_managed_sg.go:115-117`). The documentation line about a VPC-CIDR default for the internal scheme describes the LEGACY no-security-group path. So an internal NLB is open to the whole VPC and to anything routed into it unless you set source ranges explicitly. (2) **`externalTrafficPolicy` does nothing here:** the `Local` health-check branch is gated on `TargetTypeInstance` (`pkg/service/model_build_target_group.go:92-98`), and an IP-target NLB addresses pod IPs directly. (3) **`preserve_client_ip.enabled=true` is compatible** at this version precisely BECAUSE a new NLB gets security groups under that gate, so the `TargetGroupBinding` rule references the BACKEND security group (`model_build_target_group.go:423-427,499-512`) and AWS documents security-group-referencing target rules as continuing to work with client IP preservation. **Remaining caveat: hairpin fails if a target pod calls its own NLB.** (4) Chart 1.7.2 sets `enableServiceMutatorWebhook=true`, so NEW LoadBalancer Services get a `loadBalancerClass` injected, which matters for any Service you did not intend it to manage.

13. **An IP-target NLB on EKS needs TWO things beyond replicas and a PodDisruptionBudget, and without them a 'highly available' deployment is neither.** (1) **Label the pod NAMESPACE with the controller's pod-readiness-gate injection label.** Without it, a rollout can kill OLD pods while the NEW targets are still in `initial` state, which is a gap with healthy-looking Kubernetes objects throughout. (2) **Set the cross-zone load-balancing attribute explicitly:** NLB cross-zone is OFF by default, so 2 replicas spread across 3 availability-zone subnets leaves a zone with NO target, and traffic arriving at that zone's node is blackholed. ✅ Expose the namespace-label knob in the chart (an empty default is fine) and put both in the per-cloud values file, because neither is visible in a Kubernetes-only review.

14. **Two EKS behaviours that look like they should break a hardened pod and do not, each worth checking before writing a defensive workaround.** (1) **Kubelet `httpGet` probes pass through a narrow ingress NetworkPolicy** even with the AWS network-policy agent enforcing: verified live with a policy allowing ingress only from one pod selector on the probe port, whose readiness probe is Ready with 0 restarts. So a pod-only ingress policy does NOT break its own probes, and adding a node-CIDR carve-out for probes is unnecessary complexity. (2) **IRSA injection does NOT require `automountServiceAccountToken`:** the pod-identity webhook injects the projected token volume plus the role-ARN, token-file, region and regional-endpoint environment variables even when BOTH the ServiceAccount and the pod set `automountServiceAccountToken: false`. The webhook has `failurePolicy: Ignore` and an object selector that skips a specific opt-out label. So a chart that disables automount for the Kubernetes API still gets working AWS credentials.

15. **An `access_config` block WITHOUT `bootstrap_cluster_creator_admin_permissions` sends FALSE to CreateCluster, the documentation says otherwise, and the flag is ForceNew, so the mistake costs a cluster replacement.** terraform-provider-aws 6.73.0 `aws_eks_cluster`: the nested block's zero value is read as false (`cluster.go:1440`) with no schema default, while the documentation states the default is true. In `API` or `API_AND_CONFIG_MAP` authentication mode the creator then gets NO admin access entry, which is discovered the first time someone tries to use the cluster. ⚠️ Fixing it after apply REPLACES the cluster, and ADDING the block to an existing cluster (whose state flattened the value to true, `cluster.go:2333`) without the flag ALSO forces a replace. ✅ **Always set `bootstrap_cluster_creator_admin_permissions = true` explicitly**, including on clusters where you believe the default covers you.
