# Learnings: Crossplane (v2 install + Compositions + provider identity)

Vendor-neutral patterns for installing Crossplane v2.x (core + Upbound cloud providers + ProviderConfig) as a wrapper chart wired through ArgoCD, and for authoring Compositions/XRDs that mint cloud IAM. Cloud identity examples use AWS IRSA and GCP Workload Identity; the mechanics generalize.

See also: `learnings-argocd.md` (sync-waves, ignoreDifferences), `learnings-helm-ci.md` (Helm deep-merge, yamlfmt), `learnings-k8s-sa.md` (IRSA / Workload Identity), `learnings-operators.md` (CRD registration timing), `learnings-terraform.md`.

## API versions & install ordering

1. **In Crossplane 2.x, `Composition` is served ONLY at `apiextensions.crossplane.io/v1` — only the XRD graduated to v2.** A `CompositeResourceDefinition` (XRD) can be `apiextensions.crossplane.io/v2`, but its `Composition` MUST stay `/v1`, or `crossplane render` / `crank` rejects it (`not a composition: Composition/<name>`). Core logs benign startup deprecation warnings for APIs it still serves (v1 XRD, `Usage` → `protection.crossplane.io`) — these are NOT triggered by your applied objects; ignore them on a v2-native chart.

    **Further source details and anonymized verification evidence:**

    **`Composition` is served ONLY at `apiextensions.crossplane.io/v1` in crossplane 2.3.3 — there is NO Composition v2.** Only the `CompositeResourceDefinition` (XRD) graduated to v2. So an XRD is `apiextensions.crossplane.io/v2` but its `Composition` MUST stay `/v1`, or `crossplane render` / `crank` rejects it with `not a composition: Composition/<name>`. Verified against the v2.3.3 cluster CRD `apiextensions.crossplane.io_compositions.yaml` (only v1 served). Core also logs benign startup deprecation warnings ("CompositeResourceDefinition v1 is deprecated…migrate to v2"; "apiextensions.crossplane.io Usage is deprecated → protection.crossplane.io") — these are for APIs core still serves, NOT triggered by applied objects; ignore on a v2-native chart. (Only legacy v1 XRD offender in the k8s repo = `charts/example-builder`, inert/migrate-or-retire.)

2. **Provider / DeploymentRuntimeConfig CRDs are registered at RUNTIME by the core pod — wave your CRs behind core health.** The `pkg.crossplane.io` CRDs (`Provider`, `DeploymentRuntimeConfig`) are not in the core subchart; the core Deployment registers them once Healthy. Under ArgoCD sync-waves: core = wave 0; DRC + Provider = wave 5 (ArgoCD gates the wave on core health); the `ClusterProviderConfig` CRD is registered only AFTER the wave-5 provider pod is Healthy → put `ClusterProviderConfig` at wave 10 with `SkipDryRunOnMissingResource=true` + a bounded retry. `runtimeConfigRef` is a soft reference the package manager reconciles, so non-deterministic intra-wave order between DRC and Provider is self-healing.

    **Further source details and anonymized verification evidence:**

    **Provider/DRC CRDs are registered at RUNTIME by the wave-0 core pod, not shipped by the subchart → wave your CRs behind core health.** The `pkg.crossplane.io` CRDs (`Provider`, `DeploymentRuntimeConfig`) are NOT in the `crossplane-2.3.3` subchart; the wave-0 core Deployment registers them once Healthy. So wave-5 DRC/Provider depend on wave-0 being Healthy (ArgoCD gates waves on health). The `ClusterProviderConfig` CRD (`{aws,gcp}.m.upbound.io`) is registered only AFTER the wave-5 provider pod is Healthy → put `ClusterProviderConfig` at wave-10 with `SkipDryRunOnMissingResource=true` + retry (limit 10, maxDuration 5m). DRC + Provider share wave 5 (non-deterministic intra-wave order) but `runtimeConfigRef` is a soft reference the package manager reconciles → order-independent + bounded retry self-heals.

## Provider controller identity

3. **A DRC `deploymentTemplate` is API-REJECTED for a ServiceAccount-only patch — use `serviceAccountTemplate` (package-owned, unique name) or a self-owned SA.** `spec.deploymentTemplate.spec` requires both `selector` and `spec.template.spec.containers` (k8s API validation), so a `serviceAccountName`-only `deploymentTemplate` always fails — the minimal example in most docs is itself invalid. Two valid shapes: (a) **`serviceAccountTemplate.metadata.{name,annotations}`** — the *package manager* creates and owns the SA; safe ONLY with a UNIQUE per-family name (`provider-<cloud>-<family>`). Reusing one `serviceAccountTemplate` SA name across multiple provider packages = ownership conflict → reconcile loops + apiserver load. (b) **You create and own** the annotated SA and set `deploymentTemplate.spec.template.spec.serviceAccountName` with a valid `selector` + `containers` block — Crossplane uses it without taking ownership. Identity annotations: `eks.amazonaws.com/role-arn` (AWS IRSA) / `iam.gke.io/gcp-service-account` (GCP Workload Identity). Per-family unique SA names avoid the conflict either way.

    **Further source details and anonymized verification evidence:**

    **Identity is wired via `DeploymentRuntimeConfig.spec.serviceAccountTemplate.metadata.{name,annotations}`** — this sets the provider pod's ServiceAccount + the IRSA (`eks.amazonaws.com/role-arn`) or Workload Identity (`iam.gke.io/gcp-service-account`) annotation. `Provider.spec.runtimeConfigRef` points at the DRC. This is how you give the provider pod cloud identity (see `learnings-k8s-sa.md` for the WI/IRSA binding mechanism). `spec.deploymentTemplate.spec` requires `selector` AND `spec.template.spec.containers` (both required by k8s API validation), so a `serviceAccountName`-only `deploymentTemplate` always fails — the minimal example in most docs/articles is itself invalid. Two valid shapes: (a) **`spec.serviceAccountTemplate.metadata.{name,annotations}`** — the *package manager* creates+owns the SA; safe ONLY with a UNIQUE per-family name (`provider-<cloud>-<family>`, e.g. `provider-aws-iam`); configuring the SAME `serviceAccountTemplate` SA name across multiple provider packages = ownership conflict → reconcile loops + apiserver load. (b) **You create+own the SA** (annotated `eks.amazonaws.com/role-arn` / `iam.gke.io/gcp-service-account`) and set `deploymentTemplate.spec.template.spec.serviceAccountName=<that SA>` with a valid selector+containers block — Crossplane USES it without taking ownership. Per-family unique SA names avoid the conflict either way. Identity fallback per family: `family.roleArn | sharedRoleArn` (AWS) / `family.wiServiceAccount | sharedWiServiceAccount` (GCP).

4. **Renaming a provider controller SA requires a matching cloud-trust update — trust the namespace, not the exact SA name, to decouple.** If the cloud trust relationship pins the exact SA name (AWS: `system:serviceaccount:<ns>:<name>`; GCP WI: `…svc.id.goog[<ns>/<name>]`), renaming the SA leaves the provider pod HEALTHY but unable to authenticate to the cloud — and that only surfaces on managed-resource reconcile, not on the provider's Healthy status. Fix: trust ALL KSAs in the provider namespace — AWS `system:serviceaccount:<ns>:*` with a `StringLike` trust condition; GCP WI a namespace-level `principalSet` (`…/namespace/<ns>`). Then per-family SA renames need no per-family trust edit.

    **Further source details and anonymized verification evidence:**

    **Any chart change to the provider controller SA NAME requires a matching Terraform trust update — use wildcard/namespace-level trust to decouple.** Renaming SAs to `provider-<cloud>-<family>` (TICKET-NN) BROKE the controller IRSA/WI trust on both clouds: AWS `irsa.tf` trusted exact `system:serviceaccount:crossplane-system:provider-aws`; GCP WI member was exact `…svc.id.goog[crossplane-system/provider-gcp]`. Providers went HEALTHY (pod running) but could NOT authenticate to cloud (only shows on MR reconcile, not on Healthy status). FIX (infra-terraform): trust ALL `crossplane-system` KSAs — AWS `namespace_service_accounts=["crossplane-system:*"]` + `trust_condition_test=StringLike` (see #39); GCP WI member = namespace-level `principalSet` `…/namespace/crossplane-system`. Supports per-family SAs without a per-family trust edit.
    - **A BLOCKED verification is NOT a confirmation — record it UNVERIFIED and name what would unblock it.** The decoupling claim above was confirmed live on the GCP side only; the AWS equivalent was blocked on an expired SSO session — not a defect, but not evidence either (#80).

## Compositions & cloud IAM

5. **AWS IAM path-based scoping is INCOMPATIBLE with provider-aws observe-before-create — scope by NAME PREFIX at root path `/`.** The provider calls `iam:GetRole(RoleName)` to observe BEFORE `CreateRole`; `GetRole` takes a name only, so for a not-yet-existing role IAM authorizes against the PATHLESS ARN `arn:aws:iam::<acct>:role/<name>` (the deny message shows the resource with no `/<path>/` segment). A controller policy that grants `iam:GetRole` only on `role/<path>/*` never matches the pathless observe → AccessDenied → the provider never creates → deadlock. Fix: mint roles at path `/` with a name prefix (`<prefix>-<name>`); scope the controller policy by name glob (`role/<prefix>-*` + `policy/<prefix>-*`); drop `forProvider.path` from the Composition. A uniform pathless ARN covers both observe and write.

    **Further source details and anonymized verification evidence:**

    **AWS IAM PATH-based scoping is INCOMPATIBLE with provider-aws observe-before-create — scope by NAME PREFIX at root path `/`.** The provider calls `iam:GetRole(RoleName)` to observe BEFORE `CreateRole`. `GetRole` takes a **name only**, so for a not-yet-existing role IAM authorizes against the **pathless** ARN `arn:aws:iam::<account-id>:role/<name>` — the deny message shows the resource with no path segment at all. A controller policy granting `iam:GetRole` only on `role/<app-prefix>/*` therefore never matches the observe call → AccessDenied → the provider never reaches Create → permanent deadlock, and tightening the path scope makes it worse, not better. **Fix:** mint roles at path `/` with a NAME prefix (`<app-prefix>-<cluster>-<svc>`), glob the controller policy on `role/<app-prefix>-<cluster>-*` + `policy/<app-prefix>-<cluster>-*`, and drop `forProvider.path` from the Composition entirely. A uniform pathless ARN then covers observe and write with one glob. This is the canonical concrete form of the observe caveat in #42. **General rule: before scoping a controller's IAM by resource shape, work out which API the controller calls during OBSERVE — observe usually addresses the resource by name, not by the ARN you designed the scope around.** (Example estate: `orgs/<org>/crossplane.md#9`.)
    - **CORRECTION worth carrying on its own: a per-cluster name-prefix deny is NOT the same thing as an account boundary.** Sibling clusters frequently SHARE a cloud account or project; when they do, a deny you attributed to "different accounts" actually came from your own name-prefix glob, and removing the cluster segment from the name silently removes the isolation. On GCP the same trap has a sharper edge: a GSA `account_id` is unique **per project**, so two clusters in one project with identically named services collide outright. **Never state "identities are cluster-scoped" as a blanket safety claim across two clouds — verify per cloud, per account/project, with a negative control.** (See #47, where the fix is an `aws:RequestTag/cluster` ABAC condition once the name no longer carries the cluster; and #15.)

6. **GCP managed-resource delete-ordering leaves a dangling `deleted:serviceAccount:…?uid=` IAM binding.** Deleting a `ServiceAccount` (GSA) managed resource and its `ProjectIAMMember` simultaneously removes the GSA before/concurrent with the binding's `setIamPolicy` removal → the member converts to the `deleted:` form and is not cleaned up. Fix: sequence teardown (delete `ProjectIAMMember` and other IAM bindings BEFORE the `ServiceAccount`) via Composition dependency ordering. Clean a leftover: `gcloud projects remove-iam-policy-binding <proj> --member='deleted:serviceAccount:<email>?uid=<uid>' --role=<role>`. GCP auto-purges deleted-principal bindings after ~60d, but do it explicitly.

    **Further source details and anonymized verification evidence:**

    **GCP managed-resource delete-ordering leaves a dangling `deleted:serviceAccount:…?uid=` project IAM binding — fix it with Crossplane `Usage` guards, and understand what the guard is actually keyed on.** Deleting a `ServiceAccount` (GSA) MR and its `ProjectIAMMember` MR simultaneously removes the GSA before or concurrently with the binding's `setIamPolicy` removal, so the member converts to the `deleted:` tombstone form and is never cleaned. Sequence teardown so bindings delete BEFORE the SA. Cleanup for an existing tombstone: `gcloud projects remove-iam-policy-binding <proj> --member='deleted:serviceAccount:<email>?uid=<uid>' --role=<role>` (needs an identity excepted from any project deny policy on `setIamPolicy`). GCP auto-purges deleted-principal bindings after ~60d, but clean explicitly. (Example estate: `orgs/<org>/crossplane.md#10`.)
    - **The guard:** `protection.crossplane.io/v1beta1` `Usage`, namespaced, ONE per binding MR: `of` = the `ServiceAccount`, `by` = the binding, selected with `resourceSelector{matchControllerRef: true}` plus a unique label, `replayDeletion: true`. **The label alone is NOT the fence — `matchControllerRef` is what scopes the guard to the owning composite** even when several composites carry identical labels.
    - **Two general rules this cost a full round-trip to learn:**
    - (1) **"the cloud resource is cleaned up" NEVER implies "the MR can complete its delete."** Deletion ordering is a property of the **CR reconcile**, not of cloud-side cascade semantics. The AWS analogue was recorded for a year as "unaffected, the inline policy dies with the role" — true at the cloud level, **false at the Kubernetes level**, because the policy CR still needs a successful *observe* to finish its own delete and cannot once the role is gone. So AWS needs a `Usage` guard too. The stale clause had been mirrored into a template header and a chart README, which is exactly why it survived so long — **when you correct a claim, grep for every place it was copied.**
    - (2) **When the `by` side is CONDITIONAL, the `Usage` MUST be emitted inside the same conditional.** A `Usage` gating a `by` that never renders protects `of` **FOREVER** — an undeletable resource with no error message.
    - **COUPLING HAZARD in any per-item fan-out:** if the binding MR and its paired `Usage` guard are both emitted inside the same `range`, any logic that drops an item from the range drops its guard **in the same reconcile** — and Crossplane garbage-collects observed composed resources absent from desired (`composition_functions.go:271`, GC at `:566-571`) **before** server-side-applying the rest, which is precisely the tombstone condition. **Rule: never narrow the fan-out set on a teardown path without preserving the observed `Usage` guards.**

7. **An org/project Deny policy can block a Crossplane controller's project-level IAM even with the right role.** On GCP, even with unconditional `roles/resourcemanager.projectIamAdmin`, a `ProjectIAMMember` grant can `403 Policy update access denied` if a Deny policy denies `cloudresourcemanager…projects.setIamPolicy` to everyone except listed exception principals. So each new project is a rollout PREREQ: add the controller GSA to the Deny-policy exception (needs security approval) OR — recommended — grant app identities only RESOURCE-level IAM (bucket/dataset `setIamPolicy`, which the project Deny doesn't cover) and avoid project-level roles. SA-level operations and GSA creation are NOT blocked — only project `setIamPolicy`.

    **Further source details and anonymized verification evidence:**

    **A GCP project **Deny policy** beats an unconditional `roles/resourcemanager.projectIamAdmin` — and this makes every new project a rollout PREREQUISITE, not a config change.** A controller holding unconditional `projectIamAdmin` still gets `403 "Policy update access denied"` on a `ProjectIAMMember` grant if a project deny policy denies `cloudresourcemanager.googleapis.com/projects.setIamPolicy` to everyone outside its `exceptionPrincipals` list. **Scope the deny correctly before designing around it:** it blocks project-level `setIamPolicy` ONLY. Service-account-level operations and GSA creation are NOT blocked, and neither are **resource-level** bindings (bucket/dataset `setIamPolicy`). So the recommended design is to grant app identities only resource-level IAM and avoid project-level roles entirely — which removes a per-project security-team approval from the critical path of every new cluster. Where project-level roles are unavoidable, the controller identity must be added to the deny-policy exception per project, which is a security-team approval with lead time. Pairs with the AWS per-cluster OIDC-provider-ARN prerequisite: **both clouds have a per-account/per-project prerequisite that is invisible in the chart and blocks the first reconcile.** (Example estate: `orgs/<org>/crossplane.md#12`.)

8. **Owner-attribution is ASYMMETRIC across AWS and GCP — a "require owner" policy must target the right surface.** AWS IAM `Role` supports `spec.forProvider.tags` → stamp `owner`/`service`/`managed-by` on the cloud resource. GCP `ServiceAccount` + `ProjectIAMMember` have NO tag/label field on the cloud resource → owner attribution must ride (a) the k8s managed-resource `metadata.labels`, (b) the GSA `description`, or (c) the resource name. So a policy-engine "require owner" rule targets AWS `Role.tags` + the composed managed-resource's k8s labels, NOT a GCP cloud-resource tag (which doesn't exist).

    **Further source details and anonymized verification evidence:**

    **Owner-attribution is ASYMMETRIC AWS vs GCP — a "require owner tag" Kyverno policy must target the right surface.** AWS `iam.aws.m.upbound.io` `Role` supports `spec.forProvider.tags` → stamp `owner`/`service`/`managed-by` tags on the cloud resource. GCP `cloudplatform.gcp.m.upbound.io` `ServiceAccount` + `ProjectIAMMember` have NO tag/label field on the cloud resource → owner attribution must ride (a) the k8s MR `metadata.labels` (`example.com/owner`), (b) the GSA `description`, (c) the `xp-app-<cluster>-<ns>-<svc>` resource name. So a Kyverno "require owner tag" policy (TICKET-NN) targets AWS `Role.tags` + the composed-MR k8s labels, NOT a GCP cloud-resource tag (doesn't exist). XRole carries a required `spec.owner` mirrored to the `example.com/owner` label.

9. **Composition security: a scoping field like tenant/cluster ID must come from an `EnvironmentConfig`, never a CLAIM field (confused-deputy).** If a claim author can set the field that scopes what identity/permissions they get, they can escalate. Source such fields from a git-authored, per-cluster `EnvironmentConfig`, not claim-supplied input. Related: an **AWS permissions boundary is a CEILING** — actions outside the boundary's allow-set are granted-but-ineffective on any boundaried role, so you cannot "preserve an arbitrary broad policy verbatim" under a boundary; design the effective permission set to live inside the ceiling.

    **Further source details and anonymized verification evidence:**

    **Design contract for a "mint a per-service cloud identity from a claim" Composition.** (1) Per-item fan-out plus name truncate/hash REQUIRES a composition function — `function-patch-and-transform` cannot loop (#10). (2) A permissions boundary is a service-scoped **CEILING**: only actions inside the boundary's allow set are effective on a boundaried role, so *"preserve the existing kitchen-sink policy blob verbatim"* is **impossible** under a boundary and any migration that promises it is unimplementable — surface that at design time, not at cutover. (3) On GCP, a per-service identity is **3 MRs on `cloudplatform.gcp.m.upbound.io/v1beta1`** (NOT `iam.gcp.m.upbound.io`): `ServiceAccount` — which has **no `accountId` field**; the external-name IS `metadata.name`, capped at 30 chars, so long service names must be truncated or hashed — plus `ServiceAccountIAMMember`, whose `serviceAccountId` must be the **full path** `projects/<proj>/serviceAccounts/<email>` hardcoded (a reference yields a "required" error), plus `ProjectIAMMember`. (4) **`clusterID` as a CLAIM field is a confused-deputy hole** — source it from a git-authored per-cluster `EnvironmentConfig`, never from the claim. (5) The access-grant surface must be **named profiles ONLY**, with no per-claim escape hatch or `extraRoles`; a new grant need means adding a new named profile in one reviewed PR. Feed ONE catalog object to both the templating function and the admission allowlist so they cannot drift. (6) Read the existing behavioural tests before planning a Composition change — they already encode the contract, and re-deriving it from the templates gets it wrong. (Example estate: `orgs/<org>/crossplane.md#11`.)

## Composition authoring & chart hygiene

10. **Inject a Helm values object into a `function-go-templating` INLINE template with a backtick raw-string preamble.** Keep the pure Crossplane gotemplate in `files/*.gotmpl` (Helm never parses it; load via `.Files.Get`), then PREPEND a Helm-built preamble that assigns a variable from a backtick raw-string of `<value> | toJson` piped to `fromJson`. JSON contains no backticks (so no escaping) and Go `text/template` does not recurse into string literals (so the inner `{{ }}` survive Helm's pass). Concatenate preamble + body, indent under `template: |`; prove with `crank render`. `function-go-templating` can fan-out (`range`) and hash (Sprig `sha256sum` / `trunc`) at render time; `function-patch-and-transform` cannot loop over a variable array or hash. Prefer inline go-templating over a packaged `function-python` image — a packaged function ships/versions/pins a custom image (supply-chain cost) for no gain here. Weigh moving parts, not just code readability.

    **Further source details and anonymized verification evidence:**

    **Injecting a Helm values object into a `function-go-templating` INLINE template (single-source-of-truth catalog).** Keep the pure Crossplane gotemplate in `charts/<c>/files/*.gotmpl` (Helm never parses it; load via `.Files.Get`), and PREPEND a Helm-built preamble `{{- $var := ` + "`" + `<.Values.x | toJson>` + "`" + ` | fromJson }}` using a **backtick raw-string delimiter** — JSON contains no backticks so no escaping needed, and Go `text/template` does not recurse into string literals so the inner `{{ }}` survive Helm. Concatenate preamble+body, indent under `template: |`. Proven via `crank render`. `function-go-templating` can do fan-out (`range`) + hashing (`sha256sum`/`trunc`) all within Sprig → two per-cloud Compositions (no per-cloud branch) need only profile-lookup + `uniq` + `range` + hash. `function-patch-and-transform` CANNOT loop over a variable array or hash at runtime (ruled out for per-role fan-out); `function-python` was considered but REVERTED (packaged variant ships/versions/pins a custom function image = extra supply-chain vs inline go-templating). Lesson: weigh system simplicity (moving parts / supply-chain), not just code readability.

11. **Leave provider identity values empty in base `values.yaml`, guard with `required()`, and supply real identities in per-cluster files.** `{{ required "providers.aws.roleArn is required when providers.aws.enabled=true" .Values.providers.aws.roleArn }}` fails fast at template time if a provider is enabled without an identity, instead of rendering junk or TODO placeholders. Templates gated by `enabled` (both clouds default `enabled: false`) keep the base render clean. **NEVER revert real provisioned identities (role ARN / WI service account / project ID) to TODO placeholders during a schema refactor** — migrate them to the new keys (check `git log` for the real values first). For a digest-pinning contract, use `required()` to fail the render on an empty digest — never a silent fallback to a `:version` tag.

    **Further source details and anonymized verification evidence:**

    **Identity values: leave `roleArn`/`wiServiceAccount`/`projectID` empty (`''`) in base `values.yaml` and guard with Helm `required()`; put real identities in per-host-cluster files.** e.g. `{{ required "providers.aws.roleArn is required when providers.aws.enabled=true" .Values.providers.aws.roleArn }}`. Fails fast at template time if a provider is enabled without identity, instead of rendering junk — and avoids TODO/ticket-id placeholder noise (user preference). Base render stays clean because templates are gated by `enabled` (both clouds default `enabled:false`). **NEVER revert real provisioned identity values (IRSA role ARN / GCP WI SA / projectID) to TODO placeholders during a schema refactor — migrate them to the new keys** (check `git log` for the real values first; a refactor that blanked live TICKET-NN identities was a firm user correction). Unified surface: ONE `providers.<cloud>` block with a single `enabled` drives BOTH the Provider+DRC template (wave 5) and the ClusterProviderConfig template (wave 10). For AWS `crossplane/crossplane` `imagePullSecrets` wants a list of STRINGS not maps (see #26); for the digest-pinning contract in `functions.yaml`, use Helm `required()` to fail render on an empty digest — NEVER a silent fallback to a `:version` tag (CodeRabbit caught a silent fallback on PR #NNNN).

CI that doesn't build deps never sees it.

## Composition authoring & chart hygiene (continued)

13. **`mapfile` is a bash-4+ builtin, and `#!/usr/bin/env bash` silently resolves to an older bash (e.g. macOS's stock 3.2) whenever a newer bash isn't first on `PATH`.** A helper script using `mapfile` works fine for its author (who has a newer bash on `PATH`) and fails for everyone else with `mapfile: command not found` — a portability trap that a shebang alone cannot fix, because the shebang only names the interpreter, not the version. Portable replacement that works on bash 3.2+:
    - `read_into(){ local n=$1 l; eval "$n=()"; while IFS= read -r l; do eval "$n+=(\"\$l\")"; done; }` then `read_into ARR < <(cmd)`.
    Test any new shell helper script under both the system's stock `bash` and a modern `bash` (e.g. Homebrew's) before merging, rather than assuming a Linux CI runner catches what a contributor's Mac will not.

    **Further source details and anonymized verification evidence:**

    **`mapfile` is bash 4+; `#!/usr/bin/env bash` resolves to macOS's stock bash 3.2 whenever a newer bash is not first on `PATH`.** A helper script that works for its author fails for everyone else with `mapfile: command not found`. Portable form: `read_into(){ local n=$1 l; eval "$n=()"; while IFS= read -r l; do eval "$n+=(\"\$l\")"; done; }` then `read_into ARR < <(cmd)`. Test any new `helpers/scripts/*.sh` under **both** `/bin/bash` and `/opt/homebrew/bin/bash` before merge. (Evidence: found by the Codex adversarial lens.)

## Crossplane v2 runtime & lifecycle

14. **Crossplane v2.3.3's `Usage` reconciler only checked `ownerReferences[0]`, so a composed `Usage` object got updated on every single reconcile forever — fixed in v2.3.4.** A composed Usage always gets its composite as owner[0] and its protected-resource target as a later owner, so the reconciler's "does the protected target already own this Usage?" check never matched, and it updated the object unconditionally on every pass. That matters beyond wasted writes: a Usage update can retrigger composition reconciliation and open the composite's watch circuit breaker (see the entry on `Responsive=False`/`WatchCircuitOpen` below), so an apparently-unrelated "why is my XR's watch circuit open" symptom can trace back to this. Upstream: crossplane/crossplane#7590, fixed by crossplane/crossplane#7591 (backported as crossplane/crossplane#7597), released in v2.3.4. Verified at source: `internal/controller/protection/usage/reconciler.go:515` in 2.3.3 checks only `owners[0].UID`; the fixed 2.3.4 line uses `slices.ContainsFunc` over ALL `ownerReferences`.

    **Further source details and anonymized verification evidence:**

    **Crossplane v2.3.3's `Usage` reconciler only checked `ownerReferences[0]`, so a COMPOSED Usage was `client.Update()`d on every reconcile forever — fixed in v2.3.4.** A composed Usage always gets its composite as `owner[0]` and its `spec.by` target as a later owner, so the reconciler's "does `by` already own this Usage?" check **never matches** and it updates unconditionally, which can retrigger composition reconciliation and open the composite's watch circuit breaker. ## Compositions & cloud IAM (continued)

16. **GCP's 1,500-entry IAM limit is per allow-policy and counts duplicate member entries, not unique principals — the capacity unit is member entries, not principals.** GCP's own documentation is explicit that a single principal appearing in 50 different role bindings counts 50 times against the limit. A design that grants one binding per predefined role per consumer therefore consumes entries linearly in `consumers x roles`, and will breach a shared project's IAM policy long before the number of distinct identities suggests it should. Fix: one custom role bundling the needed permissions per package/consumer type, one binding per consumer — collapsing what would be several bindings-per-role into a small fixed number of entries per consumer. This is also operationally better: a fleet-wide permission trim becomes a single custom-role edit instead of an N-binding sweep.

    **Further source details and anonymized verification evidence:**

    **GCP's 1,500 IAM limit is per ALLOW POLICY and counts DUPLICATES — the capacity unit is MEMBER ENTRIES, not unique principals.** GCP's docs are explicit: "a single principal appearing in 50 different role bindings counts 50 times". So a design that emits one binding per predefined role per service consumes entries linearly in `services × roles` and will breach a shared project long before you expect. **FIX: one custom role per package, one binding per service → 2 entries per service** — transparent to consuming charts, and it makes a fleet-wide permission trim a single-role edit. Four constraints, each learned the hard way: (Example estate: `orgs/<org>/crossplane.md#33`.)
    1. **Mint the custom roles ONCE PER CLUSTER from a chart template, not inside the Composition** — per-claim minting produces one identical role per service against a **300-per-project** ceiling.
    2. **The role id MUST be cluster-qualified**, because one project can host several clusters; unqualified, two installations reconcile the SAME cloud role against different catalogs and fight (#72). The charset `[a-zA-Z0-9_.]{3,64}` **rejects hyphens** (most cluster ids contain one → `replace "-" "_"`), and a Kubernetes object name may not contain `_` — so the id rides `crossplane.io/external-name` while `metadata.name` stays RFC1123 (#50).
    3. **Generated permission lists need a render-time agreement guard that fires from BOTH sides** — stale committed file, and hand-edited generated file. A catalog edit alone then breaks the render until the generator is re-run and committed, which is the intended behaviour. Validate the generated list against the cloud's own `list-testable-permissions` — that is the exact criterion the IAM API rejects `CreateRole` on, and therefore the strongest offline proof available.
    4. **Preserve the bare-profile fan-out path alongside the package path** — it is how a per-service security trim narrows one service without touching the shared custom role. Naming a PACKAGE binds exactly ONE role; naming bare profiles fans out per role.
    - Audit selector for composed resources: `crossplane.io/composite=<name>`. When collapsing predefined roles into a custom role, expect to lose folder/org-scoped permissions that are absent from a project's testable-permission list — **ungrantable at project scope by ANY binding, so not a privilege regression**; enumerate them explicitly rather than asserting parity.

## Crossplane v2 runtime & lifecycle

17. **Crossplane v2's realtime-composition watch circuit breaker (`Responsive=False`, reason `WatchCircuitOpen`) sounds like a hard failure but is not one — know what it actually gates before sizing an alert on it.** v2 realtime compositions watch every composed resource so a change to any one immediately enqueues a reconcile instead of waiting for the poll interval; a circuit breaker guards that enqueue path and, if one composed resource emits events too fast, opens and downgrades that composite to periodic (poll-interval) delivery. Reconciliation is NOT stopped — the composite stays `Ready`, every managed resource keeps reconciling, and every grant it composes keeps applying while the breaker is open. State is keyed per-composite, not fleet-wide, so it does not aggregate: more composites in the fleet means more independent breakers, not a shared one that trips faster as the fleet grows. Source: `apis/apiextensions/v1/conditions.go` (`TypeResponsive`, `ReasonWatchCircuitOpen`/`Closed`), consumed in `internal/controller/apiextensions/composite/reconciler.go`.

    **Further source details and anonymized verification evidence:**

    **The Crossplane v2 XR watch circuit breaker: what `Responsive=False / WatchCircuitOpen` means, where it lives, and how to size an alert on it.** v2 realtime compositions WATCH composed resources so a change to any composed MR immediately enqueues an XR reconcile instead of waiting for the poll interval; a circuit breaker guards that enqueue path and, when one composed resource emits events too fast, opens and downgrades that XR to periodic delivery. **Reconciliation is NOT stopped** — the XRole stays `Ready`, every MR reconciles and all grants apply while it is open. **State is keyed per-XR (`req.NamespacedName`), so it does NOT aggregate across services: more XRoles = more independent breakers.** It scales with churn PER XRole, not with fleet size — an early "this will worsen as services multiply" reading was wrong. API surface: `apis/apiextensions/v1/conditions.go` (`TypeResponsive`, `ReasonWatchCircuitOpen`/`Closed`); consumed at `internal/controller/apiextensions/composite/reconciler.go`.
    - **The implementation is in the crossplane repo, NOT crossplane-runtime**: `internal/circuit/token_bucket.go` + `internal/circuit/mapfunc.go` (read at v2.3.3). Defaults (`token_bucket.go:121-128`): capacity 100, refill 1.0/s, cooldown 5m, half-open interval 30s, expire after 24h; overridable via `--circuit-breaker-{burst,refill-rate,cooldown}` (`cmd/crossplane/core/core.go:118-120`). **CRITICAL sizing detail: controller-runtime invokes a MapFunc TWICE per Update event (once with the old object, once with the new), so an Update costs 2 TOKENS** — capacity 100 = a 50-update burst, refill 1/s = one update per 2 s sustained. It wraps the watch→XR ENQUEUE MapFunc, not the reconciler. `triggered-by` comes from a 16-entry ring buffer.
    - **SAFETY PROPERTY: objects with a `deletionTimestamp` BYPASS the breaker entirely** (explicit branch in `mapfunc.go`), so deletion/finalizer paths are never throttled and the Usage deletion-ordering guards (#6, #NNNN) cannot be starved.
    - **Metrics `circuit_breaker_{opens,closes,events}_total` are LAZY `CounterVec` children** — the series does not exist until that controller's breaker first opens (`<aws-dev-cluster>` had `up{job="crossplane"}==1` for 24 h with ZERO series; `<gcp-dev-cluster-2>`'s counter vanished for 4.5 h across a pod restart and reappeared reset 16→15). Consequences: absence-safety for `increase(...) > 0` alerts is real and testable (a cluster with no series is a live negative control); **never assert `== 0` on them**; and a counter reset across a restart makes an observed burst duration a LOWER BOUND, so size `for:` with margin. Labels: `controller` (+ `result=Allowed|Dropped|HalfOpenAllowed` on `_events_total`), subsystem `circuit_breaker`, no namespace prefix.
    - **`for:` is the only discriminator between a benign rollout burst and a pathological hot loop** (#75d) — a legitimate mass-XR rollout produced a continuous 2h51m non-zero span. `Responsive=False` WITHOUT a corresponding config change indicates a genuine reconcile loop; alongside one it is expected churn that self-clears (~15 min observed after a mint).
    - **Companion absence trap on the OTHER side of the same class: an existence gauge emits a ZERO-VALUED series for every REGISTERED kind**, so `count by (<label>) (<existence metric>)` returns the registry, not reality — apply `> 0` (#184). Lazy counters over-report absence; eager gauges over-report presence.

18. **Removing a property from a live XRD does not brick the composites that still have it — it prunes the field silently, and the real cost is manifest drift, not validation failure.** An XRD-generated CRD is a structural schema with pruning on by default (no `x-kubernetes-preserve-unknown-fields`), so unknown fields are pruned BEFORE validation, never rejected: a stored composite carrying the removed field simply loses it on its next write and keeps reconciling normally. Removing an entry from a schema's `required` list is a pure relaxation with no such effect at all. Two side effects matter more than the schema change itself: (1) any GitOps-managed manifest that still SENDS the removed field leaves its sync permanently out-of-sync, because the field is pruned server-side on apply so live can never match desired — a schema-field removal needs a companion sweep of every caller still setting it; (2) a caller that still sets the field gets zero feedback that it was dropped — if the field had a downstream consumer, publish the value in status instead of silently discarding it.

    **Further source details and anonymized verification evidence:**

    **Removing a property from a live XRD does NOT brick stored XRs — it PRUNES, and the real cost is manifest DRIFT, not validation.** The XRD-generated CRD is a structural schema with pruning ON (`spec.preserveUnknownFields` unset, no `x-kubernetes-preserve-unknown-fields`), so unknown fields are pruned BEFORE validation, never rejected: a stored XRole carrying the removed field simply loses it on its next write and keeps reconciling (`Synced=True Ready=True` throughout — verified on `<aws-dev-cluster>` removing `spec.identityName`). Removing an entry from `required:` is a pure relaxation. **TWO side effects that matter more than the schema change:** (1) **any GitOps manifest still SENDING the removed field leaves its ArgoCD app permanently `OutOfSync`** — the field is pruned on apply so live never matches desired; a schema-field removal needs a companion sweep of every claim that still sets it. 19. **A Crossplane v2 namespaced composite is deleted BEFORE its composed managed resources finish deleting — it does not wait, which is worse than a wedged composite because it is silent at exactly the layer an operator looks at.** Deleting the composite can return success and the composite object itself disappears in roughly 15 seconds while its composed resources are still cleaning up — including cases where one composed resource gets stuck retrying a permission error on its own finalizer forever, with the real underlying (and still-billed, if it's a cloud resource) object intact, while the composite is gone and the GitOps controller reports Synced.     **Further source details and anonymized verification evidence:**

    **A v2 namespaced composite is deleted BEFORE its composed managed resources finish deleting — it does NOT wait, and that is WORSE than a wedged composite because it is silent at exactly the layer an operator looks at.** Observed: `kubectl delete <composite>` returns success, the composite is gone in ~15 s and the subordinate resources delete cleanly, but the core resource sits in `Terminating` holding `finalizer.managedresource.crossplane.io` retrying a 403 **forever** — with the real, billed cloud resource and its data intact, while `kubectl` says deleted and the GitOps controller says Synced. **A `Usage` guard does NOT help here: it orders composed resources, and ordering was never the problem.** Mitigation worth having independent of any permission fix: **alert on managed resources stuck `Terminating` past a threshold.** (Example estate: `orgs/<org>/crossplane.md#57`.)

Two claims in the first write-up were wrong **from reading Kubernetes state alone.**

    - **A cloud DENY overrides any allow, so no role grant fixes it** — the principal held full admin on the service and was still denied. **Do not spend a cycle widening the controller role.**
    - **Where you cannot read the policy, say INFERRED.** Deny-policy `get` is 403 at folder scope for ordinary accounts, so attribution is an inference, not a read (#113/#117).
    - **The DESIGN consequence, not just the ops one:** if the deny is working as intended, then the composition's permissive dev force-destroy posture is the thing that is wrong, not the plumbing. **Decide which before "fixing" either.**
    - **A wedged managed resource SELF-HEALS once the underlying cloud permission is granted — do NOT delete it, recreate it, or force-remove its finalizer.** Proven: after the policy exception was applied, a resource stuck `Terminating` for hours retried on its own reconcile backoff and completed the teardown. **This is the on-call recovery path and it is cheaper than the finalizer-removal alternative. 20. **CEL transition-rule validation on a CRD (the `oldSelf`-referencing kind used for "this field is immutable" or "only these transitions are allowed" rules) has two behaviors worth verifying on an isolated clone of the CRD before trusting them on a live one.** (1) An UNGUARDED rule like `self.x == oldSelf.x` on a field the stored object doesn't yet have fails EVERY update to that object — including a metadata-only label patch and finalizer removal on delete — because the rule dereferences a key that isn't there; `!has(oldSelf.x) ||` as a guard is mandatory, not stylistic, for any transition rule on an optional field. (2) Transition rules are SKIPPED ON CREATE unconditionally: verified at source in `apiextensions-apiserver` v0.35.0, `pkg/apiserver/schema/cel/validation.go:402-413` — a rule referencing `oldSelf` without `optionalOldSelf: true` is skipped on CREATE regardless of any ratcheting feature gate. That means "rename by creating a brand-new object" is always a valid escape hatch around a same-object immutability rule, by design. Consequence: a delete-path "brick" caused by a CEL transition rule rejecting the finalizer-removal update lives entirely at the apiserver layer — any application-level guard written as "skip validation logic while `deletionTimestamp` is set" is dead code, because CEL validation runs before and independent of any controller logic.

    **Further source details and anonymized verification evidence:**

    **CEL transition-rule semantics, proven live via an ISOLATED CLONE-XRD (same schema/CEL, different kind, no Composition bound) — the technique that lets you test admission behaviour without touching the ArgoCD-managed XRD.** (1) An **UNGUARDED** `self.x == oldSelf.x` on a field the stored object lacks fails **EVERY** update — including a metadata-only label patch and **finalizer removal on delete** (`Invalid value: "object": no such key: <field>`). **`!has(oldSelf.x) ||` is MANDATORY, not stylistic.** (2) **Transition rules are SKIPPED ON CREATE unconditionally** — verified at source, `apiextensions-apiserver v0.35.0 pkg/apiserver/schema/cel/validation.go:402-413`: a rule referencing `oldSelf` without `optionalOldSelf: true` is skipped on CREATE **regardless of the ratcheting feature gate**. This is the mechanism that makes "rename by creating a NEW object" a valid incident hatch against a `serviceName`-immutability rule. (3) A guarded rule does **not** over-reject — unrelated updates and delete still succeed. (4) **UNBRICK recipe**: edit the XRD to drop the rule (XRDs are freely updatable), Crossplane regenerates the CRD, and the object is updatable/deletable again.
    - **Delete-path bricks live at the APISERVER layer, not the composition layer** (#46): the CEL rule rejecting the finalizer-removal update is the whole mechanism. Any gotmpl guard of the form "skip while `deletionTimestamp` is set" is **DEAD CODE**.

47. **SUPERSEDED by #135 — Delimiter-joined identity inputs can collide; hash a canonical structured encoding.** **Deriving a cloud-identity name by PURE HASH — the design, the arithmetic, and the guard it forces you to build.** One formula for both clouds: `slug = "<app-prefix>-<clusterID>-<namespace>-<serviceName>"`; `name = printf "<app-prefix>-%s" (sha256sum $slug | trunc 20)` → **27 chars**, legal under both ceilings (GCP GSA `account_id` max 30 with regex `^[a-z](?:[-a-z0-9]{4,28}[a-z0-9])$`; AWS IAM role name max 64). 20 hex = **80 bits**. Birthday form `n²/(2·2⁸⁰)`: **P ≈ 4.1e-13 at 10⁶ identities**, 4.1e-19 at 10³ — both safe, but quote the one that matches your fleet size; the 10³ figure was recorded here for a year as if it were the 10⁶ figure. (Example estate: `orgs/<org>/crossplane.md#13`.)
    - **Why a truncate-then-suffix shape is wrong, not just ugly.** Under a 30-char ceiling, a `<prefix>-<cluster>-<ns>` head consumes the whole truncation budget *before the service name starts*, so every service in a cluster+namespace shares one visible base and the 8-hex suffix carries **100% of the uniqueness at 32 bits** — birthday P≈3.2e-6 at a few hundred charts, permanent and silent, and on a hit two claims dual-adopt one identity so each workload gets the **UNION** of both services' grants. **Diagnostic tell: a truncated-prefix name whose visible part never varies across services.**
    - **The output may lose the cluster; the INPUT slug must not.** Sibling clusters routinely share an account or project (#5), and a formula that drops the cluster from the *slug* collides siblings onto one identity — cross-cluster IAM takeover. Always assert this with a **negative control**, never by inspection.
    - **A denser encoding is a DEAD END in Sprig, so the lever is STRUCTURE, not hash width.** `sha256sum` returns hex TEXT and there is no raw-digest function, so `b32enc`/`b64enc` *of that hex* yields FEWER real bits (8 chars of `b32enc` = 20 bits vs 32 for plain hex). Base36 would be legal for a GCP `account_id` but needs a custom function image — rejected on supply-chain grounds (#10). A short cluster code in the visible part would make the common case collision-free by construction; a pure hash settles it outright.
    - **The literal prefix and the cluster tag are AUTHORIZATION, not cosmetics.** A controller policy globbing `role/<app-prefix>-*` + `policy/<app-prefix>-*` and requiring `aws:RequestTag/cluster == <clusterID>` on `iam:CreateRole` (gating lifecycle on `iam:ResourceTag/cluster`) means the prefix and the tag are load-bearing. Prove glob compatibility offline with `fnmatch` **in both directions** — the OLD glob must NOT match the new names; that failing match is the concrete proof of the merge-order dependency between the IAM change and the chart change.
    - **Opacity moves attribution onto tags and descriptions.** AWS `Role` tags can carry owner/service/managed-by/cluster/namespace/env — and where cluster+namespace+service are exactly the slug components, the tag set **re-derives** the name. GCP GSAs support NEITHER tags NOR labels (#8), so the `description` is the only surface and must carry the cluster id.
    - **Renaming is NOT in-place.** A formula change re-mints every identity: mint new → flip the SA annotation → restart the workload → *only then* remove the old claim. ArgoCD prune is not ordered against sync waves.
    - **A pure hash removes the eyeball check, so the derivation test IS the only guard.** A mis-derived name no longer *looks* wrong (a truncated shape at least showed the wrong cluster); it silently annotates the KSA with a nonexistent identity → runtime 403. The guard that works has five parts: three-way agreement (each cloud's template == an independent `python3 hashlib` oracle), a **source-level identical-derivation-lines check** that no finite input matrix can give you, format-ceiling assertions, negative controls on cluster/ns/svc, and a **MUTATION control** proving the oracle rejects both the retired shape and the hash-over-truncated-base trap — the latter is also 27 chars and regex-valid, so **only the value comparison catches it**.
    - **Assert format on the CONSUMER's output, not on the oracle.** The oracle is unperturbed by construction, so a `trunc 20 → 19` mutation flips the value comparison but leaves a format check *on the oracle* green — a vacuous test.
    - **The Composition is not the only consumer.** Every application chart that adopts the identity re-derives it, so a formula change is an **N-place** change, not a 2-place one. Grep for the derivation expression across all charts before declaring it complete, and keep every copy **byte-identical** so a source-level grep can assert agreement.
    - **`global.provider` (or whatever selects the cloud) stops being an input to the name — so its guard has to MOVE.** Consumers with a `required`/`fail` on the cloud inside the *name* helper lose that validation when the per-cloud branch is deleted. Move it to whatever still branches on cloud (the annotation-key / ARN-vs-email helper) and add an explicit `aws|gcp` `else fail` — an `if aws / else` shape silently treats a third value as GCP once the name helper stops checking. Assert **both** failure modes (unset, and invalid) as controls.

48. **Prove an umbrella-chart cutover with a REAL umbrella render.** `helm dep build` on a large umbrella works (even with remote third-party deps), so the "render each service chart standalone and hand-feed it the `global:` block" fallback is unnecessary and misleading — it cannot reproduce cross-chart value coalescing. Rules that make the proof mean something: (Example estate: `orgs/<org>/crossplane.md#14`.)
    - **The value stack is authoritative in the deploying Application's spec, not in the docs.** Read the ordered `valueFiles` list and the destination namespace off the ArgoCD Application; do not reconstruct them from a README. Falling back to a default namespace silently changes every namespaced object's key.
    - **The baseline must be a `git worktree add --detach <merge-base>`** with the built subchart directory and `Chart.lock` copied in — the main worktree can carry commits the branch lacks and will muddy the proof.
    - **Diff by OBJECT KEY, never by bytes.** Parse both renders into `(apiVersion, kind, namespace, name) → canonical YAML` and assert `non-target-kind added == 0`, `removed == 0`, `changed == 0`. A byte diff of the whole render is useless: Helm emits its `coalesce.go` table warnings to **stderr in nondeterministic order**, so sort stderr before comparing.
    - **Where a feature has two independent gates (mint and adopt), a values PR can silently do half of the other one.** Assert the ServiceAccount-annotation map is identical before/after rather than trusting the values diff.
    - **Land the value that only the not-yet-enabled consumer reads WITH the first half, not in a third PR** — when the missing value's failure mode is a whole-umbrella render failure, ArgoCD refuses to sync the entire bundle rather than the one service, so shipping it early strictly de-risks the cutover and is provable inert with the same object-keyed diff.
    - **Harness gotcha:** the Claude `Edit` tool is refused by the auto-mode classifier when the inserted line contains a **12-digit AWS account id**. Write it with a `Bash` `python3` heredoc that *derives* the value from a value already in the file (e.g. the existing role ARN) — which is better practice anyway, since a derived value cannot drift from the account it belongs to.
    - **Resolve any "this global is missing" claim against the FULL merge, never against the host-cluster layer alone** — a global can arrive at an intermediate layer, and a value that is unread by the key you are auditing can still be read by four other consumers, so "fixing" it would not be inert.

49. **A GCP custom role needs `roles/iam.roleAdmin` — `projectIamAdmin` does NOT grant `iam.roles.*`.** `roles/resourcemanager.projectIamAdmin` carries only `resourcemanager.*` and `iam.policybindings.*` permissions; `roles/iam.serviceAccountAdmin` carries none of `iam.roles.*` either. `iam.roles.{create,get,update,delete}` live **only** in `roles/iam.roleAdmin`, and nothing is inherited from folder or org. So adding a custom-role resource to a Composition adds a **new per-project IaC prerequisite**, alongside the deny-policy exception (#7) and the AWS boundary. **The failure mode is nasty and near-silent:** the custom-role MR never goes Ready, and the `ProjectIAMMember` binding `projects/<p>/roles/<id>` fails too because GCP rejects `setIamPolicy` on an unknown role — so a **migrating** identity loses its old bindings and gains none, turning "a brief blip" into a standing outage. **Always check the controller identity's permissions against the new MR kind's required IAM before approving a new Crossplane resource kind** — a project deny policy is a separate and narrower concern and will distract you from this one. (Example estate: `orgs/<org>/crossplane.md#15`.)

50. **`upjet`'s `TemplatedStringAsIdentifier(field, tmpl)` is why an MR's CRD is missing the field you expect** — it lists that field in `OmittedFields`, so it never appears in `spec.forProvider` and the value must ride `crossplane.io/external-name`. For `google_project_iam_custom_role` at provider `v2.6.0`: `config/externalname.go:100` maps external-name → Terraform `role_id`, ID template `projects/{{ .setup.configuration.project }}/roles/{{ .external_name }}`. Note the ID keys off the **ProviderConfig** project, not `.parameters.project` (unlike `google_service_account` on the adjacent line, which prefers `parameters` and falls back) — so a chart whose `gcpProjectID` diverges from `charts/crossplane` `providers.gcp.projectID` would resolve adoption against the wrong project. Read `config/externalname.go` at the pinned tag before assuming any external-name behaviour.

51. **A generated-permissions file needs an integrity check on the PAYLOAD, not just on its inputs.** A render-time guard that re-expands the catalog and compares the `roles:` list catches every catalog-drift case (role added/removed from a profile, profile added to a package, new package — all four negative-controlled) but is blind to the `permissions:` list itself: a hand-added or hand-removed permission renders straight through, and an **empty** list rendered `permissions: null` with no failure at all. Guard the payload explicitly (`if not (default (list) $g.permissions)`), and remember a generator's `--check` labelled "(CI)" in its header is worth nothing until a workflow actually invokes it — `grep -rn <script> .github/` before believing the comment. Same trap class: Kyverno allowlists written for composed MRs do not cover chart-minted MRs (`forbid-authoritative-iam` matches `projectiampolicies|bindings|auditconfigs`, not `projectiamcustomroles`).

52. **A reference chart is NOT representative of a fleet — assume divergence and read each target chart's own template.** Porting one pattern across ~80 charts with parallel workers, the SAME structural deltas recurred, and a blind copy of the reference produces either an unresolvable variable or a **silently wrong** value. The recurring shapes, in descending frequency: (Example estate: `orgs/<org>/crossplane.md#16`.)
    1. **A variable the reference defines above a gate is defined INSIDE the gate in most real charts.** If your new code must sit *above* the gate (so its guards are reachable under the fleet-default off state), you must **HOIST** the existing line up one gate — a three-line move, not a two-line insert. The hoist is render-inert (a pure dict assignment emits nothing) and is exactly what makes the guards fire under the default instead of silently rendering nothing.
    2. **Values-indirection**: charts that reach values via `$key := .Values.currentService` → `index .Values $key`. New templates must mirror the indirection and read `$serviceValues.<field>`, never `$.Values.<literalKey>.<field>`.
    3. **UNPREFIXED helper definitions.** **Helm's template namespace is GLOBAL across an umbrella, so bare `componentName`/`labels`/`keyValuePairs` defines in sibling charts ALREADY collide.** New helpers must therefore be defined **PREFIXED** (`<chart>.cloudIdentity.name`) or a value can silently resolve to another chart's define — while still **CALLING** the chart's own bare helper where it must match an existing template's output. **Reuse-the-chart's-own-names applies to CALLS, not to new DEFINE names.**
    4. **Chart-level `enabled` gates must be mirrored** in the new template, or a disabled service still creates the resource.
    5. **A COMBINED gate must be SPLIT** (`if and $c.enabled $c.serviceAccount $c.serviceAccount.create`) into an outer existence gate and an inner `create` gate to get your code above the create gate — each split adds an `{{- end }}`.
    6. **A helper's prefix does NOT always track its camelCase values key** (`gateway-log-consumer.componentName` vs values key `kongLogConsumer`). **Read it; never infer it.**
    7. **Multi-component charts need a DISTINCT service name per component** — a shared name silently collapses two components onto **one claim and one shared cloud identity**.
    8. **Anchor ambiguity**: repeated blocks at the same indent (e.g. several `serviceAccount:` under `cronjobs:`) make a bare anchor string ambiguous — anchor on a multi-line block with a discriminating line.
    - **A second, FLAT chart shape exists and is itself non-uniform.** Some flat charts already have the local+global merge idiom (a true two-line change); others have **no merge at all** (only `{{- with .Values….annotations }}`) so the merge must be introduced — still byte-identical at defaults because both sides are empty. Flat charts also have no component map and no anchor to insert after; append at the values key's block end instead.
    - **Watch for the one chart whose workload namespace is NOT the release namespace.** A chart with its own namespace helper (explicit → global → `.Release.Namespace`) that stamps `metadata.namespace` on its SA must use **that same helper** as the namespace input to any identity derivation, and the new object must carry `metadata.namespace` from it too. Verifying such a chart with the cluster default namespace produces a **false mismatch** against your plan document. If its SA gates on an enable flag, gate the new object on the same flag or the claim's trust subject names an SA that does not exist.

53. **The default-values inertness diff is VACUOUS on most service charts — a green byte-identical render can compare empty to empty.** Two independent causes: (a) components default to `serviceAccount.create: false`, so `serviceaccount.yaml` renders **nothing** and the `$identityAnnotations`/merge-reorder edit is never exercised; (b) charts whose top-level key defaults `enabled: false` (`zep`, `memos`) render **1 byte** total. Either way the diff passes even if the change were catastrophic.
    - **Rule: any chart-inertness check must first assert the baseline render is non-trivial (`wc -c`)**, and if it is empty, re-run with the chart's enable flag set (`--set zep.enabled=true` → 6758 bytes, 2 SAs).
    - **The control that actually proves merge-order purity** is a second render with `serviceAccount.create=true` **PLUS** a local component annotation **PLUS** `global.serviceAccount.annotations` (plus chart-enabled where there is a top gate), before vs after.
    - **The strongest negative control for the sprig-merge-mutation bug needs a MULTI-COMPONENT chart with a per-component annotation**: set `components.A.serviceAccount.annotations.only-on-A` and `identity.source=managed` on **both** A and B, then assert `only-on-A` appears on A's SA and **NOT** on B's. A green byte-diff alone cannot detect this.

54. **A `required()` inside a feature gate is not a guarantee, and a plan-doc row is NOT proof a component is eligible.** A claim that `required()`s a field fires that guard **only when the feature flag is on**, so a chart missing the field renders fine while disabled and fails **loudly at enable time**, mid-batch. **Before enabling any batch, filter your list by "the required field is non-empty" — do not trust the plan document's row set.** Two follow-ons: (Example estate: `orgs/<org>/crossplane.md#17`.)
    - **A field's standard descriptive comment is ASPIRATIONAL until you grep for a live consumer.** A comment reading "…emitted as the `<org>/owner` label" was accurate nowhere in the fleet: `grep` proved the field was read by exactly one new template and no label emitter existed. That made the field addition provably inert at chart defaults — which is good news, but only because it was checked. **Never assume a comment implies a live emitter; verify per chart.**
    - **Some gaps are explicit decisions, not oversights.** Record which ones the owning teams declined so they are not re-raised as findings every campaign. Where a required field exists ONLY in each chart's own `values.yaml` and nowhere in the bundle values stack, it **cannot** be supplied per-cluster at cutover — that constraint decides whether the gap is fixable in the campaign or is a prerequisite for it.

55. **Batch-verification rules for an incremental fleet campaign — carry all of these from batch 2 onward.** (Example estate: `orgs/<org>/crossplane.md#18`.)
    - **Scope assertions to the NEWLY ADDED items** (keys in after-but-not-before), never to the whole rendered set. Earlier batches are already on `main`, so a whole-set assertion reports dozens of bogus failures and **MASKS the real ones**. The trap grows with every batch.
    - **NEVER assert that a claim's `metadata.name` equals a derived identity.** Where the identity is derived **inside the composition at runtime**, it never appears in a `helm template` render at all, so the equality assertion reports 100% spurious mismatches. Correct method: assert from the render only what the render contains (name, service name, SA name, owner, access, absence of `metadata.namespace`), then **reproduce the identity independently in Python from the formula at source**. Add a wrong-input negative control so an N/N result is not vacuous.
    - **A pre-computed oracle table IS reliable — but only once you have proven it that way**, and reliable-for-derivation does NOT mean exhaustive-for-eligibility (#54). Two different properties, two different oracles.
    - **`helm template` cannot prove RUNTIME effects.** A change whose benefit is a controller-side reduction in emitted objects does not appear in a template render — do not try to assert it from one.
    - **Tamper-based discrimination controls must be ANCHORED and COUNTED** — a rendered scalar is quoted, and a short field value is often a substring of a longer label value, so an unanchored grep "finds" the tamper in the wrong place. (Full treatment: `learnings-agent-workflow.md#83`.)
    - See also: #47.

56. **When disabling a feature fleet-wide by glob, ENUMERATE every directory shape that can supply values — the third path is the one that bites.** A campaign that patched two preview-values globs missed a third location under a different bundle's `values/previews/` tree, found only by enumerating every `previews.yaml` / `values/previews/` / `preview/` directory in the repo. That third lane loaded **LAST**, after host-cluster values, with `prune: true`. (Example estate: `orgs/<org>/crossplane.md#19`.)
    - **Framing nuance that changes the severity, and the reason to check before escalating:** if the lane's destination **namespace differs** from the main bundle's, the identities it mints **DIFFER** too. That is identity **SPRAWL with a prune-on-close deletion path**, NOT a same-object collision — the same defect class with a different mechanism and a much lower severity. **Do not describe a namespace-differing preview lane as a same-identity conflict without first reading the ApplicationSet's destination namespace.**
    - **Non-vacuity control for the fix:** render with the override applied (expect 0), then strip **only** the disable blocks and re-render with the feature still enabled (expect N). That proves the fix is load-bearing rather than coincidental.
    - Cheap pre-check per chart before assuming a lane exists: `ls -d <chart>/preview <chart>/pr-preview`.

57. **Concurrent multi-worker chart batches: scope by explicit ALLOWLIST, and baseline from a pristine `cp -R` snapshot — never a glob, never the main worktree.** A `charts/*/` glob **will** hit charts owned by a concurrent worker (one worker clobbered another's `xrole` comment this way and had to string-round-trip it back). And where git is forbidden for the workers, snapshot the pristine chart dirs with `cp -R` to scratchpad and render BEFORE from the copies — **the main worktree can carry commits the feature branch lacks** and will muddy the proof. Apply edits with a Python script that **asserts `count == 1` on every anchor string** and exits nonzero otherwise; that assertion, not the diff, is what makes a green inertness result non-vacuous rather than a silent `sed` no-op. Two file-hygiene notes: `yamlfmt` excludes `**/templates/*.yaml`, so `xrole.yaml` is never lint-checked — only `values.yaml` is; and stage by **explicit path** so an untracked `charts/<main-app>/Chart.lock` does not leak into the commit (`charts/{<studio-app>,<agent-app>}/Chart.lock` ARE tracked and unchanged by `helm dep build` because their deps are `file://`).

58. **An adoption diff is a pure VALUE OVERWRITE, so identical render line counts are the EXPECTED signal — not evidence the change did nothing.** Where the new setting emits the **same annotation key** an existing global already set, and the template merges identity-first-wins, the value is **replaced, not appended**. **Assert on parsed annotation VALUES — never on `wc -l`, file size, or "head differs from base".** (Example estate: `orgs/<org>/crossplane.md#20`.)
    - **Cheapest complete blast-radius proof for any values-only umbrella change:** parse both renders into `{(kind, name, namespace): obj}`, assert the **key SETS are equal**, then count objects whose bodies differ. A correct batch gives *exactly* N differing objects, **all of the expected kind** — one check covering both "everything intended changed" and "nothing else did". Prior batches' objects must be byte-identical on both sides; that is the cheapest collateral check there is.
    - **Assert the BASE render's value too, not merely that head differs from base.** That upgrades "the change did something" into "the change moved this object off X onto Y", and it makes an accidental **re-application to an already-migrated target a FAIL** instead of a silent pass. Derive the expected base value **per target** from your source-of-truth table — a blanket per-cluster constant wrongly FAILS the already-dedicated targets, and the tempting fix (dropping the base assertion) silently weakens the proof for every other target.
    - **Do NOT assume a rendered object's name equals the logical name in your table.** Read the mapping off an already-rendered authoritative object rather than constructing it — a name-equality assumption passes on every batch where they coincide and then asserts against the **wrong object** the first time they diverge.
    - **A camelCase values path is NOT derivable from the chart name** where a chart holds several sibling components. Locate the component by **scanning for a `components` key whose child matches**; never construct the path.
    - **Count with `-A`** — an object in its own namespace makes a namespace-scoped query return a short count that reads as if something vanished.
    - **For ASYMMETRIC batches, also assert the target-exclusive items are ABSENT from the other targets' files** — a plain per-target count passes even when an item was wrongly added.
    - **Independent derivations are the actual evidence.** Get three or four parties to derive the expected set from **separate oracles** — including one that runs on the far side of the deployment (a CI-rendered diff comment computed cluster-side cannot repeat a local oracle's mistake). And run the PREVIOUS batch's verifier in the same session as the new batch's baseline: batch N−1 reading N/N while batch N reads 0/N proves the script **discriminates at that moment on those targets**, which a standalone 0/N baseline does not.

59. **A parser that SILENTLY SKIPS unmatched rows is the worst possible shape for a verification tool — hard-fail on any unparsed input that looks like data.** The adopt target-parser dropped a leaf because the plan doc **bolds** a dedicated-identity cell (`**`+backticks) while the row regex expected a bare backticked cell. The failure mode is the dangerous one: **the count still looks plausible and every parsed row passes, so a green run means nothing.** Four separate latent bugs in the same 200-line parser, each surfacing only on a specific batch shape:
    1. **Bolded cells** break the row regex → strip `**` before matching **and** hard-exit on any `| \`` line that fails to match.
    2. **Fixed column index**: a later batch's table added a `ns` column, so index 4 read the **CURRENT** identity instead of the new one (producing an "expected identity" of the shared principal). **Take column positions from each table's HEADER ROW**, and parse only tables whose header carries a `new identity` column.
    3. **Section terminator**: `startswith("## ")` overruns when the final batch is an **H1** heading. Terminate on "next heading of level ≤ the batch heading's own level".
    4. **Cluster attribution**: a single-cluster batch has no `### <cluster>` sub-heading, leaving `cluster=None` → `KeyError`. Seed the cluster by scanning the batch heading text.
    - **Regression-check every parser edit against all prior batches** (they must still emit their known counts) — that is what makes the fix provably non-regressive.
    - **The payoff of keeping derivations independent**: a second, differently-written parser read the `serviceName` column and never touched the bolded `current` column, so it got the right count and the cross-check caught the discrepancy.

60. **Preview lanes ARE REACHABLE from a host-cluster adopt, and `xrole.enabled: false` does NOT stop `identity.source` from leaking in.** `charts/argo-apps/templates/application-sets/preview.yaml` loads host-cluster values **then** the named-preview override. One override set `xrole.enabled: false` but **not** `identity.source`, so `managed` leaked through and hijacked the lane's dedicated IRSA annotation onto **identities that do not exist** (xrole disabled ⇒ never minted) — a silent total-auth break on a live lane. Fix: pin `identity.source: unmanaged` in the override; the lane render is then byte-identical to merge-base.
    - **The distinction that matters**: a preview lane that **shares the main workload's SA object** simply inherits the adopted identity (correct, no action). Only lanes with their **OWN** SA need the pin. `pr-preview` lanes need nothing (`serviceAccount.create: false` ⇒ zero SAs).
    - **Rule: any future adopt batch must render EVERY named preview lane that loads the touched host-cluster file, not just the bundle.**

61. **A values anomaly that is INERT today becomes load-bearing the moment a consumer of that key is enabled — so render every bundle×cluster combination you are about to arm, and never assume the value stack.** A cloud-discriminant key mis-set on one bundle×cluster pair changed nothing at merge-base, because the key was consumed *only* by helpers that were still disabled. The moment the feature flipped on, the render **HARD-FAILED**; had the missing companion value been supplied instead, it would have stamped the *wrong cloud's* identity annotation on every ServiceAccount in that cluster. Note the layering: a later values layer beats an earlier one, so pinning the correct value in the host-cluster file is an equivalent zero-diff-at-merge-base workaround — but fixing it at the layer that is actually wrong is the real fix. (Example estate: `orgs/<org>/crossplane.md#21`.)
    - **The companion rule, from a second anomaly in the same family:** **a values typo that looks inert to the key YOU are auditing may be load-bearing for a completely different consumer.** A value that was harmless to the identity helper (which read a different key) was interpolated by an unrelated chart into a storage URL, producing a wrong bucket path. **Grep every reader of a key before calling it cosmetic** — and prove the fix with an exact full-stack render showing exactly one line changed.

62. **SUPERSEDED by #93 — GKE token issuance resolves the identity at request time; AWS IRSA is admission-scoped.** **Adoption ABANDONS the old identity, it does not delete it — and pods do not pick up the new one until they recycle.** After a full 220-identity dev adoption: six leaves moved off **dedicated** identities and every one of those old GSAs/roles **still exists** (orphaned-identity cleanup is separate follow-up work), the leaves also retain **inert `serviceAccount.annotations` blocks naming the old identity**, and at completion only ~20 of 199 leaves had recycled naturally — the rest **still authenticate as the shared principal**. Positive token-exchange confirmation on a recycled pod (`AWS_ROLE_ARN=...role/xp-app-<hash>` in the running container) is the real proof the switchover works; the annotation flip alone is not. **Plan the pod-restart wave as explicit work, and remember the failure mode of a missed restart is SILENT** (IRSA env vars and the GKE metadata GSA resolve at pod creation only).
    - **Trap when checking for auth failures: do NOT grep logs for a bare `403`/`401`** — it matches port numbers (`40387`) and UUIDs, and produced dozens of phantom hits. Anchor on `AccessDenied` / `PermissionDenied` / `403 Forbidden` / `HTTP/1.1" 403`, and separately confirm the pattern matches a real denial.
    - Unrelated pre-existing unhealthiness will be co-located with your change — **check whether the bad pods PREDATE the merge** before reading it as cutover failure.
    - **CORRECTION — "pods do not pick up the new one until they recycle" holds on AWS ONLY.** On GCP the KSA→GSA mapping resolves at TOKEN-REQUEST time, so adoption cuts over immediately with no restart. See **#93** for the measured asymmetry and its planning consequences; it is the single most important fact for a test/prod cutover.

63. **Grant-parity proof between an old shared principal and a newly-minted identity — do it at PERMISSION level, on LIVE bindings, with a negative control.** Old side (GCP): `gcloud asset search-all-iam-policies --scope=organizations/<org> --query=policy:"<sa>"` catches **project- AND resource-scoped bindings in one query**. New side: live `projects get-iam-policy` filtered for the minted SA. Then **expand every role and set-subtract at the permission level** — role-name comparison is not parity. In the real run the only loss was the deliberately-trimmed catalog role, with zero unexpected loss; the only two resource-scoped bindings fleet-wide both duplicated a project-level role already in the standard profile, so both were inert.
    - **TRAP**: `gcloud iam roles describe` needs the **full** `roles/x.y` for predefined roles but a **bare id + `--project`** for custom ones. Mixing them returns empty permission sets and yields a vacuous "everything was lost" conclusion. **Always sanity-check that a known role resolves non-empty, and keep a negative control.**
    - AWS side: compare action patterns and check whether the boundary changes the ceiling; before re-adding an "uncovered" action, check **90d CloudTrail for actual calls by the old role** (one uncovered action had zero calls → correctly not re-added). Resource policies naming the old role are usually **not** gating — verify they are Allow-only with zero Deny, or carry a `Default` Allow to `:root` (which keeps IAM delegation active).

64. **Two live-verification tooling facts for Crossplane on AWS/EKS.** (a) **`aws` profile selection is a silent-wrong-answer trap**: the account behind a cluster may not be the default profile's account, so an unqualified `aws iam list-roles` returns `[]` **for a misleading reason**. **Always `sts get-caller-identity` first.** (b) **Server-side dry-run of an XRole claim without persisting anything**: `kubectl --context <dev-cluster> diff -f -` performs the server-side dry-run internally and writes nothing. Prove it non-vacuous by perturbing `spec.access` to a value outside the XRD enum — the API must reject it with `Unsupported value`.

65. **CORRECTION to #40(3) — only `Put` is constrained; `iam:DeleteRolePermissionsBoundary` has NO compensating Deny, and it is a live HIGH escalation.** Simulator-confirmed chain, every link ALLOWED on a controller-owned role: `CreateRole` (boundary forced) → **`DeleteRolePermissionsBoundary`** → `PutRolePolicy {*:*}` → `UpdateAssumeRolePolicy {Principal:*}` = an unbounded admin role with attacker-chosen trust. **The boundary's own `iam:*PermissionsBoundary*` Deny does NOT cover it** — that Deny binds sessions **of the minted role**, while the **CONTROLLER** performs the removal and carries no boundary itself. **Fix: drop `DeleteRolePermissionsBoundary` from the controller's manage-roles statement (the Composition never removes a boundary) + an explicit `Deny` on `*`.** Two adjacent facts from the same audit: `iam:RemoveRoleFromInstanceProfile` on `role*` is **INERT** (AWS requires the instance-profile resource type); and **the permissions boundary does NOT cap `iam:PassRole`**, so a minted role whose profile also grants `PassRole` + `lambda:*` can pass an arbitrary existing role into Lambda and **escalate THROUGH the ceiling** — `PassRole` is trim candidate #1.

66. **AWS tag-authz: the `aws:` vs `iam:ResourceTag` namespace is PER-RESOURCE-TYPE, not per-service, and the split is MANDATORY not stylistic.** Authoritative machine-readable source is AWS's programmatic Service Authorization Reference (`servicereference.us-east-1.amazonaws.com/v1/iam/iam.json`) → **top-level `Resources[].ConditionKeys`**, NOT `Actions[].Resources[].ConditionKeys` (empty for all 152 IAM entries — silence, not evidence of absence). Verified: resource type `role` → **both** `aws:ResourceTag` and `iam:ResourceTag`; `policy` (customer-managed) → **`aws:` ONLY**; `user` → both; `instance-profile` → `aws:` only; `group` → none. The dataset **discriminates between resource types**, which is a built-in negative control. **CONSEQUENCE: on a managed-policy statement you MUST use `aws:ResourceTag`** — `iam:ResourceTag` there never populates, so `StringEqualsIfExists` always PASSES (**silent fail-OPEN**) and plain `StringEquals` always FAILS (deadlock). A mixed `aws:`/`iam:` split within one document is therefore **CORRECT**; comment it or reviewers (and Cursor Bugbot) will keep flagging it as a false positive.

69. **Chart-shape detection, the dead-config trap, and two placement rules.** (Example estate: `orgs/<org>/crossplane.md#22`.)
    - **The host-cluster values structure does NOT tell you whether a chart is component-shaped or chart-shaped.** Decisive test: `grep -rn components <chart>/templates/` — zero hits means chart-shaped, and its templates read `.Values.<key>.<feature>` at chart level, not under `components`. **Some chart-shaped charts carry pre-existing `components:` blocks in their host-cluster values that are DEAD CONFIG — nothing reads them — so putting your new key there renders NOTHING, with no error.** Always read the consuming template's first lines before choosing where the values go.
    - **In a component-shaped chart the new config belongs UNDER THE COMPONENT**, inside the component's existing block, and the template should `range` over the components like every other template. A chart-level block plus a `component: <name>` scalar pointing back into the map is the shape to avoid: it only works for single-component charts and adds a key to keep in sync.
    - **Reuse before adding values keys.** Take the owner from whatever slug an existing label helper already reads (keeping the `required()` guard so an unset owner fails the render rather than creating an unattributed resource); take the ServiceAccount name from the exact expression the SA template uses; take the namespace by **omitting** it. Only add keys that genuinely do not exist.
    - **KEEP an explicit name field even where an existing helper renders the same string today.** A `componentName`-style helper embeds the **release name**, while the spec field may be CEL-immutable **and an input to a derived cloud-identity hash** — binding it to Helm naming means a release rename **silently rotates a live cloud identity**. Same string today, different failure mode tomorrow.

70. **The namespace used in an identity hash MUST equal the namespace the object actually lands in — and getting it wrong is SILENT until cutover.** Where the composition derives the hash's namespace from the **applied object's own** `metadata.namespace`, there are exactly two valid chart shapes: (1) the claim **omits** `metadata.namespace`, the GitOps destination supplies it, and the chart-side helper predicts it from the same global; or (2) the chart **stamps its own** `metadata.namespace`, and then the helper MUST use that same namespace helper. The two sides source the namespace differently **by construction** — one reads it off the applied object, the other must PREDICT it — so the invariant `<chart global namespace> == <deployment destination namespace>` has to be verified, not assumed. (Example estate: `orgs/<org>/crossplane.md#23`.)
    - **Deriving it from `.Release.Namespace` alone is INVOCATION-DEPENDENT and was a real shipped bug** (#107): a bare `helm template` with no `-n` inherits the caller's kubeconfig **current-context** namespace, so the derived identity becomes a function of an ambient machine-local property.
    - **Self-checking property worth reusing:** if the namespace input were wrong the hash would change, so **"identity unchanged after the refactor" is itself proof the namespace input was right.**
    - **Cross-template invariant:** "adopt" must imply "mint" AND a rendered/owned ServiceAccount. With independent gates, Helm can render a managed identity annotation with **zero claim**, or a claim with **zero ServiceAccount** — assert the pairing, do not infer it.

71. **Two Helm/Sprig facts behind an annotation merge, both commonly described wrong — and the probe design that proves them.** (Example estate: `orgs/<org>/crossplane.md#24`.)
    - (a) **`merge $local $global` does NOT leak across `range` iterations.** `$global` is a merge SOURCE and is never mutated, so component A's values never reach component B that way. What it actually does is **mutate `$local`, which is a POINTER INTO `.Values`** — so the global keys are written **back into `.Values`** and become visible to **any template rendered AFTER** this one. The correct form puts a **fresh dict first**: `merge (fromYaml $s) $local $global`, since `fromYaml` yields a new destination dict per iteration, including in the empty case.
    - (b) **`fromYaml ""` returns `{}` (an empty map, not nil) in Helm 3** — safe as merge's first argument.
    - **Guard reachability:** invoke a guarding helper **ONCE at the TOP of the template, OUTSIDE the range**, storing the rendered YAML **string**, then `fromYaml` it inside the range. This makes enum/`required()` guards run on **every** render regardless of whether any component has the feature turned on — otherwise a bad input **silently renders nothing and no error**, which is the common case when the fleet default is off. **Store the string, not the dict.**
    - **PROBE NAMING IS THE WHOLE EXPERIMENT.** Helm's engine sorts templates **REVERSE-alphabetically** (longer paths first, then z before a), so a probe named `zzz-probe.yaml` renders **BEFORE** the template under test and sees a CLEAN `.Values` — a **false negative** that makes a real pollution bug look fixed. Name the probe `aaa-probe.yaml` so it renders LAST. In the real run, `aaa-probe.yaml` showed 90 of 92 charts polluted at merge-base and 0 of 92 at HEAD, while `zzz-probe.yaml` showed both sides clean. **Run both, and report the pair** — early-vs-late is the evidence that the ordering is what you think it is.

72. **A PROJECT-scoped Crossplane managed resource MUST carry the cluster ID in its cloud-side name whenever two clusters can share one project.** Without it, two independent Crossplane installations manage the **same** cloud object and each reconciles it back to its own spec — **a permission change on one cluster silently mutates the other.** Applies to `ProjectIAMCustomRole` (`roleId`) and any future project-scoped MR. Two constraints combine: the `roleId` charset is `[a-zA-Z0-9_.]{3,64}`, so **hyphens are FORBIDDEN** and most cluster IDs contain one (`replace "-" "_"`), plus the 64-char ceiling. **Source the cluster ID from the same input the identity hash uses**, so the two derivations cannot drift (#47). (Example estate: `orgs/<org>/crossplane.md#25`.)
    - **GCP deny-policy exceptions are PER-PRINCIPAL, never per-project.** An exception template that does a literal `str.format` after filtering by project membership renders **only** for the one principal named — there is **no wildcard**. Two clusters sharing a project each need their **own** exception entry. Same trap for any future cluster pair sharing a project.

74. **Duplicate-named container env vars added via a chart's `extraEnv*` do not silently lose — they make the ENTIRE ArgoCD sync FAIL for that resource.** ArgoCD applies with **Server-Side Apply**; SSA treats `containers[].env` as an **associative list keyed by `name`** (`x-kubernetes-patch-merge-key`) and **MERGES same-keyed entries' FIELDS together** rather than picking one. An upstream built-in `GOMEMLIMIT` (`valueFrom: resourceFieldRef`) plus a custom `GOMEMLIMIT` (`value: '1350MiB'`) merge into ONE EnvVar with **both `value` and `valueFrom` set**, which core API validation rejects outright (`spec.template.spec.containers[0].env[1].valueFrom: Invalid value: "": may not be specified when value is not empty`). Confirmed via read-only `kubectl diff -n crossplane-system -f <rendered>` against a live Deployment.
    - **The methodology lesson is the bigger one**: two sequential source-reading passes (Go's `gogetenv` first-wins, then kubelet's `makeEnvironmentVariables` last-wins) were **each internally correct and both answering the WRONG QUESTION**, because neither is the layer that gates the behaviour — the API server's SSA structural merge is. **Verify duplicate-list-key behaviour against SSA structural-merge semantics (associative list + `patchMergeKey`), not runtime source.** A live read-only `kubectl diff` was the only thing that settled it, and an independent adversarial-lens pass was what forced the question.

75. **Operational facts for running Crossplane at fleet scale.** (a) **Core-controller memory scales with cached XR/MR count, not time — it is a load signal, not a leak.** Minting 15 XRoles / 60 MRs stepped the working set 324Mi → ~415Mi baseline with GC peaks to 520Mi **on the same minute as the XRole `creationTimestamp`**, on two clusters simultaneously. Diagnosis: a 5m-step range query on `container_memory_working_set_bytes{namespace="crossplane-system",container="crossplane"}` shows a clean **STEP, not a ramp**; correlate the step timestamp against XR `creationTimestamp`. **A step across multiple clusters at the same minute means a git/ArgoCD event, not a per-cluster leak.** Size any memory alert for the *remaining* batches, or it just moves to the next batch. (b) **`controller_runtime_*` / `workqueue_*` / `rest_client_*` are SHARED by every controller-runtime controller on the cluster** (argocd, envoy-gateway, cert-manager, aws-load-balancer, infisical, metrics-server, argo-rollouts…), so any Crossplane alert or panel over them **MUST** anchor `job=~"crossplane|provider-.*|upbound-provider-.*"` or it fires on unrelated components. `crossplane_*` / `crossplane_managed_resource_*` are provider-emitted and inherently scoped. (c) **The GCP custom-role migration is safe by construction**: Crossplane creates the new bindings **BEFORE** draining the old ones, so mid-transition the identity is briefly **OVER**-permissioned, never under — **do not plan for a permission gap.** The GSA is unchanged (identity derives from cluster/ns/serviceName), so the SA annotation never moves and **no pod restart is needed.** (d) **A circuit-breaker alert's `for:` is the only discriminator between a benign rollout burst and a pathological hot loop** — a legitimate mass-XR rollout produced a continuous 2h51m non-zero span, so `for: 6h` shipped instead of the specified `1h`. **Do NOT raise the THRESHOLD instead**: rollout bursts run *hotter* than a slow hot loop, so only duration separates them.

78. **AWS IAM policy limits for the XRole shape — the "10 policy limit" people cite does NOT apply to us, and the limit that WILL bite is aggregate INLINE SIZE.** The AWS composition emits exactly ONE inline `iam.aws.m.upbound.io/RolePolicy` per role, single Statement (all profile actions on `Resource: *`), and **zero** managed-policy attachments. 79. **Never let a claim supply the minted-identity NAME and use it verbatim as `external-name` — the Composition must stay the name AUTHORITY.** Two holes, both structural: (1) Crossplane's **observe-and-adopt** plus `managementPolicies: ["*"]` means a claim whose `external-name` matches an existing cloud resource **ADOPTS** it and rewrites it to desired state — so an app-supplied name is a cross-namespace identity **HIJACK** (attacker rewrites a victim Role's trust to their own KSA). The un-forgeable `metadata.namespace` baked into a server-derived name is the ONLY tenant fence, and an app-supplied name deletes it. (2) **XRD spec-scoped `x-kubernetes-validations` CEL cannot close the hole**: it cannot see `metadata.namespace` or the `EnvironmentConfig` (resolved at reconcile, not admission) and has no `sha256`, so it can neither re-derive nor authorize the name; a `contains(serviceName)` heuristic also false-rejects GCP truncated names. **Correct pattern: the Composition re-derives the canonical name from un-forgeable inputs (`metadata.namespace` + `serviceName` + `env.clusterID`) and any claim-supplied name is a CHECKED ASSERTION only — fail loudly on mismatch, always use the canonical.** Co-located server-side agreement check, preserves the namespace fence, needs no CI diff guard. 82. **Crossplane v2 NAMESPACED provider MRs REQUIRE `spec.providerConfigRef.kind`, XRD Establish enforces a CEL COST BUDGET, and NEITHER is caught by `crossplane render` — a live cluster apply is the only sufficient proof.** (a) **`providerConfigRef.kind`**: `*.m.upbound.io` MRs (`iam.aws.m.upbound.io/Role`, `RolePolicy`, `cloudplatform.gcp.m.upbound.io/…`) reject with `spec.providerConfigRef.kind: Required value` if it is omitted — v2 removed the default because a namespaced MR may point at either a namespaced `ProviderConfig` or a cluster-scoped `ClusterProviderConfig`. 88. **SUPERSEDED by #46 — The v2.3.3 deleting-XR path skips Composition functions; CEL can still block finalizer updates.** **Adding a REQUIRED + IMMUTABLE field with a Composition-side `fail` created three STACKED bugs that TOTALLY BRICK a legacy object — always test the DELETE and BACKFILL-ON-LEGACY paths, and `has()`-guard every `oldSelf` reference.** Found live on `<aws-dev-cluster>` while deleting a legacy XRole (one with no `spec.identityName`). (1) **The gotmpl `fail` on mismatch ALSO fires on DELETE** — Crossplane runs the pipeline to clean up, so the delete-reconcile fails, the finalizer never clears, and the XR shell is stuck pending deletion after its composed MRs are already gone. (2) **The immutability CEL rule blocks BACKFILLING the field** (`self == oldSelf` rejects a first-set), so the claim cannot be fixed in place. (3) **Worst: `self.identityName == oldSelf.identityName` with NO `has()` guard** — on a legacy object `oldSelf.identityName` throws `no such key: identityName`, so **EVERY update is rejected including metadata and finalizer removal** = total brick: cannot delete, cannot patch, cannot remove the finalizer. **Force-delete does not help** (CRs still run finalizers and CEL). **Unstick procedure**: patch the LIVE XRD rule to `!has(oldSelf.identityName) || self.identityName == oldSelf.identityName`, THEN remove the finalizer via a metadata patch. **The shipped fix** (PR #NNNN, adversarial-reviewed clean): delete-guard `and (not $xr.metadata.deletionTimestamp) (ne $xr.spec.identityName $name)` plus the `has()`-guarded CEL, offline-proved on an identical Go-template+Sprig engine via a throwaway `helm template` probe — **`crossplane render` cannot prove this because it short-circuits the deleting-XR pipeline.** The probe showed OLD fires on delete (reproducing the brick), NEW skips on delete, NEW still fires on a create/update mismatch. **Two review lessons**: the original adversarial review MISSED all three because it only exercised create/update mismatch, never delete or legacy-first-set; and a bot's "make `serviceName` immutable too" suggestion, taken literally and **unguarded**, would have re-created this exact brick — any such follow-up must use `!has(oldSelf.serviceName) || …`. **Related mechanics**: `metadata.namespace` is authoritative and immutable after create but is client-selected in the submitted manifest, so cross-namespace safety rests on ArgoCD destination/RBAC pinning the submitter, not on the Composition alone (#79); and the live XRD uses **STRICT decoding**, confirmed by a dry-run of a claim carrying an unknown field returning `BadRequest`, which is what makes an XRD field change a deploy-sequencing concern for any live claim.

89. **A FLAT `maxLength` on an identity-name field false-rejects one cloud — template it per-cloud off the discriminant.** `maxLength: 30` (the GCP GSA `account_id` ceiling) rejects valid AWS names. **HISTORICAL WORKED EXAMPLE — it depends on the RETIRED truncate-plus-8-hex naming formula that #47 deleted (see #90 for the retired shape); do not re-derive from it.** Under that formula, proven via `crossplane render`, the AWS canonical name for `ns=svc=echo-server` on `<aws-dev-cluster>` was `xp-app-<aws-dev-cluster>-echo-server-echo-server-<hash-8>` = **50 chars** (AWS role-name ceiling is 64; the gotmpl truncated the slug to 55 + an 8-char hash), while GCP was always ≤30 (trunc 21 + 8). **Under the current pure-hash formula (#47) every name is 27 chars on BOTH clouds, so this field is no longer where the cross-cloud divergence bites — but the RULE stands**, because any identity-name field whose ceiling differs per cloud has the same defect, and a future formula change can re-open it. **Fix**: `{{ if eq $cloud "gcp" }}30{{ else }}64{{ end }}` — the XRD is single-cloud-rendered per cluster (`learnings-helm-ci.md#36`), so this is natural rather than a redesign. **Both `helm template` and `crossplane render` PASS the flat form** — only a length-vs-real-name comparison surfaces it, which is why the check must be an explicit assertion and not a green render.

90. **Service-chart cloud-identity helper shape — the parts that outlive the naming formula.** **SUPERSEDED IN PART BY #47:** this entry's original item (1), the `trunc 55`/`trunc 21` + 8-hex naming formula, was DELETED by #47 and replaced with a pure hash. It is kept only as a historical record at `orgs/<org>/crossplane.md#29` — do not implement it. The rules below are the parts that survive the formula change. (Example estate: `orgs/<org>/crossplane.md#29`.)
    - **Return a ONE-ENTRY YAML MAP from the annotations helper, not a bare string**, so the ServiceAccount template does `fromYaml` + `merge` with **no cloud branching** — one derivation feeds both the claim and the KSA annotation.
    - **Precedence: `merge (dict) $local $identity $global`** — a **FRESH dict** as destination so the first source wins and nothing under `.Values` is mutated in place. This is the hardening over the naive `merge $local $global`, which mutates `$local` (#71). The chart's ordinary annotations map remains the escape hatch; no dedicated override value is needed.
    - **The chart's cluster-name global MUST equal the composition's `EnvironmentConfig` cluster id — a mismatch is SILENT**, because both sides independently derive an identity and neither validates the other. Assert the equality somewhere, or the two derivations drift into two different cloud identities with no error.
    - **Where a cloud discriminant is required, `fail()` on anything that is not a known value** — an `if aws / else` shape silently treats a third value as the other cloud (#47).

91. **Merging ANY PR into a Terraform-apply-on-merge repo applies that stack's ENTIRE plan, including pre-existing drift unrelated to your diff.** `terraform apply` is triggered by the push to the default branch, not by your resources. **Method: never read the plan summary line alone — "N to change" on a purely ADDITIVE diff ALWAYS means drift.** Pull every `~ resource` block out of the plan and identify each one before merging. The sharp edge is **unattended infrastructure upgrades landing as a side effect of an unrelated PR** — managed add-on version bumps that restart cluster networking or DNS, autoscaler-fought node counts being forced back, parameter-group `apply_method` flips that reboot a database. Either ask the stack owner to reconcile the drift first, or deliberately decide to apply it — but do it as a decision, not as a surprise. (Example estate: `orgs/<org>/crossplane.md#30`.)

92. **A infra-terraform apply-on-merge failure is often a TRANSIENT GCP IAM API flake, not your change — rerun, then verify against live cloud, never against the CI status.** The `infra-terraform` GitHub Actions workflow can fail on `context deadline exceeded (Client.Timeout)` while refreshing **unrelated** `google_service_account` data sources; it aborts before writing, leaves cloud untouched, and has nothing to do with the PR's diff. **Fix: `gh run rerun <id> --failed`**, which re-applies only the pending diff. Validated this way on the TICKET-NN boundary widening: the rerun succeeded and the **live** objects confirmed it — `xp-app-boundary-<aws-dev-cluster>` went v1 → v2 (37 service + 3 IAM allows, 38-action enumerated deny) and controller `xp-aws-ctl-<aws-dev-cluster>` went v4 → v5 (a `SetAppBoundaryOnly`-conditioned Put). **ALWAYS validate an infra apply against live cloud via the CLI, not the CI run status** — see #91 for why the run's plan output is also not the whole story.

93. **Identity-adoption restart-gating is CLOUD-ASYMMETRIC — the single most important planning fact for a test/prod cutover, and "pods do not pick up the new identity until they recycle" is only half true.** (Example estate: `orgs/<org>/crossplane.md#31`.)
    - **GKE Workload Identity: the KSA→GSA mapping resolves at TOKEN-REQUEST time, not pod-creation time**, so an adopted ServiceAccount swaps identity **IMMEDIATELY, with no restart** — running pods that started days earlier begin failing within hours of the annotation flip, with no restart involved.
    - **EKS IRSA: the pod-identity webhook injects `AWS_ROLE_ARN` + `AWS_WEB_IDENTITY_TOKEN_FILE` + the projected-token volume into the POD SPEC at admission**, so running pods keep the OLD role until they recycle.
    - **CONSEQUENCE: on GCP the blast radius lands at ADOPT time; on AWS it lands at NEXT RESTART.** A cutover document saying "the annotation binds at pod creation, so a running pod keeps its old credentials" is **TRUE for AWS and FALSE for GCP** — never apply it uniformly. The GCP half means the leaves you believe are "safe on old credentials" are on a **delayed fuse**, not safe.
    - **CORRECTION — "GCP cuts over with no pod restart" is TRUE for TOKEN ISSUANCE and FALSE for long-lived clients, and the difference silently KILLED a workload.** Read "no restart required" strictly as *"no restart to GET the new identity"*, **never** as *"no restart NEEDED"*. A client library that resolved the bound service-account EMAIL once at process start keeps refreshing against the email-specific metadata path, which stops resolving the moment the annotation flips — so **on a GKE adopt, pods OLDER than their batch are AT RISK, not safe. Plan a deliberate recycle of pre-adopt pods on GKE too, exactly as on EKS** — the difference is only that on GKE the recycle is *remediation* rather than *activation*. (Mechanism and detection channel: #168; the signed-URL/SignBlob variant that is invisible to every metadata-server check: #169.)
    - **REVOKING is immediate on BOTH clouds and needs no restart** — both IAM systems evaluate per request, so a running pod loses access within seconds. Security can pull a permission without a deploy. **Only GRANTING is restart-gated, and only on AWS.**
    - **The revoke MECHANISM differs by cloud**, which matters for what you watch: an inline policy is updated **in place** on AWS, while on GCP the binding objects are **DELETED** — and where deletion-ordering guards exist they must drop **before** the bindings do, which is what prevents the dangling-principal tombstone in #6.
    - **Trim at the CLAIM, not the catalog, when you want a per-service revocation.** A catalog-level trim is fleet-wide by construction; replacing a package reference with its explicit member list minus the revoked profile is per-service and reviewable in that service's own PR.
    - See also: #62, #114.

94. **A workload's cross-cloud federation can be INVISIBLE to Kubernetes entirely — a podspec/chart grep for federation markers is a FALSE-NEGATIVE instrument and must never be the primary pass.** An application can federate GCP→AWS purely in code: obtain a Google ID token from application-default credentials, then call `AssumeRoleWithWebIdentity` with an anonymous STS client and a role ARN baked into the image or per-tenant config. There is then **no `AWS_ROLE_ARN`, no token-file env var, no projected-token volume, and no role ARN anywhere in the chart.** And because **the Google-issued OIDC token's `sub` is the service account's numeric `uniqueId`**, swapping the KSA→identity mapping silently breaks the trust match **with no pod restart and no Kubernetes-visible signal at all.** (Example estate: `orgs/<org>/crossplane.md#32`.)
    - **The detection instrument that WORKS:** enumerate AWS IAM roles whose trust policy `Principal.Federated` is `accounts.google.com` and whose `Condition` names a numeric service-account `uniqueId` (`gcloud iam service-accounts describe --format='value(uniqueId)'`), across **every** account you might touch. Secondary instrument: logs.
    - **Anchor the log search on `AccessDenied`/`PermissionDenied`/`403 Forbidden`, never a bare `403`** (#62) — and note that roles consumed by **unadopted** default or preview-lane ServiceAccounts are **latent-armed, not broken**, so **classify by consumer before escalating.**
    - Two recurring DISTRACTORS in such a sweep that are NOT identity-cutover issues: a cross-cluster OIDC mismatch on a KSA-keyed exporter, and denials from a namespace outside a role's `system:serviceaccount:<ns>:*` trust. **KSA-keyed workload-identity-federation providers (`google.subject = assertion.sub`) are structurally immune to an identity swap** — knowing which of your federations are KSA-keyed vs GSA-keyed tells you the true blast radius up front.

95. **`identity.source: managed` OVERRIDES a component-level explicit `serviceAccount.annotations` IAM key, not just the global one.** `merge $identityAnnotations $localAnnotations $globalAnnotations` is sprig FIRST-SOURCE-WINS and the identity dict is deliberately first (it must be — merge mutates its first argument, and `$localAnnotations` points into `.Values`; see #71). So a leaf that pins a dedicated identity via its own annotations block in the host-cluster values file still flips to `xp-app-*` the moment `identity.source: managed` is set, and the explicit block becomes **inert dead config**. Observed on all 6 dedicated-identity leaves in TICKET-NN batches 4–6. Precedent set: LEAVE the superseded block in place rather than mixing a cleanup into an adoption PR; sweep them once after fleet-wide adoption. (Same reason adoption **abandons** the old identity rather than deleting it — #62.)

96. **Catalog TRIM mechanics, and three ways a trim proof goes vacuous.** Extends #68's two-PR delete sequence with what a *membership* trim actually costs. (Example estate: `orgs/<org>/crossplane.md#34`.)
    - **KEEP the profile definition; remove it only from the package.** Where the template fans a **bare profile** out to individual roles while a **package** binds one aggregate role, the profile key still works as a reviewable per-service opt-in — and the schema's generated name list is unchanged, so `maxItems`, CEL and schema tests need no edit. Deleting the key churns the schema for zero security gain.
    - **Where the aggregate role is minted ONCE PER CLUSTER, a trim is N in-place role updates, not per-identity churn** — dozens of live identities reconcile with zero binding/identity/guard churn and no pod restart, because the role id is unchanged.
    - **Non-vacuity method that generalises: build an INDEPENDENT oracle, and FIRST prove it byte-matches the PRE-change committed artifact.** Self-consistency alone proves nothing. Doing this caught that the committed baseline was already drifted from the live cloud, and proved the regeneration folded in zero of that drift.
    - **A negative control must perturb something that IS in scope.** Perturbing the very thing you just removed returns "identical" **vacuously** — the control has to touch a member that is still selected.
    - **A permission count computed from live cloud at time T is NOT a fact about the repo at time T+1.** Reading a generated file from a **stale checkout** produced a wrong loss figure that was repeated for a day *after* the fix had landed. Always re-read the catalog and the generated file from current default-branch state, and confirm against the live role, before quoting any count.

97. **Adding a member to a `packages:` list is a FLEET-WIDE IAM GRANT EXPANSION with ZERO claim-side diff — treat package-membership edits as permission changes requiring security review.** Both go-templates resolve a claim's `access` entry via `if hasKey $packages $a { $selected = concat $selected (index $packages $a) }` (`xrole-gcp.gotmpl:44`, `xrole-aws.gotmpl:27`), so a 13th member of `standard` grants that profile's roles/actions to EVERY XRole selecting `standard` on the next sync, with no edit to any claim and therefore **no claim-side review surface**. Only a standalone UNREFERENCED profile key is genuinely safe to add in one PR. **GENERAL LESSON: in a catalog/indirection design, "requires no edit to any consumer" is a BLAST-RADIUS property, not a safety property — docs presenting it as safety invert the risk.** (Found by CodeRabbit on PR #NNNN. The CEL cost budget, #82b, is a second reason catalog additions are not unconditionally safe.)

98. **A Composition runtime `fail()` on the UPDATE path is actively harmful, not merely noisy — it FREEZES existing grants in the cloud.** If the render fails, no composed-resource spec is produced, so the existing MRs keep their LAST-APPLIED spec and **the cloud grant is never revoked**; the XRole just parks at `Synced=False` while the broad permission persists. So a catalog trim does not take effect for any XRole referencing the trimmed profile. **Design implication: prefer "deprecate-not-delete" — empty the profile's role/action list but KEEP the key**, so `hasKey` stays true, the render succeeds, and the grant is actually revoked. This is the counterweight to the fail-closed rule in #84: fail-closed is right on CREATE (an under-privileged identity minted silently is worse), and wrong as the *policing* mechanism for catalog contents. Same reasoning as #68's two-PR delete sequence.

99. **Where ArgoCD's resource health customisations live in a Terraform module that stacks pin BY GIT TAG, promoting a feature to a new tier is a per-stack PIN BUMP, not a repo-wide apply — and until it happens ArgoCD reports a FAILING resource as Healthy.** **Without a registered health check, ArgoCD defaults an unknown CRD to Healthy.** So a tier one module tag behind shows `Synced/Healthy` for the entire time a broken custom resource exists, which **masks a failed rollout exactly where you most need the signal — in the tier you are promoting into.** Two operational consequences: (a) audit the LIVE `argocd-cm` on every target cluster for the health customisations and the resource exclusions before believing any health status there; (b) treat the module pin bump as an explicit acceptance criterion of the promotion ticket, not as adjacent cleanup. The diffs are typically surgical (a few dozen lines in one file), which is exactly why they get forgotten. (Example estate: `orgs/<org>/crossplane.md#35`.)

100. **Rolling a platform onto a NEW cluster — five rules that outlive any particular file layout.** (Example estate: `orgs/<org>/crossplane.md#36`.)
    - **A chart can FAIL `helm lint`/`helm template` with base values only, BY DESIGN.** Where an empty cloud discriminant produces an invalid resource name and an unparseable env-config, always pass a host-cluster overlay or a dedicated `ci/lint-values.yaml`. Do not "fix" the base render — the failure is the guard working.
    - **Where IaC stacks consume modules by PINNED TAG, editing the module does NOT reach any stack.** Make stack-scoped changes in the stack directory; a module edit plus a merge is a no-op until each stack's pin moves (#113, #99).
    - **Do not cross stack shapes.** Two stacks that look interchangeable can differ in how they derive the same value (a hardcoded enable flag and a direct project lookup vs a gated flag and a remote-state lookup). Read each one.
    - **Validate with a synthetic claim placed OUTSIDE `templates/`** (e.g. under `tests/`): Helm never renders it, the GitOps Application only templates `templates/`, and the App-of-Apps diff confirms the consuming Application is UNCHANGED — so merging enables the controllers and schema but mints nothing until a real claim exists. **Prefer a PR-gated real values file over a `kubectl`-applied throwaway claim**, so the enablement is reviewable and reproducible.
    - **Adopt in TWO PHASES on a new tier**: turn the mint on first, wait for `Ready`, and only THEN flip the adopt flag. One PR that does both cannot be rolled back to a working state.

101. **PREDICT the derived value before you apply, then compare — a prediction made first is FALSIFIABLE, a value read after the fact is not.** Precompute the expected identity from the formula at source, **validate the formula first by reproducing an ALREADY-COMMITTED value** (that step is what makes the prediction trustworthy rather than merely confident), then compare against the first live mint, with independent derivations agreeing — hand-written oracle, the chart's own helper, and the real runtime output. (Example estate: `orgs/<org>/crossplane.md#37`.)
    - **Know the expected composed cardinality before you count.** For N roles on GCP: 1 `ServiceAccount` + 1 `ServiceAccountIAMMember` (WI trust) + N `ProjectIAMMember` + (N+1) `Usage` guards; on AWS a `Role` + one inline `RolePolicy` + tags + a boundary. Under a per-package aggregate-role model, N is the number of packages, not the number of roles — which is how you confirm a quota workaround actually took effect.
    - **`kubectl get managed` returns NOTHING for v2 composed MRs.** They are the NAMESPACED `.m.upbound.io` variants living in the CLAIM's namespace, and the cluster-scoped `*.upbound.io` query is empty. Query the `.m.` group in the claim's namespace.
    - **THE CLI TRAP: cloud `list` commands are PAGINATED by default.** Without an explicit `--limit`/`--max-items` you can silently get **zero matches and wrongly conclude nothing exists**. A live collision/baseline check in one command: list every identity in the project with an explicit high limit, grep the target hashes (zero hits proves BOTH no collision AND genuinely-unminted pre-merge), and assert `cut -d@ -f1 | sort | uniq -d` is empty for project-global name uniqueness. The resulting count doubles as a cross-check against your cutover document's per-cluster count.
    - **A transient `Responsive=False / WatchCircuitOpen` right after a mint is expected churn and self-clears** (~15 min observed) — see #17 before escalating it.
    - See also: #47.

102. **Delete-with-no-orphan must be verified TWO-SIDED and driven through GIT, not `kubectl`.** (Example estate: `orgs/<org>/crossplane.md#38`.)
    - **A `kubectl delete` against a GitOps Application with `automated: {prune: true, selfHeal: true}` is RECREATED within seconds and verifies NOTHING.** Flip the enable flag to `false` in git so the controller prunes and the composition tears down — that is what a real decommission does (objects pruned ~3 min after the flip in practice).
    - **Capture an explicit CLOUD baseline BEFORE deleting and check BOTH directions — OVER-deletion is as much a failure as under-deletion.** Write two lists first: MUST-DISAPPEAR (the per-app identity, its bindings, its inline policy) and **MUST-SURVIVE** — every shared, chart-owned or IaC-owned object in the same blast radius, **explicitly including the SIBLING cluster's**, if the account or project is shared. If one app's teardown takes a shared aggregate role, every other app in the project silently loses its grants. Confirm bindings go to **zero**, not merely that the identity vanished: that distinguishes real revocation from deleting an identity out from under live bindings.
    - **NULL-TEST TRAP when probing a contraction→delete race: patch-then-delete back-to-back does NOT test contraction at all.** Once `deletionTimestamp` is set the composition pipeline never runs (#46), so the contraction never renders and you have measured a plain delete. You must wait for a resource to actually enter `Terminating` before deleting. And a single non-reproduction is a **single trial** — say so.
    - **Check EVERY environment for residue, not just the one you are testing.** The same sweep turned up pre-existing orphan tombstones on a project that had never been cleaned after earlier testing.

103. **Kyverno background scanning DOES cover composed Crossplane MRs, and the discrimination method beats waiting.** Confirmed on `<gcp-test-cluster>` 2026-08-07: after the first XRole minted, 5 `PolicyReport`s appeared **in the claim's namespace in ~12 minutes** (not the 1h default interval) — one for the XRole plus one per composed MR — scoped with the NAMESPACED `.m.` apiVersion (`cloudplatform.gcp.m.upbound.io/v1beta1`). **When 0 reports exist, compare the live resource's actual apiVersion against the policy's `matchConstraints.resourceRules` versions/apiGroups: exact match ⇒ a timing question; a wildcard or an unserved version ⇒ the bug, and no amount of waiting helps.** (The dev phase shipped `apiVersions: ['*']` and had to be replaced with concrete served versions.) 106. **Testing an OPAQUE derived identifier: the MUTATION control is the load-bearing half, not the equivalence check.** When a name goes from readable to a pure hash, two guards vanish at once — the admission cross-check (TICKET-NN dropped `spec.identityName`) and the eyeball check. The suite becomes the only guard, and a suite that merely asserts `template output == oracle` proves nothing unless you also prove the oracle can FAIL. Render two mutations deliberately and require rejection: **(a) the retired formula** (catches a straight revert) and **(b) the near-miss — hashing the TRUNCATED BASE instead of the full slug**, which is still 27 chars and still matches the GCP `account_id` regex, so every FORMAT assertion passes on it and only the VALUE comparison catches it. That (b) case is the argument against ever downgrading the equivalence assertion to a length/regex check. Add a **source-level assertion that both implementations carry byte-identical derivation lines**: a finite input matrix proves agreement only on the cases enumerated; only source comparison proves there is no input on which they could differ. Known-good perturbation mechanics: perturb with **Python, not BSD `sed -i ""` (which silently no-ops)**, and `grep` the file to CONFIRM the perturbation applied before trusting that the harness failed.
    - **A test's acceptance criterion is MUTATION coverage, not green output.** Recipe (k8s PR #NNNN): script the mutations (`perl -0pi` on templates/values), run both suites, expect NON-ZERO, revert, and re-confirm the baseline BEFORE and AFTER the sweep; run the SAME sweep against the pre-fix commit to produce a real before/after column. It caught two honest nuances: the old suite tripped on a catalog-rename mutation via unrelated *cardinality* asserts rather than the grant-expansion asserts the review named; and an added-5th-rule mutation was caught only by a pinned `lengthEqual`, which is defeated by bumping the pin — so a **REPLACE-an-existing-rule mutation is the honest test of an exhaustive sweep.** GOTCHA: `git checkout <sha> -- path` STAGES that version into the index, so a later `git checkout -- path` restores the OLD file; use `git reset HEAD -- path && git checkout HEAD -- path`.
    - **Two oracle traps worth asserting against**: (i) an oracle reading the same source as the code under test goes empty in LOCKSTEP under a schema rename (`assert_eq '' ''` passes) — add a startup non-empty self-check; (ii) `sort -u` applied to BOTH sides of a comparison erases a dedup regression — drop it and let `jq`'s `unique` be the only dedup.
    - **Re-derive whether a requested VERIFICATION still tests two independent things when a dispatch is re-scoped mid-flight.** A helper↔Composition equivalence harness was specified while both were to ship in ONE PR; after the split it degenerated into comparing `xrole-aws.gotmpl` vs `xrole-gcp.gotmpl` while the same file separately asserts those two are byte-identical — near-tautological. The genuinely irreducible parts were the source-level identity assertion and the **clusterID negative control** (dropping clusterID makes siblings collide → `CreateRole` AUTHORIZED but `EntityAlreadyExists`, then observe denied = a permanent non-self-healing deadlock).

107. **A harness that renders ONE way cannot catch INVOCATION-DEPENDENT derivations — it passes for the wrong reason.** `helm template` WITHOUT `-n` inherits the **KUBECONFIG current-context namespace**, not `default`. A helper doing `$ns := .Release.Namespace` therefore produces a DIFFERENT identity depending on who runs it and on what kubectl context: the same chart+values+cluster rendered `xp-app-<hash-a>…` (ns `<namespace>`), `xp-app-<hash-b>…` (ns `echo-server`) and `xp-app-<hash-c>…` (ns `default`). **Under ArgoCD it resolves correctly (`Release.Namespace == destination.namespace`), so this is invisible in production and bites exactly the offline renders, CI and verification harnesses meant to catch a wrong identity** — and the failure mode is a SILENT 403 because nothing cross-checks the name at admission. FIX: `$ns := $g.namespace | default .Release.Namespace` (this is #70's "authoritative value" made concrete). Real bug shipped and caught on review (k8s PR #NNNN).
    - **Permanent harness check whenever a chart derives a value that must be deterministic**: render (a) with the intended `-n`, (b) with NO `-n` under a kubeconfig whose current-context namespace is DELIBERATELY different, and (c) with no kubeconfig at all, then assert the derived value is byte-identical. Prove non-vacuity by reverting the fix and confirming ONLY the new assertions fail while the `-n` ones keep passing — **that asymmetry is the signature of the bug class.**
    - **Read `global.namespace` out of the actual per-cluster values file before computing an expected identity.** `echo-server` pins `global.namespace: echo-server` in ALL THREE `values-<cluster>.yaml` files and does NOT use the cluster-default namespace from the CLAUDE.md table — assuming the default produces a wrong expected hash and a false MISMATCH. When a subagent hands back a three-way-agreement table, **check its inputs are the chart's REAL inputs, not plausible ones**; a table can be internally consistent and still not describe what deploys.
    - Two shell gotchas from building this: **zsh does NOT word-split an unquoted `$var`**, so building `helm -f a -f b` in a string variable passes it as ONE argument and yields an empty render that reads as a legitimate "0 objects" result — use an array and always guard with an explicit empty-render check; and `set -o pipefail` makes `failing-cmd | grep -q X && echo ok` report failure even when grep matched, so a negative test that greps an EXPECTED render error must capture stderr first (`cmd 2>&1 >/dev/null || true`) and `case`-match it.

109. **Crossplane metrics plumbing — four gates, each of which silently drops all targets on its own.** (Example estate: `orgs/<org>/crossplane.md#40`.)
    1. **Controller pods serve `controller_runtime_*`/`workqueue_*`/`rest_client_*` on :8080 but declare NO named metrics container port** (only readyz and webhooks) → a PodMonitor must use `podMetricsEndpoints.portNumber: 8080`. **Provider pods DO declare a named `metrics` port** → use `port: metrics` with a `matchExpressions` Exists selector. There is **no shared selector label across controller + providers**, so you need TWO PodMonitors, not one.
    2. **`metrics.enabled: true` is REQUIRED in every overlay** — the upstream subchart gates `containerPort: 8080` on it (`deployment.yaml:159`), and without it the port is absent from the pod spec and prometheus-operator **silently drops all controller targets**.
    3. **Series can be dropped POST-scrape** by a metrics-tuning allowlist in your metrics-collection chart — a metric name must be added there too, or the scrape succeeds and the data still vanishes.
    4. **A capability-gated template (`.Capabilities.APIVersions.Has`) omits its output from a plain offline `helm template` even with the values key enabled** — re-render with `--api-versions <group>/<version>/<Kind>` AND separately confirm the CRD is served live. **GENERALISE: a capability-gated template makes a values key look INERT when it is not** — the same shape hides any conditional whose condition is not evaluable offline.
    - **kube-state-metrics custom-resource-state for CR conditions:** `valueFrom: [status]` emits ONE gauge series per condition type carrying the RAW status string on the `status` label **CAPITALIZED** (`"True"`/`"False"`/`"Unknown"`), value 1 when True. **A `status="true"` (lowercase) filter matches NOTHING** — a real dashboard shipped with exactly that bug. The robust not-ready alert is VALUE-based and casing-independent: `min by(...)(<metric>{type="Ready"}) == 0`.
    - **KEEP per-kind custom-resource-state entries even when a native aggregate metric exists** — CRS carries per-resource NAME + condition, while the native `crossplane_managed_resource_*` is aggregate **BY GVK ONLY**. For a per-resource table or a per-resource alert the CRS is required, not redundant. KSM tolerates absent-CRD GVKs (reflector backoff, no crash).
    - **Render an observability chart with the FULL value stack** — a CRS config gated by BOTH an `enabled` and a `create` key, where the base `values.yaml` says false and an upper layer overrides it to true, renders as disabled in any single-file render.
    - **Chart sizing coupling: the upstream subchart derives `GOMEMLIMIT` from `resources.limits.memory` via `resourceFieldRef` on BOTH the init and main containers** (2.3.3 `templates/deployment.yaml:98,178`). Changing `limits.memory` therefore **silently moves the Go soft cap on every cluster**, and pinning `GOMEMLIMIT` to exactly the hard limit gives little protection — the soft limit governs only Go-managed memory, so the working set can cross the cgroup ceiling while the runtime believes it is compliant. Reason about request and limit separately, and state what a limit change does to `GOMEMLIMIT`. (And see #74 for why you cannot simply add your own `GOMEMLIMIT` env var.) **Verify any "this matches the upstream default ratio" claim against the VENDORED subchart's `values.yaml`, not against the author's restated ratio** — a claimed "keeps the upstream 2x ratio" was measured against a vendored default that is 4x.

110. **A derived identifier with no machine-readable source, and a rotation hatch resting on an UNENFORCED convention — carry both constraints into any claim-helper design.** (Example estate: `orgs/<org>/crossplane.md#41`.)
    - **If the composite publishes no `status` field for the value it minted, the real consumer (the workload's ServiceAccount annotation) has to RE-DERIVE the value by hand** — and then nothing can cross-check the two. **An assertion that compares the composite to ITSELF protects nothing**; the only assertion worth having compares the consumer's rendered value to the composite's published one. Publish the minted value in `status` and build the cross-check; that is the difference between a verifiable and an unverifiable design.
    - **The rotation escape hatch is "bump the logical name field ⇒ a NEW composite object"** (CEL transition rules skip CREATE, #20). **That works ONLY if the composite's `metadata.name` is DERIVED from that field** — otherwise the bump is an in-place UPDATE and is rejected by the immutability rule by design. If no consumer derives `metadata.name` that way, nothing couples the rotation input to the workload's annotation, and no CI check or admission policy enforces either, then **document the hatch as future/manual until those couplings exist**, including the create-new → repoint-consumer → verify → prune-old ordering. A hatch that only works under an unstated convention is not a hatch.
    - **Replacing an indirect immutability guard with a direct one is usually right, but name what the indirect one was actually catching.** A rule on a derived field was, in practice, catching an in-place edit of the *input* field — which leaves composed resources under the old name while rendered references point at a new one (split references). Enforce that directly at admission and keep the Composition as the sole name authority.

111. **Upbound v2 family packages install BOTH the namespaced `.m.upbound.io` CRDs and the LEGACY cluster-scoped `.upbound.io` CRDs — an admission guardrail matching only the `.m.` group is bypassable through the legacy API using the same provider credentials.** Verified for `provider-aws-iam` v2.6.1 (`Role`/`RolePolicy` in both groups) and `provider-gcp-cloudplatform` v2.6.0 (`ProjectIAMAuditConfig` and other `cloudplatform` resources in both groups) from the xpkg `package.yaml` plus live `api-resources` on `<aws-dev-cluster>`/`<gcp-dev-cluster>`. **Either match BOTH groups (and update any kind-guard CEL), or remove / RBAC-deny the legacy CRDs.** Same class as #51's "Kyverno allowlists written for composed MRs do not cover chart-minted MRs". **Agreeing cross-domain restatement: `learnings-operators.md#16`** states the same dual-group fact from the admission-guardrail side and adds the AWS tags-vs-labels attribution trap; this entry owns the package-level evidence (which xpkg, which versions).

112. **A grant catalog's approved entries can import INDIRECT escalation primitives that a schema enum cannot see — the bypass is through APPROVED PROFILES, not through a forbidden string.** Rejecting direct `roles/owner|editor|admin` strings at admission feels like it closes escalation. It does not: (Example estate: `orgs/<org>/crossplane.md#43`.)
    - **GCP:** a profile granting `roles/iam.serviceAccountTokenCreator` at PROJECT scope lets a minted application identity impersonate **any** service account in the project — including the platform controller's own account, if that account holds project IAM admin and is a deny-policy exception. That is a `roles/owner` self-grant in two hops, entirely through approved catalog entries.
    - **AWS:** a profile combining `iam:PassRole` with `lambda:*`, `cloudformation:*`, `codebuild:*` and `ec2:*` at `Resource: '*'` leaves a service-role escalation path wherever a privileged passable role exists — **and a permissions boundary does not cap `PassRole`** (#65), so the escalation goes *through* the ceiling. Reached from the claim side, this is the same hole #65 found from the controller side.
    - **These follow directly from a deliberate "verbatim parity" decision** — copying today's fleet grants verbatim so that trimming is a follow-up rather than a migration prerequisite. **Verbatim parity is a legitimate choice, but it IMPORTS escalation primitives**, and the two facts must be stated together: a catalog that reproduces an existing broad grant inherits every escalation path that grant already had. Required hardening before hand-authored elevated claims can be treated as non-escalating: **remove project-level `TokenCreator` / `PassRole` from claimable packages, or resource-scope them.** Interim gate: an admission policy plus RBAC on who may create a claim. **`iam:PassRole` is trim candidate #1.**
    - **Forward constraint on tag-based scoping:** S3 general-purpose bucket APIs and the provider support tag-on-create, but tag-based AUTHORIZATION for subsequent bucket lifecycle requires S3 bucket ABAC to be enabled. Apply ABAC to IAM roles and customer-managed policies now, and retain explicit ARN scoping for buckets until an ABAC-modelling resource exists.

113. **Verifying that a MERGED infra change actually LANDED LIVE — three gates, and CI green proves NONE of them.** (Example estate: `orgs/<org>/crossplane.md#44`.)
    1. **Merge ≠ apply.** Where the apply job is skipped on the PR and runs only on the merge commit, find it explicitly: list runs on the default branch, locate the run whose `headSha` is the merge commit, then read its jobs. **An apply can FAIL post-merge** — one died during ephemeral provider config on a secrets-backend 504, before touching any resource (nothing partially applied; a plain re-run fixed it). See #92 for the transient-cloud-flake variant.
    2. **`gh run watch` exits 0 when the WATCHER succeeds, not when the run passes** — always re-read the run conclusion afterwards.
    3. **Read the LIVE policy, not the diff.** Assume into the target account first (**always `sts get-caller-identity` before believing an empty `list-roles`** — #64a), then `get-policy`/`get-policy-version` and enumerate `Statement[].Condition`. Scrub the credentials after. Gotcha: `aws iam list-policies --query "…|[0].Arn"` can emit a trailing `None` line that **silently corrupts a shell variable** — use the literal ARN.
    - **Where a live read-back is IMPOSSIBLE, SAY SO and downgrade the claim to "config landed and applied".** An ordinary cloud-engineering account cannot read GCP org deny policies at all, so post-merge validation of a deny-exception change is necessarily: PR MERGED + merge SHA, the deploy workflow run has `headSha` == that SHA with `conclusion=success`, and the entries are present on the default branch. **State the gap explicitly — the definitive confirmation is the first dependent resource reconciling `Ready`.** AWS has the same read limitation on `iam:ListOpenIDConnectProviders`, but there existence is provable **transitively**: IAM rejects `CreateRole` with `MalformedPolicyDocument` when a `Principal.Federated` provider does not exist. **A transitive proof is often available where a direct read is not — look for one before downgrading.**
    - **`aws iam simulate-custom-policy` IS the right negative-control tool for an IAM authorization review, and it IS reachable** even when your SSO role lacks `iam:SimulateCustomPolicy` — assume the target account's platform role and simulate from THAT session. Render the policy JSON offline, then simulate per case with `--context-entries` supplying the tags to construct the sibling/negative case. **ALWAYS add an OVER-DENY control** (something that must stay ALLOWED) or an all-denied result is **indistinguishable from a broken policy**. **Honest caveat: the simulator does not read real resource tags — you supply them — so it proves CONDITION LOGIC only; whether the cloud actually POPULATES that key for the resource type must come from the service authorization reference (#66). Neither alone closes the question.**
    - **Always query LIVE CLOUD for IAM ground truth, never a repo grep** — vendored `.terraform` copies and drift make the repository misleading.
    - **How a MODULE change actually reaches a cluster when stacks pin by tag.** Merging a module edit **AUTO-CUTS a new per-module tag** via semantic-release (conventionalcommits: `feat` = minor, `fix` = patch) — **you do NOT cut tags manually.** Rolling it to a cluster is then a separate one-line PR bumping that stack's `?ref`, followed by apply. **Per-stack ref = isolated blast radius**, which is exactly why a tier promotion is a per-stack pin bump (#99). **Watch for tags that are the SAME commit**: one `feat` touching two modules cuts both at the merge SHA, and a patch bump may be documentation-only — verify with `git ls-remote` before choosing which to pin.
    - **A local `terraform plan` can need FRESH credentials for a cloud the stack does not obviously use** (a remote state backend, or SOPS via a KMS in another cloud). Expired credentials surface as an `invalid_grant` on `init`, or as data sources hanging forever in `Still reading…`. **WORKAROUND that needs no credentials and is STRICTLY BETTER for a drift inventory: push the branch, let CI run its per-stack plan jobs, then harvest the job logs via the API** — CI plans with the same identity and exit node the merge-to-main apply will use. Also note a `.tool-versions` pin means an older local binary cannot read that state.
    - **Verify a stack is CI-covered WITHOUT waiting on the provider**: run the repo's own matrix-builder script locally with the event and changed-file list. **Check for `freeze: true` entries — a frozen stack is silently excluded from BOTH the PR checks AND the merge-to-main apply.**
    - **CI can stop scheduling ALL `pull_request` runs repo-wide** while the repo-level Actions setting still reads enabled (org policy, quota, or provider-side). **Symptom to recognise: the PR shows only third-party APP checks and ZERO Actions jobs.** The danger is specific to apply-on-merge repos: **merging during an outage lands the change in git, applies nothing, and then fires UNATTENDED on recovery.**
    - **`sops` key removal needs live KMS access to recompute the file MAC.** Hand-deleting an encrypted block CORRUPTS the MAC (with `unencrypted_suffix` the MAC covers all values) and breaks decryption in CI. Proper removal is `sops unset <file> '["key"]'` (a 3.9 subcommand — a `--rm` flag does NOT exist). **If credentials are expired, removal is BLOCKED: defer it, do NOT corrupt the file.** Verify the block is genuinely dead first.

114. **EKS IRSA adoption is admission-scoped: the SA annotation flip is inert until pods recycle, and a deliberate recycle is the only way to test it while someone is watching.** (Evidence: batch 2, validated live on `<aws-test-cluster>` 2026-08-10.) On GKE the metadata server re-resolves at token-request time so Workload Identity cuts over with no restart; on EKS the pod-identity webhook injects `AWS_ROLE_ARN` **only at pod admission**, so every already-running pod keeps the old shared role indefinitely. Consequences and method:
    - **Reading the SA annotation is NOT verification on AWS.** Read `AWS_ROLE_ARN` from the live pod spec — that is what the workload actually uses. A clean post-merge result on EKS means *nothing happened yet*, not *it worked*.
    - **Recycle with `kubectl rollout restart deployment/<n> -n <ns>` and `rollout status --timeout=600s`** (ML/JVM services here carry startup-probe budgets of 360–810 s; a shorter timeout reads a slow model load as failure). Confirmed working: the new pod's `AWS_ROLE_ARN` is the minted `xp-app-*` role, `AWS_WEB_IDENTITY_TOKEN_FILE` and the projected `aws-iam-token` volume are present, 0 restarts.
    - **Proving assumption when the image has no `aws` CLI and no `boto3`** (common — both services tested lacked both, so `kubectl exec … aws sts get-caller-identity` fails): read the pod's projected token and assume from the workstation — `TOK=$(kubectl exec <pod> -- cat /var/run/secrets/eks.amazonaws.com/serviceaccount/token); aws sts assume-role-with-web-identity --role-arn <xp-app> --web-identity-token "$TOK"`. Returns `assumed-role/xp-app-<hash>/<session>`, proving the trust chain end-to-end. Never print or persist the token. **Always pair with the negative control** — service A's token against service B's role must be `AccessDenied`, or a green result only proves the trust policy is permissive.
    - **Pre-flight gate before any recycle:** the minted role's trust policy must have `Principal.Federated` == the live cluster OIDC provider ARN (`aws eks describe-cluster --query cluster.identity.oidc.issuer`), `sub` == `system:serviceaccount:<ns>:<ksa>`, `aud` == `sts.amazonaws.com`. Wrong trust policy = guaranteed 403; find it before the restart, not after.
    - **Choosing a canary: verify, don't infer from the name.** A GPU-limited service (`nvidia.com/gpu: 1`) is a bad first target regardless of how stateless it looks — a `RollingUpdate` surge needs a *second* GPU while the old pod still holds one, which can deadlock the new pod in `Pending`. Check `resources.limits`, `initContainers`, volumes/PVCs, PDB/HPA, and startup-probe budget first.
    - **GPU headroom must be scheduler-compatible, not fleet-wide.** Filter allocatable GPUs through the workload's `nodeSelector`/taints/tolerations, then subtract GPU requests on those nodes; a free GPU on another pool cannot take the surge. Before calling zero compatible headroom a deadlock, also inspect the matching autoscaler/nodegroup: a healthy group below max means the surge should be temporarily `Pending` while a node scales up, whereas maxed or non-autoscaled capacity is a real stall.
    - **Rollback of the pod does NOT roll back the identity.** `kubectl rollout undo` re-admits against whatever the SA annotation currently says, so it picks up the *same* minted role. Reverting identity requires reverting the values change in git (`source: managed` → `unmanaged`). Say this plainly in any runbook; implying otherwise sends an incident responder down a dead end.

115. **Adoption does not revoke the old shared role — least-privilege is not banked until the shared trust wildcard is narrowed.** (Evidence: verified on `<aws-test-cluster>` 2026-08-10.) The legacy `eks_<cluster>_<namespace>_<serviceaccount>` role's trust policy uses `StringLike` with `sub: system:serviceaccount:<namespace>:*` — a wildcard over **every** KSA in the namespace. An already-adopted SA's live projected token still successfully assumes the broad shared role. So adoption changes what a workload *uses* (the injected `AWS_ROLE_ARN`), not what it *can* assume: a default, not a boundary — structurally the same trap as Istio `PERMISSIVE` mTLS, where an identity `AuthorizationPolicy` is bypassable until the mode is `STRICT`. Do not claim a least-privilege outcome for an adopt batch on this evidence; the security win requires a later phase that narrows the shared role's trust to exclude adopted SAs, or retires it per cluster.
    - **Record an accepted decision immediately next to the open-debt entry it sits on top of, each pointing at the other.** Without that pairing the debt entry reads as an unraised finding and gets re-raised every review cycle; the estate's acceptance record is the counterpart to this entry, and both are true at once.

116. **A "no denials" check is VACUOUS until you prove the workload calls the cloud API at all — and environment variables are not that proof.** Two recycled services showed zero `AccessDenied` in logs and in CloudTrail, and the first sweep showed neither had made a *single* `sts:AssumeRoleWithWebIdentity` call — which reads as "no denials" meaning "no calls attempted". One of them carried `AWS_ACCOUNT_ID` / `AWS_REGION` / `CLOUD_PROVIDER=aws` and still made no calls, **so selecting a canary by its environment block misleads.** (Example estate: `orgs/<org>/crossplane.md#45`.)
    - **THE WINDOW IS THE INSTRUMENT: an idle test cluster needs a ≥24 h window before "no cloud calls" is a real conclusion.** A 6-hour sweep was a **sampling artifact** — one service made its first `AssumeRoleWithWebIdentity` **16 hours after** its recycle, then succeeded on KMS operations under the new role. **Pair it with the liveness split: zero assumes over ≥24 h of uptime is CONCLUSIVELY SILENT; under 24 h of uptime is UNINFORMATIVE, not a pass — and conflating the two manufactures a clean result.**
    - **jq gotcha, stronger than it first looks: `(.userIdentity.userName // .userIdentity.principalId)` is MANDATORY, not defensive.** In an `AssumeRoleWithWebIdentity` sample, **100% of events** — not merely the denied minority, and including every error event — arrived as `userIdentity.type=AWSAccount` with **no `userName` field at all**. A jq path reading only `.userName` therefore **drops EVERY event**, not just the failures you are hunting, and reports an empty census as a clean one. Related trap: the `(.userName // .principalId)` fallback returns the SHORT form `system:serviceaccount:<ns>:<sa>` for CLI/`WebIdentityUser` events with no issuer id in it, so a later grep for the cluster's OIDC issuer discards exactly those — **filter on `.principalId` directly when you need the issuer, and NEVER apply an issuer filter to a denial census.**
    - **Several clusters can share one cloud account** — discriminate by the OIDC issuer id embedded in the subject string, not by role name.
    - **Grep denials case-insensitively across every spelling** (`AccessDenied`, `AccessDeniedException`, `UnauthorizedOperation`, `not authorized to perform`, `403`, `ExpiredToken`) and **baseline the same grep BEFORE the change**, so pre-existing noise is not misread as new breakage — a recurring denial pair belonging to an unrelated collector will otherwise be attributed to your cutover.
    - Pick the canary from evidence: `aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=AssumeRoleWithWebIdentity`, day-sliced (#176), grouped by ServiceAccount.

117. **When an identity-adoption row is dedicated→dedicated, the discriminating question for a RESOURCE-SCOPED binding is PROJECT OWNERSHIP, not permission names — and the privilege delta can run the OPPOSITE way from the rest of the batch.** A row whose old identity holds a resource-scoped binding looks equivalent to a project-scoped package on a permission-name diff and is **not** equivalent unless three things hold. Check them **in this order**: (Example estate: `orgs/<org>/crossplane.md#46`.)
    1. **Same project.** A project-scoped grant in project A never covers a resource in project B. Get the owning project *without* guessing the resource's location: `gcloud asset search-all-iam-policies --scope=organizations/<org> --query='policy:"<principal>"'` returns each resource-scoped binding **with its owning project number** alongside the full resource path — far better than per-location `list` guessing.
    2. **No IAM condition on the replacement bindings.** A *conditional* binding can exclude the resource type while passing every permission-name comparison. Read the live policy and assert `condition` is null on each replacement role.
    3. **Permission coverage EXPANDED LIVE, not recalled.** Describe the old role and require every one of its permissions to be in the replacement union.
    - **THEN CHECK THE GAIN, NOT ONLY THE LOSS.** Adoption PRs are reviewed for permission *loss* against an accepted-losses list, and that review shape **structurally cannot see the opposite failure**. Where most rows move laterally from an already-broad shared principal, a genuinely narrow dedicated identity moving onto the same broad package is an enormous privilege *expansion* — an ~84× jump in one real row. Non-blocking if it follows from a deliberate verbatim-parity decision (#112), but **it must be STATED**; the least-privilege win is banked by the later trim and shared-role-narrowing phases, never by adoption (#115).
    - **Say UNVERIFIED rather than implying a check was clean.** Org/folder-level DENY policies and VPC-SC perimeters are unreadable to an ordinary cloud-engineering account (`denypolicies.list` denied; Policy Troubleshooter / Access Context Manager APIs disabled) — name the gap (#113).

118. **An AWS permission-parity comparison must expand *ATTACHED MANAGED POLICIES*, not just inline statements — a legacy shared role often has ZERO inline statements, so an inline-only comparison reports a vacuous "0 lost" that reads as a clean pass.** `aws iam list-role-policies` + `get-role-policy` alone resolves such a role to the **empty set**, and `old − new` is then empty **by construction**. This is the AWS twin of the "assert each side resolves NON-EMPTY first" rule (#117, #119). Correct shape: (Example estate: `orgs/<org>/crossplane.md#47`.)
    - Union **inline** (`list-role-policies` → `get-role-policy`) **and attached** (`list-attached-role-policies` → `get-policy` → `get-policy-version` at `DefaultVersionId`), and **hard-fail on an empty result for either principal.**
    - **Compare WILDCARD-AWARE (`fnmatch`), not by exact string.** A replacement package written as `s3:*` / `kms:*` shapes against a legacy role enumerated action-by-action makes a plain set-subtract **fabricate hundreds of phantom losses**; with `fnmatch` the delta collapses to the genuine accepted losses.
    - **Cheap collateral check worth keeping:** hash each minted role's action set — if all of them collapse to ONE signature, the package is uniform, and you have confirmed it without reading every policy by hand.

119. **A parity cell reading "holds zero project roles" is a statement about *PROJECT* scope only and never rules out a RESOURCE-scoped binding — re-derive it live, and GATE the query with an existence check so "no bindings" is distinguishable from "wrong identifier".** (Example estate: `orgs/<org>/crossplane.md#48`.)
    - **Run an existence check (`describe`) on the principal BEFORE the org-scope binding search.** A "zero bindings" result is only evidence if a *wrong* identifier would have ERRORED — `describe` on a bad email returns `NOT_FOUND`, which is the salt-equivalent for a query whose pass condition is an empty result. Separately **oracle the search itself against a principal known to return bindings**, so you know the query shape works at all.
    - Then apply #117's three-step test (same project / no condition / permission coverage expanded live) — a resource-scoped read is frequently *subsumed* by the replacement's project-scoped package, not lost.
    - **The GAIN can be starker than any dedicated row you have seen.** A principal holding NO project roles moving onto a broad package is a `0 → N` expansion, larger in relative terms than any partially-privileged row. **A loss-only review sees nothing at all here. State it.**

130. **A NAME denylist stops "do not set this key"; it CANNOT stop "do not achieve this effect" — for anything security-sensitive use a positive ALLOWLIST, and guard at the ACTION, not at the condition.** Generalises to any escape-hatch API. Five independent bypass classes, each found on one design: (Example estate: `orgs/<org>/crossplane.md#52`.)
    - **EFFECT BY ANOTHER PATH.** Reserving a field name does not pin it when a `*Ref`/`*Selector` sibling reaches the same field — and `resolve.policy: Always` **RE-RESOLVES them at reconcile, overwriting an already-rendered value.** Reserve the field AND its `Ref`/`Selector`/`expectedOwner` siblings on **every** routed resource, and test the reserve list against the pinned CRD inventory (#128).     - **VALUE denylists are WHITESPACE- and CASE-BYPASSABLE on unconstrained upjet string fields.** Where a CRD puts NO `enum` and NO `pattern` on a field, a guard of `lower(x) == "delete"` is defeated by `'Delete '`, `' Delete'`, tab and newline — verified live: the variant rendered into the composed resource as a destructive rule and `kubectl apply --dry-run=server` **ADMITTED it with the whitespace preserved and unpruned**. Separately, **Go `text/template` map keys are CASE-SENSITIVE**, so `hasKey` against lowercase reserved keys never catches `BUCKET` — bounded by CRD admission rejecting unknown fields, but a real defence-in-depth gap.
    - **Key-level control on a RICH CONDITION SURFACE is structurally incomplete — enumerate the surface to PROVE it.** A lifecycle `condition` object exposing 15 keys, **TEN of which can match a LIVE object**, means denylisting the obvious one (`age`) is catastrophically incomplete: a Delete rule with only a prefix match and no age deletes every live object under that prefix. **The correct control is at the ACTION** (refuse the destructive action type, case-insensitively). Do the enumeration **even when you intend to block at the action** — it is what proves the key-level control cannot work.
    - **SILENT OVERRIDE IS WORSE THAN REJECT: every INVARIANT must be in the denylist, not just the structurally dangerous keys.** A design that wrote its invariants LAST (so they win) but omitted them from the protected-key list **silently overrode** a claim that set them, instead of rejecting it. The claim author gets no signal that their setting did nothing.
    - **The audit question is NOT "is this field dangerous" — it is "does any ALLOWED field make a PINNED PLATFORM INVARIANT inoperative?"** A full walk of one base CRD's 23 `forProvider` fields found exactly ONE mis-classified field: a namespace-hierarchy toggle that is ALLOWED, yet under which object versioning is **unsupported**, so it defeats a pinned `versioning: {enabled: true}` invariant under a name the denylist never saw — and it is creation-only/ForceNew, so it cannot be undone. **Fields whose vendor docs say "feature X is unsupported when this is enabled" are exactly that class — GREP THE PROVIDER DOCS FOR THAT PHRASING during any denylist audit.**
    - **REVIEW A PASSTHROUGH GUARD AT TWO LAYERS, AND PROVE BOTH.** Template ACCEPTANCE is not provider EFFECT: an `x-kubernetes-preserve-unknown-fields` subtree can render malformed casing or nesting that the composed resource's structural CRD then prunes (unknown keys) or rejects (wrong scalar type).     - **A "no equivalent exposure" claim must be proven ADVERSARIALLY, not assumed.** Two reusable proofs that a passthrough cannot compose an *additional* resource kind: **(1) template injection** — a passthrough STRING containing a newline, `---`, and a full second document renders as a **QUOTED BLOCK SCALAR** under `toYaml | nindent`, so only the intended documents are emitted; **(2) server-side pruning** — fields that are not CRD fields are PRUNED at admission where `spec.forProvider` has `properties` and no `x-kubernetes-preserve-unknown-fields`.
    - **THE REPEATABLE AUDIT PROCEDURE**, extending #127 into method: **(1)** enumerate fields from the LIVE CRD on the cluster — never from docs, never from the requester's list — and walk **NESTED** objects (a nested `rule[].destination` is invisible to any top-level name check); **(2)** ask ONE fixed question per field (permission-granting / data-movement / data-destroying) and **RECORD THE ANSWER FOR THE NOs TOO** — an allowed field with a written justification is a DECISION, an allowed field with no note is an OVERSIGHT, and that difference is the entire class of bug being fixed; **(3)** separate METADATA-ONLY leakage (access logs, event notifications) as a weaker class rather than lumping it with data exfiltration; **(4)** check for fields that make a pinned invariant inoperative, not only fields dangerous in themselves; **(5)** **a near-clean result is a valid outcome — report it plainly and LEAD with the structural containment fact that explains why the exposure is small**, so "we found little" reads as verified rather than lazy.

135. **Deriving a security- or ownership-relevant name from several user-controlled strings: DELIMITER CONCATENATION IS NOT INJECTIVE, and a schema's per-field `maxLength`s do not bound the SUM.** If the delimiter is legal inside every component, `(a, b-c, d)` and `(a-b, c, d)` produce the **same** joined string and therefore the **same hash** — so two distinct tenants collide onto one identity, silently and permanently. 143. **CMEK on a resource XRD: check the key's LOCATION against the environment config, know that a structurally-correct regex is usually charset-LOOSE, and judge a suspicious-looking key name with the cloud API rather than by pattern.** (Example estate: `orgs/<org>/crossplane.md#61`.)
    - **Location/region cross-check.** A regex-valid CMEK override naming a key in another location or region **renders verbatim while the resource stays in the cluster's location** — an ACCEPTED claim that can never reconcile. Compare the override against the environment config's location inside the composition, and **NORMALIZE CASE BEFORE COMPARING**: the KMS API's location form and the storage API's location form for the same physical multi-region differ in case, so a naive string compare rejects a legal key.
    - **A structurally-correct regex is usually charset-LOOSE — do not describe it as validating the identifier.** A pattern of the shape `^projects/[^/]+/locations/[^/]+/keyRings/[^/]+/cryptoKeys/[^/]+$` **accepts a SPACE** as a keyring or key id, where the real id charset is `[a-zA-Z0-9_-]{1,63}`; an ARN pattern of the shape `^arn:aws:kms:[a-z0-9-]+:[0-9]{12}:(key/.+|alias/.+)$` **accepts `---` as a region** (the service model's region pattern is `^([a-z]+-){2,3}\d+$`) and any string as a key id. The consequence is bounded — a malformed key is rejected at reconcile rather than silently accepted — but the claim "the pattern validates the identifier" is false.

(b) **A lowercase KMS location and an uppercase storage location for the same multi-region are API-SURFACE DIFFERENCES, not a mismatch** — cross-check by verifying both resolve to the same LOGICAL location rather than by string-comparing them.

144. **Server-side dry-run of an XRD validates the ENVELOPE and accepts arbitrary invalid inner CEL — reconstruct the CRD Crossplane will DERIVE and `kubectl diff` THAT instead.** Extends **#82b** (cost budget) and **#20** (transition-rule semantics). Nothing is persisted. **Defaulting proof:** diffing a rendered `XBucket` claim against `<gcp-dev-cluster>`/`<aws-dev-cluster>` showed `versionRetentionDays: 90` on the MERGED side even though the claim never sets it — which simultaneously proves (a) the XRD is Established and serving and (b) defaulting works. 145. **upjet models singleton Terraform blocks INCONSISTENTLY — slice vs pointer per kind — so never infer one MR's nested-block shape from another's.** Neither offline render tests nor claim-level dry-run can catch a wrong shape: composed MRs are only schema-checked at RECONCILE, so a mis-shaped nested block renders green, admits green at the claim, and fails on the composed resource. Read the installed CRD (or the generated Go type) for the exact kind before writing the block.

146. **A template file embedded as a Composition INLINE template is SHIPPED CLUSTER PAYLOAD, not repo text — and that changes what a comment costs, what a test proves, how a stacked PR must degrade, and which syntax is even legal.** Where a chart template embeds the file VERBATIM as a string via `.Files.Get`, Helm never parses it, so `{{- /* … */ -}}` blocks inside are **payload bytes**, not Helm comments that vanish at render. (Example estate: `orgs/<org>/crossplane.md#62`.)
    - **Comments are rendered manifest content.** An audit catalogue or sweep record inside such a file is a **manifest CHANGE on every consuming cluster**, and a ticket id in such a comment **LEAKS into live manifests**. **Rule: rationale that is an AUDIT RECORD belongs in the design doc; the template keeps only the load-bearing reason plus a pointer that NAMES the doc — never a local filesystem path, which is both a dead link for reviewers and shipped to clusters.** Set an explicit per-comment line ceiling for these files.
    - **A COMMENT-ONLY edit IS a rendered-output change, so a parsed-object tree comparison WILL fail on that object no matter what the edit was.** The working comparator special-cases exactly that ONE field — strip template comment blocks and full-line `#` comments from the embedded string on BOTH sides, compare the residue, and compare every other object strictly. **The negative control must be TWO mutations: one ordinary template value AND one INSIDE the embedded file** — only the second proves the comment-stripping has not blinded the check. **And the right blast radius is itself evidence:** the embedded-file mutation must fail on exactly the affected cloud's snapshots and leave the others clean.
    - **SYNTAX TRAP — Go `text/template` lexes a comment ONLY when `/*` sits exactly ONE space after the trim marker.** `lexLeftDelim` sets `afterMarker = trimMarkerLen = 2` (the `-` plus one space) and then tests `HasPrefix(input[pos+2:], leftComment)`. So `{{- /* x */ -}}` parses and **`{{-   /* x */ -}}` (extra spaces) is lexed as an ACTION** and dies with `parse error …: unexpected "/" in command` — which is why such comments must sit at column 0. **Never "tidy" one by indenting the opening delimiter; indent the comment BODY on continuation lines instead.** Helm surfaces this only as a parse error at the **CONCATENATED harness line number, not the source line**, so the reported location is misleading. Related closers: `*/ -}}` trims the newline before a `---` separator and **concatenates it onto the previous line**, and `*/ }}` is INVALID (a comment must end AT the delimiter) — use `*/}}` or `*/ -}}`. Both surfaced as a behaviour harness collapsing from ~114 passes to ~15.
    - **Companion whitespace trap: `{{- action}}` strips the PRECEDING newline.** When inserting a guard or comment between two YAML documents, use `{{ action}}` with **no leading dash** so the newline that makes `---` a valid separator survives.
    - **Every test path reads the source file DIRECTLY; what the cluster gets is the object the chart template builds by EMBEDDING it.** If only one of several embeds has a body-equality assertion, **a broken embed is invisible to unit tests, every behaviour suite and the linter alike.** Close it with a SHIPPED-ARTIFACT check: render the chart with `--show-only` the embedding template, grep the new content, and diff against the merge-base as the negative control. **Extraction gotcha:** `yq '.spec.pipeline[].input.inline.template'` emits a `null` line per pipeline step lacking an inline template (needs `| select(. != null)`) and adds ONE trailing newline versus the source file — a block-scalar round-trip artifact present on the base branch too, not a diff.
    - **The COMPLETING proof for any such change is a full chart render per target diffed against merge-base — NOT a harness render of the source file.** The behaviour suites, mutation sweeps and schema dry-runs all read the source directly and **none of them observes the embed**. Expect only the affected targets to carry a diff; **that fleet-wide byte-identity IS the scope proof.**
    - **Stacked PRs must SKIP, not `fail()`, on a not-yet-existing sibling file.** Wrap the whole object in `{{- if $body }}`. A hard `fail()` would break the PR's own lint (whose fixture may select exactly the cloud whose file is missing) and, if the earlier PR merged first, **stop the GitOps controller syncing the WHOLE chart**, taking an unrelated live feature down. But note `.Files.Get` returns `""` for a missing path **with no error**, so the UNGUARDED alternative is worse still: an empty inline template renders cleanly and composes **ZERO** resources.
    - **Process note worth the space: a knowledge search SURFACED these as prior art at task start and they were still violated. Surfacing a learning is not applying it — turn the applicable ones into an explicit pre-merge checklist for the file you are touching.**
    - See also: `learnings-code-review.md#36`.

147. **Guard-test coverage for a template-based policy: a MUTATION SWEEP is the only thing that proves the suite non-vacuous, and every rule below was learned by a green suite hiding a hole.** Extends #106. (Example estate: `orgs/<org>/crossplane.md#63`.)
    - **Every `fail()` in the template needs its own expect-failure test.** A happy-path pass is insufficient — **deleting the guard outright would leave the suite green.** Protected-key loops must cover EVERY key **INDIVIDUALLY** (one key per iteration, grepping that key's own name); one over-broad guard test **looks like coverage and is not.**
    - **A test that hand-transcribes a production table into its own table is NOT exhaustive just because its counts and mutant loop are table-driven — every count and mutant reads the TEST table.** A row added to the PRODUCTION table only can ship with no negative control and no assertion while the suite still reports hundreds of passes. **Fix: an explicit PRODUCTION-SOURCE↔TEST-ROSTER PARITY assertion** (set-equality of keys extracted from the template against the test's own roster), or derive the roster from the production table. Mutation-test it BOTH directions. **Counterpoint worth keeping: transcribe the ORACLE table independently of the template** — doing so caught a real defect where two transcriptions disagreed about one row's classification. **Independence for the ORACLE, parity assertion for the ROSTER.**
    - **The mutation-sweep SURVIVOR teaches the rule.** Of nine deliberately injected defects, eight went red. The survivor was substituting sprig `default` for an explicit `if + hasKey` — the two differ on exactly ONE input, an **EMPTY** value, which `default` silently swallows back to the fallback while `hasKey` applies it and then fails loudly. **Every "ASKED FOR, not truthy" rule needs an EMPTY-VALUE case or it is untested.**
    - **Harness pattern:** copy the file aside, apply the mutation with `python str.replace` (or `perl -0pi`) **guarded by an assert that the anchor exists** — a silently missed anchor makes the mutation a no-op and the row a **false green** — run, restore.
    - **Four probes that catch the classic vacuous-assertion bugs, beyond the author's own controls.** (a) **NEEDLE-VACUITY — corrupt the `fail()` message substring the assertions grep for; ALL expect-fail assertions must redden.** Running this moved a suite from all-pass to a large failure count, and **no PR had ever self-run it.** (b) **VALUE-VARIANT** — an explicit `false` must ALSO be rejected, proving `hasKey` semantics ("do not set this") rather than value-aware logic. (c) confirm blocked keys are asserted INDIVIDUALLY. (d) confirm the multi-doc `yq` footgun fix is still present.
    - **Two shell traps that silently disarm the suite itself.** `bash [[ "a" == "b" ]]` with a **QUOTED** rhs is literal; an **UNQUOTED** rhs **pattern-matches** (the same trap as `yq`'s `==` glob). And **self-check the failure detector before trusting it** by grepping stderr for a substring that appears in no error message. Also: **a "the negative control reddens with N failures" claim must be DECOMPOSED** — mutation self-abort guards cascade and inflate N.
    - **A shared `fail()` message must describe every case it can fire on.** A message saying "destructive or permission-granting" while several of the rows it guards are data-movement or invariant-disarming is **a false assertion shipped to clusters** (per #146, these messages are payload).

148. **Three Kyverno plumbing facts and one guard-design principle.** (Example estate: `orgs/<org>/crossplane.md#64`.)
    - **A default-off policy renders NOWHERE in your lint gates unless the CI values fixture enables it.** Where the lint workflow auto-detects a fixture by exact filename and feeds it to `helm template` + `helm lint` + the policy linter, a policy left disabled there is entirely unlinted.

Test it by rendering each overlay **TWICE** — natively, and with the env forced — asserting the prod-only policy is **ABSENT in pass 1 and PRESENT in pass 2**. **Both directions matter: pass 2 alone lets an env gate widened to every tier through; pass 1 alone reports a working gate as broken.** Do NOT template-`fail()` on enabled-but-non-prod if your guard force-enables every policy key — that breaks the render on every overlay.
    - **THE PRINCIPLE: a guard keyed on the overlay's DECLARED env scales; a guard keyed on a hardcoded cluster list does not.** The two-pass shape above quietly encodes "no overlay is natively prod", and **the first natively-prod overlay then makes the guard REJECT A CORRECT PR.** Fix by deriving the native expectation from each overlay's own declared env (`native_expected = base | (prod_only if env == 'prod' else {})`) — the other direction stays asserted by every non-prod overlay, so no coverage is lost, and the **second** natively-prod overlay then needs no guard change at all. **A guard that must be edited each time the fleet grows is a defect in the guard.**
    - **The `request` variable IS available during BACKGROUND SCAN, not just admission** — do not flag `request.kind.kind` / `request.kind.group` in a `ValidatingPolicy` expression as a background-scan hazard. Live-proven by hundreds of `pass` results in namespaced policy reports for a policy whose whole expression is built on it.
    - **`kyverno apply --context-file <f>` makes `resource.List`-based CEL `ValidatingPolicies` TESTABLE OFFLINE** — a claim that cross-resource lookups can carry no offline test is true only of `GlobalContextEntry`, which the CLI cannot load. Context shape: `apiVersion: cli.kyverno.io/v1alpha1`, `kind: Context`, `spec.resources = [<the objects resource.List should return>]`. **Also required: `--crd-path` pointing at a SINGLE concatenated `.yaml` file — a DIRECTORY is rejected with `CRD file must have .yaml or .yml extension`** — because kyverno must map every GVK in the resource file to a GVR, **including kinds the policy does NOT match.** Pull the CRDs read-only from a dev cluster.

149. **A Kyverno CEL gate that asserts the PRESENCE of sibling resources a Crossplane Composition creates alongside the matched object MUST be background-scan-only — `spec.evaluation.admission.enabled=false` + `background.enabled=true` (Kyverno ≥1.17, field on `ValidatingPolicy` v1).** Crossplane applies composed resources in **no guaranteed order**, so at the instant the parent MR is admitted its siblings do not exist: an admission-time presence assertion **rejects every LEGITIMATE create**. 150. **Binding a workload identity to a published reference: bind ALL THREE facts in the CEL, and detect post-write drift with the POLICY ENGINE's own report metric — not a re-derived metrics join.** (Example estate: `orgs/<org>/crossplane.md#65`.)
    - **REF EQUALITY ALONE IS NOT A BINDING.** The policy must assert same NAMESPACE, reference EQUALITY, **and** that the composite's declared consumer name equals the consuming object's name. Without the third, a **DIFFERENT** ServiceAccount can copy a published reference and pass admission even though the generated cloud trust binds only the declared one. Also guard `has(x.status.<field>)`: a status schema that permits the parent object without the child field means **unguarded dyn access evaluates as no-such-key** rather than erroring.
    - **BACKGROUND SCAN ALREADY CLOSES THE "ADMISSION ONLY FIRES ON WRITE" GAP — do NOT build a custom-resource-state join to re-derive the predicate in PromQL.** The reports controller re-evaluates EXISTING objects against the same CEL on its scan interval (proof: a report result carrying `properties.process = "background scan"` with a fresh timestamp on a days-old report), and the report exporter already emits every result as a metric. **The alert can never disagree with the admission gate because it is literally the same CEL.** **Label gotcha: the SUBJECT namespace is `exported_namespace`; plain `namespace` is the exporter's own namespace.**
    - **REFUTED BOT FINDING WORTH RECORDING, BECAUSE IT WILL RECUR.** Two review bots flagged a `count by(...)(A) unless count by(...)(B)` presence alert as false-positive-prone "when an orphaned parent exists with no consumer". Refuted live: the right-hand side has **no `status=` filter**, so it includes `skip` results emitted for **every** object that does NOT match the policy's match condition — hundreds per cluster — so it is essentially never empty while the reporting pipeline is alive, and goes empty only when the pipeline is genuinely dead or the policy is uninstalled, which is the intended detection target. **The bots conflated PER-OBJECT orphaning with PER-CLUSTER RESULT-SET EMPTINESS; `count by` + `unless` is a group-level PRESENCE check, not a value comparison, so ANY surviving result — including `skip` — suppresses the row.** When a bot flags a presence alert, check whether it read it as a value comparison.

151. **Six precision errors that shipped in user-facing docs — each one is a claim a reader will act on, and each has a shape worth recognising.** (Example estate: `orgs/<org>/crossplane.md#66`.)
    - **A CLOUD-ASYMMETRIC match, stated symmetrically.** A policy that matches a bare name prefix on one cloud and a substring of a full ARN on the other cannot be described by one sentence. **Any statement of the form "the policy fires on annotations starting with X" is one-cloud shorthand and wrong for the other.**
    - **ENFORCEMENT SCOPE, stated too broadly.** If `Deny` is scoped to ONE policy while its siblings remain `Audit`, never write "the policies run at Deny." And where the gate matches CREATE+UPDATE, enforcement is at **write time** — a pre-existing bad value is **NOT retroactively denied.**
    - **ADMISSION vs READINESS, conflated.** A gate can check only that a reference is PUBLISHED, not that the composite is Ready or that the cloud resource exists — and where the template writes that reference deterministically on every render, **a matching reference can pass admission before the cloud identity is usable.** Reserve "silent 403 later" for that post-admission readiness class, and tell users to check the composite's own `Ready` condition (#194).
    - **A CLOUD-AGNOSTIC restart claim repeated in THREE places, one of them self-contradictory.** The same document that stated an unconditional "restart required" also, hundreds of lines later, correctly described the other cloud re-resolving live. **LESSON: when correcting a factual claim in docs, GREP THE WHOLE REPO for the claim before declaring done — a single-site fix leaves the contradiction intact elsewhere and reads as deliberate.** (Truth is #93/#114/#168: changing permissions inside an already-assumed role needs no restart on either cloud; changing WHICH identity is restart-gated on EKS and not on GKE — except for long-lived clients that self-pin the account email.)
    - **REVOCATION TIMING IS OPERATION-SPECIFIC and easy to OVER-correct.** Removing a PERMISSION from a role a pod already assumes is evaluated **per request** (no restart, eventually consistent, tens to low hundreds of seconds). That is NOT the same as "takes effect at the next credential refresh", which describes DELETING the role or identity so the next token exchange fails. **Do not collapse the two.**
    - **A ROTATION INSTRUCTION THAT CONTRADICTS THE SYNC POLICY.** Docs saying a renamed object *"leaves the old one until you remove it"* are wrong wherever the GitOps Application hardcodes `prune: true` — renaming in one commit **DELETES the old object on the same sync that creates the new one, with no cutover guarantee.** **Short docs must POINT at the authoritative section, never restate a simplified version of a safety-critical sequence.**

152. **Provider-family (or any per-target dependency) enablement in a wrapper chart: the default values map is NOT inert documentation, the render guards check less than you think, and the invariant that matters is proven at RUNTIME.** (Example estate: `orgs/<org>/crossplane.md#67`.)
    - **AN ENTRY IN THE DEFAULT `values.yaml` MAP DEEP-MERGES INTO EVERY TARGET WITH THAT CLOUD ENABLED — and since per-target files carry digests only for the entries they name, a default-map entry installs UNPINNED (`:version` tag) FLEET-WIDE.** Enablement is per-target BY DESIGN. **Never stage a rollout by uncommenting a default stub; keep base stubs COMMENTED and add the entry to the target's own values file WITH its digest.** Verify with a full render matrix vs the base branch using `--output-dir` (not cached stdout).
    - **RENDER-GUARD BOUNDARY — know what the templates do NOT check.** Guards that reject only EMPTY identity values still accept non-empty **WHITESPACE**, which renders an unusable annotation; they accept **arbitrary digest text**; they allow the `:version` fallback when a digest is absent; and **they cannot enforce digest-to-version alignment at all.** Use mutation controls for each of those four: whitespace identity, a nonexistent/wrong-package digest, tag fallback, and an older-version digest.
    - **`crane digest <pkg>:<tag>` is the digest-to-version proof, and `helm template` CANNOT substitute for it.** Where a chart pins by **immutable digest per target** while a separate value pins the ecosystem VERSION, a promoted digest that does not resolve from that version tag **silently violates the one-version-per-cloud invariant, and no render can see it. Run `crane` BEFORE promoting a digest to a new tier.**
    - **"One registry, one version per cloud" is best proven at RUNTIME, not by repo grep.** `kubectl get providers.pkg.crossplane.io` shows the transitive family provider already installed on the target with a TAG. **If the family being promoted resolves to a DIFFERENT version, installing it forces a family-provider upgrade UNDER the already-running providers on that cluster — that CHURN, not the repo values skew, is the actual failure mode the invariant guards.** Check it before approving any promotion.

156. **Four latent bugs in one batch-verification harness, each surfacing only on the batch shape that first violated an assumption — same moral as #59: every failure is either "plausible green" or "confident RED on a correct PR".** (Example estate: `orgs/<org>/crossplane.md#70`.)

157. **Mechanically inserting a block into deeply nested YAML values files: use a PATH-AWARE WALKER with an exactly-one-match assertion, because the DIFFSTAT CANNOT CATCH EITHER FAILURE MODE.** Complements #57. (Example estate: `orgs/<org>/crossplane.md#71`.)
    - **PATH-AWARE INSERTION supersedes anchor arithmetic.** Build a key-path walker over the raw lines (`^(\s*)([A-Za-z0-9_.-]+):`, pop an indent stack, yield full tuple paths), require **exactly one** line whose resolved path equals the target, insert children at indent+2 immediately after it, and **apply bottom-up so earlier line numbers stay valid.** One pass handles duplicate keys at different paths and flat-vs-nested shapes with no special cases.
    - **Then PROVE it, two ways:** YAML-load head, walk to each path and assert `set(new paths in head) − set(in base) == expected`; and assert **head-with-those-keys-deleted == base**, which catches ANY collateral edit.
    - **THE FAILURE THAT LOOKS CLEAN:** a values file can repeat the same camelCase key under two different parents (e.g. under both a components map and a config map), and on some targets the WRONG one comes FIRST. A "take the first match" edit lands the flag where **nothing reads it** — the render is valid, lint is clean, and **zero objects appear.** Same silent-dead-config class as #69, reached by a different route. **This is exactly why "assert exactly one hit" is the right invariant and "take the first match" is the wrong one — taking the first would have silently worked on one of the two charts.**
    - **The SUPERSEDED anchor rule, kept because its failure mode is instructive:** anchoring at the component key's own line number can place the inserted block at the WRONG INDENT immediately above the next sibling — **and it still produces a clean insert-only diffstat with `helm` exiting 0. ALWAYS EYEBALL A `-U3`/`-U4` HUNK BEFORE TRUSTING AN INSERT-ONLY DIFFSTAT.**
    - **NEVER round-trip these files through pyyaml/ruamel to make the edit** — textual insertion keeps the diff insert-only and preserves comment blocks.
    - **Prove each PREREQUISITE key independently inert by ISOLATED DELETION, not by a base-vs-head diff.** For a PR combining prerequisite global keys with feature-enable additions, render HEAD twice — once normally, once against a scratch copy with ONLY that prerequisite key deleted. 168. **A GKE identity cutover kills LONG-LIVED CLIENTS that self-pinned the bound service-account EMAIL at process start, and the authoritative detection channel is the `kube-system/gke-metadata-server` container log — NOT workload logs and NOT cloud audit logs.** This is the correction to #93: "no restart required" means *no restart to GET the new identity*, never *no restart NEEDED*. **On a GKE adopt, pods OLDER than their batch are AT RISK.** (Example estate: `orgs/<org>/crossplane.md#76`.)
    - **MECHANISM (root cause is a client-library defect, not app code — see the google-auth self-pinning entry in `learnings-k8s-sa.md`):** a long-lived client resolves the bound email ONCE at process start and then refreshes tokens against the **EMAIL-SPECIFIC** metadata path `…/instance/service-accounts/<email>/token`. When the ServiceAccount annotation flips, that old-email path stops resolving and **every refresh returns 404/503.** **Whether a service is immune or latent is decided by WHICH AUTH LIBRARY it uses, not by anything in its own source** — so you cannot triage this by reading application code.
    - **THE DETECTION CHANNEL.** `gke-metadata-server` records every token request as `pod:<ns>/<pod>` + the requested path + HTTP status, making it **the only channel that names BOTH the pod and the identity it asked for.** Two queries settle a cutover: **(Q1)** filter on the OLD emails since the merge → every pod still naming a stale identity; **(Q2)** split requests by the **`default` alias** vs an **EMAIL-SPECIFIC** path → **only the email-specific users can be broken**, because `default` auto-follows the annotation and cuts over with zero restart. **`HTTP/404` on an email-specific path IS the unambiguous break signature.**
    - **WHY THE OTHER TWO CHANNELS FAIL, BOTH SILENTLY.** (a) **Cloud audit logs show NOTHING** — a vanished metadata path returns `UNAVAILABLE`/503, never `PERMISSION_DENIED` code=7, **so a clean denial query is NOT evidence of health** (the trap that makes #62/#94's denial greps insufficient on GCP). (b) **`kubectl logs` gives FALSE NEGATIVES** — kubelet rotation discards the failure window, so a grep across every pod can return ZERO. **Always query the cloud log store (or Loki) for anything hours old.**
    - **TIMING RULE — THE BREAK SURFACES UP TO ~1 HOUR AFTER THE MERGE, NOT AT MERGE.** The cached access token stays valid until expiry, then the refresh 404s. **A "clean" check run in the first hour after a batch merge proves NOTHING; re-check at merge+90 min.** A workload restarted AFTER its batch merged is immune (it resolves the new email at startup) — which means **an unrelated deploy can SILENTLY REMOVE A CANARY from the population under test.** Record which pods restarted mid-window.
    - **THE DETECTOR IS THE WORKLOAD'S OWN BACKLOG, NOT POD STATUS.** In the real case a self-rearming timer thread died after its 8th failure and **the queue consumer DIED — while the pod stayed Running / Ready / 0-restarts and kept serving HTTP.** Grade on the queue's own metrics (undelivered count, oldest-unacked age), never on pod status (#170).
    - **REMEDIATION CONFIRMED: a plain `kubectl rollout restart` is SUFFICIENT**, because a fresh client re-resolves via the `default` alias — **a pinned-dead credential object NEVER heals, so a bare application-level retry loop spins uselessly.** **GOTCHA: allow 4–6 MINUTES after pod start before judging the drain** — acks lag the pod by minutes and the monitoring series lags another 1–2, so a check at T+3 min falsely reads "still stalled". Longer-term, add a pull-thread liveness signal (a last-successful-pull timestamp gauge) to readiness, **or the next occurrence is equally invisible.**

171. **Operational mechanics for a deliberate recycle wave, plus the FOUR log-noise classes that look like cutover breakage and are NOT.** (Example estate: `orgs/<org>/crossplane.md#78`.)
    - **Check `kubectl.kubernetes.io/restartedAt` on the workload AND the cluster audit log BEFORE acting on a restart instruction.** A workload already restarted by someone else needs nothing, and a second recycle changes nothing about identity resolution. **Dispatch prompts go stale against live state within MINUTES on an actively-worked cluster — re-read state, do not replay the instruction.**
    - **Sequence large deployments LAST and check scheduler headroom first.** A multi-replica service can hit `FailedScheduling` `Insufficient cpu` on its first surge pod and need an autoscaler scale-up — minutes per pod versus seconds for single-replica services.
    - **On-pod identity proof tooling: many images ship NEITHER `curl` NOR `wget`.** Some carry only `python3` (use `python3 urllib` against the metadata server); some have `wget` but no `curl`. Check before writing the runbook step. (Extends `learnings-k8s-sa.md#27`, which lists only curl/wget.)
    - **Noise floor for a post-recycle log sweep is essentially 100% false positives on naive patterns.** Anchor on HTTP-status-shaped `403`, `PERMISSION_DENIED`, `IAM_PERMISSION_DENIED`, `caller does not have`, `metadata.google.internal`, `service-accounts/`, `DefaultCredentialsError`, `RetryError`, `UNAVAILABLE` — and see #62 for why a bare `403` grep is worthless.
    - **FOUR pre-classifiable noise classes worth recognising by shape.** **(1) A one-time client-library WARNING burst seconds after process start** (e.g. a gRPC channel-leak warning with a large stack) whose count stays **STATIC** thereafter. **Proof it is pre-existing must come from the CLOUD LOG STORE, not `kubectl`** — **a "grep the old pod = 0 hits" comparison is VACUOUS, not evidence: a terminated pod's `kubectl logs` are already gone.** **(2) A sidecar credential-startup RACE** — the sidecar fails to reach credentials for ~10 s, exits 1, kubelet restarts it, the second attempt succeeds. Net effect is `restartCount=1` on the SIDECAR while the APP container stays 0, **which reads as a dirty pod if you look only at the number** — and it happens on old- and new-identity pods alike. **(3) End-user OAuth `invalid_grant` floods** present on OLD and NEW pods in the same capture, which makes them a **BUILT-IN control**. **(4) Bare `403` and even `PERMISSION_DENIED` as SUBSTRINGS** — inside UUIDs, timestamps, and even inside a tool DESCRIPTION string logged as a schema delta. **ALWAYS print surrounding context before calling any of these a finding.**
    - **THE GENERAL RULE, and the control that settles class 2 decisively: BEFORE ATTRIBUTING ANY RESTART OR ERROR TO A CUTOVER, RUN THE SAME PATTERN QUERY BOUNDED TO BEFORE THE FIRST MERGE.** Verify-by shape: `gcloud logging read '<selectors> AND "<pattern>" AND timestamp<"<first-merge>"'`. Finding the same pattern on the same service weeks earlier ends the discussion.

172. **GCP Data Access audit logging is OFF by default, so a "zero denials in the audit log" result is HALF-VACUOUS and must NEVER be reported as a clean negative on its own — and the denial detector must be the CLOUD-SIDE log, not container logs.** (Example estate: `orgs/<org>/crossplane.md#79`.)
    - **The detector:** `gcloud logging read 'protoPayload.authorizationInfo.granted=false AND protoPayload.authenticationInfo.principalEmail=~"^<prefix>"' --project <p> --freshness=1d`. **Grepping pod logs for `PermissionDenied` is CASE-SENSITIVE and misses `PERMISSION_DENIED`, the uppercase gRPC status name Google client libraries emit** — and it fires only if the app logs the error at all.
    - **KNOW WHICH SERVICES ARE ACTUALLY LOGGED.** A project can have **no `auditConfigs` key at all**, meaning Data Access logging is off for **every** service — or have entries for several services but **not** for object storage, so storage denials are unlogged. In either case a `granted=false` query **CANNOT see object-storage, secret-access, or any other data-access denial.** What remains visible is the always-on Admin Activity stream (bucket-level admin ops and object metadata updates). Retention differs sharply between the two streams (400 d vs 30 d) — check before assuming a historical query is even possible.
    - **VACUITY CONTROLS THAT DO PASS SHOULD BE REPORTED ALONGSIDE THE ZERO, so a reader can tell a SOUND QUERY from a DARK CHANNEL.** Run the same principal filter WITHOUT the denial predicate (expect many rows) and the denial predicate ALONE (expect many rows). **The query shape is then demonstrably sound and the LOG COVERAGE is the stated limit.**
    - **BEFORE BLOCKING ON A PERMISSION LOSS, GROUND ITS SEVERITY IN AUDIT LOGS — a real grant can be DORMANT.** Query the old principal's activity against the affected service over the retention window, **and run the same query shape against a KNOWN-ACTIVE principal as a falsifiability control — without it, an empty result is indistinguishable from a broken query.** Also check denials from the NEW principals, and whether the rendered configuration even references a resource in the affected scope. **Report the loss as blocking but attach the dormancy evidence so the human accepts or fixes on facts.** **Corollary: check whether PRIOR batches already shipped the same loss — blocking batch N alone is inconsistent when N−1 already ships it.**
    - **CONSEQUENCE: pair EVERY audit-log negative with (a) configuration evidence that nothing names a resource in that scope, (b) workload-side log evidence, AND (c) a BEHAVIOURAL detector (queue backlog, error rate).** The one real cutover break in this programme was invisible to BOTH audit logs and pod status and was caught only by queue backlog (#168).

173. **When a local `preview`/`plan` is impossible, the CI preview is NOT a gate on its own, a DECLARED placement can silently disagree with reality, and the best substitute for all of it is an OFFLINE COMPONENT-WALK HARNESS.** (Example estate: `orgs/<org>/crossplane.md#80`.)

174. **GCP deny-policy topology facts that decide whether an exception is even needed — and one silent no-op that makes a correct-looking change do nothing.** (Example estate: `orgs/<org>/crossplane.md#81`.)

178. **The cheapest complete blast-radius proof for a batch is a SHA-256 over the concatenated canonical YAML of every object the batch is NOT supposed to touch — plus a CONTAINMENT render of every UNTOUCHED target.** Sharpens #58's object-keyed diff into two assertions that fit on one line each. (Example estate: `orgs/<org>/crossplane.md#83`.)
    - **For a values-only migration:** hash every object OUTSIDE the two kinds you expect to change and require byte-identical base↔head. Paired with (a) object key SETS equal, (b) exactly N changed objects all of the expected kind, and (c) the changed set equalling the target set, that proves "exactly the N intended changed and nothing else" in one pass. **For a creation batch:** hash the rendered stream with the new kind FILTERED OUT and require byte-identical, then count the new kind separately and assert the DELTA.

    - **CONTAINMENT is the strongest check and the one most PR bodies omit: render base-vs-head for every target the bundle is enabled on but the batch does NOT touch, and assert byte-identical — INCLUDING PRODUCTION. MUTATE AN EXISTING LINE INSTEAD.**

Providers Installed/Healthy on pinned digests, schemas Established and cloud gating correct **still means the controller has never performed a single write.** **A Healthy provider pod proves AUTHENTICATION, never AUTHORIZATION** (#4's failure mode: providers went Healthy while unable to authenticate to cloud, visible only on reconcile). **Corollary for any staged enablement: state explicitly in the PR body which gates are "config landed and applied" versus "behaviour observed"** (#113).

188. **EXAMPLE OWNER-APPROVED PRIORITY (2026-08-11) for an XRole adoption campaign: the ONE thing that must hold when flipping a workload to its XRole identity is NO PERMISSION LOSS. 189. **A written "must hold" rule that every PR violates TRAINS REVIEWERS TO IGNORE THE DOCUMENT — resolve it, do not keep merging past it.** Where git history shows the reference environment did the OPPOSITE of a documented sequencing rule and every subsequent PR continues to, there are **two acceptable resolutions and one unacceptable status quo**: bring practice into line with the rule, OR correct the rule to match proven practice. **Until resolved, treat it as a BLOCKING sequencing gap in review unless a reviewed exception explicitly supersedes the document — and say which, in the PR body.** Method note from the same review: where a policy renders in `Audit` on the targets under test and `Deny` on the reference targets, **the reference targets' `Deny` render is the DISCRIMINATION CONTROL that proves the check is alive** — without it, "everything renders Audit" is indistinguishable from a check that reads nothing. 190. **"Gains access, nothing can be lost" is a PARITY argument (is it safe?) and does NOT answer the NECESSITY question (is it warranted?) — a mint scope built from "has a mintable ServiceAccount" silently admits workloads that need no cloud identity at all.** (test-tier mint 210 → 207, batch 6 33 → 30.) `pipeline-smoke-test` was descoped: a synthetic smoke-test CronJob that had run every 15 min for 42 days on all three test clusters with **no identity annotation and zero failed jobs**, whose only egress is in-cluster HTTP. Minting would **EXPAND its privilege surface — the opposite of the project's goal** — and the `[standard, elevated]` in its `values.yaml` is reference-chart boilerplate, not a decision made for that workload. **Check both questions before putting a workload in scope.**

191. **Two `aws iam simulate-custom-policy` invocation traps that both LOOK like policy bugs and are not.** (TICKET-NN, infra-terraform #NNNN; the simulator's role as the right negative-control tool is **#113**.)
    - **`--policy-input-list` does NOT accept `file://`** — the CLI parses the file as the LIST itself and fails with `Policy input list item 1 has invalid content`. Pass the policy inline: `--policy-input-list "$(cat policy.min.json)"`.

192. **Parity-review REPORTING discipline: a permission-parity harness must report token counts and wildcard-EXPANDED counts separately, and must tag effective-deny as UNVERIFIED rather than passing an allow-union off as authorization.** (Evidence: adopt batch 5.) Extends **#118** with what the *output* has to say.
    - **AWS — two representations, one conclusion, and you must publish both.** The advertised "241 old / 48 new" figures are **unique live IAM Action TOKENS** after inline+attached union and boundary filtering — **not** concrete wildcard-expanded API actions. Expanding the globs with case-insensitive `fnmatch` against the official AWS Policy Generator catalog (plus four literal live-policy tokens absent from that catalog) gives **792 old / 3896 new**. Both representations yield exactly one loss, `secretsmanager:ListSecrets` — which is the point: agreement across representations is the evidence, and a reader given only "241 vs 48" reasonably concludes the new identity is 5× smaller. Harness contract: **union inline+attached, intersect boundaries, subtract denies, and HARD-FAIL on an empty principal** (#118).
    - **GCP — a successful allow-policy search does NOT enumerate IAM v2 DenyPolicies, so it is structurally incapable of answering "effective access".** On #NNNN, project and parent-folder DenyPolicy lists were readable and **empty**, but **organization `denypolicies.list` was DENIED**, and Policy Troubleshooter could not close the gap because **its API was disabled**. (#113 and #117 already say "say UNVERIFIED"; the addition here is the *mechanism* — org-wide Cloud Asset search plus direct allow-policy reads are the wrong instrument class entirely, so a green result from them is not even weak evidence.)

193. **The sharpest edge in the "merging any PR into an apply-on-merge IaC repo sweeps the whole plan" class (#91) is a VALUE-UNCHANGED diff with a LIVE BEHAVIOURAL CONSEQUENCE.** A database parameter whose `apply_method` flips `pending-reboot` → `immediate` while its **value stays the same** is such a diff: if the setting was only STAGED as pending-reboot and the cluster has not rebooted, re-applying it as `immediate` **starts enforcing it immediately** — for a TLS-enforcement parameter, on live connections. Nothing in the value column shows this. **METHOD REMINDER THAT SURFACES IT: an ADDITIVE diff reporting `Plan: 0 to add, 2 to change` has exactly ONE change of its own and ONE drift. Always pull the `~` blocks — the summary line cannot distinguish them.** **Confirm with the stack owner before merging anything into an affected stack**, and note that such drift can sit pending for weeks with nobody reconciling it. (Example estate: `orgs/<org>/crossplane.md#87`.)

194. **A Composition's `function-go-templating` STATUS-ONLY document is written into the desired composite status BEFORE `function-auto-ready` evaluates composed resources — so the presence of a derived status field does NOT prove the XR or the cloud resource is Ready.** Reproduced with `function-go-templating` **v0.9.2** + `function-auto-ready` **v0.7.0** and Kyverno CLI fixtures: XRoles with `Ready=False` and with **no condition at all** both PASSED a policy that matched on `status.identity.ref`. **Any admission policy that requires readiness must inspect a `Ready=True` CONDITION explicitly** — never a derived status field's existence. This is the pipeline-ordering MECHANISM behind **#151**'s "admission vs readiness, conflated" bullet, and the constraint that bounds the status-write path documented at **#154**. Read with **#110** (the minted identity publishes no machine-readable source) and `learnings-operators.md#29` (`Established=True` is health, not freshness).

195. **`mergeOverwrite` pins TOP-LEVEL fields only — NESTED fields under a composed MR are not reached, so a claim can still aim replication at a cross-account bucket.** Extends **#127**, which covers the base resource's own `forProvider` leaves; this is the level below. On the S3 MRs, `bucket` and `region` are pinned, but `replicationConfiguration.rule[].destination.bucket` is **not** reached by `mergeOverwrite`. **The correct fix is `block sensitive` in the ROUTING TABLE, not trying to scrub nested fields** — a scrubber has to enumerate an open-ended tree and will drift the moment the provider adds a field, whereas a routing-table block refuses the whole key. (This settles the `replicationConfiguration` line of **#132**'s "should also be constrainable" list the other way: the risky value is nested inside a list element, not one reachable top-level field.)

196. **S3 Public Access Block does NOT block ACL grants to a specific cross-account CANONICAL ID — AWS defines "public" as `AllUsers` or `AuthenticatedUsers` only.** `blockPublicAcls` / `ignorePublicAcls` therefore leave a `BucketACL` grant to a named canonical ID **entirely unblocked**, which is a cross-account data-egress path that reads as covered on any PAB-based audit. **`BucketOwnerEnforced` (via `BucketOwnershipControls`) removes the ACL grant path altogether and is what actually closes this gap.** Treat "PAB is on" as insufficient evidence for any "no cross-account access" claim. (The ACL-grant primitive itself, and the `logging.targetGrant[]` path that reaches it sideways, are **#134**.)

197. **Ground any "which clusters/environments run chart X" claim in the DEPLOYMENT CONFIG — not the chart README, and not in which overlays a policy happens to be enabled on.** A stale "this chart is deployed nowhere else" sentence in a README survived a full doubling of the deployment footprint and was then repeated verbatim in a PR's own Multi-Cluster Impact justification. **The general shape: a stale README claim survives because NO GATE READS PROSE.** Note the counterpart — the automated guard in that repo already iterated every overlay, so the *guard* was never fooled; only the prose was. When a doc and a guard disagree about scope, the guard is the fact, and the doc is the defect. (Example estate: `orgs/<org>/crossplane.md#39`.)

198. **Setting EVERY subordinate MR of a composite to `managementPolicies: ['*']` means deleting the claim STRIPS PLATFORM INVARIANTS from the resource you deliberately retained.** For an XBucket whose top-level bucket MR retains on delete, giving the SSE-KMS, versioning and public-access-block MRs full management means claim deletion **removes SSE-KMS, suspends versioning, and drops PAB from the retained bucket** — it survives, but unencrypted, unversioned and publicly reachable. The design rationale that produced this ("a retained grant outlives the claim") is sound for ACL/policy/CORS-shaped resources, where an orphaned grant is the hazard; it inverts for **platform invariants**, where the orphaned state is the hazard. **Classify each subordinate MR as grant-shaped or invariant-shaped and give the invariant-shaped ones env-derived policies, not a blanket `['*']`.** (Example estate and the exact call site: `orgs/<org>/crossplane.md#90`.)

199. **A client that caches a cloud identity's EMAIL degrades to IMPERSONATION rather than a hard failure when that identity is repointed — so a stale binding is invisible to every parity check.** GCS V4 signed URLs go through `iamcredentials.signBlob`, which takes the service account as an **API parameter, not a URL path**: a process holding the old shared principal's email keeps signing successfully *as that principal* long after its own workload identity was cut over. Symptoms you will NOT see: 404, 403, or any parity-check delta between declared and actual bindings. Detection is a log query on `iamcredentials` `SignBlob` rows grouped by the *signing* principal's `uniqueId` — and the query needs a **pre-change control window** to prove a zero is a real zero and not a broken query. The fix is a pod recycle, not a config change. Consequence for revocation sequencing: **you cannot revoke a shared principal on the strength of the cutover having merged** — only on the strength of that log going to zero.

200. **A KMS key path that gets the PROJECT segment wrong can still RESOLVE, render green, and encrypt against the wrong project's key — verifying the key NAME is not sufficient.** Two sibling projects held keyrings/keys with **identical names**, so a path built by copying a sibling's config and editing only the cluster token pointed at a real, enabled, `ENCRYPT_DECRYPT` key in the wrong project. Nothing errors. **Verify the project segment independently** (`gcloud kms keyrings list --project <p>`) rather than validating the path as a string. Duplicate key names across sibling projects are usually a bootstrap artifact and should be treated as a standing trap wherever a naming convention gained a suffix mid-life. (Example estate: `orgs/<org>/crossplane.md#105`.)

201. **Bucket teardown fails DIFFERENTLY on the two clouds, and only one of the two failures is fixable by granting a role.** AWS: a `403 AccessDenied` on teardown is an **ARN-LEVEL split** in the policy, not a missing action — `s3:ListBucketVersions` is **BUCKET-level** (belongs on the bucket ARN alongside `DeleteBucket`/`ListBucket`) while `s3:DeleteObject` and `s3:DeleteObjectVersion` are **OBJECT-level** and need their own statement on `arn:aws:s3:::<prefix>-*/*`; a policy with only bucket-ARN statements looks complete and cannot empty a bucket. GCP: a `403 "due to an IAM deny policy"` on `storage.buckets.delete` is **categorically different** — the principal already holds `roles/storage.admin` and **a deny OVERRIDES the allow, so no role grant fixes it**; the fix is a deny-policy exception, or accepting that the deny is working as intended and the `forceDestroy: true` posture is what is wrong. Before writing either fix, decide which of those two you are looking at — the AWS shape rewards more permissions, the GCP shape punishes chasing them.

202. **The controller-vs-foundation ownership boundary is decided by LIFECYCLE and SHARING, not by resource type — and the tie-break must default to the slower reconciler.** A resource belongs to the **app controller** when it is owned by exactly one application, created and destroyed **with** it, and referenced only by it. It belongs to **foundation IaC** when it is **shared** across apps, part of the **network / security / account perimeter**, or **longer-lived than any single app**. The convention that keeps the two from fighting: **the app controller owns the app-side PRINCIPAL; foundation IaC owns any GRANT on a foundation resource** (which is the same boundary #37 enforces mechanically via ABAC-on-foundation + mint-and-tag). **The tie-break is the load-bearing half: ambiguous → default to foundation, and RAISE it.** Defaulting the other way is what produces two reconcilers on one object, and that failure is not symmetric — a fast controller repeatedly reverting a slow one produces drift that looks like the slow one is broken (see #91 for the apply-on-merge version of the same confusion). Ambiguity resolved silently in favour of the app controller is how the boundary erodes one resource at a time.

203. **In a Composition that fans out an UNORDERED semantic set, key each composed resource by a hash of its semantic identity — never by array index.** Dedup the union first, then key on `hash(project + role + member)` (or whatever tuple actually identifies the item). **An index-based key means any reorder of the input list re-maps every composed resource: the controller sees resource `[3]` change identity and DELETES-then-RECREATES grants that were never meant to change** — destructive churn triggered by a cosmetic edit, on a set whose order carries no meaning. Generalizes to any function-generated fan-out, not just IAM: stable semantic keys are what let the reconciler tell "the set changed" from "the set was rewritten in a different order".

204. **Designing a claim surface: sort every provider setting into exactly FIVE ownership classes, not four — and only give a field a curated name when the name buys safety or policy semantics.** (1) **Derived** — computed by the composition, never supplied by the caller. (2) **Invariant** — absent from the API entirely, because there is one correct value. (3) **Cluster fact** — platform-owned, varies per cluster, the claim must not get to choose. (4) **Claim field** — genuinely varies per instance and the service owner is the one who knows the answer. (5) **Guarded exception** — a dangerous default with a rare legitimate need, admitted through a justification-gated path rather than exposed or forbidden outright (the class most designs omit, which forces every dangerous knob into either "exposed" or "banned"; see #132 for preferring a *constraint* over a *gate* when the risk is confined to a sub-field). **The naming rule that stops an XRD from re-growing the whole provider schema: if a feature is just "set this provider field", it does NOT need a curated cloud-neutral name — pass it through.** A curated name earns its keep only when it adds safety, cross-cloud portability, or policy meaning that the raw field does not carry; otherwise it is a second vocabulary to maintain and a translation layer to get wrong.

205. **Comparing controller vendors (e.g. Crossplane vs a cloud-native config controller vs per-service controllers): the METHOD, which matters more than any dated verdict.** (1) **Pin versions for every candidate** and re-validate the product facts before reusing the comparison — this class of tooling moves fast enough that an unpinned comparison is worthless within a quarter. (2) **State the workload and ownership PREMISE explicitly and up front** — the verdict is premise-dependent, and the premise usually flips it. A comparison written on "we are not building portable abstractions" recommends the thin cloud-native controller; the same evidence under "we ARE building abstractions" recommends the one whose abstraction layer *is* the product. **An unstated premise is how a comparison silently answers a different question than the one asked.** (3) **Anti-laundering: re-test every "production-ready" / "GA" claim against YOUR stack.** Generic maturity is not fit; a GA controller can be excellent and still wrong for your topology. (4) **Evaluate the highest-stakes seam FIRST — deletion / data-loss semantics** — because it is the one that is expensive to discover late and cannot be mitigated by process. (5) Then compare, in this order: drift behaviour · controller topology (one controller vs per-service fleet) · credential blast radius / identity scoping · GitOps integration (health reporting, ordering) · maturity-vs-fit. (6) **Ship the verdict as explicitly premise-conditional**, not as a ranking. The general framework this instantiates — gates, anti-laundering, premise-check — is `references/playbook-tech-adoption.md`.

206. **A cloud API ACCEPTING an encryption/protection configuration is not evidence the configuration WORKS — prove it with an object round-trip that asserts the key actually used, then mutation-test the verifier.** S3 does **not** validate the KMS key at `PutBucketEncryption`, so a wrong or inaccessible key alias is accepted silently and surfaces only on the **first object write**. Therefore **a bucket that merely *reports* the right key proves nothing** — a config readback tests the control plane, not the data plane. The load-bearing check is **write an object → read it back → assert the KMS key ID actually applied → delete every version**. The second half is what makes the result trustworthy: **mutation-test the verifier before believing a green run** — deliberately corrupt a known-good cloud readback (wrong key, disabled protection, absent field) and confirm each corruption is caught; a verifier that has never failed has never been tested (the same non-vacuity principle as #144's derived-CRD diff and the negative controls in `learnings-network-policy.md#38`). Generalizes to any "set-and-report" cloud protection: default encryption, retention/object-lock, public-access blocks, TLS policies — **the API that accepts the setting and the subsystem that enforces it are different services, and only the data path exercises both.**
