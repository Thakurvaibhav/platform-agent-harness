# Coder Devbox & Remote Agent Worker Learnings

See also: `learnings-agent-workflow.md` (dispatching and driving the agent CLIs that run ON these boxes), `learnings-terraform.md` (the IaC that provisions them), `learnings-code-review.md` (reviewing the templates and their guard policies).

Portable behaviour of the Coder platform at a pinned version, plus what a freshly provisioned
devbox does and does not give a remote agent worker. Instance detail (account ids, template
names, profiles) belongs in the org tier, not here.

1. **Coder v2.38.10 autostop defaults: a template created by `coder templates push` has NO autostop at all, which is the opposite of the safe assumption.** `cli/templatepush.go:213` passes NO `DefaultTTLMillis` when it CREATES a template, so `default_ttl = 0` means the workspace never stops until someone runs `coder templates edit --default-ttl`. The activity bump defaults to 1 hour (`coderd/templates.go:300`). The app-status PATCH bumps the deadline on EVERY `working` status and on the FIRST non-working status after a working one (`coderd/agentapi/apps.go` `shouldBump`), which is the mechanism a keepalive relies on. Separately, web-terminal reconnecting PTYs die 5 minutes after the last detach (`agent/reconnectingpty/reconnectingpty.go:126`), so a long job must not live in one.

2. **An app-status keepalive MUST bound its message to 160 bytes, or Coder v2.38.10 rejects it BEFORE the deadline bump and a busy workspace silently autostops.** `coderd/agentapi/apps.go:123` rejects a longer message with HTTP 400, and the activity bump is at line 229, AFTER that check. Proven by a local HTTP contract replay of the keepalive script: exit 0 at 160 bytes, `curl` exit 22 at 161 bytes, on every retry. So a keepalive that joins running process names into its message works until the box is busy enough to produce a long list, which is exactly when it is needed. ✅ Truncate the message. ⚠️ **Testing notes from the same replay, because the obvious stubs hide the bug:** fixed `ps`/`curl` stubs also miss `-U` versus `-u`, a wrong UID, wrong `ps` columns, a wrong method, header or app slug, and a dropped `curl -f`. Assert on the command ARGUMENTS and exercise the HTTP rejection SEPARATELY from the process filtering. Related configuration fact: `coder_agent` `api_key_scope` defaults to `all` (provider v2.20.0 `agent.go:83`) and `CODER_AGENT_TOKEN` is exported into EVERY session environment (`agent/agent.go:1705`).

3. **A load-balancer path-pattern guard in front of Coder v2.38.10 is BYPASSABLE with a repeated slash, and the provisioner runs template Terraform as the server's own UID.** (1) **Slash collapsing happens in the wrong place.** Coder's `singleSlashMW` (`coderd/coderd.go:2618`) collapses `//` before its router, but ALB path matching does NOT collapse slashes, although it DOES percent-decode (so `%66irst` and a single `%2F` were both blocked). Live: `POST /api/v2/users/first` returned ALB 403 while `POST /api/v2/users//first` reached Coder and returned a 400 JSON-decode error, which means the handler was reached. ✅ **Safe probe for this class: POST with a body of `x`, which fails at the request read before any database call**, so the test establishes reachability without creating anything. ✅ The generalisation worth carrying: any WAF or load-balancer path guard in front of an application that normalises paths itself is defeated by whatever normalisation the two do not share. (2) **Built-in provisioners run template Terraform as the SERVER's UID**, so `/proc/1/environ` exposes the database connection URL and the OIDC secret despite the provisioner stripping `CODER_*` from the child environment. A Template Admin, a role assignable in the open-source build, can do this, not only an Owner. That makes Template Admin an effectively privileged role on a single-process deployment.

4. **What a freshly provisioned Coder devbox does and does NOT have, which determines what a remote agent worker can be asked to do.** Measured on one aws-devbox template: the box ships `gh`, `git`, the agent CLIs, docker, a runtime manager, node, and the cloud CLIs, but NO `kubectl`, helm, Terraform, Terragrunt or GitOps CLI, and NO LOGINS (`gh` unauthenticated, no agent config, agent CLIs unauthenticated). ✅ **Git over SSH works out of the box**: the Coder agent sets `GIT_SSH_COMMAND` to its own helper using a per-user key (`coder publickey`), so adding that key to the forge ONCE makes SSH clones work on EVERY workspace. ⚠️ **`GIT_ASKPASS` falls through** when the deployment has no external-auth providers configured, and the forge's API (pull requests, reviews) still needs its own `gh auth login`. ⚠️ **The DEPLOYED template version can be ahead of the repository's default branch** (cloud CLIs installed on the box but absent from the committed cloud-init), so read the deployed template rather than the repository when deciding what is present. First boot to agent-ready took about 2 minutes.

5. **Coder v2.38.10 user secrets are the clean way to authenticate a remote agent worker, with one clipboard trap that produces a baffling 401.** `coder secret create <name> --env VAR` injects into EVERY workspace you own ON NEXT START, so a `coder restart` is required. An agent OAuth token obtained from the CLI's own token command gives a working headless run with NOTHING written to the agent's config directory, and a forge token makes the CLI work with no hosts file on disk. ⚠️ **A fine-grained personal access token pending organisation approval AUTHENTICATES (a whoami call works) while every organisation repository returns 404**, which reads as a permissions bug rather than a pending approval. ⚠️ **Copying a `pbpaste | ...` command out of a chat OVERWRITES the clipboard, so the secret becomes the command text** and the resulting 401 looks like a bad token. ✅ Check the stored value's LENGTH and PREFIX on the box without printing it.

6. **A cloud-init `runcmd` string list renders as a plain `/bin/sh` script, so a final successful `systemctl enable --now` HIDES every earlier failure and the instance comes up looking healthy.** Replaying one devbox bootstrap with a download failing (exit 22) and a package install failing (exit 1) still returned 0 and still started the agent. **A download piped straight into a shell also masks the download's exit code without `pipefail`.** ✅ Gate agent startup on a successful FAIL-FAST bootstrap, use checked downloads with bounded retries, and treat 'the agent is up' as evidence of nothing but the agent. ⚠️ Scope note: this was a shell-level reproduction of the rendered script, not a live boot, which is enough to establish the exit-code semantics and not enough to claim the live sequence is identical.
