# Learnings: Code Review

Patterns, gotchas, and best practices for PR review workflows.

See also: `learnings-progressive-delivery.md`, `learnings-agent-workflow.md`, `learnings-confluence.md`, `learnings-envoy-gateway.md`, `learnings-coder.md` (reviewing devbox templates and their guard policies), `learnings-llm-runtime.md` (grading a finding about key handling or a swallowed provider error)

## Entries

1. **Known review bots post asynchronously.** Wait for bot reviews (CodeRabbit, Cursor Bugbot) before starting your own pass — they may take several minutes. Poll with a timeout rather than blocking indefinitely.

2. **Reply to every bot finding explicitly.** Silent ignoring creates ambiguity for human reviewers. Classify each finding as fixed, acknowledged, disagreed, or out-of-scope.

3. **Bot false positives are common for YAML-only PRs.** Security scanners and code-quality bots may flag values files, namespace labels, or config-only changes that have no real risk. Document these patterns so future reviewers don't waste time re-evaluating.
    - **hackerone-code[bot] posts only a scanning comment on YAML-only PRs**: YAML values files with no secrets/code produce only the initial "Scanning for security risks..." comment and nothing else. No findings follow. Do not wait beyond the initial comment for YAML-only PRs.
    - **CodeRabbit false positive: portLevelMtls not service-bound**: CodeRabbit flags port 9901 as "not service-bound" in PeerAuthentication. In Istio ambient mode, portLevelMtls applies at pod level (ztunnel), NOT Service level. GKE NEG probes reach pod IP:port directly. Port does NOT need Service.spec.ports exposure.
    - **A bot recommending "standard" labels/annotations on chart-managed resources is a false positive wherever the repo has a deliberate contrary convention.** CodeRabbit will recommend `app.kubernetes.io/*` labels on Namespace resources regardless of house style. **Refute with the existing POPULATION plus the defining site** — cite sibling charts that omit them and the place the convention is documented — rather than arguing style. Same counter-evidence shape as the per-occurrence-documentation nitpick in #19.
    - **Cursor Bugbot false positive: split-PR missing components**: When Istio uses split control/data plane PRs (istioBase+istiod in PR A, istioCni+istioZtunnel in PR B), Bugbot flags PR B as "Missing control plane components" (HIGH severity). Reply with companion PR reference.
    - **CodeRabbit cross-cluster false positive: pre-existing divergence flagged as regression**: CodeRabbit compares cluster files CROSS-cluster (e.g. "<cluster> has these MCP routes, AWS/GCP dev don't") rather than per-cluster BEFORE/AFTER, so it flags a pre-existing cluster divergence as a regression introduced by the PR. Refute with a union-hash / per-cluster before-after proof: routes absent before the PR stay absent after.
    - **Verify EVERY bot finding against the live file before classifying fixed-vs-disagree — bots mis-scope in two recurring ways**: (a) **Re-flags an intentionally-removed matcher**: Cursor BugBot flags a deliberately-dropped label matcher (e.g. `cluster!="<cluster>"`) as a "missing filter" bug. Refute vs `origin/<base>`: if pre-existing alerts KEEP the matcher (count unchanged) and only NEW alerts omit it, and the metric doesn't exist on the excluded cluster, it's a false-positive-in-context → Disagree. (b) **Code-fence misparse**: when a code fence has NO language specifier, CodeRabbit may misparse surrounding context and report selectors as absent even when they're present in the same block (e.g. claimed ratio queries omitted `reporter=waypoint` when they had it). Always diff the bot's claim against actual file content. (Also: CodeRabbit reviews the intermediate commit SHA when a PR was force-stripped to a smaller scope — check its "Reviewing files that changed between `<base>` and `<SHA>`" header against current HEAD, cf. #6.)
    - **CodeRabbit evaluates a host-cluster Helm values file IN ISOLATION (layer 5 only), never through the full 5-layer ArgoCD value stack.** Findings of the shape "`global.provider` missing in `<cluster>.yaml`" are false positives when the value is set at `providers/aws.yaml` (layer 2). Always re-resolve a CodeRabbit Helm finding against the whole stack before accepting it. Same family as #3 (cross-cluster comparison) and #3 (bot mis-scoping).

4. **CI check context matters.** A passing CI run on a values-only PR may not exercise the actual Helm rendering. Verify with `helm template` locally when CI only runs linting.
    - **A layered-audit / polaris job can carry a PERMANENT known failure for one chart without failing CI — know which, and know why it is not actionable.** Polaris uses **exit code 1 = warning, 2 = danger**, so a chart whose dependencies the workflow cannot resolve fails the job while CI still passes. Do not spend a review cycle on it, and do not treat it as evidence about the PR. Distinct from a TRANSIENT early-run artifact (#4).
    - **Polaris Layered Audit "helm template failed" comment can be a TRANSIENT early-run artifact** — verify the actual state via `gh pr checks` (the check may be green on re-run), not the posted comment. A PR touching only `observability/*.yaml` + runbooks + dashboard artifacts does NOT affect `helm template charts/<chart>` (the layered audit templates the chart dir, not the SO values), so it CANNOT cause that chart's render failure — the comment is noise. (Distinct from #4, which is the echo-server PERMANENT failure.)
    - **A render/lint CI job on alerting rules can be SHAPE-ONLY — it proves the YAML renders, not that the expressions are valid, and it will pass a query the live TSDB rejects at execution.** Measured adversarially: identity mutations to **names, groups, metrics, labels, `by()` clauses, operators, joins, durations, severities and annotations ALL PASSED** a render check — **including a join the live TSDB refused to execute.** So a green render check is not arming evidence for an alert rule. **The complementary proof that IS load-bearing: render every expression and LIVE-QUERY it against the datasource, then state what currently arms it.** **Two adjacent review findings, both a class worth checking on any alert PR:** a runbook prescribing a rollback at the wrong SCOPE (e.g. removing service labels when the enrolment/rollback is namespace-scoped), and **a PR body left stale after the head changed thresholds** — re-read the body against the final head before approving.

5. **Cap fix iterations at 2.** After two rounds of fixes, document remaining issues and hand off to a human. Unbounded iteration loops waste tokens and rarely converge on non-trivial disagreements.

6. **A bot can be "done" without a new comment.** Some reviewers (e.g. CodeRabbit) update their existing "review in progress" comment in place — the comment count never increments and the reviews list stays empty; detect completion by a marker in the comment **body**. Cursor Bugbot's authoritative commit is its footer (`Reviewed … for commit <SHA>`), not the visible `diff_hunk` — if that SHA is not current `HEAD`, it scanned a stale commit and its findings may already be fixed. Verify against `HEAD` before acting.
    - **CodeRabbit CHILL completion on Terraform-only changes:** it can embed the walkthrough into its existing progress comment, leave `reviews[]` empty and post zero inline comments. Look for `walkthrough_start`. **GitHub carries open bot threads forward:** even `commit_id=HEAD` and a non-null `line` can accompany a historical `diff_hunk`; read the bot's footer SHA and the actual file at HEAD, then render with a negative control. Bugbot does not auto-resolve and only re-scans on a new push. CodeRabbit can leave old inline findings after a substantial redesign; reply with the fixing SHA and explicitly resolve. The bot's learned rule can itself be stale despite a current footer (#94).

7. **Reply *and* resolve.** A threaded reply alone leaves a bot finding open. Drive each to resolved — a bot resolve command (`@coderabbitai resolve`) or the host's `resolveReviewThread` GraphQL mutation for bots that do not self-resolve. Only resolve a thread you actually addressed (fixed / disagreed-with-reason / acknowledged). Target zero open bot threads at hand-off.

8. **Rendered proof beats source-diff reading.** For Helm/values PRs, render the chart at the `git merge-base` and at `HEAD`, then diff the *manifests* — a values change can be inert (disabled component, wrong key, deep-merge override) or blast wider than the source implies. Always include a **negative control** (an untouched template in the same chart whose rendered diff must be empty) to prove the render harness actually surfaces changes. Source changed but rendered diff empty = a blocking finding, not a pass.
    - **Render with ALL value files in the stack — a base `values.yaml` render alone can silently show a feature DISABLED.** In a layered GitOps repo the base `values.yaml` often sets a feature `false` and a higher layer overrides it to `true`. A single-file render therefore shows none of the feature's objects and no changed args, and the change **looks inert when it is not**. Always render the full stack in the same order the GitOps controller applies it. Second half, equally common: a template gating on `and .Values.x.enabled .Values.x.create` needs **BOTH** true — check every conjunct, not the one you changed.
    - **The strongest negative control for a chart that cannot render standalone is an UNTOUCHED TEMPLATE INSIDE THE SAME CHART — not a different chart. And docs-only PRs still earn an R1 proof.** (a) For a chart needing `helm dep build`, render both the changed and an untouched template **through the same harness**: on `charts/<composition-chart>`, `role-aws`/`role-gcp` Compositions must be **byte-identical** base→head while `bucket-aws`/`bucket-gcp` **differ**. That pins both failure modes at once — a spurious-diff harness AND an inert change — with no extra dep-build cost. (b) **Docs-only PRs deserve the same proof and it is cheap**: render the chart at HEAD and at a merge-base worktree for EVERY host-cluster overlay and byte-diff. TICKET-NN (PR #NNNN) proved *zero rendered change* across all 6 `<composition-chart>` clusters this way, with a negative control (the base render is non-empty — 13 objects) so the green diff is not vacuous. **This converts "docs-only, nothing to test" from an assertion into evidence — and it catches the real hazard, which is that a new subdirectory under `charts/<name>/` is NOT inert by default: it is PACKAGED unless `.helmignore` excludes it, and adding it to `.helmignore` would itself break the docs-only constraint.** Also: the PR template's *Tests & Validation* must say `rendered manifests: not applicable (docs-only)` EXPLICITLY rather than being left blank. Anchors at the merge-base per #10; tiering per #15.
    - **Three render-proof false greens, all of which pass `diff -q` while proving nothing.** Extends the merge-base anchoring of #10/#82.
    - **A "pre-existing error" claim needs a real merge-base WORKTREE.** Comparing `helm lint HEAD` against `helm lint HEAD` proves nothing: `git worktree add --detach /tmp/x $(git merge-base HEAD origin/<base>)` and lint there.
    - **A byte-identity render diff between two throwaway harness charts ALWAYS differs**, because helm stamps `# Source: <chartname>/templates/…` into every document — so a naive `diff -q` "proves" a difference that is only the chart name. Strip the `# Source:` lines, **and add a negative control asserting the CHANGED case really does differ**, or `diff -q` passes on a comparison that detects nothing.
    - **A recorded merge-base goes STALE the moment the branch merges a newer main**, and the PR-body render proof then becomes internally impossible even when the feature diff is still correct. Recompute `git merge-base origin/<base> HEAD` and rerun the full Argo value stack: on TICKET-NN batch 4 the stale `<commit-sha>` baseline added `Deployment/<workload>` differences through `charts/<application>/release.yaml`, while the true `<commit-sha>` merge-base isolated exactly the 12 intended ServiceAccounts per cluster.
    - Companion, already known but hit again: `helm dep build` on an umbrella sweeps `charts/<application>/Chart.lock` (untracked on main) into the branch — check `git diff --stat` against `origin/<base>` before pushing (`learnings-agent-workflow.md`).

9. **Cross-model verify high-blast findings.** On sensitive PRs (RBAC, secrets, production manifests), do not assert a blocking finding — or a clean verdict — on one model's judgment. Dispatch a different model/runtime to *refute* each blocking finding (default-to-refuted); keep only what survives, and surface splits to the human rather than silently picking a side.

10. **Anchor behavior-preservation proofs at the `git merge-base`, not the immediate parent.** With multiple commits, the parent only proves the last commit is conservative; earlier commits in the PR may have widened scope. `git merge-base origin/<base> <tip>` is the true baseline for render-diff and before/after proofs.
    - Resolve the actual PR base before computing the merge base; see #108. The immediate-parent and moving-branch-tip comparisons answer different questions.

## Entries (continued)

11. **Every automated gate you run is a correctness gate; none of them is a minimality gate, so unnecessary complexity is invisible to the entire review stack.** Render/lint checks, a policy-conformance scanner, a server-side dry-run, and even a two-model adversarial review can all go green identically on a needlessly duplicated implementation and on its much shorter equivalent — a change that duplicates a template four times over can pass every gate while a same-day human rewrite cuts most of its line count. This is not a knowledge gap: reviewers (human and model) can independently state a simplicity rule and still fail to apply it to their own output, because an agent that just wrote 900 lines will self-certify as simple. The fix that actually lands is a checkable counting rule added to the review checklist — flag near-duplicate blocks above a similarity threshold, redundant guards on one field, unreachable branches, values/config keys derivable from other values — not more prose asking for simplicity. A missing gate wants a gate, not another paragraph of guidance.
    - A concrete review threshold is **>70% template similarity**. In one measured case both lenses passed a four-knob version; a human produced a one-knob rewrite that removed 78 lines. Four of ten findings were already documented rules, so additional prose alone would not have prevented them.

12. **Never use `git diff <default-branch> --stat` as a PR's blast-radius check — the branch tip moves while you are still working.** Any fetch or remote refresh mid-task can advance the ref, so the diff silently compares against unrelated commits that landed in the meantime and can report hundreds of unrelated files changed for what is really a two-line PR. The authoritative alternatives compute the true merge base: the hosting platform's own PR-diff command (which resolves the merge base server-side), or locally `git diff $(git merge-base HEAD <default-branch>) HEAD --stat`. This matters most on any PR you'd otherwise flag as suspiciously large — a false 300+-file reading triggers a stop-and-report that a two-second re-check would have avoided.
    - Concrete checks: `gh pr diff <n> --name-only`, or `git diff $(git merge-base HEAD origin/<base>) HEAD --stat` after resolving and refreshing the PR's remote base (#108).

13. **A CI status API can be unreliable once a PR has merged and its head branch is deleted — read the merge commit's own check-runs instead of the PR's.** Two independent distortions stack: cancelled runs get bucketed as failures, and jobs still queued at merge time eventually get a runner and die at checkout because the head branch no longer exists — which surfaces as a genuine-looking failure on an unrelated job. The tell is an absurd duration (a lint job "running" for hours is runner backlog, not a slow job). Correct method: query the check-runs of the merge commit's SHA directly (e.g. GitHub's `repos/{owner}/{repo}/commits/{sha}/check-runs`), which is the authoritative signal for whether the default branch is actually healthy — then confirm functionally (local lint/render, live state) rather than trusting any CI status bucket.
    - A queued job can later fail with `git fetch +refs/heads/<branch>…: The process /usr/bin/git failed with exit code 1` after branch deletion; one title-lint run showed 3h16m. Query the head SHA's check-runs too, but use the merge commit's checks for base-branch health.

14. **`yq eval-all` silently cross-products when you extract paired fields from a multi-document YAML stream — it can fabricate evidence on a promotion or rollout proof.** `eval-all` merges every document in the stream into one root context before evaluating the expression, so `.metadata.name` returns a *sequence* of every document's name, and a `+` concatenation joins them cartesian-style: N documents each contributing two fields produce name/value pairings that read as plausible individual rows but are wrong. On a staged control-plane-before-data-plane promotion this can make it look like the control plane moved when it did not. Fix: use `yq eval` (per-document, evaluated independently) — never `eval-all` — for this class of query, and cross-check with an unrelated extractor (e.g. a plain `awk` pass); agreement between two independently-implemented methods is the real proof. The same cross-product applies to `join()` under `eval-all`. (yq v4, mikefarah/yq.)
    - For example, `yq eval-all 'select(.kind=="Application") | .metadata.name + " => " + .spec.source.targetRevision' render.yaml` turned four Applications into sixteen plausible but wrong pairs. Use the same expression with `yq eval`.

15. **Triage every PR into a small number of review-depth tiers by blast radius, and make rendered proof mandatory for the tiers that touch declarative infrastructure.** A useful split: trivial (docs, single-value config changes) / standard (most logic changes) / sensitive (RBAC, secrets, network policy, alert routing, any production-cluster manifest, CRD/operator changes). For chart or values-file PRs at standard-or-above, render the affected artifact at the merge base and at the PR head and diff the *rendered* output, not just the source — and require a negative control (an untouched target whose rendered diff must be empty) so an empty diff on the real target is a blocking finding, not a pass. Sensitive-tier PRs additionally get adversarial cross-model verification of every blocking finding, defaulting to refuted until a second model reproduces it. Detect a review bot's actual completion by an in-place marker in its comment body, not by comment count — some bots update one comment in place rather than posting new ones.
    - Sensitive changes also include ext-authz. Use the strongest available correctness lens, recheck every blocking finding independently, and explicitly resolve bot threads. Completion markers include CodeRabbit's `walkthrough_start` and Bugbot's scanned-commit footer; checks and review objects are separate surfaces (#110, #133).

16. **When two review passes disagree on severity, first check whether they disagree on the FACTS or only on how to GRADE the same facts.** If both passes independently arrived at the same underlying facts and only differ on classification or weighting, the adjudication is "fix what both flagged, then decide the grading question on its merits" — not "pick a winner." Two companion rules from the same class of split: (1) do not treat a lighter-weight automated bot as categorically lower-tier than a deeper manual or model-driven pass — a scanning bot can spot a root cause that two more thorough passes each only see a fragment of; (2) in any catalog- or allowlist-style design, "this change requires no edit to any consumer" is a *blast-radius* property, not a *safety* property — adding a member to a shared package or group silently grants it to every consumer that already selects that package, with no consumer-side diff for anyone to review. Watch for that inversion whenever a values-driven or catalog-driven allowlist is the surface under review.

17. **Running two independent review lenses (one correctness-focused, one adversarial) is only valuable if you post both findings and let the divergence stand — averaging or silently reconciling them destroys the reason you paid for a second pass.** Give each lens its own full, independent pass over the same PR at HEAD, in isolation from the other's findings — the adversarial lens should actively try to break the PR's own claims rather than just re-reviewing for style. Observed patterns worth expecting: convergence (both lenses independently catch the same real bug by different routes) is a strong signal, not redundancy; a more adversarial second lens tends to escalate documented-but-unenforced conventions that a purely correctness-focused pass discounts as future work, and it surfaces ordering/lifecycle hazards (e.g. deleting before replacing, rather than replacing then pruning) that a same-model pass tends to miss because it shares the first pass's blind spots. Post both lenses' findings and flag the split explicitly rather than resolving it yourself; a reviewer who "fixes" a genuine disagreement by editing the artifact has thrown away the signal the second lens existed to produce.
    - The adversarial checkout is a detached, read-only worktree **at PR HEAD**; isolation is its purpose. Read the base with `git show <merge-base>:<path>` when needed. Render-proof baselines remain at the merge base. Keep the lenses blind to one another; distinguish `Style=single|parallax` from `Action=fix|review-only`, and never push in review-only mode. An adversarial pass also catches trust-boundary widening hidden by a matches-existing-pattern argument.

18. **A security-policy finding measured against a permissive target must be re-verified against a strict target before it is called blocking.** A high count or volume of connections observed on the one environment whose policy posture is permissive (or matches neither your test nor your production posture) can look like proof that a policy change breaks a real flow — but on a genuinely strict target the same flow is typically orders of magnitude smaller and already includes real rejections by design. An allow-style policy change cannot break what a stricter policy already denies, so no exception is usually needed. General rule: know which of your environments are permissive-by-design and permanently so, and re-measure any authorization- or mTLS-adjacent finding on a strict environment before grading its severity — a finding measured only on the wrong posture is the cheapest way to post a wrong blocker on someone else's PR.
    - Before grading, search prior findings for the workload name: a previous investigation may already identify the discriminator between an actual strict-posture rejection and accepted plaintext.

19. **Three shipped-artifact conventions worth applying without being asked.** (1) **Rendered Helm manifests belong in the PR DESCRIPTION**, inside a collapsible `<details>` block (bodies are effectively capped at a few dozen visible lines and only `<details>` contents are exempt), **never checked into the repo**; show only the chart's OWN objects (filter on `# Source: <chart>/templates/`) and omit vendored subchart output. Regenerate them from a bash SCRIPT FILE rather than a piped `helm template`, so a token-reducing shell wrapper cannot truncate the output mid-render. (2) **Do NOT check validation, behavioural-test or analysis REPORTS into the chart repo** — they belong in the wiki/tracker, and a chart README should link the durable proposal rather than an in-repo report path. (3) **Do NOT link specific PR numbers in READMEs or committed docs** — they rot, and a reader should be able to dig. **Hint the durable LOCATION instead**: "the deny exception lives in `<repo>` under `config/policies/iam_deny/`", "controller identity lives in `<repo>` under `stacks/.../customers/<cluster>/`". PR links are fine in ephemeral PR bodies and comments.
    - **Per-cluster override values files do NOT use the `# --` doc-comment convention** — that applies only to base `values.yaml` files, for `helm-docs`. Bots flag this as a nitpick; it is non-blocking and should be **disagreed with, citing sibling files as evidence.** **Generalises: when a bot demands per-occurrence documentation on the Nth mechanical repetition of a documented pattern, the counter-evidence is the existing undocumented POPULATION plus the single DEFINING site — cite both, and keep the rationale where the next batch author will find it.**
    - **`discipline.py comment` counts each line of a `{{/* … */}}` block separately** (open line + content + close line = 3), so a 3-line docblock trips a 2-line ceiling even when the content is one sentence — use the single-line `{{/* content */}}` form. The gate diffs against `$(git merge-base origin/<default-branch> HEAD)...HEAD`, so **check against the REMOTE default branch, not a stale local one**, or files outside the PR's diff produce spurious findings.

20. **Cursor Bugbot can post its summary EMBEDDED in the PR body itself, not as a separate comment or review object.** On one PR both `gh api pulls/<n>/reviews` and `issues/<n>/comments` returned zero `cursor[bot]` rows, yet `gh pr view --json body` carried a complete `<!-- CURSOR_SUMMARY -->…<!-- /CURSOR_SUMMARY -->` block with a "Reviewed by Cursor Bugbot for commit `<sha>`" footer and a verdict. **A bot-polling loop that reads only reviews + issue comments + inline comments undercounts this shape** — also grep the PR body for `CURSOR_SUMMARY` before concluding Bugbot timed out or never ran. The footer SHA is still the ground-truth staleness check: confirm it equals HEAD before trusting the embedded verdict.

21. **A `.gotmpl` consumed as a Crossplane Composition inline template makes its COMMENTS shipped cluster payload, so a comment-only edit is a rendered-manifest change on every consuming target.** Review consequences: (a) never assume a comment-only diff is inert on these files — render it; (b) an **audit record** belongs in the design doc, while the template keeps only the load-bearing two-line reason a block exists plus a pointer that **names** the doc — never a local filesystem path, which is both a dead link for reviewers and shipped verbatim to clusters; (c) measure comment density with the author's own formula so before/after are comparable, and against a sibling template's ceiling; (d) an *added-lines* comment-ratio gate is unsatisfiable on a small diff that legitimately retains rationale — report it, do not delete a load-bearing comment to clear it.

22. **When one guard emits a SHARED error message across N keys, re-read that message against every key, not just the one being added.** On one PR the adversarial lens caught what the correctness lens missed: a denylist loop whose single `fail()` said each blocked key *"configures a security-sensitive surface (… object versioning …)"*. That was false for the newly added key, which never *configures* versioning — it makes versioning **unsupported**. A claimant hitting the error would hunt for a setting they never wrote. The fix was additive and needle-safe (*"… or makes one inoperative"*); confirm first that no test asserts the message tail and that any assertion needle precedes the edit. **Generalisation: adding a member to an existing guarded set is also an edit to every message, doc string and enum that set feeds.**

23. **On a two-lens judgment SPLIT, escalate and record — never silently reconcile, and never "fix" it by editing the live artifact.** On one guardrail PR the adversarial lens argued a cloud logging-bucket key fails a *data-movement* criterion (object-storage access logs carry client IPs, request URIs and **object names**, which routinely encode customer identifiers) while the correctness lens and the author had classified it metadata-class-allowed. Both readings were factually correct; they weighted the same evidence differently. Correct handling: (a) post both lenses with an explicit pointer at the divergence, (b) record it in the design doc as a **named approved exception** with the containment that justifies it **and the condition that would reverse it**, (c) leave the live blocklist untouched — adding a key to a guardrail running on every consuming cluster is the owner's decision, not the reviewer's. A reviewer who resolves the split by editing has destroyed the signal the second lens was bought for.
    - For a GCS `logging.logBucket` exception, concrete containment includes same-organization confinement and a destination owner pre-granting `cloud-storage-analytics@google.com`; state the condition that would reverse approval.

24. **A production table mirrored into a hand-transcribed test table is only as complete as the TEST table — pin the two key sets equal, or a production-only row ships untested.** When a suite keeps a deliberately independent transcription of a production list, its "covers all N kinds" count, its class counts, its per-row assertions AND its table-driven negative-control loop **all read the TEST table** — so "driven off the production list, so a future row cannot ship without its control" is true only for rows already in the test table. Reproduce it: add a row to the production table **alone** and watch the suite still pass with no control, no assertion and no count change. **Cheap fix that works — assert the symmetric difference is empty:** `assert_eq … "" "$(comm -3 <(<extract keys from the production file> | sort) <(<extract keys from the test table> | sort) | tr -d '\t' | paste -sd, -)"`. **Mutation-test BOTH directions (production-only row, test-only row) — a one-directional check is the trap.** Generalises to any test that re-states a production table rather than deriving from it.

25. **Two review-workflow gotchas that silently no-op a fix pass.** (a) A diff-scoped gate invoked as `discipline.py comment --base <ref>` diffs `merge-base...HEAD` — **committed state only**. Editing the working tree and re-running it reports the OLD findings unchanged, which reads as "my fix didn't work." Use the stdin form to check uncommitted work: `git diff origin/<default-branch> | discipline.py comment -`. (b) **Trimming comments in a `.gotmpl` is NOT an inert edit.** A function-go-templating body is loaded verbatim via `.Files.Get` and embedded into the rendered Composition, so its comments are **rendered payload** an operator reads on-cluster — a comment-only change alters rendered output and must be re-proved with the render matrix, not assumed no-op. Same reason a `fail()` message string is operator-facing and worth reviewing for accuracy, not just for compiling.
    - **`discipline.py comment` has THREE modes and counts CONSECUTIVE `+` runs — knowing both turns "the gate is broken" and "I must delete the comment" into neither.** VERIFIED 2026-08-13. Supersedes any claim that the script has a stdin bug; it does not.
    - **Modes.** Its own usage line documents three, and `git diff … | discipline.py comment -` **REQUIRES the trailing `-`**. Piping without `-` falls through to the default `branch` mode, which ignores stdin **by design** and diffs `merge-base(origin/<base>)...HEAD` instead — which is exactly why a 12 k-line diff, a 578-line diff, an empty diff and zero-byte stdin all returned byte-identical output. With `-`, the three inputs produce three distinct outputs. **GENERAL LESSON: before reporting a shared tool as broken, read its arg parser** — an agent measured "identical output for different inputs" and concluded *bug* when it had simply not passed the mode flag.
    - **Base ref.** `--base main` on a branch that has merged `origin/<base>` pulls in violations from already-merged files — use **`--base origin/<base>`** so only the current PR's diff is checked. And `--base <ref>` compares COMMITTED state (`merge-base…HEAD`), so it is silently vacuous as a pre-commit check — use `--staged` or the `-` form there (#25(a), #28).
    - **The comment-block violation counts only CONSECUTIVE `+` lines per hunk; a context line RESETS the run.** So a growing pre-existing comment block that a PR must edit for content reasons can be trimmed **surgically**: split the edit so only the truly-new sentence is `+`, and keep any downstream sentence byte-identical to base so it renders as unchanged context. That drops the flagged run below the 2-line ceiling **without losing content** and without relocating it to the PR body — verify first that the information really is duplicated at the specific rule's own local comment.
    - Reminder, because it is the one case where "comments-only, skip the render proof" is wrong: in a `.gotmpl` loaded via `.Files.Get`, comments are RENDERED PAYLOAD — see #21 and #25(b).

26. **An adversarial-lens dispatch is NOT done just because your end-marker grep returns a hit — `codex-dispatch.sh` echoes the full prompt into the output file, so the marker you asked for appears once as prompt echo while the run is still mid-flight.** On one review `grep -c '=== END OF ADVERSARIAL REPORT ==='` returned `1` at the prompt-echo line, and `awk` reported that as the LAST match — the run was roughly 60 % through, with four `[VERIFIED]` sections and its verdict still to emit. The correct completion test is all three: (a) the **last** marker line number is far past the prompt echo, or the count is >= 2; (b) `pgrep -f 'codex exec'` finds nothing; (c) the file **stopped growing** — sample `wc -c` about 45 s apart. The near-miss was re-dispatching a healthy run: `pgrep -fl codex` matched only the shell wrapper and looked ambiguous, but a 45 s byte-delta of +9411 proved it alive. This sharpens the general "don't judge a background run by pgrep plus a log tail" rule with the specific artifact that defeats it — the prompt echo.

27. **For a Crossplane provider-family promotion, prove one-registry-one-version-per-cloud at RUNTIME, not by repo grep.** `kubectl get providers.pkg.crossplane.io` on the TARGET cluster shows the transitive `upbound-provider-family-<cloud>` pinned by TAG (e.g. `provider-family-gcp:v2.6.0`). If the family being promoted resolves to a different version, installing it forces a family-provider upgrade *underneath* the already-running providers on that cluster — that churn, not the values-file skew, is the real failure mode the invariant guards. Also resolve the digests ALREADY pinned for the other families on that cloud, since a PR body typically shows only the new ones. Complementary checks worth adding: `crane manifest` to confirm the digest is a multi-platform index (`linux/amd64` + `linux/arm64`), and the exported `package.yaml` to confirm it is the RIGHT package with the expected family dependency — a valid-looking digest for the wrong package renders and lints perfectly.
    - Resolve every already-pinned family digest, not only the new ones listed in the PR body; one promotion required four `crane digest` checks rather than two.

28. **A committed-state-only lint gate re-run after an unstaged edit reports the old violation and reads as "my fix didn't work".** Commit first, then re-run to confirm `clean`. Related judgment call, settled more than once: when the flagged comment is byte-identical to one ALREADY merged on the default branch in sibling files, the consistency argument is exactly the reasoning the gate was built to remove — fix the new files and file the sibling sweep as a follow-up; do not extend the violation for symmetry. Cheap proof that a comment-only fix is safe on a chart PR: re-render every target and assert byte-identical output to the pre-fix render, which also re-validates any rendered-manifest blocks in the PR body.
    - **Correction:** committing is not required to inspect the fix. The gate's `--base` mode reads committed state; use `--staged` or feed the working diff to `discipline.py comment -`. A trailing `-` is required for stdin mode. The byte-identity claim also needs the `.Files.Get` caveat in #21: comments embedded as template payload change rendered output.

29. **Measured two-lens divergences: the lenses NEVER disagree on arithmetic — they disagree on SOURCE, METHOD, SCOPE, CLASSIFICATION or INTERPRETATION, and the correctness lens's systematic weakness is grounding a RUNTIME claim in a repo render.** Across repeated deep reviews the lenses agreed on every rendered and arithmetic fact, and the entire value of the second lens was one divergence per review:
    - **SOURCE** — live controller state vs what the repo render says; capacity scoped by the workload's own selector vs counted globally. The correctness lens can hold the refuting datum and not draw the inference.
    - **METHOD** — comparing permission-NAME unions (blind to scope) vs comparing per-binding ownership. Same source, different comparison.
    - **SCOPE OF THE QUESTION** — asked "can anything fire", the correctness lens answers for the rules the diff ADDS; the adversarial lens notes a PRE-EXISTING rule becomes ARMED by the new traffic. **When a dispatch asks "will anything fire", answer for the whole rule set the change ACTIVATES, not only the rules the diff adds.**
    - **CLASSIFICATION** — whether a pre-existing CI-gate gap is "blocking" or "follow-up" when the remedy lives outside the diff. **Post both and let the human adjudicate; never silently reconcile** (#23).
    - **INTERPRETATION, NOT COLLECTION** — full convergence on every measured fact, divergence on ONE sentence of prose, where the correctness lens **already HELD the refuting datum** in its own census and had not drawn the inference. **So "my census already covers that" is NOT a reason to skip the adversarial pass.**
    **COUNTERMEASURE for future dispatches: enumerate every RUNTIME/CAPACITY claim explicitly and require a live read for each BEFORE drafting the correctness lens** — that is the whole of the observed edge. **Complementarity runs both ways**: an offline adversarial lens cannot query live state, which the correctness lens can. Two dispatch facts: send the adversarial lens to a **detached worktree at HEAD**, and budget roughly 90 minutes for a deep CRD/XRD review. The second lens can earn its cost three distinct ways even on a thoroughly self-verified PR: finding the test-coverage CLASS (mutation adequacy vs non-vacuity); catching a branch the first sweep never rendered because the suite default hid it; and raising a class the first lens never tested for (a permissive regex admitting identifiers the cloud API rejects).
    - **Parallax's measured value is that the two lenses find DISJOINT issues — and the second model's edge is concentrated in claims the first grounded in the WRONG SOURCE.** Two measurements: (a) On a 92-chart fleet-plumbing PR, the Codex adversarial lens found `required` accepting an empty list (a render-time guard that actually fails at sync) while the Claude correctness lens found a global value absent from all 6 AWS host-cluster stacks (whole-umbrella render failure) — **NEITHER found the other's.** (b) On a sensitive mint+adopt PR the lenses agreed on every rendered fact (blast radius, all 5 identity hashes, SA/pod agreement, scope, collisions, controls) and **diverged on exactly one thing — where the adversarial lens was right**: Claude grepped the repo for an ArgoCD health customization, found none, and posted the wrong conclusion, while Codex checked live `argocd-cm` and refuted it. Codex also traced a values typo Claude called inert to a REAL downstream defect. **Pattern: the divergence is about SOURCE SELECTION (repo grep for runtime config), not arithmetic.**
    - **On very large PRs the third-party bots contribute ~zero and the two lenses are the only real review** — `coderabbitai` SKIPPED a 369-file PR entirely (150-file limit) and `cursor` raised nothing. **Budget for reproduction-depth parallax on any PR over ~150 files.**
    - **Parallax design points that decide whether the second lens adds anything**: (i) send a claims table **STRIPPED of reasoning** — handing the other model the report body makes it agree with the justifications instead of checking them; (ii) cycle 2 sends **ONLY deltas and contests**, never settled claims — *a correction is itself a new unverified claim*, which is the failure mode single-pass loops miss; (iii) peer relationship, neither lens authoritative, but **contesting REQUIRES source at `file:line` the other lacked** — bare disagreement is capitulation with extra words; (iv) **three outcomes, not two** — converged / open dissent (surface both positions, never fabricate agreement or silently pick a side) / **UNVERIFIED (tag it, NEVER delete — silent removal destroys the signal downstream agents need)**; (v) early-exit if cycle 1 is all CONFIRMED.
    - **When BOTH lenses block on the SAME claim by DIFFERENT evidence paths, that is the strongest verdict the two-lens review produces — and the gap between their numbers is itself information.**

30. **A learnings entry written by the PR's own author, and the dispatch prompt's characterisation of the evidence, are both CLAIMS UNDER REVIEW — never verification.** On one heavily self-verified PR the two lenses CONVERGED rather than diverged: both independently found the same single defect (a mis-transcribed byte count) and agreed on every substantive fact. That is a different value profile from the disjoint-findings case — here the lenses' worth was **CONFIRMATION of a high-stakes claim**, not new findings, which is the correct expectation when author evidence is already thorough. Two review-design consequences, both cheap and both load-bearing: (a) the author had consolidated that PR's findings into a learnings file **BEFORE** review, so the learnings file stated the answer to the very question the reviewer was dispatched to determine — **go to the primary source, the prior PRs' own text, instead**; (b) the dispatch prompt's framing of the top-priority question was itself the misreading, and **a reviewer that trusts the dispatch's characterisation of the evidence inherits its error** — read the prior PR bodies verbatim before accepting a premise the dispatch asserts. Same family as never resolving a thread on the dispatch prompt's say-so.
    - **ZERO blocking findings from both lenses is a legitimate and informative outcome — say what made it so.** On a fully pre-verified infrastructure PR, both lenses independently reproduced **the author's own claims** (byte-identical render for the unchanged branch via `sha256` + `cmp`; the new branch parsing and matching the consumer's documented semantics; upstream source confirming the field-level deltas; a bogus-value negative control failing closed) and neither found anything. **Reviewer effort was almost entirely RE-DERIVING evidence the author had already produced and cited by `file:line`.** That is what a well-evidenced PR costs a reviewer, and naming it is more useful than padding the review with suggestions — it tells the author the citation discipline worked. ⚠️ The inverse also holds: when the author cites nothing, the lenses spend their whole budget building the baseline instead of attacking it.

31. **A reviewer fix-push AUTO-DISMISSES a human approval already on the PR — check before pushing in fix mode.** On one PR a human approved and the next reviewer-agent **test-only** push flipped `reviewDecision` back to `REVIEW_REQUIRED`. Run `gh pr view <n> --json reviews,reviewDecision` BEFORE any push in fix mode; if an approval exists, either weigh whether the fix is worth invalidating it, or push and **flag the dismissal explicitly in the summary comment** so the human knows to re-approve. **It is not visible in `gh pr checks` or the comment stream — the `DISMISSED` review row is the only tell.**

## Bot mechanics, PR-body claims and mutation proofs

32. **Copilot code review posts as `copilot-pull-request-reviewer[bot]` into `reviews[]` as `state=COMMENTED` — NOT into `issues/<n>/comments` — so an issue-comment poller never sees it.** It re-reviews on **every push**; each review and inline comment carries a `commit_id`, so compare against HEAD or you act on a stale scan (same trap as Cursor Bugbot). **Its summary body hides real findings inside `<details><summary>Suppressed comments</summary>` blocks.** Two follow-on rules: **(a) suppressed comments are LATENT, not dismissed** — on the NEXT re-review, triggered by any push, Copilot can promote the same finding to a real inline thread with a **new comment id**, so resolving all visible threads is not terminal; re-enumerate `reviewThreads` AFTER your push or you hand off with an open bot thread you already answered elsewhere. **(b) On a force-push Copilot's inline `commit_id` is REBASED to HEAD — use `original_commit_id` as the staleness ground truth.** ⚠️ **Which bots run is a per-repo INSTANCE fact and guidance about it goes stale fast** — a note that Copilot was the only review bot on one repo was refuted days later when `cursor[bot]` was observed running there. Check the repo, do not carry the list.

33. **Copilot grounds its "not in the PR's stated scope" findings in the PR BODY TEXT, and re-reads the body on every re-review.** Four of five findings on one PR were **body bugs, not code bugs** — the change was maintainer-requested but undescribed. **Fix the body BEFORE or in the same beat as the push**, otherwise the re-review quotes the stale body and re-raises the same objections verbatim (it did: *"conflicts with the PR description's claim that the change only loosens"*).

34. **PR-body correctness is a REVIEW SURFACE, not metadata — and a body already "corrected" once is not clean.** On one PR a corrected body still carried **six** factual errors: the wrong base branch in its stack table, a render proof anchored at the default branch instead of the real merge-base, and a CI paragraph claiming two jobs were pre-existing failures when one had passed and the other was not even in the check set. **Always re-derive the base from `gh pr view --json baseRefName` and re-read CI live; never trust a prose CI claim in a body.**

35. **A PR-body correction does NOT propagate to the code — grep the diff for the same claim before accepting the fix.** On one PR the false claim *"Defaults to PROD so an unset value gets the strictest posture"* was removed from the body but left **verbatim in the docstring that same PR ADDS**. The repo would have shipped the falsehood permanently while the body carried the correction. **When a review forces a factual correction to a body, grep the diff for that claim in code, docstrings and comments.**

36. **When a finding is dispositioned as "deferred to PR N", VERIFY PR N actually contains the promised work.** A deferral is a claim about another artifact and must be grounded like any other claim. One PR deferred seam tests to a later PR **twice, across two review rounds**; `gh pr diff <N>` showed that PR's diff added **ZERO** references to either function named, and zero matches for the settings symbol in its test file — the promised test did not exist.

37. **Never `head`-truncate a PR comment listing: the truncated tail is exactly where a superseding comment lives.** Reading comments with `gh api issues/<n>/comments | head -N` silently dropped a LATER plan-output comment that superseded an earlier one — the newest said *"4 to destroy"*, not *"1"* — which made a reviewer clear a stale-plan finding that the adversarial lens then correctly reopened. **Count first (`jq length`) and read the newest by `created_at`.** Same class as trusting a bot's `diff_hunk` over its `commit_id`.

38. **GitHub creates NO `pull_request` workflow run while a PR is CONFLICTING — the entire Actions suite goes silently absent while the PR still looks green.** GitHub cannot build `refs/pull/N/merge`, so `pull_request`-triggered workflows do not run at all; meanwhile **head-SHA-keyed apps (Cursor, renovate, cloud build integrations) keep firing**, so the PR shows a small green check set and reads as fine. In a stacked PR this is easy to cause — one import-line edit colliding with the base branch is enough. **Detect via `commits/<sha>/check-suites`: a MISSING `github-actions` suite, plus `gh pr view --json mergeable` returning `CONFLICTING`** (API form: `mergeable=false` / `mergeable_state=dirty`). Resolve with a normal merge of the base branch — no force-push — and the suite appears within seconds.

39. **GitHub actions taken by an agent through `gh` and actions taken by the human appear as the SAME actor login, because the agent uses the user's token — so an agent CANNOT source-attribute anything in a PR timeline.** On one PR a subagent saw `ready_for_review` plus a merge attributed to the account owner, concluded an unreviewed auto-merge bot existed, and **filed a false security finding**; in fact the owner had readied and merged it deliberately and a human had reviewed it. **Before raising an "unauthorised automation" alarm from timeline actors, check the conversation and `gh pr view --json mergedBy,reviews` — and note that the NULL HYPOTHESIS IS "the human did it", not "a bot did it".** Corollary: agents should stop force-reverting a human's `ready_for_review`; leave draft state as found.

40. **Replies posted via `gh api` go out under the user's own account with no agent marker — the attribution sign-off must be in the FIRST post, never patched in.** An edit leaves the original text in the notification email a reviewer has already received. **Same for commit SHAs: never cite a SHA in a public comment before running `git log` to read it.** `gh api` path trap while fixing such a comment: **editing a PR/issue COMMENT omits the issue number** — `repos/{owner}/{repo}/issues/comments/{comment_id}` (GET/PATCH). The intuitive `…/issues/{num}/comments/{id}` **404s**; that path only accepts POST-to-collection. **Inline REVIEW comments are a different tree entirely:** `repos/{owner}/{repo}/pulls/{num}/comments/{id}/replies` to thread a reply.

41. **Reviewing a Python PR with no installed venv: AST-EXTRACT the real definitions and `exec` them — never transcribe constants or test bodies into a harness, because that only guards your own copy.** Pull the real `ClassDef`/`FunctionDef` out of the real source file (`ast.get_source_segment`) and `exec` it; import the real module via `importlib.util.spec_from_file_location` with **only its narrowest dependency stubbed into `sys.modules`**; run the whole thing under `uv run --no-project --with pydantic --default-index https://pypi.org/simple` to bypass a repo's private index. This produced a full four-value routing matrix, an exhaustive accept/reject sweep and a six-mutation adequacy suite **without ever installing the project**. Stubbing detail that matters: make the stub's `__getattr__` return a dynamically created **CLASS**, not a `SimpleNamespace` — pydantic uses these as type annotations and an instance raises *"unhashable type"*.

42. **When a refactor adds an INERT parameter (threaded now, read later), the strongest proof is STRUCTURAL, not empirical — and the real finding is usually the test coverage cliff.** Show the parameter is **never referenced in the callee body**, so output cannot depend on it for ANY value; a render diff over N sampled values is strictly weaker. Then check whether the EXISTING tests pass the new parameter: on one PR **22 of 22 test call sites passed no `environment=` and took the signature default**, so when a later PR makes it load-bearing the whole suite silently keeps asserting only the default. **That coverage cliff is invisible to both a render proof and a mutation run**, and the PR's own disposition comment asserted the opposite.

43. **For a PR whose value is a SEAM rather than a behaviour, proving the no-op is the EASY half — the load-bearing questions are whether any test pins the wiring, and what other code does the same job without the new parameter.** Both lenses proved byte-identical renders with negative controls on one plumbing PR, and the correctness lens stopped there; only the adversarial lens (a) ran real mutation testing showing that **unwiring the new seam left all 97 tests GREEN**, and (b) found a **sibling scheduling path a `node_selector` grep could not reach**, because the other renderer used different template key names. **Output assertions cannot prove a seam is connected:** mutations that drop the public renderer's keyword *and* mutations that hardcode a value inside the private builder can both stay green. **Pin the boundary explicitly** — assert that the renderer forwards the settings value and that the builder forwards its parameter to the consumer.

44. **Mutate the CROSS-PRODUCT of a guard's parametrised axis with the OTHER branch axes — a parametrised test set looks exhaustive along its own axis while being blind on every axis it does not vary.** Proof from one PR where the two lenses each found a survivor the other missed, from independent spec-derived mutation sets: the correctness lens found a **signature-default flip** that survived (133 passed) because every call site passes the argument explicitly; the adversarial lens found a **cross-product escape** — `environment = PROD if config.gpu else environment` survived all 133 tests, because every test in the file rendered `gpu=False`, leaving the non-prod GPU path's behaviour completely unpinned. **Derive mutations from the SPEC's edge set, not from the PR's claimed mutation list** — on that PR the author's three claimed mutations all passed re-execution while a fourth class survived. **For each threaded argument, mutate all four: (a) the outer call site, (b) the inner call site, (c) the SIGNATURE DEFAULT itself, and (d) the opposite direction** — hardcoding the non-default value — to prove detection is bidirectional rather than merely "these two differ". Note the two lenses may SPLIT on severity (required-change vs follow-up); **surface the split, do not push to resolve it.**

45. **Closing a "the seam has no coverage" gap: the test must go through the PUBLIC entry point and PATCH THE SETTINGS SINGLETON — passing the argument yourself is exactly what makes the wiring untestable.** Working shape: `with patch.object(APP_SETTINGS, "<field>", value): snapshot = <public_renderer>(…)`, then assert on the rendered output, parametrised over every enum value. Two lessons about the mutation proof itself. **(1) Re-run the mutations at CURRENT HEAD rather than trusting the finding that motivated the dispatch** — on one PR the adversarial lens's claim that BOTH mutations left the suite green was true at the commit it ran on, but by current head one had become covered by tests added in an intervening PR while the other was still caught by nothing. Reporting the stale claim verbatim would have been a false statement in the PR body; **say which mutations are newly covered and which are not.** **(2) The strongest evidence is not "my test failed" but "ONLY my test failed"** — record the full counts (`4 failed / 379 passed`, `2 failed / 381 passed`), because a mutation that also trips pre-existing tests proves less about the new coverage.

46. **A sortedness guard keyed on a LEXICOGRAPHIC tuple does not pin the invariant its consumers rely on — assert PAIRWISE DOMINANCE on every axis instead.** `assert sorted(X, key=lambda s: (s.a, s.b)) == X` permits a later element with a larger first field and a **smaller second**, so `X[-1]` silently stops being the maximal element while the test stays green. Counter-example that passed the lexicographic assertion while breaking the consumer: `(1.5, 6), (3, 64), (7, 28)` — a consumer reading `X[-1]` as "the largest" now rejects a request the middle element would have accepted. Inserting a duplicate-identity element also survived it. **When consumers read `X[-1]` as "the largest", assert `itertools.pairwise` monotonic non-decrease on EVERY axis** (which implies the lexicographic ordering and additionally pins `X[-1]` as maximal), or pin the exact ordered tuples plus identity uniqueness. Found independently by three lenses, each with a different counter-example — a sign the class is easy to reach and easy to miss.

47. **Pydantic v2: a plain `@property` is NEVER serialized by `model_dump()` — only `@computed_field` is.** So converting a `@property` to a plain method has **zero effect** on serialization output, which makes such a conversion safe to prove structurally rather than by render diff. (Verified on a `BaseModel` whose property was converted to a parameterised method.)

48. **Any PR body claiming CLEANUP of live resources is a CHECKABLE FACT — run `kubectl get` on the named objects.** On one PR the body claimed test artefacts were *"both deleted after the measurement"*; the template and three warm pods were still `Running` 38 minutes later. Both lenses caught it independently. **Live-evidence sections must be re-verified against the cluster, not just read.**

49. **A review comment's anchor is evidence; a relayed paraphrase is not.** When a review comment reaches you second-hand ("the reviewer says move X onto Y"), resolve the anchor yourself before acting. GitHub's review-comment API gives `path`, `line`/`original_line` and `original_commit_id`; `git show <original_commit_id>:<path> | sed -n '<line>p'` names the symbol the reviewer was actually pointing at. On one PR a relayed instruction named one accessor function while the anchor pointed at a **different, similarly named** function on the adjacent line range — and only one of the two could sensibly become a property on the enum it returns. Implementing the paraphrase would have produced a change the reviewer never asked for while leaving their actual comment unaddressed. Cheap check, and the anchor is unambiguous.

50. **Two confident readings of the same config field are still one unverified fact.** A PR that states an infrastructure limit as verified must name what was read, not just the value. One PR claimed a 30 s HTTPS load-balancer cap on every API request, citing `gcloud compute backend-services list` showing `timeoutSec: 30`. The field was read correctly; what went unread was the backend it applies to. The backend service's only backend was a **SERVERLESS** NEG, and GCP ignores `timeout_sec` for serverless NEG backends — the real ceiling is the Cloud Run request timeout. Production load-balancer logs settled it: 58.4 s and 174.2 s requests, both status 200, impossible under the claimed cap. Two lessons, in order of how much they cost: **(a)** for any GCP backend-service timeout, read `networkEndpointType` on the attached backend before quoting the number — serverless makes it inert; **(b)** a claim of the form "X caps every request at N" is falsifiable in one query against request logs, so a PR asserting it without that query has not verified it. The reviewer's "we definitely had requests which took more than 30 seconds" was worth more than the console field, because recollection of observed behaviour beats a config value whose applicability was never checked.

51. **Never grade a latency PR on a handful of sampled events — compute the DISTRIBUTION, then state the SHARE the fix addresses.** Reviewing an image-streaming PR, the correctness lens was wrong twice before measurement settled it: draft 1 reasoned from vendor docs plus non-streaming production pull times and concluded streaming could not clear a 29 s budget (refuted by a cold-pull measurement on an already-enabled pool: 15 GB in 4.7 s); draft 2 swung to "big win, fixes it" (refuted by the distribution). **n=400 for the exact production image was strictly BIMODAL: median 0.358 s, p75 0.436 s, then p90 97.7 s / p95 108 s / max 136 s — 11.5 % over the budget, and NOTHING between 0.44 s and 97 s.** A `head -20` sample showed both modes and made the slow mode look typical; it is 11.5 %. **The bimodality IS the finding** — a fix that targets the slow mode fixes only its share of traffic, so quote the share, never the worst case. Diagnosing the slow mode took a second query, not a bigger sample: the 46 slow pulls were on **46 DISTINCT nodes, one each, and 36 of those nodes later served fast pulls** → first-pull-on-new-node, NOT image-GC eviction, which would repeat on the same node. **PARSING TRAP that produced a fake result:** `r'in (?:(\d+)m)?([\d.]+)m?s'` parses `283ms` as **283 seconds**, because the optional minutes group backtracks and `m?` eats the milli-`m` — the median came out 323 s instead of 0.323 s. **Always sanity-check a computed distribution against raw sample lines before publishing it.**

52. **Your own most CONFIDENT finding is the most dangerous one — a margin argument must be SIMULATED, and a package must be resolved to the import, before it blocks a PR.** Two instances, both caught only by the second lens or by an executable check. (a) **Wrong dependency binding:** the correctness lens filed a "blocking" finding with a reproduced wire command, a negative control, a pushed fix and a tracking task — all wrong, because it verified against the wrong *installed* library. The adversarial lens refuted it in one line by checking the import. **A negative control proves your test is load-bearing; it does NOT prove your premise is right** — both can be consistent with a wrong model of the dependency, so "read the source" must first resolve WHICH package the symbol binds to. (b) **Self-refuted margin argument:** a source-grounded blocking finding (a client's retry cadence exceeds a new rate window, so `for:` could never be satisfied) was **refuted by the lens's own offline simulation before anything was pushed**. The arithmetic was right and the conclusion was wrong, for two reasons prose could not hold at once — an effective rollup window one scrape interval wider than nominal, and N concurrent senders sharing one counter (see `learnings-observability.md`). **When a finding rests on a timing margin, do not ship the arithmetic: simulate it, sweep the unknown phase, and add controls.** (c) **A refuted finding is still worth reporting** — in (b) the PR's *stated mechanism* was wrong even though its *conclusion* was right, and a wrong stated mechanism is what the next person optimises against. File it as a PR-body correction, not as nothing. **Corollary: never skip posting the adversarial lens because your own pass looks conclusive — conclusive is exactly when it is most dangerous.**

53. **A hand-rolled test double that IGNORES the query it is handed makes every assertion downstream of that query structurally blind — and the fix is a behavioural assertion against a real DB, not a compiled-query capture.** On one PR a `_FakeSession.execute(_query)` returned fixed rows regardless of its argument, so deleting the tenant-scoping `.where(<Model>.<scope_column> == <scope>)` from a revision lookup left the suite **17/17 green** while the PR body advertised per-tenant scoping as a guarantee. The Kubernetes half of that same guarantee was structurally enforced and mutation-proven; only the DB half was unguarded, which is the trap — **a partially-proven invariant reads as fully proven.** Two things generalise: (a) **the reviewer's suggested fix was to capture the compiled query; prefer asserting the BEHAVIOUR instead** — give a second tenant its own row and require that its uuid does NOT resolve, which survives a refactor of *how* the filter is expressed, whereas a query-shape assertion breaks on a rewrite that is still correct; (b) **the mutation proof must report which OTHER tests stayed green** — here seven pre-existing tests passing while only the new one failed (`[(2, 1), (1, 1)] == [(1, 1)]`, the other tenant's revision id leaking in) is what actually demonstrates the pre-existing blindness. Scan for this smell whenever a fake's method signature has an underscore-prefixed parameter (`_query`, `_sql`, `_stmt`): the underscore is the author admitting the argument is dropped.

54. **"Silent all-zeros on the wrong identifier" is a correctness bug, not a docs bug — when two lookup keys are distinct columns of a row that EXISTS, validate the key rather than documenting it.** On one endpoint a single path parameter fed both a Kubernetes label selector and a DB filter on a *different* column, so passing the display-name column instead of the key column matched nothing in either and returned a **200 with every count zero** — indistinguishable from a healthy idle workload. Both review lenses graded it a naming/doc issue and suggested a clearer parameter `description=`. **That is insufficient: a docstring does not make a wrong identifier observable at the call site — the caller still gets a plausible zero.** Validating the key against its table and returning 404 costs one query and makes the failure loud; in-repo precedent for exactly that already existed on a sibling route. Take the doc fix too, but do not let it substitute. **Test it DB-backed**, because the whole point is that both columns belong to a row that exists — a mocked backend cannot distinguish "wrong key" from "absent row", so it cannot show the foot-gun. Negative control: removing the validation fails the test with `assert 200 == 404`, which is the silent-zeros path itself.

55. **A two-lens review pays for itself in three distinct ways, and the SEVERITY SPLIT is the normal output rather than a failure.** Clearest evidence to date, from one PR. **(1) CONVERGENCE AS CONFIRMATION:** both lenses independently derived the *same* mutation (drop an environment argument at a cap call site) and measured the *identical* survival count (176 passed). Neither saw the other's work. **When two different models land on the same mutation with the same number, the finding needs no further defence — ship the fix.** **(2) DIVERGENCE AS COVERAGE:** the correctness lens swept every RENDERER exhaustively and proved the change complete — and was still **structurally blind** to the PERSISTENCE paths (#56). The adversarial lens found those because its brief is *"break it"*, which pushes past *"is the new code right"* to *"what does the new code not reach"*. **The correctness framing audits the DIFF; the adversarial framing audits the SYSTEM AROUND the diff.** **(3) SEVERITY SPLITS:** the adversarial lens returned BLOCK on four findings; on adjudication **one** was real-and-fixed, **two** were valid-but-pre-existing-or-by-design (follow-ups), and **one** was unreachable in production. ⚠️ **The adversarial lens systematically OVER-RATES severity because it constructs objects directly, bypassing the factory/validator that real traffic must pass** — always re-check an adversarial repro by asking *"can any production entry point actually construct this?"*, and ground the refutation **on the PARENT commit**: a "regression" that the factory already did pre-PR is not a regression. **Post both lenses verbatim, adjudicate in the summary, let the human decide — do not silently reconcile.**

56. **For any change to a RENDERER in a system that PERSISTS what it renders, the call-site sweep is NECESSARY BUT NOT SUFFICIENT — the fix is not retroactive and reviewing only the render path misses it.** Two persistence paths re-apply **stored** output without re-rendering. **(a) ROLLBACK:** a rollback that re-applies a stored manifest body verbatim (rewriting only an identity field) restores the **old** values indefinitely — and this is often **deliberate** ("applied as stored"), so "normalize on rollback" is a debatable fix, not an obvious one: re-rendering would mean rollback no longer restores what you rolled back to. **(b) EXISTING OBJECTS:** when a child object holds only a *reference* to the rendered parent, every already-deployed parent keeps its old values until that unit is redeployed — and if redeploy is a manual `workflow_dispatch`, production **does not self-heal**. **Three questions to add to the review: (i) what re-applies stored output; (ii) is there a migration or reconciliation for live objects; (iii) does rollback re-render?** Then check whether the PR body states the impact as **immediate** when it is actually **progressive-on-redeploy** — that is a claims defect worth correcting even when no code changes.

57. **For every DEFAULTED parameter that alters behaviour, assert it through the RENDERED OUTPUT at a NON-DEFAULT value — unit tests that pass the argument EXPLICITLY leave the CALL SITE's argument-passing completely untested.** The mutation that exposes it is *"drop the argument at the call site so it falls back to the default"*. Measured: that mutation left **all 176 tests passing** while a rendered limit silently fell from 2 CPU / 8 Gi to 1.5 / 5 Gi, because every existing render test ran at the default value. ⚠️ **ASYMMETRIC COVERAGE IS THE TELL** — the *same* mutation at the sibling call site (a routing selector on the same builder) was caught by 2 failures, and the asymmetry is what pointed at the gap. Fix by rendering at a non-default value and asserting both the capped field and the derived env var.

58. **Derive mutations from the SPEC, not from the test ASSERTIONS — an assertion-derived set is blind exactly where the author was.** On one PR the author claimed 7/7 negative controls; rebuilding the set from *what the endpoint is supposed to guarantee* produced **20 mutations, 17 caught / 3 escaped** — and all three escapes (a DB-scoping `WHERE`, a duplicate-key `ORDER BY` tie-break, a falsy-vs-`None` filter) were invisible to the author's set. **Byte-change-gate every mutation (`cmp` the file before and after) so a no-op mutation cannot re-report the clean baseline as "caught".**
    - **Assertion NON-VACUITY and mutation ADEQUACY are different properties, and only the second finds real gaps — run BOTH sweeps on any test review.** Proven on PR #NNNN (Bucket XRD). **Sweep A** asks *"does each `it:` case fail when its OWN subject breaks"* — all 17 cases passed, the suite was genuinely non-vacuous. **Sweep B** (the Codex parallax lens) asks *"what can I break that NO `it:` case catches"* — **12 one-line regressions left the suite 58/58 GREEN**: `kmsKey`/`kmsKeyArn` `maxLength` removed, `owner.pattern` weakened to `^.*$`, an ambiguous `retentionDays: {default: 90}` added beside the split pair, `apiVersion` downgraded v2→v1, `referenceable: false` (the derived CRD then has NO storage version and is rejected), `served: false`, `minLength` removed from `owner`/`serviceName`/`purpose`, group renamed, version renamed. **Sweep A alone READS as coverage and is not.** Fixed additively in `<commit-sha>`.
    - **Mutation testing measures YOUR mutation set, not the suite's strength — and an author's mutations are unconsciously drawn from what the tests visibly assert.** On one shipped harness the author ran 19 mutations, all caught, and reported the suite strong; a second model then found **4 escapes**, all in dimensions the author never probed. **Render-level suites are systematically weak where they (a) flatten match dimensions into SORTED UNIONS (`rule_versions`/`rule_groups`) so removing a version from ONE rule is invisible, and (b) assert CEL by SUBSTRING, so changing a projection (`.map(u, u.spec.of.kind)` → `by.kind`) keeps every asserted substring present while breaking the policy completely.** FIX: derive mutations from the policy's SEMANTICS, not from reading the test file; assert **exact `(group, version, resource)` tuples and exact list contents**, never unions and substrings. (Harness-side rules for actually applying such mutations: `learnings-agent-workflow.md`.)
    - **To judge whether a CI-guard "fix" is a genuine NARROWING or silently retires coverage, the decisive test is a CONTROL ON THE GUARD ITSELF, not on the code under test.** Apply the mutation the guard must catch, then **also apply the careless alternative fix to the guard** and confirm it goes GREEN. On TICKET-NN the guard changed `native_expected` from a constant to `base | (PROD_ONLY if overlay_env == prod else set())`. Mutation M1 (env gate widened to `if true`) reddened 6 clusters with the shipped conditional; with `native_expected` made UNCONDITIONAL the same mutation passed `rc=0` / 0 failures. That single A/B proves the conditional is load-bearing. **Without it, "the mutation reddens" only proves SOME code detects it, not that the CHANGED code does.**
    - **When a checker derives its expected set from a raw values DISCRIMINATOR (e.g. `environmentConfig.env`), exact set equality is insufficient unless the checker ALSO validates the discriminator's allowed enum and proves every required branch/overlay is exercised.** Otherwise a non-empty typo or an inherited default moves BOTH the render and the oracle onto the non-production branch and the suite stays green. Mutation harnesses must separately classify **assertion mismatches** from **render failures**.
    - **Denylist/blocklist tests keyed on a shared error prefix are vacuous TWICE OVER.** TICKET-NN T8: a table-driven suite marking blocked rows with a bare `BLOCKED` sentinel and asserting them with a needle built from the key name (`spec.aws.<k> is`) also matched the **unknown-key** error (`spec.aws.X is not a supported…`), so **DELETING a row from the production table still passed** — and it could not tell a *platform* block from a *sensitive* block, so a class flip was invisible. Fix: carry the CLASS in the table (PLATFORM/SENSITIVE), use class-specific needles, and add **per-class row COUNTS** so a wholesale reclassification cannot pass by making every needle match. (Companion: #24, where the same suite's completeness depended on the hand-transcribed table itself.)
    - **Include identity/cardinality mutations:** if the consumer iterates a list but the test first converts it to a dictionary, duplicate identifiers can erase the invalid row only in the test. Compare the original population and assert uniqueness before treating the keyed view as complete.

59. **A "fails closed via a uniqueness exception" argument must be verified across EVERY PRODUCER of the identifier, not just the table you queried — this is the single highest-yield question to ask a correctness lens's reasoning.** On one PR the correctness lens explicitly reasoned a cross-kind name collision away as *"fails closed"*; the adversarial lens found it real, because the correctness lens had only considered **same-table** collisions and never asked whether **other kinds** share the name space. When a lookup is claimed safe because an ORM raises on multiple matches, the claim rests on an assumption about who else can mint that identifier.

60. **An "at most N" concurrency assertion whose test only proves the peak REACHED the cap is VACUOUS — it passes under an unbounded `gather`.** Mechanism: if the fake work releases as soon as in-flight hits the cap, the first N arrivals trip the release and exit **before** the rest have piled up, so the observed peak lands on N either way. **FIX: once the cap is reached, PARK the whole first wave (`await asyncio.sleep(~50 ms)`) BEFORE releasing**, so every remaining target has time to accumulate if nothing stops it. Then unbounded peaks at the batch size and sequential peaks at 1 — a genuinely **two-sided** control. **Choose `batch_size = cap*2 + 2`** so the two failure modes give visibly different numbers. The passing direction stays timing-independent (a semaphore cannot be exceeded regardless of scheduling); only the *control* run is timing-sensitive, and it is generous. **GENERAL RULE: for any "at most N" assertion the negative control must be the OVER-limit mutation, and you must RUN it** — reasoning about which way an async scheduler falls is exactly where this goes wrong.

61. **Prove "one query, not N" with a STATEMENT-COUNT EQUALITY across two row counts, never an absolute number.** Attach a `before_cursor_execute` listener to the test engine's `sync_engine` inside a `@contextmanager`, run the call with 1 row and then with 5, and assert the two counts are **EQUAL**. Do not pin an absolute count — the listing legitimately runs other queries, and pinning the number breaks on any unrelated addition. The equality is two-sided by construction: an N+1 implementation gives 3 vs 7. ⚠️ **RUN the negative control rather than reasoning about it** — replacing the join with a per-row lookup failed with `assert 7 == 3`, while the sibling test that merely asserts the joined value **appears** still passed. **That is the whole point: a presence test cannot catch an N+1.** (The listener signature must be `(_conn, _cursor, statement, *_rest)` or `ruff` flags `PLR0913` plus five unused-argument findings.)

62. **Proving "no authorization behaviour changed" when adding members to an enum that GATES AUTH is not a diff question — it is a "who ITERATES the whole enum" question.** Grep `'in <Enum>|set(<Enum>)|list(<Enum>)|<Enum>.__members__'`. If the only whole-enum consumers are an import-time completeness check and a seeding table, and every other reference is to a **named member**, new members are **provably inert** for existing code paths. **But state the visible non-authorization change explicitly in the PR body**: if the catalog is served from the DB, a seeded or migrated entry **does** become newly selectable in an admin picker. Generalises to any catalog enum behind an admin UI.

63. **Four guard failures that recur in RESIZE / CAP / DEADLINE code, all found by adversarial repro rather than reading.** **(1) A fleet ceiling must gate INCREASES ONLY.** Enforcing it on decreases rejects the exact cleanup action the design relies on, precisely when the fleet is already over cap — i.e. when scaling down matters most. **(2) A ceiling implemented as LIST → sum → compare → PATCH across separate objects is TOCTOU.** With `total = cap-1` and two objects at 1, two concurrent `target=2` calls both project exactly `cap`, both patch, and the final total is `cap+1`. A strict shared cap needs a **distributed** per-scope critical section plus a concurrent negative test — an in-process lock is insufficient across replicas. **(3) Put the read-compute-compare guard INSIDE the branch that can act on it.** Computing a cluster-wide LIST *above* the `is_increase` test makes every **decrease** pay for a fleet-wide LIST it discards — and decreases are the automated path that runs at volume. **(4) A polling deadline must wrap EACH individual blocking call** in a timeout bounded by `(remaining, small_floor)`; checking the deadline only *between* calls does not bound a single stalled call. ⚠️ **And a cross-package timeout "contract test" that COPIES the server default into a test constant is NOT a drift guard** — changing the real budget left the test green. Contract tests must read **both** authoritative definitions or stop claiming drift protection.

64. **Assert a SKIPPED call against the MOCK, not the status code — and point a manifest test at the real apply path, not a fixture it builds itself.** A 200 passes whether or not the expensive listing ran; the decrease test must assert `totals_mock.assert_not_awaited()`, and keep the fake allocation above the cap so a regression trips the cap loudly instead of silently. Separately, a test that constructs its own model and serialises it **tests the fixture, not production**: repointing it at the genuine render → `model_dump(exclude_none=True)` → apply chain made it fail under **both** mutations (drop `exclude_none`; give the status field a non-`None` default), neither of which the fixture-based version caught.

65. **When a multi-step destructive operation fails PART-WAY, a binary `succeeded|failed` status vocabulary LIES to the operator — and the UI faithfully renders the lie.** One delete path removes the live resource **before** the database row; if the DB delete raises, the bulk endpoint returns `status=failed` while the resource is **already destroyed** and the user disconnected. An operator reads "Failed" as "nothing happened" and retries or escalates on a false premise. **The status vocabulary needs a partial signal, and the remedy belongs in the BACKEND, not the UI.** (Retry was at least idempotent there: the row survives and the second resource delete swallows not-found.)

66. **Prefer a STATE-shaped status literal over an ACTION-shaped one — state survives idempotency where action does not.** `deleted` is true whether this call removed the object or it was already absent; `refreshed` **asserts work that never happened**, and it does not sit alongside siblings like `not_found` / `failed`. Related API-shape call from the same review: **a bulk POST beat DELETE-with-body** — RFC 9110 §9.3.5 gives a DELETE body no semantics, and the call crossed two proxies that may strip it. ✅ **Renaming a wire enum consumed by TypeScript is unusually safe: `tsc` TS2367 makes a stale literal a COMPILE ERROR rather than a silently-always-false filter** — rely on that, plus a grouping regression test, and keep the *UI's* verb unchanged if users know it by that name; only the upstream path and wire literal need to move.

67. **When a COUNTING or enrichment field is expensive PER ROW, do not hang it off a list endpoint — build a SIBLING that CANNOT be called in bulk.** A list endpoint that is inherently multi-entity (repeated or comma-separated ids, a `latest_only` sweep across everything, a large page limit) turns one count field into *one expensive backend call per entity per page render* — the fan-out reviewers veto as an abuse vector — while narrowing the list endpoint breaks existing callers. **An endpoint that REQUIRES the scoping parameter makes single-entity scope STRUCTURAL rather than conventional: no request can be constructed that counts more than one.** Two shape details worth copying: keep **named leftover buckets** rather than one "other" — two buckets with *different diagnoses* ("not yet stamped" vs "stamped but unresolvable") plus the matched set, and assert that the three always **sum** to the total, which is the invariant the tests hang on; and **cache the expensive DERIVED census, not the finished response**, under a **VERSIONED key prefix**, so the cheap mapping stays fresh and a deploy that changes the cached model's shape does not read the old shape back and 500 for a whole TTL.

68. **Preserve EPISTEMIC UNKNOWN through derived booleans and aggregates — mapping "unknown" onto `false` turns "we do not know" into the FALSE CLAIM "it is not".** An operator UI that collapsed *unstamped*, *unknown* and *resolved-but-older* into a single `onTarget: false` rendered all three as "Not this revision", and depressed the confirmed counts in the header. **Use `true | false | unknown`, or separate confirmed and unknown counts — never a boolean — whenever absence of evidence is distinct from evidence of absence.** The same rule decides read-failure rendering: when a dependent fetch fails, **DROP the column rather than rendering zeros**, because a zero from a failed fetch is indistinguishable from a real zero, and `null` must mean *fetch failed*, not *zero*.

69. **A CONTROLLED selectable table that derives header state from CURRENT rows but derives the action count and request body from the raw selected set SILENTLY ACTS ON ROWS THAT ARE NO LONGER RENDERED.** After a re-list, a removed or expired row stays in the set forever: the destructive button reads "act on 1 item" with **zero rows checked**, and submits that stale identifier — which, when identifiers are short and reusable, can address a **different live object**. **Fix: intersect the selection with the rendered rows BEFORE counting or submitting.** Mutation proof: re-render with replacement rows and assert no removed id is submitted; test select-all followed by **both** additions and removals.

70. **A hand-rolled test double that ignores the query is one blindness; a test double that AGREES WITH THE BUG is another — and only the second survives a reviewer reading the test.** A cache test whose fake was `side_effect=lambda key, value, _ttl: store[key] = value` **transcribed the call it was asserting**, so eight green tests and green CI hid a guaranteed 500 from the real client. **Fix pattern: make the double honour the REAL contract (reject what the server rejects), then prove it load-bearing by reinstating the bug and watching the test fail.** Applies to any hand-rolled mock of a third-party client. (Complements #53, the ignores-the-query case.)

71. **A THRESHOLD backtest whose CONTROL SET sits below the gate's evaluation floor is a VACUOUS PASS that reads as a clean negative control.** Tuning two volume gates, the five "must pass clean" reference PRs were all small enough that **any** small-diff allowance passed them trivially — the matrix would have been green for a gate with **no discriminating power at all**. **FIX that made the tuning real: pull ten MORE samples IN THE EVALUATED REGIME before choosing any constant**; that extended control is what produced the working model, and the original five contributed almost no information. **GENERAL RULE: before reporting a backtest matrix, check the CONTROL SET's distribution against the gate's ACTIVE RANGE — if the controls cluster where the gate is inert, the matrix is decoration.** **Corollary:** when the arithmetic separating a must-flag case from a must-pass case leaves a **sub-1 % margin** (5 lines on 620), that is **overfitting a constant to one sample, not a threshold** — report the negative result and let a different gate catch that case.

72. **When a review REVERTS part of a PR, re-read the PR's own METADATA against the NEW diff — and after a squash merge the title IS the commit subject in the base branch's history.** One revert left an expression byte-identical to the base, collapsing the net diff from "two changes" to one, so the title now misdescribed what would land. **Checks after any partial revert: (a) does the TITLE describe the NET diff versus the base, not the PR's internal history; (b) does the BODY still describe the shipped values; (c) did the revert leave an earlier justification section as DEAD PROSE?** ⚠️ **Second habit, from the same PR: when a review falsifies a claim in a PR body, do NOT quietly DELETE it — mark it as a correction IN PLACE ("Correction — X does not reproduce, here is why").** The deleted version loses the reason the original reviewer was misled, which is often the reusable part, and a reader of the merged PR cannot tell an unexamined claim from a retracted one. **Applies to design docs too.**

73. **A PR-body claim about a MEASUREMENT is a review target in its own right — and the mechanism can be wrong while the conclusion is right.** On one PR the correctness lens built a source-grounded blocking finding, then **refuted it with its own executable simulation before pushing anything**: the arithmetic was right and the conclusion was wrong, for two reasons a prose argument could not hold at once. **When a finding rests on a TIMING MARGIN, do not ship the arithmetic — SIMULATE it, sweep the unknown phase, and add controls.** An offline simulator is cheap and is the only thing that catches a margin argument that is directionally right and quantitatively dead. ⚠️ **And the finding still had value after refutation:** the PR body's **stated mechanism** was wrong even though its conclusion was right, **and a wrong stated mechanism is what the next person optimises against**. Report it as a **body correction**, not as nothing.
    - The same timing-margin lesson is also covered by #52, including the package-binding caveat and the rollup-window/concurrent-senders mechanism.

## Further review and verification lessons

74. **Empty `annotations:` on Service templates cause perpetual ArgoCD OutOfSync**: Upstream charts that unconditionally render a bare `annotations:` key on Services create a perpetual diff because the API server normalizes the empty field away. Fix: set a real annotation value in wrapper values. (Same empty-field-normalized-away mechanism, different field: argocd `group: ''` perma-diff, `learnings-argocd.md`. Concrete argo-rollouts instance with chart version + key name: `learnings-progressive-delivery.md`.)

75. **Helm portLevelMtls guard missing**: Workload PeerAuthentication templates without `{{- with .portLevelMtls }}` guard emit empty `portLevelMtls:` field when no port overrides are configured. Always wrap portLevelMtls iteration with a with guard.

76. **Committed rendered files need yamlfmt pass before commit**: `helm template --show-only` outputs a leading `---` document separator before the first document. When the committed file adds a header comment above this `---`, yamlfmt strips the redundant separator (since no preceding document exists). CI yaml fmt check fails unless yamlfmt is run on committed rendered files. Fix: `yamlfmt -conf .yamlfmt <rendered-file.yaml>` after capturing helm output. Content is unchanged; only the leading `---` is removed.

77. **A repo whose PR-title lint uses `amannn/action-semantic-pull-request` v6.1.1 REJECTS comma-separated multi-scope PR titles**: `feat(scope1,scope2): title` fails validation with "Invalid PR title: multiple scopes". Only single scope is allowed. For PRs touching multiple areas, pick the PRIMARY scope or use no scope: `feat: title covering multiple areas`.

78. **Verbatim copy-paste scope creep in host-cluster values files**: When a host-cluster values file is a verbatim copy of another cluster, check for infra blocks (waypointProxies, portLevelMtls sections) that were copied from the source but don't apply to the target. The copy-pasted block may reference resources (pods, services) that don't exist on the target cluster. Review rule: for every copied block, confirm the referenced pod labels/ports exist on the target.

79. **Verify every cross-referenced issue/PR a maintainer cites against your OWN issue body + prior comments BEFORE replying** — don't deflect from memory. On an upstream issue a maintainer asked "how is #NNNN involved?"; the reply "we didn't reference it" was WRONG (our own issue body cited #NNNN), requiring a public correction. Fix: `gh issue view <n> --json body,comments` and grep for the referenced number before responding.

80. **Blanket `optional: true` stamp covers ALL secretKeyRefs, not just Infisical-managed ones**: A Helm helper guard `(not (hasKey secretKeyRef "optional"))` only skips refs that ALREADY have the `optional` field explicitly set. Always-present secrets (postgres, static k8s Secrets) will get stamped `optional: true` unless `optional: false` is pre-set in values.yaml. Fix pattern: add `optional: false` to any static secretKeyRef in values.yaml before enabling the blanket stamper.

81. **A bot line-length nitpick on machine-consumed expression strings should be DISAGREED with when reformatting risks semantics or breaks a byte-parity constraint.** Two independent grounds, both worth stating in the reply: (a) jq/PromQL/CEL expression strings cannot be safely split at a column limit without risking quoting changes the consumer may parse differently; (b) where a multi-PR rollout pattern requires the new file to be **byte-identical to an already-accepted reference**, reformatting breaks the pattern's own gate. Confirm the formatter and the CI fmt check both pass, then Disagree citing the reference file.

82. **When reducing a committed PR by reverting files, restore to the branch MERGE-BASE, not `origin/<base>`**: `git checkout $(git merge-base HEAD origin/<base>) -- <files>`. If main moved ahead, `checkout origin/<base> -- <files>` pulls unrelated upstream drift (e.g. `<application>-v1.1→v1.2` targetRevision bumps) into your commit, inflating the diff. Verify scope with `git diff --stat $(git merge-base HEAD origin/<base>) HEAD`, NOT plain `git diff origin/<base>` (which shows empty when the local `origin/<base>` ref is stale). Same merge-base anchoring principle as the proof baseline in #10.

83. **Never resolve a review thread on the dispatch prompt's say-so — verify the claim against the code first.** A dispatch asserted "the open thread about `projectIamAdmin` is now addressed by the new condition, reply + resolve." Grounding against the actual Terraform showed (a) the thread was about `serviceAccountAdmin`, a different binding, and (b) the condition sat only on the `projectIamAdmin` binding, so it could not close the other escalation — **a conditioned binding governs only its own resource**. Blindly following the instruction would have buried a live Major security residual. Trust-the-diff > trust-the-prompt. Corollary with real measured yield: a final adversarial cross-verify pass on an ALREADY-reviewed PR still caught a defect (a 10-role cap) that both the prior review and the existing learnings entry had missed.

84. **A checker workflow must be SELF-TESTING, and a far-behind branch silently breaks changed-files detection.** (a) A guard workflow's `paths:` trigger must include the checker script AND the workflow file itself — otherwise a PR that weakens the guard or its own trigger runs no guard. (b) A feature branch far behind main (418 commits) breaks `tj-actions/changed-files` with `Unable to locate the commit sha <merge-base> / fatal: bad object`, because the CI shallow checkout cannot reach the far-back merge-base — it fails the changed-charts and application matrix jobs. When force-pushing is disallowed, fix with a normal merge: `git merge origin/<base>` into the branch (non-force, clean when changes are isolated) so the changed-files base is recent and reachable, then push normally; squash-merge flattens the merge commit anyway. Rebase would also work but requires a force-push.

85. **Git's YAML hunk header LIES about which block you edited — it picks the PRECEDING top-level key, not the containing one.** In a per-target values file whose per-app blocks are structurally identical (`enable`/`source`/`targetRevision`/`helm`/`valueFiles`), a `targetRevision` edit under `istioCni` renders a hunk header of `@@ … istiod:` and a reviewer skimming headers concludes you touched the control plane. This matters most on split control-plane/data-plane promotions, where getting the order wrong is the actual risk. **Two defenses that worked (PR #NNNN, <cluster> data-plane-only Istio promotion):** (1) `git diff -U6` so the containing block's own header sits inside the context window; (2) extract `metadata.name` ⇒ `spec.source.targetRevision` from the **rendered** Helm output before and after — that names the Application unambiguously and is immune to hunk-header confusion. Pair it with a full rendered-manifest diff (base vs new) as the negative control: it must contain ONLY the intended lines. Sequencing is a separate control — per `learnings-istio.md` the control plane must merge first, and the gate is the `hold merge` label, not prose in the PR body (`learnings-helm-ci.md`).

86. **When a design is REVERTED mid-PR, grep `values.yaml` and `README` comments for the old approach — rendered output can be correct while the docs still teach the trap.** The `crossplane` chart's `values.yaml` providers-block header comment described the reverted `deploymentTemplate.spec.template.spec.serviceAccountName` SA-ownership model (API-rejected in `<commit-sha>`, it needs `selector` + `containers`) while the templates and README correctly used `serviceAccountTemplate.metadata.{name,annotations}`. A stale-comment contradiction *inside the same PR* — caught only by the reviewer, fixed in `<commit-sha>`. Reverting a design is a documentation change, not just a code change.

87. **Replying to a PR review comment: `POST /repos/{owner}/{repo}/pulls/comments/{comment_id}/replies` can return 404 on some repos.** Use `POST /repos/{owner}/{repo}/pulls/{number}/comments` with `-F in_reply_to=<comment_id>` instead — that threads correctly.

88. **`git branch -r --contains <branch HEAD>` returns NOT FOUND after a SQUASH merge** — the branch tip is never an ancestor of the base branch. Do NOT read that as unmerged and do NOT re-push. **Correct pre-cleanup checks**: (1) `gh pr view <n> --json state,mergeCommit` → `MERGED`, capture the merge SHA; (2) `git branch -r --contains <MERGE SHA> | grep origin/<base>`; (3) `git show origin/<base>:<path>` for each changed file and grep for the added identifiers. **Separate worktree trap in the same cleanup**: `git stash list` is **REPO-GLOBAL**, shared across every worktree — stashes you see while tearing down a feature worktree usually belong to the main worktree and are NOT yours to clear.

89. **Reverting a commit that ALSO made drive-by corrections REINTRODUCES the stale values.** `<commit-sha>` changed role counts 20→19 in docs and, in the same pass, fixed two leftover `21`s to `19`; `git revert` sent those two back to `21` while reality was `20`. **Rule: after any `git revert`, re-read every restored comment and prose line against the CURRENT repo state and re-derive the numbers from data** (here: `python3 yaml.safe_load` of `values.yaml`, counting the union of `packages` → `profiles` → gcp roles) — never against the pre-commit state the revert restores. **A textually-perfect revert is not a factually-correct one.**

90. **PR-facing text must never reference local-only doc paths.** PR descriptions, chart READMEs and shipped chart comments that point at `docs/<topic>/…` are dead links for reviewers — those live under `$HARNESS_DOCS`, a SEPARATE directory that is not the code repo. 130. **Deleting an explicit override does NOT fall back to the base class's default — it falls back to the nearest ancestor that sets it.** A profile class that set `cpu = 4` subclassed an intermediate class setting `cpu = 0.5`, so removing the line yielded **0.5**, not the base's 2 (or 5 on another branch). ✅ Verify by instantiating the real class, not by reading the base. ⚠️ A test asserting the old literal must change in the same commit, and a merge that moves the base default conflicts in both files.

131. **Deciding "has a HUMAN reviewed my PR" from the API needs THREE exclusions, not one.** **(1) Harness reviews**, identified by body markers — and note the two-lens ones are posted under the **PR author's own login**, `__typename: User`, so no account-based filter catches them. **(2) The PR author's own `COMMENTED` reviews**, which is how the platform records replies to review threads and which appear on nearly every PR. **(3) Bots** — and one widely-installed review bot's login is literally a plain word with **no `[bot]` suffix**, so a login denylist misses it: test `author.__typename == 'Bot'` as the primary signal and keep the login list as a supplement. ⚠️ Without (1)+(2), **every reviewed-by-nobody PR reads as "team reviewed"** — the lie that hurts most.

132. **One batched GraphQL `search(type:ISSUE)` covers author resolution, multi-repo scoping, reviews, check rollup AND required-check discovery in ~1.4 s — but four traps make a naive version wrong.** `author:@me` is accepted, so no separate identity call is needed. **TRAP 1:** `CheckRun.isRequired` takes a per-PR argument so it cannot be requested inside a batched search — and the tempting substitute, `statusCheckRollup.state`, **over-reports** (a failing *non-required* check looks like broken CI). Ask the **base ref** instead; it needs no per-PR argument. **TRAP 2:** `baseRef.branchProtectionRule.requiredStatusCheckContexts` is the WRONG field on any repo migrated to **rulesets** — it returns null there forever, even for an ADMIN viewer, while `ref.rules(first:50)` returns the real required contexts. **Read BOTH and union them**; `ref.rules` is viewer-scoped and needs no admin. **TRAP 3:** a null/empty required list is **indistinguishable from "no read permission"** — neither field errors on insufficient access — so an empty union must DEGRADE (report as non-urgent, labelled *unverified*), never be read as "nothing is required". **TRAP 4:** the `search` connection has a much tighter secondary rate limit than plain GraphQL (~15 probe calls exhausted it for ~10 min, surfacing as `errors[].type=RATE_LIMITED`), while `repository(){pullRequests}` uses the normal bucket — **use the latter to capture fixtures, then verify offline against a stubbed CLI on `PATH`.**

133. **The converse of #110: a review bot check can read `skipping` (not pass, not pending) while the bot still posts a full review with inline findings.** Seen: check went `skipping` after ~6 min and the review with 2 inline findings landed seconds later, after the poll had already exited on the non-pending check state. ✅ **Check state alone never ends the bot wait.** Once the check leaves `pending`, re-read `reviews[]` and `pulls/<n>/comments` one more time before posting, and re-read again right before posting the lens reviews.

## Review Methodology & Proofs

141. **GitHub carries OPEN bot review threads (Cursor Bugbot / CodeRabbit) FORWARD onto the PR HEAD commit's matching lines even after the finding was fixed in a later commit**: the comment's `commit_id` shows HEAD and `line` is non-null, so a fixed finding looks live. The `diff_hunk` shown is HISTORICAL (as of the comment's original commit), NOT current. GROUND TRUTH = the comment BODY footer `Reviewed by Cursor Bugbot for commit <SHA>` (the commit actually scanned) + reading the ACTUAL file at branch HEAD (`git show origin/<branch>:<path>`) + a helm render with a negative control, never the `diff_hunk`. Bugbot does NOT auto-resolve threads and only re-scans on a new push. (ref: threads fixed in `982a4fb` but scanned at `cf6e8701`.) Same for CodeRabbit: inline findings stay anchored to the commit they scanned, and when a later commit substantially changes the design CodeRabbit does NOT re-scan inline and does NOT withdraw the stale finding. Correct handling is to reply "Fixed in `<sha>`" + `@coderabbitai resolve` per thread: do NOT treat un-replied stale threads as live blocking findings.

142. **Verify EVERY bot finding against the live file before classifying fixed-vs-disagree, bots mis-scope in two recurring ways**: (a) **Re-flags an intentionally-removed matcher**: Cursor BugBot flags a deliberately-dropped label matcher (e.g. `cluster!="<cluster>"`) as a "missing filter" bug. Refute vs `origin/main`: if pre-existing alerts KEEP the matcher (count unchanged) and only NEW alerts omit it, and the metric doesn't exist on the excluded cluster, it's a false-positive-in-context → Disagree. (b) **Code-fence misparse**: when a code fence has NO language specifier, CodeRabbit may misparse surrounding context and report selectors as absent even when they're present in the same block (e.g. claimed ratio queries omitted `reporter=waypoint` when they had it). Always diff the bot's claim against actual file content. (Also: CodeRabbit reviews the intermediate commit SHA when a PR was force-stripped to a smaller scope, check its "Reviewing files that changed between `<base>` and `<SHA>`" header against current HEAD, cf. #139.)

143. **Render with ALL value files in the stack: a base `values.yaml` render alone can silently show a feature DISABLED.** In a layered GitOps repo the base `values.yaml` often sets a feature `false` and a higher layer overrides it to `true`. A single-file render therefore shows none of the feature's objects and no changed args, and the change **looks inert when it is not**. Always render the full stack in the same order the GitOps controller applies it. Second half, equally common: a template gating on `and .Values.x.enabled .Values.x.create` needs **BOTH** true, check every conjunct, not the one you changed.

144. **SUPERSEDED by #108: Resolve the PR's actual remote base before using the origin/main examples below.** **`discipline.py comment` has THREE modes and counts CONSECUTIVE `+` runs: knowing both turns "the gate is broken" and "I must delete the comment" into neither.** VERIFIED 2026-08-13. Supersedes any claim that the script has a stdin bug; it does not.
    - **Modes.** Its own usage line documents three, and `git diff … | discipline.py comment -` **REQUIRES the trailing `-`**. Piping without `-` falls through to the default `branch` mode, which ignores stdin **by design** and diffs `merge-base(origin/main)...HEAD` instead, which is exactly why a 12 k-line diff, a 578-line diff, an empty diff and zero-byte stdin all returned byte-identical output. With `-`, the three inputs produce three distinct outputs. **GENERAL LESSON: before reporting a shared tool as broken, read its arg parser**, an agent measured "identical output for different inputs" and concluded *bug* when it had simply not passed the mode flag.
    - **Base ref.** `--base main` on a branch that has merged `origin/main` pulls in violations from already-merged files: use **`--base origin/main`** so only the current PR's diff is checked. And `--base <ref>` compares COMMITTED state (`merge-base…HEAD`), so it is silently vacuous as a pre-commit check: use `--staged` or the `-` form there (#148(a), #28).
    - **The comment-block violation counts only CONSECUTIVE `+` lines per hunk; a context line RESETS the run.** So a growing pre-existing comment block that a PR must edit for content reasons can be trimmed **surgically**: split the edit so only the truly-new sentence is `+`, and keep any downstream sentence byte-identical to base so it renders as unchanged context. That drops the flagged run below the 2-line ceiling **without losing content** and without relocating it to the PR body: verify first that the information really is duplicated at the specific rule's own local comment.
    - Reminder, because it is the one case where "comments-only, skip the render proof" is wrong: in a `.gotmpl` loaded via `.Files.Get`, comments are RENDERED PAYLOAD, see #21 and #148(b).

145. **A render/lint CI job on alerting rules can be SHAPE-ONLY: it proves the YAML renders, not that the expressions are valid, and it will pass a query the live TSDB rejects at execution.** Measured adversarially: identity mutations to **names, groups, metrics, labels, `by()` clauses, operators, joins, durations, severities and annotations ALL PASSED** a render check, **including a join the live TSDB refused to execute.** So a green render check is not arming evidence for an alert rule. **The complementary proof that IS load-bearing: render every expression and LIVE-QUERY it against the datasource, then state what currently arms it.** **Two adjacent review findings, both a class worth checking on any alert PR:** a runbook prescribing a rollback at the wrong SCOPE (e.g. removing service labels when the enrolment/rollback is namespace-scoped), and **a PR body left stale after the head changed thresholds**: re-read the body against the final head before approving.

146. **SUPERSEDED by #108: Resolve the PR's actual remote base before using the origin/main examples below.** **Three render-proof false greens, all of which pass `diff -q` while proving nothing.** Extends the merge-base anchoring of #10/#20.
    - **A "pre-existing error" claim needs a real merge-base WORKTREE.** Comparing `helm lint HEAD` against `helm lint HEAD` proves nothing: `git worktree add --detach /tmp/x $(git merge-base HEAD origin/main)` and lint there.
    - **A byte-identity render diff between two throwaway harness charts ALWAYS differs**, because helm stamps `# Source: <chartname>/templates/…` into every document, so a naive `diff -q` "proves" a difference that is only the chart name. Strip the `# Source:` lines, **and add a negative control asserting the CHANGED case really does differ**, or `diff -q` passes on a comparison that detects nothing.
    - **A recorded merge-base goes STALE the moment the branch merges a newer main**, and the PR-body render proof then becomes internally impossible even when the feature diff is still correct. Recompute `git merge-base origin/main HEAD` and rerun the full Argo value stack: in one batch the stale baseline added unrelated Deployment differences through an umbrella release file, while the true merge-base isolated exactly the 12 intended ServiceAccounts per cluster.
    - Companion, already known but hit again: `helm dep build` on an umbrella sweeps the umbrella `Chart.lock` (untracked on main) into the branch, check `git diff --stat` against `origin/main` before pushing (`learnings-agent-workflow.md`#183).

## Two-Lens (Parallax) Review

147. **CodeRabbit evaluates a host-cluster Helm values file IN ISOLATION (layer 5 only), never through the full 5-layer ArgoCD value stack.** Findings of the shape "`global.provider` missing in `<cluster>.yaml`" are false positives when the value is set at `providers/aws.yaml` (layer 2). Always re-resolve a CodeRabbit Helm finding against the whole stack before accepting it. Same family as #137 (cross-cluster comparison) and #142 (bot mis-scoping).

148. **SUPERSEDED by #108: Resolve the PR's actual remote base before using the origin/main examples below.** **Two review-workflow gotchas that silently no-op a fix pass.** (a) `discipline.py comment --base <ref>` diffs `merge-base...HEAD`: **committed state only**. Editing the working tree then re-running the gate reports the OLD findings unchanged, which reads as "my fix didn't work." Use the stdin form to check uncommitted work: `git diff origin/main | discipline.py comment -`. (b) **Trimming comments in a `.gotmpl` is NOT an inert edit.** A Crossplane function-go-templating body is loaded verbatim via `.Files.Get` and embedded into the rendered Composition, so its comments are **rendered payload** an operator reads on-cluster: a comment-only change alters rendered output and must be re-proved with the render matrix, not assumed no-op. Same reason a `fail()` message string is operator-facing and worth reviewing for accuracy, not just for compiling.

149. **Measured Parallax divergences: the lenses NEVER disagree on arithmetic, they disagree on SOURCE, METHOD, SCOPE, CLASSIFICATION or INTERPRETATION, and the correctness lens's systematic weakness is grounding a RUNTIME claim in a repo render.** Extends #29. Across five deep reviews the lenses agreed on every rendered and arithmetic fact, and the entire value of the second lens was one divergence per review:
    - **SOURCE**: live controller state vs what the repo render says; capacity scoped by the workload's own selector vs counted globally. The correctness lens can hold the refuting datum and not draw the inference.
    - **METHOD**: comparing permission-NAME unions (blind to scope) vs comparing per-binding ownership. Same source, different comparison.
    - **SCOPE OF THE QUESTION**: asked "can anything fire", the correctness lens answers for the rules the diff ADDS; the adversarial lens notes a PRE-EXISTING rule becomes ARMED by the new traffic. **When a dispatch asks "will anything fire", answer for the whole rule set the change ACTIVATES, not only the rules the diff adds.**
    - **CLASSIFICATION**: whether a pre-existing CI-gate gap is "blocking" or "follow-up" when the remedy lives outside the diff. **Post both and let the human adjudicate; never silently reconcile** (#23).
    - **INTERPRETATION, NOT COLLECTION**: full convergence on every measured fact, divergence on ONE sentence of prose, where the correctness lens **already HELD the refuting datum** in its own census and had not drawn the inference. **So "my census already covers that" is NOT a reason to skip the adversarial pass.**
    **COUNTERMEASURE for future dispatches: enumerate every RUNTIME/CAPACITY claim explicitly and require a live read for each BEFORE drafting the correctness lens**, that is the whole of the observed edge. **Complementarity runs both ways**: an offline adversarial lens cannot query live state, which the correctness lens can. Two dispatch facts: send the adversarial lens to a **detached worktree at HEAD** (#17; mechanics in `learnings-agent-workflow.md`#198), and budget ~90 min for a deep CRD/XRD review. The second lens can earn its cost three distinct ways even on a thoroughly self-verified PR: finding the test-coverage CLASS (mutation adequacy vs non-vacuity, #58); catching a branch the first sweep never rendered because the suite default hid it; and raising a class the first lens never tested for (a permissive regex admitting identifiers the cloud API rejects).

150. **A learnings entry written by the PR's own author, and the dispatch prompt's characterisation of the evidence, are both CLAIMS UNDER REVIEW, never verification.** On one heavily self-verified PR the two lenses CONVERGED rather than diverged: both independently found the same single defect (a mis-transcribed byte count) and agreed on every substantive fact. That is a different value profile from #29's disjoint-findings case: here the lenses' worth was **CONFIRMATION of a high-stakes claim**, not new findings, which is the correct expectation when author evidence is already thorough. Two review-design consequences, both cheap and both load-bearing: (a) the author had consolidated this PR's findings into `learnings-crossplane.md`#118-#106 **BEFORE** review, so the learnings file stated the answer to the very question the reviewer was dispatched to determine, **go to the primary source (the prior PRs' own text) instead**; (b) the dispatch prompt's framing of PRIORITY 1 was itself the misreading ("both described their parity as computed against inline"), and **a reviewer that trusts the dispatch's characterisation of the evidence inherits its error**, read the prior PR bodies verbatim before accepting a premise the dispatch asserts. Same family as #83 (never resolve a thread on the dispatch prompt's say-so).

## Bot Mechanics, PR-Body Claims & Mutation Proofs (2026-09)

151. **Derive mutations from the SPEC, not from the test ASSERTIONS: an assertion-derived set is blind exactly where the author was.** On one PR the author claimed 7/7 negative controls; rebuilding the set from *what the endpoint is supposed to guarantee* produced **20 mutations, 17 caught / 3 escaped**, and all three escapes (a DB-scoping `WHERE`, a duplicate-key `ORDER BY` tie-break, a falsy-vs-`None` filter) were invisible to the author's set. **Byte-change-gate every mutation (`cmp` the file before and after) so a no-op mutation cannot re-report the clean baseline as "caught".** **Include identity/cardinality mutations:** if the consumer iterates a list but the test first converts it to a dictionary, duplicate identifiers can erase the invalid row only in the test; compare the original population and assert uniqueness before treating the keyed view as complete.

## Parallax in practice: grading, fixing and the shape of a clean review (2026-09)

152. **Standing rule on review threads: reply to and resolve BOT threads; leave HUMAN reviewers' threads alone, the owner answers those.** A reviewing agent that replies to a human colleague's GitHub review thread is speaking for the owner in a conversation the owner is having. **Fix the finding, describe the fix in the PR's own comment stream, and leave the thread open**: resolving it is also the owner's call, because resolution signals agreement with a person, not with a linter. (Bot threads are the opposite: reply and resolve them, per the bot-handling rules above.)

## Review bases, gate false positives and two-lens outcomes (2026-10)

153. **When BOTH lenses block on the SAME claim by DIFFERENT evidence paths, that is the strongest verdict the two-lens review produces, and the gap between their numbers is itself information.** Worked instance: both independently blocked on "the declared ceiling exceeds what the node can actually give the container", one from **live measurement** (allocatable minus measured/requested non-workload pods), the other from **declared limits in source** (documented daemonset figure plus native-sidecar limits). The two margins differed by ~70 MiB and both were negative. ⚠️ **Their SHARED blind spot is the thing to check next:** neither subtracted the kubelet hard-eviction reservation, and it turned out to be **already inside** the allocatable figure, so subtracting it would have double-counted. ✅ Reconcile the two models against a third, independent anchor (here: the provider's published reservation formula reproduced measured allocatable to within 0.03 Gi) before publishing either number.

## Telling human review from bot and harness noise (2026-10)

154. **Re-reviewing a PR whose branch was REWRITTEN needs a synthesised interdiff: `git diff <old-head> <new-head>` mixes in base drift and inflates the review by an order of magnitude.** Two cases, two tools. ✅ **Rebased / force-pushed (both ranges known):** `git range-diff <old-base>..<old-head> <new-base>..<new-head>` isolates the author's own changes; the old base is the merge-base recorded in the prior review body, which is why a review should always state it. ✅ **Rewritten or split, where the old head is not an ancestor:** replay the old PR onto the new base, `git merge-tree --write-tree --merge-base=<old-base> <new-base> <old-head>` then `git diff <tree> <new-head>`. ⚠️ Measured cost of getting this wrong: a plain head-to-head diff showed **46 files** against a true delta of **37** in one case, and **56 infrastructure files** of pure base drift in another. ✅ Record `<base-sha>..<head-sha>` in every review you post, so the next reviewer has the left-hand side.

155. **CORRECTION to #124: `hide_input_in_errors=True` is NOT a complete secret-redaction fix, `errors()` and `json()` still carry the raw input in full.** #124 lists the flag as the remedy; it suppresses the input only in `str(ValidationError)` and the traceback. Verified on pydantic 2.12 with a synthetic credential-bearing settings input: `exc.errors()[*]['input']` is unredacted. ⚠️ So the flag closes the *stderr* path and leaves every **structured** path open, which is the path a JSON log handler, an error-reporting SDK or an API error body actually takes. ✅ Test the structured serialisers **separately** from the string form; sanitise `include_input`/`ctx` or use a secret wrapper type. ✅ **Never accept a string-only redaction assertion as proof of redaction**: it is the single most common incomplete fix in this class.

156. **`StrictUndefined` plus `model_dump(exclude_none=True)` is a LATENT runtime error for every optional field: the template raises the moment any of them is None.** Dropping None keys from the render context means an optional field that is unset is not merely empty, it is *undefined*, and a strict renderer raises rather than substituting blank. ✅ It is safe only while **every** producer sets **every** field, which is true at the moment of the migration and silently stops being true when someone adds a sixth producer. ✅ Review ask: either keep the None keys, or add a test that renders with each optional field unset. ⚠️ Related control worth copying: the same change added a fetch script that **rejects any token outside the known set** (including triple-brace, conditionals and implicit built-ins), so the build fails if the upstream template starts using one, a good shape for "our renderer is a strict subset of theirs".

157. **A review bot's terminal CHECK STATE is not its completion signal: re-read reviews and inline comments before declaring bot feedback done.** A check reporting `skipping` for six minutes was followed by a full review with inline findings seconds later. ✅ Poll `reviews[]` and `pulls/<n>/comments` for the bot's login until your own budget expires. ⚠️ This is the correction that #110/#150's check-only guidance needs; treating the check as authoritative closes a review while findings are still arriving. Mechanism detail in `learnings-agent-workflow.md`#324`.

158. **A stale LOCAL base ref produces review findings that belong to unrelated commits: always diff against `origin/<base>` after a fetch.** A local `dev` 50+ commits behind origin produced **5 false findings** from commits the PR never touched. ✅ Any review tool taking a `--base` argument gets `origin/<base>`, and the fetch is part of the command, not an assumption about the checkout.

159. **A test DOUBLE that replaces a real client must track that client's `__init__` signature, and usually only an end-to-end job catches the drift.** An integration suite swapped in an adapter for the real sandbox client; a new keyword argument added to the real client's constructor and passed by the caller made the adapter raise `TypeError`, surfacing as a downstream assertion failure (*"expected length 1, received 0"*) rather than as a signature error. ⚠️ The adapter's own unit tests were **not run in CI**, so the browser-driven jobs were the only gate. ✅ When reviewing a change to a client constructor, grep for every test double of that client; when reviewing a *double*, ask what runs it.

160. **A configuration row that NO selector consumes is a documentation-only edit: map each changed row to the workflow that selects it before accepting a "this redeploys X" claim.** In a manifest where rows are chosen by per-suite boolean flags, a row with every flag false or absent has exactly one path to deployment: a manual dispatch, whose own input default **never reads the manifest**. So a replica-count change on that row is inert for every automated path. ✅ Generalise: for any declarative manifest consumed by a matrix builder, the review question is *"which builder selects this row?"*, and "none" is a common and invisible answer. ⚠️ Distinguish **matrix consumption** from a standalone default that happens to match the manifest value: the observable outcome is identical and the mechanism is not.

161. **`gh` can report `mergeable: CONFLICTING` / `dirty` on a stacked PR whose base IS an ancestor of its head, and an empty `statusCheckRollup` usually means no CI ran, not that CI passed.** Both were true simultaneously on one stacked PR where a local merge was clean. ⚠️ So neither field is usable as a merge-readiness signal on a stacked PR: verify the merge locally, and check whether the workflows' trigger conditions (often `pull_request` filtered to one base branch) even match a PR targeting a feature base. ✅ A stacked PR that never gets a particular plan/test job is a review finding in itself: say so, rather than reporting the job as passing.

162. **A brief author-facing review reports only what the PR INTRODUCES; a pre-existing issue goes in only when the PR rewrites that line, and is labelled as pre-existing.** A finding was once posted as blocking that turned out to be base-branch code the PR merely moved, only its *new consequence* was new. ✅ Shape that works: one short comment, blocking items under an explicit "To fix before merge:", plus a collapsed block holding a ready-to-paste prompt for the author's own coding agent. ⚠️ Two drafting failures to avoid, both seen: opening with "one thing to fix" and then using the "a few things… here or in a follow-up" closing (a contradiction the author will notice), and running long, a brief review that reads like a full one gets skimmed.

163. **The adversarial lens of a two-model review finds a different CLASS of defect than the correctness lens: name-length and resource-limit arithmetic is its specialty.** Concrete instance: a derived load-balancer name overflowing a 32-character cap (`learnings-terraform.md`#94`) was found by the adversarial lens and missed by the correctness lens on the same diff. ⚠️ This is evidence for *not* reasoning about whether a second lens "earns its cost" on a standard-tier PR: the two lenses are not ranked, they are differently blind. ✅ A PR whose BASE changed after review needs re-review, because the original review diffed against a base it no longer has (see #154 for how to do that diff).

164. **URL-parser component names are not proof of redaction on malformed input.** `urlsplit()` can move an intended password into `path` (`rediss://user:/Secret@cache/1`) or `port` (`rediss://:Secret#tail@cache/1`); logging `path` or allowing `.port` to raise can still reveal it. Test malformed delimiter placement and parser-raised exceptions, not only a valid userinfo with a missing host/port. Pydantic validation errors can separately echo the original credential-bearing `input_value`. Prefer a fixed sanitized parsing error and hide validation inputs. Reproduced with synthetic credentials on Python 3.13/3.14 and Pydantic 2.12.5. (ref: head baf8a3fb04)

165. **A two-lens review framed entirely around THE PR'S OWN CLAIMS will not hunt unclaimed failure modes, and an open-ended reviewer beside it finds what both lenses miss.** Measured head-to-head on one PR: a repo-native review bot, whose prompt simply says *report problems that should block this*, found **two real issues that both Parallax lenses missed**. The cause is structural, not effort: the correctness lens is told to *verify the PR's claims*, the adversarial lens to *refute the PR body's claims*, and findings are scoped to *problems this PR introduces, or gaps in something it claims*, so a failure mode the author never mentioned is outside both briefs, and a trade-off the author DISCLOSES gets read as accepted rather than traced to its consequence. Both fall under the "unmentioned consumers" seed. **A second lens legitimately CORRECTING the first is part of the value, not a failure:** one lens had graded a cloud-provider transition "settled" from a live steady-state precedent, which only proves a field is HONOURED and not that an EXISTING load balancer survives the change; the upstream source read was the better evidence and the grade was reversed.

210. **A review brief must lock owner INTENT, never an implementation line, or it tells both lenses to stop checking the thing most likely to be wrong.** Measured: a brief listed two specific chart overrides as "owner-approved, do not relitigate"; both lenses then verified the flag existed in the binary and the RBAC was correct, and NEITHER checked whether the upstream chart at the pinned version already shipped a native value that adds both. A human caught it. **Two rules.** In a brief, state the REQUIREMENT ("the controller must read this resource kind") and leave the mechanism open. And in any review of a WRAPPER chart, check every `extraArgs`, `rbac.additionalPermissions` and manual override against the upstream chart's `values.yaml` AT THE PINNED VERSION, because reuse-first applies to chart values exactly as it does to code.

211. **A GitHub approval is NOT dismissed on push unless the branch protection says so, so a behaviourally significant commit can sit one click from merge on an APPROVED PR.** Measured: a human approved one head, a later push added a commit that turned auto-sync ON across three production-adjacent clusters, and `gh pr view --json reviewDecision` still reported `APPROVED` with `mergeStateStatus: CLEAN`, because the repository has no dismiss-stale-reviews rule. **Rule: after pushing to an already-approved PR, SAY SO explicitly and offer to re-request review (`gh pr edit <n> --add-reviewer <user>`); never assume the push re-opened the gate.** Note this is the opposite of the repo in `#69`, where a fix push DID auto-dismiss: the behaviour is per-repository configuration, so check it rather than carrying either memory forward.

212. **Separate a CI flake from a real failure without touching code: `gh run rerun <id> --failed` re-runs ONLY the failed jobs, and the SPLIT is the diagnosis.** Measured on one head with two red jobs: the rerun returned one SUCCESS (a flake, one timing test out of 1579, while the sibling language-version matrix row had passed the same suite on the same commit) and the other FAILURE again (deterministic, and a breakage on the base branch rather than in the PR). It mutates nothing in the repository and is far better evidence than arguing from "my diff cannot have caused this". **Companion check before blaming your diff at all:** confirm the base branch's own status, because a red base fails every open PR regardless of what it touches, deterministically and identically.

213. **A "first run seeds the baseline" guard keyed on a workflow's run HISTORY is dead on arrival when that workflow FILE already has runs from its previous triggers.** Measured: a `gh run list --workflow <file> --status success` check intended to fire once on a new job never fired, because the old push trigger had left 40+ successful runs on the same file. 214. **GitHub code-scanning alert `created_at` is REPO-WIDE, not per ref, and one alert is shared across configurations, so a "new alerts since last run" filter on a single ref misses alerts first created by a scan of a different ref.** Upstream documents that the same alert can appear in multiple configurations. Two consequences for a diffing job: a `created_at > SINCE` filter on `?ref=refs/heads/<branch>` silently drops anything first seen on another branch or on a main push before SINCE, and REOPENED alerts keep their original `created_at`. Separately, changing an upload's CATEGORY (for example by deleting the workflow that produced it) leaves the OLD configuration stale, so its alerts never auto-close until that stale configuration is deleted.

215. **Mark a PR's review state current before handing it to a human, and expect bot findings to be ANCHORED to a stale commit even when the API says otherwise.** Restates the practical half of `#201`: update the reviewer summary and resolve or reply to bot threads once their findings are fixed. The additional mechanic worth checking per bot: one AI reviewer stamps a `Last reviewed commit` in its summary body that can sit a commit behind head, the same staleness trap as another bot's footer SHA, so read the BODY footer rather than the comment timestamp before refuting a finding as already-fixed.

216. **Pasting a rendered plan or manifest into a PR body: strip ANSI, trim to the changed hunk, and do not hand-edit a normalised block back into raw output.** Four mechanics, each of which cost a round. (1) Production plan runs come back COLORED, so strip ANSI before pasting. (2) Cut each environment's output from `Terraform will perform the following actions` through `Plan:` rather than pasting the whole run. (3) **A heredoc-embedded YAML diff marks its changes at COLUMN 10** (characters 0 to 9 blank, character 10 one of `+-~`), so a regex like `^\s*[+-~]` matches EVERY YAML line, because `+-~` inside a bracket expression is a character RANGE. (4) Trimming the heredoc to the changed hunk also keeps incidental infrastructure detail (database egress IPs) out of a public body. **And when a `<details>` block in an existing body is already yq-NORMALISED rather than raw render output, edit it minimally in that same style and prove equality with a `yq sort_keys` diff against the raw render**, or the body diff fills with spurious indentation churn that hides the real change.

217. **A two-lens review leaks through the SHARED MEMORY HIVE, and the prompt-text isolation gate cannot see that channel.** Two independent hits. In both cases the grep-based prompt-isolation gate passed, because nothing leaked through the PROMPT. ✅ **Rule: hold `bd remember` of review findings until the adversarial lens has RETURNED**, or write them after the revise round. Independence is the only thing the second lens is bought for, and a shared knowledge layer is an invisible channel into it.

218. **Once a PR is ENQUEUED in a GitHub merge queue, a fix-mode reviewer cannot push to it, and merging around the queue costs every other in-flight PR a CI rerun.** Pushes to an enqueued branch fail with `GH006 Protected branch update failed ... A pull request for this branch has been added to a merge queue`. ✅ **A fix-mode review must check queue state UP FRONT** (`gh api graphql pullRequest{mergeQueueEntry{state position}}`) and, if enqueued, report its fixes as UNFIXED with the diff rather than dequeue: dequeueing is the owner's call, not the reviewer's. ⚠️ Related cost that constrains any bot merge path: a DIRECT merge into a merge-queue branch (by a ruleset bypass actor) INVALIDATES the queue's temporary branches and RESTARTS CI for the queued groups, so an out-of-queue bot merge is not free even when it is permitted.

219. **Three owner preferences about the SHAPE of a review on someone else's PR.** (1) **A blocker goes in as an INLINE line comment** (COMMENT event, with a suggestion block when the fix is small), not a request-changes review. 220. **Review-bot roster additions and the per-repository wait budget. Extends `#193`.** (1) **A cloud-review connector bot** posts a TOP-LEVEL issue comment carrying a `codex-review-state:v1` JSON marker (with `commit_sha` and `has_any_findings`); its findings, if any, arrive as INLINE comments. Detect completion by that marker, not by a check state. (2) **A repository's OWN in-repo AI review workflow** (triggered by a slash command, two-model with a synthesis step) posts a PR REVIEW whose body ends with a `<!-- ai-review:reviewed <sha> -->` marker, with inline findings tagged `<!-- ai-review:finding -->`; findings folded into the body have NO THREAD to resolve, so they cannot be adjudicated the way a bot thread can. 221. **A chart template that is GATED OFF in the environments CI renders is invisible to every offline gate, and the measured mutation numbers say how little the gates catch.** Two mutation passes on one repository. 222. **Where a values repository tracks a branch while the CHART VERSION comes from somewhere else, the MERGE is the trigger: render the CURRENTLY LIVE chart version against the PR's values, not only the target version.** On such a split, merging a values change before applying the chart-version bump makes the live controller render the OLD chart with the NEW values, which failed closed on a required-value error and held the whole release back. ✅ The safe order is apply the version bump FIRST (verify it renders byte-identically against the current values), THEN merge. ⚠️ **Review implication: a finding of this shape is correctly graded by what it does on failure.** The adversarial lens graded it blocking; the revise round downgraded it to non-blocking once shown that it FAILS CLOSED (nothing syncs or prunes) and that the owner sequences the apply before the merge. 224. **Running an auto-merge bot (Bulldozer v1.19.3) in front of a merge queue: the design tradeoff that decided it, and the six source-level facts that decide whether it works at all.** **Tradeoff:** a self-merging bump WORKFLOW is one-shot (it gets one chance inside the build run, so a flaky rerun, a runner timeout, a base conflict or a lifted hold STRANDS the PR), while a reconciling BOT re-evaluates on every event and merges whenever conditions become true, holds no runner, and gives one in-repo config for every PR source. That is what flipped the recommendation to the bot. **Facts, all source-verified at v1.19.3:** (1) **It cannot use the GitHub merge queue:** it merges via the REST merge endpoint (`bulldozer/merge.go:97`; queue support is an open upstream issue), so on a queue-required branch its App needs a ruleset BYPASS, and a bypassing direct merge restarts CI for everything queued. (2) **It reads required checks only from CLASSIC branch protection** (`pull/github_context.go:166-200`), so on a repository using rulesets there are none and the in-repo `required_statuses` list is the ONLY gate. (3) **`branches`/`branch_patterns` signals match the PR's TARGET (base) branch, anchored `^pattern$`** (`bulldozer/signals.go:296-330`), and NO signal filters on head branch or on AUTHOR, so trigger bot PRs with a LABEL and pair it with a ruleset restricting who can push those branches. (4) **The server's `configuration_path` defaults to `.bulldozer.yml`** (`server/handler/options.go:26`), so a repository config named `.bulldozer.yaml` is IGNORED unless the server config overrides it. (5) **It acknowledges a webhook with HTTP 200 BEFORE processing it** via an async scheduler (`server/server.go:105`); a handler failure is never requeued and GitHub does not redeliver, so an eligible PR simply waits for the next event, and `/api/health` is STATIC, so a bad private key still reports healthy. Check enablement with an authenticated webhook DELIVERY, not readiness. (6) **The App ID is read with a silent integer parse** (`go-githubapp` `githubapp/config.go:61-67`), so a secret value with a TRAILING NEWLINE leaves it at 0, and a webhook secret with one fails every HMAC: create such secret versions with `printf '%s'`, since a secrets operator passes bytes through unchanged. **Image: `FROM scratch`, amd64-only, no `USER`**, binary at a fixed path mode 0755, health `GET /api/health`, webhook `POST /api/github/hook`, so a non-root UID plus a read-only root filesystem works. ⚠️ **One repository-shape fact that any auto-bump design must absorb:** a chart-version bump check that fires on ANY path under a chart directory, combined with a `.helmignore` that EXCLUDES the values directory, forces a version bump that ships byte-identical package content on every image-tag-only PR.

225. **A previously-run image-bump automation at another estate, as prior art: what its design got right and the one failure mode that cost the most.** Shape: a reusable CI workflow opened the bump PR with a **PERSONAL ACCESS TOKEN rather than the default CI token, specifically so that required checks RUN** (a default-token push does not trigger them); the branch was keyed on the TARGET FILE rather than the tag (`auto-update/<service>-<file>`), so repeated bumps REUSE one PR instead of accumulating; and PRs carried a bundle-and-environment label plus a generic automation label. The auto-merge bot ran single-replica. ⚠️ **Main failure: an auto-merge trigger matching the automation label on PRs that LACKED a merge label re-merged the default branch forever.** ⚠️ **Scale failure: check-run webhook events were 69 percent of a 15k-per-hour App rate limit**, fixed with a 250 MB cache plus an hourly stuck-PR sweep. ⚠️ **Review bypass for bot PRs lives ONLY in the forge's ruleset settings, not in git**, so it is invisible to anyone reading the repository. ✅ Carry all four into any new bump design: token choice, branch keying, label semantics, and the rate-limit budget.
