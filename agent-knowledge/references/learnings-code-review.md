# Learnings: Code Review

Patterns, gotchas, and best practices for PR review workflows.

See also: `learnings-progressive-delivery.md`, `learnings-agent-workflow.md`, `learnings-confluence.md`, `learnings-envoy-gateway.md`

## Entries

1. **Known review bots post asynchronously.** Wait for bot reviews (CodeRabbit, Cursor Bugbot) before starting your own pass — they may take several minutes. Poll with a timeout rather than blocking indefinitely.

2. **Reply to every bot finding explicitly.** Silent ignoring creates ambiguity for human reviewers. Classify each finding as fixed, acknowledged, disagreed, or out-of-scope.

3. **Bot false positives are common for YAML-only PRs.** Security scanners and code-quality bots may flag values files, namespace labels, or config-only changes that have no real risk. Document these patterns so future reviewers don't waste time re-evaluating.

4. **CI check context matters.** A passing CI run on a values-only PR may not exercise the actual Helm rendering. Verify with `helm template` locally when CI only runs linting.

5. **Cap fix iterations at 2.** After two rounds of fixes, document remaining issues and hand off to a human. Unbounded iteration loops waste tokens and rarely converge on non-trivial disagreements.

6. **A bot can be "done" without a new comment.** Some reviewers (e.g. CodeRabbit) update their existing "review in progress" comment in place — the comment count never increments and the reviews list stays empty; detect completion by a marker in the comment **body**. Cursor Bugbot's authoritative commit is its footer (`Reviewed … for commit <SHA>`), not the visible `diff_hunk` — if that SHA is not current `HEAD`, it scanned a stale commit and its findings may already be fixed. Verify against `HEAD` before acting.

7. **Reply *and* resolve.** A threaded reply alone leaves a bot finding open. Drive each to resolved — a bot resolve command (`@coderabbitai resolve`) or the host's `resolveReviewThread` GraphQL mutation for bots that do not self-resolve. Only resolve a thread you actually addressed (fixed / disagreed-with-reason / acknowledged). Target zero open bot threads at hand-off.

8. **Rendered proof beats source-diff reading.** For Helm/values PRs, render the chart at the `git merge-base` and at `HEAD`, then diff the *manifests* — a values change can be inert (disabled component, wrong key, deep-merge override) or blast wider than the source implies. Always include a **negative control** (an untouched chart whose rendered diff must be empty) to prove the render harness actually surfaces changes. Source changed but rendered diff empty = a blocking finding, not a pass.

9. **Cross-model verify high-blast findings.** On sensitive PRs (RBAC, secrets, production manifests), do not assert a blocking finding — or a clean verdict — on one model's judgment. Dispatch a different model/runtime to *refute* each blocking finding (default-to-refuted); keep only what survives, and surface splits to the human rather than silently picking a side.

10. **Anchor behavior-preservation proofs at the `git merge-base`, not the immediate parent.** With multiple commits, the parent only proves the last commit is conservative; earlier commits in the PR may have widened scope. `git merge-base origin/main <tip>` is the true baseline for render-diff and before/after proofs.

## Entries (continued)

11. **Every automated gate you run is a correctness gate; none of them is a minimality gate, so unnecessary complexity is invisible to the entire review stack.** Render/lint checks, a policy-conformance scanner, a server-side dry-run, and even a two-model adversarial review can all go green identically on a needlessly duplicated implementation and on its much shorter equivalent — a change that duplicates a template four times over can pass every gate while a same-day human rewrite cuts most of its line count. This is not a knowledge gap: reviewers (human and model) can independently state a simplicity rule and still fail to apply it to their own output, because an agent that just wrote 900 lines will self-certify as simple. The fix that actually lands is a checkable counting rule added to the review checklist — flag near-duplicate blocks above a similarity threshold, redundant guards on one field, unreachable branches, values/config keys derivable from other values — not more prose asking for simplicity. A missing gate wants a gate, not another paragraph of guidance.

12. **Never use `git diff <default-branch> --stat` as a PR's blast-radius check — the branch tip moves while you are still working.** Any fetch or remote refresh mid-task can advance the ref, so the diff silently compares against unrelated commits that landed in the meantime and can report hundreds of unrelated files changed for what is really a two-line PR. The authoritative alternatives compute the true merge base: the hosting platform's own PR-diff command (which resolves the merge base server-side), or locally `git diff $(git merge-base HEAD <default-branch>) HEAD --stat`. This matters most on any PR you'd otherwise flag as suspiciously large — a false 300+-file reading triggers a stop-and-report that a two-second re-check would have avoided.

13. **A CI status API can be unreliable once a PR has merged and its head branch is deleted — read the merge commit's own check-runs instead of the PR's.** Two independent distortions stack: cancelled runs get bucketed as failures, and jobs still queued at merge time eventually get a runner and die at checkout because the head branch no longer exists — which surfaces as a genuine-looking failure on an unrelated job. The tell is an absurd duration (a lint job "running" for hours is runner backlog, not a slow job). Correct method: query the check-runs of the merge commit's SHA directly (e.g. GitHub's `repos/{owner}/{repo}/commits/{sha}/check-runs`), which is the authoritative signal for whether the default branch is actually healthy — then confirm functionally (local lint/render, live state) rather than trusting any CI status bucket.

14. **`yq eval-all` silently cross-products when you extract paired fields from a multi-document YAML stream — it can fabricate evidence on a promotion or rollout proof.** `eval-all` merges every document in the stream into one root context before evaluating the expression, so `.metadata.name` returns a *sequence* of every document's name, and a `+` concatenation joins them cartesian-style: N documents each contributing two fields produce name/value pairings that read as plausible individual rows but are wrong. On a staged control-plane-before-data-plane promotion this can make it look like the control plane moved when it did not. Fix: use `yq eval` (per-document, evaluated independently) — never `eval-all` — for this class of query, and cross-check with an unrelated extractor (e.g. a plain `awk` pass); agreement between two independently-implemented methods is the real proof. The same cross-product applies to `join()` under `eval-all`. (yq v4, mikefarah/yq.)

15. **Triage every PR into a small number of review-depth tiers by blast radius, and make rendered proof mandatory for the tiers that touch declarative infrastructure.** A useful split: trivial (docs, single-value config changes) / standard (most logic changes) / sensitive (RBAC, secrets, network policy, alert routing, any production-cluster manifest, CRD/operator changes). For chart or values-file PRs at standard-or-above, render the affected artifact at the merge base and at the PR head and diff the *rendered* output, not just the source — and require a negative control (an untouched target whose rendered diff must be empty) so an empty diff on the real target is a blocking finding, not a pass. Sensitive-tier PRs additionally get adversarial cross-model verification of every blocking finding, defaulting to refuted until a second model reproduces it. Detect a review bot's actual completion by an in-place marker in its comment body, not by comment count — some bots update one comment in place rather than posting new ones.

16. **When two review passes disagree on severity, first check whether they disagree on the FACTS or only on how to GRADE the same facts.** If both passes independently arrived at the same underlying facts and only differ on classification or weighting, the adjudication is "fix what both flagged, then decide the grading question on its merits" — not "pick a winner." Two companion rules from the same class of split: (1) do not treat a lighter-weight automated bot as categorically lower-tier than a deeper manual or model-driven pass — a scanning bot can spot a root cause that two more thorough passes each only see a fragment of; (2) in any catalog- or allowlist-style design, "this change requires no edit to any consumer" is a *blast-radius* property, not a *safety* property — adding a member to a shared package or group silently grants it to every consumer that already selects that package, with no consumer-side diff for anyone to review. Watch for that inversion whenever a values-driven or catalog-driven allowlist is the surface under review.

17. **Running two independent review lenses (one correctness-focused, one adversarial) is only valuable if you post both findings and let the divergence stand — averaging or silently reconciling them destroys the reason you paid for a second pass.** Give each lens its own full, independent pass over the same PR at HEAD, in isolation from the other's findings — the adversarial lens should actively try to break the PR's own claims rather than just re-reviewing for style. Observed patterns worth expecting: convergence (both lenses independently catch the same real bug by different routes) is a strong signal, not redundancy; a more adversarial second lens tends to escalate documented-but-unenforced conventions that a purely correctness-focused pass discounts as future work, and it surfaces ordering/lifecycle hazards (e.g. deleting before replacing, rather than replacing then pruning) that a same-model pass tends to miss because it shares the first pass's blind spots. Post both lenses' findings and flag the split explicitly rather than resolving it yourself; a reviewer who "fixes" a genuine disagreement by editing the artifact has thrown away the signal the second lens existed to produce.

18. **A security-policy finding measured against a permissive target must be re-verified against a strict target before it is called blocking.** A high count or volume of connections observed on the one environment whose policy posture is permissive (or matches neither your test nor your production posture) can look like proof that a policy change breaks a real flow — but on a genuinely strict target the same flow is typically orders of magnitude smaller and already includes real rejections by design. An allow-style policy change cannot break what a stricter policy already denies, so no exception is usually needed. General rule: know which of your environments are permissive-by-design and permanently so, and re-measure any authorization- or mTLS-adjacent finding on a strict environment before grading its severity — a finding measured only on the wrong posture is the cheapest way to post a wrong blocker on someone else's PR.

19. **Three shipped-artifact conventions worth applying without being asked.** (1) **Rendered Helm manifests belong in the PR DESCRIPTION**, inside a collapsible `<details>` block (bodies are effectively capped at a few dozen visible lines and only `<details>` contents are exempt), **never checked into the repo**; show only the chart's OWN objects (filter on `# Source: <chart>/templates/`) and omit vendored subchart output. Regenerate them from a bash SCRIPT FILE rather than a piped `helm template`, so a token-reducing shell wrapper cannot truncate the output mid-render. (2) **Do NOT check validation, behavioural-test or analysis REPORTS into the chart repo** — they belong in the wiki/tracker, and a chart README should link the durable proposal rather than an in-repo report path. (3) **Do NOT link specific PR numbers in READMEs or committed docs** — they rot, and a reader should be able to dig. **Hint the durable LOCATION instead**: "the deny exception lives in `<repo>` under `config/policies/iam_deny/`", "controller identity lives in `<repo>` under `stacks/.../customers/<cluster>/`". PR links are fine in ephemeral PR bodies and comments.
    - **Per-cluster override values files do NOT use the `# --` doc-comment convention** — that applies only to base `values.yaml` files, for `helm-docs`. Bots flag this as a nitpick; it is non-blocking and should be **disagreed with, citing sibling files as evidence.** **Generalises: when a bot demands per-occurrence documentation on the Nth mechanical repetition of a documented pattern, the counter-evidence is the existing undocumented POPULATION plus the single DEFINING site — cite both, and keep the rationale where the next batch author will find it.**
    - **`comment-discipline.sh` counts each line of a `{{/* … */}}` block separately** (open line + content + close line = 3), so a 3-line docblock trips a 2-line ceiling even when the content is one sentence — use the single-line `{{/* content */}}` form. The gate diffs against `$(git merge-base origin/<default-branch> HEAD)...HEAD`, so **check against the REMOTE default branch, not a stale local one**, or files outside the PR's diff produce spurious findings.

20. **Cursor Bugbot can post its summary EMBEDDED in the PR body itself, not as a separate comment or review object.** On one PR both `gh api pulls/<n>/reviews` and `issues/<n>/comments` returned zero `cursor[bot]` rows, yet `gh pr view --json body` carried a complete `<!-- CURSOR_SUMMARY -->…<!-- /CURSOR_SUMMARY -->` block with a "Reviewed by Cursor Bugbot for commit `<sha>`" footer and a verdict. **A bot-polling loop that reads only reviews + issue comments + inline comments undercounts this shape** — also grep the PR body for `CURSOR_SUMMARY` before concluding Bugbot timed out or never ran. The footer SHA is still the ground-truth staleness check: confirm it equals HEAD before trusting the embedded verdict.

21. **A `.gotmpl` consumed as a Crossplane Composition inline template makes its COMMENTS shipped cluster payload, so a comment-only edit is a rendered-manifest change on every consuming target.** Review consequences: (a) never assume a comment-only diff is inert on these files — render it; (b) an **audit record** belongs in the design doc, while the template keeps only the load-bearing two-line reason a block exists plus a pointer that **names** the doc — never a local filesystem path, which is both a dead link for reviewers and shipped verbatim to clusters; (c) measure comment density with the author's own formula so before/after are comparable, and against a sibling template's ceiling; (d) an *added-lines* comment-ratio gate is unsatisfiable on a small diff that legitimately retains rationale — report it, do not delete a load-bearing comment to clear it.

22. **When one guard emits a SHARED error message across N keys, re-read that message against every key, not just the one being added.** On one PR the adversarial lens caught what the correctness lens missed: a denylist loop whose single `fail()` said each blocked key *"configures a security-sensitive surface (… object versioning …)"*. That was false for the newly added key, which never *configures* versioning — it makes versioning **unsupported**. A claimant hitting the error would hunt for a setting they never wrote. The fix was additive and needle-safe (*"… or makes one inoperative"*); confirm first that no test asserts the message tail and that any assertion needle precedes the edit. **Generalisation: adding a member to an existing guarded set is also an edit to every message, doc string and enum that set feeds.**

23. **On a two-lens judgment SPLIT, escalate and record — never silently reconcile, and never "fix" it by editing the live artifact.** On one guardrail PR the adversarial lens argued a cloud logging-bucket key fails a *data-movement* criterion (object-storage access logs carry client IPs, request URIs and **object names**, which routinely encode customer identifiers) while the correctness lens and the author had classified it metadata-class-allowed. Both readings were factually correct; they weighted the same evidence differently. Correct handling: (a) post both lenses with an explicit pointer at the divergence, (b) record it in the design doc as a **named approved exception** with the containment that justifies it **and the condition that would reverse it**, (c) leave the live blocklist untouched — adding a key to a guardrail running on every consuming cluster is the owner's decision, not the reviewer's. A reviewer who resolves the split by editing has destroyed the signal the second lens was bought for.

24. **A production table mirrored into a hand-transcribed test table is only as complete as the TEST table — pin the two key sets equal, or a production-only row ships untested.** When a suite keeps a deliberately independent transcription of a production list, its "covers all N kinds" count, its class counts, its per-row assertions AND its table-driven negative-control loop **all read the TEST table** — so "driven off the production list, so a future row cannot ship without its control" is true only for rows already in the test table. Reproduce it: add a row to the production table **alone** and watch the suite still pass with no control, no assertion and no count change. **Cheap fix that works — assert the symmetric difference is empty:** `assert_eq … "" "$(comm -3 <(<extract keys from the production file> | sort) <(<extract keys from the test table> | sort) | tr -d '\t' | paste -sd, -)"`. **Mutation-test BOTH directions (production-only row, test-only row) — a one-directional check is the trap.** Generalises to any test that re-states a production table rather than deriving from it.

25. **Two review-workflow gotchas that silently no-op a fix pass.** (a) A diff-scoped gate invoked as `comment-discipline.sh --base <ref>` diffs `merge-base...HEAD` — **committed state only**. Editing the working tree and re-running it reports the OLD findings unchanged, which reads as "my fix didn't work." Use the stdin form to check uncommitted work: `git diff origin/<default-branch> | comment-discipline.sh -`. (b) **Trimming comments in a `.gotmpl` is NOT an inert edit.** A function-go-templating body is loaded verbatim via `.Files.Get` and embedded into the rendered Composition, so its comments are **rendered payload** an operator reads on-cluster — a comment-only change alters rendered output and must be re-proved with the render matrix, not assumed no-op. Same reason a `fail()` message string is operator-facing and worth reviewing for accuracy, not just for compiling.

26. **An adversarial-lens dispatch is NOT done just because your end-marker grep returns a hit — `codex-dispatch.sh` echoes the full prompt into the output file, so the marker you asked for appears once as prompt echo while the run is still mid-flight.** On one review `grep -c '=== END OF ADVERSARIAL REPORT ==='` returned `1` at the prompt-echo line, and `awk` reported that as the LAST match — the run was roughly 60 % through, with four `[VERIFIED]` sections and its verdict still to emit. The correct completion test is all three: (a) the **last** marker line number is far past the prompt echo, or the count is >= 2; (b) `pgrep -f 'codex exec'` finds nothing; (c) the file **stopped growing** — sample `wc -c` about 45 s apart. The near-miss was re-dispatching a healthy run: `pgrep -fl codex` matched only the shell wrapper and looked ambiguous, but a 45 s byte-delta of +9411 proved it alive. This sharpens the general "don't judge a background run by pgrep plus a log tail" rule with the specific artifact that defeats it — the prompt echo.

27. **For a Crossplane provider-family promotion, prove one-registry-one-version-per-cloud at RUNTIME, not by repo grep.** `kubectl get providers.pkg.crossplane.io` on the TARGET cluster shows the transitive `upbound-provider-family-<cloud>` pinned by TAG (e.g. `provider-family-gcp:v2.6.0`). If the family being promoted resolves to a different version, installing it forces a family-provider upgrade *underneath* the already-running providers on that cluster — that churn, not the values-file skew, is the real failure mode the invariant guards. Also resolve the digests ALREADY pinned for the other families on that cloud, since a PR body typically shows only the new ones. Complementary checks worth adding: `crane manifest` to confirm the digest is a multi-platform index (`linux/amd64` + `linux/arm64`), and the exported `package.yaml` to confirm it is the RIGHT package with the expected family dependency — a valid-looking digest for the wrong package renders and lints perfectly.

28. **A committed-state-only lint gate re-run after an unstaged edit reports the old violation and reads as "my fix didn't work".** Commit first, then re-run to confirm `clean`. Related judgment call, settled more than once: when the flagged comment is byte-identical to one ALREADY merged on the default branch in sibling files, the consistency argument is exactly the reasoning the gate was built to remove — fix the new files and file the sibling sweep as a follow-up; do not extend the violation for symmetry. Cheap proof that a comment-only fix is safe on a chart PR: re-render every target and assert byte-identical output to the pre-fix render, which also re-validates any rendered-manifest blocks in the PR body.

29. **Measured two-lens divergences: the lenses NEVER disagree on arithmetic — they disagree on SOURCE, METHOD, SCOPE, CLASSIFICATION or INTERPRETATION, and the correctness lens's systematic weakness is grounding a RUNTIME claim in a repo render.** Across repeated deep reviews the lenses agreed on every rendered and arithmetic fact, and the entire value of the second lens was one divergence per review:
    - **SOURCE** — live controller state vs what the repo render says; capacity scoped by the workload's own selector vs counted globally. The correctness lens can hold the refuting datum and not draw the inference.
    - **METHOD** — comparing permission-NAME unions (blind to scope) vs comparing per-binding ownership. Same source, different comparison.
    - **SCOPE OF THE QUESTION** — asked "can anything fire", the correctness lens answers for the rules the diff ADDS; the adversarial lens notes a PRE-EXISTING rule becomes ARMED by the new traffic. **When a dispatch asks "will anything fire", answer for the whole rule set the change ACTIVATES, not only the rules the diff adds.**
    - **CLASSIFICATION** — whether a pre-existing CI-gate gap is "blocking" or "follow-up" when the remedy lives outside the diff. **Post both and let the human adjudicate; never silently reconcile** (#23).
    - **INTERPRETATION, NOT COLLECTION** — full convergence on every measured fact, divergence on ONE sentence of prose, where the correctness lens **already HELD the refuting datum** in its own census and had not drawn the inference. **So "my census already covers that" is NOT a reason to skip the adversarial pass.**
    **COUNTERMEASURE for future dispatches: enumerate every RUNTIME/CAPACITY claim explicitly and require a live read for each BEFORE drafting the correctness lens** — that is the whole of the observed edge. **Complementarity runs both ways**: an offline adversarial lens cannot query live state, which the correctness lens can. Two dispatch facts: send the adversarial lens to a **detached worktree at HEAD**, and budget roughly 90 minutes for a deep CRD/XRD review. The second lens can earn its cost three distinct ways even on a thoroughly self-verified PR: finding the test-coverage CLASS (mutation adequacy vs non-vacuity); catching a branch the first sweep never rendered because the suite default hid it; and raising a class the first lens never tested for (a permissive regex admitting identifiers the cloud API rejects).

30. **A learnings entry written by the PR's own author, and the dispatch prompt's characterisation of the evidence, are both CLAIMS UNDER REVIEW — never verification.** On one heavily self-verified PR the two lenses CONVERGED rather than diverged: both independently found the same single defect (a mis-transcribed byte count) and agreed on every substantive fact. That is a different value profile from the disjoint-findings case — here the lenses' worth was **CONFIRMATION of a high-stakes claim**, not new findings, which is the correct expectation when author evidence is already thorough. Two review-design consequences, both cheap and both load-bearing: (a) the author had consolidated that PR's findings into a learnings file **BEFORE** review, so the learnings file stated the answer to the very question the reviewer was dispatched to determine — **go to the primary source, the prior PRs' own text, instead**; (b) the dispatch prompt's framing of the top-priority question was itself the misreading, and **a reviewer that trusts the dispatch's characterisation of the evidence inherits its error** — read the prior PR bodies verbatim before accepting a premise the dispatch asserts. Same family as never resolving a thread on the dispatch prompt's say-so.

31. **A reviewer fix-push AUTO-DISMISSES a human approval already on the PR — check before pushing in fix mode.** On one PR a human approved and the next reviewer-agent **test-only** push flipped `reviewDecision` back to `REVIEW_REQUIRED`. Run `gh pr view <n> --json reviews,reviewDecision` BEFORE any push in fix mode; if an approval exists, either weigh whether the fix is worth invalidating it, or push and **flag the dismissal explicitly in the summary comment** so the human knows to re-approve. **It is not visible in `gh pr checks` or the comment stream — the `DISMISSED` review row is the only tell.**

## Bot mechanics, PR-body claims and mutation proofs

32. **Copilot code review posts as `copilot-pull-request-reviewer[bot]` into `reviews[]` as `state=COMMENTED` — NOT into `issues/<n>/comments` — so an issue-comment poller never sees it.** It re-reviews on **every push**; each review and inline comment carries a `commit_id`, so compare against HEAD or you act on a stale scan (same trap as Cursor Bugbot). **Its summary body hides real findings inside `<details><summary>Suppressed comments</summary>` blocks.** Two follow-on rules: **(a) suppressed comments are LATENT, not dismissed** — on the NEXT re-review, triggered by any push, Copilot can promote the same finding to a real inline thread with a **new comment id**, so resolving all visible threads is not terminal; re-enumerate `reviewThreads` AFTER your push or you hand off with an open bot thread you already answered elsewhere. **(b) On a force-push Copilot's inline `commit_id` is REBASED to HEAD — use `original_commit_id` as the staleness ground truth.** ⚠️ **Which bots run is a per-repo INSTANCE fact and guidance about it goes stale fast** — a note that Copilot was the only review bot on one repo was refuted days later when `cursor[bot]` was observed running there. Check the repo, do not carry the list.

33. **Copilot grounds its "not in the PR's stated scope" findings in the PR BODY TEXT, and re-reads the body on every re-review.** Four of five findings on one PR were **body bugs, not code bugs** — the change was maintainer-requested but undescribed. **Fix the body BEFORE or in the same beat as the push**, otherwise the re-review quotes the stale body and re-raises the same objections verbatim (it did: *"conflicts with the PR description's claim that the change only loosens"*).

34. **PR-body correctness is a REVIEW SURFACE, not metadata — and a body already "corrected" once is not clean.** On one PR a corrected body still carried **six** factual errors: the wrong base branch in its stack table, a render proof anchored at the default branch instead of the real merge-base, and a CI paragraph claiming two jobs were pre-existing failures when one had passed and the other was not even in the check set. **Always re-derive the base from `gh pr view --json baseRefName` and re-read CI live; never trust a prose CI claim in a body.**

35. **A PR-body correction does NOT propagate to the code — grep the diff for the same claim before accepting the fix.** On one PR the false claim *"Defaults to PROD so an unset value gets the strictest posture"* was removed from the body but left **verbatim in the docstring that same PR ADDS**. The repo would have shipped the falsehood permanently while the body carried the correction. **When a review forces a factual correction to a body, grep the diff for that claim in code, docstrings and comments.**

36. **When a finding is dispositioned as "deferred to PR N", VERIFY PR N actually contains the promised work.** A deferral is a claim about another artifact and must be grounded like any other claim. One PR deferred seam tests to a later PR **twice, across two review rounds**; `gh pr diff <N>` showed that PR's diff added **ZERO** references to either function named, and zero matches for the settings symbol in its test file — the promised test did not exist.

37. **Never `head`-truncate a PR comment listing: the truncated tail is exactly where a superseding comment lives.** Reading comments with `gh api issues/<n>/comments | head -N` silently dropped a LATER plan-output comment that superseded an earlier one — the newest said *"4 to destroy"*, not *"1"* — which made a reviewer clear a stale-plan finding that the adversarial lens then correctly reopened. **Count first (`jq length`) and read the newest by `created_at`.** Same class as trusting a bot's `diff_hunk` over its `commit_id`.

38. **GitHub creates NO `pull_request` workflow run while a PR is CONFLICTING — the entire Actions suite goes silently absent while the PR still looks green.** GitHub cannot build `refs/pull/N/merge`, so `pull_request`-triggered workflows do not run at all; meanwhile **head-SHA-keyed apps (Cursor, renovate, cloud build integrations) keep firing**, so the PR shows a small green check set and reads as fine. In a stacked PR this is easy to cause — one import-line edit colliding with the base branch is enough. **Detect via `commits/<sha>/check-suites`: a MISSING `github-actions` suite, plus `gh pr view --json mergeable` returning `CONFLICTING`** (API form: `mergeable=false` / `mergeable_state=dirty`). Resolve with a normal merge of the base branch — no force-push — and the suite appears within seconds.

39. **GitHub actions taken by an agent through `gh` and actions taken by the human appear as the SAME actor login, because the agent uses the user's token — so an agent CANNOT source-attribute anything in a PR timeline.** On one PR a subagent saw `ready_for_review` plus a merge attributed to the account owner, concluded an unreviewed auto-merge bot existed, and **filed a false security finding**; in fact the owner had readied and merged it deliberately and a human had reviewed it. **Before raising an "unauthorised automation" alarm from timeline actors, check the conversation and `gh pr view --json mergedBy,reviews` — and note that the NULL HYPOTHESIS IS "the human did it", not "a bot did it".** Corollary: agents should stop force-reverting a human's `ready_for_review`; leave draft state as found.

40. **Replies posted via `gh api` go out under the user's own account with no agent marker — the attribution sign-off must be in the FIRST post, never patched in.** An edit leaves the original text in the notification email a reviewer has already received. **Same for commit SHAs: never cite a SHA in a public comment before running `git log` to read it.** `gh api` path trap while fixing such a comment: **editing a PR/issue COMMENT omits the issue number** — `repos/{owner}/{repo}/issues/comments/{comment_id}` (GET/PATCH). The intuitive `…/issues/{num}/comments/{id}` **404s**; that path only accepts POST-to-collection. **Inline REVIEW comments are a different tree entirely:** `repos/{owner}/{repo}/pulls/{num}/comments/{id}/replies` to thread a reply.

41. **Reviewing a Python PR with no installed venv: AST-EXTRACT the real definitions and `exec` them — never transcribe constants or test bodies into a harness, because that only guards your own copy.** Pull the real `ClassDef`/`FunctionDef` out of the real source file (`ast.get_source_segment`) and `exec` it; import the real module via `importlib.util.spec_from_file_location` with **only its narrowest dependency stubbed into `sys.modules`**; run the whole thing under `uv run --no-project --with pydantic --default-index https://pypi.org/simple` to bypass a repo's private index. This produced a full four-value routing matrix, an exhaustive accept/reject sweep and a six-mutation adequacy suite **without ever installing the project**. Stubbing detail that matters: make the stub's `__getattr__` return a dynamically created **CLASS**, not a `SimpleNamespace` — pydantic uses these as type annotations and an instance raises *"unhashable type"*.

42. **When a refactor adds an INERT parameter (threaded now, read later), the strongest proof is STRUCTURAL, not empirical — and the real finding is usually the test coverage cliff.** Show the parameter is **never referenced in the callee body**, so output cannot depend on it for ANY value; a render diff over N sampled values is strictly weaker. Then check whether the EXISTING tests pass the new parameter: on one PR **22 of 22 test call sites passed no `environment=` and took the signature default**, so when a later PR makes it load-bearing the whole suite silently keeps asserting only the default. **That coverage cliff is invisible to both a render proof and a mutation run**, and the PR's own disposition comment asserted the opposite.

43. **For a PR whose value is a SEAM rather than a behaviour, proving the no-op is the EASY half — the load-bearing questions are whether any test pins the wiring, and what other code does the same job without the new parameter.** Both lenses proved byte-identical renders with negative controls on one plumbing PR, and the correctness lens stopped there; only the adversarial lens (a) ran real mutation testing showing that **unwiring the new seam left all 97 tests GREEN**, and (b) found a **sibling scheduling path a `node_selector` grep could not reach**, because the other renderer used different template key names. **Output assertions cannot prove a seam is connected:** mutations that drop the public renderer's keyword *and* mutations that hardcode a value inside the private builder can both stay green. **Pin the boundary explicitly** — assert that the renderer forwards the settings value and that the builder forwards its parameter to the consumer.

44. **Mutate the CROSS-PRODUCT of a guard's parametrised axis with the OTHER branch axes — a parametrised test set looks exhaustive along its own axis while being blind on every axis it does not vary.** Proof from one PR where the two lenses each found a survivor the other missed, from independent spec-derived mutation sets: the correctness lens found a **signature-default flip** that survived (133 passed) because every call site passes the argument explicitly; the adversarial lens found a **cross-product escape** — `environment = PROD if config.gpu else environment` survived all 133 tests, because every test in the file rendered `gpu=False`, leaving the non-prod GPU path's behaviour completely unpinned. **Derive mutations from the SPEC's edge set, not from the PR's claimed mutation list** — on that PR the author's three claimed mutations all passed re-execution while a fourth class survived. **For each threaded argument, mutate all four: (a) the outer call site, (b) the inner call site, (c) the SIGNATURE DEFAULT itself, and (d) the opposite direction** — hardcoding the non-default value — to prove detection is bidirectional rather than merely "these two differ". Note the two lenses may SPLIT on severity (required-change vs follow-up); **surface the split, do not push to resolve it.**

45. **Closing a "the seam has no coverage" gap: the test must go through the PUBLIC entry point and PATCH THE SETTINGS SINGLETON — passing the argument yourself is exactly what makes the wiring untestable.** Working shape: `with patch.object(APP_SETTINGS, "<field>", value): snapshot = <public_renderer>(…)`, then assert on the rendered output, parametrised over every enum value. Two lessons about the mutation proof itself. **(1) Re-run the mutations at CURRENT HEAD rather than trusting the finding that motivated the dispatch** — on one PR the adversarial lens's claim that BOTH mutations left the suite green was true at the commit it ran on, but by current head one had become covered by tests added in an intervening PR while the other was still caught by nothing. Reporting the stale claim verbatim would have been a false statement in the PR body; **say which mutations are newly covered and which are not.** **(2) The strongest evidence is not "my test failed" but "ONLY my test failed"** — record the full counts (`4 failed / 379 passed`, `2 failed / 381 passed`), because a mutation that also trips pre-existing tests proves less about the new coverage.

46. **A sortedness guard keyed on a LEXICOGRAPHIC tuple does not pin the invariant its consumers rely on — assert PAIRWISE DOMINANCE on every axis instead.** `assert sorted(X, key=lambda s: (s.a, s.b)) == X` permits a later element with a larger first field and a **smaller second**, so `X[-1]` silently stops being the maximal element while the test stays green. Counter-example that passed the lexicographic assertion while breaking the consumer: `(1.5, 6), (3, 64), (7, 28)` — a consumer reading `X[-1]` as "the largest" now rejects a request the middle element would have accepted. Inserting a duplicate-identity element also survived it. **When consumers read `X[-1]` as "the largest", assert `itertools.pairwise` monotonic non-decrease on EVERY axis** (which implies the lexicographic ordering and additionally pins `X[-1]` as maximal), or pin the exact ordered tuples plus identity uniqueness. Found independently by three lenses, each with a different counter-example — a sign the class is easy to reach and easy to miss.

47. **Pydantic v2: a plain `@property` is NEVER serialized by `model_dump()` — only `@computed_field` is.** So converting a `@property` to a plain method has **zero effect** on serialization output, which makes such a conversion safe to prove structurally rather than by render diff. (Verified on a `BaseModel` whose property was converted to a parameterised method.)

48. **Any PR body claiming CLEANUP of live resources is a CHECKABLE FACT — run `kubectl get` on the named objects.** On one PR the body claimed test artefacts were *"both deleted after the measurement"*; the template and three warm pods were still `Running` 38 minutes later. Both lenses caught it independently. **Live-evidence sections must be re-verified against the cluster, not just read.**

49. **A review comment's anchor is evidence; a relayed paraphrase is not.** When a review comment reaches you second-hand ("the reviewer says move X onto Y"), resolve the anchor yourself before acting. GitHub's review-comment API gives `path`, `line`/`original_line` and `original_commit_id`; `git show <original_commit_id>:<path> | sed -n '<line>p'` names the symbol the reviewer was actually pointing at. On one PR a relayed instruction named one accessor function while the anchor pointed at a **different, similarly named** function on the adjacent line range — and only one of the two could sensibly become a property on the enum it returns. Implementing the paraphrase would have produced a change the reviewer never asked for while leaving their actual comment unaddressed. Cheap check, and the anchor is unambiguous.

50. **Two confident readings of the same config field are still one unverified fact.** A PR that states an infrastructure limit as verified must name what was read, not just the value. One PR claimed a 30 s HTTPS load-balancer cap on every API request, citing `gcloud compute backend-services list` showing `timeoutSec: 30`. The field was read correctly; what went unread was the backend it applies to. The backend service's only backend was a **SERVERLESS** NEG, and GCP ignores `timeout_sec` for serverless NEG backends — the real ceiling is the Cloud Run request timeout. Production load-balancer logs settled it: 58.4 s and 174.2 s requests, both status 200, impossible under the claimed cap. Two lessons, in order of how much they cost: **(a)** for any GCP backend-service timeout, read `networkEndpointType` on the attached backend before quoting the number — serverless makes it inert; **(b)** a claim of the form "X caps every request at N" is falsifiable in one query against request logs, so a PR asserting it without that query has not verified it. The reviewer's "we definitely had requests which took more than 30 seconds" was worth more than the console field, because recollection of observed behaviour beats a config value whose applicability was never checked.

51. **Never grade a latency PR on a handful of sampled events — compute the DISTRIBUTION, then state the SHARE the fix addresses.** Reviewing an image-streaming PR, the correctness lens was wrong twice before measurement settled it: draft 1 reasoned from vendor docs plus non-streaming production pull times and concluded streaming could not clear a 29 s budget (refuted by a cold-pull measurement on an already-enabled pool: 15 GB in 4.7 s); draft 2 swung to "big win, fixes it" (refuted by the distribution). **n=400 for the exact production image was strictly BIMODAL: median 0.358 s, p75 0.436 s, then p90 97.7 s / p95 108 s / max 136 s — 11.5 % over the budget, and NOTHING between 0.44 s and 97 s.** A `head -20` sample showed both modes and made the slow mode look typical; it is 11.5 %. **The bimodality IS the finding** — a fix that targets the slow mode fixes only its share of traffic, so quote the share, never the worst case. Diagnosing the slow mode took a second query, not a bigger sample: the 46 slow pulls were on **46 DISTINCT nodes, one each, and 36 of those nodes later served fast pulls** → first-pull-on-new-node, NOT image-GC eviction, which would repeat on the same node. **PARSING TRAP that produced a fake result:** `r'in (?:(\d+)m)?([\d.]+)m?s'` parses `283ms` as **283 seconds**, because the optional minutes group backtracks and `m?` eats the milli-`m` — the median came out 323 s instead of 0.323 s. **Always sanity-check a computed distribution against raw sample lines before publishing it.**

52. **Your own most CONFIDENT finding is the most dangerous one — a margin argument must be SIMULATED, and a package must be resolved to the import, before it blocks a PR.** Two instances, both caught only by the second lens or by an executable check. (a) **Wrong dependency binding:** the correctness lens filed a "blocking" finding with a reproduced wire command, a negative control, a pushed fix and a tracking task — all wrong, because it verified against the wrong *installed* library. The adversarial lens refuted it in one line by checking the import. **A negative control proves your test is load-bearing; it does NOT prove your premise is right** — both can be consistent with a wrong model of the dependency, so "read the source" must first resolve WHICH package the symbol binds to. (b) **Self-refuted margin argument:** a source-grounded blocking finding (a client's retry cadence exceeds a new rate window, so `for:` could never be satisfied) was **refuted by the lens's own offline simulation before anything was pushed**. The arithmetic was right and the conclusion was wrong, for two reasons prose could not hold at once — an effective rollup window one scrape interval wider than nominal, and N concurrent senders sharing one counter (see `learnings-observability.md`). **When a finding rests on a timing margin, do not ship the arithmetic: simulate it, sweep the unknown phase, and add controls.** (c) **A refuted finding is still worth reporting** — in (b) the PR's *stated mechanism* was wrong even though its *conclusion* was right, and a wrong stated mechanism is what the next person optimises against. File it as a PR-body correction, not as nothing. **Corollary: never skip posting the adversarial lens because your own pass looks conclusive — conclusive is exactly when it is most dangerous.**

53. **A hand-rolled test double that IGNORES the query it is handed makes every assertion downstream of that query structurally blind — and the fix is a behavioural assertion against a real DB, not a compiled-query capture.** On one PR a `_FakeSession.execute(_query)` returned fixed rows regardless of its argument, so deleting the tenant-scoping `.where(<Model>.<scope_column> == <scope>)` from a revision lookup left the suite **17/17 green** while the PR body advertised per-tenant scoping as a guarantee. The Kubernetes half of that same guarantee was structurally enforced and mutation-proven; only the DB half was unguarded, which is the trap — **a partially-proven invariant reads as fully proven.** Two things generalise: (a) **the reviewer's suggested fix was to capture the compiled query; prefer asserting the BEHAVIOUR instead** — give a second tenant its own row and require that its uuid does NOT resolve, which survives a refactor of *how* the filter is expressed, whereas a query-shape assertion breaks on a rewrite that is still correct; (b) **the mutation proof must report which OTHER tests stayed green** — here seven pre-existing tests passing while only the new one failed (`[(2, 1), (1, 1)] == [(1, 1)]`, the other tenant's revision id leaking in) is what actually demonstrates the pre-existing blindness. Scan for this smell whenever a fake's method signature has an underscore-prefixed parameter (`_query`, `_sql`, `_stmt`): the underscore is the author admitting the argument is dropped.

54. **"Silent all-zeros on the wrong identifier" is a correctness bug, not a docs bug — when two lookup keys are distinct columns of a row that EXISTS, validate the key rather than documenting it.** On one endpoint a single path parameter fed both a Kubernetes label selector and a DB filter on a *different* column, so passing the display-name column instead of the key column matched nothing in either and returned a **200 with every count zero** — indistinguishable from a healthy idle workload. Both review lenses graded it a naming/doc issue and suggested a clearer parameter `description=`. **That is insufficient: a docstring does not make a wrong identifier observable at the call site — the caller still gets a plausible zero.** Validating the key against its table and returning 404 costs one query and makes the failure loud; in-repo precedent for exactly that already existed on a sibling route. Take the doc fix too, but do not let it substitute. **Test it DB-backed**, because the whole point is that both columns belong to a row that exists — a mocked backend cannot distinguish "wrong key" from "absent row", so it cannot show the foot-gun. Negative control: removing the validation fails the test with `assert 200 == 404`, which is the silent-zeros path itself.

55. **A two-lens review pays for itself in three distinct ways, and the SEVERITY SPLIT is the normal output rather than a failure.** Clearest evidence to date, from one PR. **(1) CONVERGENCE AS CONFIRMATION:** both lenses independently derived the *same* mutation (drop an environment argument at a cap call site) and measured the *identical* survival count (176 passed). Neither saw the other's work. **When two different models land on the same mutation with the same number, the finding needs no further defence — ship the fix.** **(2) DIVERGENCE AS COVERAGE:** the correctness lens swept every RENDERER exhaustively and proved the change complete — and was still **structurally blind** to the PERSISTENCE paths (#56). The adversarial lens found those because its brief is *"break it"*, which pushes past *"is the new code right"* to *"what does the new code not reach"*. **The correctness framing audits the DIFF; the adversarial framing audits the SYSTEM AROUND the diff.** **(3) SEVERITY SPLITS:** the adversarial lens returned BLOCK on four findings; on adjudication **one** was real-and-fixed, **two** were valid-but-pre-existing-or-by-design (follow-ups), and **one** was unreachable in production. ⚠️ **The adversarial lens systematically OVER-RATES severity because it constructs objects directly, bypassing the factory/validator that real traffic must pass** — always re-check an adversarial repro by asking *"can any production entry point actually construct this?"*, and ground the refutation **on the PARENT commit**: a "regression" that the factory already did pre-PR is not a regression. **Post both lenses verbatim, adjudicate in the summary, let the human decide — do not silently reconcile.**

56. **For any change to a RENDERER in a system that PERSISTS what it renders, the call-site sweep is NECESSARY BUT NOT SUFFICIENT — the fix is not retroactive and reviewing only the render path misses it.** Two persistence paths re-apply **stored** output without re-rendering. **(a) ROLLBACK:** a rollback that re-applies a stored manifest body verbatim (rewriting only an identity field) restores the **old** values indefinitely — and this is often **deliberate** ("applied as stored"), so "normalize on rollback" is a debatable fix, not an obvious one: re-rendering would mean rollback no longer restores what you rolled back to. **(b) EXISTING OBJECTS:** when a child object holds only a *reference* to the rendered parent, every already-deployed parent keeps its old values until that unit is redeployed — and if redeploy is a manual `workflow_dispatch`, production **does not self-heal**. **Three questions to add to the review: (i) what re-applies stored output; (ii) is there a migration or reconciliation for live objects; (iii) does rollback re-render?** Then check whether the PR body states the impact as **immediate** when it is actually **progressive-on-redeploy** — that is a claims defect worth correcting even when no code changes.

57. **For every DEFAULTED parameter that alters behaviour, assert it through the RENDERED OUTPUT at a NON-DEFAULT value — unit tests that pass the argument EXPLICITLY leave the CALL SITE's argument-passing completely untested.** The mutation that exposes it is *"drop the argument at the call site so it falls back to the default"*. Measured: that mutation left **all 176 tests passing** while a rendered limit silently fell from 2 CPU / 8 Gi to 1.5 / 5 Gi, because every existing render test ran at the default value. ⚠️ **ASYMMETRIC COVERAGE IS THE TELL** — the *same* mutation at the sibling call site (a routing selector on the same builder) was caught by 2 failures, and the asymmetry is what pointed at the gap. Fix by rendering at a non-default value and asserting both the capped field and the derived env var.

58. **Derive mutations from the SPEC, not from the test ASSERTIONS — an assertion-derived set is blind exactly where the author was.** On one PR the author claimed 7/7 negative controls; rebuilding the set from *what the endpoint is supposed to guarantee* produced **20 mutations, 17 caught / 3 escaped** — and all three escapes (a DB-scoping `WHERE`, a duplicate-key `ORDER BY` tie-break, a falsy-vs-`None` filter) were invisible to the author's set. **Byte-change-gate every mutation (`cmp` the file before and after) so a no-op mutation cannot re-report the clean baseline as "caught".**

59. **A "fails closed via a uniqueness exception" argument must be verified across EVERY PRODUCER of the identifier, not just the table you queried — this is the single highest-yield question to ask a correctness lens's reasoning.** On one PR the correctness lens explicitly reasoned a cross-kind name collision away as *"fails closed"*; the adversarial lens found it real, because the correctness lens had only considered **same-table** collisions and never asked whether **other kinds** share the name space. When a lookup is claimed safe because an ORM raises on multiple matches, the claim rests on an assumption about who else can mint that identifier.

60. **An "at most N" concurrency assertion whose test only proves the peak REACHED the cap is VACUOUS — it passes under an unbounded `gather`.** Mechanism: if the fake work releases as soon as in-flight hits the cap, the first N arrivals trip the release and exit **before** the rest have piled up, so the observed peak lands on N either way. **FIX: once the cap is reached, PARK the whole first wave (`await asyncio.sleep(~50 ms)`) BEFORE releasing**, so every remaining target has time to accumulate if nothing stops it. Then unbounded peaks at the batch size and sequential peaks at 1 — a genuinely **two-sided** control. **Choose `batch_size = cap*2 + 2`** so the two failure modes give visibly different numbers. The passing direction stays timing-independent (a semaphore cannot be exceeded regardless of scheduling); only the *control* run is timing-sensitive, and it is generous. **GENERAL RULE: for any "at most N" assertion the negative control must be the OVER-limit mutation, and you must RUN it** — reasoning about which way an async scheduler falls is exactly where this goes wrong.

61. **Prove "one query, not N" with a STATEMENT-COUNT EQUALITY across two row counts, never an absolute number.** Attach a `before_cursor_execute` listener to the test engine's `sync_engine` inside a `@contextmanager`, run the call with 1 row and then with 5, and assert the two counts are **EQUAL**. Do not pin an absolute count — the listing legitimately runs other queries, and pinning the number breaks on any unrelated addition. The equality is two-sided by construction: an N+1 implementation gives 3 vs 7. ⚠️ **RUN the negative control rather than reasoning about it** — replacing the join with a per-row lookup failed with `assert 7 == 3`, while the sibling test that merely asserts the joined value **appears** still passed. **That is the whole point: a presence test cannot catch an N+1.** (The listener signature must be `(_conn, _cursor, statement, *_rest)` or `ruff` flags `PLR0913` plus five unused-argument findings.)

62. **Proving "no authorization behaviour changed" when adding members to an enum that GATES AUTH is not a diff question — it is a "who ITERATES the whole enum" question.** Grep `'in <Enum>|set(<Enum>)|list(<Enum>)|<Enum>.__members__'`. If the only whole-enum consumers are an import-time completeness check and a seeding table, and every other reference is to a **named member**, new members are **provably inert** for existing code paths. **But state the visible non-authorization change explicitly in the PR body**: if the catalog is served from the DB, a seeded or migrated entry **does** become newly selectable in an admin picker. Generalises to any catalog enum behind an admin UI.

63. **Four guard failures that recur in RESIZE / CAP / DEADLINE code, all found by adversarial repro rather than reading.** **(1) A fleet ceiling must gate INCREASES ONLY.** Enforcing it on decreases rejects the exact cleanup action the design relies on, precisely when the fleet is already over cap — i.e. when scaling down matters most. **(2) A ceiling implemented as LIST → sum → compare → PATCH across separate objects is TOCTOU.** With `total = cap-1` and two objects at 1, two concurrent `target=2` calls both project exactly `cap`, both patch, and the final total is `cap+1`. A strict shared cap needs a **distributed** per-scope critical section plus a concurrent negative test — an in-process lock is insufficient across replicas. **(3) Put the read-compute-compare guard INSIDE the branch that can act on it.** Computing a cluster-wide LIST *above* the `is_increase` test makes every **decrease** pay for a fleet-wide LIST it discards — and decreases are the automated path that runs at volume. **(4) A polling deadline must wrap EACH individual blocking call** in a timeout bounded by `(remaining, small_floor)`; checking the deadline only *between* calls does not bound a single stalled call. ⚠️ **And a cross-package timeout "contract test" that COPIES the server default into a test constant is NOT a drift guard** — changing the real budget left the test green. Contract tests must read **both** authoritative definitions or stop claiming drift protection.

64. **Assert a SKIPPED call against the MOCK, not the status code — and point a manifest test at the real apply path, not a fixture it builds itself.** A 200 passes whether or not the expensive listing ran; the decrease test must assert `totals_mock.assert_not_awaited()`, and keep the fake allocation above the cap so a regression trips the cap loudly instead of silently. Separately, a test that constructs its own model and serialises it **tests the fixture, not production**: repointing it at the genuine render → `model_dump(exclude_none=True)` → apply chain made it fail under **both** mutations (drop `exclude_none`; give the status field a non-`None` default), neither of which the fixture-based version caught.

65. **When a multi-step destructive operation fails PART-WAY, a binary `succeeded|failed` status vocabulary LIES to the operator — and the UI faithfully renders the lie.** One delete path removes the live resource **before** the database row; if the DB delete raises, the bulk endpoint returns `status=failed` while the resource is **already destroyed** and the user disconnected. An operator reads "Failed" as "nothing happened" and retries or escalates on a false premise. **The status vocabulary needs a partial signal, and the remedy belongs in the BACKEND, not the UI.** (Retry was at least idempotent there: the row survives and the second resource delete swallows not-found.)

66. **Prefer a STATE-shaped status literal over an ACTION-shaped one — state survives idempotency where action does not.** `deleted` is true whether this call removed the object or it was already absent; `refreshed` **asserts work that never happened**, and it does not sit alongside siblings like `not_found` / `failed`. Related API-shape call from the same review: **a bulk POST beat DELETE-with-body** — RFC 9110 §9.3.5 gives a DELETE body no semantics, and the call crossed two proxies that may strip it. ✅ **Renaming a wire enum consumed by TypeScript is unusually safe: `tsc` TS2367 makes a stale literal a COMPILE ERROR rather than a silently-always-false filter** — rely on that, plus a grouping regression test, and keep the *UI's* verb unchanged if users know it by that name; only the upstream path and wire literal need to move.

67. **When a COUNTING or enrichment field is expensive PER ROW, do not hang it off a list endpoint — build a SIBLING that CANNOT be called in bulk.** A list endpoint that is inherently multi-entity (repeated or comma-separated ids, a `latest_only` sweep across everything, a large page limit) turns one count field into *one expensive backend call per entity per page render* — the fan-out reviewers veto as an abuse vector — while narrowing the list endpoint breaks existing callers. **An endpoint that REQUIRES the scoping parameter makes single-entity scope STRUCTURAL rather than conventional: no request can be constructed that counts more than one.** Two shape details worth copying: keep **named leftover buckets** rather than one "other" — two buckets with *different diagnoses* ("not yet stamped" vs "stamped but unresolvable") plus the matched set, and assert that the three always **sum** to the total, which is the invariant the tests hang on; and **cache the expensive DERIVED census, not the finished response**, under a **VERSIONED key prefix**, so the cheap mapping stays fresh and a deploy that changes the cached model's shape does not read the old shape back and 500 for a whole TTL.

68. **Preserve EPISTEMIC UNKNOWN through derived booleans and aggregates — mapping "unknown" onto `false` turns "we do not know" into the FALSE CLAIM "it is not".** An operator UI that collapsed *unstamped*, *unknown* and *resolved-but-older* into a single `onTarget: false` rendered all three as "Not this revision", and depressed the confirmed counts in the header. **Use `true | false | unknown`, or separate confirmed and unknown counts — never a boolean — whenever absence of evidence is distinct from evidence of absence.** The same rule decides read-failure rendering: when a dependent fetch fails, **DROP the column rather than rendering zeros**, because a zero from a failed fetch is indistinguishable from a real zero, and `null` must mean *fetch failed*, not *zero*.

69. **A CONTROLLED selectable table that derives header state from CURRENT rows but derives the action count and request body from the raw selected set SILENTLY ACTS ON ROWS THAT ARE NO LONGER RENDERED.** After a re-list, a removed or expired row stays in the set forever: the destructive button reads "act on 1 item" with **zero rows checked**, and submits that stale identifier — which, when identifiers are short and reusable, can address a **different live object**. **Fix: intersect the selection with the rendered rows BEFORE counting or submitting.** Mutation proof: re-render with replacement rows and assert no removed id is submitted; test select-all followed by **both** additions and removals.

70. **A hand-rolled test double that ignores the query is one blindness; a test double that AGREES WITH THE BUG is another — and only the second survives a reviewer reading the test.** A cache test whose fake was `side_effect=lambda key, value, _ttl: store[key] = value` **transcribed the call it was asserting**, so eight green tests and green CI hid a guaranteed 500 from the real client. **Fix pattern: make the double honour the REAL contract (reject what the server rejects), then prove it load-bearing by reinstating the bug and watching the test fail.** Applies to any hand-rolled mock of a third-party client. (Complements #53, the ignores-the-query case.)

71. **A THRESHOLD backtest whose CONTROL SET sits below the gate's evaluation floor is a VACUOUS PASS that reads as a clean negative control.** Tuning two volume gates, the five "must pass clean" reference PRs were all small enough that **any** small-diff allowance passed them trivially — the matrix would have been green for a gate with **no discriminating power at all**. **FIX that made the tuning real: pull ten MORE samples IN THE EVALUATED REGIME before choosing any constant**; that extended control is what produced the working model, and the original five contributed almost no information. **GENERAL RULE: before reporting a backtest matrix, check the CONTROL SET's distribution against the gate's ACTIVE RANGE — if the controls cluster where the gate is inert, the matrix is decoration.** **Corollary:** when the arithmetic separating a must-flag case from a must-pass case leaves a **sub-1 % margin** (5 lines on 620), that is **overfitting a constant to one sample, not a threshold** — report the negative result and let a different gate catch that case.

72. **When a review REVERTS part of a PR, re-read the PR's own METADATA against the NEW diff — and after a squash merge the title IS the commit subject in the base branch's history.** One revert left an expression byte-identical to the base, collapsing the net diff from "two changes" to one, so the title now misdescribed what would land. **Checks after any partial revert: (a) does the TITLE describe the NET diff versus the base, not the PR's internal history; (b) does the BODY still describe the shipped values; (c) did the revert leave an earlier justification section as DEAD PROSE?** ⚠️ **Second habit, from the same PR: when a review falsifies a claim in a PR body, do NOT quietly DELETE it — mark it as a correction IN PLACE ("Correction — X does not reproduce, here is why").** The deleted version loses the reason the original reviewer was misled, which is often the reusable part, and a reader of the merged PR cannot tell an unexamined claim from a retracted one. **Applies to design docs too.**

73. **A PR-body claim about a MEASUREMENT is a review target in its own right — and the mechanism can be wrong while the conclusion is right.** On one PR the correctness lens built a source-grounded blocking finding, then **refuted it with its own executable simulation before pushing anything**: the arithmetic was right and the conclusion was wrong, for two reasons a prose argument could not hold at once. **When a finding rests on a TIMING MARGIN, do not ship the arithmetic — SIMULATE it, sweep the unknown phase, and add controls.** An offline simulator is cheap and is the only thing that catches a margin argument that is directionally right and quantitatively dead. ⚠️ **And the finding still had value after refutation:** the PR body's **stated mechanism** was wrong even though its conclusion was right, **and a wrong stated mechanism is what the next person optimises against**. Report it as a **body correction**, not as nothing.
